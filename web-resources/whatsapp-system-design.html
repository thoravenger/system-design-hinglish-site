WhatsApp System Design — WebSocket, Connection Registry, Presence

1:1 chat at 500M DAU: kyun WebSocket (polling nahi), chat servers ka service discovery, Postgres + Cassandra + Redis ka data model aur presence server.

Scale ka andaaza

Article ke assumptions: ~1B registered users, ~500M DAU, peak pe ~50M concurrent connections. Matlab problem "message bhejna" nahi — itne saare long-lived connections sambhalna aur offline users ke liye message rakhna hai.

Polling vs long polling vs WebSocket

OptionDikkat / fayda
Short pollingHar kuch second "naya message?" — bandwidth waste + latency (just miss kiya to agle poll tak wait).
Long pollingBetter, lekin har message ke baad naya request, timeouts, server pe pending requests ka bojh.
WebSocketEk persistent, full-duplex connection — server turant push kar sakta hai. Chat ke liye default choice.

High-level components

flowchart LR
  A[Phone A] -- WSS --> LB[Load balancer]
  B[Phone B] -- WSS --> LB
  LB --> CS1[Chat server 1]
  LB --> CS2[Chat server 2]
  CS1 <--> REG[(Redis: user to server registry)]
  CS2 <--> REG
  CS1 --> MS[Message storage service]
  MS --> CAS[(Cassandra: messages)]
  CS1 --> INB[(Redis: offline inbox)]
  CS1 --> PR[Presence server]
  • Client khud bhi smart hai: local message store, failed sends retry, persistent connection.
  • Connection registry (Redis): "user X abhi kis chat server pe connected hai" — A ka server isi se B ka server dhoondh ke message forward karta hai.
  • Service discovery: chat servers crash/deploy/scale hote rehte hain, hardcoded IPs nahi chalenge. Servers registry mein heartbeat ke saath register hote hain; LB aur doosri services wahi se healthy list lete hain.
  • Offline inbox (Redis): B offline hai to message inbox mein; B reconnect kare to drain karo.

Data model — har data ke liye sahi store

DataStoreKyun
Users, GroupsSQL (PostgreSQL)Relational, kam writes, strong consistency
MessagesCassandraBahut zyada writes, (chat_id, time) se range reads, horizontal scale
Connection registry, inboxRedisFast, ephemeral, TTL

WebSocket handshake mein client pehla frame auth type ka bhejta hai (user_id, JWT, device_id, platform) aur server session_id lauta deta hai — multi-device support ke liye device_id zaroori.

Interview mein kaise bolein

Pehle numbers (500M DAU, 50M concurrent) bolo, phir kaho "connections hi asli problem hai, isliye WebSocket + stateless-ish chat servers + Redis connection registry". Message flow: A → chat server → registry lookup → B ka server → B; B offline → inbox + push notification. Storage split (Postgres / Cassandra / Redis) ka reason ek line mein do.

Key Takeaways

  • Chat = long-lived connections ki problem; WebSocket default.
  • User→server mapping Redis registry mein, servers service discovery se.
  • Messages Cassandra (write-heavy), users/groups SQL, inbox/presence Redis.
  • Offline user ke liye inbox + push; reconnect pe drain.
