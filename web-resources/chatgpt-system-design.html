ChatGPT System Design — SSE Streaming, Message Service, Single-Primary Postgres

"Bas OpenAI API call karke messages save karo" kyun kaafi nahi: 1B WAU, first token <2s, SSE (WebSocket nahi) streaming, client → LB → gateway → message service ka open connection, aur 90% reads ke liye single primary + 20+ read replicas.

Streaming: SSE, WebSocket nahi

Wait for full responseStream tokens

Article ka point: bade AI chat products Server-Sent Events use karte hain — plain HTTP pe, browser ka built-in EventSource, auto-reconnect, server→client one-way (jo yahan chahiye), WebSocket se kam overhead aur debug easy. Frontend: React + EventSource + Zustand/Redux + optimistic user message + rate-limit/network error handling.

Architecture

flowchart LR
  B[Browser / mobile] -- SSE --> LB[Load balancer]
  LB --> GW[API gateway: TLS, routing]
  GW --> AUTH[Auth service: JWT]
  GW --> MSG[Message service: orchestrator]
  MSG --> CONV[Conversation service]
  CONV --> PG[(Postgres primary)]
  PG --> RR[(20+ read replicas, multi-region)]
  MSG --> RL[Rate limiter: req + tokens]
  MSG --> INF[Model inference: GPU clusters, multi-cloud]
  INF -- tokens --> MSG

Response kaise wapas aata hai: HTTP connection Browser → LB → Gateway → Message service tak khula rehta hai; message service har token response stream pe likhti hai aur wo usi raaste ulta browser tak jaata hai. Stream khatam → poora assistant message DB mein save.

Key decisions

  • Single-primary PostgreSQL (sharded nahi): workload ~90% reads; writes ek primary pe, reads 20+ replicas across regions. Trade-off: single-writer bottleneck — isliye app-level optimisations, write batching, caching. (Article OpenAI ke public Postgres scaling posts ka reference deta hai.)
  • Multi-cloud compute: Azure primary + doosre providers — GPU capacity aur single-vendor risk.
  • Token-based rate limiting: sirf requests gin-na kaafi nahi; ek request 10 tokens, doosri 10K.

Interview mein kaise bolein

"Client SSE se stream leta hai — first token <2s target. Gateway → message service orchestrator: auth, token-aware rate limit, conversation history fetch (read replicas), model call, tokens stream back, end pe persist. DB: read-heavy, isliye single primary + many replicas; sharding tab jab writes limit cross karein." SSE vs WebSocket ka reason zaroor do.

Key Takeaways

  • Streaming UX = SSE (one-way, HTTP, auto-reconnect).
  • Connection poore path pe open; tokens same path se wapas.
  • Message service = orchestrator (auth, limits, history, model, persist).
  • Read-heavy → single primary + many replicas.
  • Rate limit requests aur tokens dono pe.
