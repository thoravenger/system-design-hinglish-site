Real-Time Presence Platform — Online/Offline Status at Scale

Requirements

  • Connections ko user ka online/offline status real-time dikhe.
  • Offline user ka last active timestamp.
  • Scalable, low latency, highly available — status thoda stale ho sakta hai, par flip-flop nahi karna chahiye.

Heartbeat — dil ki dhadkan

Client har kuch second ek chhota heartbeat bhejta hai. Article ka point: heartbeat halka aur connectionless hona chahiye — UDP natural fit; ya phir jo SSE/WebSocket connection pehle se khula hai, usi ko reuse karo (extra network hops nahi).

Status kahan rakhein

SET presence:john  "online|1730000000"  EX 30   # har heartbeat pe TTL refresh
# key expire = 30s tak koi heartbeat nahi = offline (last seen = stored timestamp)

Redis key-value + TTL perfect: heartbeat aata rahe to key zinda, ruk jaaye to apne aap expire. Prototype Redis Sets se bhi bana sakte ho (online users ka set), par TTL wala per-user key zyada clean hai.

Online → offline kaise pata chale

sequenceDiagram
  participant C as Client
  participant RT as Real-time platform
  participant P as Presence service
  participant R as Redis
  C->>RT: SSE connect
  RT->>P: online event
  P->>R: SET status + TTL
  loop every few seconds
    C->>RT: heartbeat
    RT->>R: TTL refresh
  end
  Note over C,RT: Connection toota
  P->>R: delayed trigger: key expired?
  P->>RT: broadcast offline + last seen
  • Delayed trigger: disconnect hote hi offline mat bolo — thoda ruk ke check karo ki record expire hua ya nahi.
  • Jittery connections: train/lift mein network baar-baar gaya-aaya → status flicker. Solution: debounce — chhote disconnects ignore, sign-off aur timeout ko same treat karo.
  • Publish/subscribe: user A ke friends A ke presence channel pe subscribe; A ka status badla to sirf unhi ko push.
  • Cross-DC: local DC ka dispatcher status change doosre DCs ke dispatchers ko bhejta hai.

Pub-sub server kyun nahi bas?

Generic message bus (Kafka jaisa) ke saath article ke concerns: guaranteed delivery nahi (presence ke liye), pull-based consumers se latency, aur operational complexity. Isliye dedicated real-time platform + Redis.

Reliability: Redis node gira to sab "offline" na dikhne lage — replication + persistence (AOF/RDB) rakho.

Interview mein kaise bolein

"Heartbeat + TTL" se shuru karo: "Har client existing connection pe heartbeat bhejta hai, Redis mein status key ka TTL refresh hota hai. TTL expire = offline, aur stored timestamp = last seen. Flicker rokne ke liye debounce/delayed trigger, aur status change sirf subscribers (friends) ko pub-sub se push." Scale: 100M online users × chhota key = memory estimate karke dikhao.

Key Takeaways

  • Presence = heartbeat + TTL; expire hona hi offline signal.
  • Existing SSE/WebSocket connection reuse karo — kam hops.
  • Debounce/delayed trigger se flapping status band.
  • Status change sirf interested subscribers ko fan-out.
  • Redis replicate + persist, warna failover pe sab offline dikhenge.
