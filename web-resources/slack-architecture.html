Slack Architecture — Web API + Real-time API, Snapshot, Message Ordering

Workspace → channels → messages. HTTP web API + WebSocket real-time API, login pe workspace snapshot, cursor pagination, message ordering aur thundering herd se bachav.

Scope (article ke numbers)

  • 10M DAU, ~7M concurrent connected users, read:write = 10:1.
  • Channel mein max 10K users, workspace mein max 200K. 1:1 + group chat, history persist, media files, presence.
  • Traffic office hours mein (9–17h), peak dopahar ~11–14h — capacity isi peak ke hisaab se.

Do tarah ki API

Web API (HTTP)Real-time API (WebSocket)
KaamMessage post karna, login, channel banana, history fetchMessage delivery, typing indicator, presence
KyunReliable, cache/LB-friendly, debug easyLow-latency, full-duplex push

Interesting point: message bhejna HTTP POST se ho sakta hai (WebSocket ke bina bhi), aur deliver WebSocket se. Typing indicator jaise transient events seedha WebSocket pe — DB tak jaate hi nahi.

Login pe "snapshot"

Client login kare to server poore workspace ka snapshot (channels, members, unread) deta hai. Bade workspace mein ye bhaari hai — isliye client last sync ka timestamp rakhta hai aur incremental updates leta hai; ek in-memory/edge snapshot service (article mein Flannel ka zikr) load kam karti hai.

Pagination: offset vs cursor

LIMIT 20 OFFSET 400 — simple, page number jumpWHERE created_at < :cursor LIMIT 20 — index pe seedha seek

SELECT * FROM chat WHERE channel_id = ? ORDER BY created_at DESC LIMIT 20;
-- index: (channel_id, created_at)

Deep dive points

  • Message ordering: server timestamp clock skew se galat, client timestamp pe bharosa nahi. Har channel ke andar total order chahiye → per-channel sequence / Snowflake-type sortable IDs, aur atomic broadcast ki requirement (sabko same order).
  • Storage: relational MySQL, scale ke liye Vitess se shard (by workspace/channel).
  • Thundering herd: outage ke baad poori org ek saath reconnect → reconnect mein jitter + exponential backoff, snapshot cache.
  • Fault tolerance: data center fail ho to users ko "drain" karke doosre DC pe; DB write errors ke liye dead letter queue.
  • Media S3 + CDN; clients Electron (desktop), React (web), React Native/native (mobile).
Interview mein kaise bolein

"Main do APIs rakhunga: HTTP web API state-changing kaam ke liye, aur WebSocket real-time delivery/presence/typing ke liye. Messages MySQL mein (channel_id, created_at) index ke saath, cursor pagination; scale pe Vitess sharding. Ordering per-channel sequence se, aur reconnect storms ke liye jitter + backoff." Bonus: Slack vs WhatsApp — Slack mein history server pe permanent aur search important; WhatsApp mein device-centric delivery.

Key Takeaways

  • HTTP for commands, WebSocket for real-time push — dono ka role alag.
  • Login snapshot + incremental sync se bade workspaces fast load.
  • Chat history ke liye cursor pagination, offset nahi.
  • Ordering per channel; clock skew ke wajah se raw timestamps pe bharosa nahi.
  • Reconnect storm (thundering herd) ka ilaaj: jitter, backoff, cache.
