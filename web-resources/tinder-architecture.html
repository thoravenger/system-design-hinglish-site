Profile banana

  • User data key-value DB (DynamoDB) mein; DynamoDB Streams se changes doosri jagah (location index etc.) auto push.
  • Profile update message queue mein → location index update.
  • Public API ek API Gateway ke peeche (auth, security rules); andar ~500 microservices, service mesh se communication.

Nearby log — S2 se geo-sharding

Sirf lat/long se "paas ke log" dhundhna mehenga. Duniya ko barabar grids mein baanto to samundar ke grids khaali aur Mumbai/Delhi ke grids overloaded — hot shard. Isliye Google ka S2: square-shaped hierarchical cells, har cell ka 64-bit ID (Hilbert curve order — paas wali cells ke IDs bhi paas). Paas rehne wale users same DB shard mein → recommendation query ek-do shards pe.

Passport (location change) — ordering bug

Location badli = naye index mein add + purane se remove — ye atomic nahi. User ne jaldi se A→B→A kiya to operations ulte order mein chal ke galat location pe atak sakte hain. Fix: same user ka data same Kafka partition mein → FIFO order; consumer partition pe lock leta hai.

Hot shards ka ilaaj

  • Shard load = unique users count. Ek shard ke users usually ek time-zone mein → sab ka peak ek saath.
  • Isliye kai shards randomly ek physical server pe — alag time-zones mix, load average out.
  • Reads zyada → Redis cache-aside (read hot shard solved); writes ke liye rate limiting + exponential backoff.
  • Data stores ko periodically sync — ~26M matches/day scale.
Interview mein kaise bolein

"Location ko S2 cells se index aur shard karunga taaki paas ke users ek shard mein hon; shards ko time-zones mix karke physical servers pe randomly place karunga. Swipes stream mein, match workers likes cache check karke WebSocket se notify. Location updates per-user Kafka partition se ordered." Geohash/H3 compare karna bonus.

Key Takeaways

  • Uniform grid = hot shards; hierarchical cells (S2) better.
  • Per-user Kafka partition = per-user ordering.
  • Swipes async stream + match workers + WebSocket.
  • Multi-shard per server, time-zone mix se balance.
