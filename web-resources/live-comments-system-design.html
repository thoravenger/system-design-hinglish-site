Live Comments System Design — SSE, Pub-Sub, Gateway Fan-out

Facebook Live jaise video pe real-time comments: SSE se subscribe, Kafka/Redis pub-sub ke options, actor-model gateway servers, multi-DC fan-out aur HyperLogLog se comment count.

Problem shape

Read-heavy hai: comment likhne wale kam, dekhne wale bahut. Ek popular live video pe lakhon viewers — har naya comment sab tak ~sub-second mein. Eventual consistency chalega (do viewers ko comment 200ms aage-peeche dikhe to koi baat nahi).

API ka shape

  • Subscribe: PUT /videos/:id/subscriptions with Accept: text/event-stream → server-sent events stream khulta hai.
  • Unsubscribe: DELETE /videos/:id/subscriptions/:sub-id.
  • Publish: POST /videos/:id/comments — normal HTTP.

SSE kyun? Data mostly server → client ek taraf jaata hai; SSE plain HTTP pe chalta hai, auto-reconnect browser deta hai. Publish alag HTTP call.

Architecture

flowchart LR
  PUB[Publisher] -->|POST comment| API[Comment service]
  API --> DB[(Cassandra: comments)]
  API --> D[Dispatcher]
  D -->|sirf un gateways ko jinke viewers is video pe| G1[Gateway 1]
  D --> G2[Gateway 2]
  G1 -- SSE --> V1[Viewers]
  G2 -- SSE --> V2[Viewers]
  G1 -. video to gateway subscriptions .-> SUB[(In-memory subscription store)]
  • Gateway servers SSE connections hold karte hain. Andar actor model: har connection ek halka actor — lakhon concurrent (article: ~100K connections per gateway).
  • Subscription store: kaunsa gateway kis video ke viewers rakhta hai. Dispatcher sirf relevant gateways ko bhejta hai — har gateway ko har comment broadcast karna waste hai.
  • Peak load pe single dispatcher bottleneck → dispatcher ko scale/partition karo (by video_id).

Pub-sub options compare

OptionPlusMinus
KafkaDurable, replay, scaleLakhon videos = lakhon topics/partitions nahi chalte; pull-based latency
Redis Pub/SubBahut fast, channel per videoFire-and-forget — subscriber offline to message gaya
Redis StreamsAppend-only log, consumer groups, thoda durableMemory cost, ops

Multi-DC aur extras

  • GeoDNS se user paas wale DC pe. Comment local DC mein likho, doosre DCs ke dispatchers ko forward (cross-DC publish) — "write locally, fan-out globally".
  • Total comment count: exact count expensive; Redis HyperLogLog se approximate unique count, bahut kam memory.
  • Reliability: reconnect mein jitter, backpressure + exponential backoff, rate limiter spam pe.
  • Cassandra durability ke liye; purane comments cold storage mein.
Interview mein kaise bolein

"Read-heavy fan-out problem hai. Viewers SSE se gateway servers pe subscribe karte hain; ek in-memory subscription store video→gateways map rakhta hai. Publish HTTP POST se, comment Cassandra mein aur dispatcher sirf relevant gateways ko push karta hai. Multi-region mein local write + cross-DC forward." Phir pub-sub choice (Redis vs Kafka) ka trade-off do.

Key Takeaways

  • Ek-taraf push ke liye SSE, publish ke liye normal HTTP.
  • Gateway pe actor model = lakhon halke connections.
  • Dispatcher sirf un gateways ko bheje jinke paas us video ke viewers hain.
  • Redis Pub/Sub fast par lossy; Kafka durable par per-video topics ke liye bhaari.
  • Approx counts ke liye HyperLogLog.
