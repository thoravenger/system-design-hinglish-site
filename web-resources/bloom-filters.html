Bloom Filter — Kam Memory mein "Shayad Haan / Pakka Nahi"

Bit array + k hash functions: add aur membership check O(k), false positives possible par false negatives kabhi nahi, delete nahi hota — counting, scalable aur striped variants, aur real-world use (LSM trees, URL dedup).

Problem

Chhote data set mein HashSet se "ye item hai ya nahi" turant pata chal jaata hai. Lekin billions items (crawled URLs, usernames, disk pe keys) ke liye poora set memory mein rakhna mehenga. Requirement: constant time, bahut kam memory, parallel insert/query, aur approximate answer chalega.

Kaise kaam karta hai

  • n bits ka array, sab 0.
  • Add: item ko k hash functions se hash karo, har output mod n → un k positions pe bit = 1.
  • Check: same k positions dekho — koi bhi 0 hai to pakka nahi; sab 1 hain to shayad haan.
flowchart LR
  I[item: red] --> H1[h1 mod 10 = 1]
  I --> H2[h2 mod 10 = 4]
  I --> H3[h3 mod 10 = 7]
  H1 --> B[bit array: 0 1 0 0 1 0 0 1 0 0]
  H2 --> B
  H3 --> B
  B --> Q{query: sab k bits 1?}
  Q -- koi 0 --> NO[Definitely NOT in set]
  Q -- sab 1 --> MAYBE[Maybe in set: verify with DB]

False positive kyun: doosre items ne milke wahi bits 1 kar di hon. False negative kabhi nahi, kyunki add kiye item ki bits kabhi 0 nahi hoti.

Complexity aur tuning

Value
Time (add / check)O(k) — kitne items pehle se hain usse independent; k lookups parallel
SpaceFixed bit array — items khud store nahi hote (privacy bonus)
False positive rate≈ (1 − e−kN/n)k; best k ≈ (n/N)·ln 2

Rule of thumb: ~10 bits per item → ~1% false positives (k ≈ 7). Accuracy depend karti hai: k, hash quality, n aur expected items N. Fast non-cryptographic hashes (MurmurHash, FNV-1a) use karo — MD5/SHA slow hain. Online "bloom filter calculator" se n aur k choose karo.

Limits

  • Delete nahi: ek bit kai items share karte hain, 0 karne se doosre items "gayab" ho jaayenge.
  • False positive rate zero nahi ho sakti.
  • Disk pe rakho to random access (random bit positions) — isliye memory mein rakhte hain.
  • Saturate hone pe rebalance nahi kar sakte (original items pata hi nahi).

Variants

VariantKya add karta hai
Counting Bloom filterHar bit ki jagah counter → delete possible (zyada memory)
Scalable Bloom filterBhar jaaye to upar naya, bada filter stack karo; query sab layers pe
Striped Bloom filter64-bit words ke shards, har shard ka apna mutex → high concurrency
Cuckoo / quotient filterSimilar kaam, delete support, kabhi better space

Real-world use

  • High-ingestion systems mein expensive disk seeks bachana: LSM-tree DBs (Cassandra, RocksDB, HBase) har SSTable ke liye Bloom filter — "is file mein key nahi hai" to disk read skip.
  • Crawler: URL pehle dekha? Shortener: short code taken? Username available?
  • Redis mein RedisBloom module — plain set ki tulna mein ~2% memory tak.
Interview mein kaise bolein

"Bloom filter ek bit array + k hash functions hai. Check pe koi bit 0 = definitely absent, sab 1 = maybe present → tab hi DB/disk pe jaao. False negatives nahi, false positives tunable (~10 bits/item ≈ 1%). Delete chahiye to counting Bloom filter." Phir use case: LSM tree mein SSTable reads skip karna — ye example interviewer ko pasand aata hai.

Key Takeaways

  • Bit array + k hashes; add/check O(k).
  • Pakka nahi / shayad haan — no false negatives.
  • ~10 bits/item ≈ 1% FP; best k ≈ (n/N) ln 2.
  • Delete ke liye counting BF; growth ke liye scalable BF.
  • Use: disk seeks bachana (LSM), URL/username dedup.
