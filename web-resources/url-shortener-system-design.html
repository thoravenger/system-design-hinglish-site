URL Shortener — KGS, Token Ranges, Cleanup & Analytics

Alex Xu wale chapter ke upar extra angles: PUT idempotent kyun, Key Generation Service ke 3 tareeke (random, hash, token range), lazy vs dedicated cleanup, archive aur analytics.

Chapter 08 se kya alag hai

Basic (hash vs base62, 301 vs 302, cache) Ch 08 mein hai. Ye article un cheezon pe zyada zor deta hai jo interview ke "deep dive" mein poochi jaati hain.

Requirements (thode extra)

  • Short URL predictable nahi hona chahiye (sequential IDs se competitors URLs guess kar lenge).
  • Custom alias, optional expiry, SEO-friendly, non-real-time analytics.
  • Scale: ~100M write DAU, ~100K read QPS; record ~2.5 KB, 5 saal retention.

API detail — PUT kyun?

Article shorten ke liye PUT /url use karta hai: PUT idempotent hai aur requirement hai long ↔ short ka 1-to-1 mapping — same long URL dobara bhejo to same short URL. Redirect GET /:short. Public API REST, andar ki services baad mein RPC (perf ke liye, par tight coupling).

Key Generation Service (KGS) — 3 tareeke

TareekaKaiseTrade-off
Random IDRandom function → base62Collision check DB pe; Bloom filter se sasta
Hash functionMD5/SHA(long URL) ke pehle 7 charsDedup free, par collisions + predictability
Token rangeCentral token service har app server ko range deta hai (e.g. 1M–2M); server local counter se IDs banata hai → base62No collision, no per-request coordination. Server crash = range ke kuch IDs waste (chalta hai)
flowchart LR
  TS[(Token service: ranges)] -->|range 1M-2M| S1[App server 1]
  TS -->|range 2M-3M| S2[App server 2]
  S1 -->|counter to base62| DB[(NoSQL: short to long)]
  S2 --> DB
  U[User GET short] --> CDN[Cache] -->|miss| DB

Concurrency: KGS jo IDs baant raha hai us data structure pe lock/semaphore — do clients ko same ID na mile.

Data store, cache, partitioning

  • URL table NoSQL (DynamoDB/MongoDB jaisa) — joins nahi, simple key lookup, flexible schema. Users table chhoti.
  • 80/20 rule: 20% URLs se 80% traffic → unhe cache karo.
  • Consistent hashing se partition; key = short URL.

Cleanup — expired links

  • Lazy removal: koi expired link khole tab delete karo aur 404 do. Sasta, par kabhi na khule links pade rehte hain.
  • Dedicated cleanup service: off-peak hours mein scan + delete (replica se padh ke).
  • TTL: DB ka built-in TTL (DynamoDB) — sabse kam code.
  • Archive: cold data sasti storage mein.

Analytics: redirect request ke headers (referrer, user-agent, IP → country) ko async pipeline mein bhejo; isi liye analytics chahiye to 302 (Ch 08 ka point).

Interview mein kaise bolein

"ID generation ke liye main token-range KGS lunga: har app server ke paas pre-allocated range, local counter, base62 encode — collisions zero aur hot path pe koi coordination nahi. Predictability chahiye kam to IDs ko shuffle/obfuscate." Phir cleanup (lazy + TTL) aur analytics ke liye 302 ka mention.

Key Takeaways

  • PUT idempotent = same long URL → same short URL.
  • Token range KGS: no collisions, no per-request lock.
  • Random/hash approach mein collision check + Bloom filter.
  • Expiry: lazy removal + TTL/cleanup job + archive.
  • Read-heavy: 80/20 cache, consistent hashing partitions.
