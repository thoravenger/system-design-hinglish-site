Service Discovery — Registry, Heartbeats, Client-side vs Server-side

Microservices mein instances aate-jaate rehte hain: hardcode/config/DNS/LB/registry approaches, register-heartbeat-deregister flow, client-side vs server-side discovery, self vs third-party registration aur ZooKeeper/Consul/Eureka/etcd compare.

Zaroorat kyun

Service A ko B call karna hai — par B ke instances autoscaling, deploys aur crashes se badalte rehte hain, IPs fixed nahi. Service discovery = kisi service provider ke abhi ke healthy instances ki list nikalna.

Requirements: service info ka CRUD, search, REST API, service-level health checks; aur NFR — high availability, kam CPU/memory, reliable, low latency.

Implement karne ke 5 tareeke

ApproachPlusMinus
Hardcode locationsTrivialError-prone, har change pe deploy, scale nahi
Config fileCode change nahiPhir bhi static; sync karna padta
DNSHar jagah availableTTL caching → stale IPs; dynamic instances ke liye slow, health checks weak
Load balancer per serviceClient simpleExtra hop, LB khud SPOF/bottleneck
Service registryDynamic, health-aware, metadataEk aur highly-available component chalana

Registry ka flow

sequenceDiagram
  participant P as Provider instance
  participant R as Service registry
  participant C as Consumer
  P->>R: PUT /services/:id register (IP, port, metadata)
  loop har kuch second
    P->>R: heartbeat
  end
  C->>R: GET /services/:id
  R-->>C: healthy instances list
  C->>P: request (round-robin / consistent hashing)
  P->>R: DELETE on graceful shutdown
  Note over R: heartbeat ruk gaya = instance hatao

Data model flexible rakho: service → instances (ip, port, status, last heartbeat) + key-value metadata (version, zone, tags) taaki nayi requirements bina schema change ke aa jaayein.

Client-side vs server-side discovery

Client-sideServer-side
Kaun dhoondta haiConsumer khud registry se list leta hai aur khud load-balance karta haiConsumer LB/router ko call karta hai; LB registry se instances leta hai
PlusEk hop kam, smart LB (consistent hashing, zone-aware)Client simple, language-agnostic — production mein common
MinusHar language mein client library; registry se couplingExtra hop; LB highly available hona chahiye
ExampleNetflix Eureka + client-side LBKubernetes Service, AWS ALB

Registration: self vs third-party

  • Self-registration: instance khud register/heartbeat/deregister — simple, par har service mein ye logic (coupling).
  • Third-party: alag registrar/agent (Kubernetes, Consul agent sidecar) platform se instances dekh ke register karta hai — services clean.

Tools compare

ToolModel
ZooKeeperZab consensus, filesystem-like API; ephemeral nodes session khatam hote hi gayab → auto deregister
etcdRaft, key-value + leases/watches (Kubernetes ka store)
ConsulAgents (har instance ke saath) + servers (Raft); health checks, DNS interface
EurekaREST server + client library; AP design — partition mein stale data dena behtar, registry down na ho

CP (ZooKeeper/etcd) vs AP (Eureka, ya CRDT-based eventually consistent registry) — discovery ke liye aksar thodi stale list chalegi, registry unavailable nahi.

Interview mein kaise bolein

"Main service registry lunga: instances register karte hain, heartbeat bhejte hain, TTL miss = remove. Production mein server-side discovery (Kubernetes Service / LB) kyunki clients simple rehte hain; latency-critical internal calls ke liye client-side with caching. Registry ko HA chahiye — Raft-based (etcd/Consul) ya AP (Eureka) — aur consumers last-known list cache karein taaki registry down ho to bhi chale."

Key Takeaways

  • Dynamic instances → registry + heartbeats, DNS/config kaafi nahi.
  • Register → heartbeat → deregister; heartbeat miss = evict.
  • Client-side (kam hop) vs server-side (simple clients).
  • Self vs third-party registration.
  • CP (ZooKeeper/etcd) vs AP (Eureka) — discovery mein availability zyada important.
