Airbnb / Hotel Booking — Double Booking Kaise Rokein

Booking.com scale ka hisaab (1.1B room-nights/year), search vs reservation ke alag NFRs, idempotency key, room-type × date inventory table aur strong consistency.

Asli problem

Do log ek hi room, ek hi dates pe ek saath "Book" dabayein — ek ko hi milna chahiye. Search thoda stale chal jaayega, booking kabhi nahi. Isliye do alag NFRs: search = high availability + low latency; reservation = strong consistency + high concurrency.

Back-of-envelope (article ki approach)

Room nights/year      ≈ 1.1B   (Booking Holdings 2024)
Avg stay              ≈ 2 nights  → ~550M bookings/year
Bookings/day          ≈ 550M / 365 ≈ 1.5M
Bookings/sec (avg)    ≈ 1.5M / 86,400 ≈ ~17–20 TPS (peak kai guna)
Visits/day            ≈ 517M/month / 30 ≈ 17M  → ~200 visits/sec
Pages/visit ≈ 7.5     → read QPS ~1.5K avg  → reads ≫ writes

Seekh: writes chhote hain, reads bade. Isliye search ko cache/replicas/search index pe daalo, aur reservation path ko simple aur correct rakho.

Architecture

Web/Mobile + CDN→API Gateway (auth, rate limit)→Hotel · Search · Reservation · Payment services→DB (reservation + inventory same DB)

Article ka point: na pure monolith, na 100 microservices — service boundaries rakho, par tightly coupled data (reservation + inventory) ek hi database mein, taaki ek transaction mein dono update ho sakein.

APIs

  • Admin: /v1/hotels, /v1/hotels/{id}/rooms CRUD.
  • Search: GET /v1/search?location&checkIn&checkOut&guests…
  • Reservation: POST /v1/reservations with idempotency key (reservationId frontend pe generate) — user 3 baar click kare to bhi ek hi booking.

Inventory table — double booking ka ilaaj

room_type_inventory(hotel_id, room_type_id, date, total, reserved)
-- book karte waqt, har date ke liye:
UPDATE room_type_inventory
   SET reserved = reserved + 1
 WHERE hotel_id=? AND room_type_id=? AND date BETWEEN ? AND ?
   AND reserved < total;        -- affected rows != nights → rollback

Options: pessimistic lock (SELECT … FOR UPDATE), optimistic (version column), ya upar jaisa DB constraint/conditional update. Inventory "room type + date" pe track hoti hai, individual room pe nahi (hotel check-in pe room assign karta hai).

Interview mein kaise bolein

"Search aur booking ke NFR alag hain — search eventual, booking strong. Reservation aur inventory same DB mein, ek transaction; inventory per room-type per date; conditional update/optimistic locking se overbooking nahi; aur POST pe idempotency key se double-click safe." Numbers bol ke dikhao ki booking TPS chhota hai, isliye single primary DB bhi chal sakta hai.

Key Takeaways

  • Booking = strong consistency; search = availability + cache.
  • Writes ~tens TPS, reads hazaron — design isi asymmetry pe.
  • Idempotency key frontend se.
  • Inventory (hotel, room_type, date) granularity pe.
  • Coupled data ek DB mein, ek transaction.
