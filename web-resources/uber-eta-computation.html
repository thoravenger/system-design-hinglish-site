Uber ETA — Graph Partitioning, Traffic Weights, Map Matching

Half a million requests/sec pe ETA: road network as directed graph, Dijkstra kyun kaafi nahi, partition + precompute, historical + live speed weights, Kalman filter + Viterbi se map matching.

  • Ch 16 · Proximity Service

Kyun important

ETA galat = rider ka bharosa gaya. Uber pe roz ~18M trips — chhoti galti bhi bahut mehngi. Aur ETA har screen pe chahiye: ~500K requests/sec.

1. Routing: map = graph

  • Intersection = node, road segment = directed weighted edge (one-way roads!). ETA = shortest (fastest) path.
  • Dijkstra ~O(n log n) — sirf SF Bay Area mein ~5 lakh intersections. Har request pe poora graph explore karna slow.
  • Partition the graph + har partition ke andar best paths precompute. Query time pe sirf partition boundaries pe kaam.
Intuition

Dense graph ko circle samjho: plain search pe circle ka poora area (∝ r²) explore karna padta hai; partition ke baad sirf boundary (∝ r) — bada fark.

2. Traffic = edge weights

Traffic time-of-day, weather aur gaadiyon pe depend. Edge weight = travel time, jo historical aggregated speed + real-time speed mila ke banta hai. Zyada traversal data = better estimate.

3. Map matching — noisy GPS ko sadak pe chipkao

Tunnel mein GPS gayab, buildings se signal reflect (multipath effect) → point sadak se hat ke dikhta hai. Map matching raw GPS points ko asli road segments pe map karta hai:

  • Kalman filter: purani position + naya noisy reading mila ke best guess (smoothing).
  • Viterbi (dynamic programming, Hidden Markov Model): poore GPS sequence ke liye sabse probable road-segment sequence — jaise galat spelling wale words ko context se theek karna.
flowchart LR
  GPS[Driver GPS pings] --> MM[Map matching: Kalman + Viterbi]
  MM --> SPD[Live segment speeds]
  HIST[(Historical speeds)] --> W[Edge weights]
  SPD --> W
  W --> R[Partitioned graph routing]
  R --> ETA[ETA]
  ETA --> ML[ML post-processing]

Uber routing ETA ke upar ML model (DeepETA, references mein) se residual correction bhi karta hai — routing engine + ML = final ETA.

Interview mein kaise bolein

"Road network ko directed weighted graph banaunga, weights = historical + live speeds. Har request pe Dijkstra slow, isliye graph partition karke partition ke andar paths precompute (contraction-hierarchy jaisa idea). GPS noise ke liye map matching (Kalman + HMM/Viterbi). Final ETA pe ML correction." Google Maps chapter se jodo.

Key Takeaways

  • Map = directed weighted graph; ETA = fastest path.
  • Partition + precompute → query sirf boundaries pe.
  • Weights = historical + real-time speeds.
  • Map matching: Kalman (smooth) + Viterbi (most likely road sequence).
