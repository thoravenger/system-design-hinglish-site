How Kafka Works — Log, Partitions, Replication, KRaft

Kafka ki ek line wali definition ("distributed, durable, scalable pub/sub…") ko tod ke samjho: append-only log, topic/partition, broker replication, KRaft controller, consumer groups, retention, transactions.

Problem kya tha — N² pipelines

LinkedIn ke paas sainkdon services thi jinko ek doosre ka data chahiye tha. Har pair ke beech custom pipeline banao to O(N²) connections — har VM restart pe kuch toot jaata. Kafka ka idea: data ek central jagah likho, ek standard API se padho. Likho ek baar, padho jitni baar chaho — isliye Kafka mein read throughput aksar write ka kai guna hota hai (read fan-out).

Core data structure: append-only log

  • Log = sirf end mein append; update/delete individually nahi. Har record ka monotonically increasing offset.
  • Disk pe sequential read/write — HDD pe bhi tez. Append O(1) aur lock-free, isliye scale hota hai.
  • Record = key (optional) + value, dono raw byte[]. Kafka ko types/schema se matlab nahi — serialize/deserialize client karta hai.
  • Topic = category (DB table jaisa). Partition = topic ka shard; har partition apna alag log. Same key → same partition → us key ka order maintained.

Distributed system wala hissa

ConceptHinglish mein
BrokerKafka server node. Normal cluster mein kam se kam 3.
Replication factorHar partition ki kitni copies (default/common: 3), alag brokers pe.
Leader / followerHar partition ka ek leader writes leta hai; followers copy karte hain. Leader gira to naya leader chuna jaata hai.
Controller + metadata logCluster ka control plane. Metadata bhi ek log (__cluster_metadata) mein; ek active controller likhta hai, baaki hot standby.
KRaftRaft-inspired consensus — controller election + metadata replication. ZooKeeper ki zaroorat khatam.

Kafka ko alag kya banata hai

  • Retention time-based (e.g. 7 days) — consume hone pe delete nahi hota, isliye replay possible. Traditional queues consume ke baad hata deti hain.
  • Tiered storage: purana data object storage (S3 jaisa) mein, broker disk halki — rebalancing aur recovery fast.
  • Consumer groups: ek partition group ke ek hi consumer ko milta hai → parallel reads. Progress {partition → offset} special topic __consumer_offsets mein commit hota hai; group coordinator liveness/rebalance sambhalta hai.
  • Transactions: DB transaction jaisa nahi — kai partitions pe likhe messages ek saath visible/invisible (message visibility control). Isi se exactly-once processing (read-process-write).
  • Ecosystem: Kafka Streams (stateful stream processing: windows, joins), Schema Registry (schemas convention se, kyunki Kafka bytes hi jaanta hai), Kafka Connect (DBs/systems se data andar-bahar plugins se).
  • Protocol: HTTP nahi, apna TCP-based binary protocol — isliye official/3rd-party client libraries chahiye.
Interview mein kaise bolein

"Kafka ek distributed append-only log hai. Topic partitions mein shard hota hai — partition ordering aur parallelism ki unit hai. Har partition RF=3 se replicate hota hai, leader writes leta hai, KRaft controller metadata sambhalta hai. Consumers group mein partitions baant lete hain aur offsets __consumer_offsets mein commit karte hain. Retention time-based hai, isliye replay mil jaata hai." Phir trade-off: ordering sirf partition ke andar, aur partitions badhana easy hai par key→partition mapping badal jaati hai.

Key Takeaways

  • Log + offset = Kafka ka dil; sequential disk I/O se speed.
  • Partition = scale aur ordering dono ki unit; same key same partition.
  • Replication factor 3 + leader/follower; KRaft ne ZooKeeper hataya.
  • Retention time-based hai → replay; tiered storage purana data sasta rakhta hai.
  • Exactly-once = idempotent producer + transactions (visibility control).
