uber-go/ratelimit (GitHub)

Real URL · fetched⏱ 15–30 minhttps://github.com/uber-go/ratelimit

Ye kya hai: Uber ki open-source Go library (import path go.uber.org/ratelimit). README khud kehta hai: "This package provides a Golang implementation of the leaky-bucket rate limit algorithm." Bucket ko fixed interval clock se nahi, balki do requests ke beech elapsed time ke basis pe refill karta hai.

Andar kya mila (verify kiya):

  • README.md — 10-line example: rl := ratelimit.New(100) // per second, phir loop mein rl.Take(). Output mein har call ke beech 10ms gap dikhta hai (100 RPS = har 10ms ek). Take() tab tak sleep/block karta hai jab tak agla slot na aaye — request reject nahi karta.
  • FAQ: ye golang.org/x/time/rate se kaise alag hai — Uber wala "simple API + minimal overhead" ke liye bana hai; complex use-cases ke liye x/time/rate recommend kiya gaya hai. Windows timer precision ka known issue bhi mention hai.
  • Files: ratelimit.go (public API: New, Limiter interface, options WithClock, WithoutSlack, WithSlack), limiter_atomic.go, limiter_atomic_int64.go, limiter_mutexbased.go (teen alag implementations), tests aur benchmarks.
  • Slack concept: default mein limiter kuch "unspent" requests accumulate karne deta hai taaki chhota burst nikal sake; WithoutSlack se strict ho jaata hai.

Chapter isko kyun refer karta hai: notes mein Leaking Bucket algorithm ke neeche "Example" ke taur pe. Ye dikhata hai ki leaky bucket production mein kaise dikhta hai: output rate smooth (fixed interval), aur jo zyada tez aaye unhe wait karwaya jaata hai — yaani ye client/in-process throttling hai, server-side 429 dene wala limiter nahi.

Kaise padhein (step-by-step):

  1. README ka code example padho aur output ke 10ms gaps ko 100 RPS se jodo (5 min).
  2. ratelimit.go mein sirf Limiter interface, New() aur slack wale options dekho (5 min).
  3. limiter_mutexbased.go padho — sabse readable hai: last time + per-request interval se next allowed time calculate hota hai (10 min).
  4. Skip karo: atomic implementations ki bit-level tricks, benchmark files, CI configs — interview ke liye zaroori nahi.
Interview angle"Leaky bucket ka ek practical example Uber ka go ratelimit hai — wo requests ko drop nahi, space out karta hai. Server-side API protection ke liye main isko distributed Redis-based limiter ke saath contrast karunga."

Movable Type Scripts — Geohash encoding/decoding

Real URL · fetched⏱ 20–30 minhttps://www.movable-type.co.uk/scripts/geohash.html

Ye kya hai: Chris Veness ki website ka interactive page + JavaScript library (MIT licence) jo lat/long ko geohash string mein encode/decode karti hai.

Andar kya mila:

  • Interactive tool: latitude, longitude aur precision (1–9 characters) daalo → geohash; geohash daalo → lat/long + neighbours.
  • Definition: geohash ek rectangular cell identify karta hai; har extra character 32 sub-cells mein se ek choose karta hai (base32).
  • Cell size table (sabse useful part): length 1 ≈ 5,000km × 5,000km, 4 ≈ 39.1km × 19.5km, 5 ≈ 4.89km × 4.89km, 6 ≈ 1.22km × 0.61km, 7 ≈ 153m × 153m, 8 ≈ 38.2m × 19.1m … 12 ≈ 37.2mm × 18.6mm. Note: equator se door cell width kam hoti jaati hai.
  • Edge case warning: paas ki jagah ka prefix hamesha same nahi hota — France mein La Roche-Chalais (u000) Pomerol (ezzz) se sirf 30km door hai. Isliye reliable nearby search mein cell ke 8 neighbours ke prefixes bhi query karne padte hain (page pe SQL example: WHERE LEFT(Geohash, 4) IN (…9 cells…)).
  • Neeche poora JavaScript source code (encode, decode, bounds, adjacent, neighbours).

Chapter kyun refer karta hai: Proximity service mein geohash sabse popular approach hai — radius ke hisaab se precision choose karna (e.g. ~0.5km radius → length 6) aur boundary problem ke liye current + 8 neighbour cells fetch karna. Ye page dono cheezein concretely dikhata hai.

Kaise padhein:

  1. Tool mein apne ghar/office ka lat-long daalo, precision 5, 6, 7 karke dekho string kaise lambi hoti hai (5 min).
  2. Cell-size table ko chapter ki "radius → geohash length" table se match karo (5 min).
  3. Pomerol wala edge-case paragraph dhyan se padho — yahi interview follow-up hota hai (5 min).
  4. Code mein sirf encode() aur adjacent()/neighbours() dekho: bits ko lon/lat alternately interleave karke base32 banta hai (10 min). Baaki skip.

Wikipedia — Quadtree

Real URL · fetched⏱ 20–40 minhttps://en.wikipedia.org/wiki/Quadtree

Ye kya hai: Quadtree data structure ka Wikipedia article.

Andar kya mila: Definition — tree jisme har internal node ke exactly 4 children hote hain; 2D space ko recursively 4 quadrants mein divide karta hai (octree ka 2D analog). Naam Raphael Finkel aur J.L. Bentley ne 1974 mein diya. Common features: space adaptable cells mein decompose hota hai, har cell (bucket) ki max capacity hoti hai, capacity cross hone pe bucket split hota hai. Sections: Types (Region quadtree, Point quadtree, Point-region (PR) quadtree, Edge quadtree, Polygonal map (PM) quadtree, Compressed quadtrees), Some common uses (image processing, mesh generation, connected component labelling…), aur Pseudocode (QuadTree class, Insertion, Query range).

Chapter kyun refer karta hai: Proximity service mein quadtree ek in-memory index hai: grid ko tab tak 4 mein todo jab tak har leaf mein ek threshold se kam businesses (Alex Xu ki book ka example: ~100) na rahein; notes ke mutabik ye in-memory index har LBS server pe startup pe banta hai. Dense city mein chhote cells, desert mein bade — geohash ke fixed cells se ye fayda hai.

Kaise padhein:

  1. Intro paragraph + "common features" list (5 min).
  2. Point-region (PR) quadtree section — proximity service ke sabse kareeb yahi hai (5–10 min).
  3. Pseudocode → Insertion aur Query range — ye exactly "split when full" aur "range search" dikhata hai (10–15 min).
  4. Skip karo: image processing, mesh generation, edge/PM quadtree — interview ke liye zaroori nahi.

S2 Geometry (Google)

Real URL · fetched⏱ 15 min overview; 1–2 hr deephttps://s2geometry.io/

Ye kya hai: Google ki S2 Geometry Library ka official site (Apache 2.0 licence). Unique baat: traditional GIS ki tarah flat 2D projection nahi, balki data ko 3D sphere (globe) pe represent karta hai — "no seams or singularities", poori duniya ek coordinate system mein, kam distortion.

Andar kya mila (homepage): Features list — spatial indexing jahan arbitrary regions ko discrete S2 cells ke collection se approximate kiya jaata hai (distributed spatial index banana easy), points/polylines/polygons ki fast in-memory indexing, robust operations (intersection, union, containment), nearby objects/distance queries, snap rounding. Table of contents: About (Overview, Platforms Guide), Tutorials (Quick Start), Developer Guides (Basic Types, Finding Nearby Edges, S2Cell Hierarchy, Covering Examples), Resources (The S2 Earthcube, S2Cell Statistics).

Chapter kyun refer karta hai: Google Maps/Tinder jaise companies S2 use karti hain. Proximity chapter mein ye advanced option hai: sphere ko Hilbert curve se 1D cell IDs mein map karta hai, aur region cover (circle ko alag-alag level ke cells se cover karna) geofencing ke liye powerful hai.

Kaise padhein:

  1. Homepage ka first paragraph + feature list (5 min).
  2. Developer Guide → S2Cell Hierarchy — cube faces, levels, cell IDs (20–30 min).
  3. Covering Examples — region ko cells se cover karna (10 min, pictures dekho).
  4. Skip: Platforms guide, snap rounding, exact predicates — library use karne walon ke liye hai. Interview mein itna kaafi: "S2 sphere-based, Hilbert curve, multi-level region cover; geohash simpler, quadtree adaptive."

Apache Kafka wiki — page 27846330

Real URL · fetched⏱ 10–15 minhttps://cwiki.apache.org/confluence/pages/viewpage.action?pageId=27846330

Ye kya hai: Fetch karne pe pata chala ye Apache Software Foundation ke Confluence wiki pe "Kafka mirroring (MirrorMaker)" page hai (Joel Koshy ne banaya, last update Jun 23, 2017, "4 minute read").

Andar kya mila:

  • Kafka ka mirroring feature ek existing cluster ki replica cluster maintain karta hai. MirrorMaker tool source cluster se Kafka consumer se padhta hai aur embedded Kafka producer se target (mirror) cluster mein re-publish karta hai.
  • Setup command: bin/kafka-mirror-maker.sh --consumer.config … --num.streams 2 --producer.config … --whitelist=".*".

Chapter kyun refer karta hai: Fault tolerance section mein: agar partition ke saare replicas crash ho gaye to data lost. Replicas ko data centers mein spread karna latency badhata hai — alternative hai data mirroring: ek poore cluster ko doosre DC mein asynchronously copy karna.

Kaise padhein: Pehla paragraph (architecture: consumer → producer) aur "How to check whether a mirror is keeping up" (lag) — bas yahi do interview ke liye. Varghese & Lauck — Hashed and Hierarchical Timing Wheels (SOSP '87, PDF)

Real URL · fetched⏱ Overview 30–45 min; full 2 hrhttp://www.cs.columbia.edu/~nahum/w6998/papers/sosp87-timing-wheels.pdf (notes) → https version fetched

Fetch note (honest): Notes mein link http:// wala hai. Us exact http:// URL pe hamara curl aur web fetch dono timeout ho gaye. Wahi file https:// (same host, same path) se successfully download hui (14 pages) aur pdftotext se padhi. Neeche ka summary usi PDF se hai. Link yahan https wala diya hai.

Ye kya hai: George Varghese aur Tony Lauck (Digital Equipment Corporation) ka classic OS paper: "Hashed and Hierarchical Timing Wheels: Data Structures for the Efficient Implementation of a Timer Facility".

Andar kya mila:

  • Problem (Abstract): conventional timer algorithms mein timer start/maintain karna O(n) hai (n = outstanding timers) — bade n pe mehenga. Timers kyun chahiye: failure recovery (e.g. message ack timeout → retransmission), rate control, scheduling, packet lifetimes. Example: 200 connections × 3 timers per connection wala server.
  • Model: 4 operations — START_TIMER, STOP_TIMER, PER_TICK_BOOKKEEPING, EXPIRY_PROCESSING.
  • Schemes 1–7: Scheme 1 (har timer ko har tick pe decrement), Scheme 2 (ordered list — VMS aur UNIX jaise use karte the; start O(n)), Scheme 3 (tree/heap based), Scheme 4 (basic timing wheel — circular array, O(1) jab timers wheel ki range mein hon), Scheme 5 & 6 (hashed timing wheel — interval ko hash karke slot, overflow lists per bucket), Scheme 7 (hierarchical timing wheels — seconds/minutes/hours/days jaise multiple wheels; timers upar ke wheel se neeche migrate hote hain; radix sort jaisa).
  • Conclusion: general-purpose timer module (UNIX/VMS jaisa) ke liye Scheme 6 ya 7 recommend; Scheme 6 VAX pe implement kiya. Small T + bada M → Scheme 6 better; bade T + chhota M → Scheme 7.

Chapter kyun refer karta hai: Delayed/scheduled messages (e.g. "30 min baad order cancel check karo") ke liye message queue ko timing function chahiye — dedicated delay queues ya hierarchical time wheel. Kafka internally bhi request timeouts/delayed operations ke liye hierarchical timing wheel ("Purgatory") use karta hai.

Kaise padhein:

  1. Abstract (5 min) — O(n) vs O(1) ka claim.
  2. Section 2 ke 4 operations (5 min).
  3. Seedha figures: Figure 8 (Scheme 4 array of lists), Figure 9 (Schemes 5–6 hashed wheel), Figure 10 (Scheme 7 hierarchical arrays) — diagrams se idea 80% clear (15 min).
  4. Section 6 (Extensions) mein Scheme 6 aur 7 ka text + Section 7 Summary and Conclusions (15 min).
  5. Skip: Scheme 1–3 ki detailed latency analysis, discrete-event simulation comparison, Appendix A (hardware implementation) — sirf curiosity ho to.

Gorilla: A Fast, Scalable, In-Memory Time Series Database (VLDB 2015, PDF)

Real URL · fetched⏱ Overview 45 min; full 2–3 hrhttps://www.vldb.org/pvldb/vol8/p1816-teller.pdf

Ye kya hai: Facebook ka paper (Pelkonen, Franklin, Teller, Cavallaro, Huang, Meza, Veeraraghavan), Proceedings of the VLDB Endowment Vol. 8 No. 12, 2015 — 12 pages. PDF download karke padha.

Andar kya mila:

  • Insight (Abstract): monitoring users individual data points pe nahi, aggregate analysis pe focus karte hain, aur recent data purane data se zyada valuable hai. Isliye Gorilla writes/reads ke liye highly available rehta hai, chahe write path pe thoda data drop ho jaaye.
  • Compression: timestamps ke liye delta-of-delta, values ke liye XOR with previous value (floating point). Result: 16 bytes/point se average 1.37 bytes/point (~12x reduction). Isse data memory mein fit — HBase-backed setup ke comparison mein query latency 73x kam, throughput 14x zyada.
  • Requirements (Section 2.2): 2 billion unique time series, 700 million data points/minute, 26 hours data in memory, 40,000+ peak QPS, reads < 1ms, 15-second granularity, 2 in-memory replicas (alag regions), 2x growth/year.
  • Architecture (Figure 1): Gorilla ODS (Operational Data Store) ke aage write-through cache hai jo last 26 hours rakhta hai; long-term storage HBase mein.
  • Sections: 3 (OpenTSDB, Whisper/Graphite, InfluxDB se comparison), 4.1 compression, 4.2 in-memory data structures (TSmap), 4.3 on-disk structures, 4.4 handling failures, 5 new tools (correlation engine, charting, aggregations), 6 experience/lessons learned.

Chapter kyun refer karta hai: Metrics pipeline mein Kafka queue ka downside operational overhead hai; notes kehte hain alternative ek large-scale ingestion system jaise Gorilla. Saath hi chapter ka "time-series data compression / delta encoding" idea seedha isi paper se aata hai.

Kaise padhein:

  1. Abstract + Figure 1 (10 min) — Gorilla kahan baitha hai.
  2. Section 2.2 requirements list (5 min) — real-world scale numbers, interview estimation ke liye gold.
  3. Section 4.1 + Figure 2 (compression ka visual) — delta-of-delta aur XOR (20 min). Figure 2 ko pen-paper pe ek baar khud karo.
  4. Section 4.4 failures + Section 6.3 lessons learned (10 min).
  5. Skip (first read): Section 3 comparison detail, 4.2 lock/data-structure internals, Section 5 tools (jab tak dashboards mein interest na ho).

Backblaze/erasure-coding-durability (GitHub)

Real URL · fetched⏱ 20–30 minhttps://github.com/Backblaze/erasure-coding-durability

Ye kya hai: Backblaze (cloud storage company) ka chhota repo — ek statistical model jo erasure coding (e.g. Reed-Solomon) se store kiye data ke loss ki probability calculate karta hai. Files: README.md, calculation.ipynb (math derivation), durability.py (calculator).

Andar kya mila:

  • Concept: file ko D data shards mein baanto, P parity shards compute karo → D+P shards. Koi bhi D shards se file wapas ban sakti hai — yaani koi bhi P shards kho sakte ho. Data tab lost jab P+1 shards ek saath (replace hone se pehle) lost hon.
  • Assumptions: D, P; har shard ka annual failure rate; failed shard replace karne mein kitne din; failures independent.
  • Usage: python durability.py data_shards parity_shards annual_shard_failure_rate shard_replacement_days.
  • Example output (README): 17 data + 3 parity = 20 shards, annual shard failure rate 0.00405, replacement 6.5 days → failure threshold 4 pe durability 0.999999999992646 = "11 nines" (arrow se highlighted). Table mein har threshold ke liye probability, annual odds aur nines.

Chapter kyun refer karta hai: Notes kehte hain erasure coding "11 nines of durability" deta hai vs 3-copy replication ke 6 nines (HDD annual failure rate 0.81% assumption ke saath), aur storage overhead 50% vs 3-replica ka 200%. Ye repo us 11-nines number ka source/calculation hai.

Kaise padhein:

  1. README ka Overview — D, P, "lose any P" (5 min).
  2. Assumptions list (2 min) — samjho ki "independent failures" ek optimistic assumption hai (same rack/power failure correlated hote hain).
  3. Example output table mein sirf 3 columns: failure_threshold, durability, nines — "--> 11 nines" wali row dhoondo (5 min).
  4. Optional: calculation.ipynb — binomial probability se derivation (15 min). Python install ho to apne numbers (e.g. 8+4) se khud chalao.

Phir network partition demo: A,B vs C,D,E — do leaders alag terms mein; B majority tak replicate nahi kar paata (uncommitted), doosra leader kar leta hai; partition heal hone pe B higher term dekh ke step down karta hai aur A,B uncommitted entries roll back karte hain.
  5. Other Resources.

DDoS-friendly URL design example

Example / placeholder⏱ 5 minhttps://my.website.com/data/recent vs https://my.website.com/data?from=123&to=456

Ye real URLs nahi hain — my.website.com placeholder hai. Notes ka point: DDoS se bachne ke liye URLs ko "harden" karo — prefer https://my.website.com/data/recent vs https://my.website.com/data?from=123&to=456, kyunki pehla zyada cacheable hai.

/data/recent/data?from=123&to=456
StructureFixed path, koi query param nahiSame path, lekin from/to query params (range)
