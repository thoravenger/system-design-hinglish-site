Chapter 03

A Framework for System Design Interviews

45 minute ke interview ko drive karne ka 4-step framework — sahi sawal, blueprint pe buy-in, focused deep dive aur strong wrap-up.

InterviewFrameworkCommunicationTime management

Introduction

System design interview ek real-life problem-solving simulation hai: do log milke ek ambiguous problem pe kaam kar rahe hain. Interviewer sirf technical design nahi dekh raha — wo dekh raha hai collaboration, pressure mein kaam, ambiguity ko constructively resolve karna, aur sahi sawal poochna. Red flags: over-engineering, narrow-mindedness, stubbornness.

Ye chapter ek 4-step framework deta hai jo baaki har chapter (08 se 28 tak) follow karta hai.

StepGoalTime (45 min)
1. Understand problem & scopeRequirements, scale, constraints clear karna3–10 min
2. High-level design & buy-inBlueprint + interviewer ki agreement10–15 min
3. Design deep diveCritical components mein depth10–25 min
4. Wrap-upBottlenecks, recap, follow-ups3–5 min

Step 1: Problem samjho aur design scope tay karo

Sabse badi galti: question sunte hi answer dena. Bina requirements samjhe jawab dena red flag hai. Pehle sawal poocho, assumptions clarify karo.

Kaun se sawal?

  • Exactly kaun se features build kar rahe hain? Sabse important kaun se?
  • Scale kya hai — kitne users? 3 mahine, 6 mahine, 1 saal mein kitna grow karega?
  • Web, mobile, ya dono?
  • Company ka existing tech stack kya hai? Kaun se services leverage kar sakte hain?

Assumptions whiteboard/paper pe likh lo — baad mein reference ke kaam aayenge.

Example: "Design a news feed system"

  • Mobile app, web app, ya dono? → Dono.
  • Important features? → Post publish karna aur friends ki news feed dekhna.
  • Feed reverse chronological hai ya ranked? → Simplicity ke liye reverse chronological.
  • Ek user ke kitne friends? → 5000.
  • Traffic volume? → 10 million DAU.
  • Feed mein images/videos? → Haan, media files bhi.
Functional vs non-functionalSawalon ko do buckets mein socho: functional (kya karna hai — post, feed, like) aur non-functional (kaisa karna hai — latency, availability, consistency, scale). Step 1 ke end mein dono ki list board pe ho.

Step 2: High-level design propose karo aur buy-in lo

  • Initial blueprint banao aur feedback maango. Interviewer ko teammate treat karo — achhe candidates interviewer ke saath milke design karte hain.
  • Box diagrams draw karo: clients (mobile/web), APIs, web servers, data stores, cache, CDN, message queue, etc.
  • Back-of-the-envelope (Chapter 02) se check karo blueprint scale fit karta hai ya nahi. Pehle interviewer se poochh lo ki estimation chahiye ya nahi.
  • Kuch concrete use cases walk-through karo — edge cases yahin nikalte hain.
  • API endpoints aur DB schema? Problem pe depend karta hai — "Design Google search" mein bahut low-level hai; news feed jaise problem mein theek hai. Interviewer se poochh lo.

Example: News feed — do flows

  1. Feed publishing: user post karta hai → data cache/DB mein likha jaata hai → friends ki news feed mein populate hota hai.
  2. Feed building (retrieval): friends ke posts ko reverse chronological order mein aggregate karke dikhana.

(Chapter 11 mein inke diagrams detail mein milenge.)

Step 3: Design deep dive

Is point tak tum aur interviewer ko ye mil jaana chahiye: agreed goals/scope, high-level blueprint, interviewer ka feedback, aur ek idea ki kis area pe focus karna hai.

  • Prioritize: components ko importance ke order mein rakho. Senior candidates ke saath interviewer aksar performance characteristics aur bottlenecks pe jaata hai.
  • Problem-specific depth:
    • URL shortener → hash function design (Chapter 08).
    • Chat system → latency kam karna aur online/offline status (Chapter 12).
    • News feed → feed publishing aur retrieval ka deep dive (Chapter 11).
  • Time management: unnecessary details mein mat phanso. Jaise Facebook ke EdgeRank algorithm ko detail mein explain karna ideal nahi — wo scalability dikhata hi nahi.

Step 4: Wrap-up

  • Bottlenecks identify karo aur improvements discuss karo. "Mera design perfect hai" kabhi mat bolo — hamesha kuch improve ho sakta hai. Ye critical thinking dikhata hai.
  • Recap: design ka short summary — khaaskar agar beech mein kai solutions suggest kiye the.
  • Error cases: server failure, network loss.
  • Operations: metrics kaise monitor karoge, error logs, rollout kaise karoge.
  • Next scale curve: 1 million → 10 million users pe kya badlega?
  • Aur refinements jo time hota to karte.

Dos and Don'ts

✅ Dos❌ Don'ts
Hamesha clarification maango; apni assumption ko sahi mat maano.Typical interview questions ke liye taiyar na jaana.
Problem ki requirements samjho.Requirements clarify kiye bina solution mein jump karna.
Yaad rakho — koi "right" ya "best" answer nahi hota; startup aur million-user company ke answers alag honge.Shuru mein hi ek component ki detail mein ghus jaana. Pehle high-level, phir drill down.
Interviewer ko batate raho tum kya soch rahe ho. Communicate.Stuck ho to chup baithna — hint maango.
Multiple approaches suggest karo (trade-offs ke saath).Over-engineering — "Kafka + Flink + 7 microservices" jab ek queue kaafi hai.
Blueprint pe agreement ke baad sabse critical components pe detail.Interview ko tab khatam samajhna jab interviewer bole — feedback jaldi aur baar-baar maango.
Interviewer ke saath ideas bounce karo — achha interviewer teammate ki tarah kaam karta hai.Silence. Design ek conversation hai.
Interview mein kaise bolein — 45 minute script
  1. 0–5 min: "Kuch clarifying questions — features, scale, platforms, consistency needs." Board pe functional + non-functional list.
  2. 5–8 min: Quick estimate: read/write QPS, storage. "Iska matlab read-heavy hai, cache important."
  3. 8–20 min: APIs (3–4), high-level boxes, ek happy-path flow numbered arrows ke saath. "Kya ye direction theek hai?" — buy-in.
  4. 20–40 min: 2–3 deep dives jo interviewer chahe: data model + sharding, hot path optimization, failure handling.
  5. 40–45 min: Bottlenecks, monitoring, 10x scale pe kya badlega, recap.
Real worldYe framework real design reviews jaisa hi hai: pehle PRD/requirements, phir high-level design doc review, phir detailed design, phir rollout + observability plan. Lead/FDE roles mein exactly yahi structure customer/stakeholder conversations mein bhi kaam aata hai.

Common follow-up questions

Agar interviewer bole "tum decide karo scale"?

Ek reasonable number lo aur bolo kyun: "Assume 10M DAU, read-heavy 10:1 — mid-size consumer app." Phir aage badho; flexibility dikhao.

Agar deep dive mein galti pakdi gayi?

Defend mat karo — acknowledge karo, trade-off samjho, fix propose karo. Ye "stubbornness" red flag se bachata hai.

Kitna detail API/schema mein?

Interviewer se poochho. Product-type problems (feed, chat) mein 3–5 APIs aur main tables kaafi hain; infra problems (KV store, queue) mein data path zyada important hai.

Key Takeaways

  • 4 steps: Scope → High-level + buy-in → Deep dive → Wrap-up.
  • Time split (45 min): 3–10 / 10–15 / 10–25 / 3–5 minutes.
  • Pehle sawal, phir solution. Assumptions board pe likho.
  • Interviewer teammate hai — baar-baar feedback lo.
  • Depth wahan do jahan problem ka "hard part" hai; over-engineering se bacho.
  • Wrap-up mein bottlenecks, failures, monitoring aur next-10x scale discuss karo.
