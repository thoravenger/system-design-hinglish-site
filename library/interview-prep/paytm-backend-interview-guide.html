SECTION 1 · CORE JAVA

Q1. Explain JVM memory model — Heap, Stack, Metaspace and how GC works.

Answer & Explanation

The JVM divides memory into distinct regions — crucial for tuning Paytm's payment services:

  • Heap: All objects and class instances. Young Gen (Eden+S0+S1) + Old Gen (Tenured). GC happens here.
  • Stack: Per-thread. Method frames, local primitives, references. Auto-freed on method return. Never GC'd.
  • Metaspace (Java 8+): Class metadata. Grows dynamically from native memory. Replaced PermGen.
  • PC Register: Per-thread pointer to current JVM instruction.
GC AlgorithmPause TimeBest ForJVM Flag
Serial GCHigh (full STW)Single-core, small heaps-XX:+UseSerialGC
G1GC (default Java 9+)100–200msBalanced — general use-XX:+UseG1GC
ZGC (Java 11+)< 1msLow-latency payment APIs-XX:+UseZGC
Shenandoah< 10msLarge heaps, concurrent-XX:+UseShenandoahGC

Tip: For Paytm payment API (SLA < 200ms): use ZGC. Tune: -Xmx4g -Xms4g -XX:+UseZGC -XX:MaxGCPauseMillis=5

Q2. What is the Java Memory Model (JMM)? Explain volatile and happens-before.

Answer & Explanation

The JMM defines rules for thread visibility. Without it, each CPU core's cache means one thread's writes may never be visible to another.

Java
// BROKEN — without volatile, JIT may cache 'instance' in CPU register
private static Singleton instance;

// CORRECT — volatile: guarantees visibility + prevents instruction reordering
private static volatile Singleton instance;

public static Singleton getInstance() {
    if (instance == null) { // first check (no lock — fast path)
        synchronized (Singleton.class) { // only lock when null
            if (instance == null) { // second check (inside lock)
                instance = new Singleton(); // safe — volatile stops partial construct
            }
        }
    }
    return instance;
}

// Without volatile: CPU reorders steps — another thread sees non-null but
// reads an incompletely constructed object (fields not yet initialized!)

Critical: Self-invocation this.method() skips the Spring proxy — @Transactional and @Async will be SILENTLY IGNORED!

Tip: happens-before rules: unlock → lock; volatile write → read; thread.start() → run(); run() → join() caller.

Q3. CompletableFuture — how does it work and how do you use it at Paytm scale?

Answer & Explanation

CompletableFuture enables non-blocking async pipelines. Parallelizing sequential downstream calls at Paytm dramatically cuts latency.

Java
// SEQUENTIAL — 300ms + 300ms + 100ms = 700ms total
User user = fetchUser(id); // 300ms — blocks thread
Wallet wallet = fetchWallet(id); // 300ms — blocks thread
KYC kyc = fetchKYC(id); // 100ms — blocks thread

// PARALLEL — max(300, 300, 100) = 300ms total (60% faster!)
// Always provide a CUSTOM executor — never use ForkJoinPool.commonPool() in prod!
ExecutorService executor = Executors.newFixedThreadPool(20);

CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> fetchUser(id), executor);
CompletableFuture<Wallet> walletFuture = CompletableFuture.supplyAsync(() -> fetchWallet(id), executor);
CompletableFuture<KYC> kycFuture = CompletableFuture.supplyAsync(() -> fetchKYC(id), executor);

// Wait for ALL three to complete
CompletableFuture.allOf(userFuture, walletFuture, kycFuture).thenRun(() -> {
    User user = userFuture.join(); // non-blocking — already done
    Wallet wallet = walletFuture.join();
    KYC kyc = kycFuture.join();
    buildResponse(user, wallet, kyc);
}).exceptionally(ex -> {
    log.error("Checkout fetch failed", ex);
    return null;
});

// Key API Reference:
// supplyAsync(Supplier, Executor) — run async task on executor
// thenApply(Function) — transform result (same thread)
// thenApplyAsync(Function, Executor) — transform on separate thread
// thenCompose(Function<T,CF<U>>) — flatMap: chain dependent future
// exceptionally(Function<Throwable>) — fallback on any exception
// allOf(CF...) — complete when ALL complete
// anyOf(CF...) — complete when FIRST completes

Tip: Real Paytm impact: checkout API 1,200ms → 140ms by parallelizing user-profile, wallet-balance, and fraud-score via CompletableFuture.allOf().

ReentrantLock lock = new ReentrantLock();

public void processPayment(Payment payment) {
    try {
        // tryLock with timeout — avoids deadlock risk
        if (!lock.tryLock(500, TimeUnit.MILLISECONDS)) {

    }
}

ReentrantLock lock = new ReentrantLock();

// Signal only producers OR only consumers — more efficient than notifyAll()

Q5. How does @Transactional work internally? Explain propagation + isolation levels.

Answer & Explanation

Spring wraps @Transactional methods with a proxy (CGLIB for classes, JDK proxy for interfaces). The proxy intercepts the call, starts a tx, runs your method, then commits or rolls back.

Java
// THE MOST COMMON @Transactional MISTAKE: Self-Invocation
// this.method() bypasses the Spring proxy   @Transactional SILENTLY ignored!

@Service
public class OrderService {

    // WRONG — processPayment() runs WITHOUT any transaction
    public void createOrder(Order order) {
        this.processPayment(order); // direct call, skips Spring proxy
    }

    @Transactional
    public void processPayment(Order order) { /* runs without tx context! */ }

    // FIX 1 — inject self (Spring returns the proxy, not 'this')
    @Autowired
    private OrderService self;

    public void createOrderFixed(Order order) {
        self.processPayment(order); // goes through proxy
    }
    // FIX 2 (cleaner) — extract processPayment() to a SEPARATE @Service bean
}

// PROPAGATION EXAMPLES:
@Transactional(propagation = Propagation.REQUIRES_NEW) // new tx, suspend outer
public void saveAuditLog(AuditEntry entry) {
    auditRepo.save(entry); // saved even if the outer tx rolls back
}

@Transactional(propagation = Propagation.NESTED) // savepoint in outer tx
public void processLineItem(LineItem item) {
    lineItemRepo.save(item); // rollback here = partial undo, outer tx survives
}

@Transactional(isolation = Isolation.SERIALIZABLE) // highest isolation
public void debitWallet(String userId, BigDecimal amount) {
    // No phantom reads, no dirty reads, no non-repeatable reads
    // Full serialization — use for critical payment debits
}

@Transactional(rollbackFor = Exception.class, // rollback on checked exceptions
noRollbackFor = InsufficientFundsException.class) // NOT on this one
public void charge(Payment payment) throws InsufficientFundsException {
    // InsufficientFunds = expected business outcome, should NOT roll back tx
}

Q6. How does Spring AOP work? Write a custom logging + idempotency aspect.

Answer & Explanation

AOP separates cross-cutting concerns from business logic. Spring creates proxy beans at runtime — this is exactly how @Transactional, @Cacheable, and @Async work automatically.

Java
// Step 1: Custom Annotation
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Idempotent {
    long ttlHours() default 24;
}

// Step 2: Aspect — intercepts methods at runtime via proxy
@Aspect
@Component
public class PaymentAspect {

    // Timing + Logging — wraps ALL payment service methods
    @Around("execution(* com.paytm.payment.service.*.*(..))")
    public Object logAndTime(ProceedingJoinPoint pjp) throws Throwable {
        String method = pjp.getSignature().toShortString();
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed(); // invoke the REAL method
            log.info("[OK] {} in {}ms", method, System.currentTimeMillis()-start);
            return result;
        } catch (Exception e) {
            log.error("[ERR] {}   {}", method, e.getMessage());
            metrics.counter("payment.errors","method",method).increment();
            throw e; // ALWAYS re-throw!
        }
    }

    // Idempotency — intercepts @Idempotent annotated methods
    @Around("@annotation(idempotent)")
    public Object enforceIdempotency(ProceedingJoinPoint pjp,
    Idempotent idempotent) throws Throwable {
        String key = getCurrentRequest().getHeader("Idempotency-Key");
        String redisKey = "idem:" + key;
        String cached = redis.get(redisKey);

        if (cached != null) { // already processed — return cached
            return objectMapper.readValue(cached, getReturnType(pjp));
        }
        Object result = pjp.proceed();
        redis.setex(redisKey, idempotent.ttlHours()*3600, serialize(result));
        return result;
    }
}

// Step 3: Usage — clean, declarative
@PostMapping("/payment")
@Idempotent(ttlHours = 24) // runs at most once per idempotency key
public PaymentResponse pay(@RequestBody PaymentRequest req) {
    return paymentService.process(req);
}

Tip: CGLIB proxy (default in Spring Boot) requires a no-arg constructor. JDK proxy (for interfaces) is slightly faster. Mention both — shows depth of Spring internals knowledge.

Q7. Explain Circuit Breaker with Resilience4j — states, config, fallback pattern.

Answer & Explanation

State · Behavior · Transition Trigger

  • → OPEN when failure rate ≥

CLOSED · Normal — all calls pass through threshold

  • → HALF_OPEN after

OPEN · Fail-fast — no actual calls made, fallback triggered waitDurationInOpenState

  • → CLOSED on success; → OPEN on

HALF_OPEN · N probe calls allowed to test service recovery failure

application.yml

  circuitbreaker:

  paymentGateway:
  slidingWindowSize: 10 # evaluate last 10 calls
  failureRateThreshold: 50 # OPEN if 50%+ fail
  slowCallRateThreshold: 80 # OPEN if 80%+ are slow
  slowCallDurationThreshold: 2000ms # 'slow' = > 2 seconds
  waitDurationInOpenState: 10s # stay OPEN for 10s
  permittedNumberOfCallsInHalfOpenState: 3 # 3 probes in HALF_OPEN
  retry:
  instances:
  paymentGateway:
  maxAttempts: 3
  waitDuration: 1s
  enableExponentialBackoff: true
  exponentialBackoffMultiplier: 2 # delays: 1s   2s   4s
Java
  @Service
  public class PaymentGatewayService {

  // Circuit Breaker + Retry + TimeLimiter — layered resilience
  @CircuitBreaker(name = "paymentGateway", fallbackMethod = "paymentFallback")
  @Retry(name = "paymentGateway")
  @TimeLimiter(name = "paymentGateway")
  public CompletableFuture<PaymentResponse> chargeAsync(PaymentRequest req) {
  return CompletableFuture.supplyAsync(() -> gatewayClient.charge(req));
  }

  // Fallback — triggered when CB is OPEN or all retries exhausted
  public CompletableFuture<PaymentResponse> paymentFallback(
  PaymentRequest req, Exception ex) {
  log.warn("[CB-FALLBACK] Gateway unavailable: {}", ex.getClass().getSimpleName());
  kafkaProducer.send("payment-retry-queue", req.getUserId(), req); // queue retry
  return CompletableFuture.completedFuture(
  PaymentResponse.pending(req.getOrderId())); // return PENDING to client
  }
  }

Tip: Stack all three: CB (opens at 50% failure) + Retry (3x, exponential backoff) + TimeLimiter (2s). Production resilience pattern at Paytm for all bank gateway calls.

producerProps.put("enable.idempotence", true);
producerProps.put("transactional.id", "payment-producer-pod-1"); // unique per JVM!
producerProps.put("acks", "all");

producer.initTransactions();

    producer.send(new ProducerRecord<>("payment-events", key, paymentJson));
    producer.send(new ProducerRecord<>("audit-log", key, auditJson));
    producer.commitTransaction(); // both visible atomically
} catch (ProducerFencedException e) {
    producer.close(); // another instance took over — must close
} catch (Exception e) {
    producer.abortTransaction(); // both messages invisible to consumers
}

// Consumer: MUST use read_committed to skip uncommitted messages
consumerProps.put("isolation.level", "read_committed");


// OPTION B: At-least-once + Redis Idempotency Key (PAYTM'S ACTUAL APPROACH)
// Simpler and more resilient than Kafka transactions in practice
@KafkaListener(topics = "payment-events", groupId = "payment-processor")
public void process(ConsumerRecord<String, PaymentEvent> record, Acknowledgment ack) {
    String key = "processed:" + record.value().getIdempotencyKey();

    if (Boolean.TRUE.equals(redis.hasKey(key))) {
        log.info("[SKIP] Already processed: {}", key);
        ack.acknowledge(); // commit offset — we've seen this before
        return;
    }

    paymentService.process(record.value());
    redis.opsForValue().set(key, "1", 24, TimeUnit.HOURS); // mark done
    ack.acknowledge(); // commit offset AFTER successful processing
}

Tip: Paytm REAL choice: at-least-once + Redis idempotency key. Kafka transactions add broker overhead and operational complexity. The Redis approach handles crashes, retries, and Kafka redeliveries elegantly.

Q10. Kafka Consumer Rebalancing — what triggers it and how to minimize impact?

Answer & Explanation

Rebalancing: ALL consumers in a group STOP processing while partitions are redistributed. For real-time payment processing this causes dangerous processing gaps.

Java
// REBALANCE TUNING — minimize impact for payment consumers

// CooperativeSticky = incremental rebalance — only move partitions that NEED moving
// Standard range/roundrobin: ALL consumers stop   ALL partitions reassigned (Stop-The-World)
// CooperativeSticky: ONLY affected partitions move   others continue processing
props.put("partition.assignment.strategy",
"org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

// Static membership — each pod gets a fixed ID
// On restart: Kafka waits for SAME consumer to rejoin instead of triggering rebalance
props.put("group.instance.id", "payment-consumer-pod-" + System.getenv("POD_INDEX"));

// Heartbeat / timeout tuning — prevent false rebalances from slow processing
props.put("heartbeat.interval.ms", 3000); // send heartbeat every 3s
props.put("session.timeout.ms", 45000); // consumer 'dead' if silent for 45s
props.put("max.poll.interval.ms", 300000); // 5min max between polls (for heavy DB work)
props.put("max.poll.records", 100); // don't over-fetch  slow processing    rebalance

// REBALANCE LISTENER — graceful commit before rebalance
public class PaymentConsumer implements ConsumerAwareRebalanceListener {

    @Override
    public void onPartitionsRevokedBeforeCommit(Consumer<?,?> consumer,
    Collection<TopicPartition> partitions) {
        // Commit current offsets BEFORE partitions are taken away
        consumer.commitSync(currentOffsets);
        log.info("Revoked — committed offsets for {} partitions", partitions.size());
    }

    @Override
    public void onPartitionsAssigned(Consumer<?,?> consumer,
    Collection<TopicPartition> partitions) {
        log.info("Assigned {} new partitions — warming caches", partitions.size());
    }
}

Tip: CooperativeSticky + static membership prevents 30–60 second processing gaps during rolling deployments. Critical for Paytm's zero-downtime payment processing.

Q11. Design a Dead Letter Queue (DLQ) pattern in Kafka for failed payment events.

Answer & Explanation

DLQ routes repeatedly-failing messages to a separate topic instead of blocking the main pipeline. Paytm uses a multi-level retry topology:

Java
// MULTI-LEVEL RETRY TOPOLOGY
// payment-events   (fail x1)    payment-retry-30s (retry after 30 seconds)
// (fail x2)   payment-retry-5min (retry after 5 minutes)
// (fail x3)   payment-DLQ (manual ops review + alert)

@KafkaListener(topics = "payment-events", groupId = "payment-processor")
public void processPayment(ConsumerRecord<String, PaymentEvent> record,
Acknowledgment ack) {
    try {
        paymentService.process(record.value());
        ack.acknowledge(); // success — commit offset

    } catch (RetryableException e) {
        // Transient (timeout, network) — send to retry topic with delay header
        int retryCount = parseRetryCount(record.headers());
        if (retryCount < 3) {
            sendToRetryTopic(record, retryCount + 1);
        } else {
            sendToDLQ(record, e); // exhausted retries   DLQ
        }
        ack.acknowledge(); // commit — we re-queued it

    } catch (NonRetryableException e) {
        // Permanent error (invalid account, fraud block)   DLQ immediately
        sendToDLQ(record, e);
        ack.acknowledge();
    }
}

// DLQ ENRICHMENT — ops team needs these headers for fast triage
private void sendToDLQ(ConsumerRecord<String, PaymentEvent> record, Exception ex) {
    RecordHeaders headers = new RecordHeaders(record.headers());
    headers.add("X-Exception-Class", ex.getClass().getName().getBytes());
    headers.add("X-Exception-Message", ex.getMessage().getBytes());
    headers.add("X-Original-Topic", record.topic().getBytes());
    headers.add("X-Original-Partition", String.valueOf(record.partition()).getBytes());
    headers.add("X-Original-Offset", String.valueOf(record.offset()).getBytes());
    headers.add("X-Failed-At", Instant.now().toString().getBytes());

    dlqProducer.send(new ProducerRecord<>(
    "payment-events-DLQ", null, record.key(), record.value(), headers));
    log.error("[DLQ] key={} reason={}", record.key(), ex.getMessage());
}

@Scheduled(cron = "0 */30 * * * *") // replay DLQ every 30 minutes
public void reprocessDLQ() {

Q12. Design a Wallet System — concurrent debit/credit with strong consistency.

Answer & Explanation

Java
// ENTITY — @Version enables optimistic locking
@Entity
@Table(name = "wallet_accounts",
indexes = @Index(columnList = "user_id", unique = true))
public class Wallet {
    @Id @GeneratedValue
    private Long id;

    @Column(nullable = false, unique = true)
    private String userId;

    @Column(nullable = false, precision = 15, scale = 2)
    private BigDecimal balance;

    @Version // auto-incremented on every save
    private int version; // concurrent update throws OptimisticLockException
}

// SERVICE — idempotency + optimistic lock + outbox
@Service
@Transactional(isolation = Isolation.REPEATABLE_READ)
public class WalletService {

    public void debit(String userId, BigDecimal amount, String idempotencyKey) {

        // Idempotency check — prevent double-processing same request
        if (txnRepo.existsByIdempotencyKey(idempotencyKey)) {
            log.info("[SKIP] Already processed: {}", idempotencyKey);
            return;
        }

        // Fetch wallet — @Version enables optimistic locking
        Wallet wallet = walletRepo.findByUserId(userId)
        .orElseThrow(() -> new WalletNotFoundException(userId));

        // Business validation
        if (wallet.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException(
            "Balance " + wallet.getBalance() + " < Required " + amount);
        }

        // Debit — save throws OptimisticLockException on concurrent update
        wallet.setBalance(wallet.getBalance().subtract(amount));
        walletRepo.save(wallet); // increments version; concurrent update fails here

        // Record transaction for audit trail
        txnRepo.save(WalletTransaction.debit(wallet.getId(), amount, idempotencyKey));

        // Outbox pattern — same DB tx = guaranteed event delivery to Kafka
        outboxRepo.save(OutboxEvent.walletDebit(userId, amount, idempotencyKey));
        // A separate poller reads outbox and publishes to Kafka
        // Prevents dual-write: no risk of DB commit + Kafka publish both needed atomically
    }
}

Tip: OUTBOX PATTERN is critical: write transaction + event to DB in SAME transaction. Separate poller publishes to Kafka. Eliminates dual-write problem where DB succeeds but Kafka publish fails.

// REDIS LUA SCRIPT — atomic token bucket, no race conditions
// Lua executes atomically in Redis — safe across distributed nodes!
private static final String TOKEN_BUCKET_SCRIPT = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local ttl = tonumber(ARGV[2])
local tokens = tonumber(redis.call('GET', key))
if tokens == nil then tokens = capacity end -- first request, full bucket
if tokens > 0 then
redis.call('SET', key, tokens - 1, 'EX', ttl)
return 1 -- ALLOWED
else
return 0 -- RATE LIMITED
end""";

@Component
public class RedisRateLimiter {
    // 100 requests/minute per user, burst up to 200
    public boolean isAllowed(String userId) {
        Long result = (Long) redisTemplate.execute(
        new DefaultRedisScript<>(TOKEN_BUCKET_SCRIPT, Long.class),
        List.of("rate:" + userId),
        "100", // ARGV[1] — max tokens (burst capacity)
        "60" // ARGV[2] — TTL seconds (refill window)
        );
        return result != null && result == 1L;
    }
}

Q18. Implement a Thread-Safe LRU Cache — O(1) get and put.

Answer & Explanation

Java
// LinkedHashMap(accessOrder=true) + ReentrantReadWriteLock
public class LRUCache<K, V> {

    private final int capacity;
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final LinkedHashMap<K, V> cache;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        // accessOrder=true: get() moves the accessed entry to END (most recently used)
        // removeEldestEntry: evicts the FIRST entry (least recently used) when over capacity
        this.cache = new LinkedHashMap<>(capacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                return size() > LRUCache.this.capacity; // evict LRU when full
            }
        };
    }

    public V get(K key) {
        // MUST use writeLock — accessOrder=true means get() modifies internal order!
        rwLock.writeLock().lock();
        try {
            return cache.getOrDefault(key, null);
        } finally {
            rwLock.writeLock().unlock(); // always unlock in finally
        }
    }

    public void put(K key, V value) {
        rwLock.writeLock().lock();
        try {
            cache.put(key, value); // auto-evicts LRU entry if at capacity
        } finally {
            rwLock.writeLock().unlock();
        }
    }

    public int size() {
        rwLock.readLock().lock();
        try { return cache.size(); }
        finally { rwLock.readLock().unlock(); }
    }
}

// Time: O(1) get and put | Space: O(capacity)
LRUCache<String, UserProfile> cache = new LRUCache<>(10_000);
cache.put("user123", profile);
UserProfile p = cache.get("user123"); // p is null if evicted or missing

Critical: LinkedHashMap with accessOrder=true is NOT thread-safe for reads — get() modifies the node order. Must use writeLock for BOTH get and put. This is a famous interview gotcha!

Q19. Longest Substring Without Repeating Characters — O(n) sliding window.

Answer & Explanation

Java
// SLIDING WINDOW — two pointers + HashMap
// Window [left, right]: expand right, shrink left on duplicate character

public int lengthOfLongestSubstring(String s) {
    Map<Character, Integer> lastSeen = new HashMap<>(); // char  last seen index
    int maxLen = 0;
    int left = 0; // left boundary of window

    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);

        if (lastSeen.containsKey(c)) {
            // Shrink left past the duplicate — but never move left backwards!
            left = Math.max(left, lastSeen.get(c) + 1);
        }

        lastSeen.put(c, right); // update last seen position
        maxLen = Math.max(maxLen, right - left + 1); // current window size
    }
    return maxLen;
}

Q20. Implement Thread-Safe Token Bucket Rate Limiter — in-process (no Redis).

Answer & Explanation

Java
// In-process Token Bucket — single JVM, no external dependency
public class TokenBucketRateLimiter {

    private final long capacity; // max tokens (= max burst)
    private final long refillTokens; // tokens added per interval
    private final long refillIntervalMs; // refill interval (milliseconds)
    private final AtomicLong tokens; // current tokens — thread-safe counter
    private volatile long lastRefillTime; // volatile — visible to all threads

    public TokenBucketRateLimiter(long capacity, long refillTokens, long intervalMs) {
        this.capacity = capacity;
        this.refillTokens = refillTokens;
        this.refillIntervalMs = intervalMs;
        this.tokens = new AtomicLong(capacity); // start with full bucket
        this.lastRefillTime = System.currentTimeMillis();
    }

    // synchronized: make refill + check + decrement atomic
    public synchronized boolean tryAcquire() {
        refill(); // top up tokens based on elapsed time
        if (tokens.get() > 0) {
            tokens.decrementAndGet();
            return true; // allowed
        }
        return false; // rate limited
    }

    private void refill() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastRefillTime;
        if (elapsed >= refillIntervalMs) {
            long intervals = elapsed / refillIntervalMs;
            long toAdd = intervals * refillTokens;
            // Cap at capacity — don't exceed burst limit
            tokens.set(Math.min(capacity, tokens.get() + toAdd));
            lastRefillTime = now;
        }
    }
}

// Usage: 100 requests/second, burst allowed up to 200
TokenBucketRateLimiter limiter = new TokenBucketRateLimiter(
200, // capacity — burst up to 200 requests
100, // refill 100 tokens
1000 // every 1,000ms = 1 second
);

if (!limiter.tryAcquire()) {
    throw new RateLimitExceededException("Too many requests. Slow down.");
}

Tip: synchronized on tryAcquire() makes refill + check + decrement atomic. For distributed multi-node systems: swap AtomicLong for Redis Lua script (see Q13). Same algorithm, different scope.
