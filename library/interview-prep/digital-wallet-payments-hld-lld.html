Digital Wallet & Payments System: HLD and LLD

2026-09-17 · @u_I6FOpjcCjjb50Mzghgt1DQ

1. Context and requirements

The system is a stored-value wallet for 10 million users: top up from cards, transfer and pay instantly, withdraw to banks, and never lose or duplicate money. Card and bank rails come from an external payment service provider (PSP) such as Stripe or Adyen in sandbox mode, so the wallet never handles card numbers.

The stack is Java 25 with Spring Boot 4.1, PostgreSQL, Kafka and Redis. Out of scope for version 1: cross-currency transfers, credit products, issuing cards, and automated chargeback handling.

2. High-level design

The wallet core is a modular monolith on one PostgreSQL ledger, with Kafka for side effects and a PSP adapter for card and bank rails. Money movements need one ACID transaction across balances, holds, journal entries and idempotency records. Keeping them in one service and one database avoids distributed transactions on the money path.

3. Ledger design

Every money movement is one journal transaction whose debits equal its credits in each currency, so money is never created or destroyed by a bug. Balances are derived from these entries; they are never edited on their own.

Accounts

The ledger is written from the platform's point of view. A user's wallet balance is money the platform owes that user, so it is a liability.

AccountOwnerNormal sideHolds
User wallet, one per currencyUserCredit (liability)Money a user can spend or withdraw
Merchant payableMerchantCredit (liability)Money owed to a merchant until settlement
PSP receivablePlatformDebit (asset)Card top-ups captured but not yet settled by the PSP
Bank cashPlatformDebit (asset)Money in the platform's bank account
Payout clearingPlatformCredit (liability)Withdrawals paid by the PSP but not yet settled
Fee revenuePlatformCredit (revenue)Fees charged to users or merchants
PSP feesPlatformDebit (expense)Fees the PSP charges the platform

An account's balance is credits minus debits for credit-normal accounts, and debits minus credits for debit-normal accounts.

Journal examples

A refund or correction is always a new journal that references the original. Entries are never updated or deleted.

Balances and holds

Each account has one balance row with the ledger balance, the held amount and a version. The row changes in the same database transaction as the entries, so it is a consistent cache of the entry sum. Summing billions of entries on every read would be far too slow.

A hold reserves money without moving it, for example during a withdrawal. It raises the held amount, so available balance drops while the ledger balance stays the same. Capturing a hold posts the real journal; releasing it just lowers the held amount.

Money representation

Amounts are stored as a long count of minor units plus an ISO 4217 currency code. Currencies differ in decimal places: JPY has 0, EUR and USD have 2, and BHD and KWD have 3. Floating-point types are never used for money.

BigDecimal appears only for fee percentages and future FX rates, with an explicit rounding mode such as HALF_EVEN. When a fee rounds, the remainder goes to a named account, so no fraction of a cent disappears.

Invariants

  1. For every journal and currency, total debits equal total credits.

  2. Entries are append-only; corrections are reversing journals.

  3. Each stored balance equals the sum of that account's entries.

  4. A user wallet's available balance never goes below zero.

  5. Every amount is a positive whole number of minor units, and one journal uses one currency in version 1.

The application enforces invariants 1, 4 and 5 before commit, the database enforces 2, 4 and 5 with grants and check constraints, and a nightly job verifies 1 and 3.

4. Core flows

Three flows carry most of the risk: instant transfers inside the ledger, card top-ups that finish asynchronously, and withdrawals that hold funds across a PSP call.

The idempotency record, entries, balances and outbox event commit together, so a retry either replays the saved response or finds that nothing happened.

Webhooks can arrive before the API response, twice, or out of order. The forward-only state machine in section 7 makes all three harmless, and a resolver polls the PSP when no webhook arrives within 30 minutes.

Withdrawal saga

sequenceDiagram
    actor U as User app
    participant PAY as Payments module
    participant LED as Ledger
    participant PSP as PSP payouts
    U->>PAY: POST /v1/withdrawals with Idempotency-Key
    PAY->>LED: place hold for amount plus fee
    PAY->>PSP: create payout, withdrawal id as key
    alt payout paid
        PSP->>PAY: webhook: payout paid
        PAY->>LED: capture hold, debit wallet
    else payout failed or returned
        PSP->>PAY: webhook: payout failed
        PAY->>LED: release hold
    else call timed out
        PAY->>PSP: query payout by withdrawal id
    end

The withdrawal is a saga: each step is its own local transaction, and a failure runs a compensation (release the hold) instead of a rollback. The wallet is debited only after the rail confirms, and our withdrawal id is the PSP's idempotency key, so a retried call cannot pay twice.

5. Correctness under failure

Four mechanisms keep money correct when requests repeat, run concurrently or fail halfway: idempotency keys, ordered row locks, a transactional outbox, and an explicit unknown state for PSP calls.

Idempotency keys

Mobile networks drop responses, so clients retry, and a retried transfer must not move money twice. Every request that moves money carries a client-generated Idempotency-Key (a UUID).

  1. The server inserts a row keyed by client and key, with a SHA-256 hash of the request and status IN_PROGRESS.

  2. Same key, same hash, status COMPLETED: return the stored HTTP status and body without executing again.

  3. Same key, different hash: reject with 422 idempotency_key_reused.

  4. Same key still IN_PROGRESS: return 409 request_in_progress with a Retry-After header.

  5. The final response is saved in the same database transaction as the money movement.

  6. Keys expire after 72 hours, longer than any client retry window.

Internal flows such as transfers claim and complete the key in one transaction. A concurrent duplicate then waits on the unique index and sees the committed result. Flows that call a PSP cannot hold a transaction open, so they claim with a 60-second lease that another worker can take over after a crash.

Concurrency and locking

Two transfers can debit the same wallet at the same moment. The ledger locks every balance row in the journal with SELECT ... FOR UPDATE, always in ascending account id order, and checks funds only after the locks are held.

  • Lock order prevents deadlocks. Alice paying Bob while Bob pays Alice would otherwise lock the two rows in opposite orders.

  • READ COMMITTED is enough. The rows being checked are locked, so SERIALIZABLE would add retries without adding safety on this path.

  • Pessimistic beats optimistic here. A popular merchant account receives many payments at once; version checks would cause retry storms, while ordered locks are held for a few milliseconds.

  • Hot accounts get buckets. Credits to a very busy merchant go to one of N sub-accounts, swept into the main account every minute.

Transactional outbox

Writing to PostgreSQL and publishing to Kafka are two systems, so doing both in a request goes wrong. Publishing before commit can announce a transfer that rolls back; publishing after commit loses the event if the process crashes in between.

The ledger inserts the event into an outbox_events table inside the money transaction. A relay reads unpublished rows with FOR UPDATE SKIP LOCKED, publishes them, and marks them published. Delivery is at least once, so every consumer records processed event ids and ignores repeats.

The Kafka key is the account or payment id, which keeps one entity's events in order within a partition. At higher volume, change data capture with Debezium can read the outbox from the write-ahead log instead of polling.

Unknown PSP outcomes

A timeout does not mean the payment failed: the PSP may already have charged the card. The payment moves to UNKNOWN, never straight to FAILED, and a resolver queries the PSP by our reference until the outcome is final.

  • Every PSP call sends our payment or withdrawal id as the PSP's idempotency key, so retrying cannot charge or pay twice.

  • Webhooks are verified by signature and timestamp, stored with a unique provider event id, acknowledged within 2 seconds, then processed from the table.

  • Before crediting a wallet, the service re-fetches the payment from the PSP API rather than trusting the webhook body alone.

Money value object

public record Money(long amountMinor, Currency currency) {

    public Money {
        Objects.requireNonNull(currency, "currency");
    }

    /** Converts an API amount such as 30.00 EUR; throws if it has more decimals than the currency allows. */
    public static Money of(BigDecimal amount, Currency currency) {
        BigDecimal minor = amount.movePointRight(currency.getDefaultFractionDigits());
        return new Money(minor.longValueExact(), currency);
    }

    public Money plus(Money other) {
        requireSameCurrency(other);
        return new Money(Math.addExact(amountMinor, other.amountMinor), currency);
    }

    public Money minus(Money other) {
        requireSameCurrency(other);
        return new Money(Math.subtractExact(amountMinor, other.amountMinor), currency);
    }

    public boolean isNegative() {
        return amountMinor < 0;
    }

    private void requireSameCurrency(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch: " + currency + " and " + other.currency);
        }
    }
}

Math.addExact throws on overflow instead of silently wrapping, and longValueExact rejects 30.001 EUR.

Posting a journal

@Service
public class LedgerService {

    private final BalanceRepository balances;
    private final JournalRepository journals;
    private final OutboxWriter outbox;

    public LedgerService(BalanceRepository balances, JournalRepository journals, OutboxWriter outbox) {
        this.balances = balances;
        this.journals = journals;
        this.outbox = outbox;
    }

    @Transactional
    public PostedJournal post(JournalRequest request) {
        request.requireBalanced(); // debits equal credits per currency, all amounts positive

        // One SQL statement locks every touched balance ordered by account_id, so no deadlocks.
        Map<UUID, Balance> locked = balances.lockForUpdate(request.accountIds());

        for (Posting posting : request.postings()) {
            locked.get(posting.accountId()).apply(posting); // respects the account's normal side
        }
        for (Balance balance : locked.values()) {
            if (!balance.allowsNegative() && balance.available().isNegative()) {
                throw new InsufficientFundsException(balance.accountId()); // rolls everything back
            }
        }

        UUID journalId = journals.insert(request);          // header and entries, append-only
        balances.saveAll(locked.values());                  // increments each row's version
        outbox.write(DomainEvent.journalPosted(journalId, request));
        return new PostedJournal(journalId, request.reference());
    }
}

The lock query leaves the ordering to PostgreSQL in a single statement, so every transaction locks rows in exactly the same order:

SELECT b.account_id, b.ledger_balance, b.held_amount, b.allow_negative, b.version,
       a.normal_side, a.currency
FROM account_balances b
JOIN accounts a ON a.id = b.account_id
WHERE b.account_id = ANY(:accountIds)
ORDER BY b.account_id
FOR UPDATE OF b;

Funds are checked after every posting is applied, so a journal that debits and credits the same account is judged by its final effect.

7. State machines

Every payment object follows a forward-only state machine, which makes duplicate and out-of-order webhooks harmless. Any event that would move a status backwards is logged and ignored, so a late failure notice cannot undo a success.

Top-up

stateDiagram-v2
    [*] --> CREATED
    CREATED --> PENDING: PSP accepted
    CREATED --> FAILED: PSP rejected
    CREATED --> UNKNOWN: PSP call timed out
    UNKNOWN --> PENDING: status query found it
    UNKNOWN --> FAILED: none found after grace period
    PENDING --> REQUIRES_ACTION: 3-D Secure needed
    REQUIRES_ACTION --> PENDING: customer authenticated
    REQUIRES_ACTION --> FAILED: authentication expired
    PENDING --> SUCCEEDED: payment confirmed
    PENDING --> FAILED: payment declined
    SUCCEEDED --> REFUNDED: full refund posted
    SUCCEEDED --> [*]
    FAILED --> [*]
    REFUNDED --> [*]

The wallet is credited only on the move to SUCCEEDED, and that transition posts the journal in the same transaction.

Withdrawal

stateDiagram-v2
    [*] --> REQUESTED
    REQUESTED --> REJECTED: limits or risk
    REQUESTED --> HELD: funds reserved
    HELD --> SUBMITTED: payout created
    HELD --> UNKNOWN: payout call timed out
    UNKNOWN --> SUBMITTED: status query found it
    UNKNOWN --> HELD: none found, retry same key
    SUBMITTED --> PAID: payout paid
    SUBMITTED --> RELEASED: payout failed
    PAID --> RETURNED: bank returned funds
    PAID --> [*]
    RETURNED --> [*]
    RELEASED --> [*]
    REJECTED --> [*]

A bank can return a payout days after it was paid, for example to a closed account. RETURNED posts a new journal that credits the wallet back; it never edits the original entries.

Hold

stateDiagram-v2
    [*] --> ACTIVE: hold placed
    ACTIVE --> CAPTURED: payout paid
    ACTIVE --> RELEASED: payout failed
    ACTIVE --> ESCALATED: no outcome in 3 days
    ESCALATED --> CAPTURED: ops confirms paid
    ESCALATED --> RELEASED: ops confirms not paid
    CAPTURED --> [*]
    RELEASED --> [*]

A hold never expires on its own. Releasing money whose payout might have succeeded would let the user spend it twice, so an old hold goes to a person instead.

Enforcing transitions

The allowed transitions live in one EnumMap<Status, Set<Status>> inside PaymentStateMachine. Each change is a conditional update, so two workers handling the same payment cannot both win:

UPDATE payments
SET status = :next, version = version + 1, updated_at = now()
WHERE id = :id AND status = :expectedCurrent;

Zero updated rows means another webhook or the resolver moved the payment first. The handler re-reads the row and either stops or applies the next legal step.

Design notes

  • Platform accounts have no owner. NULLS NOT DISTINCT (PostgreSQL 15 and later) still allows only one fee revenue account per currency.

  • Partitions follow time. A scheduled job or pg_partman creates next month's partition in advance; old partitions move to cheaper storage but stay queryable for the retention period.

  • Balances live apart from entries. account_balances is small and hot, so row locks never touch the large entry table.

Invariant check

This query runs nightly and after any incident. It must return no rows; any result pages the on-call engineer.

SELECT journal_id, currency
FROM journal_entries
WHERE created_at >= now() - interval '1 day'
GROUP BY journal_id, currency
HAVING sum(CASE direction WHEN 'DEBIT' THEN amount_minor ELSE -amount_minor END) <> 0;

A second job compares each balance with its last verified snapshot plus the day's entries, so it never scans the full history.

9. API design

The public API is REST over HTTPS with OAuth2 bearer tokens, and every endpoint that moves money requires an Idempotency-Key header. Errors use RFC 9457 problem details with a stable code field.

Webhook endpoint

  1. Verify the HMAC signature and reject timestamps older than 5 minutes, which blocks replayed requests.

  2. Insert the raw event into webhook_events; a duplicate key means it was already received, so return 200.

  3. Return 2xx within 2 seconds and process the stored event asynchronously.

  4. For events that credit money, re-fetch the object from the PSP API before posting a journal.

The endpoint sits on an internal path behind the gateway, accepts only the PSP's published source addresses where the PSP offers them, and never returns internal details in errors.

10. Reconciliation, risk and limits

A daily reconciliation proves the ledger matches what the PSP and bank actually moved, and limits stop money from leaving before fraud can be caught.

Daily reconciliation

flowchart LR
    SR["PSP settlement report"] --> IMP["Import and normalise"]
    BS["Bank statement"] --> IMP
    IMP --> MAT["Match on reference,<br/>amount and currency"]
    LED[("Ledger and payments")] --> MAT
    MAT -->|matched| SET["Post settlement journal"]
    MAT -->|timing difference| NXT["Carry to next run"]
    MAT -->|mismatch or missing| BRK["Break queue"]
    BRK --> FIX["Ops fixes with<br/>a reversing journal"]

This is a three-way match: internal records, the PSP's report and the bank statement must all agree on each settled amount.

CaseExampleResolution
MatchedPSP settled 100.00 for top-up T1; ledger shows T1 succeeded for 100.00Post the settlement journal: bank cash and PSP fees against PSP receivable
Timing differenceCaptured at 23:59, settled the next dayCarry forward; alert if still open after 3 days
Amount mismatchPSP settled 99.00, ledger shows 100.00Break: check fees and partial captures
PSP has it, ledger does notCard charged, but the webhook and the resolver both missed itBreak: verify, then credit the user
Ledger has it, PSP does notLedger credited a top-up the PSP reports as failedBreak, top priority: freeze the amount and reverse

Targets: at least 99.5% of items match automatically, and no break stays open longer than 48 hours.

Velocity limits

  • Counters in Redis. Keys such as vel:{userId}:out:{date} hold today's outgoing total and expire after 48 hours.

  • Reserve, then confirm. A Lua script checks the limit and increments atomically before the transfer; a failed transfer decrements it again.

  • Redis is not the source of truth. If Redis is down, the service sums today's outgoing entries in PostgreSQL, which is slower but correct.

  • Several windows. Separate counters cover amount per day, transfers per hour, and new recipients per day.

Risk scoring

Before money moves, the transfer calls the risk service with device, amount, recipient history and velocity features. The call has a 150 ms timeout.

If risk times out, transfers under EUR 50 continue and larger ones wait for review, so an outage fails safe without blocking small everyday payments. Every decision and its features go to Kafka, which gives the fraud team training data and an audit trail.

Security and compliance

  • No card data. The app collects card details through the PSP's SDK or hosted fields, so card numbers never reach our servers and PCI DSS scope stays small.

  • Authentication. OAuth2 and OpenID Connect with short-lived tokens, plus step-up authentication for transfers above EUR 500.

  • Encryption. TLS for all traffic, encrypted storage, and envelope encryption through a key management service for personal data columns.

  • Tamper resistance. The application role cannot update or delete ledger rows; corrections are reversing journals approved by two people.

  • Audit. Every operator action is logged to write-once storage with who, what, when and why.

  • Anti-money laundering. Transaction monitoring consumes Kafka events and raises cases for review and reporting.

  • Privacy and retention. A deletion request pseudonymises the person, while journal entries stay for the legally required retention period.

13. Interview questions and model answers

These are the questions a payments design interview usually reaches, each with an answer that takes under a minute to give.

  1. How do you stop a retried request from charging twice? Every money-moving request carries an idempotency key with a unique constraint. The stored response is saved in the same transaction as the money movement and replayed on retries. Calls to the PSP also carry our payment id as their idempotency key.

  2. Why double-entry instead of a balance column? A balance column cannot explain itself or prove it is right. Double-entry records where every unit came from and went to, makes conservation checkable, and turns corrections into visible reversing entries.

  3. Two transfers debit the same wallet at once. What happens? Both lock the balance row with SELECT ... FOR UPDATE, so the second waits. It then re-reads the available balance and fails with insufficient funds if needed. Locking in account id order prevents deadlocks when transfers cross.

  4. The PSP call timed out. Did the customer pay? We don't know yet, so the payment moves to UNKNOWN, never FAILED. A resolver queries the PSP by our reference until the outcome is final, and retries reuse the same idempotency key.

  5. How do you publish events without losing them or sending phantom ones? The event is written to an outbox table in the same transaction as the money movement. A relay publishes it with at-least-once delivery, and consumers ignore event ids they have already processed.

  6. How would you handle 100 times the traffic? First partitions, replicas and read models, then sub-accounts for hot merchants. Only then shard wallets by user id, keeping same-shard transfers local and running cross-shard transfers as a saga through a transit account.

  7. A user spent the money before a refund reached the merchant. What now? The refund still debits the merchant's payable account and credits the user. If the merchant balance is too low, the platform records a receivable from the merchant and recovers it from the next settlement.

  8. What does reconciliation catch that tests cannot? Lost webhooks, PSP-side reversals, fee changes, bank returns and production bugs that tests never modelled. Matching the ledger daily against the PSP and bank is how a payments team finds out it is wrong before a customer does.

  9. Which part would you split into a separate service first? Notifications and risk analytics, because they only consume events and never write money. The ledger stays last, since splitting it would turn local transactions into distributed ones.

  10. How do you store and send money amounts? As a long count of minor units plus an ISO 4217 currency code, and as decimal strings in JSON. BigDecimal with an explicit rounding mode is used only for fees and exchange rates; floating point is never used.
