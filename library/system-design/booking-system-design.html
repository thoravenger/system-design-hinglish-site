Topic 01

Requirements clarify karo, model unify karo

Yeh pehla 5 minute pura interview ka tone set karta hai. Yahin par candidate jeetta ya haarta hai.

Problem TRAP

“Design a booking system.”Interviewer, minute 0

  • Scope infinite hai. Movie, hotel, flight, restaurant — candidate ko lagta hai chaaron alag systems hain, toh woh ek generic “sab kuch” design banane lagta hai jo kisi ke liye kaam nahi karta.
  • Seedha table banane lagna. 90% log minute 1 par CREATE TABLE booking likh dete hain. Interviewer ko lagta hai isne socha hi nahi.
  • NFR poochha hi nahi. Agar “no double booking” ko hard constraint declare nahi kiya, toh baaki poora design bekaar hai — kyunki wahi is problem ka asli core hai.
  • Read vs write ratio ignore. Booking system 100:1 read-heavy hai, par candidate pura design write path ke around banata hai.
Red flag: “Main assume kar raha hoon…” bolke 4 assumption ek saath thok dena, bina interviewer se confirm kiye.

Solution FRAMEWORK

Step 1 — Ek line me unify karo. Chaaron domain ka core ek hi hai:

The one-liner: “Ye ek finite, exclusive, time-bound resource allocation problem hai. Movie me resource = seat × show, hotel me = room × night, flight me = seat × leg, restaurant me = table × slot. Inventory model same rahega, sirf allocation rule alag hoga.”
DomainResourceTime windowAllocation ka twist
MovieSeatShow (fixed 3 hrs)Contiguous seats, single-seat gap avoid
HotelRoomDate range (N nights)Interval overlap — har night free honi chahiye
FlightSeatLeg (fixed)Cabin class + deliberate overbooking
RestaurantTableSlot + turn timeParty size fit + table merging

Step 2 — FR aur NFR alag likho.

FUNCTIONALSearch availability · Seat map dekho · Hold karo · Pay karo · Confirm · Cancel + refund · Booking history
OUT OF SCOPERecommendations, reviews, loyalty points, dynamic ads — bol do ki skip kar rahe ho

Yeh line bolo: “Availability data ko main advisory maanunga — user ko jo seat map dikh raha hai woh stale ho sakta hai. Truth sirf booking commit ke time par decide hoti hai.” Isse tum poore caching design ko pehle hi justify kar dete ho. SDE-2
Topic 02

Capacity estimation — numbers se design justify karo

Estimation ka maqsad exact number nahi hai. Maqsad hai ek aisa number nikalna jo aage ka design decision drive kare.

Problem TRAP

  • Average QPS nikaal ke ruk jaana. “10M DAU / 86400 = 115 QPS, easy hai.” Ye galat picture deta hai — booking traffic bursty hoti hai.
  • Storage calculate karke chhod dena. Number nikaala par usse koi decision nahi liya. Interviewer poochta hai “toh isse kya conclude hua?” aur candidate chup.
  • Hot partition miss karna. Traffic uniform nahi hai — ek blockbuster release ka ek show poore system ka 30% traffic le sakta hai.
Red flag: Peak factor apply na karna. Average par capacity plan karoge toh release day par system gir jaayega.

Solution MATH

Round numbers lo, peak factor lagao, phir har number se ek decision nikalo.

Yeh ek line poore interview ka rukh badal deti hai — ab tum sharding, Redis lock aur waiting room sab justify kar sakte ho.

Topic 03

API design — hold aur book alag endpoints hain

Sabse bada API-level insight: booking ek single call nahi hai. Ye do-phase protocol hai.

Problem TRAP

“Toh user seat select karega aur POST /book chalega?”Interviewer, testing your API sense

  • Single endpoint jisme payment bhi ho. POST /book jo seat lock kare, payment gateway call kare, aur confirm kare — matlab DB lock 30 second tak payment gateway ka wait karega. Ye system ko maar dega.
  • Idempotency nahi. User ne double-tap kiya → 2 bookings, 2 charges. Mobile network flaky hai, retry hona hi hai.
  • GET par side-effect. Kuch log GET /seats?lock=true jaisa kuch bana dete hain. HTTP semantics tod diya.
  • Status code galat. Seat already taken par 200 OK with {"success": false}. Client retry logic likh hi nahi sakta.

Solution CONTRACT

Hold aur confirm ko alag karo. Hold chhota aur transactional hai; payment lamba aur external hai.

L10–L11POST /v1/holds ek naya resource banata hai (hold), isliye POST hai GET nahi. Idempotency-Key client-generated UUID hai — same key se dobara call aaya toh server naya hold nahi banayega, purana wahi return karega. Double-tap se double hold nahi banega.
L14409 CONFLICT — resource state ki wajah se request fail hui. Client ko exactly pata hai ki 102 gaya, 101 abhi bhi mil sakta hai. 200 + success:false se ye information kabhi nahi milti.
L17Payment intent alag call hai kyunki PG round-trip 2–30 second le sakta hai. Is beech koi database row locked nahi honi chahiye — seat Redis+DB me HELD hai, jo lock nahi reservation hai.
L21–L23Confirm request me unitIds dobara nahi bheje — sirf holdId. Server-side truth hi source of truth hai. Client kabhi bhi price ya seat list resend nahi karega (tampering surface hata diya).
L25410 GONE vs 404: 410 ka matlab “ye tha, ab expire ho gaya, dobara mat maango”. Client retry loop turant band kar dega. Ye chhoti detail interviewer notice karta hai.
L29202 ACCEPTED — refund synchronous nahi hai, bank 3–5 din leta hai. Isliye request accept karke async process karo.
L32Webhook par pgEventId ka unique index rakho. Payment gateways at-least-once deliver karte hain — same event 3 baar aa sakta hai.
English takeaway: Split the write path into two short transactions with a long, lock-free gap in between. Hold is cheap and reversible; confirm is final. Never let an external network call sit inside a database transaction.
Topic 04

HLD — services kaise cut karein

Service boundary ka rule: jo cheez ek saath transactionally consistent honi chahiye, woh ek service me rahegi.

Problem TRAP

  • Microservice ka over-split. Candidate 12 boxes bana deta hai — SeatService, LockService, HoldService, ReservationService. Ab seat hold karne ke liye 4 network hops chahiye, aur distributed transaction ka narak khul gaya.
  • Inventory aur Booking alag services me. Sunne me clean lagta hai, par ab “seat lock karo + booking row banao” atomic nahi ho sakta. 2PC lagana padega — jo interviewer ko dekh ke hi bura lagta hai.
  • Sirf boxes aur arrows, koi reasoning nahi. Diagram bana diya, par “Kafka kyun?” ka jawab “because scalable” hai.
  • Payment gateway ko andar dikhana. PG external hai, uski latency aur failure tumhare control me nahi — diagram me ye clearly boundary ke bahar hona chahiye.
Red flag: Cache ko har box ke aage laga dena bina ye bataye ki kaun sa data cache ho raha hai aur invalidate kaise hoga.

Topic 05

Schema — jahan double booking rokni physically shuru hoti hai

Sabse elegant trick yahi hai: hotel ka date-range problem ko discrete rows me tod do, taaki database ka unique constraint kaam kar sake.

Problem TRAP

  • Counter-based inventory. rooms_available INT rakh ke available = available - 1. Ab tum bata hi nahi sakte kaunsa room book hua. Aur lost-update race guaranteed hai.
  • Hotel ko range me store karna. booking(room_id, check_in, check_out). Ab overlap check karne ke liye har baar query chalani padegi — aur do concurrent requests dono ko “no overlap” dikhega. Classic double booking.
  • Seat status booking table se derive karna. Availability nikaalne ke liye poori booking table scan. 300 seats ke liye 50K rows scan — har page load par.
  • Money ko FLOAT me rakhna. ₹0.01 ka rounding error audit me pakda jaayega.
Interviewer ka killer follow-up: “Do request exact same microsecond par aayi. Tumhare schema me kaun sa constraint unhe rokega?” Agar jawab “application code check karega” hai — tum fail ho gaye.

Solution SCHEMA

Ek row = ek bookable unit × ek time window. Ye row hi truth hai, aur database ka unique constraint hi final referee hai.

Topic 06

Double booking — ye poore interview ka dil hai

Baaki sab topics support hain. Agar tum sirf ek topic deeply jaante ho, toh ye hona chahiye.

Problem THE RACE

L12–L19Poora check-and-set ek hi SQL statement me hai. Database har row par internally lock leta hai, isliye read aur write ke beech koi gap hi nahi bacha. TOCTOU window zero ho gayi. Ye pura Topic 06 ka jawab hai.
L19AND status = 'AVAILABLE' — yahi ek line hai jo double booking rokti hai. Agar B ki request A ke baad aayi, tab tak status HELD ho chuka hai, toh WHERE match nahi karega aur row update hi nahi hogi. B ko 0 rows milenge.
L21Return type int hai — kitni rows update hui. Ye API ka sabse important part hai. Agar tumne 2 seats maange aur 1 mila, matlab ek seat kisi aur ne le li → poore transaction ko rollback karo. Silently 1 seat mat de dena.
L10clearAutomatically=true — bulk update JPA persistence context ko bypass karta hai, toh cached entities stale ho jaate. Ye flag unhe clear kar deta hai. Ye chhoti detail production bug bachati hai.
L28PESSIMISTIC_WRITE = SQL me SELECT … FOR UPDATE. Ye row par exclusive lock leta hai jab tak transaction commit na ho. Zyada strong hai, isliye sirf tab use karo jab decision lene ke liye row ka data padhna zaroori ho.
L29–L30ORDER BY u.id aur method ka naam …InDeterministicOrder — deadlock prevention. Agar A seats [5,9] lock kare aur B [9,5], dono ek dusre ka wait karenge → deadlock. Hamesha same order me lock lo (yahan ID ascending), deadlock structurally impossible ho jaata hai. SDE-3
Golden rule — ise yaad rakho: DB transaction ke andar kabhi bhi external network call mat karo. Payment gateway 30 second le sakta hai; agar us dauraan row lock hai toh 300-seat show ka poora inventory freeze ho jaayega. Isiliye hold aur confirm alag transactions hain.
Topic 07

Seat hold aur expiry — “7 minutes remaining” ke peeche kya hai

Hold ek reservation hai, lock nahi. Ye distinction interviewer ko bolna zaroori hai.

Problem TRAP

“User ne seat select ki, phir payment page par tab band kar diya. Seat kab wapas milegi?”Interviewer

  • Sirf Redis TTL par bharosa. Redis restart hua, ya maxmemory-policy allkeys-lru ne key evict kar di, ya failover me replica purana tha — DB me seat hamesha ke liye HELD reh gayi. Inventory leak.
  • Sirf DB sweeper par bharosa. Sweeper har 30s chalta hai, par hot path par har request DB hit karegi. Redis ka fast-reject benefit gaya.
  • Lock kisi aur ka delete kar dena. A ka hold expire hua, B ne seat li. Tabhi A ka slow release call aaya aur usne B ka lock delete kar diya. Ab seat do jagah available hai.
  • Hold TTL bahut chhota ya bahut bada. 2 min → UPI OTP me hi nikal jaata hai, user frustrated. 30 min → scalper 300 seats block karke inventory maar dega.

Solution BELT + BRACES

Do independent expiry mechanisms. Redis TTL fast path ke liye, DB sweeper safety net ke liye. Dono me se koi bhi mare, correctness bachi rahegi.

Topic 08

Idempotency — “user ka paisa do baar mat kaato”

Distributed system me network retry guaranteed hai. Sawaal ye nahi ki retry hogi ya nahi — sawaal ye hai ki tum uske liye taiyaar ho ya nahi.

Problem TRAP

“Booking confirm hui, response bhejte waqt network toot gaya. Client retry karega. Ab?”Interviewer

  • Do bookings, do charges. Server ne kaam kar liya tha, sirf response nahi pahuncha. Retry ne dobara sab kar diya.
  • Payment webhook duplicate. Razorpay/Stripe at-least-once deliver karte hain. Same payment.captured event 3 baar aa sakta hai — 3 confirmation SMS chale gaye.
  • “Existing check kar lenge” wala fix. if (bookingRepo.existsByUserAndUnit(...)) — ye khud TOCTOU hai. Do concurrent retries dono ko “exists = false” dikhega.
  • Idempotency key server-side generate karna. Toh har retry par nayi key banegi — poora point hi khatam.

Solution KEY + CONSTRAINT

Client key banata hai, database unique constraint enforce karta hai, server pehla response replay karta hai.

Saga + Outbox — jab paisa kat gaya par seat nahi mili

Yahi woh sawaal hai jahan SDE-2 aur SDE-3 alag hote hain.

Problem TRAP

“Payment success ho gaya, par booking confirm karte waqt DB crash ho gaya. User ka paisa kahan hai?”Interviewer, the nightmare scenario

  • 2PC / XA transaction suggest karna. Payment gateway external hai — usme tum coordinator nahi ban sakte. Aur 2PC coordinator failure par sab kuch block kar deta hai.

Topic 13

Sharding — shard key hi sabse bada decision hai

Ek galat shard key aur tumhara har booking distributed transaction ban jaata hai.

Problem TRAP

  • user_id par inventory shard karna. Ek show ki seats 50 shards par bikhri hui. Ab 3 seats ek saath book karne ke liye 3 shards par atomic write chahiye → 2PC. Design mar gaya.
  • Auto-increment ID par shard karna. Naya data hamesha aakhri shard par — write hotspot. Baaki shards idle.
  • Hot shard ignore karna. Ek blockbuster release ke saare shows ek hi venue ke hain → ek shard par 40% traffic.
  • Din 1 se shard karna. 146 GB/year ke liye sharding? Premature. Ye complexity bina zarurat ke add karna hai.

Solution CO-LOCATE

The rule: Shard key aisi choose karo ki ek transaction ka saara data ek hi shard par ho. Booking ke liye woh key hai event_id — ek show/flight/night ki saari seats ek shard par. Har hold ek single-shard local transaction ban jaata hai. 2PC ki zarurat hi nahi padti.

Tradeoff jo tum khud uthao: booking aur inventory_unit ab alag shards par ho sakte hain — isliye inhe atomically likhne ke liye saga chahiye (Topic 09). Ye deliberate choice hai: booking-history read path fast rakhna vs write path me saga complexity. Interviewer ko bolo ki tumne dono trade offs dekhe hain. SDE-3

Hot shard ka ilaaj:

  • Virtual buckets. event_id ko direct shard par map mat karo — 4096 virtual buckets par map karo, phir buckets ko shards par. Hot bucket ko rebalance karna ab bina resharding possible hai.
  • Isolation, scale nahi. Blockbuster shows ko dedicated shard par pin kar do. Woh gire toh baaki system chalta rahega — blast radius kam.
  • Read replicas seat-map reads ke liye. Writes hamesha primary par (CP path).
Honest answer jo interviewer ko impress karta hai: “146 GB/year par mujhe sharding ki technically zarurat nahi hai — ek Postgres primary aur do replicas kaafi hain. Main sharding failure isolation aur contention ke liye karunga, storage ke liye nahi. Aur jab tak zarurat na ho, main isse day 1 par nahi karunga.”
Topic 14

Surge — jab 5 lakh log 300 seats ke liye aate hain

IPL final, Coldplay tickets, Tatkal. Yahi sabse acha follow-up question hai.

Problem TRAP

  • “Auto-scale kar denge” bol dena. Pods scale ho jaayenge, par database primary scale nahi hota. Aur 300 seats ke liye 500K requests — 99.94% ko toh fail hi hona hai.
  • Sabko andar aane dena. Har request DB tak jaayegi, connection pool khatam, aur jo log genuinely book kar sakte the woh bhi fail honge.
  • Retry storm. Sab fail hue, sabne retry kiya, load double. Classic congestive collapse.
  • Bots ignore karna. Scalers 10,000 requests/sec maar rahe hain aur asli user pehunch hi nahi pa raha.

Solution ADMISSION CONTROL

Core idea: Backend ko utni hi traffic do jitni woh handle kar sakta hai. Baaki ko honestly queue me rakho.

  • Virtual waiting room. Sale khulne se pehle users ko ek queue me daalo, signed token do jisme position ho. Har second sirf N tokens ko booking service tak jaane do (N = measured capacity). Baaki ko live position aur ETA dikhao — blank error page se hazaar guna behtar.
  • Rate limit multi-layer: per-IP (bots), per-user (fairness), per-event (backend protection). Token bucket at gateway.
  • Queue-based booking. Peak par requests ko Kafka par daalo, worker unhe controlled rate par process kare. Sync response ki jagah polling ya WebSocket se status do.
  • Load shedding. Overload par naye users ko reject karo, jo already funnel me hain unhe nahi. Ek adha-poora booking flow todna sabse bura outcome hai.
  • Exponential backoff + jitter client par mandatory. Retry-After header bhejo aur client usse honor kare.
  • Cache warming. Sale se 10 min pehle seat map aur metadata pre-load kar do — cold cache par surge sabse zyada khatarnak hoti hai.
Punchline: “500K users aur 300 seats me, 99.94% ko fail hona hi hai. Mera kaam unhe fail hone se bachana nahi hai — mera kaam unhe jaldi, saaf aur imaandari se bataana hai ki woh line me kahan hain. Yeh engineering problem se zyada UX problem hai, aur design dono ko address karna chahiye.”

24 questions jo actually poochhe jaate hain

Pehle khud jawab socho, phir kholo. Har answer me pehle short Hinglish reasoning hai, phir ek English line jo tum interview me bol sakte ho.

Q1Double booking kya hai aur ye kyun hoti hai?

Jab do requests ek hi seat ko read karti hain, dono ko “AVAILABLE” dikhta hai, aur dono write kar deti hain. Beech me koi atomicity nahi hai. Isse TOCTOU (Time-Of-Check to Time-Of-Use) race kehte hain. @Transactional lagane se ye theek nahi hota, kyunki Postgres ka default READ COMMITTED isolation is pattern ko allow karta hai.

Say this: “It's a lost-update race. The fix is to collapse check and write into one atomic operation — a conditional UPDATE … WHERE status = 'AVAILABLE' — and back it with a unique constraint as the final guarantee.”

Q2Optimistic aur pessimistic locking me kya farak hai? Kab kya use karoge?

Pessimistic: pehle lock lo, phir kaam karo (SELECT … FOR UPDATE). Doosre wait karte hain. Optimistic: bina lock kaam karo, likhte waqt version check karo; mismatch hua toh fail karke retry karo.

Rule of thumb: low contention → optimistic (kyunki conflict kam hai, lock ki cost bekaar hai). High contention → pessimistic (kyunki optimistic me har baar retry karoge, jo aur mehnga hai).

Say this: “For a normal Tuesday show, optimistic. For the front row of an opening-night blockbuster, pessimistic — retry storms cost more than lock waits when conflict probability is high.”

Q3Idempotency kya hai? Ek booking example do.

Same operation kitni bhi baar chalao, result wahi rahe. User ne “Pay” do baar tap kiya — dono requests me same Idempotency-Key hoga, isliye server sirf ek booking banayega aur doosri baar wahi purana response replay karega.

Implementation: key ko database me unique constraint ke saath store karo. Duplicate insert fail hoga, aur tum stored response return kar doge.

Say this: “Client generates the key, the database enforces it, the server replays the original response — not an error.”

Q4Seat book na ho paane par kaun sa HTTP status code?

409 CONFLICT — resource ki current state ki wajah se request fail hui. Response body me batao kaun si seat gayi, taaki client sirf usi ko re-select karwa sake.

Aur agar hold expire ho gaya hai toh 410 GONE — matlab “ye tha, ab nahi hai, retry mat karo”. 200 OK with success:false sabse kharab hai, kyunki client retry logic likh hi nahi sakta.

Q5Availability ke liye counter (seats_left) rakhna sahi hai?

Nahi. Do problems: (1) counter batata hi nahi ki kaunsi seat book hui — seat map dikhana impossible. (2) seats_left = seats_left - 1 classic lost update hai.

Sahi tareeka: har bookable unit ki apni row (inventory_unit), aur count usi se derive karo (ya cache karo 10s TTL par).

Say this: “Model the units, derive the count. Never model the count and try to derive the units.”

Q6Paise ko database me kaise store karoge?

BIGINT me smallest unit (paise/cents) — ₹250.50 → 25050. Kabhi FLOAT/DOUBLE nahi, kyunki 0.1 + 0.2 ≠ 0.3 aur finance me ye audit failure hai. DECIMAL bhi chalega par integer arithmetic tez aur simple hai. Currency code alag column me rakho.

Q7Booking ke liye kaunse indexes banaoge?

(1) UNIQUE(event_id, resource_id) — correctness ka index. (2) Partial index ON inventory_unit(event_id) WHERE status='AVAILABLE' — seat map query ke liye, aur ye chhota rehta hai. (3) (hold_expires_at) WHERE status='HELD' — sweeper ke liye. (4) booking(user_id, created_at DESC) — “meri bookings”. (5) UNIQUE(idempotency_key).

Har extra index write ko slow karta hai — sirf woh banao jinke liye actual query hai.

Q8User payment page par tab band kar de toh seat ka kya hoga?

Hold ka TTL hai (~7 min). Do mechanisms use hote hain: Redis key apne aap expire ho jaati hai (fast path), aur ek DB sweeper har 30s expired holds ko AVAILABLE kar deta hai (safety net). Dono isliye kyunki Redis eviction guaranteed nahi hai — key evict ho gayi toh DB me seat hamesha ke liye HELD reh jaati.

Q9Booking ko ek hi API call me kyun nahi kar dete?

Kyunki us call ke andar payment gateway ka network call aayega, jo 2–30 second le sakta hai. Agar us dauraan DB row lock hai toh poora show freeze — 300 seats ka inventory ek slow payment ki wajah se blocked.

Isliye do chhote transactions: hold (fast, reversible) aur confirm (fast, final), beech me ek lock-free gap jisme payment hota hai.

Say this: “Never hold a database lock across an external network call. That single rule shapes the entire API.”

Q10Hotel booking me date-range overlap kaise handle karoge?

Range ko store mat karo — usse discrete rows me todo. room_night(room_id, stay_date) with composite primary key. 12–15 Sep ki booking = 3 rows (12, 13, 14). Ab agar koi 13–16 book kare toh 13 aur 14 par PK clash hoga aur transaction fail ho jaayegi.

Alternative (Postgres-specific): EXCLUDE USING gist (room_id WITH =, daterange WITH &&) — ye bhi correct hai par portable nahi.

Say this: “Turn the interval problem into a discrete-key problem and let the primary key do the concurrency control.”

Q11Payment ke baad booking confirm karte waqt service crash ho gayi. Recovery?

Isiliye saga log durable hota hai. Har step ke baad DB me state likhi jaati hai. Ek recovery worker un sagas ko dhoondhta hai jo N minute se PAYMENT_CAPTURED par atke hain, aur do me se ek karta hai: aage badha ke confirm kar deta hai (agar hold abhi valid hai), ya refund compensation chala deta hai.

In-memory compensation stack crash-safe nahi hai — isliye saga state database me honi chahiye.

Q12Outbox pattern kya solve karta hai?

Dual-write problem. db.save() ke baad kafka.send() — dono alag systems hain, atomically nahi ho sakte. DB commit hua aur Kafka publish fail — SMS kabhi nahi jaayega.

Fix: event ko usi transaction me outbox table me likho. Ek alag poller usse padh ke Kafka par bhejta hai. Ab ya dono likhe jaate hain ya koi nahi. Delivery at-least-once hai, isliye consumers ko idempotent banana zaroori hai.

Q13Seat map cache karoge? Stale data ka kya?

Haan, par sirf 2 second TTL ke saath, aur booking event par explicit invalidation. Aur sabse important — UI par honestly likho “final availability is confirmed at checkout”. Isse staleness bug nahi, documented behaviour ban jaata hai.

Stampede se bachne ke liye request coalescing: cache miss par Redis lock se sirf ek thread DB jaaye, baaki stale serve karein. Plus TTL par ±20% jitter.

Q14Multiple pods par @Scheduled sweeper — problem?

6 pods = 6 sweepers ek saath chalenge, ek dusre se ladenge, DB par bekaar load. Fix: ShedLock (@SchedulerLock) — ek shared lock jo ensure karta hai ki har tick par sirf ek instance chale.

Plus query me FOR UPDATE SKIP LOCKED lagao taaki agar do workers overlap bhi kar jaayein toh ek dusre ka wait na karein, bas alag rows utha lein.

Q15Hold TTL 7 minute hi kyun? 2 ya 30 kyun nahi?

Guess se nahi, data se. payment_completion_duration ka p95 dekho aur usse ~2× rakho. India me UPI + OTP typically 90–150s leta hai, toh 7 min comfortable buffer hai.

Bahut chhota (2 min) → genuine users OTP me hi fail ho jaate hain. Bahut bada (30 min) → scalpers inventory block karke resale karte hain. High-demand shows par TTL ghata ke 4 min kar do, aur ye config hona chahiye, hardcoded nahi.

Q16Naya domain (bus booking) add karna ho toh kitna code badlega?

Ek nayi class: BusSeatAllocator implements InventoryAllocator, @Component annotation ke saath. Bas. Spring usse automatically List<InventoryAllocator> me inject kar dega aur registry khud build ho jaayegi.

Zero existing files modified. Ye Open/Closed principle ka live proof hai — aur yahi jawab interviewer sunna chahta hai.

Q17Redis lock lene ke baad process GC pause me chala gaya, lock expire ho gaya, aur doosre ne le liya. Ab?

Ye Redlock ki classic criticism hai (Martin Kleppmann). Distributed lock akela correctness guarantee nahi de sakta — kyunki lock hone aur kaam karne ke beech unbounded pause aa sakta hai.

Do fixes: (1) Fencing token — har lock ke saath monotonically increasing number do, aur storage layer purane token wali writes reject kare. (2) Behtar: correctness ke liye lock par depend hi mat karo — Redis sirf fast-reject ke liye rakho, aur asli guarantee database ke conditional update + unique constraint se lo.

Say this: “I treat Redis as an optimisation, not a correctness mechanism. If Redis is completely wrong, my system gets slower, never incorrect.”

Q18Booking system me CAP kahan apply hota hai?

Ek hi jawab poore system par nahi lagta — path ke hisaab se alag hai:

Inventory/booking = CP. Partition me availability sacrifice karo. Booking fail hona acceptable hai; double booking nahi. Isliye single-region writes with synchronous replication.

Search/browse = AP. Stale results dikhana blank page se behtar hai. Async replication, eventual consistency.

Say this: “CAP is a per-operation choice, not a per-system one. Search is AP, inventory is CP, and I'll pay the latency cost only where correctness demands it.”

Q19Multi-region deployment — inventory ka kya karoge?

Inventory par multi-master mat karo — cross-region consensus par har booking me 100ms+ lagega, aur conflict resolution me double booking ka risk hai.

Sahi approach: inventory ko geographically partition karo. Har event ka ek “home region” ho (jahan venue hai), aur us event ke saare writes wahin jaayein. Reads har region me replicate ho. Ye natural hai — Bangalore ka movie show mostly Bangalore se book hota hai.

Region failure par: read-only degraded mode, ya failover ke saath explicit RPO/RTO acceptance. Split-brain se bachne ke liye manual/quorum-based failover.

Q20Exactly-once delivery guarantee karoge?

Exactly-once delivery distributed systems me possible nahi hai — ye Two Generals problem hai. Jo possible hai woh hai at-least-once delivery + idempotent consumer = effectively-once processing.

Practically: har event me unique eventId, consumer usse ek dedupe store (Redis SETNX ya DB unique constraint) me check kare. Kafka ka transactional producer + read_committed isolation broker ke andar exactly-once deta hai, par jaise hi tum external system (SMS gateway) chhute ho, guarantee toot jaati hai.

Q21Deadlock kaise rokoge jab user multiple seats ek saath book kare?

Deterministic lock ordering. Sab clients seats ko hamesha same order me lock karein — ID ascending. Code me bas unitIds.stream().sorted().

Bina iske: A locks [5,9], B locks [9,5] — dono ek dusre ka wait karenge. Sorting ke baad dono 5 pehle lenge, ek jeetega, doosra wait karega, deadlock structurally impossible.

Backup: DB me lock_timeout set karo, aur deadlock victim ko retry with jittered backoff.

Q22Ek show ka shard 40% traffic le raha hai. Kya karoge?

Pehle accept karo ki ye logically unavoidable hai — ek show ki seats ek jagah honi hi chahiye, warna har booking distributed transaction ban jaayega.

Toh optimize karo: (1) Virtual buckets — event ko 4096 buckets par map karo, buckets ko shards par; hot bucket ko bina resharding move kar sakte ho. (2) Dedicated shard blockbuster events ke liye — blast radius contain. (3) Us shard ke aage aggressive Redis fast-reject taaki 99% requests DB tak pahunche hi na. (4) Admission control — waiting room se traffic ko backend capacity par cap kar do.

Say this: “I'd contain it rather than eliminate it. Isolation beats redistribution when the hotspot is inherent to the domain.”

Q23Payment ho gaya par confirm fail. Compensation (refund) bhi fail. Ab?

Saga ko dead-letter queue me daalo aur turant alert karo — kisi ka asli paisa phansa hai, ye chupchaap swallow karne wali cheez nahi hai.

Phir: bounded retries with exponential backoff (refund APIs aksar transiently down hote hain), ek reconciliation job jo daily PG statements ko internal bookings se match kare, aur ops team ke liye manual resolution console. Customer ko proactively inform karo — usse support ticket khulne se pehle.

Say this: “Every saga needs a terminal manual-intervention path. Silence is the worst possible outcome when money is stuck.”

Q24Kaise prove karoge ki tumhara system double-book nahi karta?

Assertion se nahi, evidence se — teen layers:

1. Structural: UNIQUE(event_id, resource_id). Database physically do bookings allow hi nahi kar sakta, chahe application me kitne bhi bugs hon.

2. Test: Jepsen-style concurrency test — 1000 threads, ek hi seat, assert karo ki exactly ek success mila. Ye CI me chale, har commit par.

3. Runtime: Ek continuous invariant checker jo periodically GROUP BY (event_id, resource_id) HAVING count(*) > 1 chalaye. Ye counter hamesha zero hona chahiye — non-zero par immediate page.

Say this: “Constraint for prevention, chaos test for confidence, invariant monitor for proof. I don't trust code review to guarantee correctness.”
