Why a load balancer?

Load balancer ki zaroorat kyun padti hai?

Problem

ShopKart runs on one big server. During the 8 PM sale it gets about 35,000 requests per second. CPU hits 100%, requests queue up, and latency jumps from 200 ms to several seconds. If that one machine crashes, the whole site is down, and every deploy means downtime too.

ShopKart ek hi bade server pe chal raha hai. Raat 8 baje ki sale mein lagbhag 35,000 requests per second aati hain. CPU 100% pe atak jaata hai, requests queue mein lag jaati hain, aur latency 200 ms se kai seconds tak pahunch jaati hai. Woh ek machine crash hui toh poori site down, aur har deploy pe bhi downtime.

Solution

Run many identical, stateless servers and put a load balancer (LB) in front of them behind one virtual IP (VIP). Clients only ever talk to the VIP.

Kai identical, stateless servers chalao aur unke aage ek load balancer (LB) lagao jo ek virtual IP (VIP) ke peeche ho. Clients sirf VIP se baat karte hain.

BeforeUsersOne server at 100%
AfterUsersLB (VIP)S1S2S3S4

What the load balancer does

  1. Spreads requests across servers using an algorithm.Algorithm ki madad se requests ko servers mein baant-ta hai.
  2. Health-checks servers and stops sending traffic to dead ones.Servers ka health check karta hai aur dead server ko traffic bhejna band karta hai.
  3. Adds or removes servers without users noticing: scaling and zero-downtime deploys.Bina user ko pata chale servers add ya remove karta hai: scaling aur zero-downtime deploy.
  4. Terminates TLS and routes by path or host (at layer 7).TLS terminate karta hai aur path ya host ke hisaab se route karta hai (layer 7 pe).

A bigger machine (vertical scaling) has a hard ceiling and is still a single point of failure. Many small machines behind an LB (horizontal scaling) have no hard ceiling. That is why the LB exists.

Bada machine lena (vertical scaling) ki ek hard limit hai aur woh ab bhi single point of failure hai. LB ke peeche kai chhote machines (horizontal scaling) ki koi hard limit nahi. Isiliye LB hota hai.

Say this in the interview: "A load balancer turns one big box that can fail into N boxes that can be replaced."

Interview mein bolo: "Load balancer ek fail ho sakne wale bade box ko N replace ho sakne wale boxes mein badal deta hai."

Clarify requirements first

Pehle requirements clear karo

Problem

The interviewer only says "Design a load balancer." Jumping straight into algorithms is the most common mistake: you don't yet know the scale, the protocol, or what "good" means here.

Interviewer sirf itna bolta hai: "Design a load balancer." Seedha algorithms pe kood jaana sabse common galti hai: abhi na scale pata hai, na protocol, na yeh ki yahan "achha" ka matlab kya hai.

Solution

Ask these five questions, in this order

  1. How many users and requests, and how spiky? Decides capacity and instance count.Kitne users, kitni requests, peak kitna? Isse capacity aur instance count decide hota hai.
  2. Which protocols? HTTP/HTTPS, gRPC, WebSocket or raw TCP/UDP. Decides L4 vs L7.Kaunse protocols? HTTP/HTTPS, gRPC, WebSocket ya raw TCP/UDP. Isse L4 vs L7 decide hota hai.
  3. Must a user stick to one server? Decides hashing vs stateless balancing.Kya user ko ek hi server pe rehna zaroori hai? Isse hashing vs stateless balancing decide hota hai.
  4. One region or global users? Decides whether you need GeoDNS or a global edge.Ek region ya duniya bhar ke users? Isse GeoDNS ya global edge ki zaroorat decide hoti hai.
  5. Availability target and latency budget? Decides redundancy (N+1 or zone-level) and target utilization.Availability target aur latency budget kya hai? Isse redundancy (N+1 ya zone-level) aur target utilization decide hote hain.

Traffic: QPS and bandwidth

Traffic ka hisaab: QPS aur bandwidth

Problem

How much traffic must the LB tier carry at its busiest moment? Averages lie: a system sized for the average falls over every evening. We size for the peak.

Sabse busy waqt pe LB tier ko kitna traffic uthana hai? Average jhooth bolta hai: average ke hisaab se bana system har shaam gir jaata hai. Sizing hamesha peak ke liye.

Solution

average QPS = DAU × requests per user ÷ 86,400
peak QPS = average QPS × peak factor
bandwidth = peak QPS × (request + response size)
Requests per day50,000,000 × 201,000,000,000
Average QPS1,000,000,000 ÷ 86,400≈ 11,574
Peak QPS11,574 × 3≈ 34,722
Bytes per request2 KB in + 20 KB out22 KB
Peak bandwidth34,722 × 22 KB × 8 bits≈ 6.11 Gbps
  • Quick mental math: treat 86,400 as 100,000. Then 1 billion ÷ 10⁵ = 10K. Slightly low, fine for an interview; just say you are rounding.Jaldi ka mental math: 86,400 ko 1 lakh maan lo. Tab 1 billion ÷ 10⁵ = 10K. Thoda kam aata hai, interview ke liye theek hai; bas bol do ki round kar rahe ho.
  • Where the peak factor comes from: your real traffic graph, the busiest minute divided by the daily average. 2–5× is typical; flash sales and cricket-final moments can hit 10× or more.Peak factor kahan se aata hai: asli traffic graph se, sabse busy minute ÷ din ka average. 2–5× normal hai; flash sale ya cricket final jaise moments pe 10× se bhi zyada.
  • An L7 proxy carries every byte twice (client ↔ LB and LB ↔ backend), so the fleet's NICs see about 6.11 Gbps coming in and 6.11 Gbps going out at the same time. NICs are full duplex, so size each direction separately.L7 proxy har byte ko do baar uthata hai (client ↔ LB aur LB ↔ backend), isliye fleet ke NICs pe ek saath ~6.11 Gbps andar aur ~6.11 Gbps bahar. NIC full duplex hota hai, isliye har direction alag se size karo.

Concurrency: Little's Law

Ek saath kitni requests khuli hain: Little's Law

Problem

Memory, thread pools and connection limits depend on how many requests are open at the same moment, not on QPS directly. 35K QPS of 5 ms requests and 35K QPS of 2-second requests need completely different machines. How do we get that "same moment" number?

Memory, thread pools aur connection limits is baat pe depend karte hain ki ek hi pal mein kitni requests khuli hain, seedha QPS pe nahi. 5 ms wali 35K QPS aur 2 second wali 35K QPS ko bilkul alag machines chahiye. Yeh "ek hi pal" wala number kaise nikaalein?

Solution

L = λ × W

L is the average number of requests inside the system, λ (lambda) is the arrival rate, W is how long each request stays inside. It holds for any stable system, whatever the traffic pattern.

L = system ke andar average kitni requests, λ (lambda) = requests aane ki rate, W = har request andar kitna time bitaati hai. Traffic pattern kuch bhi ho, stable system pe yeh hamesha lagta hai.

Restaurant check: 60 guests arrive per hour and each stays 30 minutes, so on average 30 people are inside and you need at least 30 seats.

Restaurant se samjho: ghante mein 60 log aate hain, har koi 30 minute baithta hai, toh andar average 30 log hain aur kam se kam 30 seats chahiye.

In-flight requests at peak34,722 × 0.2 s≈ 6,944
Open connections at peak4% of 50M online × 1 connection2,000,000

These are different numbers. In-flight requests are being processed right now. Open connections also include idle keep-alive or HTTP/2 connections waiting for the user's next click. The LB pays memory for both.

Yeh do alag numbers hain. In-flight requests abhi process ho rahi hain. Open connections mein woh idle keep-alive ya HTTP/2 connections bhi hain jo user ke agle click ka wait kar rahe hain. LB dono ke liye memory deta hai.

The trap: if the backend slows from 200 ms to 400 ms, in-flight requests double to ≈ 13,889 and buffer memory doubles, even though QPS did not change. Slow backends eat LB memory. That is why timeouts, circuit breakers and backpressure are capacity tools, not just reliability tools.

Yahan phasoge: backend 200 ms se 400 ms pe slow hua toh in-flight requests double hokar ≈ 13,889 ho jaati hain aur buffer memory bhi double, jabki QPS same hai. Slow backend LB ki memory kha jaata hai. Isliye timeouts, circuit breakers aur backpressure sirf reliability nahi, capacity ke tools bhi hain.

Memory per LB node

LB node ko kitni memory chahiye

Problem

How much RAM does the LB fleet need, and what actually eats it? "Just add more RAM" is not an answer an interviewer accepts.

LB fleet ko kitni RAM chahiye, aur memory asal mein khaata kaun hai? "Aur RAM daal do" interviewer ke liye jawab nahi hai.

Solution

memory = open connections × KB per connection
+ in-flight requests × KB per request
(+ a fixed base per node)

What consumes the memory

  • Kernel socket buffers (send and receive) for every TCP connection.Har TCP connection ke kernel socket buffers (send aur receive).
  • TLS session state: keys and handshake state.TLS session state: keys aur handshake ki state.
  • Proxy structures per connection: parser state, timers.Har connection ka proxy data: parser state, timers.
  • Request and response buffers while bytes are in flight.Jab tak bytes raste mein hain, request aur response buffers.
  • A fixed base: OS, proxy binary, routing tables, certificates, config (about 2 GB here).Fixed base: OS, proxy binary, routing tables, certificates, config (yahan ~2 GB).
Connection state2,000,000 × 20 KB40 GB
In-flight buffers6,944 × 64 KB≈ 0.44 GB
Fleet total (before base)40 + 0.44≈ 40.44 GB

Connections are 99% of it. For an LB holding long-lived connections, the connection count, not QPS, drives memory.

Isme 99% connections ka hai. Lambe connections rakhne wale LB mein memory QPS nahi, connections ki ginti decide karti hai.

Measuring the real per-connection number: open 100,000 idle connections against one node in a load test, measure the growth in process RSS plus kernel socket memory (ss -m, /proc/meminfo, slabtop) and divide by 100,000. Repeat with live traffic for the per-request number.

Asli per-connection number kaise nikaalein: load test mein ek node pe 1 lakh idle connections kholo, process RSS aur kernel socket memory kitni badhi dekho (ss -m, /proc/meminfo, slabtop), phir 1 lakh se divide karo. Per-request number ke liye live traffic ke saath dohraao.

  • Cutting memory: HTTP/2 (many requests share one connection), shorter idle timeouts, streaming instead of buffering, TLS session resumption, per-client connection limits.Memory kam karne ke tareeke: HTTP/2 (ek connection pe kai requests), chhote idle timeouts, buffer ki jagah streaming, TLS session resumption, har client pe connection limit.
  • The backend side: LB → backend connections are pooled and reused (keep-alive), so they don't grow with client connections. Watch the ephemeral port limit: roughly 28K–64K connections per (LB IP, backend IP:port) pair.Backend wali side: LB → backend connections pool mein reuse hote hain (keep-alive), isliye client connections ke saath nahi badhte. Ephemeral port limit dhyaan rakho: har (LB IP, backend IP:port) pair pe lagbhag 28K–64K connections.

Deciding the instance count

Kitne instances chahiye, kaise decide karein

Problem

We know the demand: 34,722 QPS, 40.44 GB of connection memory, 2 million connections and 6.11 Gbps. How many LB nodes do we run? And how many app servers sit behind them?

Demand pata hai: 34,722 QPS, 40.44 GB connection memory, 20 lakh connections aur 6.11 Gbps. Kitne LB nodes chalayein? Aur unke peeche kitne app servers?

Solution

nodes for one resource = ⌈ demand ÷ (capacity per node × target) ⌉
required nodes = max(CPU, memory, connections, network)
then add redundancy

Work out the node count separately for every resource, then take the maximum. Every resource has to fit at the same time, so the tightest bottleneck decides. Always round up: 2.48 servers means 3 servers.

Har resource ke liye node count alag se nikaalo, phir maximum lo. Saare resources ek saath fit hone chahiye, isliye sabse tight bottleneck decide karta hai. Hamesha upar round karo: 2.48 server matlab 3 server.

The insight interviewers look for: LBs that hold many long-lived connections are usually memory- or connection-bound; LBs doing many short TLS handshakes are usually CPU-bound. Say which one yours is.

Interviewer yahi insight dhoondhta hai: jo LB bahut saare lambe connections rakhta hai woh aksar memory- ya connection-bound hota hai; jo bahut saare chhote TLS handshakes karta hai woh CPU-bound. Bolo ki aapka kaunsa hai.

Why 60–70%, not 100%

Servers ko 100% pe kyun nahi chalate

Problem

"Why pay for machines that sit 30–40% idle? Run them at 100% and buy fewer." It sounds efficient. Why is it wrong?

"30–40% khaali baithi machines ke paise kyun dein? 100% pe chalao aur kam machines lo." Sunne mein efficient lagta hai. Galat kyun hai?

Solution

response time ≈ service time ÷ (1 − utilization)
UtilizationLatency multiplier
50%2×
70%3.3×
80%5×
90%10×
95%20×

Latency grows slowly, then shoots up near 100%: the hockey stick. Headroom also absorbs traffic that arrives before autoscaling reacts (new machines take minutes), a node or zone failing (its load lands on the rest), deploys that drain nodes, GC pauses and noisy neighbours.

Latency pehle dheere badhti hai, phir 100% ke paas ekdum upar bhaagti hai: hockey stick. Headroom yeh sab bhi sambhalta hai: autoscaling ke react karne se pehle aaya traffic (naye machines minutes lete hain), kisi node ya zone ka girna (uska load baakiyon pe), deploy mein drain hue nodes, GC pauses aur noisy neighbours.

Targets by role

  • Load balancers and latency-critical services: 60–70% CPU.Load balancers aur latency-critical services: 60–70% CPU.
  • Batch and offline workers: 80–90% is fine, nobody is waiting on them.Batch aur offline workers: 80–90% chalega, unka koi wait nahi kar raha.
  • Memory: 75–85%. Running out of memory is a cliff (the OOM killer), not a slope.Memory: 75–85%. Memory khatam hona dhalaan nahi, seedhi khaai hai (OOM killer).

Say this in the interview: "I target 60–70% because queueing delay explodes past about 80%, and I need room for failover and for the minutes before autoscaling catches up."

Interview mein bolo: "Main 60–70% target rakhta hoon kyunki ~80% ke baad queueing delay phat jaata hai, aur mujhe failover ke liye aur autoscaling ke pakadne tak ke minutes ke liye jagah chahiye."

High-level design

Poora architecture ek nazar mein

Problem

Draw the end-to-end architecture for 35K peak QPS, 99.99% availability and users in more than one region, including what happens when a node, a whole zone or the config system fails.

35K peak QPS, 99.99% availability aur ek se zyada region ke users ke liye end-to-end architecture banao, aur yeh bhi ki node, poora zone ya config system fail ho toh kya hoga.

Solution

Follow one request down the diagram

  1. DNS / GeoDNS answers "where is shopkart.com?" with the nearest healthy region's address. It is not in the data path; a short TTL (30–60 s) keeps failover quick.DNS / GeoDNS "shopkart.com kahan hai?" ka jawab nearest healthy region ke address se deta hai. Yeh data path mein nahi hai; chhota TTL (30–60 s) failover ko jaldi rakhta hai.
  2. Global edge (anycast): the same IP is announced from many locations, and internet routing sends each user to the nearest one.Global edge (anycast): ek hi IP kai jagah se announce hota hai, aur internet routing har user ko sabse paas wali jagah bhejti hai.
  3. L4 LB per zone (AWS NLB, Google Maglev, Linux IPVS) balances TCP connections by hashing at millions of packets per second, spreading them over the L7 fleet.Har zone ka L4 LB (AWS NLB, Google Maglev, Linux IPVS) hashing se TCP connections baant-ta hai, millions packets per second pe, aur unhe L7 fleet mein phailata hai.
  4. L7 LB fleet (Envoy, NGINX, HAProxy): 9 nodes, 3 per zone. TLS termination, path routing (/api/cart → cart service), retries, rate limits.L7 LB fleet (Envoy, NGINX, HAProxy): 9 nodes, har zone mein 3. TLS termination, path routing (/api/cart → cart service), retries, rate limits.
  5. Stateless app services: about 145 servers at peak, autoscaled.Stateless app services: peak pe lagbhag 145 servers, autoscaled.
  6. Data layer: Redis for sessions and cache, databases, queues.Data layer: sessions aur cache ke liye Redis, databases, queues.

Control plane, off the request path: the config store (etcd or Consul) holds versioned configs and the service registry; a health checker probes servers; metrics feed the autoscaler.

Control plane, request path se bahar: config store (etcd ya Consul) mein versioned configs aur service registry; health checker servers ko probe karta hai; metrics autoscaler ko jaate hain.

Data plane vs control plane: if etcd or the metrics system is down, LBs keep serving with their last-known-good config. The control plane may pause; the data plane must never stop.

Data plane vs control plane: etcd ya metrics system down ho toh bhi LBs apne last-known-good config se serve karte rehte hain. Control plane ruk sakta hai; data plane kabhi nahi rukna chahiye.

L4 vs L7

Transport layer pe balance karein ya HTTP layer pe?

Problem

Should balancing happen at layer 4 (TCP/UDP connections) or layer 7 (HTTP requests)? The choice changes speed, cost and features, and for gRPC it even changes whether the load is balanced at all.

Balancing layer 4 (TCP/UDP connections) pe ho ya layer 7 (HTTP requests) pe? Isse speed, cost aur features badalte hain, aur gRPC ke liye toh yeh bhi ki load balance hoga ya nahi.

Solution

Who balances the balancer?

Load balancer khud fail ho gaya toh?

Problem

We removed the single point of failure from the servers and created a new one: the load balancer itself. If it dies, everything behind it is unreachable.

Servers se single point of failure hataya aur ek naya bana diya: khud load balancer. Woh gira toh uske peeche sab kuch unreachable.

Solution

Active–passive pair (VRRP / keepalived)

Two nodes share a floating virtual IP. When heartbeats stop, the standby takes the IP within about 1–3 seconds. Simple, but half the capacity sits idle, and there is a split-brain risk (both think they are primary), so add fencing. Fits small or on-prem setups.

Do nodes ek floating virtual IP share karte hain. Heartbeat band hote hi standby 1–3 second mein IP le leta hai. Simple hai, par aadhi capacity khaali baithi rehti hai, aur split-brain ka risk hai (dono khud ko primary samjhein), isliye fencing lagao. Chhote ya on-prem setups ke liye.

Active–active with ECMP / anycast (BGP)

Routers spread flows across N LB nodes that all announce the same VIP. A dead node's route is withdrawn and its flows rehash to the rest. All capacity is used and it scales out, but it needs network expertise; use consistent hashing so a node change only resets that node's own flows. Fits large scale.

Routers flows ko N LB nodes mein baant-te hain jo sab ek hi VIP announce karte hain. Dead node ka route hat jaata hai aur uske flows baaki nodes pe rehash hote hain. Poori capacity use hoti hai aur scale out hota hai, par network expertise chahiye; consistent hashing lagao taaki node badalne pe sirf usi ke flows reset hon. Bade scale ke liye.

DNS-based failover

Several address records, or health-checked DNS that removes a dead region. Global and simple, but clients and resolvers cache answers beyond the TTL, so failover is slow and coarse. Fits region-level failover.

Kai address records, ya health-checked DNS jo dead region ko hata de. Global aur simple, par clients aur resolvers TTL ke baad bhi purana jawab cache rakhte hain, isliye failover slow aur mota-mota hota hai. Region-level failover ke liye.

Managed cloud load balancer

AWS ALB/NLB or Google Cloud Load Balancing are multi-zone and highly available by design. In the cloud this is the default unless you need custom behaviour.

AWS ALB/NLB ya Google Cloud Load Balancing design se hi multi-zone aur highly available hain. Cloud mein yahi default choice hai, jab tak custom behaviour na chahiye.

Layer them: DNS or anycast picks the region, ECMP or a managed L4 spreads across LB nodes, and each L7 node keeps its last-known-good config so a control-plane outage never stops traffic.

Layers mein socho: DNS ya anycast region chunta hai, ECMP ya managed L4 LB nodes mein baant-ta hai, aur har L7 node apna last-known-good config rakhta hai taaki control plane gire toh bhi traffic na ruke.

Decide in this order

  1. Must the same user or key reach the same server? Use consistent hashing, with bounded load.Kya same user ya key ko same server pe hi jaana hai? Consistent hashing lo, bounded load ke saath.
  2. Servers of different but fixed sizes? Use weighted round robin.Servers alag-alag size ke par fixed hain? Weighted round robin lo.
  3. Request durations vary a lot? Use least connections.Requests ka time bahut alag-alag hai? Least connections lo.
  4. Large fleet, many LB nodes, want load-awareness without herding? Use power of two choices on a load score.Bada fleet, kai LB nodes, load-aware chahiye par herding nahi? Load score pe power of two choices lo.
  5. Everything identical and simple? Round robin is enough.Sab kuch same aur simple? Round robin kaafi hai.

Why not always pick the least-loaded server? Every LB node sees the same slightly stale numbers, so they all pick the same "best" server at the same instant and it melts: the herd effect. Two random choices break that synchronisation and still avoid the worst servers. In balls-into-bins terms, the maximum overload drops from about log n ÷ log log n to log log n.

Hamesha sabse kam loaded server kyun nahi? Har LB node ko same thode purane numbers dikhte hain, toh sab ek hi pal mein same "best" server chunte hain aur woh pighal jaata hai: herd effect. Do random choices yeh ek-saath-pan tod deti hain aur phir bhi sabse bure servers se bachati hain. Balls-into-bins ki bhasha mein, max overload log n ÷ log log n se girkar log log n ho jaata hai.

Calculating a server's load

Server kitna busy hai, yeh kaise nikaalein

Problem

"Load" is not one number. One server has low CPU but is almost out of memory; another has few connections but is slow because of GC pauses. How does the LB turn all of that into one "how busy is this server" value it can route on?

"Load" ek number nahi hai. Ek server ka CPU kam hai par memory lagbhag khatam; doosre pe connections kam hain par GC pauses se slow hai. LB in sabko ek "yeh server kitna busy hai" value mein kaise badle jis pe route kar sake?

Solution

load = 0.40·CPU + 0.20·memory
+ 0.25·(active ÷ max connections)
+ 0.15·min(1, latency ÷ SLO)

Normalise every metric to 0–1 first, then combine with weights that add up to 1. The weights say what "busy" means for your workload.

Pehle har metric ko 0–1 mein laao, phir aise weights se jodo jinka total 1 ho. Weights batate hain ki aapke workload ke liye "busy" ka matlab kya hai.

Sticky sessions

User ko ek hi server se chipkaayein ya nahi?

Problem

A user adds a phone to the cart on server S1. The next request lands on S2, which has never seen this session, and the cart looks empty. Should the LB always send this user back to S1?

User ne server S1 pe phone cart mein daala. Agli request S2 pe gayi, jisne yeh session kabhi dekha hi nahi, aur cart khaali dikhta hai. Kya LB is user ko hamesha S1 pe hi bheje?

Solution

Option 1: sticky sessions

The LB sets a cookie such as lb=S1 and routes on it. A one-line fix with no app change, but load gets uneven (a heavy user stays on one server), sessions die with S1 anyway, and draining and scale-in take longer.

LB lb=S1 jaisi cookie set karta hai aur usi pe route karta hai. App badle bina ek line ka fix, par load uneven hota hai (heavy user ek hi server pe atka), S1 ke saath sessions waise bhi mar jaate hain, aur draining aur scale-in mein zyada time lagta hai.

Option 2: stateless servers with a shared store

Keep sessions in Redis, or in signed tokens such as JWTs. Any server can serve any request, so failover and autoscaling just work. The cost is one extra network hop (about 0.5–1 ms), and Redis must be highly available.

Sessions Redis mein rakho, ya JWT jaise signed tokens mein. Koi bhi server koi bhi request serve kar sakta hai, toh failover aur autoscaling seedhe chalte hain. Keemat: ek extra network hop (~0.5–1 ms), aur Redis highly available hona chahiye.

Option 3: consistent hashing on userId

Affinity only where it pays off: local caches, WebSocket rooms, sharded in-memory state. Only about 1/N of keys move when a server joins or leaves.

Affinity sirf wahan jahan faayda ho: local caches, WebSocket rooms, sharded in-memory state. Server aaye ya jaaye toh sirf ~1/N keys hilti hain.

Apply sticky sessions for legacy apps you can't change yet, long-lived stateful connections, or temporarily during a migration. Ignore them for every new service: keep servers stateless and put state in Redis or the database.

Sticky sessions lagao purane apps ke liye jinhe abhi badal nahi sakte, lambe stateful connections ke liye, ya migration ke dauraan thodi der ke liye. Har naye service mein ignore karo: servers stateless rakho aur state Redis ya database mein.

Say this in the interview: "I'd keep app servers stateless with sessions in Redis, and use consistent hashing only where affinity improves the cache hit rate."

Interview mein bolo: "Main app servers ko stateless rakhunga aur sessions Redis mein, aur consistent hashing sirf wahan lagaunga jahan affinity se cache hit rate badhe."

Autoscaling

Chalte system mein instances kaise badhein-ghatein

Problem

At 3 AM ShopKart gets a tenth of its 8 PM traffic. A fixed fleet of 145 servers wastes money all night and still melts during a surprise flash sale. How do we decide the instance count while the system is running?

Raat 3 baje ShopKart pe 8 PM ka sirf dasvaan hissa traffic hota hai. 145 servers ka fixed fleet poori raat paisa barbaad karta hai aur achanak flash sale mein phir bhi pighal jaata hai. System chalte-chalte instances ki ginti kaise decide karein?

Solution

desired = ⌈ current × current metric ÷ target metric ⌉

This is the rule Kubernetes' Horizontal Pod Autoscaler uses. It scales the fleet in proportion to how far the metric is from its target.

Kubernetes ka Horizontal Pod Autoscaler yahi rule use karta hai. Metric target se jitna door hai, fleet ko usi anupaat mein badhata-ghatata hai.

Scale out10 servers at 90% CPU, target 60%: ⌈10 × 0.9 ÷ 0.6⌉15 (+5 now)
Scale in15 servers at 30% CPU: ⌈15 × 0.3 ÷ 0.6⌉8 (−7, slowly)

  • Scale out fast, scale in slow: add capacity immediately; remove it only after a cooldown or stabilisation window (for example 5 minutes).Badhao tez, ghatao dheere: capacity turant jodo; hatao sirf cooldown ya stabilisation window ke baad (jaise 5 minute).

  • Pick the metric that matches the bottleneck: CPU for compute-bound services, requests in flight or RPS per instance for I/O-bound ones, queue depth for workers, p99 latency as a guardrail.Wahi metric lo jo bottleneck se match kare: compute-bound ke liye CPU, I/O-bound ke liye in-flight requests ya har instance ki RPS, workers ke liye queue depth, aur guardrail ke roop mein p99 latency.

Saving and updating config

Config save aur update, bina downtime ke

Problem

We want to switch the algorithm, change weights or add backends across all 9 LB nodes: without restarting, without dropping a single connection, without two admins overwriting each other, and with a one-click undo when a change goes wrong.

Algorithm badalna hai, weights change karne hain ya naye backends jodne hain, saare 9 LB nodes pe: bina restart, bina ek bhi connection gire, bina do admins ek-doosre ka change mitaaye, aur galti ho toh ek click mein undo.

Solution

  1. Save: config is an immutable, versioned document in a strongly consistent store (etcd, Consul, ZooKeeper). Every change writes version N+1 with compare-and-set: "write v8 only if the store is still at v7". If two admins save at once, one wins and the other reloads and retries. No lost updates, full history.Save: config ek immutable, versioned document hai jo strongly consistent store (etcd, Consul, ZooKeeper) mein rehta hai. Har change compare-and-set ke saath version N+1 likhta hai: "v8 tabhi likho jab store abhi bhi v7 pe ho". Do admins ek saath save karein toh ek jeetega, doosra reload karke retry karega. Koi update kho nahi jaata, poori history rehti hai.
  2. Distribute: LB nodes watch the key and the store pushes changes within milliseconds. Polling with a version number also works: simpler, slower.Distribute: LB nodes key ko watch karte hain aur store milliseconds mein changes push karta hai. Version number ke saath polling bhi chalti hai: simple par slow.
  3. Validate: each node checks the config (schema, weights ≥ 0, at least one backend) before using it.Validate: har node use karne se pehle config check karta hai (schema, weights ≥ 0, kam se kam ek backend).
  4. Apply: one atomic pointer swap. New requests use v8; requests already running finish with v7. No locks on the request path, zero downtime.Apply: ek atomic pointer swap. Nayi requests v8 use karti hain; chal rahi requests v7 se hi khatam hoti hain. Request path pe koi lock nahi, zero downtime.
  5. Roll out safely: apply to one canary LB node, watch error rates, then the rest.Safely roll out: pehle ek canary LB node pe lagao, error rate dekho, phir baaki pe.
  6. Roll back: save the old content as a new version (v9 = v7's content). History stays linear and auditable.Rollback: purana content naye version ki tarah save karo (v9 = v7 ka content). History seedhi aur audit karne laayak rehti hai.
  7. Survive control-plane outages: each LB keeps its last-known-good config in memory and on local disk. If etcd is down, traffic still flows; only changes pause.Control plane down ho tab bhi chalo: har LB apna last-known-good config memory aur local disk pe rakhta hai. etcd down ho toh bhi traffic chalta hai; sirf changes rukte hain.
  8. Upgrading the LB binary itself: hot restart. The new process inherits the listening socket (SO_REUSEPORT or socket hand-off) and the old process drains its connections and exits.LB ka binary hi upgrade karna ho: hot restart. Naya process listening socket le leta hai (SO_REUSEPORT ya socket hand-off) aur purana process apne connections drain karke band hota hai.

One path for everyone: even the node that saved the change applies it only when the watch event arrives, so every node, including the saver, follows exactly the same update path.

Sabke liye ek hi raasta: jis node ne change save kiya, woh bhi use tabhi apply karta hai jab watch event aata hai, isliye har node, save karne wala bhi, bilkul ek hi update path se guzarta hai.

ConfigManager.java
  1. A Java record is an immutable value. Thousands of threads can share it with zero locking; "changing" config means creating a new one.Java record ek immutable value hai. Hazaaron threads ise bina lock share kar sakte hain; config "badalna" matlab naya banana.
  2. AtomicReference holds the live config; reading it on the hot path is one volatile load.AtomicReference live config rakhta hai; hot path pe ise padhna bas ek volatile load hai.
  3. The durable, strongly consistent store is the source of truth; the LB node only holds a cached copy.Durable, strongly consistent store hi source of truth hai; LB node ke paas sirf cached copy hai.
  4. CopyOnWriteArrayList: listeners are added rarely and read on every update, so iteration needs no lock.CopyOnWriteArrayList: listeners kabhi-kabhi jude, har update pe padhe jaate hain, isliye iterate karne mein lock nahi chahiye.
  5. On boot, load the latest saved version (and keep a local last-known-good copy in case the store is down).Boot pe latest saved version load karo (aur store down hone ke case ke liye ek local last-known-good copy rakho).
  6. Watch: the store pushes every change (an etcd watch or a Consul blocking query), so propagation takes milliseconds. Started separately so the constructor never leaks this.Watch: store har change push karta hai (etcd watch ya Consul blocking query), toh propagation milliseconds mein. Alag se start kiya taaki constructor se this leak na ho.
  7. SAVE: validate, then write version base + 1 only if the store is still at base. If another admin got there first the CAS fails, and we reload and retry. Note that saving does not touch activeConfig: the watch event does.SAVE: validate karo, phir version base + 1 tabhi likho jab store abhi bhi base pe ho. Doosra admin pehle pahunch gaya toh CAS fail, reload karke retry. Dhyaan do, save activeConfig ko nahi chhoota: watch event chhoota hai.
  8. UPDATE: versions only move forward, so stale or duplicate events are ignored; then CAS the pointer. Running requests keep the old object, new ones see the new one: zero downtime, no locks.UPDATE: versions sirf aage badhte hain, toh purane ya duplicate events ignore; phir pointer ka CAS. Chal rahi requests purana object rakhti hain, nayi requests naya dekhti hain: zero downtime, koi lock nahi.
  9. Observers react: the load balancer rebuilds its strategy, the health checker changes its interval.Observers react karte hain: load balancer apni strategy dobara banata hai, health checker apna interval badalta hai.
  10. Rollback never rewinds history; it saves old content as a new version, so the audit trail stays linear.Rollback history ko peeche nahi ghumaata; purana content naye version ki tarah save karta hai, toh audit trail seedha rehta hai.
  11. Reject bad config before it reaches any node. "All weights 0" would black-hole traffic across the fleet in seconds.Kharab config ko kisi node tak pahunchne se pehle hi rok do. "Saare weights 0" seconds mein poore fleet ka traffic gayab kar dega.
  12. A read accessor and Observer registration, used by the load balancer's constructor.Ek read accessor aur Observer registration, jo load balancer ke constructor mein use hote hain.

Walk me through estimating how many load balancer nodes ShopKart needs.

ShopKart ko kitne load balancer nodes chahiye, step by step estimate karke batao.

Q2Easy

What is Little's Law, and why should a load balancer engineer care?

Little's Law kya hai, aur load balancer engineer ko iski parwah kyun karni chahiye?

Answer out loud first, then reveal.

L = λ × W: the number of requests in the system equals the arrival rate times the time each spends inside. So concurrency, and with it memory, threads and connection slots, equals throughput × latency. If backend latency doubles, the LB holds twice as many in-flight requests and needs twice the buffer memory even though QPS is unchanged. That's why timeouts, circuit breakers and backpressure protect capacity.

L = λ × W: system mein requests = aane ki rate × har request ka andar bitaaya time. Toh concurrency, aur uske saath memory, threads aur connection slots, = throughput × latency. Backend latency double hui toh LB ko double in-flight requests aur double buffer memory chahiye, jabki QPS same hai. Isliye timeouts, circuit breakers aur backpressure capacity ko bachate hain.

Q3Medium

Your LB fleet runs at 40% CPU, but nodes keep getting OOM-killed. What's going on?

LB fleet 40% CPU pe chal raha hai, phir bhi nodes OOM se mar rahe hain. Kya ho raha hai?

Answer out loud first, then reveal.

CPU isn't the bottleneck; memory or connections are. Likely causes: slow backends piling up in-flight requests (Little's Law), clients holding many idle keep-alive or WebSocket connections, large uploads buffered in memory, or idle timeouts that are too long. Fixes: cap connections per node, shorten idle timeouts, stream instead of buffering, add backend timeouts and circuit breakers, and size the fleet with max(CPU, memory, connections), not CPU alone.

Bottleneck CPU nahi, memory ya connections hain. Wajah ho sakti hai: slow backends se in-flight requests jama ho rahi hain (Little's Law), clients bahut saare idle keep-alive ya WebSocket connections rakh rahe hain, bade uploads memory mein buffer ho rahe hain, ya idle timeouts bahut lambe hain. Ilaaj: har node pe connection cap, chhote idle timeouts, buffering ki jagah streaming, backend timeouts aur circuit breakers, aur fleet ko sirf CPU nahi, max(CPU, memory, connections) se size karo.

Q4Easy

Why not run servers at 100% CPU to save money?

Paise bachane ke liye servers ko 100% CPU pe kyun nahi chalate?

Answer out loud first, then reveal.

Queueing: latency ≈ service time ÷ (1 − utilization). At 90% latency is 10× the base; at 95% it's 20×. You also need headroom for spikes before autoscaling reacts (minutes), for a node or zone failing, and for deploys and GC pauses. Latency-critical tiers target 60–70%; batch jobs can run at 80–90%.

Queueing: latency ≈ service time ÷ (1 − utilization). 90% pe latency base ki 10 guna, 95% pe 20 guna. Autoscaling ke react karne se pehle ke spikes (minutes), node ya zone ke girne, aur deploys aur GC pauses ke liye bhi headroom chahiye. Latency-critical tiers 60–70% target karte hain; batch jobs 80–90% pe chal sakte hain.

Q5Medium

L4 or L7 load balancer: how do you decide?

L4 ya L7 load balancer: kaise decide karoge?

Answer out loud first, then reveal.

L4 sees only IPs and ports: protocol-agnostic, very fast and cheap, supports TLS pass-through, but balances per connection. L7 understands HTTP: path and host routing, per-request balancing, retries, header-based canaries and TLS termination, at more CPU and a little latency. HTTP microservices and gRPC go to L7, because L4 would pin long HTTP/2 connections to one backend. Databases, game servers, raw TCP or extreme throughput go to L4. Large systems use both: L4 in front of an L7 fleet.

L4 sirf IP aur port dekhta hai: protocol-agnostic, bahut tez aur sasta, TLS pass-through karta hai, par balance per connection. L7 HTTP samajhta hai: path aur host routing, har request pe balancing, retries, header-based canary aur TLS termination, par zyada CPU aur thodi latency. HTTP microservices aur gRPC ke liye L7, kyunki L4 lambe HTTP/2 connections ko ek hi backend se chipka dega. Databases, game servers, raw TCP ya bahut high throughput ke liye L4. Bade systems dono use karte hain: L7 fleet ke aage L4.

Q6Medium

Round robin vs least connections vs power of two choices: when would you use each?

Round robin, least connections aur power of two choices: kaunsa kab use karoge?

Answer out loud first, then reveal.

Round robin fits identical servers and uniform requests; it breaks with mixed machine sizes or variable request durations. Least connections adapts to slow and long requests but needs live counts. Power of two choices picks two random servers and takes the less loaded one: almost as good as a global least-loaded pick, O(1) per request, and immune to herding when many LB nodes act on stale data. Envoy's least-request balancer is built on it, and it's my default for large fleets.

Round robin same servers aur same jaisi requests ke liye; alag size ki machines ya alag-alag duration ki requests pe toot jaata hai. Least connections slow aur lambi requests ke hisaab se adjust karta hai par live counts chahiye. Power of two choices do random servers leke kam loaded wala chunta hai: global least-loaded jitna hi achha, har request pe O(1), aur jab kai LB nodes purane data pe chalein tab herding se bacha rehta hai. Envoy ka least-request balancer isi pe bana hai, aur bade fleets ke liye mera default yahi hai.

Q7Hard

What is the herd problem in least-loaded balancing, and how do you fix it?

Least-loaded balancing mein herd problem kya hai, aur use kaise theek karoge?

Answer out loud first, then reveal.

Many LB nodes read the same stale metrics every few seconds and all pick the same least-loaded server at the same instant. It gets flooded, its metrics spike, everyone jumps to the next one, and load oscillates. A new or dead server with zero connections looks best of all. Fixes: randomise with power of two choices, prefer the LB's own fresh in-flight counts, smooth metrics with EWMA, slow-start new servers, and eject fast-failing servers with outlier detection.

Kai LB nodes har kuch second mein same purane metrics padhte hain aur sab ek hi pal mein same least-loaded server chunte hain. Woh doob jaata hai, uske metrics uchhalte hain, sab agle pe kood jaate hain, aur load jhoolta rehta hai. Naya ya dead server zero connections ke saath sabse achha dikhta hai. Ilaaj: power of two choices se randomness, LB ke apne taaze in-flight counts ko tarjeeh, EWMA se smoothing, naye servers ke liye slow start, aur outlier detection se jaldi fail hone wale servers bahar.

Q8Medium

How do you make the load balancer itself highly available?

Load balancer ko khud highly available kaise banaoge?

Answer out loud first, then reveal.

Remove it as a single point of failure. Options: an active–passive pair sharing a floating VIP through VRRP (failover in seconds, but half the capacity idle and a split-brain risk); active–active nodes announcing the same VIP with ECMP or anycast (all nodes serve, a dead node's route is withdrawn); DNS with multiple records or health-checked failover at the global level; or a managed multi-zone cloud LB. In every case the data plane keeps serving with last-known-good config even if the control plane is down.

Use single point of failure na rehne do. Options: active–passive pair jo VRRP se floating VIP share kare (seconds mein failover, par aadhi capacity khaali aur split-brain ka risk); active–active nodes jo ECMP ya anycast se same VIP announce karein (sab serve karte hain, dead node ka route hat jaata hai); global level pe multiple records ya health-checked failover wala DNS; ya managed multi-zone cloud LB. Har case mein data plane last-known-good config se serve karta rehta hai, control plane down ho tab bhi.

Q9Medium

How do health checks avoid flapping and false positives?

Health checks flapping aur false positives se kaise bachte hain?

Answer out loud first, then reveal.

Rise and fall thresholds (for example 3 fails to eject, 2 passes to restore), short timeouts, jittered intervals, shallow /health checks for routing (deep checks can eject the whole fleet during a DB blip), passive checks on real traffic for fast detection, outlier detection for gray failures, and a panic threshold: if more than about half the fleet looks unhealthy, assume the checker is wrong and spread traffic across all servers.

Rise aur fall thresholds (jaise hataane ke liye 3 fails, wapas laane ke liye 2 passes), chhote timeouts, jitter wale intervals, routing ke liye shallow /health (deep checks DB blip mein poora fleet hata sakte hain), jaldi pakadne ke liye asli traffic pe passive checks, gray failures ke liye outlier detection, aur panic threshold: aadhe se zyada fleet unhealthy dikhe toh maano checker galat hai aur traffic sab servers pe phailao.

Q10Medium

Sticky sessions: good or bad?

Sticky sessions: achhe ya bure?

Answer out loud first, then reveal.

A quick way to keep in-memory session state working, but load becomes uneven (heavy users stuck on one server), sessions die with the server, and draining and scale-in get slower. I prefer stateless servers with sessions in Redis or in signed tokens. Where affinity really helps (local caches, WebSocket rooms, sharded state) I use consistent hashing on the user ID instead of cookies.

In-memory session state ko chalaane ka jaldi wala tareeka, par load uneven hota hai (heavy users ek server pe atke), server ke saath sessions mar jaate hain, aur draining aur scale-in slow ho jaate hain. Main stateless servers pasand karta hoon, sessions Redis ya signed tokens mein. Jahan affinity sach mein madad kare (local caches, WebSocket rooms, sharded state) wahan cookies ki jagah user ID pe consistent hashing.

Q11Hard

How do you push a config change to 100 LB nodes with zero downtime and instant rollback?

100 LB nodes pe zero downtime aur turant rollback ke saath config change kaise push karoge?

Answer out loud first, then reveal.

Store config as immutable, versioned documents in etcd or Consul and save with compare-and-set so concurrent edits can't overwrite each other. Nodes watch the key, validate the new version and swap an AtomicReference, so in-flight requests finish on the old version while new ones use the new one. Roll out to a canary node first and watch error rates. Rollback means saving the previous content as a new version. Nodes keep last-known-good config locally, so a control-plane outage never stops traffic. Binary upgrades use hot restart with socket hand-off and connection draining.

Config ko etcd ya Consul mein immutable, versioned documents ki tarah rakho aur compare-and-set se save karo taaki ek saath hue edits ek-doosre ko overwrite na karein. Nodes key watch karte hain, naya version validate karte hain aur AtomicReference swap karte hain, toh chal rahi requests purane version pe khatam hoti hain aur nayi requests naya use karti hain. Pehle ek canary node pe lagao aur error rate dekho. Rollback matlab pichhla content naye version ki tarah save karna. Nodes last-known-good config locally rakhte hain, toh control plane gire tab bhi traffic nahi rukta. Binary upgrade ke liye socket hand-off aur connection draining ke saath hot restart.

Q12Medium

How does autoscaling decide the number of instances?

Autoscaling instances ki ginti kaise decide karti hai?

Answer out loud first, then reveal.

desired = ⌈current × current metric ÷ target⌉; for example 10 servers at 90% CPU with a 60% target gives 15. Add a ±10% tolerance band, scale out fast and in slowly (cooldown or stabilisation window), bound it with min and max, pick the metric that matches the bottleneck (CPU, requests in flight, queue depth), and cover boot time with headroom or predictive scaling for known peaks.

desired = ⌈current × current metric ÷ target⌉; jaise 10 servers 90% CPU pe, target 60% → 15. ±10% ka tolerance band rakho, scale out tez aur scale in dheere (cooldown ya stabilisation window), min aur max se bandho, wahi metric lo jo bottleneck se match kare (CPU, in-flight requests, queue depth), aur boot time ke liye headroom ya jaane-pehchaane peaks ke liye predictive scaling.

Q13Hard

A backend isn't down, but it answers 10× slower. How does the LB handle this gray failure?

Backend down nahi hai, par 10 guna slow jawab de raha hai. LB is gray failure ko kaise sambhalega?

Answer out loud first, then reveal.

Active health checks may still pass, so rely on the data path: latency-aware balancing (EWMA latency in the load score, least-request with power of two choices), outlier detection that ejects hosts much slower or more error-prone than their peers, per-try timeouts with a retry budget (10–20% extra load at most), circuit breakers, and hedged requests for critical reads. Re-admit the server with slow start.

Active health checks shayad pass ho jaayein, isliye data path pe bharosa karo: latency-aware balancing (load score mein EWMA latency, power of two choices ke saath least-request), outlier detection jo peers se bahut slow ya error-prone hosts ko hataye, har try pe timeout aur retry budget (zyada se zyada 10–20% extra load), circuit breakers, aur critical reads ke liye hedged requests. Server ko wapas slow start se laao.

Q14Medium

How do you take a server out for a deploy without failing any requests?

Bina ek bhi request fail kiye deploy ke liye server ko bahar kaise nikaaloge?

Answer out loud first, then reveal.

Connection draining. Mark it DRAINING so it gets no new requests (send Connection: close on HTTP/1.1 keep-alive, GOAWAY on HTTP/2), let in-flight requests finish up to a deadline such as 30 s, then deregister and stop it. Deploy, re-register, slow-start, and it's HEALTHY again. Rolling in small batches keeps enough capacity online throughout.

Connection draining. Use DRAINING mark karo taaki nayi requests na milein (HTTP/1.1 keep-alive pe Connection: close, HTTP/2 pe GOAWAY bhejo), chal rahi requests ko 30 s jaisi deadline tak khatam hone do, phir deregister karke band karo. Deploy karo, dobara register karo, slow start, aur woh phir HEALTHY. Chhote batches mein rolling karne se poore samay kaafi capacity online rehti hai.

Q15Hard

Why consistent hashing with virtual nodes instead of hash(userId) % N?

hash(userId) % N ki jagah virtual nodes wala consistent hashing kyun?

Answer out loud first, then reveal.

With % N, changing N remaps almost every key: going from 4 to 5 servers moves 80% of keys and causes a cache stampede. Consistent hashing moves only about 1/N of keys. Virtual nodes (100–200 per server) even out the uneven arcs so load balances well, and weights can be expressed as more virtual nodes. For hot keys, use bounded-load consistent hashing, capping each server at about 1.25× the average.

% N mein N badalte hi lagbhag har key ki jagah badal jaati hai: 4 se 5 servers karne pe 80% keys hilti hain aur cache stampede hota hai. Consistent hashing mein sirf ~1/N keys hilti hain. Virtual nodes (har server ke 100–200) ring ke uneven hisson ko barabar karte hain taaki load achhe se baante, aur weights ko zyada virtual nodes se dikhaya ja sakta hai. Hot keys ke liye bounded-load consistent hashing, jisme har server ~1.25× average pe cap hota hai.

Q16Easy

Where should TLS terminate?

TLS kahan terminate hona chahiye?

Answer out loud first, then reveal.

Usually at the L7 load balancer: it offloads crypto from app servers, enables HTTP routing, WAF rules and caching, and centralises certificate management. If compliance requires encryption end to end, re-encrypt from LB to backend with mTLS, or use L4 TLS pass-through and give up L7 features. The trade-off is visibility and cost versus the size of the decrypted zone.

Aam taur pe L7 load balancer pe: isse app servers ka crypto ka bojh hat-ta hai, HTTP routing, WAF rules aur caching possible hote hain, aur certificates ek jagah manage hote hain. Agar compliance ko end-to-end encryption chahiye, toh LB se backend tak mTLS se dobara encrypt karo, ya L4 TLS pass-through lo aur L7 features chhodo. Trade-off: visibility aur cost vs decrypted zone kitna bada hai.
