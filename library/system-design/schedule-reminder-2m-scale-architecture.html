Scale-Ready Schedule Reminder System — 2M+ Records/Day

Basic @Scheduled design 2M records pe kyun tootta hai, aur fix: Spring Batch partitioning, Kafka workers, Redis idempotency, HPA, DLQ + interview talking points. / Scaling the scheduler design.

1. Why the Basic Design Breaks at 2M+ Records

The original single-threaded @Scheduled + @Async design works fine up to ~50K records. Beyond that, several bottlenecks emerge:

BottleneckWhat Happens at ScaleImpact
Single DB QuerySELECT 2M rows into JVM heap in one shotOOM crash / GC freeze
ThreadPool Saturation20 threads x 2M tasks = massive queue backlogTasks sit pending for hours
Single JVM InstanceOne pod handles all work — no horizontal scaleSlow + single point of failure
DB Connection Pool20-50 connections saturated immediatelyConnection timeout errors
Email/Push API Rate LimitsSendGrid: 600/min free; FCM: bursts limitedAPI throttling / 429 errors
No IdempotencyIf job re-runs, 2M duplicate emails sentCritical business failure

GOAL: Process 2M reminders within a 2-hour daily window = ~280 reminders/second sustained throughput

3. Spring Batch — Partitioned Producer

Spring Batch reads 2M rows from MySQL in partitioned chunks. Each partition covers a range of IDs and is processed independently. This avoids loading all 2M rows into memory at once.

3.1 Partition Strategy

@Bean
public Partitioner reminderPartitioner() {
    return gridSize -> {
        Map<String, ExecutionContext> partitions = new HashMap<>();
        long total = repo.countByNextDateAndActiveTrue(LocalDate.now());
        long chunkSize = 1000;  // 1000 rows per partition
        long numPartitions = (total / chunkSize) + 1; // ~2000 partitions for 2M rows

        for (long i = 0; i < numPartitions; i++) {
            ExecutionContext ctx = new ExecutionContext();
            ctx.putLong("minId", i * chunkSize);
            ctx.putLong("maxId", (i + 1) * chunkSize - 1);
            partitions.put("partition" + i, ctx);
        }
        return partitions;
    };
}

3.2 Kafka Producer Step

@Bean
public ItemWriter<ScheduleReminder> kafkaProducerWriter() {
    return reminders -> {
        List<ProducerRecord<String, ReminderEvent>> records = reminders.getItems()
            .stream()
            .map(r -> new ProducerRecord<>("reminder.due", r.getSenderId(),
                ReminderEvent.from(r)))
            .toList();

        // Async batch publish — no blocking
        records.forEach(kafkaTemplate::send);
    };
}

3.3 Kafka Topic Config — 20 Partitions

@Bean
public NewTopic reminderTopic() {
    return TopicBuilder.name("reminder.due")
        .partitions(20)   // 20 consumers can work in parallel
        .replicas(3)      // 3 Kafka brokers for durability
        .build();
}

20 Kafka partitions = 20 consumer pods can work in parallel = ~100K records/pod = easily processed in < 2 hours

4. Kafka Consumer — Horizontal Scale Workers

4.1 Consumer Service

@Service
public class ReminderConsumerService {

    @Autowired private RedisTemplate<String, String> redis;
    @Autowired private TransactionService txService;
    @Autowired private EmailService emailService;
    @Autowired private NotificationService notifService;
    @Autowired private ScheduleReminderRepository repo;

    @KafkaListener(
        topics = "reminder.due",
        groupId = "reminder-consumer-group",
        concurrency = "5"   // 5 threads per pod
    )
    public void consume(ReminderEvent event) {
        // IDEMPOTENCY: skip if already processed today
        String key = "reminder:sent:" + event.getMtcn() + ":" + LocalDate.now();
        Boolean isNew = redis.opsForValue()
            .setIfAbsent(key, "1", Duration.ofHours(25));

        if (Boolean.FALSE.equals(isNew)) {
            log.info("Duplicate skipped: {}", event.getMtcn());
            return;
        }

        processReminder(event);
    }

    private void processReminder(ReminderEvent event) {
        TransactionDetails tx = txService.getByMtcn(event.getMtcn());
        String url = buildUrl(tx, event);

        CompletableFuture<Void> emailFuture =
            CompletableFuture.runAsync(() ->
                emailService.sendBatch(tx.getSenderEmail(), event.getReceiverName(), url));

        CompletableFuture<Void> pushFuture =
            CompletableFuture.runAsync(() ->
                notifService.sendBatch(tx.getDeviceToken(), event.getReceiverName(), url));

        CompletableFuture.allOf(emailFuture, pushFuture).join();

        // Update next_date
        LocalDate nextDate = calculateNextDate(event.getNextDate(), event.getFrequency());
        repo.updateNextDate(event.getId(), nextDate);
    }
}

5. Redis — Idempotency Guard

With 2M records and retry logic, duplicate sends are a serious risk. Redis SETNX (SET if Not eXists) ensures each reminder is processed exactly once per day.

5.1 Idempotency Key Pattern

// Key format: reminder:sent:{mtcn}:{date}
// TTL: 25 hours (covers the full day + buffer)

String key = String.format("reminder:sent:%s:%s",
    event.getMtcn(), LocalDate.now());

// Atomic SET NX EX — only first thread sets it
Boolean isNew = redisTemplate.opsForValue()
    .setIfAbsent(key, "1", Duration.ofHours(25));

if (!Boolean.TRUE.equals(isNew)) {
    return; // Already processed — skip
}

6. Batch Email & Push Notification APIs

Calling email/push APIs one record at a time is the #1 bottleneck. Use batch APIs to send in bulk.

6.1 SendGrid Batch Email

@Service
public class EmailService {

    // Buffer emails and flush every 100 or every 500ms
    private final List<Mail> buffer = Collections.synchronizedList(new ArrayList<>());

    @Scheduled(fixedDelay = 500) // flush every 500ms
    public void flushEmailBuffer() {
        if (buffer.isEmpty()) return;
        List<Mail> batch = new ArrayList<>(buffer);
        buffer.clear();

        // SendGrid supports 1000 personalizations per API call
        Lists.partition(batch, 1000).forEach(chunk -> {
            sendGridClient.api(buildBatchRequest(chunk));
        });
    }

    public void sendReminderEmail(String to, String name, String url, BigDecimal amt) {
        buffer.add(buildMail(to, name, url, amt)); // just buffer, don't send immediately
    }
}

6.2 FCM Batch Push

@Service
public class NotificationService {

    // FCM supports 500 tokens per sendMulticast call
    public void sendBatch(List<String> deviceTokens, String name, String url) {
        Lists.partition(deviceTokens, 500).forEach(chunk -> {
            MulticastMessage message = MulticastMessage.builder()
                .addAllTokens(chunk)
                .setNotification(Notification.builder()
                    .setTitle("Send money to " + name)
                    .setBody("Tap to send your scheduled payment")
                    .build())
                .putData("url", url)
                .build();

            BatchResponse response =
                FirebaseMessaging.getInstance().sendMulticast(message);
            log.info("FCM batch: {} success, {} fail",
                response.getSuccessCount(), response.getFailureCount());
        });
    }
}

7.3 Bulk UPDATE via JDBC

@Repository
public class ReminderBatchRepository {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    // Batch update 1000 rows in one statement — not 1000 separate updates
    public void bulkUpdateNextDate(List<ReminderUpdate> updates) {
        jdbcTemplate.batchUpdate(
            "UPDATE schedule_reminder SET next_date = ? WHERE id = ?",
            updates,
            1000, // batch size
            (ps, u) -> {
                ps.setDate(1, Date.valueOf(u.getNextDate()));
                ps.setLong(2, u.getId());
            }
        );
    }
}

8. ShedLock — Prevent Duplicate Runs Across Pods

When running multiple Spring Boot pods in Kubernetes, @Scheduled fires on ALL pods simultaneously. ShedLock ensures only ONE pod runs the producer job per day.

@Component
public class ReminderSchedulerJob {

    @Scheduled(cron = "0 0 6 * * *")
    @SchedulerLock(
        name = "ReminderJob",
        lockAtMostFor = "PT2H",    // release lock after 2 hours max
        lockAtLeastFor = "PT30M"   // hold lock at least 30 min
    )
    public void runDailyJob() {
        reminderBatchService.launchJob();
    }
}

9. Kubernetes — Auto-Scaling Consumers

Kafka consumer pods auto-scale based on consumer group lag (unprocessed messages).

9.1 Horizontal Pod Autoscaler (HPA)

# KEDA ScaledObject — scale on Kafka lag
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: reminder-consumer-scaler
spec:
  scaleTargetRef:
    name: reminder-consumer
  minReplicaCount: 2    # always have 2 pods
  maxReplicaCount: 20   # matches Kafka partitions
  triggers:
  - type: kafka
    metadata:
      topic: reminder.due
      consumerGroup: reminder-consumer-group
      lagThreshold: '100000'  # scale up if >100K unread messages
      bootstrapServers: kafka:9092

10. Failure Handling — Dead Letter Queue (DLQ)

In a 2M+ workload, some failures are inevitable (transient network errors, API rate limits). DLQ ensures failed messages are retried without re-processing successes.

10.1 Retry + DLQ Config

@Bean
public DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<?,?> template) {
    // Retry 3 times with 1s backoff before sending to DLQ
    ExponentialBackOffWithMaxRetries backoff =
        new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1000L);
    backoff.setMultiplier(2.0);

    DeadLetterPublishingRecoverer recoverer =
        new DeadLetterPublishingRecoverer(template,
            (rec, ex) -> new TopicPartition("reminder.due.DLQ", rec.partition()));

    return new DefaultErrorHandler(recoverer, backoff);
}

10.2 DLQ Reprocessing

// Separate job to replay DLQ — runs every 30 minutes
@Scheduled(fixedDelay = 1800000)
public void replayDlq() {
    List<ConsumerRecord<?,?>> failed = dlqConsumer.poll(Duration.ofSeconds(10));
    failed.forEach(record -> {
        ReminderEvent event = (ReminderEvent) record.value();
        log.warn("Replaying DLQ event: {}", event.getMtcn());
        kafkaTemplate.send("reminder.due", event.getSenderId(), event);
    });
}

12. Interview Talking Points — Scale Design

Q: How do you handle 2M records without OOM?

Spring Batch reads data in chunks (e.g., 1000 rows at a time) using paginated JDBC queries. No more than 1000 objects ever live in memory at once. Each chunk is published to Kafka and GC'd before the next chunk is loaded.

Q: How do you prevent duplicate sends on retry?

Redis SETNX with a 25-hour TTL. Before processing any reminder, we set a key like reminder:sent:MTCN:DATE. If the key already exists, we skip. Since Redis operations are atomic, two threads can never both get 'isNew = true' for the same key.

Q: How do you scale consumer throughput?

Kafka topics have 20 partitions. We deploy 20 consumer pods, each with concurrency=5 threads, giving 100 parallel workers. KEDA auto-scales pods based on consumer lag, so we don't over-provision during off-peak hours.

Q: What if the scheduler runs on multiple pods?

ShedLock prevents this. It inserts a lock row in the database before the job starts. Only the first pod to acquire the lock runs the job. Other pods see the lock is held and skip. The lock auto-releases after the configured max duration.

Q: How do you handle email/push API rate limits?

We use batch APIs: SendGrid supports 1000 personalizations per call, FCM supports 500 tokens per multicast call. This reduces API calls from 2M to ~4000, well within rate limits. We also add exponential backoff retry on 429 responses.

Q: How long does processing 2M records take?

With 100 parallel workers (20 pods x 5 threads) each processing ~50ms per record using batch APIs: 20,000 records / worker x 50ms = 17 minutes total. The Spring Batch producer step adds ~5 minutes for DB reads. Total: under 30 minutes well within a 2-hour SLA.

14. One-Liner Summary

"To scale the reminder system to 2M+ daily records, I replaced the single-threaded @Async design with Spring Batch partitioned reads, Kafka as the message bus with 20 partitions, horizontally auto-scaled consumer pods via KEDA, Redis for idempotency guards, SendGrid and FCM batch APIs to reduce API calls by 500-1000x, JDBC batch updates for DB writes, and ShedLock to prevent duplicate runs across Kubernetes pods — achieving under 30-minute end-to-end processing for 2 million reminders."
