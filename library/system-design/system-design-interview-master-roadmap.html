④ How to Handle the Interview

0–5 min — Clarify. “Before I design it, I want to clarify scale, users, core use cases and availability/latency expectations.”

5–10 min — Estimate. State assumptions. Calculate requests/sec, peak QPS, storage, bandwidth and major object counts.

10–20 min — Draw the simplest viable architecture. Client → LB/API → services → DB/cache/queue. Explain the data flow out loud.

20–30 min — Deep dive where it matters. Pick the hardest bottleneck: feed fanout, matching, media processing, rate limiting, etc.

30–40 min — Scale and failure. Ask yourself: “What breaks first at 10× traffic?” Then solve that bottleneck.

40–45 min — Trade-offs. Explain alternatives and why you selected the final design.

Golden rule: Do not start by drawing 20 microservices. Start with requirements → estimates → simple architecture → bottleneck → scale. The interviewer is evaluating your reasoning, not how many boxes you can draw.

When stuck

Say: “Let me make an assumption so I can move forward.” State it, continue, and invite correction.

When interviewer pushes scale

Recalculate the bottleneck. Move from vertical scaling to caching, partitioning, async processing, replication or sharding as appropriate.

When interviewer asks “Why X?”

Answer with workload + requirement + trade-off. Example: “I choose Redis because this path is latency-sensitive and read-heavy; the trade-off is cache invalidation complexity.”

When interviewer asks failure

Trace one request through the system and identify what happens if each dependency is slow, unavailable, duplicated or stale.
