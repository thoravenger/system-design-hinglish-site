Why cache at all?

Har read database tak kyun jaaye?

Problem

ShopKart's apps make 694,444 data reads per second at peak, because every screen needs about 20 pieces of data: the product, its price, stock, seller, rating and so on. The database page sized the database for 69,444 reads per second. If every read went to the database, it would need ten times the read replicas, and every screen would wait 5 ms for each read.

ShopKart ke apps peak pe 694,444 data reads per second karte hain, kyunki har screen ko lagbhag 20 cheezein chahiye: product, uska price, stock, seller, rating waghera. Database page ne database ko 69,444 reads per second ke liye size kiya tha. Agar har read database tak jaata, toh das guna read replicas chahiye hote, aur har screen har read ke liye 5 ms wait karti.

The cache layers

Phone se database tak, har layer pe ek cache

Problem

One product screen passes through the phone, the network edge, an app server, a shared cache and the database. Which layer should cache what? Put the price in the wrong layer and a customer sees yesterday's price. Put everything in one layer and that layer melts.

Ek product screen phone, network edge, app server, shared cache aur database se hokar guzarti hai. Kaunsi layer kya cache kare? Price galat layer mein daalo toh customer ko kal ka price dikhega. Sab kuch ek hi layer mein daalo toh woh layer pighal jaayegi.

Solution

Five layers, nearest first

  1. 0 msPhone or browser cache: images, scripts and styles the user already has. Controlled by the Cache-Control header the server sends.Phone ya browser cache: images, scripts aur styles jo user ke paas pehle se hain. Server jo Cache-Control header bhejta hai, wahi ise control karta hai.
  2. ~20 msCDN edge: images, scripts, styles and some public pages, served from a city near the user instead of from the far region.CDN edge: images, scripts, styles aur kuch public pages, door ke region ki jagah user ke paas wale shehar se serve hote hain.
  3. ~1 µsLocal cache in each app server: the hottest products, a few hundred MB per server, kept for seconds to a minute.Har app server mein local cache: sabse garam products, har server pe kuch sau MB, seconds se ek minute tak.
  4. ~0.5 msRedis: one shared cache per region for product data, listings, sessions and carts.Redis: har region mein ek shared cache: product data, listings, sessions aur carts ke liye.
  5. ~5 msDatabase: the truth. It only sees the misses.Database: sach. Use sirf misses dikhte hain.

  • Cache as close to the user as the data's freshness allows. Files that never change go all the way to the phone. Prices stop at Redis, where one delete fixes every server. Checkout reads the database, always.Data ki freshness jitni ijazat de, utna user ke paas cache karo. Jo files kabhi nahi badalti woh phone tak jaati hain. Price Redis pe rukta hai, jahan ek delete har server ko theek kar deta hai. Checkout hamesha database se padhta hai.
  • Each layer multiplies the protection. If the local cache answers half the reads and Redis answers 80% of the rest, the database sees only 10%.Har layer bachaav ko guna karti hai. Local cache aadhe reads ka jawab de aur Redis baaki ke 80% ka, toh database ko sirf 10% dikhta hai.

Trap: never let a shared layer cache a personal page. One missing private header on the cart page, and the CDN serves one customer's cart to the next person who asks.

Jaal: shared layer ko kabhi personal page cache mat karne do. Cart page pe ek private header chhoot gaya, aur CDN ek customer ka cart agle maangne wale ko dikha deta hai.

Hit ratio math

Hit ratio ka har extra 9 database ka kaam 10 guna ghatata hai

Problem

The team reports a 90% hit ratio and calls it great. Is it? What would 95% or 99% buy in database load and in latency? And why do most product screens still wait for the database even at 90%?

Team 90% hit ratio report karti hai aur use badhiya kehti hai. Kya sach mein? 95% ya 99% se database load aur latency mein kya milega? Aur 90% pe bhi zyaadatar product screens database ka intezaar kyun karti hain?

Solution

Database reads at 80% hits694,444 × 0.20138,889/s
Database reads at 90% hits694,444 × 0.1069,444/s
Database reads at 99% hits694,444 × 0.016,944/s
Average read at 90%0.5 + 0.10 × 5 ms1.0 ms
Average read at 99%0.5 + 0.01 × 5 ms0.55 ms

  • Think in misses. Going from 90% to 99% sounds like 9 points, but misses fall from 10% to 1%: the database does ten times less work.Misses mein socho. 90% se 99% sirf 9 points lagta hai, par misses 10% se 1% ho jaate hain: database das guna kam kaam karta hai.
  • Average latency barely moves. 1.0 ms becomes 0.55 ms per read. The big prize is database capacity and cost.Average latency mushkil se hilti hai. Har read 1.0 ms se 0.55 ms. Asli inaam database ki capacity aur kharcha hai.
  • Screens feel their worst key. A screen needs 20 keys. At 90% per key, 87.8% of screens include at least one miss and wait the full 5 ms. At 99%, only 18.2% do. Fetch all 20 keys in one round trip and load the misses in parallel.Screen apni sabse buri key ko mehsoos karti hai. Screen ko 20 keys chahiye. Har key pe 90% ho toh 87.8% screens mein kam se kam ek miss hota hai aur woh poore 5 ms wait karti hain. 99% pe sirf 18.2%. Saari 20 keys ek round trip mein lao aur misses ko parallel mein load karo.
  • Measure hit ratio per kind of key, weighted by cost. A 99% hit ratio on cheap product keys can hide a 50% hit ratio on the expensive search query that actually hurts the database.Hit ratio har tarah ki key ke liye alag napo, uski keemat ke hisaab se. Saste product keys pe 99% hit ratio us mehnge search query ke 50% ko chhupa sakta hai jo asal mein database ko dukhata hai.

Local cache vs Redis

Local cache (Caffeine)

  • A hit costs about 1 µs: a lookup in the app's own memory, no network.Hit ki keemat lagbhag 1 µs: app ki apni memory mein lookup, koi network nahi.
  • A miss falls through to Redis, not to the database, so the two levels multiply.Miss Redis tak girta hai, database tak nahi, isliye dono levels guna hote hain.

Redis

  • A hit costs one network round trip, about 0.5 ms in the same zone.Hit ki keemat ek network round trip, same zone mein lagbhag 0.5 ms.
  • 20 keys one by one cost 10 ms; one MGET or a pipeline costs about 0.5 ms.20 keys ek-ek karke 10 ms; ek MGET ya pipeline lagbhag 0.5 ms.

Redis vs Memcached for sizing

Redis

  • Executes commands on one thread per node; I/O threads only speed up the network part. More throughput means more shards.Har node pe commands ek hi thread pe chalte hain; I/O threads sirf network wala hissa tez karte hain. Zyada throughput matlab zyada shards.
  • Replicas give failover, and optional persistence (RDB, AOF) needs the fork headroom above.Replicas failover dete hain, aur optional persistence (RDB, AOF) ko upar wala fork headroom chahiye.

Memcached

  • Multi-threaded, so one large node uses all its cores: the same 548,611 commands/s fits on fewer, bigger nodes.Multi-threaded hai, toh ek bada node apne saare cores use karta hai: wahi 548,611 commands/s kam, bade nodes pe fit ho jaate hain.
  • No replication and no persistence: a dead node's keys simply become misses until they are refilled. Topic 19 shows what that does to the database.Na replication, na persistence: mare hue node ki keys refill hone tak bas misses ban jaati hain. Topic 19 dikhata hai ki isse database pe kya guzarti hai.

The hit ratio is an input, not a result you can assume. If it slips from 90% to 80%, refills double to 97,222/s and so does the database load. Size the database for the hit ratio you can defend on a bad day.

Hit ratio ek input hai, aisa result nahi jise maan liya jaaye. Agar yeh 90% se 80% pe gire, toh refills double hokar 97,222/s ho jaate hain aur database ka load bhi double. Database ko us hit ratio ke liye size karo jo bure din pe bhi tik sake.

Why a small cache works

Thodi si memory, zyaadatar reads: popularity ka hisaab

Problem

ShopKart sells 10 million products. Caching all of them takes 20 GB, far too much to copy into every app server. Is a local cache of only 100,000 products (200 MB) worth anything, or does it just miss all the time?

ShopKart 10 million products bechta hai. Sabko cache karne mein 20 GB lagta hai, jo har app server mein copy karne ke liye bahut zyada hai. Kya sirf 100,000 products (200 MB) ka local cache kisi kaam ka hai, ya woh bas miss hi karta rahega?

Solution

Popularity is steeply uneven. In many catalogs the product at rank r gets views in proportion to 1 ÷ r: the Zipf distribution with exponent s ≈ 1. The share of views that the top k of n products receive is then H(k) ÷ H(n), where H is the harmonic number, about ln n + 0.577.

Popularity bahut asmaan hoti hai. Kai catalogs mein rank r wale product ko 1 ÷ r ke anupaat mein views milte hain: yeh Zipf distribution hai, exponent s ≈ 1. Tab top k products ko n mein se H(k) ÷ H(n) views milte hain, jahan H harmonic number hai, lagbhag ln n + 0.577.

Two caches, two jobs. The small local cache holds the head of the curve and absorbs the heat. Redis holds the long tail, so a request for a rare product still avoids the database.

Do caches, do kaam. Chhota local cache curve ka head rakhta hai aur garmi sokh leta hai. Redis long tail rakhta hai, taaki kisi rare product ki request bhi database tak na jaaye.

A fresh cache has a hit ratio of zero. After a deploy, a restart or a flush, every read misses until the head of the curve is loaded again. Topics 17 and 19 cover warming it before traffic arrives.

Naye cache ka hit ratio zero hota hai. Deploy, restart ya flush ke baad har read miss karta hai jab tak curve ka head dobara load na ho. Topics 17 aur 19 batate hain ki traffic aane se pehle use garam kaise karein.

Cache-aside and the other patterns

Cache kaun bharta hai, aur write pe kya hota hai

Problem

The product service reads through the cache, and sellers change prices all day. Who loads a value into the cache, who updates it, and what exactly happens on a write so that customers do not keep seeing the old price?

Product service cache ke through padhti hai, aur sellers din bhar price badalte hain. Cache mein value kaun daalta hai, kaun update karta hai, aur write pe theek kya hota hai taaki customers ko purana price na dikhta rahe?

Solution

Cache-aside, the default

  1. 0.5 msRead, hit: GET product:42 finds the value. Done.Read, hit: GET product:42 ko value mil gayi. Kaam khatam.
  2. 5.5 msRead, miss: read the database, then SETEX product:42 3600 … so the next reader hits.Read, miss: database se padho, phir SETEX product:42 3600 … taaki agla reader hit kare.
  3. WriteUpdate the database first, the source of truth.Pehle database update karo, jo sach ka source hai.
  4. ThenDelete the key, never SET it. The next read loads the fresh value.Key delete karo, kabhi SET mat karo. Agla read taaza value load karega.
  • Why delete instead of update. Two sellers save a price at the same moment: A writes v1 to the database, B writes v2, B sets the cache to v2, then A sets it to v1. The database says v2 and the cache says v1 until the TTL ends. A delete cannot be applied in the wrong order: whoever reads next loads the latest value.Update ki jagah delete kyun. Do sellers ek hi pal mein price save karte hain: A database mein v1 likhta hai, B v2 likhta hai, B cache ko v2 set karta hai, phir A use v1 kar deta hai. Database v2 kehta hai aur cache TTL khatam hone tak v1. Delete galat order mein lag hi nahi sakta: jo agla padhega woh latest value load karega.

Problem

Solution

Three ways to hear about a change

TTLs and staleness budgets

Kaunsa data kitna purana chal sakta hai

Problem

How stale may each kind of data be? One TTL for everything is either too short, so the hit ratio falls and the database pays, or too long, so customers see wrong prices. And why keep a TTL at all if every change is already invalidated?

Har tarah ka data kitna purana chal sakta hai? Sab ke liye ek hi TTL ya toh bahut chhota hai, toh hit ratio girta hai aur database bharta hai, ya bahut lamba, toh customers ko galat price dikhta hai. Aur jab har change pehle se invalidate hota hai, toh TTL rakhein hi kyun?

Solution

The rule: a TTL is the staleness you accept if every invalidation silently fails. Invalidation keeps data fresh on a normal day; the TTL limits the damage on the day it breaks.

Niyam: TTL woh purana-pan hai jo tum manzoor karte ho agar har invalidation chupchaap fail ho jaaye. Aam din data ko invalidation taaza rakhta hai; jis din woh toote, nuksaan TTL seemit karta hai.

Four defences

Redis Cluster slots

Problem

Mumbai's cache is 10 primaries. How does a client know which one holds product:42? How do a user's cart and wishlist end up on the same node so one transaction can change both? And what do clients see while keys move to an 11th primary?

  • 16,384 hash slots. slot = CRC16(key) mod 16,384, and every slot belongs to one primary. With 10 primaries, each owns 1,638 or 1,639 slots.16,384 hash slots. slot = CRC16(key) mod 16,384, aur har slot ek primary ka hota hai. 10 primaries ke saath har ek ke paas 1,638 ya 1,639 slots.
  • Clients keep a slot map, like the shard map on the database page, and send each command straight to the owner. No proxy, no extra hop.Clients ek slot map rakhte hain, database page ke shard map jaisa, aur har command seedha maalik ko bhejte hain. Na proxy, na extra hop.
  • MOVED and ASK. A node that does not own the slot answers MOVED 3999 10.0.1.7:6379: the client fixes its map and retries. Jis node ke paas slot nahi, woh MOVED 3999 10.0.1.7:6379 jawab deta hai: client apna map theek karke retry karta hai.   • Hash tags. Only the part inside {…} is hashed, so cart:{u42} and wishlist:{u42} share a slot and one MULTI or Lua script can change both. Keys in different slots fail with CROSSSLOT. Do not tag too much: one popular tag makes one hot slot.Hash tags. Q2Easy

Walk me through cache-aside. On a write, why delete the key instead of updating it?

Q6Medium

Q8Hard

You delete the key after every write, yet customers sometimes see an old price for an hour. How is that possible?

Answer out loud first, then reveal.

The read-write race. Reader A misses and reads version 7; the seller commits version 8; the writer deletes the key, which is not there yet; reader A finishes and sets version 7. The delete ran before the stale fill. Fixes: versioned tombstones, where the delete writes "version 8 exists" and a Lua script refuses any older fill; leases, as in Facebook's memcache; or a delayed second delete. Then check the other writers: batch jobs that bypass the app are only caught by change data capture. The TTL bounds the worst case.

Read-write race. Reader A miss karke version 7 padhta hai; seller version 8 commit karta hai; writer key delete karta hai, jo abhi hai hi nahi; reader A khatam karke version 7 set kar deta hai. Delete stale fill se pehle chal gaya. Ilaaj: versioned tombstones, jahan delete "version 8 aa chuka" likhta hai aur Lua script har purane fill ko mana karti hai; leases, jaise Facebook ke memcache mein; ya der se doosra delete. Phir baaki writers dekho: app ko bypass karne wale batch jobs sirf change data capture pakadta hai. Sabse bura haal TTL seemit rakhta hai.

Q9Medium

How do you choose TTLs?

TTL kaise chunte ho?

Answer out loud first, then reveal.

A TTL is the staleness you would accept if every invalidation silently failed. So product details get an hour plus invalidation, prices 5 minutes plus invalidation and a database check at checkout, stock badges 10 s with no invalidation, listings 60 s, and sessions 30 minutes, renewed on use. Short TTLs hurt the long tail: a key read once a minute misses 50% of the time with 60 s but only 1.6% with an hour. And add ±10% jitter to every TTL so keys loaded together never expire together.

TTL woh purana-pan hai jo tum manzoor karoge agar har invalidation chupchaap fail ho jaaye. Toh product details ko ek ghanta aur invalidation, prices ko 5 minute, invalidation aur checkout pe database check, stock badges ko 10 s bina invalidation, listings ko 60 s, aur sessions ko 30 minute, use pe renew. Chhote TTL long tail ko chot dete hain: minute mein ek baar padhi jaane wali key 60 s pe 50% miss karti hai par ek ghante pe sirf 1.6%. Aur har TTL pe ±10% jitter lagao taaki saath load hui keys kabhi saath expire na hon.

A key read 5,000 times a second expires, and rebuilding it takes 50 ms. What happens, and how do you stop it?

Answer out loud first, then reveal.

Fixes, cheapest first: single-flight in each app server, one load per server, at most 102; a Redis lock with SET NX PX so one server in the fleet rebuilds while the others serve the stale copy; soft expiry so the value refreshes in the background before anyone misses; and XFetch, an early refresh with a probability that rises near expiry. For mass expiry after a warm-up, jitter the TTLs: a million keys over 720 s is 1,389 expiries a second.

Lagbhag 5,000 × 0.05 = 250 readers pehla rebuild aane se pehle miss karte hain, toh database wahi chhe queries 250 baar chalata hai: ek saath 1,500 queries. Q12Medium

LRU or LFU? What happens when a crawler reads the whole catalog?

LRU ya LFU? Jab crawler poora catalog padhta hai tab kya hota hai?

Answer out loud first, then reveal.

LRU evicts what was used longest ago; LFU evicts what is used least often. A crawler reading 10M products in an hour makes 2,778 one-time reads a second, and under LRU each looks recent: in a cache with room for 2M products, anything not re-read within 12 minutes is pushed out and the hit ratio dips. LFU, or Caffeine's W-TinyLFU admission, sees the crawler's key was used once and keeps the popular one. For Redis: allkeys-lru by default, allkeys-lfu if scans are common, and never noeviction for a cache.

LRU woh nikaalta hai jo sabse pehle use hua tha; LFU woh jo sabse kam use hota hai. Ghante mein 10M products padhne wala crawler second mein 2,778 ek-baar wale reads karta hai, aur LRU mein har ek recent lagta hai: 2M products wale cache mein jo 12 minute mein dobara na padha jaaye woh bahar, aur hit ratio girta hai. LFU, ya Caffeine ka W-TinyLFU admission, dekhta hai ki crawler ki key ek baar use hui aur popular wali ko rakhta hai. Redis ke liye: default allkeys-lru, scans aam hon toh allkeys-lfu, aur cache ke liye noeviction kabhi nahi.

Q13Medium

Bots request random product ids. What happens, and how do you protect the database?

Bots random product ids maangte hain. Kya hota hai, aur database ko kaise bachaoge?

Answer out loud first, then reveal.

Every request misses the cache and the database finds nothing: 20,000 bot requests a second become 20,000 database reads, 41% of Mumbai's miss budget. Negative caching does not help, because random ids never repeat. A Bloom filter of the 10M real ids at 1% false positives costs 12 MB and 7 hashes per lookup, and lets through about 200 of the 20,000. Add ids before products go live, rebuild it nightly to drop deleted ones, keep negative caching for deleted products, and rate-limit abusive clients.

Har request cache miss karti hai aur database ko bhi kuch nahi milta: second ki 20,000 bot requests 20,000 database reads ban jaati hain, Mumbai ke miss budget ka 41%. Negative caching kaam nahi aati, kyunki random ids kabhi repeat nahi hote. 10M asli ids ka 1% false positive wala Bloom filter 12 MB aur har lookup pe 7 hashes leta hai, aur 20,000 mein se lagbhag 200 hi jaane deta hai. Products live hone se pehle ids jodo, delete hue hatane ke liye raat ko dobara banao, delete hue products ke liye negative caching rakho, aur galat clients pe rate limit lagao.

A Redis primary dies at peak. Walk me through the next minute.

After cluster-node-timeout, 15 s by default, the other nodes mark it failed, and its replica wins the election and takes the slots at about 16 s; clients learn through MOVED. Meanwhile 48,611 reads a second lose their cache; 43,750 of them would have been hits, so the database goes from 48,611 to 92,361 reads/s, +90%. Bachaav: 20 se 50 ms timeouts, har node ka circuit breaker taaki requests mare node ko skip karein, aur bulkhead jo har server pe ek saath database reads seemit karta hai aur limit ke upar aakhri achhi values deta hai. Q15Medium

How does a Redis Cluster client find the node for a key, and what are hash tags for?

Redis Cluster client ko key ka node kaise milta hai, aur hash tags kis kaam aate hain?

Answer out loud first, then reveal.

slot = CRC16(key) mod 16,384. Each primary owns a range of slots, and clients cache the slot map and go straight to the owner. If the map is stale, the node replies MOVED with the new owner; during a migration, an ASK redirect is a one-off retry that does not change the map. Hash tags hash only the part in braces, so cart:{u42} and wishlist:{u42} share a slot and one transaction or Lua script can touch both; without them, multi-key commands fail with CROSSSLOT. Adding an 11th primary moves whole slots, about 9% of the keys.

slot = CRC16(key) mod 16,384. Har primary slots ki ek range ka maalik hai, aur clients slot map cache karke seedha maalik ke paas jaate hain. Map purana ho toh node naye maalik ke saath MOVED jawab deta hai; migration ke dauraan ASK redirect ek baar ka retry hai jo map nahi badalta. Hash tags sirf braces ke andar ka hissa hash karte hain, toh cart:{u42} aur wishlist:{u42} ek slot share karte hain aur ek transaction ya Lua script dono chhoo sakti hai; unke bina multi-key commands CROSSSLOT se fail hote hain. 11va primary jodne se poore slots hilte hain, lagbhag 9% keys.

Q16Hard

You run in Mumbai and Virginia. How do you cache, and how do you invalidate across the two regions?

Tum Mumbai aur Virginia mein chalte ho. Cache kaise karoge, aur dono regions mein invalidate kaise?

Answer out loud first, then reveal.

A cache per region, filled from that region's own database copy: never read a cache across a 190 ms ocean when the local replica answers in 5 ms. The trap is invalidation. If Mumbai sends a delete to Virginia at commit time, it arrives in about 95 ms, but Virginia's replica may apply the change only after about a second; a read in between refills the old price for the whole TTL. So each region invalidates from its own change stream, after its own replica has applied the change, with versioned tombstones and a TTL as backstops. Both regions purge the CDN tag, and the later purge wins.

Har region ka apna cache, us region ki apni database copy se bharta hua: jab local replica 5 ms mein jawab de, toh 190 ms ke ocean paar ka cache kabhi mat padho. Jaal invalidation mein hai. Agar Mumbai commit ke waqt Virginia ko delete bhejta hai, toh woh lagbhag 95 ms mein pahunchta hai, par Virginia ka replica change shayad lagbhag ek second baad apply kare; beech ka read poore TTL ke liye purana price bhar deta hai. Isliye har region apni change stream se invalidate karta hai, apne replica ke change apply karne ke baad, versioned tombstones aur TTL sahaare ke taur pe. Dono regions CDN tag purge karte hain, aur baad wala purge jeetta hai.

Q17Easy

Why consistent hashing instead of hash mod N?

hash mod N ki jagah consistent hashing kyun?

Answer out loud first, then reveal.

With mod N, going from 10 to 11 servers moves 10 of every 11 keys, 90.9%, so most of the cache misses at once and the database takes the load. On a hash ring a key belongs to the next server clockwise, so adding a server moves only the keys it takes over, about 1 in 11, 9.1%. Virtual nodes even out the load: in a test with 10 servers, one point per server left the busiest with 2.7 times the average load, while 160 points each, as ketama uses, brought it to 1.07.

mod N ke saath 10 se 11 servers pe jaane se har 11 mein se 10 keys, 90.9%, hilti hain, toh zyaadatar cache ek saath miss karta hai aur load database pe aata hai. Hash ring pe key clockwise agle server ki hoti hai, toh naya server sirf woh keys hilaata hai jo woh leta hai, lagbhag 11 mein 1, 9.1%. Virtual nodes load barabar karte hain: 10 servers ke test mein har server ka ek point hone pe sabse busy server pe average ka 2.7 guna load tha, jabki ketama ki tarah 160 points pe 1.07.

Q18Hard

Show me the read path in code: which classes, in what order?

Read path code mein dikhao: kaunsi classes, kis order mein?

Answer out loud first, then reveal.

A facade, CatalogReadService, is the only class the API calls. The Bloom filter goes first, so made-up ids get a 404 without touching anything. Then the local cache, about 1 µs. Then Redis, through the slot map and a circuit breaker. On a miss, single-flight allows one load per key per server; that load needs a database permit or fails fast; it reads the row and fills Redis with the row's version, so it can never overwrite a newer tombstone, and then keeps the value locally. Around it sit the regional invalidator on the change stream, the hot-key guard, the TTL and header policies, and metrics for the hit ratio of each layer.

Ek facade, CatalogReadService, hi woh class hai jise API call karta hai. Sabse pehle Bloom filter, taaki gadhe hue ids ko kuch chhooe bina 404 mile. Phir local cache, lagbhag 1 µs. Phir Redis, slot map aur circuit breaker ke through. Miss pe single-flight har server pe har key ka ek load hone deta hai; us load ko database permit chahiye warna jaldi fail; woh row padhta hai aur Redis ko row ke version ke saath bharta hai, taaki naye tombstone ke upar kabhi na likhe, phir value locally rakhta hai. Iske aas-paas hain change stream pe regional invalidator, hot-key guard, TTL aur header policies, aur har layer ke hit ratio ke metrics.
