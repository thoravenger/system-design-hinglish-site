1. SCALABILITY

Q: What is Scalability and why does it matter?

A: Scalability is the system's ability to handle increased load (users, data, requests) without degrading performance. It is the foundation of all distributed system design.

Types:

  • Vertical Scaling (Scale Up): Add more CPU/RAM to existing machine. Simple but has hard limits and single point of failure.
  • Horizontal Scaling (Scale Out): Add more machines. Unlimited ceiling, more complex to implement.

When to use Vertical: Early-stage startup, stateful apps (databases), quick win before architectural changes.

When to use Horizontal: High traffic web services, stateless services, microservices.

Advantages of Horizontal: No SPOF, cost-effective at scale, elastic.

Disadvantages: Distributed complexity, data consistency challenges, network latency.

HLD: Load Balancer → [App Server 1, App Server 2, App Server N] → Shared DB / Cache

LLD (Spring Boot Stateless Service):

3. API DESIGN

Q: What makes a good REST API design?

A: A good API is consistent, intuitive, versioned, and backward-compatible.

REST Principles:

  • Resources are nouns, not verbs (/users, not /getUser)
  • HTTP methods: GET=read, POST=create, PUT=replace, PATCH=partial update, DELETE=remove
  • Stateless — every request self-contained
  • Use proper HTTP status codes (200, 201, 204, 400, 401, 403, 404, 409, 422, 500)
  • Versioning: /api/v1/users
  • Pagination: ?page=0&size=20&sort=createdAt,desc
  • Consistent error response format

Richardson Maturity Model:

  • Level 0: HTTP tunnel (SOAP-style)
  • Level 1: Resources (/users/{id})
  • Level 2: HTTP verbs correctly used
  • Level 3: HATEOAS (hypermedia links in responses)
@RestController
@RequestMapping("/api/v1/users")
@RequiredArgsConstructor
@Validated
public class UserController {

    private final UserService userService;

    @GetMapping
    public ResponseEntity<PagedResponse<UserDTO>> getUsers(
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "20") @Max(100) int size,
            @RequestParam(required = false) String status) {
        Pageable pageable = PageRequest.of(page, size, Sort.by("createdAt").descending());
        Page<UserDTO> users = userService.findAll(status, pageable);
        return ResponseEntity.ok(PagedResponse.of(users));
    }

    @PostMapping
    public ResponseEntity<UserDTO> createUser(
            @Valid @RequestBody CreateUserRequest request,
            @RequestHeader(value = "Idempotency-Key", required = false) String key) {
        UserDTO created = userService.create(request, key);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}").buildAndExpand(created.id()).toUri();
        return ResponseEntity.created(location).body(created);
    }

    @PatchMapping("/{id}")
    public ResponseEntity<UserDTO> updateUser(
            @PathVariable Long id,
            @Valid @RequestBody UpdateUserRequest request) {
        return ResponseEntity.ok(userService.update(id, request));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteUser(@PathVariable Long id) {
        userService.delete(id);
        return ResponseEntity.noContent().build();
    }
}

4. FAULT TOLERANCE

Q: What patterns implement fault tolerance in distributed systems?

A: Fault Tolerance is the system's ability to continue operating correctly even when components fail.

Core Patterns:

  • Retry: Re-attempt transient failures with exponential backoff
  • Circuit Breaker: Stop calling failing service, fail fast
  • Fallback: Return cached/default response on failure
  • Bulkhead: Isolate failures to prevent cascade
  • Timeout: Never wait forever for a response
  • Redundancy: Multiple instances of every critical component

Circuit Breaker States:

  • CLOSED → OPEN (when failure rate > threshold)
  • OPEN → HALF_OPEN (after wait duration)
  • HALF_OPEN → CLOSED/OPEN (based on test calls)
// Resilience4j with Spring Boot
// build.gradle: implementation 'io.github.resilience4j:resilience4j-spring-boot3'

@Service
@RequiredArgsConstructor
public class PaymentService {

    private final PaymentGateway gateway;

    @CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
    @Retry(name = "payment")
    @TimeLimiter(name = "payment")
    @Bulkhead(name = "payment", type = Bulkhead.Type.SEMAPHORE)
    public CompletableFuture<PaymentResult> processPayment(PaymentRequest req) {
        return CompletableFuture.supplyAsync(() -> gateway.charge(req));
    }

    public CompletableFuture<PaymentResult> paymentFallback(
            PaymentRequest req, Exception ex) {
        log.warn("Payment fallback triggered: {}", ex.getMessage());
        // Queue for async retry
        eventQueue.publish(new PendingPaymentEvent(req));
        return CompletableFuture.completedFuture(PaymentResult.pending(req.getOrderId()));
    }
}

5. ERASURE CODING

Q: What is Erasure Coding and when to use it over replication?

A: Erasure Coding splits data into k data chunks + m parity chunks (total k+m), stored across nodes. Any k chunks can reconstruct original data. Tolerate up to m failures.

RS(6,3) Example: 6 data + 3 parity = 9 chunks. Tolerate 3 failures. Storage overhead = 9/6 = 1.5x.

3x Replication: Same fault tolerance but 3x storage overhead.

When to use Erasure Coding: Cold storage/archival (AWS S3 Glacier, HDFS), large objects, storage cost is primary concern.

When to use Replication: Hot data needing fast reads, real-time systems, small objects.

Disadvantage of EC: Higher CPU for encode/decode; higher read latency (must gather k chunks from different nodes).

Real-world: Facebook f4 uses RS(10,4): tolerates 4 failures at only 1.4x overhead, saving petabytes vs 3x replication.

// Conceptual RS encoding illustration
public class ErasureCodingSimulator {
    private static final int DATA_SHARDS = 4;
    private static final int PARITY_SHARDS = 2;

    // In production: use ISA-L or Jerasure library via JNI
    public List<byte[]> encode(byte[] data) {
        int shardSize = (int) Math.ceil((double) data.length / DATA_SHARDS);
        List<byte[]> shards = new ArrayList<>();

        // Split data into DATA_SHARDS chunks
        for (int i = 0; i < DATA_SHARDS; i++) {
            byte[] shard = new byte[shardSize];
            int start = i * shardSize;
            int len = Math.min(shardSize, data.length - start);
            if (len > 0) System.arraycopy(data, start, shard, 0, len);
            shards.add(shard);
        }
        // Generate parity shards via XOR (real RS uses Galois Field GF(2^8))
        shards.add(xorShards(shards.subList(0, 2)));
        shards.add(xorShards(shards.subList(2, 4)));
        return shards;
    }

    private byte[] xorShards(List<byte[]> shards) {
        byte[] result = new byte[shards.get(0).length];
        for (byte[] s : shards)
            for (int i = 0; i < result.length; i++) result[i] ^= s[i];
        return result;
    }
}

6. SHARDING

Q: What are the database sharding strategies and when does each shine?

A: Sharding is horizontal partitioning — splitting data across multiple DB instances (shards) where each shard holds a subset.

Strategies:

StrategyHowProsCons
Range-BasedShard by value range (IDs 1-1M)Easy range queriesHot partitions
Hash-Based`shard = hash(key) % N`Even distributionNo range queries; resharding painful
Directory-BasedLookup table: key → shardFlexibleLookup table is SPOF
GeographicBy region/countryData locality, complianceCross-region queries slow

When to shard: Single DB can't handle write throughput; dataset exceeds server capacity; query latency too high even with indexing.

Problems: Cross-shard JOINs (scatter-gather), rebalancing, distributed transactions, schema migrations on all shards.

Consistent Hashing solves the resharding problem — adding a node moves only K/N keys (not all).

// Consistent Hash Ring — virtual nodes for even distribution
public class ConsistentHashRouter<T> {
    private final SortedMap<Integer, T> ring = new TreeMap<>();
    private final int virtualNodes;

    public ConsistentHashRouter(List<T> nodes, int virtualNodes) {
        this.virtualNodes = virtualNodes;
        nodes.forEach(this::addNode);
    }

    public void addNode(T node) {
        for (int i = 0; i < virtualNodes; i++)
            ring.put(hash(node + "#" + i), node);
    }

    public void removeNode(T node) {
        for (int i = 0; i < virtualNodes; i++)
            ring.remove(hash(node + "#" + i));
    }

    public T getNode(String key) {
        if (ring.isEmpty()) throw new IllegalStateException("No nodes");
        int hash = hash(key);
        SortedMap<Integer, T> tail = ring.tailMap(hash);
        return (tail.isEmpty() ? ring : tail).get(
            tail.isEmpty() ? ring.firstKey() : tail.firstKey());
    }

    private int hash(String key) {
        // Use MurmurHash3 in production for better distribution
        return Math.abs(key.hashCode());
    }
}

7. EVENT-DRIVEN ARCHITECTURE

Q: When should you choose Event-Driven Architecture?

A: EDA is a paradigm where services communicate by emitting and consuming events asynchronously through an event broker.

Core Components:

  • Producer: Emits events (order-service → "OrderPlaced")
  • Broker: Routes and persists events (Kafka, RabbitMQ)
  • Consumer: Reacts to events (payment-service, inventory-service)

When to use EDA:

  • Decoupled microservices (services shouldn't directly call each other)
  • Fan-out: one event triggers many consumers
  • Workflows spanning multiple services (order → payment → shipping → notification)
  • Audit trail / event sourcing
  • Real-time data pipelines

Advantages: Loose coupling, high throughput, temporal decoupling, easy to add consumers without modifying producers.

Disadvantages: Eventual consistency, hard to debug (need distributed tracing), duplicate events (idempotency required), ordering challenges.

Outbox Pattern: Atomically save event + business data in same DB transaction, then publish separately — ensures no event is lost.

// Producer with Outbox Pattern (atomicity guarantee)
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepo;
    private final OutboxRepository outboxRepo;
    private final KafkaTemplate<String, Object> kafka;

    @Transactional  // Both order and outbox saved atomically
    public Order placeOrder(CreateOrderRequest req) {
        Order order = orderRepo.save(Order.from(req));

        // Save to outbox table — same transaction, guaranteed delivery
        outboxRepo.save(OutboxEvent.builder()
            .aggregateId(order.getId().toString())
            .eventType("OrderPlaced")
            .payload(toJson(order))
            .status(OutboxStatus.PENDING)
            .build());

        return order;
    }

    // Scheduled job or CDC picks up PENDING outbox events and publishes
    @Scheduled(fixedDelay = 1000)
    @Transactional
    public void publishPendingEvents() {
        List<OutboxEvent> pending = outboxRepo.findByStatus(OutboxStatus.PENDING);
        pending.forEach(event -> {
            kafka.send("orders", event.getAggregateId(), event.getPayload());
            event.setStatus(OutboxStatus.PUBLISHED);
            outboxRepo.save(event);
        });
    }
}

// Consumer with idempotency
@Service
public class PaymentEventConsumer {

    private final Set<String> processedIds = Collections.synchronizedSet(
        new LinkedHashSet<>() {
            protected boolean removeEldestEntry(Map.Entry e) { return size() > 10000; }
        });

    @KafkaListener(topics = "orders", groupId = "payment-service")
    public void handleOrderPlaced(@Payload OrderEvent event, Acknowledgment ack) {
        try {
            if (!processedIds.contains(event.getEventId())) {

                processedIds.add(event.getEventId());

            ack.acknowledge();
        } catch (Exception e) {

            // Don't ack — Kafka redelivers
        }
    }
}

8. BULKHEAD PATTERN

Q: What is the Bulkhead pattern and why is it critical in microservices?

A: Bulkhead isolates resources so a failure in one area doesn't cascade to others — like watertight compartments preventing a ship from sinking when one compartment floods.

Without Bulkhead: Slow payment service exhausts entire thread pool → entire application becomes unresponsive for all operations.

With Bulkhead: Payment has its own thread pool (10 threads). If payment hangs, inventory (separate 20 threads) continues serving normally.

Types:

  • Thread Pool Bulkhead: Dedicated thread pool per dependency (best isolation)
  • Semaphore Bulkhead: Limit concurrent calls (lighter, shares thread pool)
@Service
public class OrderFulfillmentService {

    // Separate thread pool per dependency = full isolation
    private final ExecutorService paymentPool = new ThreadPoolExecutor(
        5, 10, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(50),                                // Queue 50 requests
        new ThreadFactoryBuilder().setNameFormat("payment-%d").build(),
        new ThreadPoolExecutor.AbortPolicy());                        // Reject when full → fast fail

    private final ExecutorService inventoryPool = new ThreadPoolExecutor(
        10, 20, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(100),
        new ThreadFactoryBuilder().setNameFormat("inventory-%d").build(),
        new ThreadPoolExecutor.CallerRunsPolicy());

    public CompletableFuture<FulfillmentResult> fulfill(Order order) {
        // Payment hangs? Only paymentPool threads affected — inventory unaffected
        CompletableFuture<PaymentResult> payment =
            CompletableFuture.supplyAsync(() -> paymentService.charge(order), paymentPool)
                .orTimeout(5, TimeUnit.SECONDS)
                .exceptionally(ex -> PaymentResult.failed(ex.getMessage()));

        CompletableFuture<InventoryResult> inventory =
            CompletableFuture.supplyAsync(() -> inventoryService.reserve(order), inventoryPool)
                .orTimeout(3, TimeUnit.SECONDS)
                .exceptionally(ex -> InventoryResult.failed(ex.getMessage()));

        return CompletableFuture.allOf(payment, inventory)
            .thenApply(v -> FulfillmentResult.of(payment.join(), inventory.join()));
    }
}

9. BLUE-GREEN DEPLOYMENT

Q: What is Blue-Green Deployment and when to use it vs Canary?

A: Blue-Green maintains two identical production environments. Blue = current, Green = new version. Traffic switches instantly (100% at once) from Blue to Green.

Flow: Deploy Green → Test Green → Switch LB 100% → Blue becomes standby → Decommission Blue.

Blue-Green vs Canary:

Blue-GreenCanary
Traffic switch100% instantGradual (1% → 5% → 100%)
RollbackInstant (flip LB back)Slow (drain canary)
CostDouble infra during transitionMinimal extra
RiskAll users see new version at onceSmall blast radius
DB changesMust be backward compatibleSame requirement

When to use Blue-Green: Need instant rollback, compliance requirements, database migration scenarios.

When to use Canary: Gradual confidence building, A/B testing, cost-sensitive.

10. CORRELATION ID

Q: What is a Correlation ID and how do you propagate it across microservices?

A: A Correlation ID (Trace ID) is a unique identifier attached to every request, flowing through all services, enabling end-to-end request tracing across a distributed system.

Why critical: Without it, correlating logs across 10 services for a single user request is nearly impossible.

Propagation points: HTTP headers, Kafka message headers, gRPC metadata, async tasks.

// 1. Filter to generate/extract Correlation ID
@Component
@Order(1)
public class CorrelationIdFilter implements Filter {

    public static final String CORRELATION_HEADER = "X-Correlation-Id";
    public static final String MDC_KEY = "correlationId";

    @Override
    public void doFilter(ServletRequest req, ServletResponse res,
                         FilterChain chain) throws IOException, ServletException {
        HttpServletRequest httpReq = (HttpServletRequest) req;
        String id = httpReq.getHeader(CORRELATION_HEADER);
        if (id == null || id.isBlank()) id = UUID.randomUUID().toString();

        MDC.put(MDC_KEY, id);
        ((HttpServletResponse) res).setHeader(CORRELATION_HEADER, id);

        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();  // CRITICAL: prevent MDC leak in thread pools
        }
    }
}

// 2. Propagate via WebClient (reactive HTTP calls)
@Bean
public WebClient webClient() {
    return WebClient.builder()
        .filter((request, next) -> {
            String id = MDC.get(CorrelationIdFilter.MDC_KEY);
            return next.exchange(ClientRequest.from(request)
                .header(CorrelationIdFilter.CORRELATION_HEADER,
                    id != null ? id : UUID.randomUUID().toString())
                .build());
        }).build();
}

// 3. Propagate via Kafka headers
@Service
public class EventPublisher {
    public void publish(String topic, Object event) {
        String id = MDC.get(CorrelationIdFilter.MDC_KEY);
        kafkaTemplate.send(MessageBuilder.withPayload(event)
            .setHeader("X-Correlation-Id", id)
            .setHeader(KafkaHeaders.TOPIC, topic)
            .build());
    }
}

11. QUERY OPTIMIZATION

Q: What are the key techniques for database query optimization?

A: Query optimization is the #1 lever for improving application performance. Poor queries cause most production incidents.

Optimization Hierarchy (most impactful first):

  • Proper Indexing — can reduce query from full scan (O(n)) to index seek (O(log n))

  • Use Pagination — never fetch unbounded rows

  • Covering Index — all needed columns in index = no table lookup
  • Partial Index — index subset of rows (e.g., only ACTIVE records)
  • Read Replicas — route SELECT queries to replica
  • Denormalization — pre-join data for read-heavy queries
  • Query Result Caching — cache expensive aggregates

  • Disable default typing in Jackson globally
  • Validate all input after deserialization
  • Use allowlists for acceptable types

14. MAPREDUCE

Q: What is MapReduce and when should you use it vs Spark?

A: MapReduce is a batch processing paradigm: split → map (parallel processing) → shuffle/sort → reduce (aggregate). Designed for petabyte-scale batch jobs on commodity hardware.

Phases:

  • Split: Input divided into chunks (e.g., 128MB HDFS blocks)
  • Map: Each chunk processed in parallel, outputs (key, value) pairs
  • Shuffle & Sort: Framework groups all values by key across all mappers
  • Reduce: Aggregate values per key → final output

MapReduce vs Spark:

SpeedSlower10-100x faster for iterative
Fault toleranceCheckpoint to diskRDD lineage
Use caseSingle-pass batch ETLML, iterative, SQL
Learning curveSimpleModerate

Use MapReduce when: Simple single-pass ETL over petabytes, HDFS-native jobs, cost matters.

Use Spark when: Multiple passes over data, ML training, real-time, SQL analytics.

15. AVAILABILITY

Q: How do you achieve and calculate system availability?

A: Availability = uptime / total time, expressed as "nines."

Availability Tiers:

SLADowntime/YearDowntime/Month
99% (2 nines)3.65 days7.3 hours
99.9% (3 nines)8.76 hours43.8 min
99.99% (4 nines)52.6 min4.4 min
99.999% (5 nines)5.26 min26.3 sec

Series vs Parallel:

  • Series: A = A1 × A2 × A3 (each component degrades overall availability)
  • Parallel: A = 1 - (1-A1)(1-A2) (redundancy dramatically improves availability)

Example: Two 99.9% servers in parallel = 1 - (0.001)² = 99.9999%

Strategies: No SPOF (redundancy), health checks + auto-healing, multi-AZ, graceful degradation, chaos engineering.

16. SQL vs NoSQL

Q: How do you decide between SQL and NoSQL?

A: There is no universal winner. The choice depends on access patterns, consistency needs, and scale.

Choose SQL when:

  • ACID transactions required (payments, inventory adjustments, transfers)
  • Complex relationships and JOINs needed
  • Schema is well-defined and stable
  • Strong consistency required
  • Ad-hoc reporting and analytics

Choose NoSQL when:

  • Document: Flexible/evolving schema, hierarchical data (user profiles, product catalogs)
  • Key-Value: Ultra-fast simple lookups, sessions, counters
  • Column-Family: Massive write throughput, time-series, IoT data streams
  • Graph: Highly connected data, social graphs, recommendation engines

CAP Theorem positions:

  • PostgreSQL → CP (Consistency + Partition tolerance)
  • Cassandra → AP (Availability + Partition tolerance, eventual consistency)
  • MongoDB → CP (default) with tunable consistency

public class UserService {

            .orElseGet(() -> {
                User user = userRepo.findById(id)
                    .orElseThrow(() -> new UserNotFoundException(id));
                cache.put(id, user, Duration.ofMinutes(30));
                return user;
            });

    @Transactional

        user.update(req);
        userRepo.save(user);
        cache.evict(id);                    // Invalidate cache
        searchRepo.index(user);             // Update search index
        activityRepo.recordUpdate(id, req); // Log activity
        return user;
    }
}

18. HIGH AVAILABILITY

Q: What is the difference between High Availability and Fault Tolerance?

A:

  • Fault Tolerance: System continues WITHOUT interruption after failure (zero downtime, transparent to users). Requires real-time failover — expensive.

Active-Active use: Stateless services, global distribution.

Active-Passive use: Stateful services (primary DB), where synchronization complexity is high.

19. CONSENSUS

Q: What is distributed consensus and which algorithms solve it?

A: Consensus is getting all nodes in a distributed system to agree on a single value despite node failures and network partitions.

FLP Impossibility: In an async distributed system, no algorithm can guarantee consensus if even one node can fail. Real systems choose safety over liveness under extreme partitions.

Algorithms:

  • Raft: Most understandable. Leader election + log replication. Used by etcd, CockroachDB, TiKV.
  • Paxos: Foundational but complex. Used by Google Chubby, Spanner.
  • ZAB: ZooKeeper Atomic Broadcast — used by Kafka (metadata), HDFS NameNode.
  • PBFT: Byzantine fault tolerant — handles malicious nodes. Used in blockchain.

Raft Phases:

  • Leader Election: Candidate requests votes → majority wins → becomes leader
  • Log Replication: Leader appends to log, replicates to followers, commits when majority ACK
  • Safety: Only committed entries applied to state machine

Where used: etcd (Kubernetes), ZooKeeper (Kafka), CockroachDB, Consul service discovery.

// Using Redisson for distributed consensus primitives
@Service
public class DistributedCoordinator {

    private final RedissonClient redisson;

    // Leader election via Redisson (uses Raft internally in cluster mode)
    public void campaignForLeadership(String serviceName) {
        RLeaderLatch latch = redisson.getLeaderLatch("election:" + serviceName);
        latch.addListener(() -> {
            if (latch.hasLeadership()) {
                log.info("This node is now LEADER for {}", serviceName);
                onLeadershipAcquired(serviceName);
            }
        });
        latch.start();
    }

    // Distributed atomic counter (Raft-replicated across Redis cluster)
    public long incrementCounter(String counterName) {
        return redisson.getAtomicLong(counterName).incrementAndGet();
    }

    // Distributed semaphore (consensus on available permits)
    public boolean tryAcquirePermit(String resource, int maxPermits, Duration timeout) {
        RSemaphore semaphore = redisson.getSemaphore("semaphore:" + resource);
        semaphore.trySetPermits(maxPermits);
        try {
            return semaphore.tryAcquire(timeout.toMillis(), TimeUnit.MILLISECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        }
    }
}

22. RETRY LOGIC

Q: How do you implement robust retry logic without causing thundering herd?

A: Retry logic re-attempts transient failures. Key rules: exponential backoff + jitter (avoid all clients retrying simultaneously), idempotency (retries must be safe), retry budget (bound retry overhead).

Retry vs Circuit Breaker: Retry handles transient failures; Circuit Breaker handles prolonged outages. Use both together.

What to retry: Network timeouts, 503 errors, transient DB errors.

Never retry: 4xx client errors (bug in request), business logic exceptions, non-idempotent operations without idempotency key.

@Configuration
@EnableRetry
public class RetryConfig {}

@Service
public class ExternalApiService {

    @Retryable(
        retryFor = {HttpServerErrorException.class, ResourceAccessException.class},
        noRetryFor = {HttpClientErrorException.class},  // Don't retry 4xx
        maxAttempts = 3,
        backoff = @Backoff(
            delay = 1000,        // Initial delay 1s
            multiplier = 2.0,    // Double each attempt
            random = true,       // Add jitter
            maxDelay = 30000     // Cap at 30s
        )
    )
    public ApiResponse callExternalApi(ApiRequest request) {
        return restTemplate.postForObject("/external/api", request, ApiResponse.class);
    }

    @Recover  // Called when all retries exhausted
    public ApiResponse recoverFromFailure(Exception ex, ApiRequest request) {
        log.error("All retries exhausted for {}", request.getId(), ex);
        return ApiResponse.defaultResponse();
    }
}

// Manual retry with full jitter backoff (best for avoiding thundering herd)
public <T> T executeWithFullJitter(Supplier<T> op, int maxAttempts, long baseDelayMs) {
    Random rng = new Random();
    for (int attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return op.get();
        } catch (RetryableException e) {
            if (attempt == maxAttempts) throw e;
            // Full jitter: sleep random duration from 0 to cap
            long cap = Math.min(baseDelayMs * (1L << (attempt - 1)), 30_000L);
            long sleep = (long) (cap * rng.nextDouble());
            LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(sleep));
        }
    }
    throw new RuntimeException("Should not reach here");
}

Q: How do you tune HikariCP connection pool for production?

A: Connection pooling reuses database connections, avoiding ~50-200ms connection setup overhead per request. HikariCP is Spring Boot's default and fastest JVM pool.

Tuning Formula: Pool size = (core count × 2) + effective_disk_spindles

HikariCP recommendation: For most apps, pool size = 10-20. Bigger is NOT always better — excess connections cause DB-side contention.

HikariCP settings:

  • maximumPoolSize: Max concurrent connections (start at 10, increase under load)
  • minimumIdle: Connections maintained when idle (set = maximumPoolSize for fixed pool)
  • connectionTimeout: Max wait for connection from pool (30s default)
  • idleTimeout: Remove idle connections (10 min)
  • maxLifetime: Max connection age (30 min, less than DB's wait_timeout)
  • keepaliveTime: Ping idle connections (60s, prevent firewall timeout)

27. STRANGLER PATTERN

Q: What is the Strangler Fig Pattern for legacy migration?

A: The Strangler Fig Pattern incrementally migrates a legacy monolith to microservices by routing requests to new services one feature at a time, until the monolith is "strangled" and can be decommissioned.

Name origin: Strangler fig tree grows around a host tree, eventually replacing it while the host dies.

Migration Steps:

  • Put a Facade/Proxy in front of the monolith
  • Identify a bounded context to extract (e.g., User Management)
  • Build new microservice for that context
  • Route that specific traffic to new service via proxy
  • Verify new service correct, remove from monolith
  • Repeat until monolith empty

Why safe: At every step, rollback is a config change in the proxy. No big-bang cutover.

// Spring Cloud Gateway as Strangler Facade
@Configuration
public class StranglerGatewayConfig {

    @Bean
    public RouteLocator routes(RouteLocatorBuilder builder) {
        return builder.routes()
            // MIGRATED: User service — route to new microservice
            .route("user-service", r -> r
                .path("/api/users/**")
                .filters(f -> f
                    .rewritePath("/api/users/(?<segment>.*)", "/users/${segment}")
                    .addRequestHeader("X-Migrated", "true"))
                .uri("lb://user-service"))

            // MIGRATED: Order service
            .route("order-service", r -> r
                .path("/api/orders/**")
                .uri("lb://order-service"))

            // NOT YET MIGRATED: Everything else → monolith
            .route("legacy-monolith", r -> r
                .path("/**")
                .filters(f -> f.addRequestHeader("X-Legacy", "true"))
                .uri("http://monolith:8080"))
            .build();
    }
}

// Feature flag to toggle between legacy and new implementation
@Service
public class UserServiceFacade {

    @Value("${feature.new-user-service.enabled:false}")
    private boolean useNewService;

    private final LegacyUserService legacyService;
    private final NewUserService newService;

        if (useNewService) {
            try {
                return newService.findById(id);
            } catch (Exception e) {
                log.error("New service failed, falling back to legacy", e);
                metrics.counter("strangler.fallback").increment();
                return legacyService.findById(id);
            }
        }
        return legacyService.findById(id);
    }
}

28. BATCH PROCESSING

Q: When do you use batch processing vs stream processing?

A: Batch processes data in large, bounded chunks on a schedule. Stream processes data continuously as it arrives.

Use Batch when:

  • Data can wait (nightly reports, billing, payroll)
  • Processing requires full dataset (monthly aggregations)
  • Throughput over latency (ETL pipelines)
  • Resource efficiency (run during off-peak)

Use Stream when:

  • Real-time decisions required (fraud detection)
  • Low latency requirements (<1 second)
  • Continuous data arriving (IoT, clickstream)

Batch frameworks: Spring Batch, Apache Spark, AWS Glue.

Stream frameworks: Apache Flink, Kafka Streams, Apache Spark Streaming.

// Spring Batch — production-grade batch job
@Configuration
@EnableBatchProcessing
public class OrderReportBatch {

    @Bean
    public Job orderReportJob(
            JobBuilderFactory jbf,
            StepBuilderFactory sbf,
            DataSource dataSource) {

        return jbf.get("orderReportJob")
            .incrementer(new RunIdIncrementer())
            .listener(new JobCompletionListener())
            .start(generateReportStep(sbf, dataSource))
            .next(emailReportStep(sbf))
            .build();
    }

    @Bean
    public Step generateReportStep(StepBuilderFactory sbf, DataSource ds) {
        return sbf.get("generateReport")
            .<OrderRecord, ReportLine>chunk(500)    // Process in chunks of 500
            .reader(orderItemReader(ds))
            .processor(orderToReportLineProcessor())
            .writer(reportLineWriter())
            .faultTolerant()
                .retryLimit(3)
                .retry(TransientDataAccessException.class)
                .skipLimit(10)
                .skip(MalformedDataException.class)
            .listener(new ChunkProcessingListener())
            .build();
    }

    @Bean
    @StepScope
    public JdbcCursorItemReader<OrderRecord> orderItemReader(DataSource ds) {
        return new JdbcCursorItemReaderBuilder<OrderRecord>()
            .name("orderReader")
            .dataSource(ds)
            .sql("""
                SELECT o.id, o.customer_id, o.amount, o.status, o.created_at,
                       c.name as customer_name, c.email
                FROM orders o JOIN customers c ON o.customer_id = c.id
                WHERE o.created_at BETWEEN :startDate AND :endDate
                """)
            .rowMapper(new BeanPropertyRowMapper<>(OrderRecord.class))
            .build();
    }

    @Bean
    public ItemProcessor<OrderRecord, ReportLine> orderToReportLineProcessor() {
        return order -> {

            if (order.getAmount().compareTo(BigDecimal.ZERO) <= 0) return null; // Skip
            return ReportLine.builder()
                .customerId(order.getCustomerId())
                .customerName(order.getCustomerName())
                .totalAmount(order.getAmount())
                .orderCount(1)
                .build();
        };
    }

29. RELIABILITY

Q: What is Reliability and how do you measure it (SLI, SLO, SLA)?

A: Reliability is the probability a system performs its intended function over a period. Quantified via:

SLI (Service Level Indicator): Metric that measures service behavior.

Examples: request success rate, p99 latency, availability.

SLO (Service Level Objective): Target value for an SLI.

Examples: success_rate >= 99.9%, p99_latency <= 500ms.

SLA (Service Level Agreement): Business contract — consequence if SLO not met (refunds, credits).

Error Budget: Error Budget = 1 - SLO. If SLO = 99.9%, error budget = 0.1% = 43.8 min/month.

When error budget exhausted: freeze new deployments, focus on reliability.

Reliability vs Availability:

  • Availability: System is up
  • Reliability: System produces correct results consistently
// SLO monitoring with Micrometer
@Component
public class SloMonitor {

    private final MeterRegistry registry;
    private final AtomicLong totalRequests = new AtomicLong(0);
    private final AtomicLong successfulRequests = new AtomicLong(0);

    @EventListener
    public void onRequest(RequestCompletedEvent event) {
        totalRequests.incrementAndGet();
        if (event.isSuccess()) successfulRequests.incrementAndGet();

        // Record success rate gauge
        double successRate = (double) successfulRequests.get() / totalRequests.get();
        registry.gauge("slo.success.rate", successRate);

        // Alert when success rate drops below SLO
        if (successRate < 0.999) {
            registry.counter("slo.breach", "type", "success_rate").increment();
            alertService.send(Alert.builder()
                .severity(Severity.CRITICAL)
                .message(String.format("Success rate %.2f%% < SLO 99.9%%", successRate * 100))
                .build());
        }
    }

    // Track error budget consumption
    @Scheduled(fixedDelay = 60_000)
    public void calculateErrorBudget() {
        double currentFailureRate = calculateFailureRateForMonth();
        double errorBudget = 0.001; // 0.1% for 99.9% SLO
        double budgetConsumed = currentFailureRate / errorBudget;

        registry.gauge("slo.error.budget.consumed.pct", budgetConsumed * 100);

        if (budgetConsumed > 0.9) { // 90% budget consumed
            alertService.send(Alert.builder()
                .severity(Severity.WARNING)
                .message("Error budget 90% consumed — consider deployment freeze")
                .build());
        }
    }
}

    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        return serviceInstanceListSupplier.get(request)
            .next()
            .map(instances -> {
                ServiceInstance best = instances.stream()
                    .filter(this::isHealthy)
                    .min(Comparator.comparingInt(i ->
                        connectionCounts.computeIfAbsent(
                            i.getInstanceId(), k -> new AtomicInteger(0)).get()))

                return new DefaultResponse(best);
            });

32. CAP THEOREM

Q: What is CAP Theorem and how does it guide database selection?

A: CAP Theorem (Brewer, 2000) states a distributed system can guarantee at most 2 of 3 properties simultaneously:

  • C (Consistency): Every read returns the most recent write (or error)
  • A (Availability): Every request gets a non-error response (not necessarily latest data)
  • P (Partition Tolerance): System continues despite network partition

Critical insight: In a distributed system, network partitions will happen. Therefore P is not optional — you must choose between C and A when a partition occurs.

Real-world DB positioning:

DatabaseTypeSacrifice
PostgreSQL, MySQLCPAvailability during partition
Cassandra, CouchDBAPConsistency (eventual consistency)
MongoDBCP (default)Availability
DynamoDBAP (default)Consistency (tunable)
Zookeeper, etcdCPAvailability

PACELC (extends CAP): Even without partition, there's a tradeoff between Latency and Consistency.

// AP choice: Eventual consistency — prioritize availability
@Repository
public class EventuallyConsistentOrderRepo {

    private final CassandraTemplate cassandra;

    public Order save(Order order) {
        // Cassandra with ConsistencyLevel.ONE — writes to one replica, returns
        // Fast but replica may lag (eventual consistency)
        WriteOptions opts = WriteOptions.builder()
            .consistencyLevel(ConsistencyLevel.ONE)  // Fast
            .build();
        cassandra.insert(order, opts);
        return order;
    }

    public Optional<Order> findById(UUID id) {
        // Read with QUORUM: must read from majority of replicas → stronger consistency
        // But slower than LOCAL_ONE
        ReadOptions opts = ReadOptions.builder()
            .consistencyLevel(ConsistencyLevel.QUORUM)
            .build();
        return Optional.ofNullable(cassandra.selectOneById(id, Order.class, opts));
    }
}

34. DENORMALIZATION

Q: When should you denormalize your database schema?

A: Denormalization intentionally introduces redundancy (violating normal forms) to improve read performance by pre-joining data or pre-computing aggregates.

Normalization vs Denormalization:

  • Normalized: Low redundancy, easy writes, complex reads (many JOINs)
  • Denormalized: Some redundancy, complex writes (update multiple places), fast reads

When to Denormalize:

  • Read-heavy workloads where JOIN cost dominates
  • Reporting tables / data warehouses (designed for reads)
  • Caching computed values (aggregate counts, sums)
  • High-cardinality joins that are expensive
  • When query latency SLO cannot be met even with indexes

When NOT to Denormalize:

  • Write-heavy workloads (writes become expensive — must update all copies)
  • Data that changes frequently (consistency maintenance costly)
  • When indexes can solve the problem

Q: What is Pub/Sub and how does it differ from a queue?

A: In Pub/Sub, publishers emit messages to topics without knowing who will receive them. All subscribers to a topic receive every message. This is broadcast/fan-out semantics.

Queue vs Pub/Sub:

  • Queue: Message consumed by ONE worker (task distribution)
  • Pub/Sub: Message received by ALL subscribers (event notification)

Kafka as Pub/Sub:

  • Same message delivered to all consumer groups
  • Within a consumer group = queue semantics (only one instance processes each message)

When Pub/Sub is the right choice:

  • Order placed → notify: payment service, inventory service, notification service, analytics service — all simultaneously
  • Domain events that multiple bounded contexts care about
  • Building an event-driven architecture

36. TIMEOUT

Q: How do you implement timeouts at every layer of a distributed system?

A: Timeouts prevent indefinite blocking when downstream services are slow or unresponsive. Without timeouts, threads pile up waiting → thread pool exhaustion → cascade failure.

Timeout Layers:

  • Client connect timeout: Max time to establish TCP connection
  • Client read timeout: Max time to wait for response data
  • Server request timeout: Max time to process a request
  • DB query timeout: Max time for SQL query
  • Async operation timeout: Max time for CompletableFuture

Setting values: Start with P99.9 of normal operation + buffer. Too short = false timeouts. Too long = slow cascade failure.

@Component
public class RequestTimeoutFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletResponse httpRes = (HttpServletResponse) res;
        ScheduledFuture<?> timeout = scheduler.schedule(() -> {

                httpRes.setStatus(503);

        try {
            chain.doFilter(req, res);
        } finally {
            timeout.cancel(false);
        }
    }
}

Alerting Principles:

  • Alert on symptoms, not causes (alert on high error rate, not high CPU — CPU may be fine)
  • Every alert must be actionable (if no runbook exists, don't alert)
  • Alert on SLO burn rate, not individual threshold breaches
  • Use multiple severity levels (P1=wake up, P2=business hours, P3=ticket)
  • Avoid flapping (require sustained violation, not single point)

Alert Fatigue Solution: Multi-window burn rate alerts (SLO-based alerting) — only page when error budget is burning fast enough to matter.

39. CACHE STAMPEDE

Q: What is Cache Stampede and how do you prevent it?

A: Cache Stampede (Thundering Herd) occurs when a popular cache entry expires and many concurrent requests all miss the cache simultaneously, all hitting the database at once, potentially overwhelming it.

Scenario: 10,000 req/sec hit the cache. Cache expires. All 10,000 requests → DB simultaneously → DB overwhelmed.

Prevention Strategies:

  • Mutex/Locking: Only one request fetches from DB; others wait for cache to repopulate.
  • Probabilistic Early Recomputation (PER): Randomly recompute before expiry to prevent simultaneous expiry.
  • Background Refresh: Async refresh before expiry. Serve stale while refreshing.
  • Jitter on TTL: ttl = baseTTL + random(0, jitterRange) — prevents all keys expiring simultaneously.
// Strategy 1: Redis distributed lock prevents stampede
@Service
public class CacheStampedeProtectedService {

    private final StringRedisTemplate redis;
    private final ProductRepository repo;

    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;
        String lockKey = "lock:product:" + id;

        // Check cache first
        String cached = redis.opsForValue().get(cacheKey);
        if (cached != null) return deserialize(cached, Product.class);

        // Try to acquire lock for DB fetch
        Boolean lockAcquired = redis.opsForValue()
            .setIfAbsent(lockKey, "1", Duration.ofSeconds(10));

        if (Boolean.TRUE.equals(lockAcquired)) {
            try {
                // Double-check after acquiring lock
                cached = redis.opsForValue().get(cacheKey);
                if (cached != null) return deserialize(cached, Product.class);

                // Fetch from DB and populate cache
                Product product = repo.findById(id).orElseThrow();
                // TTL with jitter: 30 min ± 5 min
                long ttlSeconds = 1800 + ThreadLocalRandom.current().nextLong(-300, 300);
                redis.opsForValue().set(cacheKey, serialize(product),
                    Duration.ofSeconds(ttlSeconds));
                return product;
            } finally {
                redis.delete(lockKey);
            }
        } else {
            // Another thread is fetching — wait briefly and retry
            LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(50));
            return getProduct(id); // Retry (cache should be populated now)
        }
    }
}

// Strategy 2: Stale-while-revalidate (serve stale, refresh async)
@Service
public class StaleWhileRevalidateCache {

    record CacheEntry<T>(T value, Instant expiresAt, Instant softExpiresAt) {
        boolean isHardExpired() { return Instant.now().isAfter(expiresAt); }

        boolean isSoftExpired() { return Instant.now().isAfter(softExpiresAt); }
    }

    public <T> T get(String key, Supplier<T> loader, Duration ttl) {
        CacheEntry<T> entry = localCache.get(key);

        if (entry == null || entry.isHardExpired()) {
            T fresh = loader.get();  // Must fetch synchronously
            cache(key, fresh, ttl);
            return fresh;
        }

        if (entry.isSoftExpired()) {
            // Serve stale, refresh in background
            CompletableFuture.runAsync(() -> {
                T fresh = loader.get();
                cache(key, fresh, ttl);
            });
        }
        return entry.value();  // Return stale immediately
    }
}

41. LSM TREES (Log-Structured Merge Trees)

Q: What is an LSM Tree and which databases use it?

A: LSM Tree is a data structure optimized for high write throughput. Writes go to an in-memory buffer (MemTable), which is periodically flushed to immutable disk files (SSTables). Background compaction merges SSTables.

Write Path:

  • Write to WAL (Write-Ahead Log) for durability
  • Write to MemTable (in-memory sorted structure)
  • When MemTable full → flush to SSTable on disk
  • Background compaction merges SSTables

Read Path:

  • Check MemTable (latest data)
  • Check SSTables newest to oldest (Bloom filters to skip non-containing files)

Advantages: Sequential writes = very high write throughput (avoids random disk I/O).

Disadvantages: Read amplification (may check multiple SSTables), write amplification from compaction, space amplification.

Databases using LSM: RocksDB, Cassandra, HBase, LevelDB, InfluxDB, ScyllaDB.

Databases using B-Tree: PostgreSQL, MySQL InnoDB, SQLite.

When to use LSM-based DB: Write-heavy workloads (IoT, logging, metrics, event sourcing), time-series data.

    public void recordMetric(String metricKey, long timestamp, double value) throws RocksDBException {
        // Key design: metricKey:timestamp ensures sorted order = efficient range scans
        String key = metricKey + ":" + String.format("%020d", timestamp);
        byte[] valueBytes = ByteBuffer.allocate(8).putDouble(value).array();
        db.put(key.getBytes(), valueBytes);
    }

    // Range scan: get all values for metric in time range
    public List<Double> getMetricsInRange(String metricKey, long from, long to)
            throws RocksDBException {
        List<Double> results = new ArrayList<>();
        String startKey = metricKey + ":" + String.format("%020d", from);
        String endKey = metricKey + ":" + String.format("%020d", to);

        try (RocksIterator iter = db.newIterator()) {
            iter.seek(startKey.getBytes());
            while (iter.isValid() && new String(iter.key()).compareTo(endKey) <= 0) {
                results.add(ByteBuffer.wrap(iter.value()).getDouble());
                iter.next();
            }
        }

        return results;
    }

@Configuration
public class OrderStreamProcessor {

    @Bean
    public KStream<String, OrderEvent> orderStream(StreamsBuilder builder) {

        KStream<String, OrderEvent> orders = builder
            .stream("order-events", Consumed.with(Serdes.String(), orderEventSerde));

        // Windowed aggregation: count orders per customer per hour
        KTable<Windowed<String>, Long> orderCountPerHour = orders
            .filter((key, order) -> order.getStatus().equals("COMPLETED"))
            .groupBy((key, order) -> order.getCustomerId(),
                Grouped.with(Serdes.String(), orderEventSerde))
            .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofHours(1)))
            .count(Materialized.as("order-counts-per-hour"));

        orderCountPerHour.toStream()

            .map((windowedKey, count) -> KeyValue.pair(
                windowedKey.key(),
                new FraudAlert(windowedKey.key(), count, windowedKey.window().startTime())))
            .to("fraud-alerts", Produced.with(Serdes.String(), fraudAlertSerde));

        // Real-time revenue aggregation
        KTable<String, BigDecimal> revenueByCustomer = orders
            .filter((k, v) -> v.getStatus().equals("COMPLETED"))
            .groupBy((k, v) -> v.getCustomerId(), Grouped.with(Serdes.String(), orderEventSerde))
            .aggregate(
                BigDecimal::new,
                (customerId, order, total) -> total.add(order.getAmount()),
                Materialized.as("customer-revenue")
            );

44. CACHING

Q: What are the caching strategies and when to use each?

A: Caching stores frequently accessed data in fast storage (memory) to reduce latency and database load.

Caching Strategies:

  • Cache-Aside (Lazy Loading): App checks cache → miss → read DB → write to cache. Most common.
  • Pro: Only caches what's needed
  • Con: Cache miss penalty (read-your-writes inconsistency briefly)
  • Read-Through: Cache manages DB reads automatically.
  • Pro: Application simplicity
  • Con: First-read miss always goes to DB
  • Write-Through: Write to cache AND DB synchronously.
  • Pro: Always consistent
  • Con: Write penalty (must write to DB even for hot-path writes)
  • Write-Behind (Write-Back): Write to cache only; async flush to DB.
  • Pro: Fast writes
  • Con: Data loss risk if cache fails before flush
  • Refresh-Ahead: Pre-emptively refresh cache before expiry.
  • Pro: No cache miss on hot entries
  • Con: May cache stale data

45. gRPC

Q: When do you choose gRPC over REST?

A: gRPC is a high-performance RPC framework using Protocol Buffers (binary serialization) over HTTP/2.

46. CONSISTENCY MODELS

Q: What are the different consistency models and when does each apply?

A: Consistency models define the rules about when and how updates become visible to readers in a distributed system.

Consistency Spectrum (strongest to weakest):

  • Strict Consistency: Every read sees the most recent write across all nodes. Impossible in distributed systems (would require instantaneous propagation).
  • Linearizability (Strong Consistency): Operations appear atomic and in real-time order. Used by: etcd, ZooKeeper, CockroachDB (Serializability).
  • Sequential Consistency: All processes see operations in the same order (not necessarily real-time order). Used by: traditional databases.
  • Causal Consistency: Causally related operations appear in order. If A causes B, everyone sees A before B. Used by: MongoDB (causal sessions), some distributed databases.
  • Eventual Consistency: Given no new updates, all replicas will eventually converge. Used by: Cassandra, DynamoDB, DNS.
  • Read Your Own Writes: You always see your own writes, others may not. Common in web apps.
// Demonstrating consistency choices in Spring Boot

48. ACID

Q: What does ACID mean and how do you use transactions in Spring Boot?

A: ACID defines transaction properties that guarantee database reliability:

  • Atomicity: Transaction is all-or-nothing. Either all operations succeed or all are rolled back.
  • Consistency: Transaction brings DB from one valid state to another. All constraints maintained.
  • Isolation: Concurrent transactions don't see each other's intermediate states.
  • Durability: Committed transactions persist even after system crash (WAL/journal).

Isolation Levels (weakest to strongest):

LevelPreventsAllows
Read Uncommitted—Dirty read, non-repeatable, phantom
Read Committed (default)Dirty readNon-repeatable, phantom
Repeatable ReadDirty + Non-repeatablePhantom
SerializableAll anomaliesNothing — slowest
// Spring @Transactional
@Service
public class FundsTransferService {

    // SERIALIZABLE: for financial transactions
    @Transactional(isolation = Isolation.SERIALIZABLE, timeout = 30)
    public TransferResult transfer(Long fromId, Long toId, BigDecimal amount) {
        // Both reads get locked — no phantom reads, no non-repeatable reads
        Account from = accountRepo.findByIdWithLock(fromId)
            .orElseThrow(() -> new AccountNotFoundException(fromId));
        Account to = accountRepo.findByIdWithLock(toId)
            .orElseThrow(() -> new AccountNotFoundException(toId));

        if (from.getBalance().compareTo(amount) < 0)
            throw new InsufficientFundsException(fromId, amount);

        from.debit(amount);
        to.credit(amount);

        accountRepo.save(from);
        accountRepo.save(to);
        auditRepo.save(TransferAudit.of(fromId, toId, amount));  // All atomic

        return TransferResult.success(from.getBalance());
        // If any exception thrown → entire transaction rolled back
    }

    // Savepoints: partial rollback within transaction
    @Transactional
    public OrderResult createOrderWithOptionalInsurance(CreateOrderRequest req) {
        Order order = orderRepo.save(Order.from(req));  // Must succeed

        try {
            // Try to add insurance — if fails, rollback only this, not whole order
            Object savepoint = TransactionAspectSupport.currentTransactionStatus()
                .createSavepoint();
            try {
                insuranceService.addCoverage(order);
            } catch (InsuranceException e) {
                TransactionAspectSupport.currentTransactionStatus()
                    .rollbackToSavepoint(savepoint);
                log.warn("Insurance failed, continuing without it: {}", e.getMessage());
            }
        } catch (NestedTransactionNotSupportedException e) {
            // DB doesn't support savepoints — skip insurance
        }


        return OrderResult.of(order);
    }
}

49. SYNC vs ASYNC

Q: When do you choose synchronous vs asynchronous communication?

A:

  • Synchronous: Caller blocks waiting for response. Simple, immediate consistency, tight coupling.
  • Asynchronous: Caller sends request and continues. Loose coupling, resilient, eventual consistency.

Use Synchronous when:

  • Immediate response required (user queries)
  • Strong consistency needed (payment confirmation)
  • Simple request-response pattern
  • Failure in callee should immediately fail the caller

Use Asynchronous when:

  • Long-running operations (video processing, report generation)
  • Fan-out to multiple services
  • Decoupling for resilience (callee down = messages queue up)
  • Rate limiting / traffic shaping

Hybrid Pattern (Async Request-Reply): Client sends async request, gets back a job ID, polls for result or receives webhook callback.

50. SERVICE DISCOVERY

Q: What is Service Discovery and what are the patterns?

A: Service Discovery allows services to find each other dynamically without hardcoded IPs/ports. Critical in dynamic environments where service instances scale up/down and IPs change.

Two Patterns:

  • Client-Side Discovery: Client queries registry directly, selects instance, calls it.
  • Example: Netflix Eureka + Ribbon
  • Pro: Client has full control of load balancing

  • Pro: Simple clients, LB separate concern
  • Con: Extra hop

Tools: Consul, Eureka, etcd, ZooKeeper, Kubernetes (built-in via kube-dns + Services).

52. FULL-TEXT SEARCH

Q: When do you use Elasticsearch vs PostgreSQL full-text search?

A: Full-text search finds documents by relevance based on text content, not exact matches.

PostgreSQL FTS: Built-in, good for moderate volumes, no extra infrastructure, integrates with ACID transactions.

Elasticsearch: Dedicated search engine. Best for: large datasets, complex queries, faceting, aggregations, real-time search.

Use PostgreSQL FTS: < 10 million docs, simple search requirements, want transactional consistency with writes.

Use Elasticsearch: > 10 million docs, complex relevance tuning, real-time analytics, log analysis.

53. CACHE WARMING

Q: What is Cache Warming and why is it important?

A: Cache Warming (pre-loading) populates the cache before it's needed in production, preventing a cold-start where all initial requests miss the cache and overwhelm the database.

When needed:

  • After deployment (new pod starts with empty cache)
  • After cache flush/eviction
  • Before major traffic events (flash sale, marketing campaign)
  • After cache server restart

Strategies:

  • Eager warming: Load all expected data at startup
  • Lazy warming: Cache fills naturally via traffic (cold start penalty)
  • Scheduled warming: Refresh cache before entries expire
  • Event-driven warming: Pre-populate based on predicted access patterns
// Eager cache warming on application startup
@Component
@Slf4j

    @Autowired private CategoryService categoryService;

            Duration.between(start, Instant.now()).toMillis());
    }
}

54. CQRS (Command Query Responsibility Segregation)

Q: What is CQRS and when does it offer the most benefit?

A: CQRS separates read operations (Queries) from write operations (Commands) into different models, potentially different services, and even different databases.

Why separate reads from writes:

  • Read and write models have different optimization needs
  • Reads are typically 10x-100x more frequent than writes
  • Read model can be denormalized for query performance
  • Write model can be normalized for consistency
  • Scale reads and writes independently

CQRS Spectrum:

  • Basic CQRS: Separate command/query interfaces, same DB
  • Segregated CQRS: Separate read/write services + DBs (sync via events)
  • Event Sourced CQRS: Write side = event store; read side = materialized views

When to use: Complex domain with many query patterns, high read/write ratio difference, need to scale reads independently, reporting requirements.

When NOT to use: Simple CRUD apps, small teams, no scalability requirements — adds significant complexity.

55. B-TREES

Q: How does a B-Tree index work and why is it the default for most databases?

A: B-Tree (Balanced Tree) is a self-balancing tree data structure where all leaf nodes are at the same depth. Provides O(log n) for search, insert, and delete. Values are sorted, enabling efficient range queries.

Why B-Tree is the default:

  • Supports equality (=) AND range queries (>, <, BETWEEN, LIKE 'abc%')
  • Supports ORDER BY (data already sorted)
  • Stable performance: O(log n) regardless of data distribution
  • Works well for both point queries and scans

B-Tree vs B+Tree (what DBs actually use):

  • B+Tree: Data only in leaf nodes; all leaves linked in sorted order
  • Enables efficient full-scans of sorted data
  • Better cache performance (smaller internal nodes → more keys per page)

When B-Tree excels: Most database query patterns — range queries, sorted results, prefix matching.

When B-Tree loses: Hash (equality only, faster); GIN (full-text, arrays); BRIN (huge sequential tables).

// Understanding B-Tree through Spring Data index usage

// This index makes the following queries fast (all B-tree compatible):
@Index(name = "idx_order_customer_date", columnList = "customer_id, created_at")

// Query 1: Equality on customer_id (leftmost column) ✅
orderRepo.findByCustomerId("cust-123");

56. ETL (Extract, Transform, Load)

Q: What is ETL and how do you implement it in Java/Spring?

A: ETL is a data integration process: Extract data from sources, Transform it to fit the target schema/format, Load into destination (data warehouse, analytics DB).

ETL vs ELT:

  • ETL: Transform before loading. Traditional. Used when destination has limited compute.
  • ELT: Load raw data, then transform in destination. Modern (Snowflake, BigQuery). Uses destination's compute power.

When to use ETL: Data warehouse population, migration between systems, data quality enforcement, aggregation pipelines.

Challenges: Large data volumes (streaming in chunks), error handling (skip/retry/fail), idempotency (re-runnable), monitoring, schema evolution.

// Spring Batch ETL Pipeline
@Configuration

            .start(extractStep(sbf))

            .build();

57. THROUGHPUT

Q: What is Throughput and how do you maximize it?

A: Throughput is the number of operations (requests, transactions, messages) a system processes per unit of time. Measured as RPS (requests/sec), TPS (transactions/sec), or MB/s.

Throughput vs Latency tradeoff: Batching increases throughput but increases latency per item. Optimizing one often degrades the other.

Little's Law: L = λ × W

Where L = avg items in system, λ = throughput (arrival rate), W = avg time in system.

If W (latency) doubles, either L doubles (queue grows) or λ halves (throughput drops).

How to increase throughput:

  • Horizontal scaling (more instances)
  • Async processing (don't block threads)
  • Batching (process multiple items together)
  • Connection pooling (reuse expensive connections)
  • Caching (avoid redundant work)
  • Efficient algorithms and data structures
  • Database: read replicas, indexing, query optimization
// Throughput optimization with batching
@Service
public class HighThroughputOrderService {

                ps.setString(2, order.getCustomerId());

                ps.setString(4, order.getStatus().name());

    }

58. CACHE INVALIDATION

Q: What is cache invalidation and why is it considered one of the hardest problems?

A: Phil Karlton's famous quote: "There are only two hard things in Computer Science: cache invalidation and naming things."

Cache invalidation ensures cached data is removed or updated when the underlying data changes, preventing stale reads.

Invalidation Strategies:

  • TTL (Time-To-Live): Cache expires after fixed duration. Simple but stale during TTL window.
  • Event-Driven Invalidation: Invalidate on write event. Consistent but couples write path to cache.
  • Write-Through: Update cache on every write. Always fresh but slower writes.
  • Cache-Aside Eviction: Application evicts on write. Most common pattern.
  • CDC (Change Data Capture): DB triggers invalidation. Decoupled but complex.

The Inconsistency Window Problem: Between cache eviction and cache repopulation, concurrent reads may create multiple DB calls.

// Strategy 1: Event-driven cache invalidation
@Service
@Transactional
public class ProductService {

    }

        @CacheEvict(value = "products", key = "#id"),

    })

    }
}

59. AUTHENTICATION

Q: How do you implement stateless JWT authentication in Spring Boot?

A: Authentication verifies WHO you are. Common methods: session cookies (stateful), JWT (stateless), OAuth2, API keys, mutual TLS.

JWT (JSON Web Token):

  • Header.Payload.Signature
  • Stateless: server doesn't store sessions — scales horizontally trivially
  • Payload contains claims: userId, roles, expiry
  • Signed with secret (HMAC) or key pair (RS256)

JWT Disadvantages:

  • Cannot revoke before expiry (use short-lived access tokens + refresh tokens)
  • Payload visible (don't store sensitive data)
  • Token grows large with many claims

When to use JWT: Stateless microservices, mobile clients, cross-domain auth.

When to use Sessions: Traditional web apps where server storage is acceptable.

// JWT filter — validates token on every request
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenService jwtService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String authHeader = request.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = authHeader.substring(7);
        try {
            Claims claims = jwtService.validateAndParse(token);
            String userId = claims.getSubject();
            List<String> roles = claims.get("roles", List.class);

            UsernamePasswordAuthenticationToken auth = new UsernamePasswordAuthenticationToken(
                userId, null,
                roles.stream().map(SimpleGrantedAuthority::new).collect(toList()));

            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(auth);
        } catch (JwtException e) {
            response.setStatus(HttpStatus.UNAUTHORIZED.value());
            response.getWriter().write("{\"error\":\"Invalid token\"}");
            return;
        }
        filterChain.doFilter(request, response);
    }
}

    private static final Duration REFRESH_TTL = Duration.ofDays(30);

            .claim("roles", user.getRoles())
            .claim("email", user.getEmail())

            .parseClaimsJws(token).getBody();
    }

60. REPLICATION

Q: What are the database replication modes and when to use each?

A: Replication copies data from primary to one or more replicas for high availability and read scaling.

Replication Modes:

ModeDurabilityPerformanceUse Case
SynchronousHigh (no data loss)Slower writesFinancial, critical data
AsynchronousRisk of data loss on failoverFast writesAnalytics replicas
Semi-synchronousBalanceModerateMost production systems

Replication Topologies:

  • Single Primary, Multiple Replicas: Most common. Writes → primary; reads → replicas.
  • Multi-Primary: All nodes accept writes. Complex conflict resolution.
  • Cascading Replication: Replica replicates to another replica (reduces primary load).

Replication Lag: Async replicas can be seconds behind. Don't read your own writes from replica.

// Spring Boot read/write splitting with AbstractRoutingDataSource
public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {

    private static final ThreadLocal<DbType> contextHolder = new ThreadLocal<>();

    public enum DbType { PRIMARY, REPLICA }

    public static void usePrimary() { contextHolder.set(DbType.PRIMARY); }
    public static void useReplica() { contextHolder.set(DbType.REPLICA); }
    public static void clear() { contextHolder.remove(); }

    @Override
    protected Object determineCurrentLookupKey() {
        return contextHolder.get() != null ? contextHolder.get() : DbType.PRIMARY;
    }
}

// AOP: route @Transactional(readOnly=true) to replica automatically
@Aspect
@Component
public class ReadWriteDataSourceAspect {

    @Around("@annotation(transactional)")
    public Object routeDataSource(ProceedingJoinPoint pjp,
                                   Transactional transactional) throws Throwable {
        try {
            if (transactional.readOnly()) {
                ReadWriteRoutingDataSource.useReplica();
            } else {
                ReadWriteRoutingDataSource.usePrimary();
            }
            return pjp.proceed();
        } finally {
            ReadWriteRoutingDataSource.clear();
        }
    }
}

}

62. BASE

Q: What is BASE and how does it contrast with ACID?

A: BASE is the consistency model used by most NoSQL/distributed databases, in contrast to ACID.

  • Basically Available: System guarantees availability (responses, even if stale)
  • Soft State: State may change over time even without input (due to replication)
  • Eventually Consistent: System will become consistent given enough time and no new updates

ACID vs BASE:

ACIDBASE
ConsistencyStrong (immediate)Eventual
AvailabilityMay sacrifice for consistencyPrioritized
PerformanceSlowerFaster
ScaleHarder to scale outDesigned for horizontal scale
Use casePayments, inventorySocial feeds, recommendations

When BASE is acceptable: User profiles, social feeds, product recommendations, shopping cart (eventual is OK for reads), analytics counters.

When ACID required: Money transfers, inventory reservation, order creation.

// BASE example: Cassandra eventual consistency
@Service
public class ActivityFeedService {

    public void recordActivity(String userId, Activity activity) {

                .consistencyLevel(ConsistencyLevel.ONE)  // Available immediately
                .build());

                .consistencyLevel(ConsistencyLevel.ONE)  // Fast but may be stale
                .build());

    public long getExactFollowerCount(String userId) {

    }
}

63. IDEMPOTENCY

Q: What is Idempotency and how do you implement it?

A: An operation is idempotent if calling it multiple times produces the same result as calling it once. Critical for safe retries in distributed systems.

HTTP Idempotency:

  • GET, PUT, DELETE: Idempotent by definition
  • POST: Not idempotent (each call creates a new resource)
  • PATCH: Not inherently idempotent

Why matters: Networks fail. Clients retry. Without idempotency, a retry creates duplicate orders, charges.

Implementation Pattern:

  • Client generates Idempotency-Key (UUID) per unique operation
  • Server stores (idempotency_key → result) on first processing
  • Duplicate request with same key returns stored result without re-processing
// Idempotency key interceptor
@Service
public class IdempotentOrderService {

    private final OrderRepository orderRepo;
    private final IdempotencyKeyRepository idempotencyRepo;

    @Transactional
    public OrderResult createOrder(CreateOrderRequest request, String idempotencyKey) {
        // Check if we've already processed this key
        if (idempotencyKey != null) {
            Optional<IdempotencyRecord> existing =
                idempotencyRepo.findByKey(idempotencyKey);
            if (existing.isPresent()) {
                // Return the original result — don't process again
                log.info("Duplicate request detected for key: {}", idempotencyKey);
                return existing.get().getResult(OrderResult.class);
            }
        }

        // First time processing
        Order order = processOrder(request);
        OrderResult result = OrderResult.of(order);

        // Store result for future duplicate requests
        if (idempotencyKey != null) {
            idempotencyRepo.save(IdempotencyRecord.builder()
                .key(idempotencyKey)
                .result(serialize(result))
                .expiresAt(Instant.now().plus(Duration.ofDays(7)))
                .build());
        }

        return result;
    }
}

// Idempotent Redis increment (atomic — safe for concurrent calls)
@Service
public class WalletService {

    private final RedisTemplate<String, Long> redis;
    private final WalletRepository walletRepo;

    // Use idempotency key to prevent double-charges
    public boolean chargeWallet(String userId, long amount, String transactionId) {
        String idempotencyKey = "tx:" + transactionId;

        // SET NX (set if not exists) — atomic in Redis
        Boolean firstTime = redis.opsForValue()
            .setIfAbsent(idempotencyKey, 1L, Duration.ofDays(1));

        if (!Boolean.TRUE.equals(firstTime)) {
            log.info("Duplicate charge attempt for transaction: {}", transactionId);

            return true; // Already processed, idempotent success
        }

        // Actually charge
        return walletRepo.debit(userId, amount, transactionId);
    }
}

64. API GATEWAY

Q: What does an API Gateway do and what should you put in it?

A: An API Gateway is a single entry point for all client requests to a microservices backend. It handles cross-cutting concerns.

Functions of API Gateway:

  • Routing: Route requests to correct microservice
  • Authentication/Authorization: Validate JWT, API keys
  • Rate Limiting: Protect backends from overload
  • SSL Termination: Handle HTTPS centrally
  • Load Balancing: Distribute among service instances
  • Request/Response Transformation: Header manipulation, body transformation
  • Caching: Cache responses at gateway level
  • Circuit Breaking: Fail fast if backend is down
  • Logging/Tracing: Centralized access logs, correlation IDs

What NOT to put in API Gateway: Business logic (belongs in services), complex data aggregation (use BFF instead).

68. EVENT SOURCING

Q: What is Event Sourcing and when does it provide the most value?

A: Event Sourcing persists the state of a domain object as a sequence of immutable events (facts) rather than just current state. To get current state: replay all events from beginning.

Traditional DB: Store current state. UPDATE orders SET status='SHIPPED' WHERE id=1

Event Sourcing: Append event. INSERT INTO events (order_id, type, data) VALUES (1, 'OrderShipped', {...})

Benefits:

  • Complete audit trail: know every state change, who made it, when
  • Time travel: reconstruct state at any point in time
  • Event replay: rebuild read models, debug bugs with production data
  • Natural fit with Event-Driven Architecture

Drawbacks:

  • Complexity: more code, unfamiliar pattern
  • Event versioning: schema evolution of events is hard
  • Snapshot needed: replaying 10M events to get current state is slow
  • Eventually consistent read models

// Order aggregate with event sourcing
public class OrderAggregate {
    private String id;
    private OrderStatus status;
    private BigDecimal amount;
    private List<OrderItem> items;
    private long version = 0;

    private final List<DomainEvent> uncommittedEvents = new ArrayList<>();

    // Apply events to reconstruct state
    public void apply(DomainEvent event) {
        switch (event.getEventType()) {
            case "OrderPlaced" -> {
                OrderPlacedPayload p = deserialize(event.getPayload(), OrderPlacedPayload.class);
                this.status = OrderStatus.PLACED;
                this.amount = p.getAmount();
                this.items = p.getItems();
            }
            case "OrderPaid" -> this.status = OrderStatus.PAID;
            case "OrderShipped" -> this.status = OrderStatus.SHIPPED;
            case "OrderCancelled" -> this.status = OrderStatus.CANCELLED;
        }
        this.version++;
    }

    // Commands produce events
    public void cancel(String reason) {
        if (!status.isCancellable())
            throw new OrderNotCancellableException(id, status);

        DomainEvent event = DomainEvent.builder()
            .eventId(UUID.randomUUID())
            .aggregateId(id)
            .eventType("OrderCancelled")
            .payload(serialize(new OrderCancelledPayload(reason)))
            .sequenceNumber(version + 1)
            .occurredAt(Instant.now())
            .build();
        uncommittedEvents.add(event);
    }
}

    }

        Optional<Snapshot> snapshot = loadSnapshot(orderId);
        long fromSequence = snapshot.map(Snapshot::getVersion).orElse(0L);

            .map(s -> deserialize(s.getState(), OrderAggregate.class))
            .orElse(new OrderAggregate(orderId));

        recentEvents.forEach(order::apply);
        return order;
    }

69. MERKLE TREES

Q: What is a Merkle Tree and where is it used in distributed systems?

A: A Merkle Tree is a binary tree where every leaf node contains the hash of a data block, and every non-leaf node contains the hash of its children. The root hash represents the integrity of all data.

Properties:

  • Verify data integrity: if root hash matches, all data is intact
  • Efficient diff: compare two trees to find exactly which leaves differ — O(log n) instead of O(n)
  • Tamper-evident: changing any data changes the root hash

Where used:

  • Bitcoin/Blockchain: Each block contains Merkle root of all transactions. Verify a transaction is in a block without downloading all transactions (SPV proof).
  • Git: Every commit is a Merkle tree of file hashes.
  • Cassandra/DynamoDB: Anti-entropy repair — compare Merkle trees across replicas to find inconsistencies efficiently.
  • IPFS: Content-addressed storage.
  • Certificate Transparency Logs.
// Merkle Tree implementation
public class MerkleTree {

    private final List<String> dataBlocks;
    private List<String> tree;

    public MerkleTree(List<String> dataBlocks) {
        this.dataBlocks = dataBlocks;
        this.tree = buildTree(dataBlocks);
    }

    private List<String> buildTree(List<String> data) {
        List<String> current = data.stream()
            .map(this::hash).collect(Collectors.toList());

        List<String> allNodes = new ArrayList<>(current);

        while (current.size() > 1) {
            List<String> nextLevel = new ArrayList<>();
            for (int i = 0; i < current.size(); i += 2) {
                String left = current.get(i);
                String right = i + 1 < current.size() ? current.get(i + 1) : left; // Duplicate odd
                nextLevel.add(hash(left + right));
            }
            allNodes.addAll(nextLevel);
            current = nextLevel;
        }
        return allNodes;
    }

    public String getRootHash() {
        return tree.get(tree.size() - 1);
    }

    // Generate proof that dataBlocks[index] is in the tree
    public List<String> getProof(int index) {
        List<String> proof = new ArrayList<>();
        int levelSize = dataBlocks.size();
        int levelStart = 0;

        while (levelSize > 1) {
            int siblingIndex = (index % 2 == 0) ? index + 1 : index - 1;
            if (siblingIndex < levelSize) proof.add(tree.get(levelStart + siblingIndex));
            index /= 2;
            levelStart += levelSize;
            levelSize = (levelSize + 1) / 2;
        }
        return proof;
    }

    // Compare two trees to find differing blocks (anti-entropy)
    public List<Integer> findDifferences(MerkleTree other) {
        List<Integer> diffs = new ArrayList<>();
        compareNodes(tree.size() - 1, other.tree, diffs, 0, dataBlocks.size());
        return diffs;
    }

    private String hash(String data) {
        try {

            MessageDigest md = MessageDigest.getInstance("SHA-256");
            return HexFormat.of().formatHex(md.digest(data.getBytes()));
        } catch (NoSuchAlgorithmException e) { throw new RuntimeException(e); }
    }
}

70. DATA PIPELINE

Q: What is a Data Pipeline and how do you design one?

A: A Data Pipeline is an automated series of steps that moves and transforms data from sources to destinations for analytics, reporting, or ML.

Components:

  • Ingestion: Collect data from databases, APIs, event streams (Kafka, Kinesis)
  • Processing: Clean, transform, enrich (Spark, Flink, Beam)
  • Storage: Data warehouse (Snowflake, BigQuery, Redshift) or data lake
  • Serving: BI tools, APIs, dashboards

  • Batch: Scheduled, process large chunks (nightly ETL)
  • Streaming: Real-time, low latency (fraud detection, recommendations)
  • Lambda: Both batch (accuracy) + streaming (freshness) → merge results
  • Kappa: Streaming only, reprocess from Kafka for historical (simpler than Lambda)

Q: How do you reduce bandwidth consumption in a distributed system?

  • Compression: gzip/Brotli for HTTP (typically 70-90% size reduction for text)

73. AUTHORIZATION

Q: How does Authorization differ from Authentication and how do you implement fine-grained authorization?

A:

  • Authentication (AuthN): Proves WHO you are. (Login, JWT validation)
  • Authorization (AuthZ): Determines WHAT you can do. (Permission checks)

Authorization Models:

  • RBAC: Role-based. "Admin can do X."
  • ABAC: Attribute-based. "Managers can edit their team's orders."
  • ReBAC: Relationship-based (Google Zanzibar). "User can view document if they own it or it's shared with them."
  • Policy-based (OPA): Externalized policy rules evaluated at runtime.
// OPA (Open Policy Agent) integration for externalized authz
@Service
public class OpaAuthorizationService {

    private final WebClient opaClient = WebClient.builder()
        .baseUrl("http://opa:8181/v1/data/authz")
        .build();

    public boolean isAllowed(String userId, String action, String resource) {
        AuthzRequest req = AuthzRequest.builder()
            .input(Map.of(
                "user", getUserAttributes(userId),
                "action", action,
                "resource", resource,
                "context", Map.of("time", Instant.now().toString())))

            .bodyValue(req)
            .retrieve()
            .bodyToMono(OpaResponse.class)
            .map(OpaResponse::getResult)
            .blockOptional()
            .orElse(false);

        auditLog(userId, action, resource, allowed);
        return Boolean.TRUE.equals(allowed);
    }
}

77. BACKPRESSURE

Q: What is Backpressure and how do you implement it?

A: Backpressure is a mechanism where a slow consumer signals to a fast producer to slow down, preventing the consumer from being overwhelmed.

Without backpressure: Producer → [buffer fills up] → OOM, dropped messages, or cascading failure.

With backpressure: Consumer signals "I'm full" → Producer slows down or routes to overflow handling.

Implementation approaches:

  • Reactive streams (Project Reactor): Built-in backpressure via request(n) protocol
  • Queue depth limits: Bounded queues with rejection policies
  • Rate limiting: Cap producer rate based on consumer capacity
  • Load shedding: Drop low-priority requests when overwhelmed
// Reactive backpressure with Project Reactor
@Service
public class OrderProcessingPipeline {

    public void startProcessing() {
        Flux.fromIterable(orderSource.getAllOrders())
            .onBackpressureBuffer(1000,     // Buffer up to 1000 items
                dropped -> log.warn("Order dropped due to backpressure: {}", dropped),
                BufferOverflowStrategy.DROP_OLDEST)
            // Or: .onBackpressureDrop(dropped -> sendToDeadLetter(dropped))
            // Or: .onBackpressureLatest()  // Keep only most recent
            .flatMap(order -> processOrder(order), 10)  // Max 10 concurrent
            .doOnError(e -> log.error("Pipeline error", e))
            .retryWhen(Retry.backoff(3, Duration.ofSeconds(1)))
            .subscribe();
    }

    // Reactive HTTP endpoint with backpressure
    @GetMapping(value = "/orders/stream", produces = MediaType.APPLICATION_NDJSON_VALUE)
    public Flux<Order> streamOrders(
            @RequestParam(defaultValue = "10") int prefetch) {
        return orderRepository.findAllAsFlux()
            .limitRate(prefetch)  // Subscriber controls rate
            .delayElements(Duration.ofMillis(10)); // Throttle
    }
}

// Bounded queue with backpressure in thread pool
@Service
public class BoundedOrderProcessor {

    private final BlockingQueue<Order> queue = new ArrayBlockingQueue<>(500);

    // Producer: submits orders with backpressure
    public boolean submit(Order order) {
        boolean accepted = queue.offer(order);  // Returns false if full
        if (!accepted) {
            metrics.counter("orders.rejected.backpressure").increment();
            // Options: reject, send to overflow queue, wait, or drop
        }
        return accepted;
    }

    @PostConstruct
    public void startConsumers() {
        // Fixed number of consumers — natural backpressure via bounded queue
        IntStream.range(0, 5).forEach(i ->
            Thread.ofVirtual().start(() -> {

                while (!Thread.currentThread().isInterrupted()) {
                    try {
                        Order order = queue.poll(1, TimeUnit.SECONDS);
                        if (order != null) processOrder(order);
                    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                }
            }));
    }
}

78. LOAD SHEDDING

Q: What is Load Shedding and how does it differ from Rate Limiting?

A:

  • Rate Limiting: Cap requests from a specific client/API key. "You get max 100 req/s."
  • Load Shedding: Drop lowest-priority requests when system is overloaded. "System at 95% — drop non-critical requests globally."

Load shedding protects the service itself when total load exceeds capacity, regardless of source.

Priority tiers (example):

  • Health checks (always pass)
  • Payment/checkout (critical business)
  • Product browsing (important)
  • Analytics/reporting (can wait)
  • Background jobs (shed first)
// Adaptive load shedding based on system metrics
@Component
public class LoadSheddingFilter implements Filter {

    private final MeterRegistry registry;

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpReq = (HttpServletRequest) req;
        HttpServletResponse httpRes = (HttpServletResponse) res;

        if (shouldShed(httpReq)) {
            metrics.counter("requests.shed", "path", httpReq.getRequestURI()).increment();
            httpRes.setStatus(503);
            httpRes.setHeader("Retry-After", "30");
            httpRes.getWriter().write("{\"error\":\"Service overloaded, please retry\"}");
            return;
        }
        chain.doFilter(req, res);
    }

    private boolean shouldShed(HttpServletRequest req) {
        double cpuLoad = getSystemCpuLoad();
        double memUsage = getMemoryUsagePercent();
        int queueDepth = getRequestQueueDepth();

        // Never shed health checks
        if (req.getRequestURI().startsWith("/actuator/health")) return false;

        // Always shed if critically overloaded
        if (cpuLoad > 0.95 || memUsage > 0.90) return true;

        // Probabilistic shedding: higher load → more shedding
        if (cpuLoad > 0.80) {
            double shedProbability = (cpuLoad - 0.80) / 0.15; // 0% → 100% as CPU 80% → 95%
            if (!isHighPriority(req) && Math.random() < shedProbability) return true;
        }

        return false;
    }

    private boolean isHighPriority(HttpServletRequest req) {
        String path = req.getRequestURI();
        return path.startsWith("/api/checkout") || path.startsWith("/api/payment");
    }
}

Q: What is a Vector Database and when do you need one?

A: A Vector Database stores and queries high-dimensional vectors (embeddings) by semantic similarity, not exact match.

Why needed: Machine learning models represent text, images, audio as dense vectors (embeddings). Traditional DBs can't efficiently find "similar" vectors.

Use cases:

  • Semantic search (find documents similar in meaning, not keywords)
  • Recommendation systems (find products similar to what user liked)
  • RAG (Retrieval-Augmented Generation) for LLMs
  • Image similarity, anomaly detection, duplicate detection

Similarity metrics: Cosine similarity (angle), Euclidean distance, dot product.

Vector DBs: Pinecone, Weaviate, Milvus, pgvector (PostgreSQL extension), Chroma, Qdrant.

public class PayloadCompressor {

    private final ZstdDecompressor decompressor = new ZstdDecompressor();

    public byte[] compress(byte[] data) {
        int maxCompressedLength = Zstd.compressBound(data.length);
        byte[] compressed = new byte[(int) maxCompressedLength];
        int compressedSize = (int) Zstd.compress(compressed, data, 3); // Level 3: balanced
        return Arrays.copyOf(compressed, compressedSize);
    }

    public byte[] decompress(byte[] compressed, int originalSize) {
        byte[] decompressed = new byte[originalSize];
        Zstd.decompress(decompressed, compressed);
        return decompressed;
    }

    // Store original size in header for decompression
    public byte[] compressWithHeader(byte[] data) {
        byte[] compressed = compress(data);
        ByteBuffer result = ByteBuffer.allocate(4 + compressed.length);
        result.putInt(data.length);  // Original size header
        result.put(compressed);
        return result.array();
    }

83. BLOOM FILTER

Q: What is a Bloom Filter and when is it useful?

A: A Bloom Filter is a space-efficient probabilistic data structure that tests whether an element is in a set. It can have false positives but never false negatives.

  • "Definitely NOT in set" → 100% certain
  • "Might be in set" → need to verify (possible false positive)

Space efficiency: Storing 1 million items with 1% FP rate requires only ~1.1MB vs millions of bytes for HashSet.

Use cases:

  • Database: Check if record likely exists before disk read (avoid I/O for non-existent keys)
  • Cache: Avoid caching items that will never be requested again (prevent cache pollution)
  • URL shortener: Quickly check if custom alias exists
  • Network: Routers checking if destination was recently seen
  • Google BigTable, Cassandra, HBase use Bloom filters per SSTable
// Google Guava Bloom Filter
@Service
public class ProductExistenceFilter {

    // 10M items, 1% false positive rate
    private final BloomFilter<Long> productFilter =
        BloomFilter.create(Funnels.longFunnel(), 10_000_000, 0.01);

    @PostConstruct
    public void loadExistingProducts() {
        // Load all product IDs at startup
        productRepo.findAllIds().forEach(productFilter::put);
        log.info("Bloom filter loaded with {} products", productRepo.count());
    }

    public Optional<Product> findProduct(Long id) {
        // Bloom filter check: O(1), no DB call
        if (!productFilter.mightContain(id)) {
            // Definitely not in DB — skip the DB call entirely
            return Optional.empty();
        }
        // Might exist — check DB (handles false positives)
        return productRepo.findById(id);
    }

    @EventListener
    public void onProductCreated(ProductCreatedEvent event) {
        productFilter.put(event.getProductId());
    }
}

// Distributed Bloom filter with Redis (for multi-instance)
@Service
public class DistributedBloomFilter {

    private final RedisTemplate<String, byte[]> redis;
    private static final String KEY = "bloom:products";
    private static final int HASH_FUNCTIONS = 7;  // k hash functions
    private static final long FILTER_SIZE = 100_000_000L;  // 100M bits

    public void add(Long id) {
        List<Long> positions = getHashPositions(id);
        positions.forEach(pos ->
            redis.opsForValue().setBit(KEY, pos, true));
    }

    public boolean mightContain(Long id) {
        List<Long> positions = getHashPositions(id);
        return positions.stream().allMatch(pos ->
            Boolean.TRUE.equals(redis.opsForValue().getBit(KEY, pos)));
    }

    private List<Long> getHashPositions(Long id) {
        return IntStream.range(0, HASH_FUNCTIONS)
            .mapToLong(i -> Math.abs(hash(id, i)) % FILTER_SIZE)
            .boxed().collect(Collectors.toList());
    }
}

// Redis sliding window rate limiter
@Service
public class RateLimiterService {

    private final StringRedisTemplate redis;

    // Sliding window: count requests in last N seconds
    public boolean allowRequest(String clientId, int limit, Duration window) {
        String key = "ratelimit:" + clientId;
        long now = System.currentTimeMillis();
        long windowStart = now - window.toMillis();

        // Lua script for atomicity (atomic check-and-increment)
        String luaScript = """
            local key = KEYS[1]
            local now = tonumber(ARGV[1])
            local window = tonumber(ARGV[2])
            local limit = tonumber(ARGV[3])
            local windowStart = now - window
            
            redis.call('ZREMRANGEBYSCORE', key, '-inf', windowStart)
            local count = redis.call('ZCARD', key)
            
            if count < limit then
                redis.call('ZADD', key, now, now .. '-' .. math.random())
                redis.call('EXPIRE', key, math.ceil(window / 1000))
                return 1
            end
            return 0
            """;

        Long allowed = redis.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            List.of(key),
            String.valueOf(now),
            String.valueOf(window.toMillis()),
            String.valueOf(limit));

        return Long.valueOf(1L).equals(allowed);
    }
}

// Token bucket (allows bursts)
@Service
public class TokenBucketRateLimiter {

    private final StringRedisTemplate redis;

    public boolean tryAcquire(String clientId, int tokensPerSecond, int maxBurst) {
        String key = "bucket:" + clientId;
        long now = System.currentTimeMillis();

        String script = """
            local key = KEYS[1]
            local now = tonumber(ARGV[1])
            local rate = tonumber(ARGV[2])      -- tokens per ms
            local capacity = tonumber(ARGV[3])
            

            local data = redis.call('HMGET', key, 'tokens', 'last_refill')
            local tokens = tonumber(data[1]) or capacity
            local lastRefill = tonumber(data[2]) or now
            
            -- Refill tokens based on elapsed time
            local elapsed = now - lastRefill
            local newTokens = math.min(capacity, tokens + elapsed * rate / 1000)
            
            if newTokens >= 1 then
                redis.call('HMSET', key, 'tokens', newTokens - 1, 'last_refill', now)
                redis.call('EXPIRE', key, 60)
                return 1
            end
            return 0
            """;

        Long allowed = redis.execute(
            new DefaultRedisScript<>(script, Long.class),
            List.of(key), String.valueOf(now),
            String.valueOf(tokensPerSecond),
            String.valueOf(maxBurst));

        return Long.valueOf(1L).equals(allowed);
    }
}

// Data integrity verification service
@Service
public class ChecksumService {

    // Fast checksums for data integrity (not cryptographic)
    public String computeCRC32(byte[] data) {
        CRC32 crc = new CRC32();
        crc.update(data);
        return Long.toHexString(crc.getValue());
    }

    // Strong checksum for security/deduplication
    public String computeSHA256(byte[] data) throws NoSuchAlgorithmException {
        MessageDigest md = MessageDigest.getInstance("SHA-256");
        return HexFormat.of().formatHex(md.digest(data));
    }

    // File upload integrity verification
    @PostMapping("/upload")
    public ResponseEntity<String> uploadFile(
            @RequestParam MultipartFile file,
            @RequestHeader("Content-MD5") String expectedChecksum) throws Exception {

        byte[] data = file.getBytes();
        String actualChecksum = Base64.getEncoder().encodeToString(
            MessageDigest.getInstance("MD5").digest(data));

        if (!actualChecksum.equals(expectedChecksum)) {
            return ResponseEntity.badRequest()
                .body("Checksum mismatch: file corrupted in transit");
        }
        storageService.store(file.getOriginalFilename(), data);
        return ResponseEntity.ok("Uploaded successfully");
    }

    // ETag generation for HTTP conditional requests
    public String generateETag(Object resource) {
        try {
            String json = objectMapper.writeValueAsString(resource);
            return '"' + computeSHA256(json.getBytes()) + '"';
        } catch (Exception e) { throw new RuntimeException(e); }
    }
}

89. ENCRYPTION

Q: What are the encryption types and when to use each?

A:

  • Symmetric: Same key for encrypt/decrypt (AES-256). Fast. Problem: key distribution.
  • Asymmetric: Public key encrypts, private key decrypts (RSA, EC). Slower. Solves key distribution.
  • Hybrid: Asymmetric to exchange symmetric key, symmetric for data. Used by TLS.
  • Hashing: One-way, not reversible. For passwords (bcrypt, argon2), integrity checks.

Encryption at Rest vs In Transit:

  • In Transit: TLS 1.3 (HTTPS, gRPC)
  • At Rest: AES-256 for stored data, database encryption, disk encryption
// Encrypting sensitive data at rest
@Service
public class EncryptionService {

    @Value("${encryption.key}")  // 256-bit key from Vault
    private String base64Key;

    public String encrypt(String plaintext) throws Exception {
        byte[] key = Base64.getDecoder().decode(base64Key);
        SecretKeySpec secretKey = new SecretKeySpec(key, "AES");

        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        byte[] iv = new byte[12]; // 96-bit IV for GCM
        SecureRandom.getInstanceStrong().nextBytes(iv);
        cipher.init(Cipher.ENCRYPT_MODE, secretKey, new GCMParameterSpec(128, iv));

        byte[] encrypted = cipher.doFinal(plaintext.getBytes(StandardCharsets.UTF_8));

        // Prepend IV to ciphertext for storage (IV is not secret)
        byte[] combined = new byte[iv.length + encrypted.length];
        System.arraycopy(iv, 0, combined, 0, iv.length);
        System.arraycopy(encrypted, 0, combined, iv.length, encrypted.length);
        return Base64.getEncoder().encodeToString(combined);
    }

    public String decrypt(String ciphertext) throws Exception {
        byte[] combined = Base64.getDecoder().decode(ciphertext);
        byte[] key = Base64.getDecoder().decode(base64Key);

        byte[] iv = Arrays.copyOfRange(combined, 0, 12);
        byte[] encrypted = Arrays.copyOfRange(combined, 12, combined.length);

        SecretKeySpec secretKey = new SecretKeySpec(key, "AES");
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.DECRYPT_MODE, secretKey, new GCMParameterSpec(128, iv));

        return new String(cipher.doFinal(encrypted), StandardCharsets.UTF_8);
    }
}

91. CIRCUIT BREAKER

Q: How does the Circuit Breaker pattern work in detail?

A: Circuit Breaker monitors calls to external services. When failure rate exceeds threshold, it "opens" and fails fast (no actual call made), giving the failing service time to recover.

States:

  • CLOSED: Normal operation. Failures tracked.
  • OPEN: Failures exceeded threshold. All calls fail immediately (fast fail). After waitDuration, transitions to HALF_OPEN.
  • HALF_OPEN: Allow limited test calls. If successful → CLOSED. If fail → OPEN.

Why it prevents cascade failure: Without CB, thread pool fills waiting for slow external service → entire application becomes unresponsive for all operations.

// Resilience4j Circuit Breaker detailed configuration
@Configuration
public class CircuitBreakerConfig {

    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry() {
        io.github.resilience4j.circuitbreaker.CircuitBreakerConfig config =
            io.github.resilience4j.circuitbreaker.CircuitBreakerConfig.custom()
                .slidingWindowType(COUNT_BASED)
                .slidingWindowSize(20)              // Track last 20 calls
                .minimumNumberOfCalls(10)           // Need 10 calls before evaluating
                .failureRateThreshold(50)           // Open if >50% failure rate
                .slowCallRateThreshold(80)          // Also open if >80% calls are slow
                .slowCallDurationThreshold(Duration.ofSeconds(3))
                .waitDurationInOpenState(Duration.ofSeconds(30))
                .permittedNumberOfCallsInHalfOpenState(5)
                .automaticTransitionFromOpenToHalfOpenEnabled(true)
                .recordExceptions(IOException.class, TimeoutException.class)
                .ignoreExceptions(BusinessException.class)  // Don't count business errors
                .build();

        return CircuitBreakerRegistry.of(config);
    }
}

@Service
public class ResilientPaymentService {

    @Autowired private CircuitBreakerRegistry registry;

    public PaymentResult processPayment(PaymentRequest request) {
        CircuitBreaker cb = registry.circuitBreaker("payment-gateway");

        // Add event listeners for monitoring
        cb.getEventPublisher()
            .onStateTransition(e -> {
                log.warn("CB state transition: {} → {}",
                    e.getStateTransition().getFromState(),
                    e.getStateTransition().getToState());
                alertService.notify("Circuit breaker state change: " + e.getStateTransition());
            })
            .onCallNotPermitted(e -> metrics.counter("cb.rejected").increment());


        return CircuitBreaker.decorateSupplier(cb,
                () -> paymentGateway.charge(request))
            .andThen(result -> { /* success */ return result; })
            .recover(CallNotPermittedException.class,
                ex -> PaymentResult.rejected("Circuit open")) // Fast fail fallback
            .recover(Exception.class,
                ex -> PaymentResult.failed(ex.getMessage()))
            .get();
    }
}

93. TRACING

Q: What is distributed tracing and how do you implement it?

A: Distributed tracing tracks a request as it flows through multiple services, showing the complete timeline and where time was spent.

Concepts:

  • Trace: Complete end-to-end journey of a request (has a Trace ID)
  • Span: Unit of work within a service (has Span ID, parent Span ID, start time, duration, tags)
  • Context propagation: Trace ID passed via HTTP headers (traceparent, b3-trace-id)

Tools: Jaeger, Zipkin, AWS X-Ray, Datadog APM, Grafana Tempo.

// Spring Boot 3 with OpenTelemetry (auto-instrumented)
// application.yml:
// management.tracing.sampling.probability=0.1  # 10% sampling in prod
// management.otlp.tracing.endpoint=http://jaeger:4318/v1/traces

// Custom spans for business operations
@Service
public class OrderFulfillmentService {

    @Autowired private Tracer tracer;
    @NewSpan("order.fulfillment")  // Creates new span automatically
    public FulfillmentResult fulfill(
            @SpanTag("order.id") String orderId) {
        // This method creates a span with the orderId tag automatically
        return doFulfill(orderId);
    }

    // Manual span creation for fine-grained tracing
    public FulfillmentResult fulfillManual(String orderId) {
        Span span = tracer.nextSpan()
            .name("order.fulfillment")
            .tag("order.id", orderId)
            .start();

        try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
            // Child spans for each step
            Span inventorySpan = tracer.nextSpan().name("inventory.reserve").start();
            try (Tracer.SpanInScope s = tracer.withSpan(inventorySpan)) {
                inventoryService.reserve(orderId);
            } finally { inventorySpan.end(); }

            Span paymentSpan = tracer.nextSpan().name("payment.charge").start();
            try (Tracer.SpanInScope s = tracer.withSpan(paymentSpan)) {
                paymentService.charge(orderId);
            } finally { paymentSpan.end(); }

            span.tag("fulfillment.status", "completed");
            return FulfillmentResult.success();
        } catch (Exception e) {
            span.error(e);
            throw e;
        } finally {
            span.end();
        }
    }
}

Q: What is a Materialized View and when should you use it?

A: A Materialized View stores the result of a query physically on disk (unlike regular views which re-execute on every access). Dramatically speeds up expensive aggregate queries at the cost of staleness.

When to use: Expensive GROUP BY / JOIN queries run frequently; dashboard queries over large tables; reporting that can tolerate slight staleness.

When NOT to use: Data that must be real-time fresh; write-heavy tables (refresh overhead); small datasets.

97. HYPERLOGLOG

Q: What is HyperLogLog and what problem does it solve?

A: HyperLogLog (HLL) is a probabilistic algorithm for estimating the cardinality (count of distinct elements) of a very large dataset using very little memory.

The Problem: COUNT(DISTINCT user_id) for 1 billion records requires storing all 1 billion IDs to count exactly.

HLL Solution: ~1.5KB of memory to estimate 1 billion distinct values with ~0.81% error. Incredibly space-efficient.

Use cases:

  • Unique visitor counting (DAU, MAU)
  • Distinct event counting
  • A/B test reach estimation
  • Network: unique IP counting
// Redis HyperLogLog for unique visitor counting
@Service
public class UniqueVisitorService {

    private final StringRedisTemplate redis;

    public void trackVisit(String userId, String date) {
        String key = "uv:" + date;
        redis.opsForHyperLogLog().add(key, userId);
        // Memory: constant ~12KB regardless of billions of users
    }

    public long getUniqueVisitors(String date) {
        // Approximate count with ~0.81% error
        return redis.opsForHyperLogLog().size("uv:" + date);
    }

    // Merge multiple days (union of unique visitors)
    public long getUniqueVisitorRange(String startDate, String endDate) {
        String mergeKey = "uv:merged:" + startDate + ":" + endDate;
        List<String> keys = getDatesInRange(startDate, endDate).stream()
            .map(d -> "uv:" + d).collect(Collectors.toList());

        redis.opsForHyperLogLog().union(mergeKey, keys.toArray(String[]::new));
        long result = redis.opsForHyperLogLog().size(mergeKey);
        redis.delete(mergeKey);
        return result;
    }

    // Custom HyperLogLog for embedded use (no Redis needed)
    public long estimateCardinality(Stream<String> elements) {
        // Using stream-lib HyperLogLog
        HyperLogLog hll = new HyperLogLog(0.01); // 1% error
        elements.forEach(hll::offer);
        return hll.cardinality();
    }
}

Q: What is a Data Warehouse and how do you design one?

A: A Data Warehouse is a centralized repository for structured, integrated data from multiple sources, optimized for complex analytical queries (OLAP — Online Analytical Processing).

OLTP vs OLAP:

OLTP (Operational DB)OLAP (Data Warehouse)
PurposeTransactionsAnalytics

DataCurrentHistorical
SchemaNormalized (3NF)Denormalized (Star/Snowflake)
ExamplesPostgreSQL, MySQLSnowflake, BigQuery, Redshift
Record countThousands per queryBillions per query

Star Schema: Fact table (events/transactions) surrounded by Dimension tables (who, what, where, when).
