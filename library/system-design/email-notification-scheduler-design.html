Email Notification Scheduler — Design Document

Recurring schedules ke liye scheduler-service: 3 DB strategies, ShedLock, Kafka dispatch, idempotency, failure handling aur observability. / A compact real-world scheduler design doc.

1. Overview

The Email Notification Scheduler is a background job inside scheduler-service that periodically scans for recurring transaction schedules due for notification, sends email and push alerts via Kafka, then updates the next notification date in the database so the cycle continues at the correct frequency (Weekly / Bi-Weekly / Monthly).

Design Goals

GoalDecision
Single source of truthAll 3 DB strategies kept in sync — each serves a different query pattern
No duplicate sendsShedLock prevents concurrent job runs across pods; Redis idempotency key per run
Failure resiliencePer-channel failure counters; auto-deactivate after threshold; full audit log
ExtensibilityTemplate code column → easy to add new notification types (TXN_FAILED, RECEIVER_UPDATED)
ObservabilityMicrometer counters on dispatched/failed; Prometheus scrape; structured log per strategy

2. Database Strategies

Three complementary table approaches are used together. Each serves a distinct purpose. The job runs all three strategies in a single cron invocation.

#TableKey ColumnPurposeUpdated After Send?
S1recurring_schedulenext_notification_atFast index scan — primary cron driverYES → next_notification_at = now + freq
S2notification_schedulenext_send_atPer-channel (EMAIL/PUSH) independent control + failure trackingYES → next_send_at = lastSentAt + freq
S3notification_lognext_send_atImmutable audit trail — every send appends a row carrying next_send_atN/A (append-only log)

Strategy 1 — recurring_schedule.next_notification_at

New columns added via Flyway V2 migration:

  • next_notification_at TIMESTAMP — when to next fire a notification
  • last_notification_at TIMESTAMP — last successful send time (audit)
  • notification_attempts INT — consecutive failure counter (reset on success)

Index: idx_schedule_next_notif ON (next_notification_at, status) WHERE status='ACTIVE'

Query: SELECT ... WHERE status='ACTIVE' AND next_notification_at <= NOW()

Update after send: UPDATE recurring_schedule SET next_notification_at = NOW() + freq, last_notification_at = NOW(), notification_attempts = 0 WHERE id = ?

Strategy 2 — notification_schedule (dedicated control table)

New table with one row per (schedule_id, channel). EMAIL and PUSH are tracked independently — user can disable email but keep push.

Key columns: next_send_at, last_sent_at, last_status, failure_count, max_retry, is_active Index: idx_notif_sched_next_send ON (next_send_at, is_active) WHERE is_active=TRUE

Update after send: UPDATE notification_schedule SET next_send_at=?, last_sent_at=?, last_status='SENT', failure_count=0 WHERE id=?

Deactivate on failure: UPDATE notification_schedule SET is_active=false, last_status='SUPPRESSED' WHERE id=?

Strategy 3 — notification_log.next_send_at (audit trail)

Every notification dispatch appends a new row to notification_log. The row carries next_send_at = computed next date at time of dispatch. This gives a full, immutable progression: you can see every date shift over time.

This table is never updated — only inserted. Failed sends get their own row with status=FAILED. Retries append another row. This means the log shows: SENT → FAILED → SENT → SENT...

New columns added: next_send_at, channel, template_code, retry_count, error_message

Index: idx_notif_log_next_send ON (next_send_at, status) WHERE status IN ('PENDING','FAILED')

4. Concurrency & Safety

4.1 ShedLock — Distributed Lock

Problem: Multiple scheduler-service pods run in Kubernetes. Without coordination, all pods would fire the job simultaneously → duplicate emails sent.

Solution: ShedLock acquires a row-level lock in the shedlock PostgreSQL table. Only the pod that wins the lock executes the job. Others skip silently.

Config: lockAtLeastFor=PT50S, lockAtMostFor=PT55S (prevents ghost locks if pod crashes). The DB clock is used (usingDbTime()) so JVM clock skew across pods is irrelevant.

4.2 Optimistic Locking

recurring_schedule has a version column (JPA @Version). If two pods somehow read the same row concurrently (before ShedLock fires), the UPDATE will return rowCount=0 for the loser — logged as a warning, the row will be picked up on the next cron tick.

notification_schedule also has a version column for the same protection.

4.3 Idempotency

Before publishing to Kafka, the job checks a Redis key: Key: notif:sent:{scheduleId}:{channel}:{YYYYMMDD} — TTL 25 hours. If the key exists, the dispatch is skipped (SKIPPED status logged in notification_log). This prevents double-send if the same job somehow runs twice (e.g. during deployment).

Summary

The notification scheduler is self-contained inside scheduler-service and:

  • Uses 3 complementary DB strategies — each addresses a different concern (fast scan, per-channel control, full

audit trail)

  • Runs on two triggers simultaneously: a fixed cron AND database-driven next_send_at / next_notification_at

timestamps

  • Updates the next date atomically after every successful dispatch using @Modifying JPQL queries with optimistic

locking

  • Is cluster-safe via ShedLock on PostgreSQL; no duplicate sends possible
  • Full failure handling: per-channel failure counters, auto-deactivation, Strategy-3 retry loop, idempotency keys in

Redis

  • All sends go through Kafka topic notification.send — decoupled from SMTP/FCM
