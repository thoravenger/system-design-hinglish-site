1. Context and requirements

The platform is a three-sided marketplace: customers order food, restaurants accept and prepare it, and drivers pick it up and deliver it. An order is never owned by one service — it crosses order, restaurant, driver, pricing, payment and notification services, each with its own database. The hard part is keeping a single order consistent across all of them without a distributed transaction.

Stack: Java 25 with Spring Boot 4.1, PostgreSQL per service, Kafka 4.x for the event backbone, Redis for geospatial driver state, PostGIS or an H3 index for proximity queries, and Kubernetes across three zones. Payments run through an external PSP in sandbox mode.

2. High-level design

Each capability owns its own database and publishes domain events to Kafka. An order is a saga that an orchestrator drives across services. A transactional outbox per service guarantees that a state change and its event commit together. Driver location is a hot path kept entirely in Redis with a geospatial index; only state changes are persisted.

3. Order saga and domain events

Placing an order is a saga with six steps, each a local transaction in its owning service. The order service is the orchestrator; it stores the saga state and decides the next step or the compensation.

#StepServiceCompensation
1Create order (PENDING_PAYMENT)OrderMark CANCELLED
2Authorise paymentPaymentVoid authorisation
3Request restaurant acceptRestaurantCancel request
4Reserve a driverDriverRelease driver
5Capture payment on pickupPaymentRefund capture
6Mark delivered, settle payoutsOrder / DriverManual review
A saga step never rolls back another service. It emits a compensation that the owning service applies as a new, forward-only transition.

5. Correctness under failure

Four mechanisms keep an order correct when a service is slow, a message repeats, or a saga step fails halfway: the transactional outbox, idempotent consumers, saga compensation with timeouts, and a reconciliation job that compares internal state to the event log.

Transactional outbox

Writing to a service database and publishing to Kafka are two systems. Publishing before commit can announce a state change that rolls back; publishing after commit loses the event on a crash. Each service writes the event into an outbox_events table inside the same local transaction as the state change. A relay reads unpublished rows with FOR UPDATE SKIP LOCKED, publishes to Kafka, and marks them published.

flowchart LR TX["BEGIN transaction"] --> S1["Update order state"] S1 --> S2["Insert row into outbox_events"] S2 --> CM["COMMIT"] CM --> REL["Relay polls unpublished rows"] REL --> PUB["Publish to Kafka"] PUB --> MARK["Mark published_at"]

Idempotent consumers

Delivery is at-least-once, so every consumer records the eventId it has processed in a processed_events table with a unique constraint. Replays are dropped. The consumer applies its state change and writes the dedupe row in one transaction.

Saga timeouts and compensation

StepTimeoutOn timeout
Restaurant accept90 sCompensate: void payment, cancel order
Driver match120 sBroadcast wider; if still none, cancel and refund
Driver pickup15 min after prep ETAReassign driver, notify ops
Payment capture3 retries with backoffSend to manual settlement queue

Order reconciliation

A nightly job replays the event log for each order and checks that the stored state and the event-derived state agree. Any divergence pages the on-call engineer and opens a break case. This catches bugs that unit tests miss, such as a consumer that silently dropped an event type.

Saga orchestrator

@Service
public class OrderSagaOrchestrator {

    private final SagaStateRepository sagas;
    private final CommandPublisher commands;
    private final CompensationRegistry compensations;
    private final Clock clock;

    public OrderSagaOrchestrator(SagaStateRepository sagas,
                                 CommandPublisher commands,
                                 CompensationRegistry compensations,
                                 Clock clock) {
        this.sagas = sagas;
        this.commands = commands;
        this.compensations = compensations;
        this.clock = clock;
    }

    @Transactional
    public void onEvent(OrderEvent event) {
        SagaState saga = sagas.findByOrderId(event.orderId())
                .orElseThrow(() -> new IllegalStateException("no saga for " + event.orderId()));

        // Forward-only: a late or duplicate event that would move us backwards is dropped.
        if (!saga.accepts(event)) {
            return;
        }

        SagaStep next = saga.advance(event);
        switch (next) {
            case AUTHORISE_PAYMENT -> commands.authorise(event.orderId(), event.amount());
            case REQUEST_RESTAURANT -> commands.requestAccept(event.orderId(), event.restaurantId());
            case MATCH_DRIVER -> commands.matchDriver(event.orderId(), event.restaurantId());
            case CAPTURE_PAYMENT -> commands.capture(event.orderId());
            case COMPLETE -> commands.complete(event.orderId());
            case FAILED -> compensate(saga);
        }
    }

    private void compensate(SagaState saga) {
        for (SagaStep done : saga.completedStepsReversed()) {
            compensations.forStep(done).ifPresent(cmd -> commands.send(cmd, saga.orderId()));
        }
        saga.markCompensated();
    }

    @Scheduled(fixedDelay = 1000)
    public void sweepTimeouts() {
        for (SagaState saga : sagas.findExpired(clock.instant())) {
            compensate(saga);
        }
    }
}

Outbox writer

@Component
public class OutboxWriter {

    private final JdbcTemplate jdbc;
    private final ObjectMapper json;

    public OutboxWriter(JdbcTemplate jdbc, ObjectMapper json) {
        this.jdbc = jdbc;
        this.json = json;
    }

    @Transactional(propagation = Propagation.MANDATORY) // must join the money/order transaction
    public void write(DomainEvent event) {
        jdbc.update("""
            INSERT INTO outbox_events
                (event_id, aggregate_type, aggregate_id, event_type, payload)
            VALUES (?, ?, ?, ?, ?::jsonb)
            """,
            event.id(), event.aggregateType(), event.aggregateId(),
            event.type(), json.writeValueAsString(event));
    }
}

10. Geospatial driver matching

Driver positions are hot, high-frequency, and short-lived. They live entirely in Redis with a geospatial index. Only state changes (online, assigned, offline) are persisted to PostgreSQL.

Ranking

Distance alone is wrong: a driver 300 m away heading the other way is worse than one 1.2 km away heading to the restaurant. The matcher computes an ETA with a routing provider and combines it with rating and recent acceptance rate.

public record Candidate(UUID driverId, double distanceKm, Duration eta,
                        double rating, double acceptanceRate) {

    /** Lower score is better. ETA dominates, then rating and acceptance. */
    public double score() {
        return eta.toSeconds()
             + (5.0 - rating) * 30.0
             + (1.0 - acceptanceRate) * 60.0;
    }
}

@Service
public class DriverMatcher {

    private final GeoIndex geo;
    private final RoutingClient routing;
    private final OfferBroadcaster offers;

    public DriverMatcher(GeoIndex geo, RoutingClient routing, OfferBroadcaster offers) {
        this.geo = geo;
        this.routing = routing;
        this.offers = offers;
    }

    public Optional<UUID> match(Order order) {
        for (double radiusKm : new double[]{2, 5, 10}) {
            List<GeoHit> hits = geo.search(order.restaurantId(), radiusKm, 20);
            List<Candidate> ranked = hits.stream()
                    .filter(h -> geo.isAvailable(h.driverId()))
                    .map(h -> new Candidate(
                            h.driverId(),
                            h.distanceKm(),
                            routing.eta(h.driverId(), order.restaurantId()),
                            geo.rating(h.driverId()),
                            geo.acceptanceRate(h.driverId())))
                    .sorted(Comparator.comparingDouble(Candidate::score))
                    .limit(5)
                    .toList();

            if (!ranked.isEmpty()) {
                // Broadcast to top N; first accept wins in the driver service.
                return offers.broadcast(order.id(), ranked, Duration.ofSeconds(15));
            }
        }
        return Optional.empty();
    }
}

First-accept-wins

The driver service keeps a single row per order offer in PostgreSQL with a unique constraint on order_id. The first accept wins; later accepts hit the unique constraint and are rejected with a friendly "offer already taken" response.

13. Interview questions and model answers

1. Why a saga instead of a distributed transaction?

Two-phase commit requires every participant to be up and to hold locks across the network. A restaurant service that is deploying or a payment PSP that is slow would block all orders. A saga makes each step a local transaction and uses compensations, so a slow participant only delays its own step.

2. What happens if the payment is authorised but the restaurant rejects the order?

The saga compensates: the order service emits a void for the authorisation, and the payment service voids it against the PSP. Because compensation is a new forward-only transition, a retried void is harmless.

3. How do you stop a duplicate event from assigning two drivers?

The driver service has a unique constraint on order_id in the offer table. The first accept wins; the second hits the constraint and is rejected. Every consumer also records the event id in a dedupe table, so a replayed DriverAssigned is dropped at the order service.

4. How do you guarantee an event is not lost when a service crashes after committing state?

The event is written to the outbox in the same local transaction as the state change. A relay publishes it later. If the service crashes after commit but before publish, the relay picks up the unpublished row on restart.

5. How do you match nearby drivers without hammering PostGIS?

Live positions live in Redis with GEOADD and GEOSEARCH. Only state transitions (online, assigned, offline) are persisted to PostgreSQL. PostGIS is the fallback when Redis is unavailable, and the historical store for analytics.

6. How do you avoid offering the same driver to two orders at once?

The driver service marks a driver as OFFERED in Redis with a short lease. The first offer to be accepted flips the driver to ASSIGNED; other orders see the driver as unavailable. A failed accept releases the lease.

7. What is your source of truth for an order?

The order service database is the source of truth for order state. Every other service keeps its own copy of what it needs, updated from Kafka. A nightly reconciliation replays the event log and compares it to the stored state.

8. How do you handle a restaurant that is slow to accept?

The saga has a 90-second deadline. If the restaurant has not accepted, the order service compensates: it voids the payment and cancels the order. This is configurable per restaurant tier.

9. How would you handle 10x the traffic?

Partition Kafka by orderId and scale consumer groups. Shard Redis geo by city. Partition the orders table by month. Move order history to a read model. The saga and outbox patterns do not change.

10. How do you test a saga end-to-end?

With contract tests per consumer, a saga simulator that injects failures at each step, and a staging environment that runs the full Kafka topology. The simulator asserts that every failure path ends in a terminal state with a compensating event.
