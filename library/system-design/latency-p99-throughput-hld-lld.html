Pehle vocabulary saaf karo, warna interview mein ghoomte reh jaoge

Interviewer ye sunna chahta hai ki aap latency aur throughput ko alag-alag cheez maanate ho, aur percentile ko "average ka fancy naam" nahi samajhte. Ye char definitions har round ka base hain.

latency

Ek request ka time

Request bhejne se leke poora response milne tak ka duration. Ye ek user ka experience hai. Unit: milliseconds. Hamesha distribution hoti hai, single number nahi.

throughput

Kitni requests / second

System ek second mein kitna kaam nipta raha hai (RPS / QPS / TPS). Ye system ki capacity hai. High throughput ≠ low latency — dono alag knobs hain.

p99

100 mein se 99 iske andar

Requests ko sort karo, 99th percentile point uthao. Matlab 1% requests isse slow hain. p99 = 1.2s ka matlab: 1M requests par 10,000 log dukhi hain.

tail

p99 se aage ka hissa

p99.9 / p99.99 — sabse slow requests. Yahi GC pause, cache miss, retry, lock contention aur noisy-neighbour chhupa ke rakhta hai. Tail hi aapka real SLO hai.

L = λ × W

Little's Law. Concurrency (L) = arrival rate (λ) × latency (W). Interview mein sabse zyada return dene wala formula. 500 RPS × 200ms = 100 concurrent requests chahiye. Isse thread pool aur connection pool dono size hote hain.

P(slow) = 1 − (1 − p)^n

Tail amplification. Ek service ka p99 = 1%. Agar ek request 100 services ko parallel call karti hai, to 63% requests slow ho jayengi. Microservices mein p99 apne aap kharab hota hai.

W = S / (1 − ρ)

Queueing. ρ = utilization. 50% par latency 2× service time, 90% par 10×, 95% par 20×. Isliye capacity planning 100% utilization par nahi, ~60–70% par hoti hai.

T-01

Average latency jhooth bolta hai

hits
HLDLLDSDE-1/2

⚠ problem

Dashboard par avg latency = 84ms chamak raha hai, SLO green hai, par support tickets aa rahe hain: "checkout hang ho jaata hai".

  • Average outliers ko dabata hai. 990 requests 40ms par aur 10 requests 5s par — average phir bhi 89ms.
  • Average se aap kabhi nahi bata sakte ki kitne users affected hain.
  • Latency distribution normal nahi, right-skewed / multi-modal hoti hai (cache hit ek hump, cache miss doosra hump). Aise data par mean meaningless hai.
  • Aur bada bug: teams p99 ko average of p99s nikaal ke aggregate karti hain — mathematically galat. Percentiles average nahi hote.
Interview trap: "Aapka p99 kya hai?" ka jawab agar "average 80ms hai" hai, to round wahin khatam.

✓ solution

Latency ko hamesha distribution ki tarah store karo — histogram buckets mein, single number mein nahi.

  • Histogram publish karo, summary nahi. Micrometer ka publishPercentileHistogram raw buckets Prometheus ko bhejta hai, taaki percentile server side par sahi tarah aggregate ho (histogram_quantile).
  • SLO define karo percentile + threshold + window ke saath: "p99 < 300ms over 30 din, 99.9% availability".
  • Har latency metric par dimension daalo: endpoint, status, cache-hit — taaki bimodal distribution alag-alag dikhe.
  • SLI ke liye bucket-count ratio lo: "kitni requests 300ms bucket ke andar aayi" — ye aggregate-safe hai aur error budget ke liye seedha use hota hai.
Cost: Har histogram bucket ek time-series hai. 30 buckets × 40 endpoints × 20 pods = cardinality blast. Buckets soch samajh ke chuno.

@Component
public class LatencyMetricsRecorder {

  private final MeterRegistry meterRegistry;

  public LatencyMetricsRecorder(MeterRegistry meterRegistry) {
    this.meterRegistry = meterRegistry;
  }

  /** Ek endpoint call ka poora duration record karta hai, saare dimensions ke saath. */
  public <T> T recordEndpointLatency(String endpoint,
                                    String cacheOutcome,
                                    Supplier<T> work) {

    Timer.Sample sample = Timer.start(meterRegistry);        // (5)
    String outcome = "success";
    try {
      return work.get();
    } catch (RuntimeException failure) {
      outcome = "error";                                       // (6)
      throw failure;
    } finally {
      sample.stop(Timer.builder("api.request.latency")
          .tag("endpoint", endpoint)
          .tag("outcome", outcome)
          .tag("cache", cacheOutcome)                          // (7)
          .register(meterRegistry));
    }
  }
}
  1. (1)Ek MeterFilter bean — ye har matching timer par ek hi jagah se config lagata hai. Har controller mein manually likhne ki zaroorat nahi; naya endpoint apne aap sahi histogram config le lega.
  2. (2)percentilesHistogram(true) raw bucket counts export karta hai. Isse Prometheus mein histogram_quantile(0.99, ...) saare pods par correctly aggregate hota hai. Client-side .publishPercentiles() per-pod numbers deta hai jinhe add nahi kiya ja sakta.
  3. (3)serviceLevelObjectives exact SLO buckets add karta hai. 300ms bucket ka counter seedha "kitni requests SLO ke andar thi" batata hai — error budget ka numerator mil gaya.
  4. (4)min/max range bucket count control karti hai. Ye cardinality guard hai — bina iske Micrometer bahut saare buckets bana deta hai aur Prometheus ka memory footprint phat jaata hai.
  5. (5)Timer.Sample monotonic clock par start hota hai (System.nanoTime), wall clock par nahi — NTP jump se latency corrupt nahi hogi.
  6. (6)Failures ko alag tag karo. Fail-fast errors 2ms mein return hote hain aur aapka p99 artificially accha dikha dete hain. Success-only latency dekho.
  7. (7)cache tag bimodal distribution ko do saaf modes mein todta hai. Cache-miss ka p50 dekhna cache-hit ke mixed p99 se zyada actionable hota hai.
T-02

Load test bolta hai "p99 = 90ms", production bolta hai "p99 = 4s"

hits
HLDSDE-3

⚠ problem — coordinated omission

Load generator har request ka response wait karke agli request bhejta hai. Jab server ek 3 second ka stall karta hai, us dauraan load generator ne koi request bheji hi nahi.

  • Jo requests sabse zyada suffer karti (stall ke dauraan queue mein khadi hoti), wo record hi nahi hui.
  • Ek 3s stall = ~150 missing slow samples at 50 RPS. Aapka histogram unhe 0 count deta hai.
  • Result: closed-loop load test ka p99 real p99 se 10–100× optimistic hota hai.
  • Same bug app-side mein bhi: agar aap latency queue-entry ke baad measure karte ho, to queue wait time chhut jaata hai — user ne wo bhi jhela hai.
Symptom: Load test aur prod graph ka shape alag — test smooth, prod spiky.

✓ solution — open-loop + intended-time

  • Open-loop load model use karo: fixed arrival rate (Gatling constantUsersPerSec, k6 constant-arrival-rate), na ki fixed virtual users. Server slow ho to bhi requests aati rahengi.
  • Intended start time se measure karo, actual start time se nahi: latency = responseTime − scheduledSendTime. Ye queue wait ko wapas count karta hai.
  • App ke andar: latency ka timer filter/interceptor ki entry par start karo, service method mein nahi. Aur agar aap khud queue karte ho (async executor), to queueWaitTime alag metric banao.
  • HdrHistogram ka recordValueWithExpectedInterval() synthetic missing samples backfill karta hai.
Ignore kab karein: Agar aapka traffic genuinely closed-loop hai (fixed 20 batch workers, koi user nahi), tab closed-loop test hi correct model hai.
QueueWaitAwareLatencyFilter.javaqueue time ko latency mein wapas jodna
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)                              // (1)
public class QueueWaitAwareLatencyFilter extends OncePerRequestFilter {

  private static final String EDGE_TS_HEADER = "X-Edge-Request-Start-Ms";

  private final MeterRegistry registry;

  @Override
  protected void doFilterInternal(HttpServletRequest request,
                                  HttpServletResponse response,
                                  FilterChain chain) throws IOException, ServletException {

    long serverEntryNanos = System.nanoTime();
    long queueWaitMs = calculateEdgeToAppQueueWaitMs(request);       // (2)

    try {
      chain.doFilter(request, response);
    } finally {
      long serviceMs = (System.nanoTime() - serverEntryNanos) / 1_000_000;

      recordUserPerceivedLatency(request, response, queueWaitMs + serviceMs); // (3)
      recordQueueWaitOnly(request, queueWaitMs);                          // (4)
    }
  }

  /** Edge (LB/gateway) ne request stamp ki thi; app tak pahunchne mein jitna laga wahi queue wait hai. */
  private long calculateEdgeToAppQueueWaitMs(HttpServletRequest request) {
    String edgeStart = request.getHeader(EDGE_TS_HEADER);
    if (edgeStart == null) return 0L;                                  // (5)
    long wait = System.currentTimeMillis() - Long.parseLong(edgeStart);
    return Math.max(0L, Math.min(wait, 30_000L));                       // (6)
  }

  private void recordUserPerceivedLatency(HttpServletRequest req,
                                         HttpServletResponse res,
                                         long totalMs) {
    Timer.builder("api.request.latency")
        .tag("endpoint", req.getRequestURI())
        .tag("status", String.valueOf(res.getStatus()))
        .register(registry)
        .record(totalMs, TimeUnit.MILLISECONDS);
  }
}
  1. (1)HIGHEST_PRECEDENCE zaroori hai — ye filter sabse pehle chalega, isliye baaki filters (auth, tracing, compression) ka time bhi count hoga. Neeche rakhoge to unka cost invisible ho jayega.
  2. (2)Queue wait pehle nikaalo, kyunki iske baad chain block ho sakti hai. Ye wo time hai jo request Tomcat ke accept queue mein khadi thi.
  3. (3)User-perceived latency = queue wait + service time. Yahi wo number hai jo user ne actually jhela. Sirf serviceMs report karna hi coordinated omission ka app-side version hai.
  4. (4)Queue wait ka apna metric alag rakho. Agar ye badhta hai to signal saaf hai: capacity kam hai, code slow nahi hua.
  5. (5)Header missing ho to 0 return karo, exception nahi. Observability code kabhi request fail nahi karna chahiye.
  6. (6)Clamp lagana zaroori hai. Edge aur app ki clocks alag machines par hain; clock skew se negative ya 4-ghante ka wait aa sakta hai jo poora histogram corrupt kar dega.
T-03

Har service fast hai, phir bhi page slow hai — tail amplification

hits
HLDLLDSDE-3

⚠ problem

Product page 8 downstream services ko call karta hai. Har service ka p99 = 100ms, p50 = 10ms. Sabhi teams bolti hain "hamari service theek hai". Page ka p99 phir bhi 900ms.

  • Parallel fan-out mein request sabse slow response ka intezaar karti hai — max, average nahi.
  • P(koi ek slow) = 1 − 0.99^8 = 7.7%. Matlab page ka p92 hi 100ms cross kar gaya.
  • 100 shards par ye 63% ho jaata hai. Aur agar call sequential hain to latency add hoti hai — 8 × p50 bhi bura hai.
  • Fix karne ki koshish mein team har service ka p99 chase karti hai — jo infinite aur mehnga game hai.
Root insight: Ye ek architecture problem hai, individual service ki performance problem nahi.

✓ solution

  • Fan-out kam karo. Read-optimised denormalised view (materialised view / CQRS read model) banao taaki 8 call ki jagah 1–2 call ho.
  • Non-critical calls ko optional banao. "Recommendations" aur "reviews count" ke bina page render ho sakta hai — unhe short deadline do aur timeout par skip kar do (graceful degradation).
  • Deadline propagation: poora request ek deadline carry kare (jaise 400ms). Har downstream call ko bacha hua time milta hai, apna fixed timeout nahi.
  • Critical vs optional ka split explicitly code mein dikhao — interview mein yahi maturity dikhti hai.
Cost: Degraded response = stale ya incomplete UI. Product ke saath decide karo ki kaunsa block missing ho sakta hai.
ProductPageAggregator.javadeadline-aware fan-out with optional degradation
@Service
public class ProductPageAggregator {

  private static final Duration PAGE_DEADLINE = Duration.ofMillis(400);

  private final Executor fanOutExecutor;   // bulkhead se aaya hua, T-05 dekho

  public ProductPageView buildProductPage(String productId) {

    Deadline deadline = Deadline.startingNow(PAGE_DEADLINE);           // (1)

    // --- CRITICAL: inke bina page render hi nahi ho sakta ---
    CompletableFuture<Product> product =
        callCritical(() -> catalogClient.fetchProduct(productId, deadline));
    CompletableFuture<Price> price =
        callCritical(() -> pricingClient.fetchPrice(productId, deadline));

    // --- OPTIONAL: timeout par empty, page phir bhi jayega ---
    CompletableFuture<List<Review>> reviews =
        callOptional(() -> reviewClient.fetchTopReviews(productId, deadline),
                     List.of(), "reviews");                            // (2)
    CompletableFuture<List<Product>> similar =
        callOptional(() -> recoClient.fetchSimilar(productId, deadline),
                     List.of(), "recommendations");

    CompletableFuture.allOf(product, price).join();                    // (3)

    return new ProductPageView(
        product.join(), price.join(),
        reviews.getNow(List.of()),                                    // (4)
        similar.getNow(List.of()));
  }

  private <T> CompletableFuture<T> callCritical(Supplier<T> call) {
    return CompletableFuture.supplyAsync(call, fanOutExecutor);
  }

  /** Optional call: fail ya timeout hone par fallback deta hai, exception propagate nahi karta. */
  private <T> CompletableFuture<T> callOptional(Supplier<T> call,
                                                  T fallback,
                                                  String blockName) {
    return CompletableFuture
        .supplyAsync(call, fanOutExecutor)
        .exceptionally(error -> {                                        // (5)
          degradationCounter.increment(blockName);
          return fallback;
        });
  }
}

/** Remaining-time deadline. Har hop apna share nahi, bacha hua time use karta hai. */
public record Deadline(long expiresAtNanos) {

  public static Deadline startingNow(Duration budget) {
    return new Deadline(System.nanoTime() + budget.toNanos());
  }

  public Duration remaining() {
    return Duration.ofNanos(Math.max(0, expiresAtNanos - System.nanoTime())); // (6)
  }

  public boolean isExpired() { return remaining().isZero(); }
}
  1. (1)Deadline ek baar request ke start par banti hai aur neeche pass hoti hai. Ye "har call ko 300ms timeout" se fundamentally behtar hai — 3 sequential calls × 300ms = 900ms worst case, jo aapke 400ms SLO ko tod deta hai.
  2. (2)Optional blocks ko explicit fallback (List.of()) milta hai. Ye product decision code mein visible hai — reviewer turant samajh jaayega ki kya degrade ho sakta hai.
  3. (3)allOf sirf critical futures par wait karta hai. Optional futures ka intezaar nahi hota — yahi tail amplification cut karta hai. n = 8 se effective n = 2 ho gaya.
  4. (4)getNow(fallback) block nahi karta — jo aa gaya wo le lo, warna default. Yahan join() likhna poori optimisation bekaar kar deta.
  5. (5)exceptionally failure ko value mein badal deta hai, saath hi ek counter badhata hai taaki silent degradation dashboard par dikhe. Silent fallback sabse khatarnak bug hai.
  6. (6)Math.max(0, ...) negative duration se bachata hai. Deadline nikal chuki ho to client ko turant fail karna chahiye, na ki negative timeout ke saath call bhejni chahiye.
T-04

Throughput badhaya, latency phat gayi — Little's Law aur batching

hits
HLDLLDSDE-2

⚠ problem

Team ne throughput badhane ke liye thread pool 50 se 500 kar diya. RPS thoda badha, par p99 12× ho gaya.

  • Threads badhane se CPU nahi badhti. Extra threads sirf queue ko thread pool ke andar chhupa dete hain.
  • Utilization jitna 100% ke paas jaata hai, queueing latency utni exponentially badhti hai: W = S/(1−ρ).
  • Batching se throughput badhta hai par har item ko batch bharne ka wait jhelna padta hai — ye pure latency cost hai.
  • Ulta bhi sach hai: latency ke liye over-optimise karo (batch size 1, no pooling) to throughput gir jaata hai aur infra cost 3× ho jaata hai.
Rule: Throughput aur latency ek hi dial ke do sire hain. Dono ek saath maximise nahi hote — aap sirf operating point chunte ho.

✓ solution

  • Concurrency Little's Law se size karo, guess se nahi: threads = targetRps × p99LatencySeconds, phir headroom ke liye 1.2–1.5×.
  • Pool ko chhota aur bounded rakho + bounded queue. Bhari load par fail-fast karna, silently 4s tak queue karne se behtar hai.
  • Batching ka dono-taraf ka trigger lagao: size (100 items) ya time (10ms) — jo pehle aaye. Ye maxLinger latency ko cap karta hai.
  • Target utilization ~60–70% rakho. 85%+ par p99 exponential curve mein chala jaata hai.
Ignore kab karein: Batch / offline pipelines mein latency matter hi nahi karti — wahan batch size zyada rakho aur utilization 95% tak le jao. Cost jeetta hai.
BufferedWriteAccumulator.javasize-or-time flush — throughput bina unbounded latency ke
@Component
public class BufferedWriteAccumulator {

  private static final int  MAX_BATCH_SIZE   = 200;
  private static final long MAX_LINGER_MILLIS = 10;                     // (1)

  private final BlockingQueue<EventRow> pendingRows =
      new ArrayBlockingQueue<>(20_000);                              // (2)

  private final EventRowRepository repository;
  private final Timer flushTimer;

  /** Caller block nahi hota. Queue full ho to turant reject — backpressure upar jaata hai. */
  public boolean offerRowForBatchWrite(EventRow row) {
    return pendingRows.offer(row);                                   // (3)
  }

  @Scheduled(fixedDelay = MAX_LINGER_MILLIS)                            // (4)
  public void flushPendingRowsOnScheduleOrWhenFull() {
    List<EventRow> batch = new ArrayList<>(MAX_BATCH_SIZE);
    pendingRows.drainTo(batch, MAX_BATCH_SIZE);                       // (5)

    if (batch.isEmpty()) return;

    flushTimer.record(() -> repository.insertAllInSingleRoundTrip(batch)); // (6)
  }

  /**
   * Little's Law se pool size: L = lambda * W.
   * 800 RPS aur 120ms p99 -> 96 concurrent, 1.3x headroom -> ~125 threads.
   */
  public static int calculateConcurrencyFromLittlesLaw(int targetRps,
                                                    Duration p99Latency,
                                                    double headroomFactor) {
    double concurrency = targetRps * (p99Latency.toMillis() / 1000.0);
    return (int) Math.ceil(concurrency * headroomFactor);              // (7)
  }
}
  1. (1)Linger = maximum extra latency jo aap throughput ke badle dene ko taiyaar ho. Ye number product SLO se aata hai, feeling se nahi. 10ms linger p99 mein 10ms se zyada kabhi nahi jodega.
  2. (2)ArrayBlockingQueue bounded hai. LinkedBlockingQueue (unbounded) yahan classic blunder hai — wo memory kha jaata hai aur latency ko infinite bana deta hai instead of failing.
  3. (3)offer() use kiya, put() nahi. put() caller thread ko block karta — matlab web thread ruk jaati aur backpressure poore system mein ulta failta. offer() false return karta hai aur caller decide karta hai (shed / 429).
  4. (4)fixedDelay (na ki fixedRate) — flush slow ho to overlapping executions nahi honge. fixedRate se pile-up ho sakta hai.
  5. (5)drainTo(batch, MAX) ek hi lock acquisition mein N items nikalta hai — N alag poll() calls se kaafi sasta. Size cap batch ko bounded rakhta hai.
  6. (6)Ek DB round trip mein 200 rows. Network RTT 1ms hai to 200 individual inserts = 200ms, batch = ~3ms. Yahi throughput ka asli source hai — threads badhana nahi.
  7. (7)Sizing ko ek named, testable method banao. Interview mein ye line sabse zyada impress karti hai: aap capacity ko derive kar rahe ho, tune nahi.
T-05

Ek slow dependency ne poori service le dubi — bulkhead isolation

hits
HLDLLDSDE-2/3

⚠ problem

Recommendation service 8 second lena shuru ho gayi. 5 minute mein poora checkout down ho gaya — jabki checkout ka recommendations se koi lena-dena nahi.

  • Sab kuch ek hi shared thread pool par tha. Slow calls ne saare 200 threads occupy kar liye.
  • Health check bhi usi pool se serve hota tha — pod unhealthy mark hua, Kubernetes ne restart kiya, load bache hue pods par gaya, cascade complete.
  • Same pattern DB connection pool aur HTTP client pool mein bhi hota hai — resource exhaustion cascade.
Yaad rakho: Slow ho jaana, fail ho jaane se zyada khatarnak hai. Failure fast hoti hai; slowness resources hold karti hai.

✓ solution — bulkhead

  • Har downstream dependency ka apna bounded pool. Recommendations ke 20 threads khatam — sirf recommendations degrade hoga, checkout chalta rahega.
  • Queue bhi bounded, aur rejection policy explicit: CallerRunsPolicy nahi (wo web thread block karta hai) — AbortPolicy + fallback.
  • Health / readiness endpoints ko alag connector par rakho (Spring Boot management port) taaki wo kabhi app pool se compete na karein.
  • Naming discipline: pool ka naam dependency ke naam par ho, taaki thread dump padhne mein 5 second lage 5 minute nahi.
Cost: Total threads badh jaate hain aur pools individually under-utilised rehte hain. Ye deliberate waste hai — isolation ki keemat.
DependencyBulkheadConfig.javaper-dependency isolated pools
@Configuration
public class DependencyBulkheadConfig {

  @Bean("checkoutCriticalExecutor")
  public ThreadPoolTaskExecutor checkoutCriticalExecutor() {
    return buildBulkhead("checkout-critical", 40, 40, 200,          // (1)
                         new ThreadPoolExecutor.AbortPolicy());
  }

  @Bean("recommendationExecutor")
  public ThreadPoolTaskExecutor recommendationExecutor() {
    return buildBulkhead("reco-optional", 10, 20, 50,              // (2)
                         new ThreadPoolExecutor.AbortPolicy());
  }

  /**
   * Ek isolated, bounded, observable pool banata hai.
   * Har parameter ka latency par seedha asar hai — koi bhi default mat chhodo.
   */
  private ThreadPoolTaskExecutor buildBulkhead(String name,
                                               int coreThreads,
                                               int maxThreads,
                                               int queueCapacity,
                                               RejectedExecutionHandler onOverflow) {

    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setThreadNamePrefix(name + "-");                          // (3)
    executor.setCorePoolSize(coreThreads);
    executor.setMaxPoolSize(maxThreads);
    executor.setQueueCapacity(queueCapacity);                          // (4)
    executor.setKeepAliveSeconds(60);
    executor.setRejectedExecutionHandler(onOverflow);                  // (5)
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(20);                          // (6)
    executor.initialize();
    return executor;
  }

  /** Har pool ka saturation metric — alert isi par lagta hai, CPU par nahi. */
  @Bean
  public MeterBinder bulkheadSaturationMetrics(
          Map<String, ThreadPoolTaskExecutor> pools) {
    return registry -> pools.forEach((beanName, pool) ->
        Gauge.builder("bulkhead.queue.utilization", pool,
                p -> (double) p.getThreadPoolExecutor().getQueue().size()
                     / (p.getQueueCapacity() + 1))                       // (7)
            .tag("pool", beanName)
            .register(registry));
  }
}
  1. (1)Critical path ko bada, fixed pool (core == max) milta hai. Fixed size ka matlab: load par thread creation ka jitter nahi — thread banane mein hi 1ms+ lag sakta hai aur wo p99 mein dikhta hai.
  2. (2)Optional dependency ka pool jaan-boojh ke chhota hai. Reco service mar bhi jaaye to max 20 threads phasengi. Ye blast radius ki definition hai.
  3. (3)Thread name prefix — incident ke waqt jstack mein reco-optional-7 dikhega, pool-3-thread-7 nahi. Ye 3 baje raat ko sabse valuable line hoti hai.
  4. (4)Bounded queue. Spring ka default Integer.MAX_VALUE hai — matlab unbounded queue, matlab unbounded latency. Ye default badalna hi bulkhead ka asli kaam hai.
  5. (5)AbortPolicy exception fenkta hai jise caller fallback mein badal deta hai. CallerRunsPolicy yahan mat lagao — wo task ko web thread par chala dega, aur wahi to aap bachana chahte the.
  6. (6)Graceful shutdown. Iske bina rolling deploy ke waqt in-flight requests kat jaati hain aur aapko deploy window mein p99 spike + 5xx dikhta hai.
  7. (7)Alert queue utilization par lagao, CPU par nahi. Queue bharna latency badhne se pehle hota hai — ye leading indicator hai, CPU lagging indicator hai.

⚠ problem

"Connection timeout" errors aa rahe the, to pool 20 se 200 kar diya. Ab timeouts to gaye, par har query 3× slow hai.

  • DB ke paas fixed cores hain. 200 concurrent queries = context switching, lock contention, disk thrash.
  • Pool bada karne se DB par queue shift ho gayi — jahan aapke paas na visibility hai na control.
  • 50 pods × 200 connections = 10,000 connections. Postgres har connection par ~10MB backend memory leta hai. DB OOM.
  • Aur pool se connection lene ka wait time latency metrics mein invisible tha — sirf "query slow hai" dikh raha tha.

✓ solution

  • Pool ko chhota karo. Rule of thumb: connections ≈ (2 × cpuCores) + effectiveSpindleCount. Ek 8-core Postgres ke liye ~20 connections total (saare pods milaake), 200 nahi.
  • connectionTimeout chhota rakho (250ms). Fail fast > 30s tak wait.
  • Multi-pod deployments mein PgBouncer jaisa external pooler lagao — connection multiplexing app pool se behtar karta hai.
  • Pool acquire time ka apna metric banao. "Query slow" vs "connection ka wait" — do bilkul alag problems hain.
Counter-intuitive: Chhota pool aksar zyada throughput deta hai. DB ko queue karne dene se behtar hai app mein queue rakhna, jahan aap shed kar sakte ho.

Retry ne outage ko 3× lamba kar diya — timeout, budget, breaker

hits
HLDLLDSDE-3

⚠ problem — retry storm

Inventory service ne 30 second ke liye 5% errors diye. Har caller ne 3 retries kiye. Load 3× ho gaya, service poori tarah gir gayi, aur 20 minute tak wapas nahi aayi.

  • Retries exactly us waqt load badhate hain jab service already struggling hai — metastable failure.
  • Nested retries multiply hote hain: gateway 3 × BFF 3 × service 3 = 27 calls ek user request ke liye.
  • Fixed backoff se saare clients sync ho jaate hain aur ek saath dobara hit karte hain (thundering herd).
  • Retry after timeout: agar timeout 3s hai aur 3 retries hain, user ka worst case 9s+ hai — aapka SLO 400ms ka tha.

✓ solution

  • Retry budget: retries total requests ke ≤10% honi chahiye. Budget khatam = retry band. Ye retry storm ko mathematically impossible bana deta hai.
  • Exponential backoff + full jitter — synchronisation todta hai.
  • Sirf ek layer par retry karo (aam taur par edge ke sabse paas wali). Baaki layers fail-fast karein.
  • Circuit breaker: error rate threshold cross ho to turant fail karo, taaki dying service ko saans mile.
  • Retry sirf idempotent ya idempotency-key wale operations par. Payment ka blind retry = double charge.
Ignore kab karein: Non-idempotent writes bina idempotency key ke — wahan retry karna bug hai, feature nahi.
BudgetedRetryExecutor.javatoken-bucket retry budget + full jitter + breaker
@Component
public class BudgetedRetryExecutor {

  private static final int    MAX_ATTEMPTS      = 3;
  private static final double RETRY_RATIO_CAP   = 0.10;                  // (1)
  private static final long   BASE_BACKOFF_MS   = 20;

  private final RetryBudget budget = new RetryBudget(RETRY_RATIO_CAP, 10);
  private final CircuitBreaker breaker;

  public <T> T executeWithBudgetedRetry(String dependency,
                                        Deadline deadline,
                                        Callable<T> call) throws Exception {

    budget.recordInitialAttempt();
    Exception lastFailure = null;

    for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {

      if (deadline.isExpired()) throw new DeadlineExceededException(dependency); // (2)

      try {
        return breaker.executeCallable(call);                            // (3)

      } catch (CallNotPermittedException open) {
        throw open;                                                    // (4)

      } catch (Exception failure) {
        lastFailure = failure;

        if (!isRetryable(failure))            throw failure;              // (5)
        if (attempt == MAX_ATTEMPTS)          break;
        if (!budget.tryConsumeRetryToken())  break;                       // (6)

        sleepWithFullJitter(attempt, deadline);                          // (7)
      }
    }
    throw lastFailure;
  }

  /** Full jitter: sleep = random(0, base * 2^attempt), deadline ke andar clamp. */
  private void sleepWithFullJitter(int attempt, Deadline deadline) throws InterruptedException {
    long ceiling = BASE_BACKOFF_MS * (1L << (attempt - 1));
    long sleepMs = ThreadLocalRandom.current().nextLong(ceiling + 1);
    Thread.sleep(Math.min(sleepMs, deadline.remaining().toMillis()));      // (8)
  }

  /** Sirf transient failures retry hoti hain. 4xx retry karna bug amplify karta hai. */
  private boolean isRetryable(Exception failure) {
    return failure instanceof SocketTimeoutException
        || failure instanceof ConnectException
        || (failure instanceof HttpServerErrorException e
              && e.getStatusCode().value() != 501);
  }
}

/** Token bucket: har success 'ratio' token deta hai, har retry 1 token kharch karta hai. */
final class RetryBudget {
  private final double tokensPerRequest;
  private final double maxTokens;
  private final AtomicDouble tokens = new AtomicDouble(0);

  void recordInitialAttempt() {
    tokens.updateAndGet(t -> Math.min(maxTokens, t + tokensPerRequest));
  }

  boolean tryConsumeRetryToken() {
    return tokens.getAndUpdate(t -> t >= 1 ? t - 1 : t) >= 1;         // (9)
  }
}
  1. (1)10% cap ka matlab: worst case load 1.1× hoga, 3× nahi. Retry storm structurally impossible ho gaya — ye "max 3 retries" se bahut strong guarantee hai.
  2. (2)Har attempt se pehle deadline check. Iske bina retries aapke latency SLO ko silently 3× kar dete hain.
  3. (3)Breaker retry loop ke andar hai, bahar nahi. Isse har attempt breaker ke stats mein count hota hai aur breaker sahi decision leta hai.
  4. (4)Breaker OPEN hai to turant throw karo, retry bilkul nahi. Breaker ka poora point hi ye hai ki downstream ko rest mile.
  5. (5)400 Bad Request retry karna faltu hai — wo dobara bhi fail hoga. Sirf transient failures retry karo. Ye check retry logic ka 50% value hai.
  6. (6)Budget check sleep se pehle. Budget khatam to seedha break — sona bhi mat, kyunki wo latency hai bina kisi fayde ke.
  7. (7)Full jitter, "equal jitter" ya fixed backoff nahi. AWS ke experiments mein full jitter sabse kam contention aur sabse kam total work deta hai.
  8. (8)Sleep ko bache hue deadline se clamp karo. Warna aap 800ms so jaoge jabki request ke paas sirf 40ms bache the.
  9. (9)Atomic compare-and-update — bina lock ke thread safe. Ye hot path par hai, isliye yahan synchronized daalna khud ek latency source ban jaata.

⚠ problem

p99 = 900ms, p50 = 20ms. Profiling se kuch nahi mila kyunki har baar alag alag node slow hota hai — GC pause, noisy neighbour, disk hiccup, network retransmit.

  • Ye slowness random aur unpredictable hai. Koi single fix nahi hai.
  • Slow node ko pehle se identify karna impossible hai — jab tak pata chale, request already stuck hai.
  • Simple timeout+retry se madad nahi milti: aap 900ms timeout ka intezaar karke tab retry karte ho, matlab 900ms+ ho gaya.

✓ solution — hedging (Tail at Scale)

  • p95 latency tak wait karo. Response nahi aaya? Doosre replica par duplicate request bhejo. Jo pehle aaye wo lo, doosri cancel.
  • Extra load sirf ~5% hai (kyunki sirf 5% requests hedge hoti hain), par p99 lagbhag p95 tak gir jaata hai.
  • Hedge threshold live p95 se aana chahiye, hardcoded constant se nahi — traffic pattern badalta rehta hai.
  • Sirf idempotent reads par. Writes par hedging duplicate side-effects deta hai.
Cost: +5% infra load aur double resource usage un requests par. Overload ke waqt hedging band honi chahiye, warna wo fire mein ghee hai.
HedgedReadExecutor.javaadaptive p95 threshold · first-wins · loser cancelled
@Component
public class HedgedReadExecutor {

  private final Timer latencyTimer;                // live distribution
  private final ScheduledExecutorService hedgeScheduler;
  private final AdaptiveLoadShedder loadShedder;

  /**
   * Idempotent read ko hedge karta hai: p95 par ek duplicate attempt bhejta hai,
   * pehla successful response return karta hai, doosra cancel kar deta hai.
   */
  public <T> CompletableFuture<T> executeHedgedRead(Supplier<CompletableFuture<T>> attempt) {

    CompletableFuture<T> primary = attempt.get();

    if (!shouldHedgeRightNow()) return primary;                       // (1)

    CompletableFuture<T> winner = new CompletableFuture<>();
    CompletableFuture<T> hedge   = new CompletableFuture<>();

    long hedgeDelayMs = currentHedgeDelayMillis();                     // (2)

    ScheduledFuture<?> hedgeTrigger = hedgeScheduler.schedule(() -> {
      if (primary.isDone()) return;                                  // (3)
      hedgeCounter.increment();
      attempt.get().whenComplete(completeInto(hedge));
    }, hedgeDelayMs, TimeUnit.MILLISECONDS);

    primary.whenComplete(completeInto(winner));
    hedge.whenComplete(completeInto(winner));                          // (4)

    winner.whenComplete((value, error) -> {
      hedgeTrigger.cancel(false);                                    // (5)
      primary.cancel(true);
      hedge.cancel(true);                                            // (6)
    });

    return winner;
  }

  /** Hedging tabhi jab system healthy ho. Overload mein hedging aag mein ghee hai. */
  private boolean shouldHedgeRightNow() {
    return !loadShedder.isUnderPressure()
        && hedgeRateLimiter.tryAcquire();                              // (7)
  }

  /** Threshold live p95 se, hardcoded value se nahi. */
  private long currentHedgeDelayMillis() {
    double p95 = latencyTimer.takeSnapshot()
                            .percentileValues()[0].value(TimeUnit.MILLISECONDS);
    return (long) Math.max(10, p95);                                  // (8)
  }
}
  1. (1)Pehle guard, phir kaam. Unhealthy system mein hedging load double karke cascade banata hai — ye check hedging ka sabse important hissa hai.
  2. (2)Delay ek baar compute hota hai. Har call par snapshot lena mehnga hai (percentile snapshot cheap nahi hota), isliye ise cache karna production mein zaroori hai.
  3. (3)Trigger chalne par dobara check — race window mein primary complete ho chuka ho sakta hai. Ye ek faltu backend call bachata hai.
  4. (4)Dono futures ek hi winner mein complete karte hain. CompletableFuture.complete() idempotent hai: doosri call ignore ho jaati hai — yahi "first wins" deta hai bina kisi lock ke.
  5. (5)Scheduled trigger cancel karo. Warna primary 5ms mein complete hone ke baad bhi 40ms par ek bekaar hedge nikal jayega.
  6. (6)Haarne wali request cancel karo. Bina iske aap backend par hamesha extra load daal rahe ho — hedging ka pura cost-benefit ulta ho jaata hai.
  7. (7)Rate limiter hedge ratio ko hard cap karta hai (jaise 5%). Do independent guards: health-based aur rate-based.
  8. (8)Minimum 10ms floor. Agar p95 = 2ms ho (sab cached) to har request hedge hone lagegi — floor is degenerate case se bachata hai.

Cache expire hua aur 40,000 requests DB par gir gayi — stampede

hits
HLDLLDSDE-3

⚠ problem

Homepage banner ka cache key TTL 300s tha. Har 5 minute par p99 spike aata tha aur DB CPU 95% chhu jaata tha.

  • Thundering herd: ek popular key expire hoti hai, saare concurrent requests ek saath DB par jaate hain.
  • Saari keys ek hi deploy par warm hui thi, isliye sab same second par expire hoti hain — synchronised stampede.
  • DB slow hua to cache rebuild aur slow hua, jisse aur zyada requests miss hui — feedback loop.
  • Aur cache hit ka p50 2ms tha, isliye average metrics mein ye problem bilkul invisible thi.

✓ solution — 3 layers

  • TTL jitter: TTL = base ± random(10%). Ek hi second par saari keys expire nahi hongi.
  • Single-flight lock: ek hi caller recompute kare, baaki uska intezaar karein ya stale value lein.
  • Probabilistic early refresh (XFetch): TTL khatam hone se pehle hi, badhti hui probability ke saath, ek request background mein refresh kar de. Expiry cliff hi khatam.
  • Stale-while-revalidate: logical TTL cross hone ke baad bhi purana data serve karo jab tak naya na aa jaye. Availability > freshness.
Cost: Stale data ka window. Price aur inventory ke liye ye acceptable nahi ho sakta — wahan single-flight + short TTL use karo.
StampedeSafeCache.javajitter + single-flight + probabilistic early refresh
@Component
public class StampedeSafeCache {

  private static final double EARLY_REFRESH_BETA = 1.0;                // (1)

  private final StringRedisTemplate redis;
  private final Executor refreshExecutor;

  public <T> T getOrRecompute(String key, Duration baseTtl,
                             Class<T> type, Supplier<T> loader) {

    CacheEnvelope<T> cached = readEnvelope(key, type);

    if (cached == null) {
      return recomputeUnderSingleFlightLock(key, baseTtl, loader, null); // (2)
    }

    if (shouldRefreshEarly(cached)) {                                 // (3)
      refreshExecutor.execute(() ->
          recomputeUnderSingleFlightLock(key, baseTtl, loader, cached.value()));
    }
    return cached.value();                                            // (4)
  }

  /**
   * XFetch: jaise-jaise expiry paas aati hai, refresh ki probability badhti hai.
   * Mehngi recompute jitni mehngi, utni jaldi refresh trigger hoti hai.
   */
  private boolean shouldRefreshEarly(CacheEnvelope<?> envelope) {
    long now = System.currentTimeMillis();
    double gap = envelope.recomputeCostMillis()
               * EARLY_REFRESH_BETA
               * -Math.log(ThreadLocalRandom.current().nextDouble());     // (5)
    return now + gap >= envelope.expiresAtMillis();
  }

  private <T> T recomputeUnderSingleFlightLock(String key, Duration baseTtl,
                                             Supplier<T> loader, T staleFallback) {

    String lockKey = "lock:" + key;
    boolean acquired = Boolean.TRUE.equals(
        redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(10))); // (6)

    if (!acquired) {
      if (staleFallback != null) return staleFallback;                // (7)
      return awaitFreshValueBriefly(key, Duration.ofMillis(120), loader);
    }

    try {
      long startedAt = System.currentTimeMillis();
      T fresh = loader.get();
      long costMillis = System.currentTimeMillis() - startedAt;

      writeEnvelope(key, fresh, applyJitter(baseTtl), costMillis);       // (8)
      return fresh;
    } finally {
      redis.delete(lockKey);
    }
  }

  /** TTL par +/-15% jitter — synchronised expiry todne ke liye. */
  private Duration applyJitter(Duration baseTtl) {
    double factor = 0.85 + (ThreadLocalRandom.current().nextDouble() * 0.30);
    return Duration.ofMillis((long) (baseTtl.toMillis() * factor));      // (9)
  }
}
  1. (1)beta aggressiveness knob hai. >1 = jaldi refresh (zyada freshness, zyada backend load), <1 = late refresh. 1.0 balanced default hai.
  2. (2)Cold miss par single-flight lock. Ye stampede ka actual fix hai — baaki sab optimisation hai.
  3. (3)Probabilistic check har hit par chalta hai par sirf ek-do requests hi true payengi. Expiry "cliff" ek smooth slope ban jaati hai.
  4. (4)Early refresh ke dauraan bhi user ko cached value milti hai — zero added latency. Refresh background executor par hai, request path par nahi.
  5. (5)-log(random) exponential distribution deta hai. Ye XFetch paper ka core hai: expiry ke jitna paas, probability utni exponentially zyada.
  6. (6)setIfAbsent + TTL = atomic SET NX EX. TTL bina lock rakhna deadlock hai — process crash hua to key hamesha locked reh jaati.
  7. (7)Stale-while-revalidate. Lock nahi mila? Purana data de do. 200ms purana data, 3 second ke wait se hamesha behtar hai.
  8. (8)Recompute cost ko envelope mein store karo. Mehngi keys apne aap jaldi refresh hongi — self-tuning behaviour, koi manual config nahi.
  9. (9)±15% jitter. Ek line ka change jo deploy-ke-baad wale periodic p99 spikes ko poori tarah khatam kar deta hai.

⚠ problem

"Place Order" API 1.8s leti hai. Andar: order save, payment authorise, inventory reserve, email bhejo, analytics likho, search index update karo, loyalty points do — sab synchronously, ek hi request mein.

  • User un 5 kaamon ka intezaar kar raha hai jinse usse koi matlab nahi.
  • Sabse slow dependency poore write ka p99 decide karti hai.
  • Agar email service down hai to order fail ho jaata hai — availability chain multiply hoti hai: 0.999^7 = 99.3%.
  • Naive fix — "DB commit ke baad Kafka par event daal do" — dual-write problem banata hai: commit hua par publish fail, ya ulta. Data permanently inconsistent.

✓ solution

  • Write ko do hisso mein baanto: synchronous core (jiske bina order valid hi nahi — order row + payment auth + inventory reserve) aur asynchronous tail (email, analytics, index, loyalty).
  • Transactional Outbox: business row aur event row ek hi DB transaction mein likho. Ek relay/CDC process outbox se padh kar Kafka par publish karta hai. Dual-write khatam.
  • Consumers idempotent honge (event id se dedupe), kyunki delivery at-least-once hai.
  • Read-after-write ke liye: cache invalidate karo (update nahi), aur user ko apni hi write dikhane ke liye short window mein primary se padho.
Cost: Eventual consistency. User ko order dikh gaya par email 3s baad aaya — product ko ye accept karna hoga.
OrderWriteService.javasync core + transactional outbox + cache invalidation
@Service
public class OrderWriteService {

  private final OrderRepository  orderRepository;
  private final OutboxRepository outboxRepository;
  private final PaymentClient    paymentClient;
  private final CacheInvalidator cacheInvalidator;

  /**
   * Synchronous core. Sirf wahi kaam jiske bina order legally exist nahi karta.
   * Target: p99 < 250ms.
   */
  @Transactional(timeout = 2)                                          // (1)
  public OrderConfirmation placeOrder(PlaceOrderCommand command) {

    Optional<Order> existing =
        orderRepository.findByIdempotencyKey(command.idempotencyKey());
    if (existing.isPresent()) return OrderConfirmation.from(existing.get()); // (2)

    PaymentAuthorization auth =
        paymentClient.authorize(command.amount(), command.idempotencyKey()); // (3)

    Order order = orderRepository.save(Order.confirmed(command, auth));

    appendToOutboxInSameTransaction(order);                            // (4)

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
          @Override public void afterCommit() {
            cacheInvalidator.invalidateCustomerOrderViews(order.customerId()); // (5)
          }
        });

    return OrderConfirmation.from(order);
  }

  /** Event usi transaction mein likha jaata hai — atomic, isliye dual-write nahi. */
  private void appendToOutboxInSameTransaction(Order order) {
    outboxRepository.save(new OutboxEvent(
        UUID.randomUUID(),
        "order.placed.v1",
        order.id().toString(),                                          // (6)
        OrderPlacedPayload.of(order).toJson(),
        Instant.now()));
  }
}

@Component
public class OutboxRelayPublisher {

  /** Outbox se padh kar Kafka par bhejta hai. At-least-once — consumer idempotent ho. */
  @Scheduled(fixedDelay = 200)
  public void publishPendingOutboxEvents() {

    List<OutboxEvent> pending =
        outboxRepository.lockNextUnpublishedBatch(200);                 // (7)

    for (OutboxEvent event : pending) {
      kafkaTemplate.send(event.topic(), event.partitionKey(), event.payload())
          .whenComplete((result, error) -> {
            if (error == null) outboxRepository.markPublished(event.id());   // (8)
          });
    }
  }
}
  1. (1)Transaction par explicit timeout. Bina timeout ke ek stuck transaction row locks pakde rehta hai aur baaki sab ka p99 kharab karta hai. Ye ek attribute poore DB ko bachata hai.
  2. (2)Idempotency check sabse pehle. Client retry karega (network timeout par karta hi hai) — bina iske double order aur double charge pakka hai.
  3. (3)Payment sync hai kyunki bina auth ke order confirm nahi ho sakta. Notice: idempotency key downstream bhi pass ho rahi hai — retry safe.
  4. (4)Outbox row usi transaction mein. Order commit hua = event bhi commit hua. Ye dual-write problem ka standard interview answer hai.
  5. (5)Cache invalidation afterCommit par, transaction ke andar nahi. Andar karoge to ek race hai: cache clear hua, koi purana data padh ke wapas cache mein daal gaya, phir commit — cache permanently stale.
  6. (6)orderId partition key hai. Ek hi order ke events ek hi Kafka partition par jaate hain = per-order ordering guaranteed. Global ordering ki zaroorat nahi hoti.
  7. (7)SELECT ... FOR UPDATE SKIP LOCKED pattern. Multiple relay instances bina duplicate ya lock contention ke parallel chal sakte hain.
  8. (8)Publish ke baad mark karo. Crash hua to event dobara publish hoga — at-least-once. Isliye consumer ko event id par dedupe karna hi padega.

⚠ problem

Sale ke waqt traffic 5× hua. Kuch reject hone ki jagah, sabhi requests 12 second leni lagi. Har user ne timeout dekha, phir refresh kiya — aur load aur badha.

  • Bina load shedding ke, overload sabko equally barbaad karta hai — 100% requests fail, 0% goodput.
  • Requests queue mein baithi rehti hain jab tak client already timeout kar chuka hota hai. Server dead work kar raha hai.

  • Priority-aware shedding: checkout aur payment kabhi shed mat karo; recommendations aur analytics pehle shed karo.

AdaptiveLoadShedder.javalatency-gradient limit · priority tiers · dead-request drop
@Component
public class AdaptiveLoadShedder {

  private final AtomicInteger inFlight       = new AtomicInteger();
  private volatile int        concurrencyLimit = 50;
  private volatile long       baselineLatencyMs = Long.MAX_VALUE;      // (1)

  /** Har request ke start par. false = 429 bhejo. */
  public boolean tryAdmitRequest(RequestPriority priority, Deadline deadline) {

    if (deadline.isExpired()) {
      droppedDeadCounter.increment();
      return false;                                                  // (2)
    }

    int effectiveLimit = limitForPriority(priority);                  // (3)
    int current = inFlight.incrementAndGet();

    if (current > effectiveLimit) {
      inFlight.decrementAndGet();                                      // (4)
      shedCounter.increment(priority.name());
      return false;
    }
    return true;
  }

  /**
   * Low priority ko limit ka chhota hissa milta hai.
   * Overload mein analytics pehle marta hai, checkout aakhir mein.
   */
  private int limitForPriority(RequestPriority priority) {
    return switch (priority) {
      case CRITICAL -> concurrencyLimit;                               // (5)
      case STANDARD -> (int) (concurrencyLimit * 0.70);
      case BULK     -> (int) (concurrencyLimit * 0.30);
    };
  }

  /**
   * Vegas-style gradient: agar observed latency baseline se kaafi zyada hai,
   * matlab queue ban rahi hai -> limit ghatao. Warna dheere se badhao.
   */
  public void onRequestCompleted(long observedLatencyMs) {
    inFlight.decrementAndGet();
    baselineLatencyMs = Math.min(baselineLatencyMs, observedLatencyMs); // (6)

    double gradient = (double) baselineLatencyMs / Math.max(1, observedLatencyMs);
    double clamped  = Math.max(0.5, Math.min(1.0, gradient));            // (7)

    double queueAllowance = Math.sqrt(concurrencyLimit);              // (8)
    int next = (int) (concurrencyLimit * clamped + queueAllowance);

    concurrencyLimit = Math.max(10, Math.min(2000, next));            // (9)
  }

  public boolean isUnderPressure() {
    return inFlight.get() > concurrencyLimit * 0.85;                  // (10)
  }
}
  1. (1)Baseline = ab tak ka best-observed latency, matlab "bina queue ke" service time. Isi se compare karke pata chalta hai ki queue ban rahi hai ya nahi.
  2. (2)Sabse pehle dead requests drop karo. Ye free capacity hai — client already ja chuka hai, uska kaam karna 100% waste hai. Overload mein aksar 30% requests aisi hoti hain.
  3. (3)Priority-based limit. Interview mein "load shedding karunga" bolna easy hai; "kis order mein shed karunga" batana senior signal hai.
  4. (4)Reject karte waqt counter wapas decrement karna zaroori hai. Ye classic bug hai — leak hone par limit permanently exhausted dikhne lagti hai aur service khud ko throttle kar leti hai.
  5. (5)CRITICAL ko poori limit milti hai. Ek hi pool, alag admission thresholds — isse critical traffic ke liye alag infra nahi chahiye.
  6. (6)Running minimum. Production mein isme decay hona chahiye (jaise har 10 min par reset), warna ek lucky 2ms sample hamesha ke liye baseline pakad leta hai.
  7. (7)Gradient 0.5 par clamp — ek hi bura sample limit ko aadhe se zyada nahi gira sakta. Stability > reaction speed.
  8. (8)sqrt(limit) allowance limit ko dheere-dheere badhne deta hai jab system healthy ho. Additive-increase / multiplicative-decrease — TCP congestion control ka wahi idea.
  9. (9)Absolute floor aur ceiling. Floor bina limit 0 tak gir sakti hai aur service khud ko deadlock kar leti hai; ceiling runaway growth rokta hai.
  10. (10)Yahi signal hedging (T-08) aur optional fan-out (T-03) ko band karta hai. Ek jagah pressure detect karo, poore system mein use karo.

Har 40 second par ek 700ms spike — GC aur JVM ka tail

hits

⚠ problem

p50 bilkul flat hai, par p99.9 par periodic spikes hain. Application code profiling mein bilkul clean.

  • Stop-the-world GC pause — us dauraan har in-flight request ruk jaati hai.
  • Fan-out ke saath ye multiply hota hai: 100 nodes, har ek 1% time GC mein — 63% requests kisi na kisi paused node se takrayengi.
  • Doosre chhupe hue causes: JIT deoptimisation, biased-lock revocation, safepoint pauses, aur transparent huge pages defrag.
  • Container mein: CPU throttling (cfs_quota) GC threads ko starve karta hai, jisse pause aur lamba hota hai.

✓ solution

  • Low-pause collector: ZGC ya Shenandoah — pause <1ms, heap size se independent. G1 tab lo jab throughput priority ho.
  • Allocation rate ghatao — GC ka asli ilaaj yahi hai. Per-request garbage kam karo: streaming JSON, object reuse, chhote DTOs.
  • Container mein MaxRAMPercentage set karo aur CPU limits itna tight mat rakho ki GC threads throttle ho.
  • Load balancer par node ko GC ke dauraan drain karo — brownout detection se traffic hata do.
  • Ye jitna kam-jarurat wala lage utna hi important: GC logs on rakho, wo lagbhag free hain.
Ignore kab karein: Batch jobs mein throughput chahiye, pause nahi. Wahan Parallel GC ya G1 sahi choice hai — ZGC ka throughput overhead faltu hai.

"p99 kharab hai" pata hai, par kahan kharab hai ye nahi pata

hits

⚠ problem

Alert aaya "p99 > 1s". Dashboard par 40 services hain. Kaunsi wajah hai — koi nahi jaanta. Debugging mein 3 ghante gaye.

  • Metrics batate hain kya hua, par kahan nahi.
  • Head-based sampling 1% par: aapke slow requests sample mein hai hi nahi. Jo chahiye wahi missing.
  • Logs mein trace id nahi hai, isliye ek slow request ko services ke aar-paar follow karna impossible hai.

✓ solution

  • RED metrics har service par: Rate, Errors, Duration (histogram). Ye baseline hai.
  • Tail-based sampling: request poori hone ke baad decide karo — slow ya error hai to 100% sample, warna 1%. Aapko exactly wahi traces milte hain jo chahiye.
  • Exemplars: histogram bucket ko trace id se link karo. Grafana par p99 bucket click karo, seedha ek asli slow trace khul jaata hai.
  • Trace id ko log MDC mein daalo, taaki logs aur traces jud jayein.
Order: Pehle RED metrics, phir tail-based traces, phir profiling. Ulta karoge to hafte barbad honge.
TailSamplingTracingConfig.javaslow & error traces 100%, baaki 1%
@Configuration
public class TailSamplingTracingConfig {

  private static final Duration SLOW_THRESHOLD = Duration.ofMillis(500);
  private static final double BASELINE_SAMPLE_RATE = 0.01;

  /**
   * Span khatam hone par decide karta hai ki export karna hai ya nahi.
   * Slow ya failed spans hamesha jaate hain; baaki 1%.
   */
  @Bean
  public SpanExportingPredicate exportSlowAndFailedSpansAlways() {
    return span -> {
      if (span.getError() != null)                    return true;    // (1)
      if (spanDuration(span).compareTo(SLOW_THRESHOLD) > 0) return true; // (2)
      return isInBaselineSample(span.getTraceId());                  // (3)
    };
  }

  /** Trace id ka hash — poore trace par consistent, isliye trace tuta hua nahi aayega. */
  private boolean isInBaselineSample(String traceId) {
    int bucket = Math.abs(traceId.hashCode()) % 10_000;
    return bucket < (BASELINE_SAMPLE_RATE * 10_000);                    // (4)
  }

  /** Histogram bucket ko trace se jodta hai — dashboard se seedha trace tak. */
  @Bean
  public SpanContextSupplier exemplarTraceContext(Tracer tracer) {
    return new SpanContextSupplier() {
      @Override public String getTraceId() {
        return tracer.currentSpan() == null
             ? null : tracer.currentSpan().context().traceId();       // (5)
      }
      @Override public boolean isSampled() { return true; }
    };
  }
}
  1. (1)Errors hamesha export. Error rate itna kam hota hai ki 100% sampling ka cost negligible hai, par debugging value maximum.
  2. (2)Ye poore setup ka dil hai: slow requests guaranteed capture hoti hain. Head sampling mein aapko p99 trace milna luck par depend karta hai.
  3. (3)Baseline sample chahiye taaki aapke paas "normal" ka comparison ho. Sirf slow traces dekhne se aap nahi bata paoge ki kya badla.
  4. (4)Trace id ka deterministic hash — saari services same decision lengi. Random sampling se aadhe-adhure traces milte hain jo bekaar hote hain.
  5. (5)Exemplars Prometheus histogram ko trace id se attach karte hain. "p99 spike" se ek asli slow trace tak ka safar 2 second ka ho jaata hai.

03 · mock interview

Mock questions — jawab ke saath, aur "interviewer kya dhoondh raha hai"

Har jawab ka structure ek jaisa hai: seedha answer, phir reasoning, phir tradeoff. Level filter se apne round ke hisaab se practice karo. Bolte waqt jawab 60–90 second mein khatam karo, phir ruko aur poocho "isme deeper jaana hai?"

p50, p95 aur p99 mein kya fark hai — aur p99 par itna focus kyun?SDE-1/2

Answer: Requests ko latency se sort karo. p50 beech wali request hai, p95 95th position par, p99 99th par. p99 = 1.2s ka matlab hai 1% requests 1.2s se slow hain.

p99 par focus isliye hai kyunki ek user ek request nahi karta. Ek page 20 API calls karta hai — to 1 − 0.99^20 = 18% chance hai ki us user ne kam se kam ek slow call dekhi. Matlab "1% slow" actually "18% users unhappy" hai.

Aur p99 wale users aksar aapke sabse valuable users hote hain: sabse zyada data, sabse bada cart, sabse purana account — kyunki unka payload sabse bada hai.

Interviewer dekh raha hai: Aap percentile ko user-impact mein translate kar paate ho ya nahi. "1% slow" bolna definition hai; "18% sessions affected" bolna understanding hai.
Latency aur throughput mein kya rishta hai? Dono ek saath improve ho sakte hain?SDE-1/2

Answer: Latency ek request ka time hai, throughput per-second requests hai. Little's Law inhe jodta hai: L = λ × W.

Dono ek saath improve ho sakte hain sirf tab jab aap actual kaam kam karo — better index, kam payload, N+1 hatana, kam serialization. Ye "free" wins hain.

Par ek baar system efficient ho jaye, to dono ek dusre ke against trade hote hain: batching throughput badhata hai par wait add karta hai; utilization badhana throughput badhata hai par queueing latency exponentially badhati hai (W = S/(1−ρ)).

Signal: "Depends" bolna kaafi nahi. Free wins aur zero-sum tradeoffs ka fark batao — yahi answer ko strong banata hai.
Average latency 80ms hai par users bol rahe hain app slow hai. Kaise debug karoge?SDE-1/2

Answer — order matter karta hai:

  • Pehle percentiles dekho, average nahi. p99/p99.9 nikaalo. Average outliers chhupata hai.
  • Phir endpoint aur dimension se break karo — ho sakta hai ek endpoint (search) ya ek segment (bade accounts) hi slow ho.
  • Client-side latency check karo, server-side nahi. Server 80ms bole par TLS, DNS, LB queue aur mobile network milaake user ko 2s dikhe.
  • Queue wait alag se measure karo. Agar server-side timer request handling ke baad start hota hai to aap coordinated omission kar rahe ho.
  • Ek slow trace uthao aur poore span breakdown dekho — guess karna band karo.
Signal: Systematic funnel — user → network → edge → queue → app → DB. Randomly "cache laga dete hain" bolna red flag hai.
Thread pool size kaise decide karoge? "CPU cores × 2" theek hai?SDE-1/2

Answer: Depends ki work CPU-bound hai ya IO-bound.

  • CPU-bound: cores ya cores + 1. Isse zyada sirf context switching hai.
  • IO-bound: Little's Law se — threads = targetRps × avgLatencySeconds. 500 RPS × 0.2s = 100 threads, phir 1.3× headroom.

Par size se zyada important ye hai: pool bounded ho, queue bounded ho, aur rejection policy explicit ho. Unbounded queue wala 50-thread pool, bounded queue wale 500-thread pool se zyada khatarnak hai.

Signal: Formula ke saath bounds ka zikr. Sirf formula bolna aadha answer hai.
Downstream call ka timeout kitna rakhoge, aur wo number kahan se aayega?SDE-1/2

Answer: Timeout downstream ke observed p99 (ya p99.9) se thoda upar hona chahiye — jaise p99 × 1.5 — aur aapke apne latency budget ke andar fit hona chahiye. Dono constraints check karo; jo chhota ho wahi lo.

Round number (3s, 30s) kabhi mat lo. 30s timeout matlab 30s tak thread hold — matlab overload par cascade.

Behtar approach: fixed timeout ki jagah deadline propagate karo. Har hop ko bacha hua time milta hai, isliye 3 sequential calls milkar SLO nahi tod sakti.

Signal: Timeout ko data se derive karna, aur connect timeout vs read timeout ka fark pata hona.
Cache TTL 5 minute hai. Har 5 minute par latency spike aata hai. Kya ho raha hai?SDE-1/2

Answer: Cache stampede. Popular key expire hoti hai, saare concurrent requests miss hote hain, sab ek saath DB par jaate hain. Aur kyunki saari keys ek hi deploy par warm hui thi, wo ek saath expire hoti hain.

Fix (badhte hue effort ke saath): TTL jitter (±15%) → single-flight lock (ek recompute, baaki wait) → stale-while-revalidate → probabilistic early refresh.

Sabse sasta fix jitter hai aur wo aksar 80% problem solve kar deta hai — ek line ka change.

Signal: Solution ko cost ke order mein batana. Seedha "distributed lock lagayenge" bolna over-engineering hai.
Aapke paas 2 hafte hain aur p99 aadha karna hai. Kahan se shuru karoge?SDE-1/2

Answer — sabse zyada return dene wale kaam pehle:

  • Naapo: tail-based tracing on karo, ek din ke slow traces dekho. Aksar 70% tail ek hi jagah se aata hai.
  • N+1 queries dhoondo — ye lagbhag hamesha milte hain aur fix sasta hota hai.
  • Missing index — DB slow query log 10 minute mein bata dega.
  • Payload size ghatao — response mein aadhe fields kabhi use hi nahi hote.
  • Timeouts kaso — 30s timeout ko 1s karna p99.9 turant theek karta hai.

Jo nahi karna: naya cache layer, service split, ya framework change. 2 hafte mein wo risk hai, fix nahi.

Signal: Pragmatism. Interviewer dekh raha hai ki aap constraint ke andar prioritise kar sakte ho ya har baar rewrite propose karte ho.
Har service ka p99 = 100ms hai. Page 10 services ko parallel call karta hai. Page ka p99 kya hoga?SDE-3

Answer: Page ka p99, service ke p99 se bahut bura hoga — kyunki page sabse slow response ka wait karta hai.

P(kam se kam ek call > 100ms) = 1 − 0.99^10 = 9.6%. Matlab ~10% requests 100ms cross karengi, to page ka p90 hi 100ms hai. Page ka p99 nikalne ke liye aapko har service ka p99.9 dekhna padega.

Fix architecture level par hai: fan-out ghatao (denormalised read model), optional calls ko degrade karo, deadline propagate karo. Har service ka p99 chase karna infinite regress hai.

Signal: Math karke dikhana, aur phir bolna ki fix per-service tuning nahi balki fan-out reduction hai. Yahi SDE-3 signal hai.
Downstream ne 30 second ke liye 5% error diye aur poora system 20 minute down ho gaya. Kya hua?SDE-3

Answer: Retry storm → metastable failure. 5% errors par sabne retry kiya, load 3× hua, service aur girti gayi, aur error rate badhne se retries aur badhe. Original trigger hat jaane ke baad bhi system apne hi retry load se down raha.

Rokne ke liye:

  • Retry budget — retries ≤10% of requests. Ye storm ko mathematically impossible banata hai.
  • Full jitter backoff — synchronised herd todta hai.
  • Circuit breaker — dying service ko recover hone ka space deta hai.
  • Ek hi layer par retry. Nested retries multiply hote hain (3×3×3 = 27).

Recovery: traffic band karo (load shed / feature flag), service ko warm hone do, phir dheere-dheere ramp karo. Bina traffic ghataye system apne aap nahi nikalega — yahi metastable state ki definition hai.

Signal: "Metastable" word bolna, aur ye samajhna ki recovery ke liye load actively ghatana padta hai.
Load test bolta hai p99 = 90ms, production bolta hai p99 = 4s. Same code, same hardware.SDE-3

Answer — sabse pehla suspect: coordinated omission. Closed-loop load generator response ka wait karke agli request bhejta hai. Server stall hone par generator ne requests bheji hi nahi — matlab jo requests sabse slow hoti, wo record hi nahi hui.

Doosre real differences: production ka data volume aur cardinality alag hai; cache hit ratio alag hai (test mein 5 keys, prod mein 5 million); traffic pattern burst-y hai, smooth nahi; aur prod mein noisy neighbours hain.

Fix: open-loop model (constant arrival rate), intended-start-time se latency measure karo, production-shaped data use karo, aur burst inject karo — flat load nahi.

Signal: Coordinated omission naam se pehchanna. Ye ek clean senior-level discriminator hai.
Batching se throughput 4× hua par p99 200ms badh gaya. Rakhein ya hataayein?SDE-3

Answer: Ye product question hai, engineering question nahi — par engineer ke paas iska structured jawab hona chahiye.

  • Latency budget check karo: agar SLO 400ms hai aur ab p99 350ms hai, to rakho. Agar 450ms ho gaya, hatao.
  • Cost quantify karo: 4× throughput ka matlab 4× kam pods. Wo dollars hain — number lekar aao.
  • Dono lena hai to: linger time ghatao (10ms), size-or-time dual trigger lagao, aur latency-sensitive traffic ke liye batching bypass karo (priority flag).

Ideal answer: "Main linger ko itna set karunga ki added latency budget ke andar rahe, aur throughput ka jo bhi hissa us constraint mein milta hai wo le lunga." Batching binary nahi, tunable hai.

Signal: Yes/no ki jagah tunable knob dhoondhna, aur cost ko numbers mein rakhna.
Connection pool 20 se 200 kiya, ab har query slow hai. Explain.SDE-3

Answer: Aapne queue app se DB par shift kar di. DB ke paas fixed cores aur fixed IO hai — 200 concurrent queries ka matlab context switching, lock contention aur buffer pool pressure. Har query ab dheere chalti hai, aur total throughput bhi gir sakta hai.

Plus: 50 pods × 200 = 10,000 connections. Postgres har connection par ek backend process aur ~10MB memory leta hai — DB memory pressure mein aa jaata hai.

Sahi approach: pool chhota rakho ((2 × cores) + spindles, fleet-wide), connection timeout chhota (250ms), aur multi-pod setup mein PgBouncer lagao. Queue app-side rakhna behtar hai kyunki wahan aap dekh sakte ho, priority de sakte ho aur shed kar sakte ho.

Signal: "Queue kahin nahi jaati, sirf shift hoti hai" — ye insight bolna. Aur ye samajhna ki chhota pool aksar zyada throughput deta hai.
Order save karne ke baad Kafka event bhejna hai. "Commit karo phir publish" mein kya galat hai?SDE-3

Answer: Dual-write problem. Do alag systems ko atomically likhna possible nahi hai. Commit ke baad app crash hua to order exist karta hai par event kabhi nahi gaya — inventory update nahi hua, email nahi gaya, permanently inconsistent.

Ulta order (publish phir commit) aur bura hai: event chala gaya par transaction rollback ho gaya — downstream ek aise order ko process kar raha hai jo exist hi nahi karta.

Fix — Transactional Outbox: business row aur event row ek hi DB transaction mein likho. Ek relay (polling with SKIP LOCKED, ya Debezium CDC) outbox se padh kar publish karta hai. Delivery at-least-once hoti hai, isliye consumers event id par dedupe karein.

Alternative: listen-to-yourself (event se hi state banao) ya event sourcing — par outbox sabse kam invasive hai.

Signal: At-least-once ka zikr aur consumer idempotency. Sirf "outbox lagayenge" bolna aadha answer hai.
User ne profile update kiya, refresh kiya, purana data dikha. Cache + read replica dono hain. Fix?SDE-3

Answer — do alag staleness sources hain, dono handle karo:

  • Cache: write ke afterCommit par invalidate karo, update nahi. Update karne mein race hai (purana reader naya cache overwrite kar deta hai).
  • Replica lag: write ke baad short window (jaise 5s) tak us user ko primary se padho. Session mein last-write timestamp ya LSN rakho.

Behtar pattern — read-your-writes: write ke response mein version/LSN wapas bhejo, client agli read mein wo bheje, aur server ya to us version tak wait kare ya primary par jaye.

Sabse sasta hack: write ke response mein hi updated object lauta do, taaki client ko refetch karna hi na pade. Ye 80% cases solve kar deta hai.

Signal: Cache staleness aur replica lag ko alag-alag problem maanna, aur sabse sasta fix pehle propose karna.
Poore checkout flow ka p99 SLO 400ms hai, 6 services involved hain. Budget kaise allocate karoge?Staff

Answer — top-down, additive nahi:

  • User-facing SLO 400ms se shuru. Network aur TLS ke liye ~80ms reserve — app ke paas 320ms bacha.
  • Critical path map karo. Sequential hops add hote hain; parallel hops mein max lagta hai. Sirf sequential chain par budget baanto.
  • Har hop ko budget do uske p99 ke hisaab se, average ke nahi: gateway 20, BFF 40, order 120, payment 100, DB 40 = 320.
  • 10–20% slack chhodo. Bina slack ke koi bhi ek regression SLO tod dega.
  • Har hop ka budget uska timeout ban jaata hai, aur deadline header se propagate hota hai.
  • Fir error budget define karo: 30 din mein 1% requests SLO cross kar sakti hain. Ye release velocity ko control karta hai.

Aur ek important bat: agar allocation possible hi nahi ho rahi, to architecture badalna padega (fan-out ghatao, precompute karo) — budget ko wishful thinking se nahi bhara ja sakta.

Hedged requests kab lagaoge, kab bilkul nahi? Cost kya hai?Staff

Lagao jab: operation idempotent read ho, latency variance zyada ho (p99 >> p50), multiple replicas available hon, aur slowness random ho (koi deterministic slow query nahi).

Mat lagao jab: writes hon ya non-idempotent operations, system already saturated ho, replicas na hon, ya p99/p50 ratio chhota ho (tab hedging sirf load badhata hai).

Cost: ~5% extra load agar threshold p95 par ho. Par asli risk ye hai ki overload ke waqt hedging load double karke cascade bana deti hai — isliye hedging ko health signal se gate karna mandatory hai, optional nahi.

Behtar variant: "tied requests" — dono replicas ko batao ki doosra bhi try kar raha hai, jo pehle uthaye wo doosre ko cancel kar de. Duplicate work aur kam ho jaata hai.

Signal: Hedging ko conditional treat karna aur overload interaction ko khud se uthana. Ye wo detail hai jo sirf production experience se aati hai.
Load shedding design karo. Kya shed karoge aur kaise decide karoge ki ab shed karna hai?Staff

Kab shed karna hai — signal: fixed RPS threshold mat lo (real capacity badalti rehti hai). Latency gradient use karo: observed latency / best-known latency. Ratio badha matlab queue ban rahi hai. Ye adaptive hai aur payload ya cache state badalne par apne aap adjust hota hai.

Kya shed karna hai — priority order:

  • Pehle dead requests (client deadline nikal chuki) — ye free capacity hai.
  • Phir background / bulk traffic: analytics, prefetch, reporting.
  • Phir optional enrichment: recommendations, reviews, badges.
  • Aakhir mein standard reads.
  • Kabhi nahi: checkout, payment, auth, health checks.

Kaise shed karna hai: 429 + Retry-After jitter ke saath. Silently drop mat karo — client ko backoff ka signal chahiye.

Aur ek cheez: shedding ko har layer par mat lagao, warna aap same request ko 4 baar reject karoge. Edge par ya ek admission point par lagao.

Signal: Goodput vs throughput ka fark, dead-request drop, aur priority classification. Agar aap "429 with Retry-After" bolte ho to client ke bare mein soch rahe ho — accha sign.
Aapki service ka p99 200ms hai, par usse 50ms lane mein 6 mahine aur 3 engineers lagenge. Kya karoge?Staff

Answer: Pehle poochho — kyun 50ms chahiye? Aksar ye number kisi ne feeling se rakh diya hota hai.

  • Business impact measure karo: A/B test karo artificial delay ke saath. Agar 200ms → 250ms se conversion nahi girta, to 200ms → 50ms ka business case hi nahi hai.
  • Perceived latency dekho: optimistic UI, skeleton screens, prefetch. 200ms ko 50ms feel karana aksar 6 mahine ke backend kaam se sasta hai.
  • Agar number sach mein zaroori hai (bidding, trading), to architecture badlo — precompute, in-memory, edge par le jao. Incremental tuning 4× improvement nahi deti.

Traffic normal ho gaya par system abhi bhi down hai. Restart karne par 2 minute chalta hai phir gir jaata hai. Diagnosis?Staff

Answer: Ye metastable failure hai. System ek aise stable state mein phans gaya hai jahan wo apna hi load generate kar raha hai. Trigger ja chuka hai, par sustaining loop chal raha hai.

Common sustaining loops: retry amplification; cold cache (miss → DB load → slow → timeout → retry → aur miss); connection storm on restart; queue backlog jo poora hone se pehle hi expire ho jaata hai (100% dead work).

Recovery — load ghatana zaroori hai, capacity badhana kaafi nahi:

  • Traffic aggressively shed karo (feature flags, edge par rate limit, non-critical band).
  • Cache pre-warm karo traffic wapas dene se pehle.
  • Retries temporarily disable karo.
  • Traffic ko dheere ramp karo — 10%, 25%, 50%. Ek saath 100% dena wapas usi state mein le jayega.
  • Queues drain karo ya expired items drop karo.

Prevention: retry budgets, bounded queues, admission control, aur regular cold-start drills.

Signal: Ye samajhna ki "trigger hat gaya" ka matlab "recover ho jayega" nahi hota, aur recovery plan mein ramp ka hona.
p99.9 ko p99 se alag treat karna chahiye? Kahan line kheenchoge?Staff

Answer: Haan, kyunki inke causes alag hain aur cost curve alag hai.

  • p50–p90 aapka normal code path hai. Yahan fix algorithmic hai: index, N+1, payload, serialization.
  • p99 aksar contention hai: queueing, pool waits, lock contention, cache miss.
  • p99.9+ lagbhag hamesha infrastructure jitter hai: GC pause, kernel scheduling, network retransmit, disk hiccup, noisy neighbour, deploy events.

Isliye p99.9 ko code se fix karna bahut mehnga hai; usse redundancy se fix kiya jaata hai — hedging, retry on a different node, brownout-aware routing.

Line kahan: user-facing SLO p99 par rakho (measurable, actionable, achievable). p99.9 ko internal engineering metric ki tarah track karo, aur uska paisa tabhi kharch karo jab request volume itna ho ki 0.1% bhi bada number ho — jaise 1B requests/day par 1M unhappy requests.

Signal: Percentile bands ko alag causes se map karna. Ye ek framework hai, list nahi — interviewers isko yaad rakhte hain.
Sync se async karne se p99 gir gaya. Kya ye "asli" improvement hai?SDE-3

Answer: Aadha. API ka p99 sach mein gira — user ko response jaldi mil raha hai, aur ye real user-facing win hai.

Aap p99 kaise measure karoge across 20 pods? Har pod ka p99 average kar sakte hain?SDE-1/2
