Authentication vs Authorization: 401 aur 403 ka farak

Beginner

✗ Problem

Bahut log sochte hain ki user login ho gaya matlab woh kuch bhi kar sakta hai. Neeche wale code me sirf itna check hai ki user logged in hai ya nahi. Result: ek normal user bhi admin API se kisi ka bhi account delete kar sakta hai.

  1. Ye sirf authentication check hai: 'tum kaun ho'. Role ka koi check nahi. Aur RuntimeException se client ko 500 milega, 401 nahi.
  2. Koi bhi logged-in user kisi ka bhi account delete kar sakta hai. Seedha security bug.

✓ Solution

Authentication = identity prove karna (password, Google login, JWT). Fail ho toh 401 Unauthorized.

Authorization = permission check (role, ownership). Identity valid hai par permission nahi, toh 403 Forbidden.

Office analogy: gate pe ID card dikhana authentication hai. Andar jaake sirf apne floor ka door khulna authorization hai.

  1. Saare admin endpoints ek base path /api/admin/users ke neeche, taaki SecurityConfig me /api/admin/** ek jagah se lock ho sake (Topic 7).
  2. Constructor injection: dependency final hai aur test me mock pass karna easy.
  3. Method chalne se pehle check. User ke paas ROLE_ADMIN nahi hai toh method run hi nahi hoga, 403 milega. Iske liye @EnableMethodSecurity on hona chahiye.
  4. Naming: verb + noun + criteria. deleteUserById padhte hi samajh aata hai method kya karega.
  5. 204 No Content: delete ho gaya, body bhejne ki zarurat nahi.

Tradeoff: Permission na ho toh 403 bhejein ya 404?

403 honest hai: resource hai, par tumhe allowed nahi. 404 resource ka existence bhi chhupata hai.

✓ Kab apply karein
  • 403: admin ya internal APIs me, jahan clear error se debugging fast hoti hai.
  • 404: kisi aur user ke private resource (order, document) pe, taaki 'ye exist karta hai' bhi leak na ho.
✗ Kab ignore karein
  • 404 wali trick tab ignore karo jab resource ID pehle se public hai (jaise product page). Chhupane ko kuch hai hi nahi.
  • Token missing ya expired hone pe kabhi 403 mat bhejo. Wahan 401 chahiye, taaki frontend refresh ya login flow chalaye.

Password ko database me kaise save karein: hashing with BCrypt

Beginner

✗ Problem

Password plain text me save kiya aur database leak hua (backup, SQL injection, galat access) toh attacker ko sabke passwords seedhe mil jayenge. Log wahi password Gmail aur bank me bhi use karte hain, isliye nuksaan sirf tumhari app tak nahi rukta.

  1. DB me riya@123 jaisa hi dikhega. Ek leak = saare accounts compromised.
  2. MD5/SHA fast algorithms hain: GPU ek second me arabon guesses try kar leta hai. Salt nahi hai toh same password ka hash sabke liye same, aur rainbow tables se turant crack.

Encryption bhi galat choice hai. Encryption reversible hai: key leak hui toh saare passwords decrypt ho jayenge.

✓ Solution

Password ke liye one-way, slow, salted hash chahiye. Spring Security me PasswordEncoder interface hai: encode() hash banata hai, matches() verify karta hai. Default algorithm BCrypt hai.

  • Salt: har password ke saath random value mix hoti hai. Do users ka password riya@123 ho, fir bhi hash alag.
  • Cost factor: BCrypt jaan-boojh ke slow hai (cost 10 = 2¹⁰ rounds). User ko ek baar ~0.1 sec lagta hai, attacker ko har guess pe.
  • BCrypt salt ko hash string ke andar hi store karta hai, alag column ki zarurat nahi.
  1. PasswordEncoder alag config class me. SecurityConfig ke andar banane se kabhi-kabhi circular dependency aa jati hai.
  2. Default BCrypt use karta hai aur hash ke aage {bcrypt} id lagata hai. Kal Argon2 pe shift karoge toh purane hashes bhi verify hote rahenge.
  3. Har call pe naya random salt, isliye same password ka hash har baar alag aata hai.
  4. Stored hash se salt aur cost padh ke raw password ko same tarike se hash karta hai aur compare karta hai. encode(raw).equals(stored) kabhi mat likhna: woh hamesha false aayega.

Database me kuch aisa save hota hai:

  1. {bcrypt} algorithm id, $2a$ BCrypt version, 10 cost, agle 22 characters salt, baaki 31 characters asli hash.

Tradeoff: BCrypt vs Argon2id vs PBKDF2

Teeno safe hain agar settings sahi hon. Farak attacker ke hardware aur tumhari compliance needs me hai.

✓ Kab apply karein
  • BCrypt (cost 10–12): zyada tar apps ke liye. Spring default, har jagah tested.
  • Argon2id: naya high-security system jahan GPU cracking ka dar hai. Memory-hard hai aur OWASP ki pehli pasand.
  • PBKDF2: jab FIPS-140 compliance zaroori ho (government, kuch banks).
✗ Kab ignore karein
  • Argon2id tab skip karo jab server memory tight hai: har login kaafi RAM leta hai, peak traffic ki capacity planning karni padegi.
  • BCrypt sirf pehle 72 bytes padhta hai. Bahut lambe passphrases allow karne hain toh max length validate karo ya Argon2id lo.
  • MD5, SHA-1, plain SHA-256 aur encryption: password ke liye hamesha ignore.

User entity aur table design: duplicate aur leak se bachao

Beginner

✗ Problem

Table design ki chhoti galtiyan baad me bade bugs banti hain:

  • email pe unique constraint nahi, toh duplicate accounts ban jate hain.
  • Riya@Mail.com aur riya@mail.com alag maan liye gaye: ek insaan ke do accounts.
  • Password column length = 50, jabki BCrypt hash {bcrypt} ke saath 68 characters ka hai. Hash kat gaya, login hamesha fail.
  • Entity ka naam User: PostgreSQL me user reserved word hai aur Spring Security ki User class se naam clash hota hai.
  1. Na unique, na not-null. Duplicate aur khaali email dono possible.
  2. Hash truncate ho jayega.
  3. Ek hi role string. Kal user ko USER + SUPPORT dono dene hon toh redesign.

Aur agar controller seedha entity return kare, toh JSON response me password hash bhi chala jayega.

✓ Solution

Entity ka naam UserAccount, table users. Email unique, hash ke liye kaafi length, roles alag table me, aur API ke liye alag DTO.

  1. Class UserAccount, table users: reserved word user aur Spring ki User class, dono se bache.
  2. unique = true sirf tab kaam aata hai jab Hibernate schema banaye. Production me asli guard SQL migration wala UNIQUE constraint hai (LLD me). 254 email ki practical max length hai.
  3. Nullable: Google se login karne wale user ka local password hota hi nahi.
  4. Login pe roles turant chahiye aur list chhoti hai, isliye EAGER. Badi collections ke liye LAZY rakho.
  5. Admin kisi user ko disable kare toh login pe Spring khud rok dega (Topic 5).
  6. Password change ya 'logout from all devices' pe +1 hoga, aur purane JWT reject ho jayenge (Topic 13).
  7. Optimistic locking: do log ek saath update karein toh ek fail hoga, chupchap overwrite nahi hoga (Topic 13).
  8. JPA ko no-arg constructor chahiye. protected rakha taaki baaki code galti se khaali object na banaye.
  9. Static factory with clear name: object hamesha valid state me banta hai, setters ki bheed nahi.
  10. Roles ko ROLE_USER jaise strings me convert: Spring Security isi format ko samajhta hai.
  1. Record = immutable DTO. Isme password ya roles field hi nahi, toh leak ho hi nahi sakta.
  2. Mapping ek jagah. Controller kabhi entity return nahi karega.

Tradeoff: Email normalize app me karein ya database me?

Case-insensitive uniqueness ke do raaste hain.

✓ Kab apply karein
  • App me normalize (trim().toLowerCase(Locale.ROOT)) + normal unique index: simple, har DB pe chalta hai. Default yahi.
  • DB level (PostgreSQL me LOWER(email) pe unique index ya citext type): jab kai services ek hi table me likhti hon aur koi normalize karna bhool sakti ho.
✗ Kab ignore karein
  • MySQL ki default collation (utf8mb4_0900_ai_ci) pehle se case-insensitive hai, wahan functional index ki zarurat nahi.
  • Gmail ke dots hatana (r.iya@gmail.com → riya@gmail.com) jaisi provider-specific normalization ignore karo. Har provider pe ye sahi nahi hai.

Register: user exist check fast karo, phir save, warna 'already exists'

Intermediate

✗ Problem

Seedha tareeka: findByEmail karo, mila toh 'already exists', warna save. Dikhne me sahi hai, par isme kai problems chhupi hain:

  1. Sirf 'hai ya nahi' janna tha, par poora entity (saare columns + roles) load ho gaya.
  2. HTTP 200 ke saath ek string. Client ko pata hi nahi chalega ki error hai. Sahi status 409 Conflict hai.
  3. Password bina hash ke save.
  4. Race condition: do requests same email ke saath ek hi millisecond me aayi, dono ne 'nahi hai' dekha, dono save kar dengi.
  • Email pe index nahi hai toh 1 crore rows me full table scan.
  • Riya@Mail.com (space + capital letters) check se bach ke nikal jata hai.

✓ Solution

Teen layers me socho:

  1. Fast check existsByEmail(): sirf boolean, index se lookup. Duplicate mila toh mehenga BCrypt hashing skip.
  2. Truth guard DB ka UNIQUE constraint: race me bhi sirf ek INSERT jeetega.
  3. Graceful error: constraint violation pakdo aur UserAlreadyExistsException se 409 Conflict bhejo.
  1. Spring Data method ke naam se query banata hai jo sirf ek row tak dekhti hai aur entity load nahi karti. Unique index hai toh B-tree lookup: 1 crore rows me bhi kuch hi page reads.
  2. Login ke liye poora user chahiye, wahan findByEmail sahi hai.
  1. Poora register ek transaction: role assign aur user insert saath me commit ya saath me rollback.
  2. Pehle normalize, phir check. Warna Riya@Mail.com duplicate ban jayega.
  3. Sasta check pehle. Duplicate mila toh yahin exit, aur BCrypt ka ~100 ms CPU bach gaya.
  4. Hashing sirf naye user ke liye.
  5. Factory method se hamesha valid user object.
  6. saveAndFlush INSERT turant DB ko bhejta hai, taaki constraint error isi try ke andar aaye. Sirf save hota toh (SEQUENCE ids ke saath) INSERT commit tak ruk sakta tha aur exception method ke bahar aata.
  7. Race case: dono requests ne check pass kiya, par DB ne doosra INSERT reject kar diya. User ko 500 nahi, wahi 409. Production me constraint name (uk_users_email) bhi check karo taaki doosre errors galat map na hon.
  8. Locale.ROOT zaroori hai: Turkish locale me I ka lowercase alag hota hai aur same email alag ban jata.
  1. @Valid DTO ke annotations chalata hai. Galat input pe 400, service tak request pahunchti hi nahi.
  2. Naya resource bana: 201 Created.
  3. Min length security ke liye. Max isliye ki BCrypt 72 bytes ke baad ignore karta hai aur bahut lamba input CPU bhi khata hai.
  4. Saare controllers ke exceptions ek jagah handle.
  5. Spring 6 ka standard error format (RFC 9457): status, title, detail. Frontend ke liye consistent.

Tradeoff: Pehle check karein ya seedha INSERT karke exception pakdein?

Har approach me DB ka UNIQUE constraint compulsory hai. Farak performance aur code clarity me hai.

✓ Kab apply karein
  • existsBy + UNIQUE + catch (upar wala): default choice. Duplicates pe hashing bachata hai, code padhne me clear.
  • Seedha INSERT + catch: bahut high signup traffic jahan duplicates rare hain. Ek DB round-trip kam.
  • PostgreSQL INSERT … ON CONFLICT (email) DO NOTHING RETURNING id: exception ke bina duplicate pata chalta hai, par native query likhni padegi.
✗ Kab ignore karein
  • Sirf existsBy check (bina UNIQUE constraint) wala approach hamesha ignore karo: race condition me duplicate pakka banega.
  • High-privacy apps (dating, health) me '409 already exists' bhi batata hai ki ye email registered hai. Wahan 409 ignore karke generic message + verification email bhejo.

Login ke andar kya hota hai: AuthenticationManager flow

Intermediate

✗ Problem

Beginners apna khud ka login likhte hain. Isme teen dikkat hain: hash ko equals se compare (hamesha fail), alag-alag error messages se attacker ko pata chal jata hai ki email registered hai (user enumeration), aur disabled ya locked account ke checks chhoot jate hain.

  1. Attacker emails try karke registered users ki list bana sakta hai.
  2. Hash aur raw password kabhi equal nahi honge. Plain equals timing se info leak bhi kar sakta hai.
  3. Na token, na session. Agli request pe user phir anonymous.

✓ Solution

Spring Security ka ready flow use karo. Tumhe sirf batana hai ki user DB se kaise aayega (UserDetailsService).

  1. AuthController.loginUser() → AuthenticationManager.authenticate()
  2. ProviderManager → DaoAuthenticationProvider
  3. DatabaseUserDetailsService.loadUserByUsername(email) → DB se hash + roles
  4. PasswordEncoder.matches(raw, hash) + enabled/locked checks
  5. Success pe authenticated Authentication. Fail pe BadCredentialsException → 401
  1. Spring ko bas yahi interface chahiye. Iska bean bana toh Spring Boot khud isko DaoAuthenticationProvider me laga deta hai.
  2. Wahi normalization jo register me kiya, warna Riya@Mail.com se login fail hoga.
  3. Google-only user (password NULL) password login nahi kar payega.
  4. Spring ise andar hi BadCredentialsException bana deta hai, taaki 'email nahi mila' aur 'password galat' ka response ek jaisa ho.
  5. Ye Spring Security ki User class hai (isi liye hamari entity ka naam UserAccount rakha). Hash, roles aur enabled flag Spring ko de diye; password compare Spring khud karega.
  1. Poora flow yahan chalta hai. Galat password pe exception, method aage badhta hi nahi.
  2. Abhi ye sirf ek 'claim' hai: email + raw password. Verified nahi.
  3. Success pe access token (JWT) + refresh token issue (Topic 6 aur 8).

DaoAuthenticationProvider user na milne par bhi ek dummy password hash karta hai, taaki response time dekh ke attacker ko pata na chale ki email exist karta hai.

Tradeoff: Generic error message vs helpful message

✓ Kab apply karein
  • Login pe hamesha generic message: 'Invalid email or password'.
  • 'Forgot password' pe bhi ek jaisa response: 'Agar account hai toh reset link bhej diya'.
✗ Kab ignore karein
  • Chhote internal admin tool (company VPN ke andar) me helpful message chal sakta hai, risk kam hai.
  • Registration pe 409 aksar accept hota hai (Topic 4) kyunki UX zyada important hai; sensitive apps me wahan bhi generic rakho.

Session vs JWT: token kaise banta aur verify hota hai

Intermediate

✗ Problem

Classic session me login ke baad server memory me session banta hai aur browser ko JSESSIONID cookie milti hai. Ek server tak sab theek hai.

  • 5 instances load balancer ke peeche: login instance 1 pe hua, agli request instance 3 pe gayi, wahan session hi nahi. User logout.
  • Sticky sessions lagao toh load uneven, aur instance restart pe us par wale sab users logout.
  • Mobile apps aur doosri microservices ke liye cookie-based session awkward hai.

✓ Solution

JWT (JSON Web Token) ek signed token hai: header.payload.signature. Server signature verify karke user pehchan leta hai, DB ya session store dekhe bina. Isliye koi bhi instance request handle kar sakta hai.

  1. Kis algorithm se sign hua. Server ko hamesha apna expected algorithm enforce karna chahiye, token ki baat nahi maanni.
  2. Payload sirf Base64URL encoded hai, encrypted nahi. Koi bhi padh sakta hai, isliye password, PAN ya phone yahan kabhi nahi. exp − iat = 900 sec = 15 min.
  3. Payload me ek character bhi badla toh signature match nahi karega. Isi se tampering pakdi jati hai.
  1. Secret code me hardcode nahi, environment variable ya secrets manager se. Banane ke liye: openssl rand -base64 32 (256-bit).
  2. Access token 15 minute ka. :PT15M default hai jo config se override ho sakta hai.
  3. 256 bit se chhoti key pe JJWT WeakKeyException deta hai. Kamzor secret brute-force ho sakta hai.
  4. sub = user kaun hai. Kai teams yahan immutable user id rakhti hain, taaki email change hone pe confusion na ho.
  5. Roles authorization ke liye, tv (token version) revocation ke liye (Topic 13).
  6. Key size dekh ke JJWT HS256 chunta hai aur signature lagata hai.
  7. Signature galat, token expire ya format kharab ho toh JwtException. Sab theek hai toh claims milte hain.

Tradeoff: JWT kab, session kab?

✓ Kab apply karein
  • JWT: mobile app, SPA, multiple backend instances ya microservices jahan har service khud token verify kare.
  • JWT: doosri services ya partners ko short-lived access dena.
✗ Kab ignore karein
  • JWT tab ignore karo jab ek hi server-rendered monolith web app hai: session + Spring Session (Redis) simple hai aur logout turant hota hai.
  • Agar har request pe DB se user check karna hi hai, toh stateless JWT ka main fayda chala gaya. Wahan session bhi utna hi achha hai.

JWT filter aur SecurityConfig: har request pe token check

Intermediate

✗ Problem

Har controller me header se token nikalna repeated code hai. Ek endpoint me bhool gaye toh wahi security hole ban jata hai.

  1. Header chhota ya galat format ka hua toh exception aur 500 error.
  2. Signature aur expiry verify nahi hui: koi bhi fake token bana ke kisi ka bhi profile dekh sakta hai.
  3. Aur ye sab har controller method me copy-paste hoga.

✓ Solution

Ek OncePerRequestFilter banao jo Spring Security filter chain me har request pe chale: token verify kare aur SecurityContext me user set kare. Controllers ko bas @PreAuthorize ya Authentication chahiye.

  1. Guarantee: ek request me filter ek hi baar chalega.
  2. Token nahi hai toh chupchap aage bhejo. Public endpoints (/register) chalte rahenge; protected endpoints pe Spring baad me 401 dega.
  3. Signature + expiry check. Yahan koi DB call nahi: stateless.
  4. Verified user ka Authentication object. Credentials null, kyunki ab password ki zarurat nahi.
  5. Iske baad controller, @PreAuthorize aur Authentication parameter, sabko user pata hai.
  6. Invalid ya expired token pe context clear. Response 401 entry point dega (config me).
  7. JWT ke roles claim ko Spring authorities me convert. Null-safe, taaki bina roles wale token pe crash na ho.
  1. @PreAuthorize isi se kaam karta hai.
  2. CSRF attack browser ki automatic cookies ka fayda uthata hai. Hum token Authorization header me bhej rahe hain (cookie nahi), isliye yahan disable karna safe hai.
  3. Spring HttpSession nahi banayega. Har request apna token khud laati hai.
  4. Sirf ye teen endpoints bina token ke. Rules upar se neeche match hote hain: specific pehle, anyRequest() sabse last.
  5. URL level pe coarse lock. Andar method level check bhi lagega (Topic 12).
  6. Token nahi ya galat hai toh clean 401. Login page pe redirect nahi, kyunki ye API hai, browser page nahi.
  7. Hamara JWT filter Spring ke username/password filter se pehle chalega.
  8. Login controller ke liye AuthenticationManager. Spring isme DatabaseUserDetailsService + PasswordEncoder khud jod deta hai.

Tradeoff: Har request pe sirf JWT verify karein, ya DB/cache se user bhi check?

✓ Kab apply karein
  • Sirf JWT verify: high-traffic read APIs, jahan 15 min tak purana role chal sakta hai.
  • tv claim ko Redis cache se match: jab password change ya ban turant effective chahiye, par DB pe load nahi dalna (Topic 13).
  • DB se fresh user: money transfer, admin actions jaise critical endpoints.
✗ Kab ignore karein
  • Har request pe DB lookup sab endpoints pe mat lagao: 10k RPS pe DB hi bottleneck ban jayega.
  • Filter pe @Component hai toh Spring Boot use servlet filter bhi register karta hai. OncePerRequestFilter double-run rok leta hai; strict setup chahiye toh FilterRegistrationBean se servlet registration disable karo.

Refresh token, rotation aur logout

Architect

✗ Problem

  • Access token 7 din ka rakha aur chori ho gaya: attacker 7 din tak access me, server kuch nahi kar sakta.
  • Access token 15 min ka rakha: user ko har 15 min me dobara login. Bura UX.
  • Logout pe frontend ne token delete kiya, par chori hui copy ab bhi valid hai.
  • Refresh token DB me plain text: DB leak = sabke sessions hijack.

✓ Solution

Do tokens: access token (JWT, 15 min, har API call pe) aur refresh token (random string, 14 din, sirf /api/auth/refresh pe). Refresh token DB me sirf SHA-256 hash ke roop me.

  • Rotation: har refresh pe purana token revoke, naya issue. Ek refresh token sirf ek baar chalega.
  • Reuse detection: revoked token dobara aaya matlab kisi ne chori kiya. User ke saare refresh tokens revoke.
  • Logout: refresh token revoke. Access token max 15 min me khud expire (turant chahiye toh tokenVersion +1).
  1. 14 din baad dobara login. Sensitive apps me isko chhota rakho.
  2. Random nahi, SecureRandom: iski value predict nahi ho sakti.
  3. Raw token sirf client ko jata hai, DB me sirf hash. DB leak ho bhi jaye toh tokens use nahi ho sakte.
  4. Reuse pe hum 'revoke all' karke exception phenkte hain. noRollbackFor ke bina transaction rollback hota aur revoke bhi undo ho jata.
  5. Hash se lookup. BCrypt yahan nahi chalega: har baar random salt, toh hash se dhoondh hi nahi paoge. Token 256-bit random hai, isliye fast SHA-256 kaafi hai.
  6. Revoked token wapas aaya = chori ka signal. User ke saare sessions khatam, user dobara login karega.
  7. Rotation: purana band, naya issue. Controller naya access token JwtTokenService se banayega.
  8. 32 bytes = 256 bits randomness, URL-safe Base64 me.
  1. Bulk UPDATE ek hi SQL me. Har token load karke save karne se kahin fast.
  2. Password change, logout-all aur reuse detection, teeno me yahi method.

Browser me refresh token HttpOnly; Secure; SameSite=Strict cookie me rakho, path /api/auth/refresh. Mobile app me Keychain (iOS) ya Keystore (Android).

Tradeoff: Rotation strict rakhein ya grace period dein?

Do browser tabs ek saath refresh karein toh doosri request ko abhi-abhi revoked token dikhega, aur reuse detection user ko logout kar dega.

✓ Kab apply karein
  • Strict rotation: banking, admin panels. Kabhi-kabhi galat logout chalega, security pehle.
  • Chhota grace period (10–30 sec) ya client pe ek hi refresh call ka lock: consumer apps jahan multiple tabs common hain.
  • Redis me refresh tokens: bahut high volume ho, TTL se auto-expiry chahiye.
✗ Kab ignore karein
  • Refresh token ko JWT banana ignore karo jab DB me check karna hi hai: random opaque string simple aur chhoti hai.
  • Pure SPA jahan backend cookie set nahi kar sakta, wahan long-lived refresh token localStorage me mat rakho; BFF (backend-for-frontend) pattern socho.

OAuth 2.0 basics: roles, flows aur OIDC

Intermediate

✗ Problem

Pehle kai apps 'contacts import' ke liye tumhara Gmail password maangti thin. App ke paas poore account ka access, aur sirf us ek app ka access band karne ka koi tareeka nahi.

Aaj bhi ye confusion common hai:

  • 'OAuth = login'. Asal me OAuth authorization ke liye hai; login (identity) ke liye OIDC hai.
  • 'JWT = OAuth'. JWT sirf ek token format hai, OAuth ek framework aur flows ka set.
  • Frontend me seedha access token lena (Implicit flow), jo ab deprecated hai.

OAuth 2.0 delegated authorization hai: user apna password sirf Authorization Server ko deta hai, app ko sirf limited aur revoke ho sakne wala token milta hai.

  • Resource Owner: user (Riya).
  • Client: hamari Spring Boot app.
  • Authorization Server: Google, Keycloak, Okta. Login karwata hai aur tokens deta hai.
  • Resource Server: woh API jiske paas data hai (Google Calendar API ya hamari Orders API).
Authorization Code flow (+ PKCE), step by step
  1. User 'Login with Google' dabata hai. App browser ko Google ke /authorize pe bhejti hai: client_id, redirect_uri, scope=openid email profile, state, code_challenge.
  2. User Google pe login aur consent karta hai. Password Google ke paas hi rehta hai.
  3. Google browser ko wapas bhejta hai: redirect_uri?code=abc&state=xyz.
  4. App ka backend code + client_secret + code_verifier Google ke /token endpoint ko bhejta hai (browser ke bina).
  5. Google deta hai access_token, id_token (OIDC) aur kabhi-kabhi refresh_token.
  6. App id_token verify karke user find-or-create karti hai aur apna session ya JWT deti hai.
  • state: callback pe CSRF rokta hai. Jo value bheji thi, wahi wapas aani chahiye.
  • PKCE: authorization code beech me chori ho jaye, tab bhi code_verifier ke bina token nahi milega.
  • OIDC = OAuth 2.0 + identity layer. id_token (JWT) me sub, email, name. OAuth batata hai app kya access kar sakti hai; OIDC batata hai user kaun hai.
Kaunsa grant type kab
  • Authorization Code + PKCE: web, SPA, mobile. Default choice.
  • Client Credentials: service-to-service, koi user nahi (jaise cron job Payments API call kare).
  • Refresh Token: naya access token lena.
  • Device Code: Smart TV ya CLI, jahan keyboard nahi.
  • Implicit aur Password grant: deprecated. OAuth 2.1 inhe hata raha hai, naye systems me mat use karo.

Tradeoff: Apna Authorization Server banayein ya managed lein?

✓ Kab apply karein
  • Sirf social login (Google/GitHub): MVP ya consumer app, jaldi launch.
  • Managed (Auth0, Okta, AWS Cognito): MFA, SSO aur compliance chahiye par team chhoti hai.
  • Self-hosted (Keycloak, Spring Authorization Server): bahut saari internal apps ke liye SSO, data residency, full control.
✗ Kab ignore karein
  • Apna OAuth server scratch se likhna ignore karo: spec tricky hai aur security bugs mehenge padte hain.
  • Ek chhoti single app ke liye Keycloak chalana ignore karo: ek aur system maintain, upgrade aur monitor karna padega.

Microservices me JWT verify: Resource Server + JWKS

Architect

✗ Problem

10 microservices hain aur sab HS256 shared secret se JWT verify karti hain.

  • Har service ke paas wahi secret: koi ek service hack hui toh attacker kisi ka bhi valid token bana sakta hai.
  • Secret rotate karna = 10 services ek saath redeploy.
  • Har team apna JwtAuthenticationFilter copy-paste karti hai: kahin expiry check chhoota, kahin audience.

✓ Solution

Auth server private key se sign kare (RS256 ya ES256). Services sirf public key se verify karein, jo JWKS endpoint se aati hai. Public key leak hone se koi token nahi bana sakta.

  1. Spring issuer ka discovery document padh ke JWKS URL khud nikal leta hai, aur iss claim bhi validate karta hai.
  2. Token isi API ke liye bana ho (aud claim). Payments ka token Orders pe nahi chalega.
  1. Authorization rules wahi rahe, bas token verification ab standard.
  2. Hand-written filter ki jagah Spring ka tested filter: signature (JWKS se), exp, nbf, iss, aud sab check.
  3. Default me Spring scope claim padh ke SCOPE_xyz authorities banata hai. Hamare token me roles claim hai, isliye custom converter.
  4. Token me pehle se ROLE_ADMIN likha hai, dobara prefix nahi chahiye.

Key rotation: naya key (naye kid ke saath) pehle JWKS me publish karo, phir us se sign karna shuru karo. Purana key tab hatao jab uske saare tokens expire ho jayein.

Tradeoff: HS256 vs RS256/ES256 vs opaque token

✓ Kab apply karein
  • HS256: ek monolith jo token banata bhi hai aur verify bhi karta hai. Simple aur fast.
  • RS256/ES256 + JWKS: multiple services ya third parties verify karein. ES256 ke keys aur signatures chhote hain.
  • Opaque token + introspection: jab har request pe turant revocation chahiye (har baar auth server se poochna).
✗ Kab ignore karein
  • Microservices me HS256 shared secret ignore karo.
  • Har request pe introspection ignore karo jab latency critical ho: har API call ke saath ek extra network call judti hai (cache karo ya JWT lo).

Roles, permissions aur ownership: har authorization feature

Intermediate

✗ Problem

  • if (user.getRole().equals("ADMIN")) 50 jagah likha. Ek jagah bhool gaye toh breach.
  • Sirf role check: USER order edit kar sakta hai, par kiska order? User A ne URL me ID badli aur User B ka order edit ho gaya. Ise IDOR/BOLA kehte hain, OWASP API Top 10 me number 1.

✓ Solution

Authorization ko layers me lagao:

  1. URL level (SecurityFilterChain): /api/admin/** sirf ADMIN. Coarse, ek jagah.
  2. Method level (@PreAuthorize): har method pe role ya permission.
  3. Ownership level: 'ye resource isi user ka hai?' Custom bean ya query me owner condition.
  4. Roles → permissions: ROLE_ADMIN ke paas order:delete, user:read. Code permission check kare, roles DB me badlein.
  1. Admin kisi ka bhi order edit kar sakta hai; baaki users sirf apna.
  2. @beanName se Spring bean call hota hai. #orderId method ka parameter, authentication.name logged-in user ka email (JWT ka sub).
  3. Permission-based check. Role ka naam badle ya naya role bane, code wahi rahega.
  1. Bean ka naam wahi jo SpEL me @orderAccessChecker likha hai.
  2. Ek sasti exists query: order ki id aur owner ka email match. Poora order load nahi hota.

#orderId jaise parameter names tabhi milte hain jab code -parameters flag ke saath compile ho. Spring Boot ka Maven/Gradle plugin ye by default karta hai.

Tradeoff: RBAC kaafi hai ya ABAC/ReBAC chahiye?

✓ Kab apply karein
  • RBAC + ownership check: zyada tar apps (e-commerce, SaaS dashboards). Simple aur samajhne me aasaan.
  • RoleHierarchy (ADMIN > MANAGER > USER): jab upar wale role ko neeche wale saare rights chahiye.
  • ABAC/ReBAC (OPA, OpenFGA, SpiceDB): Google Docs jaisa sharing, ya department/region based rules.
✗ Kab ignore karein

  • Shuru me hi ReBAC engine lagana ignore karo jab tak sharing model sach me complex na ho: ek aur service, ek aur failure point.

User update aur password change safely

Architect

✗ Problem

  • Password change pe current password nahi poocha: chura hua token ya khula laptop, aur koi bhi password badal ke account le lega.
  • Naya password save hua par purane JWT aur refresh tokens chalte rahe: attacker logged-in hi raha.
  • Mobile aur web se ek saath profile edit: jo baad me save hua, usne pehle wala chupchap overwrite kar diya (lost update).
  • Entity ko hi request body bana diya: user ne JSON me "roles": ["ROLE_ADMIN"] bhej diya (mass assignment).
  1. Client jo field bheje wahi set: roles, passwordHash, enabled, sab kuch.
  2. Kisi bhi id pe kisi ka bhi data overwrite, aur response me password hash bhi wapas.

✓ Solution

  • Alag endpoints aur DTOs: PATCH /api/users/me/profile (sirf fullName) aur POST /api/users/me/password.
  • Password change: current password verify → naya hash → tokenVersion + 1 → saare refresh tokens revoke.
  • Concurrent edits: @Version optimistic locking, aur client se expectedVersion (ya If-Match ETag).
  1. Email JWT se aata hai (authentication.getName()), request body se nahi. User sirf apna password badal sakta hai.
  2. Current password verify: chura hua access token akela kaafi nahi. Google-only user ke paas password hai hi nahi.
  3. Naya password purane jaisa nahi hona chahiye.
  4. Entity @Transactional ke andar load hui, isliye managed hai. save() ki zarurat nahi: commit pe Hibernate dirty checking khud UPDATE chalata hai.
  5. tv +1: purane access tokens (jinme purana tv hai) filter me reject honge.
  6. Saare devices ke refresh tokens band. 'Logout from all devices' free me mil gaya.
  7. @Version sirf ek saath chal rahi transactions pakadta hai. User ne 5 minute pehle form khola tha? Uske liye client ka expectedVersion compare karo. Mismatch pe 409: 'refresh karke dobara try karo'.
  8. Sirf allowed field badla. Roles ya email yahan se badal hi nahi sakte: mass assignment khatam.
  1. Token banate waqt ka version.
  2. Redis ya Caffeine cache se current tokenVersion (cache miss pe DB). Match nahi hua toh token purana hai.
  3. Filter ka existing catch (JwtException …) isko pakad lega: context clear, response 401.

Password change ke baad cache evict commit ke baad karo (@TransactionalEventListener(phase = AFTER_COMMIT)). Warna beech me aayi koi request purana version dobara cache me bhar sakti hai.

Tradeoff: Optimistic vs pessimistic locking

✓ Kab apply karein
  • Optimistic (@Version): profile, settings, jahan conflicts rare hain. Koi lock nahi, performance achhi.
  • Pessimistic (@Lock(PESSIMISTIC_WRITE), SELECT … FOR UPDATE): wallet balance, inventory, seat booking, jahan conflict common hai aur retry mehenga.
✗ Kab ignore karein
  • Profile jaise low-conflict data pe pessimistic lock ignore karo: rows locked rahengi, throughput girega, deadlock ka risk.
  • Naam change jaise chhote update pe saare devices logout karna ignore karo. Ye sirf password/email change ya security incident ke liye hai.

Brute force, rate limiting aur account lockout

Architect

✗ Problem

  3. Pehli galti pe hi expiry set: 15 min baad counter khud gayab.

✓ Kab apply karein

  • IP/device rate limit + CAPTCHA: consumer apps, taaki attacker kisi ka account lock na kar sake.
  • Dono + MFA: admin accounts.
✗ Kab ignore karein
  • Permanent lockout (support call se unlock) ignore karo: attacker ke haath me DoS ka button aa jata hai.
  • Sirf IP-based limit pe bharosa ignore karo: credential stuffing botnets hazaron IPs se aate hain. Per-account limit bhi rakho.

Crore users me 'user exists?' check: index, replica aur Bloom filter

Architect

✗ Problem

5 crore users. Signup form har keystroke pe 'username available hai?' API call karta hai (r, ri, riy, riya). Launch day pe hazaron requests per second, sab database pe.

  • Index ke bina har check full table scan, DB CPU 100%.
  • Index ke saath bhi primary DB pe itna read load baaki writes (signup, orders) ko slow karta hai.
  • Cache me sirf 'taken' emails rakhe: 'available' wale checks (jo zyada hote hain) phir bhi DB pe.

✓ Solution

Step by step scale karo, aur har step se pehle measure karo:

  1. Unique B-tree index: O(log n). 5 crore rows me bhi 3–4 levels ka tree, bas kuch page reads. Zyada tar apps ke liye yahi kaafi.
  2. Frontend debounce (300 ms) + endpoint rate limit: sabse sasta fix, 5 calls ki jagah 1.
  3. Read replica: availability checks replica pe, INSERT primary pe.
  4. Bloom filter: memory me bit-array jo bolta hai 'pakka nahi hai' ya 'shayad hai'. 'Pakka nahi' pe DB call hi nahi.
  5. Final truth hamesha DB ka UNIQUE constraint, INSERT ke waqt.
  1. 5 crore emails aur 1% false positive: lagbhag 9.6 bits per email, yaani ~60 MB RAM. Poori users table cache karne se kahin kam.
  2. Bloom filter 'nahi hai' bole toh 100% nahi hai. DB call skip, turant 'available'.
  3. 'Shayad hai' (1% cases me galat ho sakta hai) toh DB se confirm.
  4. Signup commit hone ke baad call karo. App start hone pe saare emails stream karke filter warm karo.

Guava filter har instance ki apni memory me hai: 5 instances = 5 copies jinhe sync rakhna padega. Multiple instances me Redis wala Bloom filter (RedisBloom / Redis Stack) ek shared copy deta hai.

Tradeoff: Bloom filter kab lagayein?

✓ Kab apply karein
  • Username ya email availability endpoint pe bahut high QPS, jahan zyada tar answers 'available' hote hain.
  • Multiple shards ya regions me 'kahin exist karta hai?' check, jahan har shard se poochna mehenga hai.
✗ Kab ignore karein
  • Jab tak index + replica ke saath DB ki p99 latency aur CPU theek hain, Bloom filter ignore karo: extra complexity, warm-up aur sync.
  • Users baar-baar delete hote hain toh standard Bloom filter ignore karo (usme se remove nahi hota); Cuckoo filter ya periodic rebuild socho.
  • Bloom filter ko final decision banana hamesha ignore karo. INSERT pe UNIQUE constraint hi truth hai.

  5. UserAccount.createLocalAccount() + assignRole(ROLE_USER).
  6. saveAndFlush() INSERT chalata hai. Unique violation aaya toh UserAlreadyExistsException.
  7. GlobalExceptionHandler exception ko 409 ProblemDetail me badalta hai.
  8. Success pe UserResponse.fromEntity() ke saath 201 Created.

Tradeoffs: kab kya apply, kab ignore

Architect ka kaam 'best' option dhoondhna nahi, apni situation ke liye sahi compromise chunna hai. Har decision me pehle socho: kitne users, kitna risk, team kitni badi, aur galti hui toh nuksaan kitna.

Password hashing algorithm

BCrypt vs Argon2id vs PBKDF2

✓ Kab apply karein
  • BCrypt: zyada tar apps, team familiar, Spring default.
  • Argon2id: naya high-security system, GPU attack ka dar.
  • PBKDF2: FIPS compliance zaroori ho.
✗ Kab ignore karein
  • MD5, SHA-1, plain SHA-256 aur encryption: hamesha.
  • Argon2id jab server RAM budget tight ho.

Default pick: BCrypt (cost 10–12) via DelegatingPasswordEncoder, taaki baad me migration aasaan ho. Detail dekho

Duplicate user check

existsBy + UNIQUE vs INSERT-and-catch vs ON CONFLICT

✓ Kab apply karein
  • existsBy + UNIQUE + catch: default, clear code, duplicates pe hashing bachata hai.
  • INSERT-and-catch: bahut high signup traffic, duplicates rare.
  • ON CONFLICT: PostgreSQL, exception ke bina.
✗ Kab ignore karein
  • Sirf existsBy bina UNIQUE constraint: race me duplicate pakka.
  • findByEmail sirf existence ke liye: bekaar ka data load.

Default pick: existsByEmail + UNIQUE constraint + DataIntegrityViolationException → 409. Detail dekho

User exists check at scale

Index vs read replica vs Bloom filter

✓ Kab apply karein
  • Index: hamesha, pehla step.
  • Replica: read load primary ko slow kar raha ho.
  • Bloom filter: availability endpoint pe bahut high QPS.
✗ Kab ignore karein
  • Bloom filter bina measure kiye.
  • Bloom filter ko final decision banana.

Default pick: Index + debounce pehle; Bloom filter sirf metrics bolein tab. Detail dekho

Session vs JWT

Server session vs stateless token

✓ Kab apply karein
  • JWT: SPA, mobile, microservices, multiple instances.
  • Session: server-rendered monolith, instant logout chahiye.
✗ Kab ignore karein
  • JWT jab har request pe DB lookup karna hi hai.
  • Sticky sessions pe poora scaling plan.

Default pick: API + mobile: JWT (15 min) + refresh token. Server-rendered app: session + Spring Session. Detail dekho

JWT signing

HS256 vs RS256/ES256

✓ Kab apply karein
  • HS256: ek hi service sign aur verify kare.
  • RS256/ES256 + JWKS: multiple services ya third parties.
✗ Kab ignore karein
  • Microservices me shared HS256 secret.
  • Token ke alg header pe bharosa: server apna algorithm enforce kare.

Default pick: Monolith: HS256. Multiple services: RS256/ES256 + JWKS. Detail dekho

Token lifetime

Short access + refresh vs long access token

✓ Kab apply karein
  • Access 5–15 min + refresh 7–30 din with rotation: default.
  • Aur chhota access token: banking, admin.
✗ Kab ignore karein
  • Din bhar ya hafte bhar ka access token.
  • Refresh token bina rotation ke.

Default pick: Access 15 min, refresh 14 din, rotation + reuse detection. Detail dekho

Refresh token storage (server)

PostgreSQL vs Redis

✓ Kab apply karein
  • PostgreSQL: durability, audit, user ke saath joins.
  • Redis: bahut high volume, TTL se auto-expiry.
✗ Kab ignore karein
  • Redis bina persistence ke: restart pe sab logout.
  • Raw token store karna, kahin bhi.

Default pick: PostgreSQL me hash; scale pe Redis. Detail dekho

Token storage (browser)

HttpOnly cookie vs localStorage vs memory

✓ Kab apply karein
  • HttpOnly + Secure + SameSite cookie: refresh token ke liye. JavaScript use padh hi nahi sakta.
  • Memory (JS variable): access token; reload pe refresh se naya.
✗ Kab ignore karein
  • localStorage me long-lived token: koi bhi XSS script chura lega.
  • Cookie use kiya toh CSRF protection band karna.

Default pick: Access token memory me, refresh token HttpOnly cookie me. Detail dekho

Roles kahan se aayein

JWT claims vs har request fresh lookup

✓ Kab apply karein
  • JWT claims: fast, zyada tar endpoints.
  • tv check (Redis): role/password change turant effective.
  • Fresh DB lookup: critical admin ya money actions.
✗ Kab ignore karein
  • Sab endpoints pe DB lookup: DB bottleneck.
  • Lambi TTL wale token me roles.

Default pick: Roles JWT me + tv cache check; critical actions pe fresh lookup. Detail dekho

Identity provider

Social login vs managed (Auth0/Okta/Cognito) vs self-hosted (Keycloak)

✓ Kab apply karein
  • Social login: MVP, consumer app.
  • Managed: MFA/SSO chahiye, team chhoti.
  • Self-hosted: enterprise SSO, data residency.
✗ Kab ignore karein
  • Apna OAuth server scratch se.
  • Chhoti app ke liye Keycloak ka operational bojh.

Default pick: MVP: Google login + apne JWT. Growth: managed provider. Detail dekho

OAuth account linking

Auto-link verified email vs user confirmation

✓ Kab apply karein
  • Auto-link: trusted provider + email_verified = true.
  • Confirmation (password/OTP): kam trusted provider ya sensitive account.
✗ Kab ignore karein
  • Unverified email pe link.
  • Email ko permanent ID maanna (sub use karo).

Default pick: (provider, sub) se link; Google verified email pe auto-link. Detail dekho

Concurrent updates

Optimistic vs pessimistic locking

✓ Kab apply karein
  • Optimistic (@Version): profile, settings.
  • Pessimistic: wallet, inventory, seat booking.
✗ Kab ignore karein
  • Low-conflict data pe pessimistic lock.
  • Bina locking ke 'last write wins' jahan data important hai.

Default pick: Optimistic by default; paisa aur stock pe pessimistic. Detail dekho

Brute force defense

Account lockout vs rate limit + CAPTCHA

✓ Kab apply karein
  • Temporary lockout: fintech.
  • Rate limit + CAPTCHA: consumer apps.
  • MFA: admin accounts.
✗ Kab ignore karein
  • Permanent lockout (DoS risk).
  • Sirf IP-based limits (botnets).

Default pick: Per-account + per-IP rate limit, 15 min temporary lock, admins ke liye MFA. Detail dekho

Duplicate email response

409 already exists vs generic message

✓ Kab apply karein
  • 409: normal consumer/B2B apps, clear UX.
  • Generic + verification email: dating, health, privacy-sensitive apps.
✗ Kab ignore karein
  • Generic message jab instant feedback product ke liye zaroori ho aur email khud sensitive na ho.
  • 200 OK ke saath error string.

Default pick: 409 by default; privacy-sensitive app me generic. Detail dekho

Authorization model

RBAC vs ABAC/ReBAC

✓ Kab apply karein
  • RBAC + ownership: zyada tar apps.
  • ABAC/ReBAC: complex sharing, attribute-based rules.
✗ Kab ignore karein
  • Sirf roles bina ownership check (IDOR).
  • Shuru me hi policy engine.

Default pick: RBAC + ownership check; complex sharing aaye tab ReBAC. Detail dekho

Mock interview questions

Pehle khud answer socho, phir question pe tap karke answer kholo. Beginner se architect level tak.

Beginner

Q1Hashing aur encryption me kya farak hai? Password ke liye kaunsa?+

Encryption reversible hai: key se original wapas mil jata hai. Hashing one-way hai: hash se password wapas nahi nikalta.

Password ke liye slow, salted hash (BCrypt/Argon2id). Encryption key leak hui toh saare passwords khul jayenge. Login pe hum decrypt nahi karte, matches() se compare karte hain.

Q2Salt kya hai, aur BCrypt me salt kahan store hota hai?+

Salt ek random value hai jo har password ke saath mix hoti hai, taaki same password ke hash alag hon aur rainbow tables bekaar ho jayein.

BCrypt salt ko hash string ke andar hi rakhta hai ($2a$10$ ke baad ke 22 characters), isliye alag column nahi chahiye.

Q3passwordEncoder.encode(raw).equals(storedHash) hamesha false kyun deta hai?+

encode() har baar naya random salt use karta hai, toh naya hash stored hash se kabhi equal nahi hoga.

Sahi tareeka passwordEncoder.matches(raw, storedHash), jo stored hash ka salt aur cost use karke compare karta hai.

Q4401 aur 403 me farak?+

401 Unauthorized: identity prove nahi hui (token missing, galat ya expired). 403 Forbidden: identity valid hai par permission nahi.

Frontend 401 pe refresh ya login karta hai, 403 pe 'access denied' dikhata hai. Isliye dono ko mix mat karo.

Q5User exist check ke liye existsByEmail better hai ya findByEmail?+

Sirf haan/na chahiye toh existsByEmail: Spring Data limit-1 wali query banata hai aur entity load nahi karta.

Jahan user ka data chahiye (jaise login), wahan findByEmail. Dono ke liye email column pe index zaroori hai.

Q6Registration me user pehle se exist kare toh kaunsa HTTP status, aur kyun?+

409 Conflict, kyunki request resource ki current state se clash karti hai. Body me consistent ProblemDetail.

200 + message ya 500 dono galat. Privacy-sensitive apps generic response dete hain taaki 'ye email registered hai' leak na ho.

Q7JWT ke teen parts kya hain? Kya payload encrypted hota hai?+

Header (algorithm), payload (claims jaise sub, roles, exp) aur signature.

Payload sirf Base64URL encoded hai, encrypted nahi. Koi bhi decode karke padh sakta hai, isliye sensitive data mat daalo. Signature sirf tampering pakadta hai.

Q8@PreAuthorize kaam kyun nahi kar raha?+

Sabse common reason: @EnableMethodSecurity nahi lagaya.

Doosre reasons: method private hai, ya same class ke andar se call ho raha hai (Spring proxy bypass ho jata hai), ya SpEL me #param naam nahi mil raha (-parameters compile flag).

Intermediate

Q9Sirf existsByEmail check karke save karna kaafi kyun nahi?+

Check aur save ke beech gap hai (check-then-act race). Do requests ek saath aayein toh dono ko 'nahi hai' milega aur dono INSERT karengi.

Isliye DB me UNIQUE constraint compulsory hai, aur DataIntegrityViolationException ko 409 me convert karo.

Q10save() aur saveAndFlush() me farak, aur duplicate handle karne me ye kyun matter karta hai?+

save() entity ko persistence context me daalta hai; SQL flush ya commit pe ja sakta hai (IDENTITY ids turant insert hote hain, SEQUENCE wale nahi). saveAndFlush() SQL turant bhejta hai.

Isliye constraint error try-catch ke andar hi aata hai. Warna exception method return hone ke baad commit pe aata aur catch miss ho jata.

Q11Spring Security me username/password login internally kaise hota hai?+

AuthenticationManager (ProviderManager) request DaoAuthenticationProvider ko deta hai. Woh UserDetailsService.loadUserByUsername() se user laata hai aur PasswordEncoder.matches() se password verify karta hai.

Phir account enabled/locked check. Success pe authenticated Authentication, fail pe BadCredentialsException aur AuthenticationFailureBadCredentialsEvent.

Q12JWT stateless hai, toh logout kaise karoge?+

Access token chhota (5–15 min) rakho aur logout pe refresh token revoke karo.

Turant logout chahiye toh tokenVersion claim ko cache se match karo, ya jti denylist (Redis, TTL = token ki bachi hui life). Trade-off: jitna turant revocation, utna state wapas aata hai.

Q13Refresh token rotation aur reuse detection samjhao.+

Har refresh pe purana refresh token revoke hota hai aur naya milta hai. Agar koi revoked token dobara aaye, matlab do log ek hi token rakhte hain (chori).

Tab user ke saare refresh tokens revoke karke dobara login karwao. Tokens DB me SHA-256 hash ke roop me rakho.

Q14CSRF protection disable karna kab safe hai?+

Jab browser credentials automatically nahi bhejta, jaise Authorization: Bearer header jo JavaScript khud lagati hai.

Agar token ya session cookie me hai, toh browser har request pe cookie bhejega aur CSRF possible hai. Tab SameSite cookie + CSRF token rakho.

Q15OAuth 2.0, OpenID Connect aur JWT me kya farak hai?+

OAuth 2.0 authorization framework hai: app ko limited access token dilwata hai. OIDC uske upar identity layer hai: id_token batata hai user kaun hai.

JWT sirf ek token format hai jo dono me use ho sakta hai. OAuth ke access tokens opaque bhi ho sakte hain.

Q16Authorization Code flow me state aur PKCE kyun chahiye?+

state random value hai jo callback pe match hoti hai, taaki attacker apna code tumhare session me inject na kar sake (CSRF).

PKCE me client ek secret code_verifier banata hai aur uska hash pehle bhejta hai. Code chori ho jaye tab bhi verifier ke bina token nahi milega. Mobile aur SPA me PKCE must hai.

Q17hasRole('ADMIN') aur hasAuthority('ROLE_ADMIN') me farak?+

Result same hai: hasRole khud ROLE_ prefix jodta hai, hasAuthority exact string match karta hai. Permissions (order:delete) ke liye hasAuthority.

Common galti: DB me role ADMIN (bina prefix) save kiya aur code me hasRole('ADMIN') likha. Required authority ROLE_ADMIN hai, match hi nahi hoga.

Q18IDOR kya hai aur Spring me kaise rokoge?+

Insecure Direct Object Reference: user URL me ID badal ke kisi aur ka data access kar le (/orders/8). Role check isse nahi rokta.

Ownership check lagao: @PreAuthorize me custom bean, ya query me hi owner condition (findByIdAndOwnerId). Non-owner ko 404 dena existence bhi chhupata hai.

Architect

Q195 crore users, har keystroke pe username availability check. Design batao.+

Pehle frontend debounce + endpoint rate limit. DB me unique B-tree index, reads replica pe.

Load phir bhi zyada ho toh shared Bloom filter (Redis): 'pakka nahi hai' pe DB skip, 'shayad hai' pe DB se confirm. Final guarantee INSERT pe UNIQUE constraint. Har layer p99 latency aur DB CPU dekh ke hi add karo.

Q20Microservices me HS256 ya RS256? Key rotation kaise karoge?+

RS256/ES256: private key sirf auth server ke paas, services JWKS se public key lekar verify karti hain. Kisi service ke hack hone se tokens forge nahi honge.

Rotation: naya key naye kid ke saath JWKS me publish, phir naye key se sign karna shuru, purana key tab hatao jab uske saare tokens expire ho jayein.

Q21Password change ke baad saare devices se logout kaise design karoge?+

Users table me token_version, JWT me tv claim. Password change pe tv + 1 aur saare refresh tokens revoke.

Filter ya gateway har request pe token ka tv current value se match kare (Redis cache, miss pe DB). Cache eviction transaction commit ke baad.

Q22BCrypt cost factor capacity planning ko kaise affect karta hai?+

Cost +1 = hashing time double. Cost 10 pe ek hash ~50–100 ms CPU, yaani ek core ~10–20 logins/sec. 2,000 logins/sec peak ≈ 100–200 cores sirf hashing.

Mitigation: refresh tokens se password logins kam, login rate limit, cost factor load test karke chuno, aur auth service ko alag scale karo.

Q23Google login aur existing email/password account: secure account linking kaise karoge?+

oauth_accounts(provider, provider_user_id) table, link Google ke sub se (email se nahi). UNIQUE constraint (provider, provider_user_id) pe.

Pehli baar: trusted provider aur email_verified = true ho toh same email wale account se link; warna user se password ya OTP se confirm karwao. Login ke baad apne tokens issue karo, Google ke nahi.

Q24Admin ne user ka role hataya, par user ke JWT me abhi bhi ADMIN hai. Kya karoge?+

Teen levels: access token TTL chhota rakho taaki naya token naye roles le; role change pe tokenVersion + 1 taaki purana token turant reject ho; critical admin actions pe har baar DB/cache se fresh roles.

Trade-off: jitni freshness, utna lookup cost.

Q25Forgot password flow design karo.+

Request pe hamesha same response ('agar account hai toh email bhej diya'). Random 256-bit token, DB me sirf hash, expiry 15–30 min, single-use. Endpoint pe rate limit.

Link pe naya password set karo, tokenVersion + 1, saare refresh tokens revoke, aur user ko 'password changed' email bhejo.
