What is a Circuit Breaker?

A Circuit Breaker is a resilience pattern that prevents your application from repeatedly calling a failing remote service. Like an electrical circuit breaker that trips to stop damage — it detects failures, "opens" the circuit to stop calls, gives the downstream service time to recover, then cautiously tries again.

❌ Without Circuit Breaker
  • Every request waits for timeout (30s each)
  • Threads pile up → thread pool exhausted
  • Your service goes down too (cascade failure)
  • User gets 500 errors after long waits
✅ With Circuit Breaker
  • After N failures, circuit OPENS immediately
  • Calls fail fast — no waiting for timeout
  • Returns fallback response instantly
  • Downstream gets breathing room to recover

In Spring Boot, the standard implementation is Resilience4j (replaced Netflix Hystrix, which is now deprecated).

The Three States

🟢
CLOSED
Normal operation
failure rate ≥ threshold
──────▶
🔴
OPEN
Blocking all calls
wait duration expires
──────▶
🟡
HALF-OPEN
Testing recovery
HALF-OPEN → CLOSED (if probe calls succeed)  |  HALF-OPEN → OPEN (if probe calls fail)
🟢 CLOSED

Everything is fine. All calls pass through to the remote service.

The CB records success/failure rates in a sliding window.

Transitions to OPEN when failure rate ≥ threshold.

🔴 OPEN

Remote service is failing. All calls are short-circuited immediately — no actual call is made.

Transitions to HALF-OPEN after waitDurationInOpenState expires.

🟡 HALF-OPEN

Cautiously allows a limited number of probe calls through to test if the service recovered.

→ CLOSED if probe calls succeed
→ OPEN if probe calls fail

Two Sliding Window Modes
COUNT_BASED

Tracks the last N calls. If failure rate among last 100 calls ≥ 50% → OPEN.

Good for high-traffic services.

TIME_BASED

Tracks calls within the last N seconds. If failure rate in last 60s ≥ 50% → OPEN.

Good for bursty / low-traffic services.

// ─── Basic usage — annotate any Spring bean method ─────────────────

@Service
public class PaymentService {

    private final PaymentGatewayClient gatewayClient;

    // "paymentGateway" maps to a named config in application.yml
    @CircuitBreaker(
        name     = "paymentGateway",
        fallbackMethod = "paymentFallback"
    )
    public PaymentResult charge(PaymentRequest request) {
        return gatewayClient.charge(request);   // may fail / timeout
    }

    // Fallback: SAME return type, SAME params + the exception as last param
    private PaymentResult paymentFallback(PaymentRequest request,
                                           Throwable ex) {
        log.warn("Payment gateway unavailable, using fallback: {}", ex.getMessage());
        return PaymentResult.pending(request.orderId()); // safe default
    }
}

Fallback Methods — All Patterns

A fallback provides a graceful degraded response when the circuit is open or an exception occurs. Spring Resilience4j supports several fallback patterns.

@Service
public class ProductService {

    private final ProductClient    productClient;
    private final ProductCacheRepo cache;

    // ─── Pattern 1: Return cached / stale data ─────────────────────
    @CircuitBreaker(name = "productService", fallbackMethod = "cachedProducts")
    public List<Product> getProducts(Long categoryId) {
        return productClient.fetchByCategory(categoryId);
    }

    private List<Product> cachedProducts(Long categoryId, Throwable ex) {
        log.warn("Product service down, returning cache for category {}", categoryId);
        return cache.findByCategory(categoryId)      // try cache first
                    .orElse(List.of());              // empty if no cache
    }

    // ─── Pattern 2: Return empty / default object ──────────────────
    @CircuitBreaker(name = "productService", fallbackMethod = "defaultProduct")
    public Product getProduct(Long id) {
        return productClient.fetchById(id);
    }

    private Product defaultProduct(Long id, Throwable ex) {
        return Product.unavailable(id);   // placeholder with "Unavailable" title
    }

    // ─── Pattern 3: Throw custom exception (let caller decide) ─────
    @CircuitBreaker(name = "productService", fallbackMethod = "throwServiceException")
    public Product getProductStrict(Long id) {
        return productClient.fetchById(id);
    }

    private Product throwServiceException(Long id, Throwable ex) {
        throw new ServiceUnavailableException(
            "Product service is currently unavailable", ex
        );
    }

    // ─── Pattern 4: Multiple fallback methods by exception type ────
    @CircuitBreaker(name = "productService", fallbackMethod = "networkFallback")
    @CircuitBreaker(name = "productService", fallbackMethod = "timeoutFallback")
    public Product getProductRobust(Long id) {
        return productClient.fetchById(id);
    }

    private Product networkFallback(Long id, IOException ex) {
        return Product.offline(id);
    }

    private Product timeoutFallback(Long id, TimeoutException ex) {
        return cache.findByIdOrDefault(id);  // timeout → try cache
    }
}

Java 17 — Fallback Patterns
💡
Fallback method rules:
  • Same return type as the original method
  • Same parameters as the original + Throwable as the last parameter
  • Can be private (unlike @Transactional which needs public)
  • Multiple fallbacks possible — most specific exception type is matched first

Resilience4j provides several complementary annotations that work together. Order of execution (outside-in):

Annotation Purpose When to use
@CircuitBreaker Stop calling failing services All external HTTP/gRPC calls
@Retry Retry transient failures automatically Flaky services, network blips
@TimeLimiter Enforce a max call duration (timeout) Async calls that might hang
@RateLimiter Limit calls per time window Rate-limited APIs (e.g. SMS, email)
@Bulkhead Limit concurrent calls (thread isolation) Prevent thread pool exhaustion 
@Service
public class WeatherService {

    private final WeatherApiClient client;

    // ─── Full resilience stack on a single method ───────────────────

    @Bulkhead(name = "weatherApi")                          // max 10 concurrent calls
    @CircuitBreaker(name = "weatherApi",
                    fallbackMethod = "weatherFallback")    // open on failures
    @RateLimiter(name = "weatherApi")                       // max 100 calls/min
    @Retry(name = "weatherApi")                              // retry 3 times
    public WeatherData getWeather(String city) {
        return client.fetchCurrent(city);
    }

    private WeatherData weatherFallback(String city, Throwable ex) {
        return WeatherData.unavailable(city);
    }
}

What Happens Without a Circuit Breaker?

Without a circuit breaker, a single failing downstream service can take down your entire application — this is called a cascading failure.

@Service
public class OrderService {

    private final PaymentClient paymentClient;

    // ❌ NO circuit breaker — catastrophic failure chain
    public OrderResult placeOrderBroken(OrderRequest request) {

        // Payment service is down with 30s timeout...
        //
        // Thread 1  → waiting 30s ─────────────────────┐
        // Thread 2  → waiting 30s ─────────────────────┤
        // Thread 3  → waiting 30s ─────────────────────┤  Thread pool
        // Thread 4  → waiting 30s ─────────────────────┤  EXHAUSTED
        // Thread 5  → waiting 30s ─────────────────────┤
        // Thread 6+ → rejected (queue full) ──────────┘
        //
        // Result: YOUR service is now also down

        PaymentResult result = paymentClient.charge(request.payment());
        return OrderResult.of(result);
    }

    // ✅ WITH circuit breaker — fast failure, preserved capacity
    @CircuitBreaker(name = "payment", fallbackMethod = "orderFallback")
    public OrderResult placeOrderSafe(OrderRequest request) {
        PaymentResult result = paymentClient.charge(request.payment());
        return OrderResult.of(result);
    }

    private OrderResult orderFallback(OrderRequest request, Throwable ex) {
        // Circuit OPEN: returns instantly, thread is free in microseconds
        return OrderResult.queued(request.id());  // queue for retry later
    }
}

Java 17 — Cascading Failure Demo
Without CB — Impact
  • 30s timeout per request
  • Threads block and pile up
  • Connection pool exhausted
  • Your service → 500 errors
  • Cascades to upstream callers
CB OPEN — Impact
  • Fails in < 1ms (no call made)
  • Threads freed immediately
  • Fallback served instantly
  • Your service stays healthy
  • Downstream gets recovery time
CB HALF-OPEN — Impact
  • Controlled recovery testing
  • Only N probe calls allowed
  • Returns to CLOSED on success
  • Automatically managed
  • Zero manual intervention

Common Pitfalls

@Service
public class PitfallExamples {

    // ─── Pitfall 1: Self-invocation (same as @Transactional) ────────
    public void doWork() {
        callRemote();    // ❌ bypasses the AOP proxy, CB never activates
    }

    @CircuitBreaker(name = "remote")
    public String callRemote() { return client.fetch(); }

    // ─── Pitfall 2: Business exceptions tripping the circuit ─────────
    // ValidationException is a BUG in your code, not a remote failure.
    // Including it will falsely open the circuit.

    @CircuitBreaker(name = "payment")  // ❌ counts ALL exceptions
    public PaymentResult chargeBad(PaymentRequest req) {
        validate(req);              // throws ValidationException (your bug)
        return gateway.charge(req); // this is what CB should protect
    }

    // Fix: use ignoreExceptions in config, or handle validation before CB
    public PaymentResult chargeGood(PaymentRequest req) {
        validate(req);              // validate BEFORE the CB method
        return chargeViaGateway(req);
    }

    @CircuitBreaker(name = "payment", fallbackMethod = "payFallback")
    private PaymentResult chargeViaGateway(PaymentRequest req) {
        return gateway.charge(req);
    }

    // ─── Pitfall 3: Retry inside CB amplifying failure count ─────────
    // @Retry runs INSIDE @CircuitBreaker.
    // 3 retries × 10 calls = 30 failures counted → CB opens too fast!

    @Retry(name = "svc")                     // ❌ retry inside CB
    @CircuitBreaker(name = "svc")
    public String callBadOrder() { return svc.get(); }

    // Fix: CB wraps Retry (CB is outer decorator)
    @CircuitBreaker(name = "svc")            // ✅ CB is the outer layer
    @Retry(name = "svc")                     // Retry runs inside CB
    public String callGoodOrder() { return svc.get(); }

    // ─── Pitfall 4: Missing minimumNumberOfCalls ─────────────────────
    // Default is 100. If you have 5 calls/min, circuit NEVER trips.
    // Fix: set minimumNumberOfCalls: 5 in application.yml

    // ─── Pitfall 5: Fallback that also fails ─────────────────────────
    @CircuitBreaker(name = "svc", fallbackMethod = "fallback")
    public Data getData() { return svc.get(); }

    private Data fallback(Throwable ex) {
        return dbCache.load();  // ❌ what if DB is also down?
    }

    // Fix: make fallback bulletproof — handle its own exceptions
    private Data fallback(Throwable ex) {
        try {
            return dbCache.load();
        } catch (Exception cacheEx) {
            return Data.empty();   // ✅ always returns something
        }
    }
}

Java 17 — Pitfalls
❌ Pitfall 6 — Using CB on DB calls

Don't wrap @Repository calls with a circuit breaker. DB failures are handled differently (connection pool, retries). CB is for remote service calls.

❌ Pitfall 7 — Not monitoring CB state

Without registerHealthIndicator: true and Actuator, you're flying blind. You won't know when your circuit is open in production.

Best Practices

// ─── 1. One CB per external dependency ───────────────────────────────
//    Name them after the service they protect, not the method.
//    This lets you tune thresholds per dependency.

@CircuitBreaker(name = "paymentGateway")   // named after the service
@CircuitBreaker(name = "inventoryService") // separate config per service
@CircuitBreaker(name = "notificationApi")  // independent failure tracking

// ─── 2. ignoreExceptions for business validation errors ──────────────
//    Don't let bad input trip your circuit. Only infra failures count.

@CircuitBreaker(name = "payment",
    fallbackMethod = "payFallback",
    ignoreExceptions = {
        InvalidCardException.class,
        InsufficientFundsException.class
    }
)
public PaymentResult charge(PaymentRequest req) {
    return gateway.charge(req);
}

// ─── 3. Make fallbacks meaningful — not just null/exception ──────────
//    A good fallback = graceful degradation, not another failure.

private List<Recommendation> recommendationFallback(Long userId, Throwable ex) {
    // Priority: 1. personalized cache  2. popular items  3. empty list
    return cache.getPersonalized(userId)
               .orElseGet(() -> popularItemsRepo.findTop10());
}

// ─── 5. Programmatic CB for advanced control ─────────────────────────
//    Sometimes you need to check state or force OPEN/CLOSED manually.

@Service
public class CircuitBreakerMonitor {

    private final CircuitBreakerRegistry registry;

    // Get current state
    public CircuitBreaker.State getState(String name) {
        return registry.circuitBreaker(name).getState();
    }

    // Force OPEN (e.g. during planned maintenance of downstream)
    public void forceOpen(String name) {
        registry.circuitBreaker(name).transitionToForcedOpenState();
    }

    // Force CLOSED (e.g. after confirmed recovery)
    public void forceClose(String name) {
        registry.circuitBreaker(name).transitionToClosedState();
    }

    // Listen to state changes for alerting
    @PostConstruct
    public void registerEventListeners() {
        registry.getAllCircuitBreakers().forEach(cb ->
            cb.getEventPublisher()
              .onStateTransition(event -> {
                  log.warn("CB [{}] transitioned: {} → {}",
                      event.getCircuitBreakerName(),
                      event.getStateTransition().getFromState(),
                      event.getStateTransition().getToState()
                  );
                  // alert.send("Circuit breaker opened!", event)
              })
        );
    }
}

Real-World Examples

Example A — E-Commerce: Payment Gateway

Payment must never block the UI. Fast fallback queues the order for async retry.

@Service
public class CheckoutService {

    private final StripeClient         stripeClient;
    private final PendingPaymentRepo   pendingPayments;
    private final NotificationService  notifications;

    @CircuitBreaker(name = "stripe", fallbackMethod = "queuePayment")
    @TimeLimiter(name = "stripe")         // max 3s — don't let Stripe hang us
    public CompletableFuture<CheckoutResult> checkout(Cart cart) {
        return CompletableFuture.supplyAsync(() -> {
            var charge = stripeClient.charge(cart.total(), cart.card());
            return CheckoutResult.success(charge.id());
        });
    }

    // CB OPEN or timeout: queue for later, tell user order is received
    private CompletableFuture<CheckoutResult> queuePayment(Cart cart,
                                                              Throwable ex) {
        var pendingId = pendingPayments.queue(cart);
        notifications.sendOrderQueued(cart.customerId(), pendingId);

        return CompletableFuture.completedFuture(
            CheckoutResult.queued(pendingId,
                "Your order is confirmed! Payment will be processed shortly.")
        );
    }
}

Example B — Microservices: Product Recommendations

Recommendations are non-critical. Degrade gracefully through multiple fallback tiers.

@Service
public class RecommendationService {

    private final RecommendationClient mlClient;      // ML service
    private final RecommendationCache  redisCache;    // Redis
    private final PopularItemsRepo     popularItems;  // local DB

    // Tier 1: ML service (best personalization)
    @CircuitBreaker(name = "mlService", fallbackMethod = "fromCache")
    @Bulkhead(name = "mlService")          // max 20 concurrent ML calls
    public List<Product> getRecommendations(Long userId) {
        return mlClient.recommend(userId, 10);
    }

    // Tier 2: Redis cache (recent personalization)
    @CircuitBreaker(name = "redisCache", fallbackMethod = "fromPopular")
    private List<Product> fromCache(Long userId, Throwable ex) {
        return redisCache.get(userId)
                         .orElseThrow(); // throws → triggers CB on Redis too
    }

    // Tier 3: Popular items from local DB (always works)
    private List<Product> fromPopular(Long userId, Throwable ex) {
        return popularItems.findTop10();  // never fails — local DB
    }
}

Example C — Notification Service with Rate Limiting

SMS API has a rate limit. CB + RateLimiter prevents API bans and bill shock.

@Service
public class NotificationService {

    private final TwilioClient    smsClient;
    private final EmailClient     emailClient;
    private final NotificationLog notifLog;

    // CB stops calls when Twilio is down
    // RateLimiter enforces Twilio's limit (100 SMS/min)
    @CircuitBreaker(name = "twilioSms", fallbackMethod = "emailFallback")
    @RateLimiter(name = "twilioSms",   fallbackMethod = "emailFallback")
    public void sendSms(String phone, String message) {
        smsClient.send(phone, message);
        notifLog.log(phone, "SMS", "SENT");
    }

    // Fallback: send email instead of SMS
    private void emailFallback(String phone, String message, Throwable ex) {
        String email = userRepo.findEmailByPhone(phone)
                               .orElse(null);

        if (email != null) {
            emailClient.send(email, "Notification (SMS unavailable)", message);
            notifLog.log(phone, "EMAIL", "FALLBACK");
        } else {
            notifLog.log(phone, "NONE", "DROPPED");
        }
    }
}

// ─── Feign client with CB auto-configured ───────────────────────────

@FeignClient(
    name     = "inventory-service",

// Fallback bean for all methods
@Component
public class InventoryClientFallback implements InventoryClient {

    @Override
    public StockLevel getStock(Long productId) {
        return StockLevel.unknown(productId); // show "Stock unknown" in UI
    }

    @Override
    public ReservationResult reserve(ReservationRequest req) {
        return ReservationResult.queued(req.orderId()); // queue for later
    }
}
