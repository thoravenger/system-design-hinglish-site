Support model — jo log "LTS" dhoondte hain, unke liye

Spring Boot mein koi LTS designation hai hi nahi. Har minor 6 mahine mein aata hai aur ~12 mahine OSS support paata hai. Matlab: upgrade ek project nahi, ek recurring operational cost hai. Architecture decision yeh hai ki aap saal mein do baar chhote upgrade karenge, ya teen saal baad ek 6-month "big bang" migration jhelenge. Pehla sasta hai, dusra career-limiting.

PROBLEM

Tomcat version hardcode karke pin kar diya

  • Security team ne CVE-fix ke liye <tomcat.version> override kiya
  • Boot upgrade hua, property override wahin rehti hai
  • Boot 3.x (Servlet 6.0 expect) + Tomcat 11 (Servlet 6.1) = NoSuchMethodError deploy ke baad, startup pe nahi
  • Ya ulta: Boot 4 + pinned Tomcat 10.1 = ClassNotFoundException on jakarta.servlet 6.1 types

Root cause: starter version aur container version ke beech koi compile-time check nahi hai. Maven silently woh version le lega jo aapne likha hai.

SOLUTION

  • L11–15Enforcer rule build ko fail kar deta hai agar koi Boot 4 ke saath 10.1.x chhod de. Yeh woh guardrail hai jo Boot upgrade ke waqt "purani override" ko pakadta hai — CI mein, prod mein nahi.
  • RuleSirf patch version override karo (11.0.22 → 11.0.24). Minor/major kabhi nahi (10.1 → 11.0), kyunki woh Servlet spec badal deta hai aur Boot ka auto-config uske hisaab se compile hua hai.

TRADE-OFF · Tomcat / version pinning

Apply karo jab
  • CVE patch Boot release se pehle chahiye (typical: 2–4 hafte ka gap)
  • Compliance scanner specific patch demand kar raha ho
  • Sirf patch-level bump ho, same minor line ke andar
Ignore karo jab
  • Gap 2 hafte se kam ho — Boot ka apna release wait kar lo
  • Aap minor cross kar rahe ho (Servlet spec change)
  • Jetty/Undertow pe switch karna "faster hoga" sochke — Undertow Boot 4 mein hai hi nahi
Kyun
  • Boot BOM ka poora point yeh hai ki version matrix ek jagah tested ho
  • Har manual override us test coverage se bahar nikal jaata hai
  • Enforcer rule = override ki expiry date
02

POM ko padhna kaise hai

Ek pom ko upar se neeche nahi padha jata. Use chaar layers mein padha jata hai: kaun version decide kar raha hai, kya classpath pe aa raha hai, kya runtime pe leak ho raha hai, aur packaging kya banayegi. Neeche wahi order hai.

PROBLEM

"Version kahan se aaya?" — nobody knows

  • Do team members ke laptop pe alag transitive version resolve ho raha hai
  • spring-boot-starter-parent hai, par kisi ne <version> bhi explicitly likh diya hai
  • Test-only library prod jar mein pahunch gayi (scope missing)
  • Boot 4 mein upgrade karte hi ClassNotFoundException — kyunki class ab alag module mein chali gayi

Mental model galat hai: log samajhte hain starter "library" hai. Starter ek curated dependency set + auto-config trigger hai. Uska apna koi code nahi hota (ya na ke barabar).

SOLUTION

BOM import karne pe aapko plugin config manually likhni padegi; yeh iski keemat hai.

03

Auto-configuration — jo "magic" nahi hai

Auto-config ek hi cheez karti hai: conditionally registered @Bean definitions, sabse aakhir mein. Agar aapne bean khud define kiya hai, Boot peechhe hat jata hai. Poora contract bas itna hai.

PROBLEM

"Mera bean pick hi nahi ho raha"

  • Custom ObjectMapper banaya, phir bhi Boot wala use ho raha hai
  • Boot 3 pe upgrade kiya aur custom auto-config chup-chaap gayab
  • Do DataSource beans → NoUniqueBeanDefinitionException
  • Test mein kaam karta hai, prod profile mein nahi

Root cause #1: Boot 2.7 mein registration META-INF/spring.factories se hoti thi. Boot 3.0 se woh mechanism auto-config ke liye hata diya gaya. Agar aapki library abhi bhi spring.factories use kar rahi hai, woh silently load hi nahi hogi — koi error nahi, bas bean missing.

Root cause #2: ordering. Auto-config user configuration ke baad chalti hai, par @ConditionalOnMissingBean tabhi kaam karta hai jab aapka bean tab tak register ho chuka ho. @Bean method ka return type var/interface hone se condition match miss ho jaati hai.

SOLUTION

Naya registration format + explicit conditions

AuditTrailAutoConfiguration.javaBoot 3.x / 4.x style
1@AutoConfiguration(after = DataSourceAutoConfiguration.class)
2@ConditionalOnClass(JdbcTemplate.class)
3@ConditionalOnProperty(name = "audit.trail.enabled", havingValue = "true",
4                       matchIfMissing = true)
5@EnableConfigurationProperties(AuditTrailProperties.class)
6public class AuditTrailAutoConfiguration {

8  @Bean

10  public AuditTrailWriter jdbcAuditTrailWriter(
11          JdbcTemplate jdbcTemplate, AuditTrailProperties properties) {
12    return new JdbcAuditTrailWriter(jdbcTemplate, properties.tableName());
13  }
14}

17//   org.springframework.boot.autoconfigure.AutoConfiguration.imports
18// com.acme.audit.AuditTrailAutoConfiguration
  • L1@AutoConfiguration ek composed annotation hai (@Configuration(proxyBeanMethods=false) + ordering). after= guarantee karta hai ki DataSource pehle ban chuka ho — warna condition evaluate hoti hai jab bean maujood hi nahi.
  • L2@ConditionalOnClass ASM se bytecode padhta hai, class load nahi karta. Isiliye missing class pe NoClassDefFoundError nahi aata — condition bas false ho jaati hai.
  • L3–4matchIfMissing=true = "default on". Yeh opt-out design hai. Internal platform libraries ke liye theek, par public library ke liye false rakho — kisi ke classpath pe aake chup-chaap behaviour badalna rude hai.
  • L9@ConditionalOnMissingBean pe type explicitly likho. Bina argument ke woh method ka return type use karta hai; agar aapka custom bean subclass hai aur return type concrete hai, match fail ho jaata hai aur do beans register ho jaate hain.
  • L17–18Yeh file spring.factories ko replace karti hai. Ek line per class, no key. Boot 2.7 dono padhta hai (compatibility window), Boot 3.0+ sirf yeh. Library upgrade karte waqt sabse pehle yahi check karo.

TRADE-OFF · custom auto-configuration likhna

Apply karo jab
  • Aap ek internal platform starter bana rahe ho jo 5+ services use karengi
  • Cross-cutting concern hai: tracing, audit, tenant resolution, error contract
  • Consumers ko override karne ki zarurat hai
Ignore karo jab
  • Sirf 1–2 services use karengi — simple @Configuration kaafi hai
  • Aap conditions ka use "if-else in XML" ki tarah kar rahe ho
  • Team ke paas condition report debug karne ka experience nahi hai
Kyun
  • Auto-config ka cost invisible failure hai — bean chup-chaap gayab
  • Plain @Configuration loud fail karti hai, jo debug karna asaan hai
  • Magic tab justify hoti hai jab uska reuse ratio high ho
04

Async — proxy, pool aur context

@Async teen alag cheezein ek saath maangta hai: ek working proxy, ek named executor, aur context propagation. Teeno mein se koi ek bhi miss ho toh yeh production mein galat tareeke se fail hota hai — silently.

PROBLEM

Teen classic @Async failures

  • Self-invocation: same class ke andar method call — proxy bypass, sab kuch synchronous chalta hai aur koi error nahi aata
  • Default executor: Boot ka SimpleAsyncTaskExecutor (jab koi TaskExecutor bean na ho) har call pe naya thread banata hai — unbounded, no queue, OOM at load
  • Silent exceptions: void return karne wale @Async method ka exception kahin log hi nahi hota
  • Context loss: Security context, MDC, tenant ID — sab worker thread pe khali
OrderService.javagalat — self-invocation
1public void placeOrder(OrderRequest request) {
2  orderRepository.save(toEntity(request));
3  publishOrderPlacedEvent(request);  // this.* → proxy skip
4}
5@Async                              // ye annotation ab dead hai
6public void publishOrderPlacedEvent(OrderRequest r) { ... }
SOLUTION

Bounded pool + separate bean + handler

AsyncExecutionConfig.javaBoot 3.2+ / 4.x
1@Configuration
2@EnableAsync
3public class AsyncExecutionConfig implements AsyncConfigurer {
4
5  @Bean("orderEventExecutor")
6  public ThreadPoolTaskExecutor orderEventExecutor() {
7    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
8    executor.setCorePoolSize(8);
9    executor.setMaxPoolSize(16);
10    executor.setQueueCapacity(200);
11    executor.setRejectedExecutionHandler(
12            new ThreadPoolExecutor.CallerRunsPolicy());
13    executor.setThreadNamePrefix("order-evt-");
14    executor.setTaskDecorator(new ContextCopyingTaskDecorator());
15    executor.setWaitForTasksToCompleteOnShutdown(true);
16    executor.setAwaitTerminationSeconds(30);
17    executor.initialize();
18    return executor;
19  }
20
21  @Override
22  public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
23    return (throwable, method, params) ->
24        log.error("Async failure in {} args={}", method.getName(), params, throwable);
25  }
26}
27
28// alag bean — proxy ab beech mein hai
29@Component
30public class OrderEventPublisher {
31  @Async("orderEventExecutor")
32  public CompletableFuture<Void> publishOrderPlacedEvent(OrderId id) {
33    notificationGateway.sendOrderConfirmation(id);
34    return CompletableFuture.completedFuture(null);
35  }
36}
  • L5Executor ko naam do aur @Async("name") mein wahi naam likho. Ek shared default pool ka matlab hai: slow email calls aapke fast audit writes ko bhookha maar dengi. Har workload ka apna bulkhead.
  • L8–10Yeh teen numbers hi ThreadPoolExecutor ka poora behaviour decide karte hain. Order yeh hai: core threads bharo → queue bharo → tab jaake max tak grow karo. Yani agar queue 200 hai, thread 9 tab tak nahi banega jab tak 200 tasks queue mein na ho. Unbounded queue = maxPoolSize kabhi use hi nahi hoga.
  • L11–12CallerRunsPolicy = natural backpressure. Pool full hone pe task submitting thread (yani Tomcat worker) pe chalta hai, jisse woh request slow hoti hai aur upstream apne aap dheema hota hai. AbortPolicy (default) load pe requests drop karta hai.
  • L14TaskDecorator woh single hook hai jahan aap MDC, SecurityContext aur tenant copy karte ho. Boot 4 / Framework 7 mein Micrometer ContextSnapshot ke saath yeh kaam pehle se hota hai agar context-propagation classpath pe ho.
  • L15–16Graceful shutdown. Iske bina rolling deploy in-flight async tasks ko beech mein maar deta hai — jo aksar "kabhi kabhi email nahi jaata" bug ban jaata hai.
  • L22–24void-returning @Async methods ka exception kahin nahi jaata unless yeh handler ho. CompletableFuture return karo (L32) toh exception future mein aati hai — behtar, kyunki caller decide kar sakta hai.
  • L31Alag bean hone se call orderEventPublisher.publishOrderPlacedEvent(...) proxy se guzarta hai. Yahi self-invocation ka asli fix hai — @Autowired self-reference ya AopContext.currentProxy() nahi, jo dono code smell hain.

Virtual threads (Boot 3.2+) — kya badalta hai, kya nahi

spring.threads.virtual.enabled=true set karne se Tomcat har request ko virtual thread pe chalata hai aur Boot SimpleAsyncTaskExecutor ko virtual-thread mode mein daal deta hai. Badalta hai: blocking I/O ab sasta hai, 200-thread pool ki limit khatam. Nahi badalta: CPU-bound kaam (woh carrier threads pe hi hai), synchronized blocks (Java 21 mein pinning — Java 24+ mein largely fix), aur ThreadLocal-heavy libraries ka memory footprint. Aur sabse zaroori: connection pool abhi bhi bottleneck hai. 10,000 virtual threads 20 Hikari connections ke liye ladenge. Virtual threads ne bottleneck hataya nahi, use thread pool se connection pool pe shift kar diya.

TRADE-OFF · @Async vs message queue vs virtual threads

Apply karo jab
  • @Async: fire-and-forget jiska loss tolerable ho — cache warm, metrics push, best-effort notification
  • Queue (Kafka/SQS): kaam ka loss tolerable nahi — payment, invoice, outbox
  • Virtual threads: I/O-bound service jisme fan-out downstream calls ho
Ignore karo jab
  • @Async ko durability ke liye — JVM crash pe queue silently gayab
  • Virtual threads CPU-bound service pe — koi faayda nahi, sirf profiling confusion
  • Queue ek internal 50-req/day admin action ke liye — operational cost zyada hai
Kyun
  • @Async ki queue in-memory hai: crash = data loss, no retry, no DLQ
  • Virtual threads concurrency ka cost ghatate hain, capacity nahi
  • Durability ek storage property hai, thread model ki nahi

Transactions — boundary hi design hai

Ek transaction ka asli kharcha uska duration hai, uska kaam nahi. Har millisecond jab tak TX khuli hai, ek DB connection block hai aur DB pe locks tike hue hain. Isiliye TX boundary ek architecture decision hai, ek annotation nahi.

PROBLEM

Transaction ke andar HTTP call

CheckoutService.javagalat — connection starvation
1@Transactional
2public Receipt checkout(CartId cartId) {
3  Cart cart = cartRepository.findById(cartId).orElseThrow();
4  PaymentResult result =
5      paymentGateway.charge(cart.total());   // 900 ms external
6  cart.markPaid(result.reference());
7  return receiptFactory.from(cart);
8}
  • Hikari pool 20 connections · gateway 900 ms → max ~22 checkouts/sec, CPU 4% pe idle
  • HikariPool-1 - Connection is not available, request timed out after 30000ms
  • Gateway timeout → TX rollback, par paisa kat chuka hai. DB aur payment provider ab out of sync
  • Row locks 900 ms tak tike — same cart pe concurrent requests deadlock karti hain

Aur ek chhupa hua bug: @Transactional default sirf RuntimeException pe rollback karta hai. paymentGateway agar checked PaymentDeclinedException throw kare toh Spring commit kar dega.

SOLUTION

TX ko sirf DB ke aas-paas rakho

CheckoutOrchestrator.javaTX boundary shrunk + outbox
1@Service
2public class CheckoutOrchestrator {          // NO @Transactional here
3

5    CartSnapshot snapshot = cartReader.loadPayableSnapshot(cartId);
6    PaymentResult result = paymentGateway.charge(snapshot.total());
7    return checkoutWriter.recordSuccessfulPayment(cartId, result);
8  }
9}

  • L2Orchestrator pe TX nahi hai. Yeh sabse important line hai jo yahan nahi likhi gayi. Slow external call ab kisi bhi connection ke bahar hai.
  • L5–7Teen phases: read → external → write. Har phase ka apna short TX (ya koi TX nahi). Connection hold time 900 ms se ~4 ms ho gaya. Same 20-connection pool ab ~5000 checkouts/sec handle kar sakta hai.
  • L14timeout=3 ek circuit breaker hai TX level pe — koi bhi query jo pool ko 3 sec se zyada hold kare, marr jaayegi. rollbackFor=Exception.class checked exception wale silent-commit bug ko band karta hai. Team-wide baseline yahi hona chahiye.
  • L17Yahan koi save() call nahi hai — aur zarurat bhi nahi. Managed entity pe kiya gaya change dirty checking se flush hota hai commit ke waqt. Yeh JPA ka woh hissa hai jo sabse zyada galat samjha jata hai (animation section mein isi ko visually dikhaya hai).
  • L18Transactional outbox. Event usi TX mein DB pe likha jaata hai jisme business data. Ek separate poller use Kafka pe bhejta hai. Yeh dual-write problem solve karta hai bina distributed transaction (XA) ke — jo modern stacks mein practically dead hai.
  • L22REQUIRES_NEW outer TX ko suspend karke naya connection leta hai. Failure ko audit karne ke liye sahi (outer roll back hoga, yeh nahi), par yeh do connections ek saath hold karta hai — pool exhaustion ka classic route. Kabhi loop ke andar mat rakho.
  • L28readOnly=true sirf hint nahi hai: Hibernate flush mode MANUAL kar deta hai (dirty-check skip = tez), aur JDBC driver ko batata hai, jisse read replica routing possible hoti hai.

TRADE-OFF · transaction boundary

Apply karo jab
  • TX service layer pe, use-case ke around — repository pe nahi
  • Har write TX pe explicit timeout

AOP — proxy ka mechanics

@Transactional, @Async, @Cacheable, @Retryable, @PreAuthorize — yeh sab ek hi machine hain: proxy + interceptor chain. Ek baar yeh machine samajh aa gayi toh in sabke saare bugs ek hi shakal ke lagte hain.

PROBLEM

Proxy kab kaam nahi karta

  • Self-invocation — this.method() proxy ke bahar hai
  • private / final method — CGLIB override nahi kar sakta, annotation silently ignore
  • final class — CGLIB subclass hi nahi bana sakta, startup pe error
  • static method — proxy ka concept hi lagu nahi
  • new se banaya object — Spring container ke bahar, koi proxy nahi
  • @PostConstruct se call — bean abhi poori tarah proxy-wrapped nahi hua

Sabse mehnga: in sab cases mein koi exception nahi aata. @Transactional bas nahi lagta, aur aapko pata chalta hai tab jab data half-written mil jaata hai.

SOLUTION

Embedded Tomcat tuning

Tomcat ke sirf chaar numbers matter karte hain, aur unmein se teen ek dusre se bandhe hue hain. Inhe alag-alag tune karna sabse common capacity-planning galti hai.

PROBLEM

"Threads badha do" — jo kabhi kaam nahi karta

  • Latency spike aaya, kisi ne max-threads: 800 kar diya
  • Hikari pool abhi bhi 10 pe hai → 800 threads 10 connections pe queue
  • Latency badh gayi (ab queue thread pool mein bhi hai aur pool mein bhi), throughput same
  • GC pressure badh gayi: 800 × 1 MB stack = 800 MB reserved
  • Deploy pe in-flight requests kat jaati hain — graceful shutdown off hai

Asli rule: ek service ki concurrency uska sabse tang resource decide karta hai. Aksar woh DB connection pool hota hai, ya downstream service ka rate limit. Thread count usse zyada rakhna sirf queue ki jagah badalna hai, capacity badhana nahi.

Q1Boot 2 se Boot 3 mein sabse bada breaking change kya hai, aur uska blast radius kya hai?migration

Change: javax.* → jakarta.* namespace, kyunki Oracle ne "Java EE" trademark Eclipse Foundation ko transfer karte waqt package naam use karne nahi diya. Yeh cosmetic rename nahi hai — yeh binary incompatible hai.

Blast radius (yahi asli jawab hai): aapka apna code sabse chhota hissa hai; usse openrewrite 20 minute mein fix kar deta hai. Asli problem transitive dependencies hain — koi bhi library jo javax.servlet, javax.persistence, javax.validation ya javax.annotation ke against compile hui hai, woh runtime pe NoClassDefFoundError degi. Isme aksar internal shared libraries, purane SOAP/JAXB clients, monitoring agents aur servlet filters aate hain.

Practical first step: code touch karne se pehle mvn dependency:tree se poori inventory banao aur har third-party jar ka Jakarta-compatible version dhoondo. Agar koi ek bhi library abandoned hai, woh aapka critical path hai — migration ka schedule usi se decide hoga, aapke code se nahi.

Q2spring.factories ko auto-config ke liye kyun hataya gaya, aur upgrade pe iska symptom kya hota hai?LLD

spring.factories ek multi-purpose key-value file thi jisme har entry ke liye poori file parse honi padti thi, aur auto-config entries ek hi lambi comma-separated line mein hoti thi — diff karna aur maintain karna dono kharab. Boot 3.0 se auto-configurations ke liye META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports use hoti hai: ek class per line, no key, faster parsing aur AOT-friendly.

Symptom: koi exception nahi aata. Library load hoti hai, jar classpath pe hai, par uska bean kabhi register nahi hota. Aapko NoSuchBeanDefinitionException kisi bilkul alag jagah milta hai. --debug se condition report nikalo — agar aapki auto-config class na positiveMatches mein hai na negativeMatches mein, iska matlab woh discover hi nahi hui. Yeh single diagnostic ghanton bacha deta hai.

spring.factories abhi bhi ApplicationListener, EnvironmentPostProcessor, FailureAnalyzer jaise doosre extension points ke liye zinda hai — sirf auto-config uske se nikli hai.

Q3Self-invocation pe @Transactional kaam kyun nahi karta? Teen fixes aur unke trade-offs?trap

Kyun: Spring AOP proxy-based hai. Container aapke bean ka ek proxy inject karta hai; annotation ka behaviour proxy par lagta hai, target object pe nahi. Jab aap class ke andar this.method() likhte ho, call proxy ke through jaati hi nahi — woh direct target instance pe hai. Interceptor chain skip.

Fix 1 — method ko alag bean mein nikalo. ✅ Recommended. Cost: ek extra class. Faayda: TX boundary code padh ke dikh jaati hai; koi runtime magic nahi. Zyadatar cases mein yeh design ko behtar hi banata hai, kyunki alag TX boundary ka matlab hai alag responsibility.

Fix 2 — self-injection (@Autowired @Lazy OrderService self) ya AopContext.currentProxy(). ⚠️ Kaam karta hai par circular reference banata hai (Boot 2.6+ mein by default disallowed, explicitly enable karna padta hai) aur naye readers ko confuse karta hai. Sirf legacy code mein use karo jahan class todna mehnga ho.

Fix 3 — AspectJ load-time / compile-time weaving. ❌ Technically sahi (bytecode weave hota hai, proxy nahi), self-invocation bhi kaam karta hai. Par cost bahut zyada: build complexity, javaagent, IDE support issues, aur debugging mein bytecode aapke source se match nahi karta. Ek design problem ke liye poore build system ka change — 99% cases mein galat trade hai.

Interviewer ko yeh sunna hai: "Main Fix 1 lunga, kyunki self-invocation ki problem actually ek missing boundary ki nishani hai."

Q4Hikari pool size kaise decide karoge? Kya formula hai?perf

HikariCP ki apni guidance: connections = ((core_count × 2) + effective_spindle_count) — yeh database server ke resources pe based hai, aapke app pe nahi. Modern SSD/cloud DB pe practically iska matlab hai: chhota pool rakho. 8-core DB pe ~20 connections per instance kaafi hain.

Asli constraint jo log bhool jaate hain: pool per-pod hai. 50 pods × 20 = 1000 connections. PostgreSQL default max_connections 100 hai, aur har connection ~10 MB backend memory leta hai. Toh formula yeh hona chahiye: pool_size ≤ (db_max_connections × 0.8 - admin_reserve) / max_pod_count. Agar yeh number 5 se neeche jaa raha hai, aapko PgBouncer jaisa external pooler chahiye — pool tuning se problem solve nahi hogi.

Aur zyada important: pool badhane se pehle hold time ghatao. 20 connections × 5 ms hold = 4000 TPS. 100 connections × 500 ms hold = 200 TPS. Ek slow query ya TX ke andar chhupa hua HTTP call theek karna pool doubling se hamesha behtar hai.

Q5Virtual threads on karne se aapke system mein kya-kya badlega?HLD

Badalta hai: Tomcat ab har request ko naya virtual thread deta hai — 200-thread ceiling khatam. Blocking I/O sasta ho jaata hai: 10,000 concurrent blocked requests ab ~10,000 platform threads nahi maangti.

Nahi badalta (aur yahi jawab ka core hai):

  • Downstream capacity. Bottleneck thread pool se DB pool / downstream rate limit pe shift ho jaata hai. Ab aapke paas 10,000 threads hain jo 20 connections ke liye lad rahe hain — pehle backpressure Tomcat pe thi, ab woh Hikari pe hai aur wahan timeouts different hain.
  • CPU-bound kaam. Virtual threads carrier (platform) threads pe hi chalte hain. Compute mein koi faayda nahi.
  • Pinning. Java 21 mein synchronized block ke andar blocking carrier thread ko pin kar deta hai. Purani JDBC drivers aur logging libraries isse affected hain. JDK 24+ mein largely address ho gaya hai, par apni library versions verify karo.
  • ThreadLocal-heavy code. Ab 10,000 copies ho sakti hain. MDC aur SecurityContext memory footprint badh jaata hai.

Isliye zaroori hai: virtual threads ke saath explicit admission control lagao — semaphore, @ConcurrencyLimit (Boot 4), ya bounded queue. Warna aapne ek fail-fast system ko ek slowly-collapsing system mein badal diya.

Q6@Async void method ka exception kahan jaata hai?trap

Kahin nahi. Task executor pe submit hota hai, exception Future mein capture hoti hai, aur kyunki return type void hai, koi us future ko hold hi nahi karta. Exception silently discard ho jaati hai.

Do fixes: (1) AsyncConfigurer.getAsyncUncaughtExceptionHandler() implement karo — yeh sirf void methods ke liye chalta hai. (2) Behtar: CompletableFuture<T> return karo, tab exception future mein aati hai aur caller .exceptionally() / .handle() se decide kar sakta hai.

Follow-up jo aksar aata hai: "@Async + @Transactional ek hi method pe?" — Do proxy interceptors hain. Async pehle chalta hai, toh method naye thread pe jaata hai aur wahan naya TX shuru hota hai. Caller ka TX inherit nahi hota (TX ThreadLocal pe bind hai). Iska matlab: caller commit ho sakta hai aur async part fail ho sakta hai, ya ulta. Agar aap consistency chahte ho toh @TransactionalEventListener(phase = AFTER_COMMIT) use karo — tab async kaam tabhi shuru hoga jab main TX safely commit ho chuki ho.

Q7Tomcat ke max-threads badhane se throughput kyun nahi badhta?perf

Little's Law: concurrency = throughput × latency. Throughput system ke sabse tang resource se decide hota hai, threads se nahi. Agar DB pool 20 hai aur har request 50 ms DB pe kharch karti hai, toh ceiling 400 req/s hai — chahe aap 60 threads rakho ya 800.

800 threads rakhne se jo actually hota hai: (a) 800 MB+ stack memory reserve, (b) zyada context switching, (c) queue Tomcat se hat ke Hikari pe chali gayi jahan uski visibility kam hai, (d) latency badh gayi kyunki ab requests do jagah wait kar rahi hain, aur (e) load shedding khatam — pehle Tomcat busy hone pe reject karta tha (jo LB ko signal deta tha), ab sab accept hokar dheere-dheere timeout hoti hain.

Sahi approach: bottleneck ko measure karo (thread dump lo — threads kis state mein hain?), phir usi ko fix karo. Aur thread count ko downstream capacity se thoda upar rakho, taaki backpressure wahin lage jahan woh visible ho.

Q8Dirty checking kya hai? Update ke liye save() kab zaroori hai aur kab nahi?LLD

Dirty checking: jab Hibernate ek entity load karta hai, woh uske field values ka ek snapshot persistence context mein rakh leta hai. Flush ke waqt (aksar commit se just pehle) woh current values ko snapshot se compare karta hai aur sirf changed entities ke liye UPDATE generate karta hai.

Isliye: ek managed entity pe setter call karna hi kaafi hai. save() ki zarurat nahi — woh merge() call karega jo managed entity pe practically no-op hai (bas ek extra check aur potential copy).

save() zaroori hai jab: (a) entity NEW hai (persist chahiye), (b) entity detached hai — jaise DTO se banayi gayi, ya kisi purani TX se aayi, ya em.clear() ke baad. Detached entity pe setter kuch nahi karta aur koi error bhi nahi aata — yeh silent data loss hai.

Architect-level addition: @DynamicUpdate se sirf changed columns UPDATE hote hain. Default behaviour sab columns likhna hai, jo wide tables pe row-lock contention aur replication traffic badhata hai — par har flush pe SQL string cache miss bhi karta hai, toh yeh measure karke lagane wali cheez hai, default nahi.

Q9LazyInitializationException — root cause aur chaar fixes with trade-offs?trap

Root cause: lazy association ko tab access kiya gaya jab persistence context band ho chuka tha — aksar controller ya Jackson serialization ke waqt, kyunki TX service layer pe khatam ho gayi thi.

  • Fix 1 — JOIN FETCH ya @EntityGraph query pe. ✅ Best default. Aap explicitly bolte ho ki is use-case ko kya chahiye. Cost: har use-case ke liye alag query. Faayda: N+1 bhi solve, aur data requirement code mein documented.
  • Fix 2 — DTO projection. ✅ Best for read APIs. Entity controller tak jaati hi nahi. Cost: mapping code. Faayda: over-fetching khatam, API contract entity se decouple.
  • Fix 3 — open-in-view: true. ❌ Boot mein default true hai aur startup pe warn karta hai. Exception "chali jaati hai" par cost bhayanak: DB connection poore request ke liye hold hoti hai, aur lazy loads view rendering ke waqt trigger hote hain — matlab N+1 queries invisible ho jaati hain. Ise explicitly false karo aur jo toote use theek karo. Yeh migration ka acha pehla task hai.
  • Fix 4 — FetchType.EAGER. ❌ Sabse kharab. Problem ko poore application pe fail deta hai — ab har query, har jagah, woh association fetch karegi chahe zarurat ho ya na ho. Cartesian products aur N+1 dono milte hain.
Q10Security config mein securityMatcher aur requestMatchers mein kya farak hai?LLD

securityMatcher(...) — chain-level. Yeh decide karta hai ki yeh poori filter chain kis request pe apply hogi. Agar match nahi hua, Spring agli chain dekhta hai.

requestMatchers(...) — rule-level, authorizeHttpRequests ke andar. Yeh decide karta hai ki us chain ke andar kis path ko kya authority chahiye.

Critical behaviour: chains @Order ke hisaab se evaluate hoti hain aur pehla matching chain jeet jaata hai — baaki chains dekhi bhi nahi jaati. Toh agar aapki pehli chain ka securityMatcher bahut broad hai (ya hai hi nahi, jo "sab" ka matlab hai), aapki baaki saari chains dead code hain. Yeh production security holes ka common source hai kyunki koi error nahi aata.

Debug: logging.level.org.springframework.security=DEBUG se dikh jaata hai ki kaunsi chain match hui aur kaunse filters chale.

Q11hasRole("ADMIN") aur hasAuthority("ADMIN") mein kya farak hai? Kya use karoge?trap

hasRole("ADMIN") internally "ROLE_ADMIN" authority dhoondta hai — prefix Spring apne aap laga deta hai. hasAuthority("ADMIN") exactly "ADMIN" dhoondta hai.

Problem yeh hai: OAuth2 resource server JWT scopes ko SCOPE_ prefix deta hai, LDAP ROLE_ deta hai, aur custom converters kuch bhi de sakte hain. Mismatch pe aapko 403 milta hai bina kisi useful log ke — bas "Access Denied".

Team convention: hamesha hasAuthority with the full literal string. Prefix implicit rakhne se koi faayda nahi hota, sirf ek chhupa hua contract banta hai jo naya joiner nahi jaanta. Agar aap hasRole use karte ho, toh authority converter ko codebase mein ek jagah rakho aur uspe test likho jo actual JWT sample verify kare.

Q12Spring Boot CGLIB use karta hai ya JDK dynamic proxy? Iska practical asar kya hai?LLD

Boot 2.0 se spring.aop.proxy-target-class=true default hai — yani hamesha CGLIB (subclass-based), chahe class interface implement karti ho. Plain Spring Framework ka default alag tha (interface ho toh JDK proxy).

Practical asar:

  • Class final nahi ho sakti; final/private/static methods intercept nahi honge — aur chup-chaap ignore honge. Kotlin mein yeh badi problem thi (classes default final), isliye kotlin-spring plugin exist karta hai.
  • Spring 6+ Objenesis se instance banata hai, toh proxy ka constructor nahi chalta. Field initializers proxy pe null rahenge. Isliye proxy ke fields pe kabhi bharosa mat karo — hamesha methods se jao.
  • Native image (GraalVM) mein CGLIB runtime bytecode generation problematic hai; isiliye Boot AOT processing build time pe proxies generate karta hai.

Design implication: agar aap chahte ho ki interception guaranteed ho, toh public methods pe annotate karo aur classes ko non-final rakho — ya behtar, interface-driven design use karo taaki intent explicit ho.

Q13Custom aspect ko @Transactional ke andar chalana hai ya bahar? Kaise decide karoge?LLD

Interceptor chain @Order se banti hai — chhota number = bahar (pehle chalega). Spring ka TransactionInterceptor default Ordered.LOWEST_PRECEDENCE pe hai, yani sabse andar.

TX ke andar rakho (order = LOWEST_PRECEDENCE - N) jab aapka aspect DB pe likhta hai aur uska write business write ke saath atomic hona chahiye — jaise audit row jo rollback pe bhi gayab ho jaani chahiye.

TX ke bahar rakho (chhota order) jab aapka aspect commit/rollback ka result observe karna chahta hai — jaise metrics, timing, ya error rate. Bahar hone se aap commit() mein aayi exception bhi pakad sakte ho, jo andar se dikhti hi nahi.

Trap: agar aapka aspect exception nigal leta hai (rethrow nahi karta) aur woh TX ke andar hai, toh transaction commit ho jaayega — kyunki TransactionInterceptor ko exception dikhi hi nahi. Yeh AOP ka sabse mehnga single-line bug hai.

Q14Distributed transaction chahiye — order service aur payment service dono update karne hain. Kya karoge?HLD

Pehla jawab: 2PC/XA mat karo. Kaam karta hai par cost bahut zyada hai — coordinator ek naya single point of failure hai, locks network round-trips tak hold hote hain, aur cloud-managed DBs / Kafka mein XA support aksar hai hi nahi ya second-class hai. Modern distributed systems mein yeh practically dead hai.

Recommended: Transactional Outbox + Saga.

  1. Order service apni local TX mein dono likhta hai: business row aur ek outbox row. Yeh ek hi DB hai, toh atomicity free hai.
  2. Ek separate poller (ya Debezium/CDC) outbox se padh ke Kafka pe publish karta hai, phir row mark karta hai.
  3. Payment service consume karta hai, apna kaam karta hai, aur apna event publish karta hai.
  4. Failure pe compensating action (refund, cancel) — rollback nahi, compensation.

Jo trade-off aapko naam lekar batana hai: yeh eventual consistency hai, strong nahi. Delivery at-least-once hai, toh har consumer ko idempotent banana hi padega (dedupe key / natural idempotency). Aur ek window hoti hai jisme order "paid" dikhta hai par payment abhi confirm nahi hui — yeh business ko explicitly accept karna hoga (UI mein "processing" state). Agar business yeh accept nahi kar sakti, toh aapko services ko merge karna chahiye, distributed transaction nahi.

Q15Boot 4 ke modular starters se aapki build mein kya toota, aur aap uska plan kaise banayenge?migration

Kya hua: pehle spring-boot-autoconfigure ek bada jar tha jisme sab auto-configurations thin. Boot 4 mein woh chhote, feature-specific modules mein split ho gaya hai. Faayda: lean classpath, tez startup, chhoti native images, saaf module boundaries.

Kya toota: jo classes aap transitively paa rahe the, woh ab nahi aatin. Symptom runtime ClassNotFoundException hai — compile pe pata nahi chalta agar aap us class ko directly import nahi karte (jaise ek auto-config jo kisi aur module mein chali gayi).

Plan (do-step, deliberately):

  1. Step A: spring-boot-starter-classic add karke Boot 4 pe upgrade karo. Yeh purana "sab kuch ek jagah" layout wapas de deta hai. Ab aapke paas ek chalti hui Boot 4 app hai, aur aap Jackson 3 / JSpecify jaise asli changes pe focus kar sakte ho.
  2. Step B (alag PR, alag sprint): starter-classic hatao, explicit modular starters add karo, aur integration tests se verify karo. Yahan har missing module ek chhota fix hai.

Kyun do steps: ek hi PR mein karne se aapko pata nahi chalega ki failure Jackson ki wajah se hai ya missing module ki. Bridge module ka poora maqsad ek waqt pe ek variable badalna hai. Par uski expiry date CI mein likh do — warna woh permanent ho jaayega.

Q16Jackson 2 → 3 migration mein kya-kya toot sakta hai?migration
  • Package rename: com.fasterxml.jackson.databind → tools.jackson.databind. Core imports sab badalne padenge.
  • Annotations same rehte hain: jackson-annotations 2.x dono versions ke saath kaam karta hai. Yeh deliberately kiya gaya hai taaki shared domain models na tootein — par iska side effect yeh hai ki aapka code compile ho jaata hai aur aapko lagta hai migration ho gaya, jabki runtime behaviour badal chuka hai.
  • Immutable mappers: Jackson 3 mein JsonMapper build ke baad configure nahi ho sakta. Jo bhi code mapper.configure(...) ya setSerializationInclusion(...) runtime pe karta tha, use builder pe shift karna hoga.

Q17Kubernetes pe graceful shutdown ka poora sequence samjhaao. Kahan-kahan galti hoti hai?HLD

Sahi sequence:

  1. Pod ko Terminating mark kiya jaata hai; endpoints controller use Service se hatata hai. Yeh async hai — kubelet ka SIGTERM aur LB ka update ek saath nahi hote.
  2. Kubelet preStop hook chalata hai, phir SIGTERM bhejta hai.
  3. Boot server.shutdown=graceful pe: Tomcat naye connections lena band karta hai, in-flight requests ko spring.lifecycle.timeout-per-shutdown-phase tak complete hone deta hai.
  4. Context close: @PreDestroy, executors ka awaitTermination, Hikari pool close.
  5. terminationGracePeriodSeconds ke baad SIGKILL.

Galti #1 (sabse common): LB abhi bhi traffic bhej raha hai jab app shutdown shuru kar chuki hai — kyunki step 1 async hai. Fix: preStop: sleep 5 lagao. Yeh counter-intuitive lagta hai par yahi standard fix hai: 5 second de do taaki endpoint removal propagate ho jaaye, tab shutdown shuru ho.

Galti #2: terminationGracePeriodSeconds (default 30) app ke shutdown timeout se chhota hona. Tab kubelet SIGKILL bhej dega aur graceful shutdown ka koi matlab nahi rahega. Rule: terminationGracePeriod > preStop sleep + shutdown timeout + buffer.

Galti #3: readiness probe ko liveness probe jaisa treat karna. Shutdown ke waqt readiness fail honi chahiye (traffic band), liveness nahi (warna kubelet turant maar dega).

Q18MDC / SecurityContext thread pool mein leak kaise hota hai? Kaise rokoge?trap

Mechanism: MDC aur SecurityContextHolder dono ThreadLocal pe based hain. Thread pool mein threads reuse hote hain. Agar request ke end mein clear nahi kiya, toh agli request usi thread pe purana userId, traceId ya poora Authentication object dekh legi.

Impact: logs mein galat customer ka data (compliance incident), aur worst case mein authorization decision purane user ke context pe. Yeh sirf bug nahi, yeh security issue hai.

Prevention:

  • Request ke liye: Spring ka SecurityContextPersistenceFilter / MDCInsertingServletFilter yeh handle karte hain — agar aapne custom filter likha hai toh finally block mein clear karna aapki zimmedari hai.
  • Manual MDC ke liye: try (MDC.MDCCloseable c = MDC.putCloseable(k, v)) — try-with-resources hi use karo, plain put() nahi.
  • Async ke liye: TaskDecorator jo copy karta hai aur finally mein clear bhi karta hai. Sirf copy karna aadha kaam hai — worker thread pe bhi leak hota hai.
  • Boot 3.2+ / 4.x mein Micrometer context-propagation library yeh standardise karti hai; use prefer karo apne custom decorator pe.

Test kaise karein: ek integration test jo same executor pe do requests chalaye, aur assert kare ki dusri request ka MDC pehli ka data na dekhe. Yeh test aksar likha nahi jaata, isiliye yeh bug prod tak pahunchta hai.

Q20Boot 4 ke @Retryable aur @ConcurrencyLimit — kab use karoge aur kab Resilience4j?HLD

Boot 4 mein spring-boot-starter-resilience basic patterns framework mein hi le aata hai: @Retryable (exponential backoff + jitter ke saath) aur @ConcurrencyLimit (bulkhead). Yeh spring-context par based hai, koi external dependency nahi.

Built-in use karo jab: simple retry chahiye (transient network error, 503), ya ek downstream ke liye concurrency cap chahiye. Faayda: ek kam dependency, Boot ke saath version-aligned, aur observability already wired.

Resilience4j use karo jab: aapko circuit breaker chahiye state machine ke saath (closed → open → half-open), sliding-window failure rate, rate limiter, ya bulkhead metrics jo aap Grafana pe chahte ho. Built-in retry circuit breaker nahi hai — yeh important distinction hai.

Trade-off jo naam lena hai: retry without circuit breaker = retry storm. Agar downstream down hai aur aapki 200 instances har request 3 baar retry kar rahi hain, aapne load 3× kar diya jab woh already gir raha hai. Retry hamesha (a) circuit breaker ke saath, (b) jitter ke saath, aur (c) sirf idempotent operations pe. Non-idempotent POST retry karna duplicate order banata hai — isliye idempotency key ka design retry se pehle aata hai.
