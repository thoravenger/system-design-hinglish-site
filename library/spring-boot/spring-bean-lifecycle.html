What is the Bean Lifecycle?

The Spring Bean Lifecycle is the sequence of steps Spring follows from the moment it decides to create a bean to the moment the application context is closed. Understanding it lets you hook into any phase for custom initialization, resource setup, validation, and cleanup.

Why It Matters
  • Open DB connections after all properties injected
  • Validate required config before serving traffic
  • Register listeners/metrics/caches at startup
  • Close file handles / connections on shutdown
  • Implement AOP proxies at the right moment
  • Control bean creation order (dependencies)
The 3 Big Phases
1. INITIALIZATION
→ Create + Wire + Init hooks
2. USE
→ Application uses the bean
3. DESTRUCTION
→ Context closes + cleanup

Instantiation — How Spring Creates Beans

// ── 3 ways Spring instantiates beans ─────────────────────────────────

// 1. Component scanning — most common
@Service                   // shortcut for @Component + "service layer" semantics
@Repository               // @Component + translates persistence exceptions
@Controller               // @Component + web layer
@RestController           // @Controller + @ResponseBody
@Component                // base annotation — generic bean
public class OrderService {}

// 2. @Configuration + @Bean — for beans you DON'T own (third-party libs)
@Configuration
public class AppConfig {

    @Bean                          // method name = bean name by default
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
            .findAndRegisterModules();
    }

    @Bean("myDataSource")        // explicit bean name
    @Primary                       // preferred when multiple DataSources
    public DataSource dataSource() {
        return new HikariDataSource(config());
    }
}

// 3. @Import — import other @Configuration classes
@SpringBootApplication
@Import({SecurityConfig.class, CacheConfig.class})
public class App {}

Instantiation
Constructor Injection — PREFERRED ✅
@Service
public class OrderService {
    private final OrderRepo    repo;   // final!
    private final EmailService email;  // final!

    // @Autowired not needed if only 1 constructor (Spring 4.3+)
    public OrderService(OrderRepo r, EmailService e) {
        this.repo  = r;
        this.email = e;
    }
}
  • Dependencies are final — immutable
  • Fails fast at startup if dep missing
  • Easy to unit test (plain new)
  • No circular dependency surprises
Field Injection — AVOID ❌
@Service
public class OrderService {
    @Autowired
    private OrderRepo repo;     // ❌ not final
    @Autowired
    private EmailService email; // ❌ null in tests!
}
  • Can't unit test without Spring context
  • Can't make fields final
  • Hides dependencies — hard to see what's needed
  • Circular dep errors surface later (runtime)
// ── BeanFactoryPostProcessor — modify definitions BEFORE creation ─────
// Runs before ANY beans are instantiated
// Use: custom property placeholders, bean definition modification

@Component
public class CustomBFPP implements BeanFactoryPostProcessor {

    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory factory) {
        // View all registered bean definitions
        String[] names = factory.getBeanDefinitionNames();

        // Modify a specific bean definition
        BeanDefinition bd = factory.getBeanDefinition("orderService");
        bd.setScope(BeanDefinition.SCOPE_PROTOTYPE); // change scope dynamically

        // Built-in BFPP: PropertySourcesPlaceholderConfigurer
        // resolves ${spring.datasource.url} in @Value — runs as BFPP
    }
}

Dependency Injection — All Types

// ── @Autowired resolution order ──────────────────────────────────────
// Spring tries in this order:
// 1. Match by TYPE — if exactly one bean of that type → inject it
// 2. Match by NAME — if multiple beans of same type → match by parameter name
// 3. @Qualifier — explicitly specify which bean to inject
// 4. @Primary — one bean marked @Primary → preferred in ambiguous cases

@Service
public class NotificationService {

    // Multiple EmailSender beans → use @Qualifier to disambiguate
    private final EmailSender primarySender;
    private final EmailSender backupSender;

    public NotificationService(
            @Qualifier("smtpSender")   EmailSender primarySender,
            @Qualifier("sendGridSender") EmailSender backupSender) {
        this.primarySender = primarySender;
        this.backupSender  = backupSender;
    }
}

// ── Inject all beans of a type into a List ───────────────────────────
@Service
public class PaymentService {
    private final List<PaymentGateway> gateways; // Spring injects ALL PaymentGateway beans

    public PaymentService(List<PaymentGateway> gateways) {
        this.gateways = gateways;
    }
}

// ── @Value — inject from application.yml ─────────────────────────────
@Service
public class FeeCalculator {
    @Value("${app.fee.percentage:2.5}")   // with default value
    private double feePercentage;

    @Value("#{systemProperties['user.timezone']}") // SpEL expression
    private String timezone;

    @Value("${app.allowed-currencies}")   // comma-separated list
    private List<String> allowedCurrencies;
}

// ── @ConfigurationProperties — type-safe config (preferred over @Value) ─
@ConfigurationProperties(prefix = "app.payment")
public record PaymentConfig(
    String   gatewayUrl,
    int      timeoutMs,
    int      retryCount,
    String   apiKey,
    List<String> supportedCurrencies
) {}
// application.yml:
// app.payment.gateway-url: https://stripe.com
// app.payment.timeout-ms: 5000

Aware Interfaces — Access Spring Infrastructure

Aware interfaces let your bean access parts of the Spring infrastructure it's running in. They are called after injection but before @PostConstruct.

// ── All important Aware interfaces ───────────────────────────────────

@Component
public class AwareDemo implements
        BeanNameAware,            // get this bean's name in ApplicationContext
        BeanFactoryAware,         // access BeanFactory to get other beans programmatically
        ApplicationContextAware,  // access full ApplicationContext
        EnvironmentAware,         // access Environment (profiles, properties)
        ResourceLoaderAware,      // access classpath resources
        MessageSourceAware {       // access i18n messages

    private String             beanName;
    private BeanFactory        factory;
    private ApplicationContext context;
    private Environment        env;

    @Override
    public void setBeanName(String name) {
        this.beanName = name;
        log.info("My bean name: {}", name); // "awareDemo"
    }

    @Override
    public void setBeanFactory(BeanFactory beanFactory) {
        this.factory = beanFactory;
        // Can now do: factory.getBean(SomeService.class)
        // But prefer constructor injection — this is for special cases
    }

    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        this.context = ctx;
        // Access any bean, publish events, check environment
        boolean isWeb = ctx instanceof WebApplicationContext;
    }

    @Override
    public void setEnvironment(Environment env) {
        this.env = env;
        String profile = env.getActiveProfiles()[0]; // "prod", "dev"
        String url     = env.getProperty("spring.datasource.url");
    }
}

// ── REAL USE CASE: ApplicationContextAware for dynamic bean lookup ────
// Sometimes you need to look up beans dynamically at runtime
// (e.g. strategy pattern, plugin system)

@Component
public class PaymentStrategyFactory implements ApplicationContextAware {

    private ApplicationContext context;

    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        this.context = ctx;
    }

    public PaymentGateway getGateway(String type) {
        // Dynamically get bean by name at runtime (can't inject at construction)
        return context.getBean(type + "Gateway", PaymentGateway.class);
    }
}

Aware Interfaces
⚠️
Prefer constructor injection over ApplicationContextAware. Using ApplicationContext.getBean() everywhere is the service locator anti-pattern — it hides dependencies and makes code hard to test. Only use Aware interfaces when truly necessary (plugin systems, framework code).

BeanPostProcessor — The Most Powerful Extension Point

BeanPostProcessor (BPP) is called for every single bean in the context — before and after initialization. It's how Spring implements @Transactional, @Async, @Cacheable, and all AOP features.

// ── BPP signature ────────────────────────────────────────────────────
public interface BeanPostProcessor {

    // Called BEFORE @PostConstruct / afterPropertiesSet / initMethod
    default Object postProcessBeforeInitialization(Object bean, String beanName) {
        return bean; // return SAME bean (or a modified/wrapped version)
    }

    // Called AFTER @PostConstruct / afterPropertiesSet / initMethod
    default Object postProcessAfterInitialization(Object bean, String beanName) {
        return bean; // return PROXY instead of original bean for AOP!
    }
}

// ── Custom BPP: validate all beans with @RequiredConfig ───────────────
@Component
public class RequiredConfigBPP implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        // Check all @RequiredProperty fields are not null
        Field[] fields = bean.getClass().getDeclaredFields();
        for (Field f : fields) {
            if (f.isAnnotationPresent(RequiredProperty.class)) {
                f.setAccessible(true);
                try {
                    if (f.get(bean) == null)
                        throw new BeanCreationException(name,
                            "Required property '" + f.getName() + "' is null");
                } catch (IllegalAccessException e) { throw new RuntimeException(e); }
            }
        }
        return bean;
    }
}

// ── Custom BPP: wrap beans with timing proxy ─────────────────────────
@Component
public class TimingBPP implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        // Wrap beans with @Timed annotation in a timing proxy
        if (!bean.getClass().isAnnotationPresent(Timed.class)) return bean;

        return Proxy.newProxyInstance(
            bean.getClass().getClassLoader(),
            bean.getClass().getInterfaces(),
            (proxy, method, args) -> {
                long start = System.nanoTime();
                try {
                    return method.invoke(bean, args);
                } finally {
                    long ms = (System.nanoTime() - start) / 1_000_000;
                    log.info("{}.{}() took {}ms", name, method.getName(), ms);
                }
            }
        );
    }
}

// ── How @Transactional actually works via BPP ─────────────────────────
// Spring's InfrastructureAdvisorAutoProxyCreator (a BPP):
// 1. postProcessAfterInitialization() is called for your OrderService
// 2. Detects @Transactional on methods
// 3. Creates a CGLIB subclass proxy of OrderService
// 4. Returns the PROXY, NOT the original OrderService
// 5. Your bean reference in other services = the PROXY
// 6. Every method call goes through the proxy's transaction interceptor

Initialization Methods — @PostConstruct, InitializingBean, initMethod

// ── All 3 init mechanisms — execution order within init phase ─────────

@Service
public class CacheService implements InitializingBean {

    private final CacheRepository repo;
    private final String region;

    public CacheService(CacheRepository repo, @Value("${cache.region}") String region) {
        this.repo   = repo;
        this.region = region;
        // ⚠️ Do NOT use @Value fields here — they're injected AFTER constructor
        // @Autowired fields also null here — use @PostConstruct instead
    }

    // 1. @PostConstruct — runs FIRST (JSR-250, not Spring-specific)
    // ✅ All dependencies + @Value already injected at this point
    // ✅ Use this for most initialization logic
    @PostConstruct
    public void init() {
        log.info("Loading cache for region: {}", region);
        repo.warmUp(region);                   // safe: repo is injected
    }

    // 2. afterPropertiesSet — runs SECOND (Spring-specific)
    // ⚠️ Tightly couples to Spring — prefer @PostConstruct
    @Override
    public void afterPropertiesSet() {
        if (region == null || region.isBlank())
            throw new IllegalStateException("cache.region must not be empty");
    }
}

// 3. initMethod — runs THIRD (specified in @Bean)
// ✅ Best for third-party classes you don't control
@Configuration
public class ThirdPartyConfig {

    @Bean(initMethod = "connect")   // "connect()" called after BPP
    public RedisClient redisClient() {
        return new RedisClient("localhost", 6379);
    }
}

// ── REAL USE CASE: @PostConstruct for startup validation ──────────────
@Component
@ConfigurationProperties(prefix = "payment")
public class PaymentConfigValidator {

    private String apiKey;
    private String webhookSecret;
    private String gatewayUrl;

    @PostConstruct
    public void validate() {
        // App fails to start if payment config is invalid — better than runtime NPE
        Assert.hasText(apiKey,         "payment.api-key must not be empty");
        Assert.hasText(webhookSecret,  "payment.webhook-secret must not be empty");
        Assert.hasText(gatewayUrl,     "payment.gateway-url must not be empty");
        if (!gatewayUrl.startsWith("https"))
            throw new IllegalStateException("payment.gateway-url must use HTTPS");
        log.info("Payment config validated ✓ gateway={}", gatewayUrl);
    }
}

// ── REAL USE CASE: @PostConstruct for cache warm-up ──────────────────
@Service
public class ProductCacheService {

    private final ProductRepository repo;
    private Map<Long, Product>    cache;

    @PostConstruct
    public void warmUpCache() {
        log.info("Warming up product cache...");
        cache = repo.findAll().stream()
            .collect(Collectors.toMap(Product::getId, p -> p));
        log.info("Cache warmed with {} products", cache.size());
    }

    public Optional<Product> findById(long id) {
        return Optional.ofNullable(cache.get(id)); // O(1) from cache
    }
}

Init Methods
💡
Rule of thumb: Use @PostConstruct for most initialization. Use @Bean(initMethod=...) for third-party classes. Avoid InitializingBean — it couples your code to Spring API unnecessarily.

Destruction Methods — @PreDestroy, DisposableBean, destroyMethod

// ── All 3 destroy mechanisms — execution order ────────────────────────

@Service
public class DatabaseConnectionPool implements DisposableBean {

    private HikariDataSource     dataSource;
    private ScheduledExecutorService healthChecker;

    @PostConstruct
    public void init() {
        dataSource    = new HikariDataSource(config);
        healthChecker = Executors.newScheduledThreadPool(1);
        healthChecker.scheduleAtFixedRate(this::checkHealth, 0, 30, TimeUnit.SECONDS);
    }

    // 1. @PreDestroy — runs FIRST on shutdown (JSR-250)
    // ✅ Use this for most cleanup
    @PreDestroy
    public void preDestroy() {
        log.info("Stopping health checker thread...");
        healthChecker.shutdown();
        try { healthChecker.awaitTermination(5, TimeUnit.SECONDS); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    // 2. DisposableBean.destroy() — runs SECOND
    // ⚠️ Tightly couples to Spring — prefer @PreDestroy
    @Override
    public void destroy() {
        log.info("Closing connection pool...");
        if (dataSource != null) dataSource.close();
    }
}

// 3. @Bean destroyMethod — runs THIRD (for third-party beans)
@Bean(destroyMethod = "disconnect")  // "disconnect()" called on context close
public KafkaProducer<String, String> kafkaProducer() {
    return new KafkaProducer<>(props);
}
// Note: Spring auto-detects close() and shutdown() as destroyMethods!
// If your bean has close() or shutdown(), Spring calls them automatically.
// To DISABLE: @Bean(destroyMethod = "")

// ── Shutdown hooks — triggered by ────────────────────────────────────
// context.close()         — explicit close
// context.registerShutdownHook() — JVM shutdown (CTRL+C, SIGTERM)
// Spring Boot: registers shutdown hook automatically
// server.shutdown=graceful → Tomcat waits for requests, then @PreDestroy fires

// ⚠️ Prototype beans: Spring does NOT call @PreDestroy on prototypes!
// Spring gives prototype instances to caller → caller must destroy them

// ── Scope annotations ─────────────────────────────────────────────────
@Component
@Scope("singleton")              // default — can omit
public class OrderService {}

@Component
@Scope("prototype")
public class ReportBuilder {}    // new instance every time it's injected/requested

@Component
@RequestScope                     // shortcut for @Scope("request")
public class RequestContext {
    private String traceId;
    private String userId;
}

@Component
@SessionScope                     // shortcut for @Scope("session")
public class ShoppingCart {
    private List<CartItem> items = new ArrayList<>();
}

// ── Singleton injecting Prototype — the scoped-proxy problem ──────────
// PROBLEM: Singleton holds ONE reference. It gets the FIRST prototype.
// Every call reuses the SAME prototype instance. Defeats the purpose!

@Service
public class ReportService {
    private final ReportBuilder builder; // ❌ SAME instance every time!
    public ReportService(ReportBuilder b) { this.builder = b; }
}

// FIX 1: @Scope with proxyMode — scoped proxy injects a stub
// Each call to stub.method() → gets a FRESH ReportBuilder
@Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ReportBuilder {}
// Now injection works: singleton holds a PROXY, each call → new instance

// FIX 2: ApplicationContext.getBean() (provider pattern)
@Service
public class ReportService {
    private final ObjectProvider<ReportBuilder> builderProvider;
    public ReportService(ObjectProvider<ReportBuilder> p) { builderProvider = p; }

    public Report generate() {
        ReportBuilder freshBuilder = builderProvider.getObject(); // NEW every call
        return freshBuilder.build();
    }
}

Lazy Beans, @Conditional & @Profile

// ── @Lazy — don't create until first use ─────────────────────────────
// Default: singleton beans created at startup (ApplicationContext refresh)
// @Lazy: bean created only when first requested

@Service
@Lazy
public class HeavyAnalyticsService {
    @PostConstruct
    public void init() { /* expensive ML model loading */ }
}
// Not initialized at startup — only when someone calls getBean() or injects it

// @Lazy on injection point — even if the bean is eager, inject it lazily
@Service
public class OrderController {
    @Lazy
    private final HeavyAnalyticsService analytics;
}

// Global lazy initialization (Spring Boot 2.2+):
# application.yml:
# spring.main.lazy-initialization: true
# ✅ Faster startup, but first request slow (first access creates beans)

// ── @Conditional — create bean only if condition met ─────────────────

// @Profile — create bean only for specific environment
@Bean
@Profile("prod")
public EmailService realEmailService() { return new SmtpEmailService(); }

@Bean
@Profile("!prod")                // NOT prod (dev, test)
public EmailService fakeEmailService() { return new NoOpEmailService(); }

// @ConditionalOnProperty — create only if property has specific value
@Bean
@ConditionalOnProperty(name = "feature.fraud-detection.enabled", havingValue = "true")
public FraudDetectionService fraudDetection() { return new MLFraudDetector(); }

// @ConditionalOnMissingBean — create only if no other bean of this type exists
@Bean
@ConditionalOnMissingBean(CacheManager.class)  // fallback if user didn't configure one
public CacheManager defaultCacheManager() { return new ConcurrentMapCacheManager(); }

// @ConditionalOnClass — create only if class is on the classpath
@Bean
@ConditionalOnClass(name = "io.lettuce.core.RedisClient") // only if Lettuce on classpath
public RedisCacheManager redisCacheManager() { ... }

// Custom @Conditional — fully flexible
public class OnWeekdayCondition implements Condition {
    @Override
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        DayOfWeek day = LocalDate.now().getDayOfWeek();
        return day != DayOfWeek.SATURDAY && day != DayOfWeek.SUNDAY;
    }
}

@Bean
@Conditional(OnWeekdayCondition.class)
public BatchJobScheduler scheduler() { return new BatchJobScheduler(); }

Application Context Events — Lifecycle Hooks

// ── Built-in Application Events (in order) ───────────────────────────
//
// ApplicationStartingEvent   → very early, before almost anything
// ApplicationEnvironmentPreparedEvent → Environment ready, before context created
// ApplicationContextInitializedEvent  → context created, but not refreshed
// ApplicationPreparedEvent           → context loaded, not refreshed yet
// ContextRefreshedEvent      → context fully initialized (all beans ready)
// ApplicationStartedEvent    → Spring Boot app started
// ApplicationReadyEvent      → app ready to serve requests (after CommandLineRunner)
// ContextClosedEvent         → context is closing
// ContextStoppedEvent        → context is stopped

// ── Listen to events — 3 ways ─────────────────────────────────────────

// 1. Implement ApplicationListener (old way)
@Component
public class StartupListener implements ApplicationListener<ApplicationReadyEvent> {
    @Override
    public void onApplicationEvent(ApplicationReadyEvent event) {
        log.info("Application is READY to serve requests!");
        registerWithServiceDiscovery(); // e.g. register with Eureka
    }
}

// 2. @EventListener (modern, cleaner)
@Component
public class EventHandler {

    @EventListener(ContextRefreshedEvent.class)
    public void onContextRefreshed() {
        log.info("All beans initialized — loading initial data...");
    }

    @EventListener(ApplicationReadyEvent.class)
    public void onReady() {
        log.info("Application READY!");
    }

    @EventListener(ContextClosedEvent.class)
    public void onShutdown() {
        log.info("Context closing — deregistering from service discovery...");
    }
}

// 3. CommandLineRunner / ApplicationRunner (run code after startup)
@Component
@Order(1)   // if multiple runners, controls order
public class DataSeeder implements CommandLineRunner {
    private final UserRepository userRepo;

    @Override
    public void run(String... args) {
        if (userRepo.count() == 0) {
            userRepo.save(new User("admin", "admin@app.com", "ADMIN"));
            log.info("Seeded admin user");
        }
    }
}

// ApplicationRunner — same but gets ApplicationArguments (typed args)
@Component
@Order(2)
public class CacheWarmer implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        if (args.containsOption("warm-cache")) {
            cacheService.warmUp();
        }
    }
}

// ── Publish custom events ─────────────────────────────────────────────
public record OrderCreatedEvent(Order order) {}

@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public Order createOrder(OrderRequest req) {
        Order order = orderRepo.save(buildOrder(req));
        publisher.publishEvent(new OrderCreatedEvent(order)); // decouple side effects
        return order;
    }
}

@Component
public class OrderNotifier {
    @EventListener
    @Async                           // fire-and-forget — don't slow down order creation
    public void onOrderCreated(OrderCreatedEvent event) {
        emailService.sendConfirmation(event.order());
    }

Common Pitfalls — Lifecycle Anti-Patterns

// ── Pitfall 1: Using @Autowired fields in constructor ────────────────
@Service
public class BadService {
    @Value("${app.name}")
    private String appName;

    public BadService() {
        log.info(appName); // ❌ NULL! @Value injected AFTER constructor
    }

    @PostConstruct
    public void init() {
        log.info(appName); // ✅ Safe — all injection done before @PostConstruct
    }
}

// ── Pitfall 2: Circular dependency ───────────────────────────────────
@Service
public class ServiceA {
    public ServiceA(ServiceB b) {} // ❌ A needs B
}
@Service
public class ServiceB {
    public ServiceB(ServiceA a) {} // ❌ B needs A → UnsatisfiedDependencyException!
}

// Fix options:
// 1. Redesign — break the cycle (usually the right answer)
// 2. @Lazy on one injection point — defer one bean's creation
// 3. Extract shared dependency into a third bean
// 4. Setter injection (not constructor) — allows cyclic deps (but ugly)

@Service
public class ServiceA {
    public ServiceA(@Lazy ServiceB b) {} // ✅ @Lazy breaks the cycle
}

// ── Pitfall 3: @Transactional on private/final methods ───────────────
@Service
public class OrderService {

    @Transactional
    private void saveOrder(Order o) { // ❌ private — proxy can't intercept
        repo.save(o);                     // @Transactional silently IGNORED
    }

    public void process(Order o) {
        saveOrder(o); // ❌ self-invocation — bypasses proxy!
    }
}

// ── Pitfall 4: @PostConstruct throws before context fully started ─────
@Service
public class BadInitService {
    @PostConstruct
    public void init() {
        throw new RuntimeException("Init failed!");
        // Application context refresh FAILS — app doesn't start
        // All beans partially created — potential resource leaks
    }
}
// Wrap in try-catch and log instead of letting it propagate (unless mandatory)

// ── Pitfall 5: Prototype bean injected into Singleton ────────────────
@Service
public class SingletonService {
    private final PrototypeBean proto; // ❌ SAME prototype forever
    public SingletonService(PrototypeBean p) { this.proto = p; }
}
// Fix: use ObjectProvider<PrototypeBean> or @Scope proxyMode

// ── Pitfall 6: @EventListener + @Transactional ────────────────────────
@EventListener
@Transactional
public void onEvent(MyEvent e) {
    // ⚠️ This creates a NEW transaction — not part of the publishing transaction
    // Use @TransactionalEventListener(phase=AFTER_COMMIT) instead
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) // ✅
public void onOrderCreated(OrderCreatedEvent e) {
    // Fires only AFTER the publishing transaction commits
    // Safe to send email — order definitely saved
    emailService.send(e.order());
}

💡
Golden rules:
  • Always use constructor injection — never field injection
  • Use @PostConstruct for init logic — never do it in the constructor
  • Use @PreDestroy for cleanup — close connections, stop threads
  • Use ApplicationReadyEvent for code that needs the full app ready (CommandLineRunner also works)
  • Remember: @Transactional on private methods is silently ignored — proxy can't intercept them
  • Prototype beans' @PreDestroy is NOT called by Spring — you manage cleanup yourself
