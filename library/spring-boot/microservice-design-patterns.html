Service decomposition by business capability

Cut along business capabilities, never along technical layers. Agar aapne controller-service, business-service, data-service banaya hai, toh aapne monolith ko teen network hops mein tod diya hai — that is a distributed monolith, not microservices.

!Problem

  • Invoice PDF ka ek chhota change bhi poore checkout ka regression suite chalata hai. One release train, 40 engineers waiting.
  • Search endpoint gets 80% of traffic, but you must scale the entire 900 MB JAR to serve it. Baaki sab modules bekaar mein RAM kha rahe hain.
  • A god class OrderService is edited by four teams. Merge conflicts daily, ownership zero.
  • One memory leak in the reporting module takes down payments. Blast radius = whole product.

✓Solution

  • Identify bounded contexts: Catalog, Order, Payment, Inventory, Shipping. Har context ka apna language hai — "Order" ka product aur "Catalog" ka product same cheez nahi hai.
  • Boundary test: can this team ship on Friday evening without asking any other team? Agar haan, boundary sahi hai.
  • Talk across boundaries only through an explicit port (API or event). No shared entity classes, no shared JAR of domain models.
  • Translate foreign models at the edge with an anti-corruption layer, so other teams' schema changes don't leak into your domain.

@Service
@RequiredArgsConstructor
public class OrderPlacementService {

    private final CatalogPort catalogPort;                     //» Port ka reference — implementation REST, gRPC ya local cache kuch bhi ho sakta hai.
    private final OrderRepository orderRepository;

    @Transactional
    public OrderId placeOrder(PlaceOrderCommand command) {     //» Method naam business intent bolta hai, "saveOrderData" jaisa CRUD naam nahi.
        List<OrderLine> lines = command.items().stream()
                .map(this::toOrderLineWithPriceSnapshot)        //» Har item ko Order ki apni bhasha mein translate karte hain — this is the anti-corruption step.
                .toList();

        Order order = Order.draftFor(command.customerId(), lines);
        order.rejectIfBelowMinimumValue();                     //» Business rule aggregate ke andar, service ke andar nahi — LLD interviewers yahi dekhte hain.
        return orderRepository.save(order).id();
    }

    private OrderLine toOrderLineWithPriceSnapshot(RequestedItem item) {
        CatalogProductView product = catalogPort.fetchProduct(item.productId());
        return new OrderLine(
                item.productId(),
                product.name(),                                //» Naam aur price ko copy kar rahe hain, reference nahi rakh rahe.
                product.price(),                               //» Kal catalog price badle toh purana order badalna nahi chahiye — immutability of history.
                item.quantity());
    }
}
Tradeoff docket — when, why, and when to ignore

apply when

  • 3+ teams blocking each other on one release train.
  • Different modules need wildly different scaling or SLAs.
  • Domain is understood well enough to name stable boundaries.

ignore when

  • Team under ~8 engineers. Ek modular monolith zyada tez chalega.
  • Product still pivoting — boundaries roz badlengi, har boundary change ab ek migration hai.
  • You have no CI/CD, no on-call rota, no centralised logging. Pehle woh banao.

what it costs

  • Every in-process call becomes a network call that can fail, retry and duplicate.
  • Refactoring across a boundary now needs two deploys and a compatibility window.
  • Local dev, testing and debugging get materially harder.

Database per service

Shared database ke saath aap microservices nahi, sirf multiple deployables chala rahe ho. Schema is the real API — jab tak DB shared hai, coupling zinda hai.

!Problem

  • Payment team adds NOT NULL to a shared table; order-service crashes at 2 am. Kisi ne bataya bhi nahi.
  • Foreign keys create invisible coupling: you cannot delete or move a row without knowing every reader.
  • One hot table lock (e.g. inventory) becomes a global bottleneck for unrelated flows.
  • Everyone is stuck on the same engine. Search chahiye Elasticsearch, ledger chahiye Postgres, cart chahiye Redis — sab Postgres mein ghuse hain.

✓Solution

  • Each service owns its schema. Bahar se koi direct SQL nahi maar sakta — only API or events.
  • Replace foreign keys with IDs plus a denormalised snapshot of the fields you actually need.
  • Cross-service reads: API composition for small joins, an event-fed read model for big ones.
  • Analytics ko production DB se mat jodo — events ko warehouse (BigQuery / Snowflake) mein bhejo.

Tradeoff docket — when, why, and when to ignore

apply when

  • Always, if you claim to run microservices. Yeh optional nahi hai.
  • Teams need to run migrations independently.
  • Different storage engines genuinely fit different workloads.

ignore when

  • Mid-migration from a monolith — a shared DB with strict schema ownership per table is an acceptable interim, with a deadline.
  • Reporting that truly needs 8-table joins: use a read replica or warehouse instead of forcing per-service joins.
  • Two "services" that always change together — merge them, don't split the data.

what it costs

  • No cross-service JOIN and no cross-service ACID transaction — you now need Saga.
  • Data duplication, and the job of keeping copies fresh.
  • Eventual consistency becomes a product decision, not just a technical one.

API gateway and backend-for-frontend

Gateway ek single front door hai: routing, auth, rate limit, TLS. BFF usse aage jaata hai — har client type ke liye ek alag response shape. Gateway ko patla rakho; business logic wahan gaya toh naya monolith ban jaayega.

!Problem

  • Mobile home screen needs data from 7 services. On a 3G connection that is 7 round trips — 4 seconds before anything paints.
  • JWT validation, rate limiting, CORS and TLS termination copy-pasted into every service, each with its own bug.
  • Internal topology leaks to clients. Ek service ka naam badla toh Android app ka purana version toot gaya.
  • Web needs 40 fields, mobile needs 6 — dono ko same fat payload mil raha hai.

✓Solution

  • One edge entry point handles cross-cutting concerns once: authN, rate limit, request ID, TLS, routing.
  • Aggregate fan-out calls in parallel at the edge and return one payload.
  • Give each client family its own BFF so payload shape can evolve at client speed.
  • Keep it stateless and horizontally scaled, so the "single door" is not a single machine.

@Service
@RequiredArgsConstructor
public class HomeScreenAggregator {

    private final CatalogClient catalogClient;
    private final OrderClient orderClient;
    private final OfferClient offerClient;
    private final Executor edgeExecutor;                        //» Dedicated pool — request threads ko block nahi karna. Yeh bulkhead ka hi ek roop hai.

    public HomeScreenView buildHomeScreen(UserId userId) {
        var trending = supplyOrFallback(
                () -> catalogClient.fetchTrending(12), List.of());   //» Har section apne fallback ke saath — catalog gir gaya toh khali list, exception nahi.
        var recentOrders = supplyOrFallback(
                () -> orderClient.fetchRecentOrders(userId, 3), List.of());
        var offers = supplyOrFallback(
                () -> offerClient.fetchOffers(userId), List.of());

        CompletableFuture.allOf(trending, recentOrders, offers)
                .orTimeout(800, TimeUnit.MILLISECONDS)          //» Poore screen ka ek hard budget. Slow section ko chhodo, page bhejo.
                .exceptionally(ignored -> null);                //» Timeout ko swallow karte hain kyunki har future ke paas already fallback hai.

        return new HomeScreenView(
                trending.getNow(List.of()),                     //» getNow = jo ready hai wahi lo, warna default. Yahi partial rendering ko enable karta hai.
                recentOrders.getNow(List.of()),
                offers.getNow(List.of()));
    }

    private <T> CompletableFuture<T> supplyOrFallback(Supplier<T> call, T fallback) {
        return CompletableFuture
                .supplyAsync(call, edgeExecutor)
                .exceptionally(ex -> {
                    log.warn("home section degraded", ex);      //» Degradation ko log + metric karo, warna silent data loss ban jaayega.
                    return fallback;
                });
    }
}

Service discovery and client-side load balancing

Autoscaling ke saath IP addresses har deploy par badalte hain. Discovery iska jawab hai — lekin Kubernetes par aksar yeh pattern already built-in hai, aur Eureka add karna ek extra failure domain hai.

!Problem

  • Hardcoded IPs and ports in config. Har scale-out ke baad manual update, aur ek stale IP = 100% failure.
  • A central hardware load balancer per service pair is slow to change and expensive.
  • Instance dies but keeps receiving traffic because nothing removed it from rotation.
  • Rolling deploys create a window where half the callers hold dead endpoints.

✓Solution

  • Instances register themselves with a registry (Eureka / Consul) and send heartbeats; unhealthy ones are evicted.
  • Callers resolve by logical name, then pick an instance client-side — no extra network hop.
  • On Kubernetes, the platform already does this: a Service name resolves through DNS to healthy pod endpoints.
  • Combine with readiness probes so a booting pod never gets traffic.

Saga — orchestration

Ek business transaction jo 4 services ko chhuti hai, usme 2PC/XA mat lagao — woh locks pakadta hai, availability girata hai aur Kafka/HTTP par kaam hi nahi karta. Saga usko chhote local transactions + compensations mein todta hai.

!Problem

  • Order placed, inventory reserved, but payment fails. Stock 30 minute tak block pada hai aur customer ko kuch pata nahi.
  • Two-phase commit holds locks across services for the whole round trip — throughput collapses and one slow participant freezes everyone.
  • Retry logic scattered in five places; nobody can answer "abhi order kis step par hai?".
  • Partial failure leaves no audit trail, so support has to fix rows by hand.

✓Solution

  • Split into local ACID transactions, one per service, each with an explicit compensating action.
  • An orchestrator holds the state machine and decides the next step. State DB mein persist hota hai, memory mein nahi.
  • Failure ke baad backwards chalo: releaseInventory, refundPayment, markOrderFailed.
  • Every step is idempotent and carries a saga id, so replays and duplicates are safe.

LLD view

order-service · OrderSagaOrchestrator
@Service
@RequiredArgsConstructor
public class OrderSagaOrchestrator {

    private final SagaInstanceRepository sagaRepository;        //» Saga ka state DB mein — pod restart hone par bhi flow resume ho sake.
    private final InventoryCommandGateway inventoryGateway;
    private final PaymentCommandGateway paymentGateway;

    @Transactional
    public SagaId startOrderSaga(Order order) {
        SagaInstance saga = SagaInstance.startedFor(order.id(), SagaStep.RESERVE_INVENTORY);
        sagaRepository.save(saga);                              //» Pehle state likho, phir command bhejo. Ulta karoge toh "bheja par yaad nahi" wala bug aayega.
        inventoryGateway.requestReservation(saga.id(), order.lines());
        return saga.id();
    }

    @EventListener
    @Transactional
    public void onInventoryReserved(InventoryReserved event) {
        SagaInstance saga = sagaRepository.lockById(event.sagaId());  //» Row lock — do parallel events ek hi saga ko aage badha kar race na kar dein.
        if (!saga.isAwaiting(SagaStep.RESERVE_INVENTORY)) return;     //» Idempotency guard: duplicate event chup-chaap ignore, error nahi.

        saga.advanceTo(SagaStep.CHARGE_PAYMENT);
        paymentGateway.requestCharge(saga.id(), saga.orderId(), saga.amount());
    }

    @EventListener
    @Transactional
    public void onPaymentDeclined(PaymentDeclined event) {
        SagaInstance saga = sagaRepository.lockById(event.sagaId());
        saga.beginCompensation(event.reason());                 //» Yahin se direction ulta ho jaata hai — forward steps band, compensations chalu.
        compensateReservedInventory(saga);
    }

    private void compensateReservedInventory(SagaInstance saga) {
        inventoryGateway.requestRelease(saga.id(), saga.orderId());  //» Compensation bhi ek command hai, saga id ke saath — receiver isko dedupe kar sake.
        saga.advanceTo(SagaStep.RELEASE_INVENTORY);
    }

    @Scheduled(fixedDelay = 30_000)
    public void retryStuckSagas() {                             //» Timeout sweeper: koi reply hi na aaye toh saga hamesha ke liye atka rahega.
        sagaRepository.findStalledOlderThan(Duration.ofMinutes(2))
                .forEach(saga -> saga.resendCurrentStepCommand(inventoryGateway, paymentGateway));
    }
}
Tradeoff docket — orchestration vs choreography vs neither

apply when

  • 4+ steps, conditional branches, or a flow the business wants to see and audit.
  • You need a single place to answer "where is this order stuck?".
  • Compensations are genuinely business-meaningful (refund, release, cancel).

ignore when

  • 2–3 simple steps with no branching — choreography (plain events) is lighter.
  • All steps live in one service: just use a local @Transactional. Saga ki zaroorat hi nahi.
  • Steps cannot be compensated at all (email already sent) — redesign the order of steps instead.

what it costs

  • Orchestrator is a coupling point and can drift toward god-service.
  • No isolation: other reads see intermediate states. Semantic locks or a PENDING status are needed.
  • You must write, test and monitor every compensation — that is roughly double the paths.

Transactional outbox and choreography

DB commit ho gaya lekin Kafka publish fail — event hamesha ke liye gum. Yeh dual-write problem hai, aur iska ek hi saaf jawab hai: event ko usi transaction mein ek outbox table mein likho.

!Problem

  • save(order) succeeds, then kafkaTemplate.send() throws. Order exists but nobody downstream knows — invisible inconsistency.
  • Reverse order is no better: publish succeeds, DB rollback happens, and you have announced an order that does not exist.
  • Wrapping Kafka and JDBC in one XA transaction is slow, fragile and often unsupported.
  • Consumers receive events out of order or twice and blindly apply them twice.

✓Solution

  • Insert the event row into an outbox table inside the same local transaction as the business write. Ek hi commit, ek hi truth.
  • A relay (poller or Debezium CDC on the WAL) reads unpublished rows and pushes them to the broker.
  • Delivery is at-least-once, so every consumer must be idempotent — dedupe by event id.
  • Choreography: consumers react to events and emit their own, with no central orchestrator.

public class OrderService {

    private final OutboxRepository outboxRepository;

    @Transactional
    public OrderId placeOrderAndRecordEvent(PlaceOrderCommand command) {
        Order order = orderRepository.save(Order.from(command));
        outboxRepository.save(OutboxRecord.of(                  //» Business row aur event row — dono ek hi transaction mein. Yahi poora trick hai.
                "Order", order.id().value(),
                "OrderPlaced", toJson(OrderPlaced.from(order))));
        return order.id();                                      //» Kafka ko yahan touch bhi nahi kiya, isliye broker down hone par bhi order safe hai.
    }
}

@Component
@RequiredArgsConstructor
public class OutboxRelay {

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void publishPendingEvents() {
        List<OutboxRecord> batch = outboxRepository
                .lockNextUnpublishedBatch(100);                 //» SELECT ... FOR UPDATE SKIP LOCKED — multiple relay pods same row par nahi ladenge.

        for (OutboxRecord record : batch) {
            kafkaTemplate.send(record.topic(), record.aggregateId(), record.payload());
            record.markPublished(Instant.now());                //» Publish ke baad mark. Crash yahan hua toh dobara publish hoga = at-least-once, at-most-once nahi.
        }
    }
}

@Component
@RequiredArgsConstructor

Tradeoff docket — when, why, and when to ignore

apply when

  • Any time a DB write and an event publish must both happen. Yeh money flows ke liye must hai.
  • Choreographed flows with 2–4 steps and no branching.
  • You already run Debezium or can afford a small poller.

ignore when

  • The event is genuinely disposable — a "nice to have" analytics ping. Losing it costs nothing.
  • You use event sourcing: the event store is the write model, so there is no dual write to fix.
  • Flow has 6+ steps and branches — choreography becomes untraceable; switch to orchestration.

what it costs

  • An extra table, a relay process and its lag monitoring.
  • Duplicates are now guaranteed, so every consumer needs a dedupe store.
  • Choreography spreads the flow across services — "who does what next" ka koi single diagram nahi bachta.

CQRS — command query responsibility segregation

Ek hi model se likhna aur padhna dono karoge toh dono taraf compromise hoga. CQRS write model ko normalized aur rules-heavy rakhta hai, read model ko flat aur fast. Lekin isko default mat banao — 80% screens ke liye simple CRUD hi sahi hai.

!Problem

  • The seller dashboard needs a 6-table join with aggregates; the query takes 4 seconds and locks rows that checkout needs.
  • Write path chahta hai normalization aur constraints, read path chahta hai denormalized rows aur bade indexes — ek hi table dono nahi de sakti.
  • Adding read indexes slows down every insert on the hot path.
  • Search needs full-text ranking that a relational table cannot deliver.

✓Solution

  • Commands go through the aggregate and enforce invariants; queries bypass it entirely and hit a purpose-built read model.
  • Read models are projected from domain events, and can live in Postgres, Elasticsearch or Redis — jo bhi query pattern ko suit kare.
  • You can rebuild a read model from scratch by replaying events, so schema changes stop being scary migrations.
  • Scale read and write sides independently.

@RequiredArgsConstructor
public class PlaceOrderCommandHandler {                         //» Naam se hi pata chalta hai yeh write side hai. Read side kabhi is class ko nahi chhuyega.

    private final OrderRepository orderRepository;
    private final DomainEventPublisher eventPublisher;

    @Transactional

    private OrderStatus status;

    private final List<DomainEvent> uncommittedEvents = new ArrayList<>();

    public static OrderAggregate rehydrateFromEventStream(List<DomainEvent> history) {
        OrderAggregate aggregate = new OrderAggregate();
        history.forEach(aggregate::applyEvent);                 //» Fold: har event ko kramsh apply karke current state banate hain.
        return aggregate;

            throw new OrderAlreadyShippedException(id);         //» Decision current state par — jo state events se aayi hai.

        recordEvent(new OrderCancelled(id, reason, Instant.now()));  //» Command state ko seedha nahi badalta; woh ek event record karta hai.
    }

Circuit breaker

Ek slow dependency poore system ko le doobti hai: threads block hote hain, pool khatam hota hai, aur callers ke callers bhi girte hain. Breaker kehta hai — jab dependency clearly beemar hai, toh usse poochho hi mat, turant fallback do.

!Problem

  • Payment provider p99 goes from 200 ms to 30 s. Har request ek thread 30 second tak pakadti hai.
  • Tomcat's 200 threads are all parked. Health endpoint bhi respond nahi kar raha, so Kubernetes restarts a healthy pod.
  • Callers retry, which multiplies load on a dependency that is already drowning.
  • Failure spreads upstream — checkout, cart and home page sab down, jabki galti sirf ek provider ki thi.

✓Solution

  • Track the failure rate over a sliding window. Threshold cross hote hi breaker OPEN — calls fail instantly, no thread parked.
  • After a wait duration, allow a few trial calls (HALF_OPEN). Succeed → CLOSED, fail → OPEN again.
  • Every breaker needs a meaningful fallback: queue the request, serve cached data, or return a clear degraded response.
  • Always pair with a timeout — bina timeout ke breaker kabhi trip hi nahi karega, kyunki call kabhi khatam hi nahi hoti.

Retry, backoff and idempotency

Retry sabse aasan pattern lagta hai aur sabse zyada nuksan yahi karta hai. Bina backoff ke retry ek DDoS hai, aur bina idempotency key ke retry customer ko do baar charge kar deta hai.

!Problem

  • A one-off 503 or TCP reset fails a checkout that would have worked on the second attempt.
  • Naive for(int i=0;i<5;i++) retry: 1,000 clients retry at the same instant and finish off a recovering service — the retry storm.
  • Timeout after the server already committed. Client retries, and the customer is charged twice.
  • Retries at three layers (client, gateway, service) multiply: 3 × 3 × 3 = 27 real calls for one request.

✓Solution

  • Retry only safe or idempotent operations, and only on transient errors — never on 400/422.
  • Exponential backoff plus jitter, so clients don't synchronise into a thundering herd.
  • Server-side idempotency key with a unique index: the second attempt returns the first result instead of doing the work again.
  • Retry at exactly one layer, cap total attempts, and always combine with timeout + circuit breaker.

@Service
@RequiredArgsConstructor
public class IdempotencyGuard {                                 //» Server side ka aadha hissa. Client ki retry safe tabhi hai jab server dedupe kare.

    private final IdempotencyRecordRepository records;

    @Transactional
    public <T> T executeOnce(String idempotencyKey, Supplier<T> operation, Class<T> type) {
        Optional<IdempotencyRecord> existing = records.findByKey(idempotencyKey);
        if (existing.isPresent()) {
            return deserialize(existing.get().responseBody(), type);  //» Pehla response wapas do — kaam dobara mat karo. Yahi "exactly once effect" hai.
        }
        T result = operation.get();
        records.insertOrThrowOnDuplicate(                       //» Unique index on idempotency_key — do parallel retries mein se ek hi jeetega.
                new IdempotencyRecord(idempotencyKey, serialize(result), Instant.now()));
        return result;
    }
}

Bulkhead and rate limiting

Jahaz mein bulkhead ka kaam hai: ek compartment mein paani bhare toh poora jahaz na doobe. Software mein wahi — ek slow dependency sirf apna pool khaaye, sabka nahi.

!Problem

  • The slow recommendation API consumes all 200 Tomcat threads. Checkout, jo recommendations use hi nahi karta, woh bhi mar gaya.
  • One tenant runs a 50,000-row export and exhausts the shared DB connection pool for everyone.
  • A batch job and live traffic share the same pool; the batch always wins because it never sleeps.
  • A buggy client hammers one endpoint at 5,000 rps and takes down the whole service.

✓Solution

  • Give each dependency or workload class its own bounded pool — separate thread pools, connection pools, or semaphore limits.
  • When the pool is full, reject fast with a clear error instead of queueing forever.
  • Add a rate limiter per client or per tenant so a single caller cannot consume all capacity.
  • Separate critical from non-critical traffic even at the pod level — alag deployment, alag scaling.

Sidecar

Cross-cutting concern ko har service mein dobara likhne ke bajaye usse ek alag container mein rakho, jo same pod mein chalta hai — same network, same volumes. Language-agnostic upgrade path mil jaata hai.

!Problem

  • Log shipping, metrics, TLS certs and config reload are re-implemented in Java, Go and Python — teen implementations, teen bug sets.

  • The library version drifts: half the fleet emits v1 log format, half emits v2, and dashboards break.
  • Legacy services cannot take a new library at all.

✓Solution

  • Run the concern as a second container in the same pod: log shipper, secret refresher, proxy, or metrics agent.
  • Application writes plain stdout or a shared volume and knows nothing about the destination.
  • Upgrading the sidecar image upgrades the behaviour for every language at once.
  • Use init containers for one-shot setup and sidecars for long-running concerns.

    private final FeatureFlagClient featureFlags;

    public RouteTarget resolveTargetFor(HttpRequest request, String customerId) {
        String capability = capabilityOf(request.path());       //» Route ka faisla capability par, URL string par nahi — flags readable rehte hain.
        if (!featureFlags.isEnabled("migrate." + capability)) {

        return isWithinRollout(customerId, rolloutPercent)
                ? RouteTarget.NEW_SERVICE
                : RouteTarget.LEGACY;

        int bucket = Math.floorMod(customerId.hashCode(), 100); //» Customer id ka stable hash — ek user hamesha ek hi side par rahega, flip-flop nahi karega.
        return bucket < percent;
    }
}

        }
    }

Correlation ID and distributed tracing

Yeh is poori list ka ekmatr pattern hai jiske liye "ignore when" section practically khali hai. Microservices ke saath observability optional nahi hai — uske bina aap ek distributed system ko blind debug kar rahe ho.

!Problem

  • A request touches nine services and fails somewhere. Nau alag log files, koi common key nahi.
  • "Checkout is slow" — but which of the nine hops is slow? Nobody can answer without guessing.
  • An error in service G was actually caused by a malformed payload from service B two hops earlier.
  • Alerts fire on CPU, not on the thing users feel: error rate and latency.

✓Solution

  • Generate a trace id at the edge and propagate it on every hop using the W3C traceparent header.
  • Put trace and span ids into the logging MDC so every log line is joinable across services.
  • Emit RED metrics per endpoint — rate, errors, duration — and alert on those, not on machine stats.
  • Use OpenTelemetry so instrumentation is not locked to one vendor.

public class CorrelationIdFilter extends OncePerRequestFilter {

    public static final String HEADER = "X-Correlation-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws IOException, ServletException {
        String correlationId = Optional.ofNullable(request.getHeader(HEADER))
                .filter(StringUtils::hasText)
                .orElseGet(() -> UUID.randomUUID().toString());  //» Aaya hua id reuse karo; na aaye toh naya banao. Edge par hi ek baar generate hota hai.
        MDC.put("correlationId", correlationId);                //» MDC mein daalte hi har log line automatically tagged ho jaati hai.
        response.setHeader(HEADER, correlationId);              //» Response mein wapas bhejo — support team screenshot se hi request dhoondh legi.
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.clear();                                        //» finally mein clear — warna thread pool ka agla request purana id le kar chalega.
        }
    }
}

Tradeoff docket — when, why, and when to ignore

apply when

  • From service number two onward. Pehle din se lagao.
  • Any async or event-driven hop, where causality is otherwise invisible.
  • Whenever an SLO exists that someone is accountable for.

ignore when

  • Practically never. Sirf sampling rate tune karo — 100% traces mehnge hain, 1–10% + all-errors usually sahi hai.

Mock interview questions with answers

Har jawab woh structure follow karta hai jo interviewer sunna chahta hai: pehle problem restate, phir approach, phir tradeoff, phir "yeh kab nahi karunga". Answers dekhne ke liye question par click karo.

HLDDesign checkout across Order, Payment, Inventory and Shipping. Consistency kaise rakhoge without 2PC?

Order service ek saga orchestrator chalata hai. Steps: reserve inventory → charge payment → create shipment → confirm order. Har step ek local ACID transaction hai in its own service, and each has a named compensation: releaseInventory, refundPayment, cancelShipment.

Saga state DB mein persist hoti hai (saga_instance table) taki pod restart par flow resume ho. Commands aur events outbox ke through jaate hain, so no dual-write loss. Every consumer dedupes on event id.

2PC isliye nahi kyunki woh saare participants par lock pakadta hai aur ek slow service poore system ko rok deti hai; plus HTTP/Kafka par XA practically chalta hi nahi. Saga availability chunta hai consistency ke over — order thodi der PENDING dikhega, par system chalu rahega.

Cost jo main openly bataunga: no isolation. Beech ke states doosre readers ko dikhte hain, isliye order ko PENDING status ke saath model karta hoon aur UI wahi dikhata hai.

HLDService boundary decide karne ka concrete test kya hai?

Teen tests jo main saath lagata hoon:

  • Deploy test — can this team deploy on Friday without coordinating with anyone? Agar nahi, boundary galat hai.
  • Data test — does exactly one service write this table? Do writers matlab boundary galat jagah hai.
  • Change test — pichhle 6 mahine ke PRs dekho. Jo files hamesha saath badalti hain woh ek hi service mein honi chahiye.
Sabse aam galti: layers par kaatna — api-service, business-service, data-service. Yeh microservices nahi, ek monolith hai jisme teen network hop daal diye gaye hain, aur latency badhi bina koi independence mile.
HLDEk screen ko 4 services ka data chahiye. Kya karoge?

Teen options, is order mein evaluate karta hoon:

  • API composition at a BFF — parallel calls, per-section fallback. Simplest; use it when the data set is small and latency budget allows.
  • CQRS read model — events se ek denormalized table banao. Use when the join is large, frequent, or needs sorting/filtering across services.
  • Client-side composition — sirf tab jab client fast network par ho aur sections independent ho.
Default composition rakhunga kyunki woh sasta hai. Read model tab banaunga jab measurement dikhaye ki fan-out p99 budget se bahar ja raha hai — pehle se nahi.
HLDGateway single point of failure hai — isko kaise handle karoge?

Gateway ko stateless rakho, multiple replicas across AZs, aur uske aage ek managed L4/L7 load balancer. Health checks + readiness probes se dead replicas rotate ho jaati hain. Gateway mein koi session state ya business logic nahi — sirf routing, auth, rate limit.

Deployment bottleneck se bachne ke liye routes ko per-team config files mein rakho, ek monolithic route file mein nahi, aur CI mein validate karo.

Asli khatra "single point of failure" se zyada "single point of change" hai — jab har team ko ek hi file edit karni pade, tab gateway release train ban jaata hai. Isliye config ownership distribute karna zaroori hai.
HLDMonolith ko migrate karna hai bina feature freeze ke. Plan?

Strangler fig. Step by step: (1) facade/gateway lagao taki client URLs na badlein; (2) sabse independent capability chuno — usually notifications or search; (3) naya service banao, dual-run karke responses compare karo; (4) percentage rollout with a stable customer hash; (5) traffic 100% hone ke baad legacy path delete, with a dated ticket.

Data ke liye: पहले read path migrate karo (easy), phir write path with dual-write or CDC sync, phir source of truth flip.

Sabse important discipline: har capability ke liye ek deletion deadline likho. Deadline ke bina team hamesha ke liye do systems maintain karti rahegi — aur yahi strangler ka sabse common failure mode hai.
HLDZero-downtime schema change ek live service mein kaise karoge?

Expand–migrate–contract, teen alag deploys mein:

  • Expand — naya nullable column add karo. Purana code chalta rahta hai.
  • Migrate — code dono column likhta hai, backfill job purana data bharta hai, reads abhi bhi purane column se.
  • Contract — reads naye column par shift, phir purana column drop. Har step alag deploy.
Rule: ek hi deploy mein kabhi bhi column rename ya drop mat karo, kyunki rollout ke dauraan purana aur naya code ek saath chal rahe hote hain. Rename = add + backfill + switch + drop, chaar alag steps.
HLDKafka ke through trace kaise propagate karoge?

Producer side par traceparent ko Kafka record headers mein daalo; consumer side par header se context extract karke naya span parent set karo. OpenTelemetry ke Kafka instrumentation yeh automatically karta hai, par manual bhi 10 lines ka kaam hai.

Consumer span ko CONSUMER kind ke saath mark karo taki trace view mein async boundary saaf dikhe, aur queue lag ko span attribute mein record karo.

Async hop par trace tootne ka matlab hai ki aap producer aur consumer ko kabhi jod nahi paoge. Yeh exactly wahi jagah hai jahan debugging sabse zyada mushkil hoti hai — isliye headers propagate karna optional nahi hai.
LLDOutbox kyun chahiye? Commit ke baad publish kyun nahi kar sakte?

Kyunki DB commit aur broker publish do alag systems hain, aur unke beech process kabhi bhi mar sakta hai. Commit hone ke baad publish se pehle crash = event permanently lost, aur koi bhi retry mechanism usko recover nahi kar sakta kyunki intent kahin record hi nahi hua.

Outbox event ko usi local transaction mein likh deta hai. Ab intent durable hai; relay chahe 1 second baad publish kare ya 10 minute baad, event kabhi gum nahi hoga.

Iske badle mein aapko at-least-once delivery milti hai — matlab duplicates guaranteed hain. Isliye har consumer ko dedupe karna hi padega, usually event id par ek unique index se.

@TransactionalEventListener(AFTER_COMMIT) bhi isko solve nahi karta — woh commit ke baad chalta hai, aur us gap mein crash ho sakta hai.

LLDSaga step mein @Transactional boundary kahan rakhoge?

Transaction ke andar sirf local DB writes — saga state update aur outbox insert. Remote call kabhi transaction ke andar nahi, kyunki network wait DB connection ko pakde rakhta hai aur ek slow downstream aapka connection pool khatam kar dega.

Pattern: @Transactional mein state advance + outbox row likho; transaction commit ke baad relay actual command bhejta hai.

Ek aur zaroori cheez: incoming event handle karte waqt saga row ko lockById se lock karo. Do events parallel aayein toh dono ek hi saga ko aage badha kar state corrupt kar sakte hain — row lock isko rokta hai.
LLDKafka consumer ko idempotent kaise banaoge? Mechanism batao.

Sabse simple aur sabse reliable: ek processed_event table with a unique index on event_id. Consumer pehle insert try karta hai; duplicate key exception aaya toh event already processed hai, silently return karo.

Critical detail — yeh insert aur business write ek hi local transaction mein hone chahiye. Alag transactions mein karoge toh crash ke baad ek ho jaayega aur doosra nahi.

Doosra tareeka natural idempotency ka hai: UPDATE inventory SET reserved = 5 WHERE order_id = ? jaisa absolute set operation dubara chalane par bhi wahi result deta hai, jabki reserved = reserved + 5 increment har baar galat kar dega.

Dedupe table ko TTL ke saath rakho (jaise 7 din), warna woh anant tak badhta rahega.

LLD@Retry aur @CircuitBreaker ka order kya hona chahiye, aur kyun?

Resilience4j ka default order bahar se andar: CircuitBreaker → Retry → TimeLimiter → Bulkhead. Matlab breaker retries ke bahar hai: agar breaker OPEN hai toh retry karne ka mauka hi nahi milta, aur ek retried-then-failed call breaker ko ek failure gina jaata hai.

Ulta karoge (retry bahar, breaker andar) toh har retry ek breaker call banega, breaker jaldi trip karega, aur retry ka faayda khatam.

Aur teeno se pehle timeout zaroori hai. Bina timeout ke call kabhi khatam hi nahi hoti, isliye na retry trigger hoti hai na breaker ke paas koi failure signal aata hai — poora resilience stack chup-chaap bekaar ho jaata hai.
LLDEvent sourcing mein optimistic locking kaise implement karoge?

Har aggregate ke stream mein ek monotonically increasing version hoti hai. Load karte waqt aap version N tak padhte ho. Append karte waqt store ko batate ho: "expected version N". Store ek conditional insert karta hai — usually a unique constraint on (aggregate_id, version).

Beech mein kisi aur ne likh diya toh version N+1 already exist karega, unique violation aayega, aur aap ConcurrencyException throw karke command ko reload-and-retry karoge.

Yahan pessimistic lock jaan-boojh kar nahi lagate, kyunki event store append-only hai aur conflicts kam hote hain. Retry ka matlab hai: aggregate dobara rehydrate karo, business rule dobara check karo, phir append — kyunki naye event ne shayad decision hi badal diya ho.
LLDAsync calls mein MDC / correlation id leak kaise rokoge?

MDC ThreadLocal hai, isliye do problems hain: naya thread context nahi paata, aur pool ka thread purana context leke rehta hai.

  • Filter mein hamesha finally { MDC.clear(); } — yeh leak rokta hai.
  • @Async ke liye TaskDecorator lagao jo submit karte waqt MDC.getCopyOfContextMap() capture kare aur worker thread par set kare, phir clear kare.
  • Micrometer Tracing use kar rahe ho toh ContextPropagatingTaskDecorator yeh already karta hai.
Leak ka lakshan bahut khatarnak hai: logs mein galat traceId dikhta hai, aur debugging aapko poori tarah galat request par le jaati hai. Isliye clear karna optional nahi hai.
LLDEvent sourcing mein snapshot kyun, aur usko correct kaise rakhoge?

Snapshot sirf performance ke liye hai — 50,000 events replay karna har read par mehnga hai. Har N events (jaise 200) par current state serialize karke store karo, phir load par snapshot + uske baad ke events replay karo.

Correctness rule: snapshot kabhi source of truth nahi. Saare snapshots delete kar do toh system exactly same state par pahunchna chahiye. Snapshot mein apni schema version rakho; aggregate ka shape badle toh purane snapshots ko invalidate karo, migrate karne ki koshish mat karo.

Ek common bug: snapshot mein derived data store kar dena jo naye business rules se badal gaya hai. Isliye snapshot version mismatch par usse chup-chaap discard karke pura stream replay karna hi safe design hai.
LLDCQRS mein read-your-own-write kaise handle karoge?

Chaar practical options, situation ke hisaab se:

  • Command ka response hi updated view return kare — client ko read hi na karna pade.
  • Us ek record ke liye write model se padho (jaise findJustPlacedOrder), list ke liye read model se.
  • Client ko ek version/token do; read model us version tak catch up na ho toh short poll karo.
  • UI par optimistic update dikhao aur background mein reconcile karo.
Interview mein sabse achha jawab yeh hai ki aap isko product decision maano: "order placed" screen par lag bilkul unacceptable hai, lekin analytics dashboard par 5 second ka lag koi problem nahi. Ek hi rule sab jagah mat lagao.
LLDGateway aggregation mein ek downstream slow ho toh code kya karega?

Har section ka apna future, apna fallback, aur poore screen ka ek global deadline. Deadline hit hone par jo ready hai woh bhejo (getNow(default)), baaki sections empty ya cached. Exception ko kabhi upar propagate mat karo, warna ek slow section poora page gira dega.

Degradation ko metric karo — home.section.degraded{section="offers"} — warna users ko toota page dikhta rahega aur dashboards green rahenge.

Aggregation ke liye alag executor rakhna zaroori hai. Agar aap request-handling threads par hi fan-out karoge, toh ek slow downstream poore server ka thread pool kha jaayega — yeh bulkhead ka classic use case hai.
tradeoffMicroservices kab nahi karoge?

Jab in mein se koi bhi sach ho: team 8 se chhoti hai; domain boundaries abhi tak clear nahi hain; koi CI/CD ya centralized logging nahi hai; product roz pivot kar raha hai; ya sirf ek module ko scale karna hai jo ek read replica se ho sakta hai.

In sab cases mein modular monolith better hai — module boundaries enforce karo (ArchUnit, Java modules), taki kal split karna sasta rahe.

Interview mein yeh line strong hoti hai: "Microservices ek organizational solution hai, technical nahi. Agar aapke paas coordination problem nahi hai, toh microservices sirf latency, complexity aur on-call load add karenge."
tradeoffSaga: orchestration ya choreography? Kaise chunoge?

Choreography tab jab flow 2–3 steps ka ho, koi branching na ho, aur services genuinely independent hon. Kam coupling, kam code.

Orchestration tab jab steps 4+ hon, conditional paths hon, timeouts aur retries manage karne hon, ya business ko visibility chahiye ki order kis step par atka hai.

Decision ka asli signal yeh hai: agar aap "yeh flow poora kaise chalta hai" ka jawab ek jagah dekh kar nahi de sakte, toh aapko orchestrator chahiye. Choreography mein knowledge services mein bikhri hoti hai, aur ek limit ke baad woh debug karna namumkin ho jaata hai.

Hybrid bhi valid hai: core money flow orchestrated, side effects (email, analytics) choreographed.

tradeoffCQRS chahiye ya read replica kaafi hai?

Read replica kaafi hai jab query same shape ki hai aur sirf load offload karna hai. Yeh ek config change hai, code change nahi — isliye pehle yahi try karo.

CQRS tab chahiye jab read ko alag model ki zaroorat ho: different denormalization, different engine (search, geo), ya different consistency window. Replica same schema deta hai, alag model nahi.

Beech ka ek option bhi hai jo log bhool jaate hain: materialised view. Woh CQRS ka 60% faayda deta hai bina projector, bina event pipeline, bina eventual consistency ke — bas refresh cost ke saath.
tradeoffTimeout, retry, breaker, bulkhead — priority order kya hai?
  1. Timeout — sabse pehle, hamesha. Iske bina baaki teeno kaam hi nahi karte.
  2. Bulkhead / pool limits — taki ek dependency poore process ko na khaaye.
  3. Circuit breaker — cascading failure rokne ke liye.
  4. Retry — sabse aakhir mein, aur sirf idempotent operations par.
Log aksar ulta karte hain — sabse pehle retry lagate hain, jo actually sabse khatarnak hai. Bina timeout aur breaker ke retry ek healthy dependency ko bhi maar sakti hai, kyunki jab woh slow hoti hai tabhi aap uspar teen guna load daal dete ho.
tradeoffService mesh kab worth nahi hai?

Jab services ~15 se kam hon, ek hi language ho, aur koi dedicated platform capacity na ho. Us case mein Resilience4j (retry, breaker, bulkhead) + Kubernetes Services + ek ingress controller aapko 90% value 5% operational cost mein de dete hain.

Mesh tab justify hota hai jab: polyglot fleet, mTLS ek compliance requirement ho, ya progressive delivery (canary, mirroring, fault injection) routine capability chahiye.

Mesh ka asli kharcha license nahi, samajh hai. Jab production mein request fail hoti hai toh ab aapko app, sidecar proxy aur control plane teeno debug karne aate hone chahiye. Team ke paas yeh skill nahi hai toh mesh reliability badhata nahi, ghatata hai.
tradeoffEvent sourcing chahiye ya ek audit table kaafi hai?

Audit table kaafi hai jab aapko sirf "kya badla, kisne badla, kab" record karna hai. Ek append-only order_history table state table ke saath, aur kaam ho gaya — 5% cost mein.

Event sourcing tab chahiye jab events hi source of truth hon: aapko past state reconstruct karna ho, purane data par naye read models banane hon, ya regulator temporal correctness maange.

Ek honest warning jo interview mein achhi lagti hai: GDPR ke saath event sourcing mushkil ho jaata hai, kyunki immutable log se personal data delete nahi hota. Uska jawab crypto-shredding hai — per-user key se encrypt karo aur key delete kar do — lekin yeh design pehle din se sochna padta hai.
tradeoffDB per service chahiye, par reporting ko 8-table join chahiye. Kya karoge?

Reporting ko OLTP se bilkul alag karo. Services domain events publish karti hain, ek sink (Debezium/Kafka Connect) unhe warehouse mein daalta hai, aur saare joins wahan chalte hain. Analysts ko warehouse access milta hai, production DB nahi.

Chhote internal dashboards ke liye ek CQRS read model kaafi hai, poora warehouse nahi.

Jo cheez kabhi nahi karni: reporting ke liye services ke DBs par direct read access de dena. Woh ek hi din mein aapka data ownership boundary tod deta hai, aur uske baad koi bhi team apna schema safely nahi badal sakti.
tradeoffInterviewer poochta hai: "2PC kyun nahi? Woh toh strong consistency deta hai."

Kyunki 2PC availability aur throughput dono kharch karta hai. Prepare phase se commit tak saare participants locks pakde rehte hain, isliye ek slow participant sabki latency badha deta hai. Coordinator crash ho jaaye toh participants "in-doubt" state mein atak jaate hain jab tak manual recovery na ho.

Practically, Kafka aur REST XA support nahi karte, aur cloud managed databases aksar distributed transactions restrict karte hain.

Balanced jawab yeh hai: 2PC ek hi database ke andar ya ek trusted, low-latency boundary par theek hai — jaise DB aur message broker jo dono XA support karte hon. Services ke beech, internet-scale par, saga behtar tradeoff hai: thodi der ki inconsistency ke badle mein availability.
tradeoffDistributed monolith kya hai, aur usko detect kaise karoge?

Distributed monolith woh system hai jisme deployment toh alag hai par coupling monolith jaisi hi hai. Detect karne ke signals:

  • Ek feature ke liye 3+ services ek saath release karni padti hain.
  • Services shared database ya shared domain JAR use karti hain.
  • Ek service down hone par baaki sab bhi practically down ho jaati hain.
  • Local development ke liye poora stack chalana padta hai.
Fix aksar counter-intuitive hota hai: services ko wapas merge karo, phir business capability par dobara kaato. Interviewers ko yeh jawab pasand aata hai kyunki yeh dikhata hai ki aap "zyada services = behtar architecture" wali soch se aage badh chuke ho.
