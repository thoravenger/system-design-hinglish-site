Java core: exception ka raw material

Spring kuch naya invent nahi karta — woh sirf Java ke Throwable model ke upar ek routing layer chadhata hai. Agar yeh 12 topics clear hain, to Spring ka poora error handling apne aap samajh aa jaayega.

T-01

Throwable hierarchy — Error, Exception, RuntimeException

catch(Throwable) catch(Exception) JVM

Sab kuch Throwable se shuru hota hai. Uske neeche do bilkul alag duniya hain — aur unko ek jaisa treat karna hi pehli galti hai.

Problem — catch-all jo JVM ko zinda laash bana deta hai
public Report generateReport(long id) {
  try {
    return reportEngine.build(id);
  } catch (Throwable t) {        // <-- sab kuch nigal liya
    log.error("report failed");
    return Report.empty();
  }
}

Kyun tootta hai: Throwable ke andar OutOfMemoryError, StackOverflowError, NoClassDefFoundError aur ThreadDeath bhi aate hain. Heap khatam ho chuki hai, par aapka code "empty report" return kar ke chal raha hai. JVM corrupt state me hai, monitoring green hai, aur 40 minute baad pod bina kisi clue ke mar jaata hai. Yeh silent data corruption ka classic source hai.

Solution — recoverable pakdo, fatal ko upar jaane do
public Report generateReportSafely(long id) {
  try {
    return reportEngine.build(id);
  } catch (ReportGenerationException e) {  // 1
    log.warn("report {} degraded: {}", id, e.getMessage());
    return Report.empty();                    // 2
  } catch (RuntimeException e) {              // 3
    throw new ReportGenerationException(id, e);  // 4
  }
  // Error/Throwable deliberately NOT caught  // 5
}

public boolean isFatal(Throwable t) {          // 6
  return t instanceof VirtualMachineError
      || t instanceof LinkageError;
}
  • 1Sirf woh exception pakdo jiske liye aapke paas ek real fallback hai. Baaki sab pass-through.
  • 2Degraded response — business decision, technical accident nahi. Isliye warn, error nahi.
  • 3RuntimeException tak hi jaao, Throwable tak nahi. NPE/IllegalState yahan aayenge.
  • 4Wrap karke domain exception banao — caller ko JDBC/Jackson ka pata nahi hona chahiye (T-07).
  • 5Sabse important line woh hai jo likhi hi nahi gayi. OutOfMemoryError ko upar jaana chahiye taaki pod restart ho.
  • 6Agar framework/thread-pool likh rahe ho aur Throwable pakadna hi pade, to fatal ko explicitly re-throw karo.

Trade-off: kab apply, kab ignore

Apply karoHar business/service layer method me. Domain-specific catch + fallback = predictable behaviour.
Ignore karoFramework-level thread pools, Runnable wrappers, aur JNI boundaries me Throwable pakadna theek hai — warna thread chup-chaap mar jaata hai. Par log karo aur fatal re-throw karo.
KyunRecoverability ka faisla exception type se nahi, fallback ke existence se hota hai. Fallback nahi hai to catch mat karo.
T-02

Checked vs Unchecked — sabse zyada poocha jaane wala trade-off

throws IOException RuntimeException API design

Checked exception ek compile-time contract hai: "caller, tujhe iska jawab dena padega". Unchecked ek programming bug ya un-recoverable state ka signal hai.

Problem — checked exception ka leak aur throws ka pollution
// Repository layer
public User findById(long id) throws SQLException { ... }

// Service layer — forced to declare
public UserDto getProfile(long id) throws SQLException { ... }

// Controller — forced again
@GetMapping("/users/{id}")
public UserDto get(@PathVariable long id) throws SQLException { ... }

// Aur phir yeh, kyunki koi handle nahi karna chahta:
catch (SQLException e) { }   // empty catch = data loss

Do damage: (a) SQLException ek persistence detail hai, lekin ab woh aapke HTTP controller ke signature me likha hai — abstraction leak. Kal MongoDB pe shift kiye to poora call chain badalna padega. (b) Compiler force karta hai, developer thak ke empty catch likh deta hai — jo no-exception se bhi bura hai.

Solution — boundary pe translate karo, ek hi baar
// ---- Repository: checked ko boundary par hi maaro ----
public User findUserById(long id) {
  try {
    return jdbcTemplate.queryForObject(SQL, mapper, id);  // 1
  } catch (EmptyResultDataAccessException e) {          // 2
    throw new UserNotFoundException(id, e);
  }
}

// ---- Checked tab rakho jab caller SACH ME recover kar sake ----
public Money convertToInr(Money src)
       throws RateUnavailableException {                  // 3
  return rateProvider.latest(src.currency())
      .map(src::convert)
      .orElseThrow(() -> new RateUnavailableException(src.currency()));
}

// Caller ke paas asli fallback hai: cached rate
public Money convertWithCachedFallback(Money src) {
  try {
    return convertToInr(src);                              // 4
  } catch (RateUnavailableException e) {
    return cachedRateStore.convertUsingLastKnown(src);      // 5
  }
}
  • 1Spring ka JdbcTemplate already SQLException ko unchecked DataAccessException me translate kar deta hai — yeh design intentional hai.
  • 2"Row nahi mila" ek business case hai, infra failure nahi. Isliye domain exception.
  • 3Yahan checked justified hai: FX rate down hona ek expected, recoverable business condition hai.
  • 4Compiler caller ko force karta hai socho — aur yahan sochne layak cheez hai.
  • 5Real fallback. Agar yahan bhi sirf rethrow hota, to checked ka koi fayda nahi tha — unchecked bana do.

Decision rule (interview me yahi bolna hai)

Checked chuno jabCaller ke paas ek meaningful alternate action hai (retry, cache, alternate provider, user prompt). Aur woh exception aapke module ke domain ki hai.
Unchecked chuno jabYe bug hai (IllegalArgument, IllegalState, NPE), ya infra failure hai jiske liye caller kuch nahi kar sakta, ya aap ek library/framework likh rahe ho jo streams/lambdas me use hogi.
Ignore kabModern Spring/Boot codebases me practically 95% exceptions unchecked rakho — lambda + Stream + CompletableFuture checked exceptions ke saath kaam nahi karte. Checked ko sirf narrow, genuinely-recoverable cases ke liye bachao.
T-03

try / catch / finally — aur woh trap jo exception gayab kar deta hai

return in finally no-return finally JLS 14.20.2

finally block ka return ya throw chal rahe exception ko discard kar deta hai. Yeh JLS me defined behaviour hai, bug nahi — isliye compiler warn bhi nahi karta.

Problem — exception ko finally ne kha liya
public int chargeCustomer(Order o) {
  try {
    paymentGateway.charge(o);      // throws PaymentDeclined
    return 200;
  } finally {
    auditLog.write(o);
    return 202;                 // <-- exception silently DISCARDED
  }
}

// Variant 2: mutation illusion
public int counter() {
  int x = 1;
  try { return x; }        // return value 1 already latched
  finally { x = 99; }      // returns 1, not 99
}

Kya hota hai: pehla case 202 return karta hai aur PaymentDeclined ka naamo-nishaan nahi bachta — customer ko paisa kata nahi, system ko laga sab theek hai. Doosre case me return value pehle hi stack pe copy ho chuki hoti hai, isliye x = 99 ka koi asar nahi. Dono JLS-compliant hain, dono production bug hain.

Solution — finally sirf cleanup ke liye, control flow ke liye nahi
public ChargeResult chargeCustomerWithAudit(Order order) {
  ChargeResult result = ChargeResult.pending(order.id()); // 1
  try {
    paymentGateway.charge(order);
    result = ChargeResult.captured(order.id());            // 2
    return result;
  } catch (PaymentDeclinedException e) {
    result = ChargeResult.declined(order.id(), e.reason()); // 3
    throw e;                                                // 4
  } finally {
    writeAuditTrail(order, result);                           // 5
  }                                                           // 6 - no return, no throw
}

private void writeAuditTrail(Order o, ChargeResult r) {
  try { auditLog.write(o, r); }
  catch (RuntimeException ignored) {                      // 7
    log.warn("audit write failed for order {}", o.id(), ignored);
  }
}
  • 1Outcome ko ek variable me capture karo taaki finally ko pata chale kya hua — bina control flow chhue.
  • 2Success path outcome set karta hai, phir return.
  • 3Failure path bhi outcome set karta hai — audit ko "declined" dikhega, "pending" nahi.
  • 4throw e; — original exception + original stack trace intact. throw new ...(e) bhi chalega, par yahan zaroorat nahi.
  • 5finally sirf side-effect karta hai. Yahi uska ekmatr kaam hona chahiye.
  • 6Rule: finally me kabhi return, break, continue ya throw mat likho.
  • 7Cleanup ka failure primary failure ko maskaana nahi chahiye — isliye andar hi catch karke sirf log.

Trade-off

Apply karoHar jagah jahan finally me I/O, audit, metrics ya lock-release ho raha hai.
Ignore karoAgar cleanup pure in-memory hai (lock.unlock(), counter decrement) to extra guard mat lagao — woh throw hi nahi karega, aur try-catch noise badha dega.
Enforce kaiseSpotBugs FI_FINALIZER/REC rules, Error Prone Finally check, ya Sonar rule S1143 CI me on kar do. Code review pe bharosa mat karo.
T-04

try-with-resources aur suppressed exceptions

manual close() AutoCloseable getSuppressed()

Manual finally { close(); } me agar close bhi fail ho jaaye, to woh asli exception ko replace kar deta hai. TWR isko getSuppressed() me bacha leta hai.

Problem — close() ne root cause mita diya
public String readFirstLine(Path p) throws IOException {
  BufferedReader r = null;
  try {
    r = Files.newBufferedReader(p);
    return r.readLine();       // throws CharacterCodingException
  } finally {
    if (r != null) r.close();   // throws IOException(disk full)
  }                             // caller ko sirf "disk full" milega
}

Kyun bura hai: asli bug encoding ka tha, par log me "disk full" dikha. On-call engineer 2 ghante storage debug karega. Aur agar newBufferedReader hi fail ho jaaye, to r null hai — null-check bhoolna NPE de dega jo original IOException ko chhupa dega.

Solution — TWR + suppressed ko surface karo
public String readFirstLineSafely(Path path) {
  try (BufferedReader reader =
           Files.newBufferedReader(path, UTF_8)) {          // 1
    return reader.readLine();
  } catch (IOException e) {
    logWithSuppressed("read failed: " + path, e);              // 2
    throw new FileReadException(path, e);                    // 3
  }
}

private void logWithSuppressed(String msg, Throwable primary) {
  log.error(msg, primary);
  for (Throwable s : primary.getSuppressed()) {               // 4
    log.error("  suppressed during close: {}", s.toString(), s);
  }
}

// Custom resource — Java 9+ effectively-final form
public void processWithLease(String key) {
  DistributedLock lease = lockRegistry.acquire(key);           // 5
  try (lease) {                                               // 6
    inventoryService.reserveStock(key);
  }
}
  • 1TWR resource ko reverse order me close karta hai, aur body ka exception primary rehta hai.
  • 2Close-time exception getSuppressed() me chhupa rehta hai — agar aap print nahi karoge to woh kahin nahi dikhega.
  • 3Domain exception me wrap. Caller ko IOException ka pata nahi chahiye.
  • 4Yeh loop bahut kam log likhte hain — production debugging me game-changer hai.
  • 5Koi bhi class jo AutoCloseable implement karti hai, TWR me chalti hai — locks, spans, tenants, MDC scopes.
  • 6Java 9+: already-initialised effectively-final variable ko seedha try (lease) me daal sakte ho.

Trade-off

Apply karoHar Closeable/AutoCloseable: streams, JDBC Connection, HttpClient responses, Kafka consumers, tracing scopes.
Ignore karoSpring-managed resources (JdbcTemplate, EntityManager, connection pools) ko manually close mat karo — container already handle kar raha hai. TWR lagana yahan pool corruption kar dega.
KyunOwnership rule: jisne resource banaya, wahi band karega. Injected resource ka owner aap nahi ho.
T-05

Multi-catch, catch order, aur precise rethrow

catch(Exception) catch(A | B) Java 7+

Catch blocks top-down match hote hain — pehla assignable type jeet jaata hai. Isliye subclass hamesha superclass se pehle.

Problem — duplicate blocks aur dead catch
try {
  importCatalog(file);
} catch (Exception e) {            // widest FIRST
  metrics.increment("import.fail");
  throw new ImportException(e);
} catch (IOException e) {          // COMPILE ERROR: unreachable
  ...
}

// aur yeh duplication:
catch (ParseException e)  { audit(e); throw new ImportException(e); }
catch (CsvException e)    { audit(e); throw new ImportException(e); }
catch (SchemaException e) { audit(e); throw new ImportException(e); }

Do problems: unreachable catch compile hi nahi hoga (achha hai), lekin agar Exception hi akela ho to aap InterruptedException aur IOException ko ek jaisa treat kar rahe ho — jo bilkul alag semantics hain. Aur teen identical blocks ka matlab hai teen jagah bug fix karna padega.

Solution — multi-catch + precise rethrow
public ImportSummary importCatalogFile(Path file) {
  try {
    return catalogImporter.run(file);
  } catch (ParseException | CsvException | SchemaException e) { // 1
    auditRejectedFile(file, e);
    throw new CatalogImportException(file, e);                   // 2
  } catch (InterruptedException e) {                            // 3
    Thread.currentThread().interrupt();                          // 4
    throw new CatalogImportException(file, e);
  }
}

// Precise rethrow (Java 7+): compiler A|B infer karta hai, Exception nahi
public void retryOnce(Path file)
       throws ParseException, CsvException {                       // 5
  try {
    catalogImporter.run(file);
  } catch (Exception e) {
    metrics.increment("import.retry");
    throw e;                                                     // 6
  }
}
  • 1Multi-catch: teeno ka handling identical hai, isliye ek hi block. Variable e implicitly final hota hai.
  • 2Ek hi wrapping point — maintainability ke liye.
  • 3InterruptedException ko kabhi bhi generic bucket me mat daalo.
  • 4Interrupt flag restore karna mandatory hai; warna thread-pool shutdown atak jaayega. Yeh line miss karna classic bug hai.
  • 5Method sirf do exceptions declare karta hai, jabki catch Exception hai.
  • 6Precise rethrow: compiler dekhta hai ki try body me sirf ParseException/CsvException hi throw ho sakte hain, isliye throw e valid hai. Java 6 me yeh compile nahi hota tha.

Trade-off

Multi-catch use karoJab handling bilkul identical ho. 3+ branches ke liye ideal.
Ignore karoJab har exception ka alag error code, alag HTTP status, ya alag retry policy ho. Tab alag blocks hi chahiye — merge karna information destroy karta hai.
GotchaMulti-catch variable implicitly final hai — usme reassign nahi kar sakte. Aur sibling types hi chahiye; IOException | Exception compile nahi hoga.
T-06

Custom exception design — BaseAppException + ErrorCode

new Exception("failed") ErrorCode enum LLD

Exception ka kaam sirf "kuch toota" batana nahi hai — usme machine-readable code, context data, aur retry hint hona chahiye.

Problem — exception class explosion aur message-based parsing
// 60+ classes, sab ek jaisi
class UserNotFound       extends RuntimeException {}
class OrderNotFound      extends RuntimeException {}
class InvoiceNotFound    extends RuntimeException {}
// ... 57 more

throw new RuntimeException("Insufficient balance for user 91");

// Consumer ka code — asli horror
if (e.getMessage().contains("Insufficient")) { ... }

Kyun tootta hai: message ek human string hai — kal koi typo theek karega aur client ka contains() chup-chaap fail ho jaayega. i18n add karoge to message Hindi me aa jaayega. Aur 60 near-identical classes maintain karne se koi fayda nahi, sirf cognitive load hai.

Solution — chhoti hierarchy + rich ErrorCode
public enum ErrorCode {                                       // 1
  USER_NOT_FOUND      ("USR-404", NOT_FOUND,   false),
  INSUFFICIENT_FUNDS  ("PAY-422", UNPROCESSABLE_ENTITY, false),
  RATE_PROVIDER_DOWN  ("FX-503",  SERVICE_UNAVAILABLE,  true);  // 2

  private final String code;
  private final HttpStatus status;
  private final boolean retryable;
  // constructor + getters omitted
}

public abstract class BaseAppException extends RuntimeException {
  private final ErrorCode errorCode;
  private final Map<String, Object> context;                  // 3

  protected BaseAppException(ErrorCode code, String msg,
                              Map<String,Object> ctx, Throwable cause) {
    super(msg, cause);
    this.errorCode = code;
    this.context = ctx == null ? Map.of() : Map.copyOf(ctx);
  }
  public ErrorCode getErrorCode() { return errorCode; }
  public boolean isRetryable()   { return errorCode.isRetryable(); }
}

// Sirf 4 subclasses — semantic buckets
public class ResourceNotFoundException  extends BaseAppException { } // 4
public class BusinessRuleException      extends BaseAppException { }
public class DownstreamException        extends BaseAppException { }
public class ConcurrencyConflictException extends BaseAppException { }

// Call site — clean, typed, context-rich
throw new BusinessRuleException(
    ErrorCode.INSUFFICIENT_FUNDS,
    "balance below order total",
    Map.of("userId", userId, "shortfallPaise", shortfall),  // 5
    null);
  • 1Enum = single source of truth. Naya error add karna ek line ka kaam, naya class file nahi.
  • 2retryable flag exception ke saath travel karta hai — resilience layer isse padh ke decide karega (T-24).
  • 3Structured context, string concatenation nahi. Yeh JSON logs aur ProblemDetail extensions me directly jaata hai.
  • 44-6 buckets kaafi hain, kyunki @ExceptionHandler type pe match karta hai. Bucket = HTTP mapping.
  • 5Map.of(...) immutable hai — exception object kabhi mutate nahi hona chahiye.

Trade-off: kitni granularity?

Bucket + code (recommended)Handler count kam, error catalogue rich. Naya error = enum entry. Yeh 90% microservices ke liye sahi choice hai.
Per-case class kabJab kisi specific exception pe alag control flow chahiye — e.g. @Retryable(retryFor = OptimisticLockException.class), ya circuit breaker ka recordExceptions. Type-based matching ke liye alag class chahiye hi.
Ignore karoEk public library likh rahe ho? Tab enum-based codes mat thopo — consumers ko stable, granular types chahiye, aapka internal code catalogue nahi.
T-07

Wrap vs swallow vs rethrow — cause chain ka anatomy

new Ex(e.getMessage()) new Ex(msg, e) initCause

Cause pass karna ek line ka kaam hai, aur usko bhoolna production debugging ka sabse bada single cause hai.

Problem — cause chain toot gayi
try {
  paymentClient.capture(req);
} catch (FeignException e) {
  throw new PaymentException(e.getMessage());  // cause GONE
}

// Production log:
// PaymentException: [500] during [POST] to [http://pay/v2/capture]
//   at PaymentService.capture(PaymentService.java:88)
//   ... 40 frames of Spring proxies
// Caused by: (nothing)

Kya kho gaya: HTTP response body, downstream ka trace-id, socket timeout details, aur woh 12 frames jo batate ki connection pool exhaust hua tha. Ab aapke paas sirf ek generic 500 ka message hai. Doosra variant: catch (Exception e) { } — bilkul khaali. Yeh exception aur uska stack trace dono mita deta hai.

Solution — teen valid strategies, aur kab konsi
// STRATEGY 1: WRAP — layer boundary cross karte waqt
public CaptureReceipt capturePayment(CaptureRequest req) {
  try {
    return paymentClient.capture(req);
  } catch (FeignException e) {
    throw new DownstreamException(
        ErrorCode.PAYMENT_GATEWAY_DOWN,
        "capture failed for txn " + req.txnId(),
        Map.of("httpStatus", e.status(), "txnId", req.txnId()),
        e);                                        // 1  <-- cause
  }
}

// STRATEGY 2: RETHROW — enrich karo, replace mat karo
public void settleBatch(String batchId) {
  try {
    settlementEngine.run(batchId);
  } catch (BaseAppException e) {
    metrics.counter("settle.fail", "code",
                    e.getErrorCode().name()).increment();   // 2
    throw e;                                             // 3
  }
}

// STRATEGY 3: SWALLOW — only when truly optional
public void sendOrderConfirmationBestEffort(Order order) {
  try {
    notificationClient.sendEmail(order.customerEmail(), order);
  } catch (RuntimeException e) {
    log.warn("confirmation email skipped for order {}",
             order.id(), e);                                // 4
    outbox.enqueueRetry(order.id(), EMAIL_CONFIRMATION);   // 5
  }
}
  • 1Cause hamesha last constructor arg. Yeh Caused by: chain banata hai — poora downstream trace bach jaata hai.
  • 2Enrich = metric/log/MDC add karo. Exception object ko mat badlo.
  • 3throw e; original stack trace preserve karta hai. Agar throw new X(e) karoge to ek aur frame layer add ho jaayegi bina kisi fayde ke.
  • 4Swallow tabhi jayaz hai jab (a) failure genuinely optional ho aur (b) aap usko log/metric karo.
  • 5Sachcha swallow kabhi nahi hota — compensating action honi chahiye. Yahan outbox retry.

Decision table

Wrap karoLayer boundary par (repo→service, client→service). Jab caller ko lower layer ka type nahi pata hona chahiye.
Rethrow karoSame layer me, jab aapko sirf observe karna hai. Double-wrapping se stack trace 3x lamba ho jaata hai aur cause 4 levels neeche chhup jaata hai.
Swallow karoSirf best-effort side-effects: analytics, notification, cache warm-up, audit. Kabhi bhi persistence ya payment path me nahi.
T-08

Logging rules — log-and-throw anti-pattern

log + throw log at boundary MDC / traceId

Rule: ek exception, ek error log. Woh bhi uss jagah jahan exception ka safar khatam hota hai.

Problem — ek failure, paanch stack traces
// Repository
catch (DataAccessException e) {
  log.error("db fail", e); throw e;   // log #1
}
// Service
catch (DataAccessException e) {
  log.error("service fail", e); throw new AppEx(e); // log #2
}
// Facade
catch (AppEx e) {
  log.error("facade fail", e); throw e;   // log #3
}
// ControllerAdvice
log.error("handled", e);                   // log #4

// Aur uska ulta bhi bura:
log.error("payment failed: " + e.getMessage());  // no stack trace

Do costs: ek request ke liye 4 alag stack traces — alerting me 4 incidents ban gaye, aur log bill 4x. Doosri taraf e.getMessage() string me concat karna stack trace bilkul hata deta hai; aur agar message null hai (NPE me hota hai) to log line "payment failed: null" ban jaati hai.

Solution — boundary logging + structured context
// Inner layers: koi log nahi, sirf context add karo
public Order loadOrderForUpdate(String orderId) {
  return orderRepository.findByIdForUpdate(orderId)
      .orElseThrow(() -> new ResourceNotFoundException(       // 1
          ErrorCode.ORDER_NOT_FOUND, "order missing",
          Map.of("orderId", orderId), null));
}

// Boundary (ControllerAdvice) — ekmatr logging point
@ExceptionHandler(BaseAppException.class)
public ProblemDetail handleApplicationException(BaseAppException e) {
  logAtSeverity(e);                                          // 2
  return problemDetailFactory.from(e);
}

private void logAtSeverity(BaseAppException e) {
  ErrorCode code = e.getErrorCode();
  if (code.getStatus().is5xxServerError()) {                  // 3
    log.error("code={} ctx={}", code.name(), e.getContext(), e);
  } else {
    log.warn("code={} ctx={}", code.name(), e.getContext());   // 4
  }
}

// Trace correlation — filter me, request start pe
public void bindTraceContext(String traceId, String userId) {
  MDC.put("traceId", traceId);                              // 5
  MDC.put("userId", userId);
}
  • 1Inner layer exception banata hai context ke saath, log nahi karta. Context exception ke andar travel karta hai.
  • 2Ek hi jagah severity decide hoti hai — poore app me consistent.
  • 34xx = client ki galti = warn. 5xx = hamari galti = error + alert. Yeh distinction PagerDuty noise 80% kam kar deta hai.
  • 44xx me stack trace mat daalo — validation failure ka stack trace bekaar hai aur log volume kha jaata hai.
  • 5MDC har log line me traceId inject karta hai. finally me MDC.clear() zaroori hai, warna thread reuse pe leak hoga.

Trade-off

ApplyBoundary-only logging — REST advice, message listener, scheduled job ka outermost method.
Ignore (i.e. double-log allowed)Jab exception async boundary cross karta hai (thread pool, Kafka listener, CompletableFuture) — wahan trace toot jaata hai, isliye crossing point pe ek extra log valid hai.
Kabhi mat karolog.error(msg + e.getMessage()). Hamesha log.error("msg {}", arg, e) — last arg Throwable ho to SLF4J usko stack trace ki tarah treat karta hai.
T-09

Performance — stack trace ka asli cost

exception as flow fillInStackTrace() JIT

Exception throw karna sasta hai. Uska stack trace capture karna mehnga hai — kyunki JVM poore stack ko walk karke frames materialize karta hai.

Problem — control flow ke liye exception
// Har cache miss pe exception — 50k rps pe CPU kill
public Rate lookup(String ccy) {
  try {

// Result type — Java 21 sealed + record
public sealed interface Result<T>
       permits Result.Ok, Result.Err {                        // 1

  record Ok<T>(T value) implements Result<T> {}
  record Err<T>(ErrorCode code, String detail)
         implements Result<T> {}

  static <T> Result<T> ok(T v)  { return new Ok<>(v); }
  static <T> Result<T> err(ErrorCode c, String d) {
    return new Err<>(c, d);
  }
}

      case Result.Ok<Row>(Row row)      -> accepted.add(row);
      case Result.Err<Row>(var c, var d) ->

    }
  }

  return new ImportReport(accepted.size(), failures);        // 5
}

  • 3Pattern matching switch (Java 21) — default ki zaroorat nahi, sealed hierarchy exhaustive hai.
  • 4Valid rows save ho gaye. Partial success ek valid business outcome hai.
  • 5Client ko poori failure list milti hai — ek round trip me sab theek kar sakta hai.
  • 6Optional sirf "nahi mila" ke liye. Kabhi bhi field, parameter, ya collection element me Optional mat rakho — sirf return type.

@Component

  public JwtAuthenticationFilter(
      @Qualifier("handlerExceptionResolver")                  // 1
      HandlerExceptionResolver resolver) {
    this.resolver = resolver;
  }

  @Override
  protected void doFilterInternal(HttpServletRequest request,
      HttpServletResponse response, FilterChain chain)
      throws ServletException, IOException {
    try {
      extractAndAuthenticate(request);                       // 2
      chain.doFilter(request, response);
    } catch (JwtValidationException e) {
      resolver.resolveException(request, response, null, e); // 3
    }

    String header = request.getHeader(HttpHeaders.AUTHORIZATION);
    if (header == null || !header.startsWith(BEARER_PREFIX)) {
      return;                                              // 4
    }
    Authentication auth = jwtDecoder.decode(
        header.substring(BEARER_PREFIX.length()));
    SecurityContextHolder.getContext().setAuthentication(auth);
  }
}

public RestClient paymentRestClient(RestClient.Builder builder) {

      ClientHttpRequestFactorySettings.DEFAULTS
          .withConnectTimeout(Duration.ofSeconds(2))          // 1
          .withReadTimeout(Duration.ofSeconds(5));

      .baseUrl(paymentProperties.baseUrl())

                            this::translateDownstreamError)       // 2

private void translateDownstreamError(HttpRequest request,
    ClientHttpResponse response) throws IOException {

  HttpStatusCode status = response.getStatusCode();
  String body = new String(response.getBody().readAllBytes());

  if (status.value() == 404) {                                 // 3
    throw new ResourceNotFoundException(
        ErrorCode.PAYMENT_TXN_NOT_FOUND, Map.of("uri", request.getURI()));
  }
  if (status.is4xxClientError()) {                             // 4
    throw new BusinessRuleException(
        ErrorCode.PAYMENT_REJECTED, body,
        Map.of("downstreamStatus", status.value()), null);
  }
  throw new DownstreamException(                              // 5
      ErrorCode.PAYMENT_GATEWAY_DOWN, "payment service error",
      Map.of("downstreamStatus", status.value()), null);
}

@Scheduled(fixedDelay = 500)
public void drainOutboxToBroker() {

      outboxRepository.findUnpublished(BATCH_SIZE);            // 5

PART 5 / DECISIONS

Trade-off matrix: kab handle, kab wrap, kab ignore

Ek exception aane par exactly paanch options hain. Yeh table batata hai kaunsa kab.

OptionKab apply kareinKab ignore kareinCost agar galat chuna
1. Propagate (kuch mat karo) Default. Aapke paas fallback nahi hai. Upar koi layer isko better handle karegi. Jab exception type caller ki layer ke liye meaningless ho (SQLException controller me). Abstraction leak; caller ko lower-layer types pe depend karna pada.
2. Wrap + propagate Layer boundary cross ho rahi hai. Cause hamesha attach karo. Same layer me — double wrapping se cause 4 levels neeche dab jaata hai. Stack trace 3x lamba, root cause dhoondhna mushkil.
3. Handle + fallback Aapke paas ek real alternative hai: cache, default value, degraded mode. Jab "fallback" sirf null ya empty ho — woh problem ko aage sarkana hai. Silent data corruption; caller ko laga sab theek hai.
4. Retry Transient failure + idempotent operation + bounded attempts + backoff with jitter. 4xx, validation, business rejection, ya non-idempotent POST bina idempotency key ke. Duplicate charges; downstream pe 3x load jab woh already gir raha ho.
5. Swallow + compensate Best-effort side effect: analytics, cache warm, notification. Hamesha log + outbox/retry ke saath. Kisi bhi persistence, payment, ya state-change path me. Kabhi nahi. Data loss jo months baad reconciliation me pakda jaata hai.

3. Agar main isko chhupa doon, to kaun kab pata lagayega?"Koi nahi" ya "3 mahine baad" → mat chhupao. Yeh sabse important sawaal hai.

PART 7 / MOCK ROUND

40 mock questions with answers

Pehle apna jawab socho, phir kholo. Jo teen-chaar galat ho, unke topic pe wapas jaao — har answer me relevant T-number diya hai.

Java core

Q1Checked aur unchecked exception me asli farak kya hai — sirf compiler ka hai ya runtime ka bhi?

Farak sirf compile-time ka hai. JVM runtime pe dono ko bilkul ek jaisa treat karta hai — same stack unwinding, same exception table lookup. Compiler checked exceptions ke liye "handle or declare" rule enforce karta hai; RuntimeException aur Error ki subclasses isse exempt hain. Design intent: checked = "caller iska jawab de sakta hai", unchecked = "yeh bug hai ya un-recoverable state". (T-02)

Q2finally block kab nahi chalega?

Chaar cases: (1) System.exit() call ho gaya, (2) JVM crash ya kill -9, (3) thread ko forcibly stop kiya gaya (deprecated Thread.stop()), (4) try block me infinite loop ya deadlock — control kabhi bahar nikla hi nahi. OutOfMemoryError pe finally chal sakta hai, par uske andar allocation dobara fail ho sakti hai. (T-03)

Q3try { return 1; } finally { return 2; } — kya return hoga aur kyun?

2. finally ka return try ke pending return ko override kar deta hai. Agar try me exception thrown hoti aur finally me return hota, to exception discard ho jaati — bilkul silently. Isliye rule: finally me kabhi return/throw/break/continue nahi. (T-03)

Q4try-with-resources me suppressed exception kya hoti hai?

Agar try body exception throw kare aur phir close() bhi exception throw kare, to body wali primary rehti hai aur close wali getSuppressed() array me chali jaati hai. Manual finally { close(); } me ulta hota hai — close wali primary ko replace kar deti hai aur root cause gayab ho jaata hai. Suppressed exceptions ko log karna zaroori hai, warna woh kahin dikhenge nahi. (T-04)

Q5Resources kis order me close hote hain, aur kya catch se pehle ya baad me?

Declaration ke ulte order me (last declared, first closed) — kyunki baad wala resource pehle wale pe depend kar sakta hai. Aur close pehle hota hai, uske baad catch/finally chalte hain. Isliye catch block me resource already band ho chuka hota hai. (T-04)

Q6Multi-catch catch (A | B e) me e ka type kya hota hai?

A aur B ka least upper bound — aksar Exception ya unka common supertype. Aur e implicitly final hota hai, usme reassign nahi kar sakte. Multi-catch me sibling types hone chahiye; IOException | Exception compile nahi hoga kyunki ek doosre ka subtype hai. (T-05)

Q7Precise rethrow kya hai?

Java 7 se compiler analyse karta hai ki try body actually kaunse exceptions throw kar sakti hai. Isliye catch (Exception e) { throw e; } likhne par bhi method sirf throws ParseException, CsvException declare kar sakta hai — throws Exception nahi. Condition: e effectively final ho. (T-05)

Q8InterruptedException catch karne ke baad kya karna chahiye?

Ya to usko propagate karo, ya Thread.currentThread().interrupt() call karke flag restore karo. Exception throw hote waqt JVM interrupt flag clear kar deta hai — agar aapne restore nahi kiya to upar wale code ko kabhi pata nahi chalega ki cancel signal aaya tha, aur thread-pool ka graceful shutdown hang ho jaayega. Isko chup-chaap swallow karna sabse common concurrency bug hai. (T-05, T-10)

Q9Exception throw karna kitna mehnga hai?

throw aur stack unwinding sasta hai. Mehnga hai fillInStackTrace() — JVM poore stack ko walk karke har frame materialize karta hai, typically 1–10 µs stack depth ke hisaab se. Isse bachne ke do tareeke: 4-arg constructor me writableStackTrace = false, ya fillInStackTrace() override karke this return karna. Par yeh sirf hot paths pe karo — normal business exceptions me stack trace ki value cost se kahin zyada hai. (T-09)

Q10Production me NPE ka stack trace khaali kyun aata hai?

HotSpot ka OmitStackTraceInFastThrow optimisation. Jab ek hi jagah se same implicit exception (NPE, ArrayIndexOutOfBounds, ClassCast) baar-baar throw hoti hai, JIT usko ek pre-allocated stack-trace-less instance se replace kar deta hai. Debug karne ke liye -XX:-OmitStackTraceInFastThrow lagao. Java 14+ me -XX:+ShowCodeDetailsInExceptionMessages helpful NPE messages bhi deta hai. (T-09)

Q11ExecutorService.submit() aur execute() me exception handling ka farak?

execute() ka exception thread ke UncaughtExceptionHandler tak jaata hai. submit() exception ko Future ke andar capture kar leta hai — agar aapne get() call nahi kiya to woh exception kahin log nahi hoga, bilkul silent. Aur get() usko ExecutionException me wrap karta hai, isliye asli exception e.getCause() me milti hai. (T-10)

Q12OutOfMemoryError catch karna chahiye?

Practically nahi. Heap khatam hone ke baad logging ka StringBuilder bhi allocate nahi ho payega, kuch threads mar chuke honge, locks held reh jaayenge. Sahi jawab hai -XX:+ExitOnOutOfMemoryError + -XX:+HeapDumpOnOutOfMemoryError — heap dump lo aur process ko marne do, orchestrator restart kar dega. Rokne ka asli tarika: pagination, streaming, aur request size limits. (T-11)

Q13Optional kab use karein aur kab nahi?

Sirf return type ke liye, aur sirf jab "absent" ek valid, expected outcome ho. Fields, method parameters, ya collection elements me Optional mat rakho — woh serialization todta hai aur extra allocation deta hai. Aur orElse() ki jagah orElseGet() use karo agar fallback mehnga ho, kyunki orElse() ka argument hamesha evaluate hota hai. (T-12)

Q14Custom exception me kya-kya hona chahiye?

Ek machine-readable ErrorCode, immutable structured context map, cause lene wala constructor, aur ek retryable hint. Message human ke liye hai — usko kabhi programmatically parse mat karo. Aur hierarchy chhoti rakho: 4–6 semantic buckets + ek rich error-code enum, 60 near-identical classes se behtar hai. (T-06)

Q15Exception controller se response tak ka poora rasta bataiye.

Controller method ka exception HandlerAdapter se DispatcherServlet.doDispatch() ke catch tak aata hai, wahan dispatchException me store hota hai. Phir processHandlerException() chalta hai jo HandlerExceptionResolverComposite ko poochta hai. Chain order: ExceptionHandlerExceptionResolver (aapka @ExceptionHandler/advice) → ResponseStatusExceptionResolver → DefaultHandlerExceptionResolver. Pehla jo non-null ModelAndView de, wahi jeet-ta hai. Koi na de to request /error pe forward hoti hai. (T-18)

Q16Filter me thrown exception ko @ControllerAdvice kyun nahi pakadta?

Filter chain DispatcherServlet se pehle chalti hai — request MVC ki duniya me daakhil hui hi nahi, isliye processHandlerException() kabhi call nahi hota. Do fix: filter me HandlerExceptionResolver inject karke (@Qualifier("handlerExceptionResolver")) khud resolve karo, ya filter ke andar hi JSON response likho. Security ke 401/403 ke liye AuthenticationEntryPoint aur AccessDeniedHandler use karo. (T-19)

Q17@ControllerAdvice aur @RestControllerAdvice me farak?

@RestControllerAdvice = @ControllerAdvice + @ResponseBody. Yani return value seedha message converter se JSON ban jaati hai, view resolve karne ki koshish nahi hoti. REST APIs me hamesha @RestControllerAdvice. Dono ko basePackages, assignableTypes, ya annotations se scope kiya ja sakta hai. (T-14)

Q18Do advices ek hi exception handle karte hain — kaun jeet-ta hai?

Pehle: controller-local @ExceptionHandler hamesha global advice se pehle. Advices ke beech @Order/Ordered decide karta hai (kam number = zyada priority). Ek hi advice ke andar do methods ho to Spring closest type match chunta hai — BusinessRuleException ke liye BusinessRuleException wala handler jeetega, Exception wala nahi. Catch-all advice ko hamesha LOWEST_PRECEDENCE pe rakho. (T-14, T-18)

Q19ProblemDetail kya hai aur Boot 2.x se kya badla?

Spring Framework 6 (Boot 3.x) ka RFC 7807 implementation. Fields: type, title, status, detail, instance, plus setProperty() se custom extensions. Content-type application/problem+json. Boot 2.x me har team apna DTO banati thi. 3.x me exceptions khud ErrorResponse implement karke apna status + body bata sakti hain, aur spring.mvc.problemdetails.enabled=true se framework ke apne errors bhi RFC 7807 ban jaate hain. (T-15)

Q20Boot 2 se 3 migrate karte waqt exception handling me kya-kya tootta hai?

Char cheezein: (1) javax.* → jakarta.* — saare validation aur servlet imports. (2) ResponseEntityExceptionHandler ke override methods me HttpStatus → HttpStatusCode. (3) Boot 3.2+ me @RequestParam/@PathVariable validation ab HandlerMethodValidationException deti hai, ConstraintViolationException nahi. (4) spring.mvc.throw-exception-if-no-handler-found default true ho gaya — jo advices 404 nahi handle karte the, unme ab 404 aane lagega. (T-15, T-17, T-18)

Q21@ResponseStatus(reason = "...") se kya problem hai?

reason set karte hi Spring HttpServletResponse.sendError() call karta hai. Isse request container ke error page mechanism pe chali jaati hai — aapka @ControllerAdvice bypass ho jaata hai aur response me aapka JSON contract nahi, Tomcat ka HTML error page aata hai. Codebase me grep karke hata do. (T-16)

Q22MethodArgumentNotValidException aur ConstraintViolationException kab aati hain?

MethodArgumentNotValidException: @Valid @RequestBody pe — body binding fail hui, default 400. ConstraintViolationException: class pe @Validated + method parameters pe constraints (@RequestParam @Min(1)) — yeh method-level validation hai aur default 500 deta hai, isliye explicit handler zaroori hai. Teesra: @ModelAttribute forms pe BindException. Boot 3.2+ me HandlerMethodValidationException. (T-17)

Q23List<ItemDto> ke elements validate kyun nahi hote?

Kyunki @Valid collection pe lagane se sirf collection-level constraints chalti hain. Elements ke liye @Valid element type pe chahiye: List<@Valid ItemDto> items. Isi tarah nested objects ke liye field pe @Valid chahiye, warna uske andar ke constraints skip ho jaate hain. Yeh silent hole hai — koi error nahi aata, bas validation hoti hi nahi. (T-17)

Q24404 pe mera advice kyun nahi chalta?

Fix: spring.mvc.throw-exception-if-no-handler-found=true aur spring.web.resources.add-mappings=false. Boot 3.2+ me pehla flag default true hai. (T-18)

Q25Custom HandlerExceptionResolver kab likhoge?

Q26@Async method ka exception kahan jaata hai?

void return karne wale @Async method ka exception AsyncUncaughtExceptionHandler ko jaata hai — agar aapne AsyncConfigurer.getAsyncUncaughtExceptionHandler() configure nahi kiya to sirf ek default log line aati hai (aur aksar woh bhi miss ho jaati hai). Agar return type CompletableFuture hai to exception future me store hoti hai, uncaught handler chalta hi nahi — caller ko .exceptionally()/.handle() lagana hoga. (T-23)

Q27@Async aur @Transactional ek saath lagane se kya hota hai?

Naya thread = naya transaction context. Caller ka transaction async method me available nahi hota, kyunki transaction ThreadLocal (TransactionSynchronizationManager) me bandha hota hai. Isliye lazily-loaded JPA entities pe LazyInitializationException aati hai, aur async method ka rollback caller ko affect nahi karta. Entity ki jagah ID pass karo aur async method ke andar dobara load karo. (T-23)

Q28MDC/traceId async thread me kyun gayab ho jaata hai?

MDC ek ThreadLocal hai. Naya thread apna khaali MDC leke aata hai. Fix: ThreadPoolTaskExecutor.setTaskDecorator() me parent ka MDC.getCopyOfContextMap() submit-time pe capture karo aur run-time pe setContextMap() karo, phir finally me MDC.clear(). Reactive me MDC kaam hi nahi karti — Reactor Context use karo. (T-23, T-25)

Q29Downstream service ka 500 aapke API me kya banna chahiye?

502 ya 503, 500 nahi — kyunki failure aapki service ki nahi, dependency ki hai. Aur usko ek domain exception (DownstreamException) me translate karo jisme retryable = true ho. Downstream ka 4xx alag hai: woh matlab humne galat request bheji ya business rule fail hui — usko retry mat karo, apne domain ke 422/409 me map karo. (T-24)

Q30@Retryable aur @Transactional ek hi method pe kyun nahi lagane chahiye?

Kyunki retry transaction ke andar ho jaata hai — pehli attempt me transaction already rollback-only mark ho chuka hota hai, to baaki attempts usi doomed transaction me chalti hain aur commit pe UnexpectedRollbackException aata hai. Sahi structure: outer method pe @Retryable (bina TX), aur woh ek alag bean ke @Transactional method ko call kare — har attempt ka apna fresh transaction. (T-22)

Q31WebFlux me try/catch kyun kaam nahi karta?

Kyunki try block sirf pipeline assemble karta hai; actual execution subscribe ke waqt hoti hai, jab woh stack frame khatam ho chuka hota hai. Reactive me exception ek onError signal hai jo stream me travel karta hai. Operators use karo: onErrorResume (fallback stream), onErrorReturn (fallback value), onErrorMap (translate), doOnError (observe only), retryWhen. (T-25)

Q32WebFlux me global exception handler kaise banate hain?

Annotated controllers ke liye @RestControllerAdvice + @ExceptionHandler chalta hai. Functional routes aur filter-level errors ke liye AbstractErrorWebExceptionHandler extend karke ek bean banao aur @Order(-2) do — Boot ke DefaultErrorWebExceptionHandler (order -1) se pehle chalna zaroori hai. (T-25)

Q33Kafka me poison message ko kaise handle karte hain?

DefaultErrorHandler + DeadLetterPublishingRecoverer: bounded retries with exponential backoff, phir .DLT topic pe park. addNotRetryableExceptions() me deserialization aur validation failures daalo — woh kabhi theek nahi honge. Deserialization ko ErrorHandlingDeserializer se wrap karo taaki woh exception ki jagah ek handle-able record bane. Aur DLT depth pe alert lagao, warna woh silent graveyard ban jaata hai. (T-26)

Q34Blocking retry aur @RetryableTopic me kya chuno?

Blocking retry (DefaultErrorHandler) ordering preserve karta hai, par retries ke dauraan poori partition ruk jaati hai — financial ledgers ke liye sahi. @RetryableTopic non-blocking hai: message alag retry topic pe chala jaata hai aur main partition aage badh jaati hai — throughput high, par ordering guarantee khatam. Notifications aur analytics ke liye yahi behtar hai. (T-26)

Transactions

Q35Default me kaunsi exceptions rollback trigger karti hain?

Sirf RuntimeException aur Error (aur unki subclasses). Checked exceptions pe transaction commit ho jaata hai. Badalne ke liye @Transactional(rollbackFor = X.class) ya noRollbackFor. Yeh rule RuleBasedTransactionAttribute.rollbackOn() me implement hai — Animation Lab ka Tab 3 isko step-by-step dikhata hai. (T-20)

Q36Same class ke method ko call karne par @Transactional kyun ignore ho jaata hai?

Spring ka @Transactional proxy-based AOP hai. Bahar se call proxy pe aati hai, proxy TransactionInterceptor chalata hai, phir target ko call karta hai. Lekin this.method() seedha target object pe jaata hai — proxy beech me hai hi nahi, isliye interceptor chalta hi nahi. Fix: method ko alag bean me nikalo (best), ya TransactionTemplate use karo, ya AopContext.currentProxy() (hacky). Yahi limitation @Async, @Cacheable aur @Retryable pe bhi lagti hai. (T-20)

Q37UnexpectedRollbackException kyun aata hai jabki maine exception catch kar li thi?

Inner method REQUIRED tha, yani usne naya transaction nahi banaya — outer wala hi join kiya. Inner me exception aane par Spring ne shared transaction pe rollbackOnly = true set kar diya. Aapne exception catch kar li par flag laga reh gaya, aur commit ke waqt Spring ne dekha ki transaction rollback-only hai. Fix: inner ko REQUIRES_NEW do, ya us kaam ko @TransactionalEventListener(AFTER_COMMIT) me le jaao. (T-21)

Q38REQUIRES_NEW ka hidden cost kya hai?

Woh outer transaction ko suspend karta hai par uska connection release nahi karta — inner ke liye pool se ek doosra connection leta hai. Loop me lagaya to har iteration me do connections held. 10 concurrent requests × 20 items = pool exhaustion aur deadlock. Alternative: outbox pattern ya AFTER_COMMIT event. (T-21)

Q39Optimistic aur pessimistic locking me kab kya chuno?

Optimistic (@Version): low contention, read-heavy. Zero lock overhead; conflict pe OptimisticLockingFailureException → 409 + client retry. Pessimistic (SELECT ... FOR UPDATE): high contention aur chhota critical section — inventory, seat booking. Throughput kam par predictable; lock timeout aur deadlock tune karne padte hain. Rule of thumb: conflict rate 10% se upar jaaye to pessimistic sasta pad jaata hai. (T-22)

Q40DB write aur Kafka publish ko atomic kaise karein?

Kar nahi sakte — @Transactional broker ko cover nahi karta (2PC practically viable nahi). Solution: transactional outbox. Business row aur ek outbox row ek hi DB transaction me likho. Ek alag poller ya Debezium CDC outbox ko broker pe publish karta hai aur publish confirm hone par mark karta hai. Yeh at-least-once deta hai, isliye consumer ko idempotent hona chahiye — ek processed_events table ya unique constraint se. (H-03, T-26)
