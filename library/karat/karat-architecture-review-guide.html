Problem → Nuksaan → Fix

Karat ke "what issues do you see" round ki poori taiyari, ek jagah. Method, red-flag words, teen solved questions with diagrams, aur agar interviewer design banane ko bole toh kya karna hai.

Round kaise hota hai

Karat mein system design wale hisse mein lagbhag 15–20 minute mein kai chhote scenarios aate hain, har ek par 3–4 minute. Poora question (diagram + spec + clarifications) ek saath screen par aata hai. Aapko issues list karne hain, redesign nahi. Interviewer ek-ek issue ko count karta hai, aur dekhta hai ki aapne nuksaan (impact) samjha ya nahi.

4 minute ka time plan

TimeKya karna hai
0:00 – 0:30Pehle clarifications padho, phir spec par nazar. Zaroorat ho toh ek clarifying question poochho.
0:30 – 3:00Spec section by section padhte hue issues bolte jao. Sabse bade issues pehle (data loss, leak, galat data).
3:00 – 4:00Checklist sweep: 5 sawal (neeche) mein se kaunsa category abhi tak nahi bola? Diagram vs spec mismatch check karo.
Aapki teen rounds ki sabse badi galti: (1) redesign kar dena, (2) sirf diagram se issues nikalna aur spec/clarifications chhod dena, (3) fix bolna par nuksaan nahi bolna. Yeh teeno theek karo, score double ho jayega.

Solve karne ka method

  1. Clarifications pehle padho. Har clarification line kam se kam ek issue ka hint hoti hai. "No backups", "one data center", "sequential ID", "no load testing" jaisi lines free points hain.
  2. Spec ko upar se neeche, section by section padho. Har component ke liye poochho: yeh gira toh? zyada load aaya toh? isme kaunsa data hai? isko kaun access kar sakta hai?
  3. Red-flag words par ruko. "in memory", "single", "dropped", "saves card", "waits", "every 5 minutes", "local file". Neeche poori list hai.
  4. Diagram ko spec se match karo. Spec mein kuch likha hai jo diagram mein nahi (ya ulta)? Arrow ki direction galat? Yeh mismatch khud ek issue hai, aur interviewers isko jaanbujh kar daalte hain.
  5. 5 sawal ka sweep karo (yeh aapki purani 4-point checklist ka upgraded version hai):
    SawalKya dhoondhna hai
    Kya fail hoga?Single instance, single LB/DB/queue, ek data center, bina health check ke routing
    Kya slow hoga?Traffic spike, heavy reports on main DB, sync third-party calls, ML per request, no cache
    Kya leak hoga?PII copy, card/CVV store, PII in URL, public admin panel, guessable IDs, weak kiosk auth
    Kya galat ya lost hoga?Double booking, stale cache, dropped messages, no backups, offline sync conflicts, state in memory
    Pata kaise chalega?Monitoring, alerts, centralized logs, replication lag, audit logs

    "Galat ya lost" nayi category hai. Cinema question mein double booking isi se pakda jaata hai, aur purani checklist mein yeh chhoot raha tha.

  6. Priority order mein bolo. Pehle data loss + security leak + galat data (business ko sabse zyada nuksaan), phir SPOF, phir performance, phir monitoring.

Ek issue bolne ka format

"Payment service card ka CVV save karti hai → breach hua toh lakhon cards leak, aur yeh card rules (PCI) ka seedha ulanghan hai → CVV kabhi store mat karo, payment provider ka token use karo."

Ek saans mein, ek line. Fix ek hi bolo, diagram mat banao. Agar interviewer aur detail maange tabhi explain karo.

Kya nahi karna

  • Diagram dobara banana ya "main aise design karunga" bolna.
  • Sirf fix bolna ("add more servers") bina problem aur nuksaan ke.
  • Ek issue ko do baar alag shabdon mein ginna (jaise "ek gateway" aur "no load balancer").
  • Strong-consistency data (seats, stock, balance) ke liye cache suggest karna. Isse double booking hoti hai.
  • Spec mein likhi baat assume karna. Pakka nahi ho toh interviewer se poochho.

Fix cheat sheet

Fix hamesha problem ki category se match karna chahiye. Galat category ka fix (jaise availability ke liye sharding) half credit bhi nahi deta.

Problem ki categorySahi fixGalat fix (avoid)
Availability (gira toh band)Replica, failover, 2+ instances, health checksSharding (data baant-ti hai, backup nahi deti)
Data lossBackups, retries, DLQReplication akela (delete bhi copy ho jata hai)
Scale / speed (reads)Cache, CDN, read replicaBade server akela
Scale / speed (writes, data size)Sharding, queuesCache
Correctness (double booking)DB row lock / shared lock with TTL, idempotencyCache se padhna
Security / PIIAuth, MFA, RBAC, encryption, tokenization, min data"Firewall laga do" bina detail ke
Third-party dependencyTimeout, retry with backoff, circuit breaker, fallbackAur servers add karna
VisibilityCentral logs, metrics, alerts, tracing, audit logs"Logs check kar lenge"

Q1 Postal service

Prompt: Delivery notifications wala postal system, "what issues do you see". Aapka score: 15 mein se lagbhag 3 (redesign kar diya tha).

Note: yeh diagram aapke notes se reconstruct kiya gaya hai, original se thoda alag ho sakta hai.

Issue wala component

Issues with solution (pehle khud try karo)
  1. ProblemSingle A record aur single WAF
    NuksaanEk bhi gira toh poori service band
    FixMultiple DNS records with health checks, WAF pair
  2. ProblemLB SPOF, LB2 sirf 90% uptime
    Nuksaan90% = saal mein ~36 din down
    FixReliable LB pair, active-passive, health checks
  3. ProblemFake regional resiliency: notifications sirf NY, packages sirf LA, DB ek jagah spec
    NuksaanEk region gira toh ek poora feature gayab
    FixHar region mein full stack, DB cross-region replication
  4. ProblemRound-robin bina health checks
    NuksaanMare hue server ko bhi traffic, users ko errors
    FixHealth checks, unhealthy server ko rotation se hatao
  5. ProblemWeak servers 512MB / 1GHz spec
    NuksaanLoad aate hi crash
    FixRight-size karo, autoscaling
  6. ProblemHar server par local auth list
    NuksaanRound-robin se doosre server par login fail; lists out of sync; security risk
    FixCentral auth service / identity provider
  7. ProblemS6 logging proxy single
    NuksaanProxy gira toh logs gayab ya traffic block
    FixHar server par log agent, central log store
  8. ProblemSingle MQ + single API handler, no retries / DLQ
    NuksaanNotifications chupchaap lost
    FixMQ cluster, multiple handlers, retries, dead-letter queue
  9. ProblemSMS call HTTP par, phone number URL mein, no auth, public internet, malformed URL
    NuksaanPII leak (URLs logs mein save hote hain), spoofing, SMS fail
    FixHTTPS POST, number body mein, API auth, URL validation
  10. ProblemThird-party lockers bina timeout / retry / circuit breaker
    NuksaanLocker API slow hua toh hamare servers atak jayenge
    FixTimeout, retry with backoff, circuit breaker
  11. ProblemS3 failover workaround
    NuksaanFailover par saara load S3 par, woh bhi crash
    FixProper failover capacity (N+1), LB-based failover
  12. ProblemS1 / S2 DB se connected nahi diagram vs spec
    Nuksaan"Delivered" status save nahi hota
    FixSab app servers ko DB access (ya ek data service)
  13. ProblemNo backups
    NuksaanPermanent data loss
    FixAutomated backups + restore test
  14. ProblemNo monitoring
    NuksaanOutage customer se pata chalega
    FixHealth checks, metrics, alerts

Har question ka alag "signature" issue

Postal
Fake redundancy: dikhne mein 2 regions, asal mein har feature ek hi jagah. Aur state per server (local auth).
Supermarket
Data placement: PII galat jagah copy, sensitive health data, ML request path par.
Cinema
Correctness under concurrency: double booking (memory lock, offline sales, stale cache) aur payment safety.
Agla question?
Naya domain = naya signature. Poochho: "is business mein sabse mehenga galat kya ho sakta hai?" Wahi signature issue hai.

Agar design banana ho

Review round mein aap inspector ho (dhoondho kya toota hai). Design round mein aap builder ho (khud banao). Checklist same rehti hai, bas order ulta: pehle banao, phir apne hi design par 5 sawal lagao.

Chhota version (3–4 minute)

  1. 1 line mein requirement confirm karo. "Users seats dekh ke book karenge, payment hoga, ticket email par." Ek question poochho: scale kitna? peak kab?
  2. Main flow bolo. Client → LB → stateless app servers → DB, aur side mein cache / queue / third party.
  3. Hardest part pakdo. Har domain mein ek hota hai (cinema: seat contention; supermarket: PII + stock; postal: notifications reliability). Uska solution 2 line mein.
  4. 5 sawal apne design par. Fail (redundancy), slow (cache/replica), leak (auth/encryption), galat/lost (locks, retries, backups), pata kaise chalega (monitoring).

Lamba version (30–45 minute)

StepKya bolna haiTime
RequirementsFunctional (kya karta hai) + non-functional (scale, latency, availability, consistency)5 min
EstimatesUsers, requests/sec, peak, data size3 min
API + data modelMain endpoints, main tables, kaunsa data strong consistency maangta hai5 min
High-level designBoxes + arrows, har box ka ek kaam8 min
Deep diveHardest part: locking, sharding key, queue design10 min
Review your own design5 sawal + trade-offs5 min

Example: cinema booking scratch se (4 minute answer)

"Users showtimes browse karte hain aur seats book karte hain; peak Friday 10 AM. Main flow: app → CDN → LB → stateless API servers. Catalog cache mein, kyunki woh read-heavy hai. Hardest part seat contention hai: seat select karne par DB mein ya Redis mein TTL wala lock (10 min), payment ke baad booking confirm, idempotency key ke saath. Seat DB primary + standby, reports read replica se. Payment provider ke saath timeout aur circuit breaker; card token only. Tickets queue se email, retries + DLQ, random signed QR. Friday ke liye waiting room aur load test. Monitoring aur central logs sab par."

Dekho: yeh wahi 17 issues ke fixes hain, bas ulta likha hua. Isliye review practice design bhi sikhati hai.
