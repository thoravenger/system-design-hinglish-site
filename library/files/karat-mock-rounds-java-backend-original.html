Design scenarios

For each one, spend about 7 minutes: name the problems, starting with the most serious, then give a fix and a trade-off for each.

1

Charged twice after a timeout

A payment service charges cards by calling an external card processor. If the processor hasn't answered within 3 seconds, the service treats the call as failed and retries, up to 3 times. Support keeps hearing from customers who were charged twice, mostly at busy times.

What is causing the double charges, and how would you fix the design?

Show model answerHide model answer
What's wrong
  • A timeout doesn't mean the charge failed. The processor may have charged the card and simply answered late, so each retry can create another charge.
  • Busy periods bring more slow responses, so more retries and more duplicates.
  • Nothing on our side records which attempt actually succeeded.
How to fix it
  • Send an idempotency key, created once per payment (such as the order ID), with every attempt, so the processor returns the original result instead of charging again. Store it with a unique constraint on our side too.
  • On a timeout, mark the payment as pending and ask the processor for its status (or wait for its webhook) before retrying.
  • Model payments as a state machine (created, pending, succeeded, failed) where only one move to succeeded is possible.
  • Retry with exponential backoff and jitter, and add a circuit breaker for when the processor is struggling.
  • Reconcile daily against the processor's settlement report to catch and refund anything that slips through.
Trade-off to mention

Status checks make the unhappy path slower, and customers may briefly see "payment processing". For money, correctness beats speed.

Line to end on

In payments, a timeout means unknown, not failed.

2

Stale balances and a morning spike

To reduce database load, the mobile banking app caches every customer's balance in Redis with a fixed 30-minute expiry. A job loads all balances into the cache at 6:00 every morning. Customers say their balance doesn't change after a transfer, and some repeat the transfer. Separately, database CPU jumps to 100% at about 6:30 every day.

What problems do you see, and how would you fix them?

Show model answerHide model answer
What's wrong
  • The cache isn't updated when money moves, so customers see the old balance for up to 30 minutes.
  • If transfers are checked against the cached balance, repeated transfers can overdraw the account.
  • Every key loaded at 6:00 expires at 6:30 at the same moment, so all requests hit the database together (a cache stampede).
  • Pre-loading every customer fills the cache with accounts nobody opens.
How to fix it
  • Delete or update the cached balance in the same flow that commits the transfer (after the commit), and read from the database right after a customer's own write.
  • Never make money decisions from the cache. Check the balance in the database inside the transaction; the cache is for display only.
  • Add random jitter to expiry times, refresh popular keys before they expire, and let only one request rebuild a missing key while the others wait.
  • Cache on first read (cache-aside) instead of pre-loading everything.
Trade-off to mention

A shorter expiry means fresher data but more database load. Updating the cache on every write adds a little latency to writes.

Line to end on

Use the cache for reading, and the database for deciding.

3

One slow service takes down checkout

When a customer places an order, the order service calls inventory to reserve stock, then payment to charge the card, then shipping to create a shipment. All three are synchronous HTTP calls, one after another, with no timeouts, and the customer only gets a reply when all three succeed. During a sale, shipping slows down, the whole site stops responding, and some customers are charged for orders that show as failed.

What is wrong with this design?

Show model answerHide model answer
What's wrong
  • With no timeouts, threads wait forever on the slow shipping service until the order service runs out of threads and the whole site stalls (a cascading failure).
  • A long synchronous chain adds up latency and multiplies failure: three services at 99.9% each give about 99.7% together.
  • There's no plan for partial failure, so payment can succeed while a later step fails, leaving paid-but-failed orders.
  • The customer waits for shipping, which they don't need to wait for.
How to fix it
  • Put timeouts on every call, add circuit breakers, and give each dependency its own thread pool (bulkheads).
  • Confirm the order once payment succeeds, and create the shipment asynchronously from an "order paid" event on a queue.
  • Use the saga pattern: each step has a compensating action (release the stock, refund the payment), and the order's state is stored so it can be recovered.
  • Make every step idempotent, because retries and saga recovery will call steps more than once.
Trade-off to mention

Asynchronous steps mean eventual consistency, so the customer sees "shipment pending". Sagas add complexity and need monitoring for stuck orders.

Line to end on

Keep only what the customer must wait for on the synchronous path.

4

A rate limit that isn't a limit

The public API allows each client 100 requests per minute. Each API gateway instance counts requests in its own memory. There are 5 instances behind a round-robin load balancer, and autoscaling adds up to 15 more at peak. Partners say the limit behaves inconsistently, and at peak some clients send far more than 100 requests a minute without being blocked.

Explain what's happening and how you would fix it.

Show model answerHide model answer
What's wrong
  • Each instance sees only part of a client's traffic, so the real limit is about 100 times the number of instances: roughly 500 normally and up to 2,000 at peak.
  • The limit shifts whenever autoscaling adds or removes instances, and counters reset when an instance restarts.
How to fix it
  • Keep the counters in a shared store such as Redis, with an atomic token bucket or sliding window (a Lua script, or INCR with EXPIRE), so every instance checks the same count.
  • Or route each client to the same instance with consistent hashing. It's simpler, but load gets uneven and it breaks when instances change.
  • Decide what happens when Redis is down: fail open (allow traffic, risk overload) or fail closed (block traffic, risk an outage). Public APIs often fail open with a local fallback limit.
  • Return 429 with a Retry-After header, and support different limits per partner tier.
Trade-off to mention

One extra network hop per request, and Redis becomes a critical dependency that needs replication.

Line to end on

A limit that must be global needs shared state.

5

Missing receipts, then double receipts

A notification service reads "transaction posted" events from Kafka and emails a receipt for each one. It used auto-commit, which commits offsets every 5 seconds. After crashes, some customers never got their receipt. The team changed it to commit the offset only after the email is sent. Now some customers get the same receipt twice.

Explain both problems, and how you would make the service reliable.

Show model answerHide model answer
What's wrong
  • Auto-commit can commit an offset before the email is sent. If the service crashes in between, that event is skipped for good (at-most-once delivery).
  • Committing after sending fixes that, but a crash after sending and before committing means the event is read and sent again (at-least-once delivery).
  • Exactly-once isn't possible end to end when the side effect is an external email.
How to fix it
  • Accept at-least-once delivery and make the consumer idempotent: before sending, record the transaction ID in a "sent receipts" table with a unique constraint, and skip events that are already there.
  • Use the email provider's idempotency key if it offers one, to close the gap between sending and recording.
  • Retry temporary failures with backoff, send repeatedly failing events to a dead-letter queue, and monitor consumer lag.
Trade-off to mention

One extra database write per event, and the dedupe table needs a retention period, such as 30 days.

Line to end on

Design for at-least-once delivery, and make the consumer idempotent.

6

The nightly statement job

Every night, a batch job creates monthly statements for 5 million accounts. It loads all accounts into memory, processes them one at a time on a single thread, and writes the statements to the primary database. To make it highly available, the team set up the same cron job on two servers. It now takes 7 hours, sometimes crashes near 90% with an OutOfMemoryError and starts again from the beginning, and some customers received two statements.

What are the problems, and how would you fix them?

Show model answerHide model answer
What's wrong
  • Loading every account into memory causes the out-of-memory crashes.
  • With no checkpoints, a crash means starting over from zero.
  • Both servers run the same cron job and both do the work, which causes the duplicate statements.
  • A single thread over 5 million accounts is simply slow.
How to fix it
  • Process accounts in chunks (for example 1,000 at a time) with a streaming cursor, so memory stays flat.
  • Save progress after each chunk so a rerun resumes, and make writes idempotent (an upsert keyed by account and month) so redoing a chunk is harmless.
  • Make sure only one runner starts the job, with a distributed lock or leader election such as a database lock or ShedLock in Spring. Idempotent writes are the safety net.
  • Split the work by account ranges across several workers, with a cap so the database isn't overwhelmed. Spring Batch partitioning does this.
  • Alert on run time and failures, not only on success.
Trade-off to mention

More workers finish sooner but put more load on the database. Locks need an expiry so a crashed runner can't block every future run.

Line to end on

A batch job must be restartable, idempotent, and run exactly once, by design rather than by luck.
