Foundations — 15 topics, har ek problem se solution tak

01 Synchronous REST chain vs event backbone

Problem

Booking API andar hi andar Coupon → Payment → Notification ko sync HTTP se call kar rahi hai. Sale ke din Coupon service ka p99 200ms se 4s ho gaya.

  • Booking ka latency = sabka latency ka sum. Ek slow service pura API gira deti hai.
  • Notification service down → booking bhi fail, jabki notification business‑critical hai hi nahi.
  • Client retry karta hai → retry storm → already-loaded service aur mar jaati hai.
  • Tight coupling: naya "Loyalty points" feature add karne ke liye Booking ka code chhedna padta hai.
A synchronous fan‑out makes availability multiplicative: 4 services at 99.9% each give you ~99.6%.
Solution

Booking service sirf ek event likhti hai booking.requested.v1 aur turant 202 Accepted + bookingId return karti hai. Baaki sab consumers apne pace pe kaam karte hain.

  • Temporal decoupling: Coupon service 10 min down rahe, events Kafka mein retained rahenge (default 7 din), wapas aake catch‑up kar lega.
  • Load levelling: 50k RPS spike Kafka absorb karta hai, consumer apni capacity se drain karta hai.
  • Extensibility: Loyalty service naya consumer group bana ke same topic subscribe kar leta hai — producer ko pata bhi nahi chalta.
  • User ko final status SSE/WebSocket/polling se milta hai (aakhri section mein animation isi ka hai).
Trade‑off to state aloud: you trade strong consistency for eventual consistency, and you now owe the user a status channel.

02 Topic aur partition design

Problem

Team ne ek hi topic events bana diya jisme coupon, booking, payment sab ja raha hai. Partitions = 1 (default).

  • Coupon consumer ko payment events bhi deserialize karke discard karne padte hain — CPU waste.
  • 1 partition = maximum 1 consumer thread → horizontal scaling possible hi nahi.
  • Retention policy sab events ke liye same — audit events 90 din chahiye, temp events 1 din.
  • ACL alag nahi kar sakte: analytics team ko payment data dikh jaata hai.
Solution

Ek topic = ek event type (ya ek closely-related family). Naming convention fix karo: <domain>.<entity>.<event>.v<n>.

  • coupon.redemption.requested.v1, booking.confirmed.v1, order.payment.captured.v1.
  • Partition count = peak throughput ÷ per‑consumer throughput, phir 2–3× headroom. Example: 30k msg/s ÷ 2k msg/s per consumer = 15 → 32 partitions le lo.
  • Partitions sirf badha sakte ho, ghata nahi — aur badhane par key→partition mapping toot jaati hai. Isliye pehle din sahi socho.
  • Per‑topic retention/ACL/compaction alag set kar sakte ho.
Rule of thumb: partitions are the unit of parallelism and the unit of ordering. You cannot have more consumers in one group than partitions.

03 Partition key selection aur hot partition

Problem

Coupon events ka key couponCode rakha. Sale mein BIGBILLION50 par 90% traffic aa gaya.

  • Ek partition 90% load le rahi hai, baaki 31 partitions khaali — classic hot partition.
  • Us partition ka lag lakhon mein, dusri sab 0. Consumer add karne se kuch nahi hota.
  • Ulta case: key null kar do to round‑robin hoga, par ordering guarantee khatam — APPLIED aur REVERSED ulte order mein process ho sakte hain.
Solution

Key wahi entity hai jiski serial ordering chahiye. Hot key ho to composite key se sub‑shard karo aur shared counter ko DB/Redis atomic operation se guard karo.

  • Per‑user ordering chahiye → key = userId. Per‑booking → bookingId. Per‑order → orderId.
  • Hot coupon ke liye: key = couponCode + "#" + (userId.hashCode() & 7) — 8 sub‑shards, load spread ho gaya.
  • Global budget ab partition‑ordering se protect nahi hai, isliye budget decrement conditional UPDATE se karo: UPDATE coupon SET used = used + 1 WHERE code = ? AND used < max_limit — rows‑affected 0 matlab exhausted.
Ordering is per‑partition, never global. Pick the smallest entity that still gives you the ordering the business needs.

04 Producer reliability — acks, retries, idempotence

Problem

Producer ne coupon.redeemed bheja, network timeout hua, ack nahi mila. Producer ne retry kiya.

  • Pehla message actually pahunch chuka tha → broker mein duplicate ban gaya → user ko double cashback.
  • acks=1 par leader crash hua replication se pehle → message silently lost.
  • max.in.flight=5 + retries bina idempotence → messages reorder ho sakte hain.
  • send() async hai; koi callback nahi laga to failure chupchaap nigal jaata hai.
Solution

Idempotent producer on karo aur full ISR ack maango. Broker producer ko sequence number deta hai aur duplicate/reorder khud reject karta hai.

  • enable.idempotence=true (Kafka 3.x default), jo automatically acks=all, retries=MAX, max.in.flight≤5 set karta hai.
  • Broker side: replication.factor=3 + min.insync.replicas=2. Warna acks=all ka matlab hi nahi.
  • delivery.timeout.ms (default 120s) — iske andar retries hote hain, uske baad hard fail.
  • Har send() par callback/CompletableFuture handle karo — failure par outbox row ko FAILED mark karo, silently ignore mat karo.
Idempotent producer removes duplicates caused by producer retries only — it does not protect you from application‑level double sends.

05 Consumer group aur rebalance

Problem

6 partitions, par deployment mein 10 pods chala diye. Rolling deploy ke waqt lag graph spike kar jaata hai.

  • 4 consumers hamesha idle — paisa waste, throughput same.
  • Har pod restart par stop‑the‑world rebalance: sab consumers apni partitions chhod dete hain, 20–40s processing rukti hai.
  • Processing 6 min leti hai par max.poll.interval.ms=300000 (5 min) → broker consumer ko dead maan leta hai → infinite rebalance loop.
Solution

Consumers ≤ partitions rakho, cooperative rebalancing on karo, aur poll interval ko worst‑case processing time se bada rakho.

  • partition.assignment.strategy=CooperativeStickyAssignor — sirf affected partitions move hoti hain, baaki chalti rehti hain.
  • group.instance.id (static membership) + session.timeout.ms=45000 — rolling restart par rebalance hi trigger nahi hota.
  • max.poll.records ghata do (500 → 50) taaki ek poll batch time budget mein khatam ho.
  • Long DB/HTTP work ho to record ko internal queue mein daal ke poll loop free rakho, phir manual ack.

06 Offset commit strategy

Problem

enable.auto.commit=true chal raha tha. Consumer ne 500 records poll kiye, offset auto‑commit ho gaya, phir 200th record par pod OOM‑kill ho gaya.

  • Baaki 300 coupon redemptions hamesha ke liye gayab — at‑most‑once behaviour.
  • Koi alert nahi bajta, kyunki technically koi exception hi nahi hua.
  • Reconciliation job ne 3 din baad mismatch pakda.
Solution

Auto‑commit off. Business work successful hone ke baad hi manually ack karo — at‑least‑once.

  • enable-auto-commit: false + ack-mode: MANUAL_IMMEDIATE.
  • Listener signature mein Acknowledgment ack lo, aur DB commit ke baad ack.acknowledge() call karo.
  • At‑least‑once ka matlab duplicates aayenge → isliye topic 08 (idempotent consumer) mandatory hai.
Delivery semantics are a chain: producer idempotence + manual commit + consumer‑side dedupe = effectively‑once for the business.

07 Ordering guarantee

Problem

User ne coupon apply kiya phir 2 second mein remove kar diya. COUPON_APPLIED aur COUPON_REVERSED alag partitions mein chale gaye.

  • REVERSED pehle process ho gaya, APPLIED baad mein → DB mein coupon applied hi reh gaya.
  • User ne bina eligible hue discount le liya — direct revenue loss.
  • Consumer concurrency badhane par same partition ke andar bhi order tootne laga (multi‑threaded processing).
Solution

Same key → same partition → guaranteed order. Uske upar payload mein version rakho taaki late/stale event drop ho sake.

  • Dono events ka key bookingId — ek hi partition, ek hi consumer thread, natural order.
  • Payload mein version ya occurredAt: consumer if (event.version ≤ row.version) return; — idempotent + out‑of‑order safe.
  • Spring mein concurrency badhao to bhi ek partition ek hi thread ko milti hai — ordering safe rehti hai, bas apne aap threads mat spawn karo.

08 Duplicate events aur idempotent consumer

Problem

Rebalance ke baad consumer ne last committed offset se dobara start kiya. Wahi coupon.redeemed event 2 baar process ho gaya.

  • Ledger mein do entries → user ko ₹200 ki jagah ₹400 cashback.
  • Notification 2 baar gaya — user ko lagta hai bug hai.
  • Duplicate 100% avoid karna Kafka‑only setup mein possible nahi, kyunki external DB involved hai.
Solution

Consumer ko idempotent banao. Har event ka unique eventId ho aur ek processed_event table par unique constraint ho.

  • Ek hi DB transaction mein: (a) INSERT INTO processed_event(consumer_group, event_id), (b) business update. Duplicate par unique‑violation aayega → safely skip.
  • Business‑level natural key bhi kaam karta hai: UNIQUE(coupon_code, user_id, booking_id) on redemption table.
  • High‑volume ke liye Redis SETNX eventId with TTL, but source of truth DB hi rakho.
Say this in interviews: "Kafka gives at‑least‑once across an external DB; exactly‑once is achieved in the consumer, not the broker."

09 Retry, backoff aur DLQ

Problem

Payment gateway 30 second ke liye down. Consumer exception throw karta hai, Kafka wahi record dobara deta hai, infinite loop.

  • Head‑of‑line blocking: ek stuck record ke peeche us partition ke sab records ruk gaye.
  • Ek permanently invalid message (coupon code hi galat) infinite retry karta rehta hai — CPU 100%, logs bhar gaye.
  • Retryable (gateway timeout) aur non‑retryable (validation fail) errors mein farq hi nahi kiya gaya.
Solution

Exceptions ko classify karo, non‑blocking retry topics banao, aur haar ke DLT (dead letter topic) mein daalo.

  • Spring: DefaultErrorHandler + ExponentialBackOff + DeadLetterPublishingRecoverer.
  • addNotRetryableExceptions(CouponInvalidException.class) — ye seedha DLT jaate hain, retry hi nahi.
  • Non‑blocking retry: @RetryableTopic → ...-retry-0, -retry-1, -dlt. Main partition free rehti hai.
  • DLT ke liye alert + replay endpoint banao. DLT jo kabhi dekha na jaaye woh silent data loss hai.

10 Dual‑write problem aur transactional outbox

Problem

Service DB mein booking CONFIRMED save karti hai, phir Kafka par event bhejti hai. Do alag systems, ek hi logical operation.

  • DB commit ho gaya, Kafka publish fail → downstream ko kabhi pata nahi chala. Booking confirmed but no ticket email.
  • Kafka publish ho gaya, DB rollback → phantom event, downstream ne kaam kar diya jo hua hi nahi.
  • @Transactional DB aur Kafka dono ko cover nahi karta — 2PC production mein practical nahi.
Solution

Event ko usi DB transaction mein outbox table mein likho. Alag relay use karke usse Kafka par bhejo.

  • Atomicity DB level par mil gayi — ya dono likhe jaayenge ya koi nahi.
  • Relay options: (a) Debezium CDC binlog se, (b) polling publisher SELECT ... FOR UPDATE SKIP LOCKED.
  • Relay at‑least‑once hai → consumer idempotent hona chahiye (topic 08). Ye combo hi standard answer hai.
Outbox turns an unsolvable distributed‑transaction problem into a boring single‑database transaction plus a retryable pump.

11 Exactly‑once semantics (EOS) — kab kaam aata hai

Problem

Consume → transform → produce pipeline hai: order.placed padho, discount calculate karo, order.priced likho. Crash ke baad dobara process hua to output topic mein duplicate.

  • Downstream aggregation service ne revenue double count kar liya.
  • Manual dedupe har downstream consumer mein likhna padega — duplicated effort.
Solution

Kafka transactions: output produce aur input offset commit dono ek atomic transaction mein.

  • Producer par transactional.id set karo, Spring mein KafkaTemplate.executeInTransaction(...).
  • Consumer par isolation.level=read_committed — warna aborted transactions ke messages bhi dikh jaayenge.
  • Limitation zaroor batao: EOS sirf Kafka→Kafka ke liye hai. Beech mein external DB write ya HTTP call aaya to idempotency wapas aapki zimmedari.
  • Cost: throughput ~10–20% kam, latency thodi zyada. Har pipeline par EOS mat lagao.

12 Schema evolution aur poison pill

Problem

Producer team ne discountAmount ko String se BigDecimal kar diya bina batayen. Consumer ka deserializer blow up ho gaya.

  • Deserialization exception listener ke andar nahi, uske pehle aata hai — error handler ko record milta hi nahi.
  • Offset aage nahi badh sakta → poison pill → pura consumer group ruk gaya.
  • Manual fix: offset seek karke skip karna, production incident.
Solution

Schema Registry + backward compatibility + defensive deserializer.

  • Avro/Protobuf + Schema Registry, compatibility mode BACKWARD. Registry incompatible schema ko publish hone hi nahi dega.
  • Safe changes: naya optional field with default add karna. Unsafe: required field remove/rename ya type change.
  • Breaking change zaroori ho to naya versioned topic: coupon.redeemed.v2, dono ko parallel chalao, phir cutover.
  • ErrorHandlingDeserializer wrap karo — bad record null payload ban ke error handler tak pahunchta hai aur DLT chala jaata hai.

13 Consumer lag aur scaling

Problem

Sale ke 20 minute mein lag 2 million messages. Users ko coupon confirmation 40 minute baad mil raha hai.

  • Consumer har record par ek sync HTTP call kar raha hai (80ms) → max ~12 msg/s per thread.
  • Consumers badha diye par partitions 8 hi hain → koi fayda nahi.
  • Per‑record INSERT DB par 1 row/txn — DB IOPS choke.
Solution

Lag ko diagnose karo pehle: producer rate zyada hai, ya consumer slow hai, ya partitions kam hain.

  • Metrics: records-lag-max, fetch-latency-avg, commit-latency-avg + kafka‑lag‑exporter/Burrow.
  • Partitions badhao (32) + consumers = partitions. Ye pehla lever hai.
  • Batch listener (batch-listener: true) + bulk INSERT — 500 rows ek transaction mein, 10–50× jump.
  • Sync HTTP hot path se hatao; enrichment ko alag topic par push karo.
  • KEDA/HPA ko lag metric par autoscale karao, CPU par nahi.

14 Retention, compaction aur replay

Problem

Naya Analytics service bana, purane 30 din ke coupon events replay karne the — par retention 3 din tha.

  • Historical data gaya. Backfill ke liye DB dump se ETL likhna pada.
  • Coupon ka current state kahin ek jagah nahi tha — state reconstruct karne ke liye pura event log chahiye tha.
  • Bug fix ke baad "sirf pichle 2 ghante replay karo" ka koi safe tarika nahi tha.
Solution

Do tarah ke topics rakho: event topics (delete policy) aur state topics (compacted).

  • Event topic: cleanup.policy=delete, retention.ms=7d (audit ke liye 30–90d).
  • State topic: cleanup.policy=compact, key = couponCode. Kafka har key ka latest value hamesha rakhta hai — ek tarah ka distributed key‑value snapshot.
  • Delete karne ke liye tombstone bhejo: same key, null value.
  • Replay: naya group.id + auto-offset-reset: earliest, ya kafka-consumer-groups --reset-offsets --to-datetime.

15 Observability — kya hua kaise pata chale

Problem

User bolta hai "booking confirm nahi hui". 6 services, 9 topics — kaun sa step atka, koi nahi bata paata.

  • Har service apna correlation id banati hai, chain toot jaati hai.
  • DLT mein 4000 messages pade hain, kisi ko pata hi nahi.
  • Alerting CPU par hai, lag par nahi — system "healthy" dikhta hai jabki 40 min peeche chal raha hai.
Solution

Har event mein standard headers, aur teen alerts jo actually matter karte hain.

  • Headers: traceId, eventId, eventType, schemaVersion, producedAt, sourceService. Consumer inhe MDC mein daal ke aage propagate kare.
  • Alerts: (1) consumer lag > threshold for 5 min, (2) DLT message count > 0, (3) producer error rate.
  • Business SLI track karo: "booking.requested se booking.confirmed tak p99 latency".
  • Micrometer + Grafana; Spring Boot Kafka metrics already expose hote hain.

Code 1 — request producer

Producer ka kaam sirf teen cheez hai: sahi partition key banao, tracing headers lagao, aur send ka result kabhi ignore mat karo. Code ki kisi bhi line par tap karo — neeche uska explanation highlight ho jaayega, aur ulta bhi chalta hai.

CouponRedemptionRequestProducer.javaproducer
@Component
@Slf4j
@RequiredArgsConstructor
public class CouponRedemptionRequestProducer {

    private static final String TOPIC = "coupon.redemption.requested.v1";
    private static final int SUB_SHARD_COUNT = 8;

    private final KafkaTemplate<String, CouponRedemptionRequested> kafkaTemplate;
    private final OutboxRepository outboxRepository;

    public void publishRedemptionRequested(CouponRedemptionRequested event) {
        String partitionKey = buildPartitionKey(event.couponCode(), event.userId());

        ProducerRecord<String, CouponRedemptionRequested> record =
                new ProducerRecord<>(TOPIC, partitionKey, event);

        record.headers().add("eventId", event.eventId().getBytes(UTF_8));
        record.headers().add("eventType", "COUPON_REDEMPTION_REQUESTED".getBytes(UTF_8));
        record.headers().add("traceId", MDC.get("traceId").getBytes(UTF_8));

        kafkaTemplate.send(record).whenComplete((sendResult, failure) -> {
            if (failure != null) {
                log.error("kafka publish failed eventId={}", event.eventId(), failure);
                outboxRepository.markPublishFailed(event.eventId());
                return;
            }
            RecordMetadata metadata = sendResult.getRecordMetadata();
            outboxRepository.markPublished(event.eventId());
            log.info("published eventId={} partition={} offset={}",
                     event.eventId(), metadata.partition(), metadata.offset());
        });
    }

    private String buildPartitionKey(String couponCode, String userId) {
        int subShard = Math.floorMod(userId.hashCode(), SUB_SHARD_COUNT);
        return couponCode + "#" + subShard;
    }
}
  1. L6–L7Topic name aur shard count constants mein. Kabhi bhi topic name inline string mat likho — version bump (v2) ke time ek hi jagah change ho.Constants also make the topic greppable across the repo.
  2. L9–L10Typed KafkaTemplate — key String, value ek immutable record. Outbox repo isliye taaki publish failure DB mein dikhe.
  3. L12–L13Method ka naam event ke naam se match karta hai: publishRedemptionRequested. Naming rule — producer methods publishXxx, listeners onXxx, guards tryXxx.
  4. L15–L16ProducerRecord isliye use kiya (na ki simple send(topic, key, value)) kyunki humein headers chahiye aur key par poora control chahiye.
  5. L18–L20eventId header consumer ki idempotency ke liye, traceId end‑to‑end debugging ke liye. Headers payload se alag rehte hain, isliye schema change kiye bina metadata add kar sakte ho.
  6. L22send() async hai aur CompletableFuture deta hai. whenComplete lagana mandatory hai — bina iske publish failure chupchaap gayab ho jaata hai.Fire‑and‑forget is the single most common Kafka bug in Spring codebases.
  7. L23–L27Failure branch: outbox row FAILED mark hoti hai, relay job baad mein retry karega. Yahan exception throw karne ka koi fayda nahi — ye callback alag thread par chal raha hai.
  8. L28–L32Success par partition aur offset log karo. Production incident mein "kaunsi partition par gaya" pehla sawaal hota hai.
  9. L35–L38Hot partition ka ilaaj. BIGBILLION50 ab 8 keys mein toot gaya: BIGBILLION50#0 … #7. Load 8 partitions par phail gaya, aur budget safety DB constraint se aa rahi hai, partition ordering se nahi.Use floorMod, not %, because hashCode() can be negative.

Code 2 — listener with manual ack

Yeh method interview ka centerpiece hai. Isme teen guarantees ek saath dikh rahi hain: dedupe, atomic budget, aur commit‑after‑work.

CouponRedemptionListener.javaconsumer
@Component
@Slf4j
@RequiredArgsConstructor
public class CouponRedemptionListener {

    private static final String GROUP = "coupon-redemption-worker";

    private final EventDeduplicationService deduplicationService;
    private final CouponBudgetGuard couponBudgetGuard;
    private final CouponRedemptionResultPublisher resultPublisher;

    @KafkaListener(
            topics = "coupon.redemption.requested.v1",
            groupId = GROUP,
            concurrency = "8",
            containerFactory = "manualAckListenerContainerFactory")
    @Transactional
    public void onRedemptionRequested(ConsumerRecord<String, CouponRedemptionRequested> record,
                                      Acknowledgment acknowledgment) {

        CouponRedemptionRequested event = record.value();
        MDC.put("traceId", readHeader(record, "traceId"));

        if (!deduplicationService.markProcessedIfFirstTime(GROUP, event.eventId())) {
            log.info("duplicate ignored eventId={} partition={}", event.eventId(), record.partition());
            acknowledgment.acknowledge();
            return;
        }

        BudgetReservation reservation = couponBudgetGuard.tryReserveCouponBudget(
                event.couponCode(), event.userId(), event.bookingId());

        if (reservation.isRejected()) {
            resultPublisher.publishRedemptionRejected(event, reservation.rejectionReason());
        } else {
            resultPublisher.publishCouponRedeemed(event, reservation.discountAmount());
        }

        acknowledgment.acknowledge();
    }
}
  1. L12–L16Topic, group aur container factory. concurrency = "8" ka matlab 8 threads, har thread ko alag partitions milti hain — ek partition kabhi do threads mein nahi jaati, isliye ordering safe hai.
  2. L17@Transactional dedupe insert aur budget update dono ko ek DB transaction mein bandh deta hai. Yahi "effectively once" ka asli mechanism hai.
  3. L18–L19Sirf payload lene ke bajaye poora ConsumerRecord liya — headers, partition, offset sab chahiye. Acknowledgment manual commit ke liye inject hota hai.
  4. L21–L22Trace id ko MDC mein daal diya, ab is request ke saare logs ek hi trace se filter ho jaayenge, chahe wo 4 services aage ho.
  5. L24–L28Idempotency gate. Agar event pehle process ho chuka hai to sirf ack karke return. Ack zaroori hai — warna wahi duplicate baar‑baar aata rahega.
  6. L30–L31Saara business decision ek hi call mein, jo atomic DB operations par tikka hai. Listener khud koi business rule nahi jaanta — testable rehta hai.
  7. L33–L37Rejection bhi ek first‑class event hai. "Kuch nahi hua" wala silent path mat rakho — user ko reason chahiye aur analytics ko funnel drop chahiye.
  8. L39Ack sabse aakhir mein. Agar upar kahin exception aayi, ack nahi hoga, error handler retry karega, aur DB transaction rollback ho chuka hoga — state consistent.
Interview follow-up: "@Transactional ke andar ack karna theek hai?" — Strictly, acknowledge() DB commit se pehle chalta hai. Zyada tar setups mein ye acceptable hai kyunki duplicate handle ho raha hai. Fully strict chahiye to ack ko TransactionSynchronizationManager.registerSynchronization(...afterCommit...) mein daalo, ya listener ko non‑transactional rakho aur transaction service layer par shift karo.

Code 3 — budget guard (over‑redemption ka ilaaj)

CouponBudgetGuard.java + CouponRepository.javadomain
@Service
@RequiredArgsConstructor
public class CouponBudgetGuard {

    private final CouponRepository couponRepository;
    private final CouponRedemptionRepository redemptionRepository;

    @Transactional(propagation = Propagation.MANDATORY)
    public BudgetReservation tryReserveCouponBudget(String couponCode, String userId, String bookingId) {

        int claimInserted = redemptionRepository.insertClaimIfAbsent(couponCode, userId, bookingId);
        if (claimInserted == 0) {
            return BudgetReservation.rejected(RejectionReason.ALREADY_REDEEMED_BY_USER);
        }

        int budgetTaken = couponRepository.reserveOneRedemption(couponCode, Instant.now());
        if (budgetTaken == 0) {
            redemptionRepository.markClaimRejected(couponCode, userId, RejectionReason.BUDGET_EXHAUSTED);
            return BudgetReservation.rejected(RejectionReason.BUDGET_EXHAUSTED);
        }

        Coupon coupon = couponRepository.findByCode(couponCode).orElseThrow();
        return BudgetReservation.reserved(coupon.calculateDiscountFor(bookingId));
    }
}

Choreography ka dard

Har service dusre ka event sunti hai, koi central brain nahi. 3 steps tak theek lagta hai.

    private final BookingSagaStateRepository sagaStateRepository;
    private final EventDeduplicationService deduplicationService;
    private final SagaCommandPublisher commandPublisher;

    @KafkaListener(topics = "booking.inventory.held.v1", groupId = GROUP,
                   containerFactory = "manualAckListenerContainerFactory")
    @Transactional
    public void onInventoryHeld(InventoryHeld event, Acknowledgment acknowledgment) {
        BookingSagaState saga = loadSagaForUpdate(event.bookingId(), event.eventId());
        if (saga == null) { acknowledgment.acknowledge(); return; }

        saga.moveTo(SagaStep.INVENTORY_HELD);
        commandPublisher.publishApplyCouponCommand(saga.bookingId(), saga.couponCode(), saga.userId());
        acknowledgment.acknowledge();
    }

    @KafkaListener(topics = "coupon.redeemed.v1", groupId = GROUP,
                   containerFactory = "manualAckListenerContainerFactory")
    @Transactional
    public void onCouponRedeemed(CouponRedeemed event, Acknowledgment acknowledgment) {
        BookingSagaState saga = loadSagaForUpdate(event.bookingId(), event.eventId());
        if (saga == null) { acknowledgment.acknowledge(); return; }

        saga.applyDiscount(event.discountAmount());
        saga.moveTo(SagaStep.COUPON_APPLIED);
        commandPublisher.publishCapturePaymentCommand(saga.bookingId(), saga.payableAmount());
        responseEmitter.pushStatus(saga.bookingId(), "COUPON_APPLIED", saga.payableAmount());
        acknowledgment.acknowledge();
    }

    @KafkaListener(topics = "booking.payment.failed.v1", groupId = GROUP,
                   containerFactory = "manualAckListenerContainerFactory")
    @Transactional
    public void onPaymentFailed(PaymentFailed event, Acknowledgment acknowledgment) {
        BookingSagaState saga = loadSagaForUpdate(event.bookingId(), event.eventId());
        if (saga == null) { acknowledgment.acknowledge(); return; }

        saga.moveTo(SagaStep.COMPENSATING);
        commandPublisher.publishReverseCouponCommand(saga.bookingId(), saga.couponCode(), saga.userId());
        commandPublisher.publishReleaseInventoryCommand(saga.bookingId(), saga.seatIds());
        saga.moveTo(SagaStep.CANCELLED);
        responseEmitter.pushFailure(saga.bookingId(), event.failureReason());
        acknowledgment.acknowledge();
    }

    private BookingSagaState loadSagaForUpdate(String bookingId, String eventId) {
        if (!deduplicationService.markProcessedIfFirstTime(GROUP, eventId)) {
            return null;
        }
        return sagaStateRepository.findByBookingIdForUpdate(bookingId).orElseThrow();
    }
}

    public SseEmitter registerBookingStream(String bookingId) {
        SseEmitter emitter = new SseEmitter(Duration.ofMinutes(2).toMillis());

        emitter.onTimeout(() -> activeStreams.remove(bookingId));
        activeStreams.put(bookingId, emitter);
        return emitter;
    }

    public void pushStatus(String bookingId, String step, BigDecimal payableAmount) {
        sendSafely(bookingId, BookingStatusUpdate.inProgress(step, payableAmount));
    }

    public void pushConfirmation(String bookingId, BookingConfirmation confirmation) {
        sendSafely(bookingId, BookingStatusUpdate.confirmed(confirmation));
        closeStream(bookingId);
    }

    public void pushFailure(String bookingId, String failureReason) {
        sendSafely(bookingId, BookingStatusUpdate.failed(failureReason));
        closeStream(bookingId);
    }

    private void sendSafely(String bookingId, BookingStatusUpdate update) {
        SseEmitter emitter = activeStreams.get(bookingId);
        if (emitter == null) {
            log.debug("no live stream for {} — client will fall back to polling", bookingId);
            return;
        }
        try {
            emitter.send(SseEmitter.event().name("booking-status").data(update));
        } catch (IOException clientDisconnected) {
            activeStreams.remove(bookingId);
        }
    }

    private void closeStream(String bookingId) {
        SseEmitter emitter = activeStreams.remove(bookingId);
        if (emitter != null) {
            emitter.complete();
        }
    }

@Component
@Slf4j
@RequiredArgsConstructor
public class OrderOutboxRelay {

    private static final int BATCH_SIZE = 200;

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void publishPendingOutboxEvents() {
        List<OutboxEvent> pendingEvents = outboxRepository.lockNextPendingBatch(BATCH_SIZE);
        if (pendingEvents.isEmpty()) {
            return;
        }

        for (OutboxEvent outboxEvent : pendingEvents) {
            ProducerRecord<String, String> record = new ProducerRecord<>(
                    outboxEvent.getTopic(), outboxEvent.getAggregateId(), outboxEvent.getPayload());
            record.headers().add("eventId", outboxEvent.getEventId().getBytes(UTF_8));

            try {
                kafkaTemplate.send(record).get(5, TimeUnit.SECONDS);
                outboxEvent.markPublished();
            } catch (Exception publishFailure) {
                outboxEvent.markRetryWithBackoff(publishFailure.getMessage());
                log.warn("outbox publish failed eventId={} attempt={}",
                         outboxEvent.getEventId(), outboxEvent.getAttempts(), publishFailure);
            }
        }
        outboxRepository.saveAll(pendingEvents);
    }
}

Q1Kafka ek message queue hai ya kuch aur? RabbitMQ se farq batao.+

Kafka ek distributed append‑only commit log hai, traditional queue nahi. Queue mein message consume hone ke baad delete ho jaata hai; Kafka mein message retention tak padha rehta hai aur har consumer group apna offset independently aage badhata hai.

Isi wajah se ek hi coupon.redeemed.v1 ko ledger, notification aur analytics teeno alag‑alag padh sakte hain, aur naya consumer kal aake purana data replay bhi kar sakta hai. RabbitMQ mein per‑message ack aur complex routing behtar hai; Kafka mein high throughput, replay aur ordered partitions behtar hain.

One line answer: RabbitMQ is a smart broker with dumb consumers; Kafka is a dumb broker with smart consumers.

Q2Ordering guarantee exactly kahan tak hai?+

Ordering sirf ek partition ke andar guaranteed hai, topic level par nahi. Same key wale messages same partition mein jaate hain (hash(key) % partitions), isliye per‑key ordering milti hai.

Practical example: COUPON_APPLIED aur COUPON_REVERSED dono ka key bookingId rakho — ek hi partition, ek hi consumer thread, order safe. Key null ho to round‑robin/sticky partitioning hoti hai aur ordering chali jaati hai.

Do gotchas: (1) partition count badhane par purani keys ka mapping badal jaata hai, (2) consumer ke andar khud thread pool bana ke process karoge to partition ordering hone ke bawajood processing order toot jaayega.

Q3Ek partition ek consumer group ke do consumers ko mil sakti hai?+

Nahi. Ek consumer group ke andar ek partition sirf ek consumer ko assign hoti hai — yehi ordering aur offset management ka base hai. Isliye consumers > partitions karne ka koi fayda nahi, extra consumers idle baithe rahenge.

Lekin alag‑alag consumer groups same partition ko parallel padh sakte hain. Ledger group aur analytics group dono ko har message milega, aur dono ke offsets independent honge.

Q4Offsets kahan store hote hain?+

Kafka ke internal compacted topic __consumer_offsets mein, key = (group, topic, partition). Purane Kafka mein ye Zookeeper mein tha.

Consumer restart hone par wahi se resume karta hai. Isliye offset commit ka timing hi decide karta hai ki aap at‑most‑once mein ho ya at‑least‑once mein. Manual commit + business work pehle = at‑least‑once.

Reset karna ho to kafka-consumer-groups --reset-offsets --to-datetime 2026-09-01T00:00:00.000 — group ko pehle band karna padta hai.

Q5ISR kya hai aur min.insync.replicas ka role?+

ISR = In‑Sync Replicas, wo followers jo leader ke saath sync mein hain. acks=all ka matlab hai "sabhi ISR members ne likh liya", na ki "saare replicas ne".

Agar RF=3 par 2 replicas peeche chale gaye aur ISR sirf 1 (leader) bacha, to acks=all bhi sirf leader se ack le lega — durability chali gayi. min.insync.replicas=2 is case mein producer ko NotEnoughReplicasException deta hai. Better fail fast than silent data loss.

Standard production combo: RF=3, min.insync.replicas=2, acks=all — ek broker down hone par bhi likhte raho.

Q6unclean.leader.election.enable kya karta hai?+

true hone par out‑of‑sync replica bhi leader ban sakta hai — availability milti hai par data loss hota hai, kyunki us replica ke paas latest messages hain hi nahi.

Payment aur coupon jaise topics par hamesha false. Metrics ya clickstream jaise topics par jahan thoda data loss chalega, true justify kar sakte ho. Ye classic CAP trade‑off ka concrete example hai — interview mein isi tarah frame karo.

Q7Log compaction aur retention mein kya farq hai?+

cleanup.policy=delete: time ya size ke hisaab se purane segments delete hote hain. Event streams ke liye.

cleanup.policy=compact: Kafka har key ka latest value hamesha rakhta hai, purane versions hata deta hai. Topic ek distributed key‑value snapshot ban jaata hai.

Humare design mein coupon.definition.v1 compacted hai — koi bhi naya service topic ko shuru se padh ke saare active coupons ka current state bana sakta hai. Delete karne ke liye tombstone bhejo: same key, null value.

Q8KRaft ne Zookeeper ko kyun replace kiya?+

Zookeeper alag cluster tha — alag ops, alag failure mode, aur metadata ka bottleneck. KRaft mein Kafka apna metadata khud Raft se manage karta hai.

Fayde: ek hi system chalana hai, controller failover seconds mein, aur partition count ki limit kaafi upar chali gayi (lakhon partitions). Kafka 3.x se KRaft production‑ready hai, Kafka 4.x mein Zookeeper hata diya gaya.

Q9acks=0, 1, all — kab kya use karoge?+
  • acks=0: fire and forget, sabse fast, data loss guaranteed hai agar broker down ho. Sirf metrics/logs ke liye.
  • acks=1: leader ne likh liya, replication se pehle leader crash = message gaya. Default lagta hai safe, hai nahi.
  • acks=all: saare ISR ne likh liya. Coupon, booking, payment — sab yahin.

Latency ka farq usually 2–5ms ka hota hai. Paise wale flow mein ye trade karna galti hai.

Q10Idempotent producer internally kaam kaise karta hai?+

Producer ko broker ek producerId (PID) deta hai. Har (PID, partition) ke liye producer ek monotonically increasing sequence number bhejta hai.

Broker last accepted sequence yaad rakhta hai. Wahi sequence dobara aaya (retry ki wajah se) to broker use silently drop kar deta hai; sequence mein gap aaya to OutOfOrderSequenceException deta hai.

Iska scope: ek producer session, ek partition. Application ne khud do baar send() kar diya alag payload ke saath, to wo duplicate idempotent producer nahi rok payega — uske liye consumer‑side dedupe chahiye.

Q11linger.ms aur batch.size ko kaise tune karoge?+

Producer messages ko per‑partition batch mein jama karta hai. Batch tab jaata hai jab batch.size bhar jaaye ya linger.ms khatam ho jaaye.

linger.ms=0 (default) matlab har message alag request — low latency, bahut kam throughput. linger.ms=20 + batch.size=64KB par high‑volume topics par 5–10× throughput milta hai, 20ms latency dekar.

Saath mein compression.type=lz4 lagao — compression batch level par hota hai, isliye bada batch = better compression ratio.

Q12Key null bhejo to Kafka partition kaise chunta hai?+

Modern Kafka mein sticky partitioner: producer ek partition chun ke usme batch bharta hai, batch bhejne ke baad doosri partition par switch karta hai. Purana behaviour pure round‑robin tha (chhote batches, zyada requests).

Trade‑off saaf hai — load perfectly even, par ordering ki koi guarantee nahi. Isliye null key sirf tab jab har event independent ho, jaise page‑view analytics.

Q13At‑most‑once, at‑least‑once, exactly‑once — code mein farq kya hai?+
  • At‑most‑once: pehle offset commit, phir process. Crash = message gaya. enable.auto.commit=true ka default risk yehi hai.
  • At‑least‑once: pehle process, phir commit. Crash = duplicate. Ye 95% systems ka sahi default hai.
  • Exactly‑once: Kafka→Kafka ke liye transactions se; external DB ke saath sirf idempotent consumer se "effectively once".

Interview line: "Kafka gives at‑least‑once delivery; exactly‑once is a property of my processing, not of the broker."

Q14Rebalance kab trigger hota hai aur usse kaise kam karein?+

Trigger: consumer join/leave, pod restart, session.timeout.ms tak heartbeat na aana, max.poll.interval.ms cross hona, ya partition count badalna.

Kam karne ke tareeke: CooperativeStickyAssignor (sirf affected partitions move), group.instance.id static membership (rolling restart par rebalance hi nahi), session.timeout.ms=45000, aur processing time ko poll interval ke andar rakhna.

Q15max.poll.interval.ms aur session.timeout.ms mein kya farq hai?+

session.timeout.ms — heartbeat thread ka timeout. Process zinda hai ya nahi, ye batata hai. Alag thread par chalta hai.

max.poll.interval.ms — do poll() calls ke beech max gap. Process zinda ho par processing mein atka ho (slow DB), tab bhi ye breach hoga aur consumer group se nikal diya jaayega.

Classic bug: har record par 3 second ka external call, max.poll.records=500 → 1500 second lagenge, interval 300s hai → infinite rebalance loop. Fix: records ghatao ya interval badhao.

Q16Consumer lag 2 million hai. Aap kya karoge?+

Pehle diagnose, phir scale. Teen sawaal: producer rate badha hai? consumer per‑record time badha hai? ya partitions hi kam hain?

  1. Metrics dekho: records-lag-max per partition — sab partitions ka lag high hai ya sirf ek (hot key)?
  2. Ek hi partition hot hai → partition key badlo / sub‑shard karo.
  3. Sab high hain → partitions badhao aur consumers ko partitions ke barabar le jao.
  4. Per‑record processing slow hai → batch listener + bulk insert, sync HTTP hot path se hatao.
  5. Turant relief chahiye → temporary non‑critical consumer band karo, autoscaling ko lag metric par set karo (CPU par nahi).
Q17Poison pill kya hai aur kaise handle karoge?+

Aisa message jo deserialize hi nahi ho pata. Deserialization listener ke pehle hoti hai, isliye aapka try/catch aur error handler dono bekaar — offset aage badh hi nahi sakta aur poori partition ruk jaati hai.

Ilaaj: ErrorHandlingDeserializer jo asli deserializer ko wrap karta hai. Ab bad record null payload + exception header ke saath aata hai, error handler use pakadta hai aur DLT bhej deta hai.

Emergency fix production mein: kafka-consumer-groups --reset-offsets --shift-by 1 us partition par — par pehle message ko DLT ya S3 mein copy kar lo.

Q18Coupon par max 50,000 redemptions hain. 3 lakh parallel requests. Over‑redemption kaise rokoge?+

Kafka ordering par bharosa mat karo — wo sirf per‑partition hai aur hot key ke liye humne sub‑shard bhi kar diya hai. Final authority database ka atomic conditional UPDATE hoga:

UPDATE coupon SET used_count = used_count + 1 WHERE code = ? AND used_count < max_redemptions — rows affected 0 matlab budget khatam.

Uske upar teen layers: (1) Redis se fast pre‑check taaki 90% invalid requests DB tak pahunche hi na, (2) UNIQUE(coupon_code, user_id) per‑user limit ke liye, (3) processed_event table duplicate Kafka delivery ke liye.

Key sentence: the counter's guard condition lives inside the write, never in a separate read.

Q19Ek coupon code par 90% traffic aa raha hai. Hot partition kaise theek karoge?+

Key ko sub‑shard karo: couponCode + "#" + floorMod(userId.hashCode(), 8). Ab load 8 partitions par baant gaya.

Isse per‑coupon ordering tootti hai — par humein wo chahiye hi nahi, kyunki budget safety DB constraint se aa rahi hai, partition ordering se nahi. Ye trade‑off explicitly bolna important hai.

Doosre options: custom Partitioner jo sirf known hot keys ko spread kare, ya hot coupon ko alag dedicated topic par nikal dena.

Q20DB mein save ho gaya par Kafka publish fail ho gaya. Ab?+

Ye dual‑write problem hai — do systems, ek logical operation, koi shared transaction nahi. @Transactional Kafka ko cover nahi karta.

Solution transactional outbox: event ko usi DB transaction mein outbox table mein likho. Alag relay (Debezium CDC ya FOR UPDATE SKIP LOCKED polling job) usse Kafka par bhejta hai.

Relay at‑least‑once hai, isliye consumer idempotent hona chahiye. Ye jodi — outbox + idempotent consumer — hi standard production answer hai.

Q21Booking flow ke liye orchestration chunoge ya choreography?+

Booking mein inventory hold, coupon redeem, aur payment — teeno reversible operations hain aur compensation ka order matter karta hai. Isliye orchestration.

Reasons: poora flow ek class mein readable, compensation sequence explicit, timeout handling ek jagah, aur "booking abhi kahan hai" ka jawab ek DB row se mil jaata hai.

Choreography tab jab 2–3 steps hon, koi compensation na ho, aur services ko genuinely independent rakhna ho — jaise coupon.redeemed par notification aur analytics ka fan‑out.

Trade‑off bolna mat bhoolo: orchestrator coupling point aur potential SPOF hai; isliye stateless rakho, state DB mein, replicas 3.

Q22Same coupon event do baar aa gaya. Design kaise bachayega?+

At‑least‑once delivery hai, isliye duplicate aana normal hai — usse rokne ki nahi, absorb karne ki design chahiye.

Layer 1: har event mein producer‑generated eventId (UUID). Consumer processed_event(consumer_group, event_id) par unique constraint ke saath insert karta hai; ON CONFLICT DO NOTHING se 0 rows mile to skip.

Layer 2: business natural key — UNIQUE(coupon_code, user_id). Dedupe table kisi wajah se fail bhi ho jaaye to ye phir bhi double redemption nahi hone dega.

Dono cheezein ek hi DB transaction mein honi chahiye, warna gap reh jaata hai.

Q23Coupon apply aur reverse ulte order mein process ho gaye. Kya karoge?+

Root cause: dono events alag partitions mein gaye (alag key ya null key). Fix: dono ka key bookingId — same partition, same consumer thread, natural order.

Defence in depth: payload mein version ya occurredAt rakho aur consumer stale event drop kare — if (event.version <= row.version) return;. Isse late‑arriving event kabhi naye state ko overwrite nahi karega.

Aur ek baat: consumer ke andar khud ka thread pool mat banao. Partition ordering ka fayda usi waqt khatam ho jaata hai.

Q24Producer team ne field ka type badal diya. Consumers kaise bachenge?+

Structural fix: Schema Registry with BACKWARD compatibility — incompatible schema publish hi nahi ho payega, CI mein hi fail ho jaayega.

Safe change: naya optional field with default. Unsafe: required field remove, rename, ya type change. Breaking change zaroori ho to naya topic coupon.redeemed.v2; dono parallel chalao, consumers migrate karo, phir v1 retire.

Runtime safety net: ErrorHandlingDeserializer taaki koi purana bad record poison pill na ban jaaye.

Q25DLQ design kaise karoge? Messages wapas kaise chalenge?+

Naming: <topic>-dlt, same partition number, retention 30 din. Original headers preserve karo — Spring khud kafka_dlt-exception-message, kafka_dlt-original-topic, kafka_dlt-original-offset add kar deta hai.

Retry vs DLT ka classification zaroori hai: transient (gateway timeout, DB deadlock) → backoff retry; permanent (invalid coupon, bad JSON) → seedha DLT.

Replay ke liye ek admin endpoint jo DLT se padh ke original topic par wapas publish kare, saath mein replayAttempt header. Aur alert: DLT message count > 0 par page karo — jo DLT kabhi dekha na jaaye wo silent data loss hai.

Q26Naye analytics service ko 30 din ka purana data chahiye, par retention 7 din hai.+

7 din se purana data Kafka mein hai hi nahi — wo wapas nahi aayega. Do cheezein karni hain.

Abhi: warehouse/S3 se ek‑baar ka backfill chalao, aur naye consumer group ko auto-offset-reset=earliest se topic ka available data padhne do. Backfill aur live stream ke overlap ko idempotent writes se handle karo.

Aage ke liye: audit‑grade topics par retention 30–90 din, ya tiered storage (S3 backed) on karo. Aur state topics ko compact rakho — unka current state kabhi expire hi nahi hota.

Q27Production mein lag badh raha hai. Step by step kya check karoge?+
  1. kafka-consumer-groups --describe --group X — lag har partition par hai ya ek‑do par?
  2. Ek partition par → hot key. Key strategy badlo.
  3. Sab par → consumer count vs partition count check karo. Consumers kam hain to scale karo.
  4. Consumers = partitions already → per‑record processing time dekho (DB p99, external call p99).
  5. Rebalance logs check karo — agar har 5 min par rebalance ho raha hai to consumer actually kaam hi nahi kar raha.
  6. Producer rate check karo — kya genuinely traffic 5× ho gaya hai (sale/campaign)?
  7. Quick relief: non‑critical consumers pause, batch size badhao, ya temporarily zyada pods.
Q28Consumer group har 2 minute par rebalance ho raha hai. Kyun?+

Sabse common wajah: max.poll.interval.ms breach. Ek poll batch ka processing time interval se zyada ho raha hai, broker consumer ko dead maan ke nikaal deta hai, wo wapas join karta hai, loop chalta rehta hai.

Check karo: max.poll.records × per‑record time < max.poll.interval.ms hona chahiye. Fix: records ghatao (500→50) ya interval badhao.

Doosri wajahein: long GC pause (heap tune karo), k8s liveness probe pod restart kar raha hai, network flakiness, ya deployment loop mein pods aa‑ja rahe hain. Static membership + cooperative assignor ye dard bahut kam kar dete hain.

Q29Producer log mein "Expiring N records for topic-partition" aa raha hai. Kya matlab?+

Records producer ke buffer mein delivery.timeout.ms tak pade rahe aur bheje nahi ja sake — ab drop kiye ja rahe hain. Ye data loss hai agar aapne callback handle nahi kiya.

Common causes: broker/partition leader unavailable, network saturation, buffer.memory bhar gaya, ya min.insync.replicas satisfy nahi ho raha (ISR shrink ho gaya).

Kya karein: callback mein failure zaroor handle karo (outbox row FAILED), delivery.timeout.ms aur request.timeout.ms tune karo, broker‑side ISR health dekho, aur producer ke record-error-rate par alert lagao.

Q30Messages produce ho rahe hain par consumer ko mil hi nahi rahe. Checklist?+
  1. Topic sahi hai? Typo aur version suffix (.v1 vs .v2) sabse common galti hai.
  2. --describe se dekho ki messages actually pahunche — log‑end offset badh raha hai ya nahi.
  3. Consumer group ka offset already log‑end par hai? Naya group hai to auto-offset-reset=latest ki wajah se purane messages skip ho gaye honge.
  4. Consumer group active hai? --describe mein assigned partitions dikhni chahiye. Khaali hai to consumer start hi nahi hua.
  5. isolation.level=read_committed hai aur producer transactional hai par commit nahi kar raha — messages dikhenge hi nahi.
  6. Deserialization silently fail ho ke DLT mein ja rahi hai? DLT topic check karo.
  7. Consumer poll kar raha hai par filter/condition sab drop kar raha hai — listener ke pehle ek debug log lagao.
