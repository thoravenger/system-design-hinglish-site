Java Bug-Fix Patterns — Study Guide

How to use this guide

Every pattern has the same four parts: the task, the buggy code, the fix, and why it breaks. Cover the fix, read the buggy code, and name the bug out loud before you look.

Code targets Java 11+ and uses only the standard library. Amounts are double to keep the stream code readable; pattern 32 shows why real banking code uses BigDecimal.

The 60-second bug-hunt checklist

Run these ten questions against any method before you change a line.

  1. Inputs: can the list, an element, or a field be null? What happens with an empty list or a single item?

  2. Conditions: is every > / >= right at the exact boundary value? Are && and || grouped the way the rule says?

  3. Loops and indexes: does the loop stop at size() - 1? Can get() or subList() go out of range?

  4. Equality: is == used on String or Integer? Does the class override both equals() and hashCode()?

  5. Maps: can a key repeat? What does get() return for a key that is missing?

  6. Streams: is the stream result actually used? Does get() or getAsDouble() assume a value exists?

  7. Ordering and mutation: does the result need an order? Does the method change the caller's list?

  8. Numbers: integer division, (int) casts, overflow, double used for money?

  9. Exceptions: is anything swallowed, or caught too broadly?

  10. Dates: are range ends inclusive or exclusive? Which time zone? Is now() called inside the logic?

Shared model used in every example

public class Transaction {
    private String id;               // "T1"
    private String accountId;        // "ACC-1"
    private String type;             // "CREDIT" or "DEBIT"
    private double amount;           // 150.75
    private String currency;         // "GBP", "USD", "HKD"
    private String status;           // "SUCCESS", "FAILED", "PENDING"
    private LocalDateTime timestamp; // 2026-10-03T09:15
    private List<String> tags;       // ["salary", "monthly"], can be null

}

Part A — The 20 core patterns

1. equals() / hashCode()

If you override equals(), override hashCode() with the same fields, or hash-based collections keep "duplicates".

Task: two Customer objects with the same id are the same customer, so a HashSet should hold only one.

class Customer {
    private final String id;
    private final String name;
    // constructor and getters omitted

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Customer)) return false;
        Customer other = (Customer) o;
        return id.equals(other.id);
    }
    // BUG: no hashCode()
}

Set<Customer> customers = new HashSet<>();
customers.add(new Customer("C1", "Asha"));
customers.add(new Customer("C1", "Asha"));
customers.size();   // 2, expected 1

Fix:

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Customer)) return false;
    Customer other = (Customer) o;
    return Objects.equals(id, other.id);   // null-safe
}

@Override
public int hashCode() {
    return Objects.hash(id);               // same field(s) as equals()
}

Why: a HashSet or HashMap uses hashCode() to pick a bucket first, and only calls equals() inside that bucket. Without hashCode(), each object gets an identity hash, lands in a different bucket, and equals() is never called.

Also watch for:

  • public boolean equals(Customer other) is an overload, not an override, so collections ignore it and the set still holds 2. Always equals(Object o) with @Override.

  • Don't use mutable fields in hashCode() for objects stored in sets or used as map keys. If the field changes after insertion, contains() returns false.

Test with: same id with a different name, a null id, the same instance added twice, the object used as a HashMap key.

2. List → Map with a loop

When you build a map of lists or counts in a loop, use computeIfAbsent() or merge(); a plain put() overwrites what was there.

Task: group transactions by account.

Map<String, List<Transaction>> byAccount = new HashMap<>();
for (Transaction t : transactions) {
    List<Transaction> list = new ArrayList<>();
    list.add(t);
    byAccount.put(t.getAccountId(), list);   // BUG: replaces the earlier list
}
// ACC-1 had T1 and T2, but the map holds only [T2]

Fix:

Map<String, List<Transaction>> byAccount = new HashMap<>();
for (Transaction t : transactions) {
    byAccount.computeIfAbsent(t.getAccountId(), k -> new ArrayList<>()).add(t);
}

Same family, counting per key:

// BUG: get() returns null the first time an account appears → null + 1 → NullPointerException
counts.put(t.getAccountId(), counts.get(t.getAccountId()) + 1);

// Fix
counts.merge(t.getAccountId(), 1, Integer::sum);
// or: counts.put(id, counts.getOrDefault(id, 0) + 1);

Why: put() always replaces the existing value. computeIfAbsent() creates the list only for a new key and returns the existing list otherwise. merge() inserts 1 for a new key, or adds 1 to the old value.

Stream equivalent: groupingBy(Transaction::getAccountId) (pattern 6). Test with: one account with several transactions, an empty list.

3. Map → List

A HashMap has no order, so "the first N keys" means nothing; sort the entries, then limit().

Task: return the 3 accounts with the highest balance, highest first.

List<String> top3(Map<String, Double> balances) {
    List<String> result = new ArrayList<>(balances.keySet());   // BUG: random order
    return result.subList(0, 3);                                 // BUG: crashes with fewer than 3 accounts
}

Fix:

List<String> top3(Map<String, Double> balances) {
    return balances.entrySet().stream()
            .sorted(Map.Entry.comparingByValue(Comparator.reverseOrder()))
            .limit(3)
            .map(Map.Entry::getKey)
            .collect(Collectors.toList());
}

Why: streaming over entrySet() keeps each key next to its value while you sort. limit(3) is safe when only 2 entries exist, while subList(0, 3) throws IndexOutOfBoundsException: toIndex = 3.

Also watch for:

  • Ties: if equal balances must come out in a fixed order, add a key tie-breaker. It needs a type hint: Map.Entry.<String, Double>comparingByValue(Comparator.reverseOrder()).thenComparing(Map.Entry.comparingByKey()).

  • keySet(), values() and entrySet() are live views of the map. Copy them with new ArrayList<>(...) before you change either side.

Test with: an empty map, fewer than 3 entries, ties, a null balance (comparingByValue throws on null).

4. toMap()

Collectors.toMap() throws NullPointerException if any value is null, even though a plain HashMap accepts null values.

Task: build a lookup of transaction id → currency. Some old records have no currency.

Map<String, String> currencyById = transactions.stream()
        .collect(Collectors.toMap(Transaction::getId, Transaction::getCurrency));
// NullPointerException as soon as one currency is null

Fix: decide what a missing value means, then say it in code.

// Option A: skip records with no currency
Map<String, String> currencyById = transactions.stream()
        .filter(t -> t.getCurrency() != null)
        .collect(Collectors.toMap(Transaction::getId, Transaction::getCurrency));

// Option B: keep them with a default
Map<String, String> currencyById = transactions.stream()
        .collect(Collectors.toMap(
                Transaction::getId,
                t -> t.getCurrency() == null ? "UNKNOWN" : t.getCurrency()));

Why: toMap() rejects null values internally, so one bad record kills the whole collect(). If you truly need null values in the map, use a plain loop with HashMap.put().

Also: toMap() promises no key order. If order matters, use the 4-argument form with LinkedHashMap::new (insertion order) or TreeMap::new (sorted), shown in pattern 5.

Test with: a null value, an empty list, a repeated id (pattern 5).

5. Duplicate keys in toMap()

Before every toMap(), ask "can this key repeat?" If yes, you need a merge function, and it has to match the business rule.

Task: keep the latest transaction for each account.

Map<String, Transaction> latestByAccount = transactions.stream()
        .collect(Collectors.toMap(Transaction::getAccountId, t -> t));
// IllegalStateException: Duplicate key ACC-1 (attempted merging values ...)

The tempting fix is still wrong:

.collect(Collectors.toMap(Transaction::getAccountId, t -> t, (a, b) -> b));
// keeps the LAST one in the list, which is the latest only if the list is sorted by time

Fix:

Map<String, Transaction> latestByAccount = transactions.stream()
        .collect(Collectors.toMap(
                Transaction::getAccountId,
                t -> t,
                (a, b) -> b.getTimestamp().isAfter(a.getTimestamp()) ? b : a));

Pick the merge function from the rule:

RuleMerge function
Total per keyDouble::sum
Keep the first seen(a, b) -> a
Keep the latest by time(a, b) -> b.getTimestamp().isAfter(a.getTimestamp()) ? b : a
Keep the largestBinaryOperator.maxBy(Comparator.comparingDouble(Transaction::getAmount))
Need every valuenot toMap(): use groupingBy() (pattern 6)

Need sorted keys as well: Collectors.toMap(Transaction::getAccountId, Transaction::getAmount, Double::sum, TreeMap::new).

Test with: two transactions for one account in reverse time order, a single transaction, equal timestamps.

6. groupingBy / partitioningBy

groupingBy() only creates keys that actually occur, so a group with zero items has no key and get() returns null.

Task: show the number of FAILED transactions on a dashboard.

Map<String, Long> countByStatus = transactions.stream()
        .collect(Collectors.groupingBy(Transaction::getStatus, Collectors.counting()));

long failed = countByStatus.get("FAILED");   // NullPointerException on a day with no failures

Fix:

long failed = countByStatus.getOrDefault("FAILED", 0L);

For a yes/no split, partitioningBy() always returns both keys, even when one side is empty:

Map<Boolean, Long> bySize = transactions.stream()
        .collect(Collectors.partitioningBy(t -> t.getAmount() >= 10_000, Collectors.counting()));
// {false=4, true=0}, so bySize.get(true) is safe

Also watch for:

  • A null classifier result (a null status) throws NullPointerException: element cannot be mapped to a null key. Filter nulls first, or map them to "UNKNOWN".

  • counting() returns Long, so assigning to Map<String, Integer> won't compile.

  • Pick the downstream collector from the question: counting(), summingDouble(), averagingDouble(), mapping(f, Collectors.toList()), or maxBy(cmp), which gives an Optional per group.

Test with: a status that never occurs, a null status, an empty list.

7. filter

Streams never change the list they came from; if you don't collect the result, the filter did nothing.

Task: keep only successful transactions.

List<Transaction> successfulOnly(List<Transaction> transactions) {
    transactions.stream().filter(t -> "SUCCESS".equals(t.getStatus()));   // BUG: result thrown away
    return transactions;                                                   // still has FAILED and PENDING
}

Fix:

List<Transaction> successfulOnly(List<Transaction> transactions) {
    return transactions.stream()
            .filter(t -> "SUCCESS".equals(t.getStatus()))
            .collect(Collectors.toList());
}

Why: filter() returns a new stream, and nothing runs until a terminal operation such as collect(). To change the list in place, use transactions.removeIf(t -> !"SUCCESS".equals(t.getStatus())), but only when the caller expects their list to change.

Also watch for:

  • Write string checks as "SUCCESS".equals(t.getStatus()). The literal on the left can never be null.

  • Two .filter() calls in a row mean AND. An OR rule must sit inside one filter: .filter(t -> isA(t) || isB(t)).

  • removeIf() on List.of(...) throws UnsupportedOperationException, even when nothing matches.

Test with: no successful transactions, a null status, an immutable input list.

8. map

map() should turn each element into a new value; calling setters inside map() corrupts the original data.

Task: show amounts in USD (rate 1.25) without touching the stored GBP data.

List<Transaction> toUsd(List<Transaction> transactions) {
    return transactions.stream()
            .map(t -> { t.setAmount(t.getAmount() * 1.25); return t; })   // BUG: changes the original
            .collect(Collectors.toList());
}
// Call it twice: the stored 100.0 becomes 156.25

Fix:

List<Double> toUsd(List<Transaction> transactions) {
    return transactions.stream()
            .map(t -> t.getAmount() * 1.25)    // a new value; the original stays 100.0
            .collect(Collectors.toList());
}

Why: the stream holds references to the same objects the caller owns, so a setter inside map() edits shared data. If the caller needs whole objects, build new ones (a DTO or a copy) inside map().

Also watch for:

  • map(Transaction::getAmount) gives Stream<Double>, which has no sum(). Use mapToDouble() for number work.

  • Filter before you map away the fields you need: after .map(Transaction::getAmount), the status is gone.

  • map() is one in, one out. One in, many out is flatMap() (pattern 9).

Test with: calling the method twice on the same list, then checking the original amounts.

9. flatMap

Use flatMap() when each element holds a list and you want one flat stream of the inner items; filter out null inner lists first.

Task: return every distinct tag used across transactions. Data: T1 [salary, monthly], T2 [rent, monthly], T3 [salary], T4 no tags (null).

List<List<String>> allTags = transactions.stream()
        .map(Transaction::getTags)            // BUG: Stream<List<String>>, not Stream<String>
        .distinct()
        .collect(Collectors.toList());
// [[salary, monthly], [rent, monthly], [salary], null]: tags repeat and a null slipped in

Fix:

List<String> allTags = transactions.stream()
        .map(Transaction::getTags)
        .filter(Objects::nonNull)             // T4 has no tag list
        .flatMap(List::stream)
        .distinct()
        .collect(Collectors.toList());
// [salary, monthly, rent]

Why: map() gives one output per input, so you get a stream of lists and distinct() compares whole lists. flatMap() pours each inner list into the main stream, so distinct() works on single tags. Without the null filter, flatMap(t -> t.getTags().stream()) throws NullPointerException.

Test with: a null tag list, an empty tag list, the same tag on different transactions. Need them sorted? Add .sorted() before collect().

10. sum

Sum with mapToDouble() over exactly the records the rule names; an (int) cast or a missing filter gives a confident, wrong total.

Task: total of successful debits. Data: 10.50 (SUCCESS), 20.75 (SUCCESS), 99.00 (FAILED).

int total = transactions.stream()
        .filter(t -> "DEBIT".equals(t.getType()))   // BUG 1: the FAILED debit is included
        .mapToInt(t -> (int) t.getAmount())          // BUG 2: drops the pence
        .sum();
// 129, expected 31.25

Fix:

double total = transactions.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .mapToDouble(Transaction::getAmount)
        .sum();
// 31.25

Why: a cast to int truncates (10.50 becomes 10) with no warning. Each word in the rule ("successful", "debit") should map to one filter you can point at.

Also: the sum of an empty stream is 0, which is usually right, unlike average(). Summing large int values overflows silently; use mapToLong() or Math.addExact() when totals can pass about 2.1 billion. Real money belongs in BigDecimal (pattern 32).

Test with: a FAILED debit, a CREDIT, amounts with pence, an empty list.

11. average

average() returns OptionalDouble because an empty input has no average; decide what "no data" means before you unwrap it.

Task: average transaction amount for one account.

double averageAmount(List<Transaction> transactions, String accountId) {
    return transactions.stream()
            .filter(t -> accountId.equals(t.getAccountId()))
            .mapToDouble(Transaction::getAmount)
            .average()
            .getAsDouble();   // NoSuchElementException: No value present, for an account with no transactions
}

Fix:

double averageAmount(List<Transaction> transactions, String accountId) {
    return transactions.stream()
            .filter(t -> accountId.equals(t.getAccountId()))
            .mapToDouble(Transaction::getAmount)
            .average()
            .orElse(0.0);     // or return the OptionalDouble and let the caller decide
}

Hand-written averages have their own traps:

CodeResultProblem
int sum = 25, count = 2; sum / count12integer division drops the .5
(double) sum / count12.5correct
int division when count == 0ArithmeticException: / by zerocrash
double total divided by 0NaN or Infinitysilent nonsense

Ask the interviewer whether "no data" should be 0, empty, or an error; a 0 can look like a real average.

Test with: an account with no transactions, a single transaction, amounts that don't divide evenly.

12. max / min

max() and min() return Optional because the stream may be empty; read the requirement twice to pick the direction.

Task: return the largest successful transaction.

Transaction largest(List<Transaction> transactions) {
    return transactions.stream()
            .filter(t -> "SUCCESS".equals(t.getStatus()))
            .min(Comparator.comparingDouble(Transaction::getAmount))   // BUG 1: min, not max
            .get();                                                     // BUG 2: crashes when nothing matches
}

Fix:

Optional<Transaction> largest(List<Transaction> transactions) {
    return transactions.stream()
            .filter(t -> "SUCCESS".equals(t.getStatus()))
            .max(Comparator.comparingDouble(Transaction::getAmount));
}

Why: on an empty stream max() returns Optional.empty, and get() throws NoSuchElementException. The non-stream Collections.max(list) also throws on an empty list.

Also watch for:

  • "Oldest" is min() of the timestamp and "newest" is max(). Swapping them is one of the most common bugs in these rounds.

  • On ties, don't rely on which element wins. Add .thenComparing(Transaction::getId) if the result must be predictable.

  • Comparator.comparing(Transaction::getAmount) boxes every value; comparingDouble() avoids that.

Test with: no successful transactions, two equal maximums, a single element.

13. Comparator: business ordering

Alphabetical order is rarely the business order; when the spec gives a priority, encode it explicitly.

Task: the support queue shows PENDING first, then FAILED, then SUCCESS. Unknown or missing statuses go last.

transactions.sort(Comparator.comparing(Transaction::getStatus));
// BUG: alphabetical gives FAILED, PENDING, SUCCESS, and a null status throws NullPointerException

Fix:

private static int priority(String status) {
    if ("PENDING".equals(status)) return 0;
    if ("FAILED".equals(status))  return 1;
    if ("SUCCESS".equals(status)) return 2;
    return 3;                                   // unknown or null go last
}

transactions.sort(Comparator.comparingInt(t -> priority(t.getStatus())));
// PENDING, FAILED, SUCCESS, null

Why: comparing(Transaction::getStatus) uses String's natural, alphabetical order. A rank function makes the rule visible, handles null safely, and puts unknown values somewhere on purpose. In production code an enum with a priority field does the same job.

Also watch for:

  • List.of(...).indexOf(null) and Map.of(...).get(null) throw NullPointerException, so rank lookups built on them break on a null status.

  • Highest first is .reversed(), for example Comparator.comparingDouble(Transaction::getAmount).reversed().

Test with: every status once, a null status, an unexpected value such as "CANCELLED".

14. Multi-field comparator

A .reversed() at the end of a chain reverses every field in it; reverse a single field inside its own thenComparing().

Task: sort by account A→Z, then by amount, highest first.

transactions.sort(Comparator.comparing(Transaction::getAccountId)
        .thenComparingDouble(Transaction::getAmount)
        .reversed());
// BUG: ACC-2 500, ACC-2 50, ACC-1 300, ACC-1 100 (accounts are now Z→A as well)

Fix:

transactions.sort(Comparator.comparing(Transaction::getAccountId)
        .thenComparing(Comparator.comparingDouble(Transaction::getAmount).reversed()));
// ACC-1 300, ACC-1 100, ACC-2 500, ACC-2 50

Why: each chained call wraps everything before it, so a trailing .reversed() flips the whole comparator, not just the last field.

Also watch for:

  • Two separate sorts (by amount, then by account) only work because List.sort() is stable, and they're easy to write in the wrong order. Build one comparator.

  • In a chain, an untyped lambda loses its type: Comparator.comparing(t -> t.getAccountId()).thenComparing(...) doesn't compile. Use method references or (Transaction t) -> t.getAccountId().

  • Null keys: wrap the key comparator, e.g. Comparator.comparing(Transaction::getAccountId, Comparator.nullsLast(Comparator.naturalOrder())).

Test with: two accounts with two amounts each, equal amounts, a null account id.

15. Null handling

Check nulls at three levels: the collection, each element, and each field you read.

Task: total amount in a given currency.

double totalFor(List<Transaction> transactions, String currency) {
    double total = 0;
    for (Transaction t : transactions) {            // NPE if the list is null
        if (t.getCurrency().equals(currency)) {     // NPE if t is null, or if its currency is null
            total += t.getAmount();
        }
    }
    return total;
}

Fix:

double totalFor(List<Transaction> transactions, String currency) {
    if (transactions == null || currency == null) {
        return 0.0;                                    // or fail fast; see the contract note
    }
    return transactions.stream()
            .filter(Objects::nonNull)                  // null elements
            .filter(t -> currency.equals(t.getCurrency()))   // currency is known non-null here
            .mapToDouble(Transaction::getAmount)
            .sum();
}

Contract note: a null argument is usually a caller bug, so failing fast with Objects.requireNonNull(transactions, "transactions") is often better than returning 0. Null data inside records is normal real-world mess: skip it, default it, or report it. Say which one you chose; interviewers listen for that.

Null-safe tools: "LITERAL".equals(x), Objects.equals(a, b), Objects.requireNonNull(x, "message"), map.getOrDefault(key, default), Comparator.nullsLast(...), Optional.ofNullable(x).

Test with: a null list, a null element, a null currency field, a null currency argument.

16. Empty list

Return an empty collection, never null, and know what each operation does when there is nothing to process.

Task: return the ids of failed transactions.

List<String> failedIds(List<Transaction> transactions) {
    if (transactions.isEmpty()) {
        return null;        // BUG: every caller must now null-check, and most won't
    }
    return transactions.stream()
            .filter(t -> "FAILED".equals(t.getStatus()))
            .map(Transaction::getId)
            .collect(Collectors.toList());
}

Fix: delete the special case. The stream already returns [] for an empty input, so callers can loop or call size() safely.

17. Boundary conditions

Translate the words of the rule into operators exactly, then test the exact boundary values.

Task: fees are free up to £100, £1.50 up to £1,000, and £5 above £1,000. Negative amounts are invalid.

double fee(double amount) {
    if (amount < 100) return 0.0;
    if (amount > 100 && amount < 1000) return 1.5;
    return 5.0;
}
// fee(100) = 5.0 (should be 0.0)
// fee(1000) = 5.0 (should be 1.5)
// fee(-50) = 0.0 (should be rejected)

Fix:

double fee(double amount) {
    if (amount < 0) {
        throw new IllegalArgumentException("Amount cannot be negative: " + amount);
    }
    if (amount <= 100) return 0.0;
    if (amount <= 1000) return 1.5;
    return 5.0;
}

Why: the buggy tiers leave gaps at exactly 100 and 1000, so those values fall through to the last return. An ordered chain of <= checks has no gaps, because each tier starts where the previous one ended.

Words in the specOperator
at least, minimum, from, or more>=
more than, above, over, exceeds>
up to, at most, maximum, no more than<=
less than, below, under<

Test with: -1, 0, 100, 100.01, 1000, 1000.01. Ask whether 0 is a valid amount.

18. Duplicate records

distinct() and HashSet only remove duplicates that equals() and hashCode() call equal; to dedupe by a field, track the keys you have already seen.

Task: upstream sometimes sends the same transaction twice (same id). Keep the first occurrence and the original order.

List<Transaction> dedupe(List<Transaction> transactions) {
    return transactions.stream()
            .distinct()      // BUG: Transaction doesn't override equals()/hashCode(), so nothing is removed
            .collect(Collectors.toList());
}

Fix:

List<Transaction> dedupe(List<Transaction> transactions) {
    Set<String> seenIds = new HashSet<>();
    List<Transaction> result = new ArrayList<>();
    for (Transaction t : transactions) {
        if (seenIds.add(t.getId())) {     // add() returns false if the id was already seen
            result.add(t);
        }
    }
    return result;
}

Stream version with the same result:

new ArrayList<>(transactions.stream()
        .collect(Collectors.toMap(Transaction::getId, t -> t, (first, second) -> first, LinkedHashMap::new))
        .values());

Why: without an overridden equals(), two objects are equal only when they are the same instance, so distinct() sees four different objects. LinkedHashMap keeps first-seen order; a plain HashMap would scramble it.

Ask first: what makes two records duplicates? The same id, or the same account, amount and timestamp? Keep the first or the latest? Asking that question out loud scores points by itself.

Test with: the same id twice, three copies, no duplicates, duplicates far apart in the list.

19. Optional

Never call get() on an Optional you haven't proven is present; transform it with map() and finish with orElse(), orElseGet() or orElseThrow().

Task: return the id of the first FAILED transaction, or "NONE".

String firstFailedId(List<Transaction> transactions) {
    Optional<Transaction> failed = transactions.stream()
            .filter(t -> "FAILED".equals(t.getStatus()))
            .findFirst();
    return failed.get().getId();    // NoSuchElementException: No value present
}

Fix:

String firstFailedId(List<Transaction> transactions) {
    return transactions.stream()
            .filter(t -> "FAILED".equals(t.getStatus()))
            .findFirst()
            .map(Transaction::getId)
            .orElse("NONE");
}

Rules that catch most Optional bugs:

The default is expensive or has side effectsorElseGet(() -> loadDefault()); orElse(loadDefault()) runs it even when a value exists

findFirst() vs findAny(): findFirst() respects list order, while findAny() may return any match and exists for parallel streams. findFirst() also throws NullPointerException if the element it finds is null.

Test with: no match, a match in the middle of the list, a null element.

20. Fix a method so all hidden edge cases pass

Hidden tests hit the same dozen cases every time; list them before you touch the code, then fix everything in one pass.

Task: for each account, return the average amount of SUCCESSFUL DEBIT transactions, rounded to 2 decimals, sorted by account id.

Map<String, Double> avgDebitByAccount(List<Transaction> transactions) {
    Map<String, Double> result = new HashMap<>();
    for (Transaction t : transactions) {
        if (t.getType() == "DEBIT") {
            result.put(t.getAccountId(), (result.get(t.getAccountId()) + t.getAmount()) / 2);
        }
    }
    return result;
}

Bugs, in the order you would say them:

  1. t.getType() == "DEBIT" compares references. It passes with literal test data and fails with strings read from a database or JSON.

  2. result.get(...) is null the first time, so the addition throws NullPointerException.

  3. (old + new) / 2 is not an average: for 10, 20, 60 it gives 37.5 instead of 30.

  4. FAILED and PENDING debits are counted.

  5. A HashMap is not sorted by account id.

  6. Nothing handles a null list, null elements or a null account id, and nothing rounds.

Fix:

Map<String, Double> avgDebitByAccount(List<Transaction> transactions) {
    if (transactions == null) {
        return new TreeMap<>();
    }
    Map<String, Double> averages = transactions.stream()
            .filter(Objects::nonNull)
            .filter(t -> t.getAccountId() != null)
            .filter(t -> "DEBIT".equals(t.getType()))
            .filter(t -> "SUCCESS".equals(t.getStatus()))
            .collect(Collectors.groupingBy(
                    Transaction::getAccountId,
                    TreeMap::new,                                         // sorted keys
                    Collectors.averagingDouble(Transaction::getAmount)));
    averages.replaceAll((account, avg) -> Math.round(avg * 100) / 100.0);
    return averages;
}

Math.round(avg * 100) / 100.0 is fine for display; for money, round a BigDecimal with setScale(2, RoundingMode.HALF_EVEN) (pattern 32).

Hidden-test checklist:

  1. Null list: empty result, or the exception you agreed.

  2. Empty list: empty result.

  3. Exactly one element.

  4. A null element in the list.

  5. Null fields (account, type, status).

  6. Nothing matches the filter.

  7. Duplicate records.

  8. Exact boundary values, zero, negatives.

  9. Ties when sorting.

  10. Very large values, precision and rounding.

  11. The required order of the output.

  12. Case: "debit" vs "DEBIT" (ask).

How to run it in the interview:

  1. Restate the rule in one sentence and confirm it.

  2. Say the edge cases out loud from the checklist.

  3. Fix the code, smallest safe change first.

  4. Trace two inputs by hand: a normal case and an edge case.

  5. State complexity: here O(n) time and O(a) extra space for a accounts.

Part B — Level 3 bug types

21. Wrong condition: && vs ||

To negate "A or B" you need "not A and not B"; read every compound condition aloud with one concrete value.

Task: retry a transaction unless it is SUCCESS or CANCELLED.

boolean shouldRetry(Transaction t) {
    return !t.getStatus().equals("SUCCESS") || !t.getStatus().equals("CANCELLED");
}
// Always true: a SUCCESS payment is "not CANCELLED", so it gets retried (a double charge)

Fix:

boolean shouldRetry(Transaction t) {
    return !"SUCCESS".equals(t.getStatus()) && !"CANCELLED".equals(t.getStatus());
}

Why: De Morgan's law says !(A || B) equals !A && !B. Plug in SUCCESS: "not SUCCESS" is false, "not CANCELLED" is true, and false OR true is true. One concrete value exposes the bug in seconds.

Also watch for:

  • && binds tighter than ||, so a || b && c means a || (b && c). Add brackets whenever you mix them.

  • Set.of("SUCCESS", "CANCELLED").contains(status) reads well but throws NullPointerException for a null status.

  • Inverted checks copied from a neighbouring line: if (!isValid) vs if (isValid), < vs >.

Test with: every status once, plus null.

22. Off-by-one

Valid indexes run from 0 to size() - 1, and subList(from, to) excludes to; clamp both ends.

Task: return the last N transactions from a list sorted oldest to newest.

List<Transaction> lastN(List<Transaction> transactions, int n) {
    List<Transaction> result = new ArrayList<>();
    for (int i = transactions.size() - n; i <= transactions.size(); i++) {   // BUG: <= runs one past the end
        result.add(transactions.get(i));                                      // BUG: negative index when n > size
    }
    return result;
}
// 5 items, n = 2: IndexOutOfBoundsException, index 5 for length 5
// 5 items, n = 7: index -2

Fix:

List<Transaction> lastN(List<Transaction> transactions, int n) {
    if (n <= 0) {
        return new ArrayList<>();
    }
    int start = Math.max(0, transactions.size() - n);
    return new ArrayList<>(transactions.subList(start, transactions.size()));
}
// n = 2 gives [T4, T5]; n = 7 gives all 5; an empty list gives []

Why: index loops use i < size(). Math.max(0, ...) clamps the start when n is bigger than the list. Copying the subList() into a new ArrayList detaches the result from the caller's list (pattern 25).

Quick rules: n items run i = 0; i < n. The last element is get(size() - 1). "First k" is subList(0, Math.min(k, size())). A page numbered from 1 starts at index (page - 1) * pageSize.

Test with: n = 0, n = 1, n = size, n > size, negative n, an empty list.

23. Wrong null assumption

Any lookup can come back empty (a map get(), a repository find, a field from JSON), so handle "not found" where it happens.

Task: add 2% interest to an account's balance. Account and AccountRepository are simple classes for this example.

double balanceAfterInterest(AccountRepository repo, String accountId) {
    Account account = repo.findById(accountId);   // returns null for an unknown id
    return account.getBalance() * 1.02;           // NullPointerException, far from the real cause
}

Fix:

double balanceAfterInterest(AccountRepository repo, String accountId) {
    Account account = repo.findById(accountId);
    if (account == null) {
        throw new AccountNotFoundException(accountId);   // your own exception, clear message at the source
    }
    return account.getBalance() * 1.02;
}

Better design: make the lookup return Optional<Account> (Spring Data's findById already does), so every caller is forced to handle "not found":

return repo.findById(accountId)
        .map(account -> account.getBalance() * 1.02)
        .orElseThrow(() -> new AccountNotFoundException(accountId));

Same bug, other places: double limit = limits.get(accountId); throws NullPointerException when the key is missing, because the null Double is unboxed (use getOrDefault). Any Integer or Long from a map or entity unboxed into a primitive has the same risk.

Test with: an unknown id, an existing id, a null id.

24. Wrong collection

Choose the collection by the question you ask it: order, uniqueness, sorted keys, or fast lookup.

Task A: return each account id once, in the order first seen. Task B: find transactions from blocked accounts.

List<String> uniqueAccounts(List<Transaction> transactions) {
    Set<String> ids = new HashSet<>();            // BUG: HashSet scrambles the order
    for (Transaction t : transactions) {
        ids.add(t.getAccountId());
    }
    return new ArrayList<>(ids);
}

List<Transaction> fromBlocked(List<Transaction> transactions, List<String> blocked) {
    return transactions.stream()
            .filter(t -> blocked.contains(t.getAccountId()))   // BUG: List.contains scans the whole list every time
            .collect(Collectors.toList());
}

Fix:

Set<String> ids = new LinkedHashSet<>();           // unique, and keeps first-seen order

Set<String> blockedSet = new HashSet<>(blocked);   // build once, then O(1) lookups
return transactions.stream()
        .filter(t -> blockedSet.contains(t.getAccountId()))
        .collect(Collectors.toList());

With ids seen in the order ACC-9, ACC-1, ACC-5, ACC-20, ACC-3: HashSet returned ACC-20, ACC-3, ACC-1, ACC-5, ACC-9, and TreeSet would return ACC-1, ACC-20, ACC-3, ACC-5, ACC-9 (string order, so "20" sorts before "3").

Complexity: n transactions against m blocked ids is O(n × m) with a list and O(n + m) with a set. Say this out loud; it's an easy senior-level point.

Test with: repeated ids, the order of the output, a large blocked list.

25. Mutation bug

A method should not change its inputs unless that is its job: sort or filter a copy, and never hand out your internal list.

Task: return the 3 largest transactions for a report.

List<Transaction> top3(List<Transaction> transactions) {
    transactions.sort(Comparator.comparingDouble(Transaction::getAmount).reversed());   // BUG: reorders the caller's list
    return transactions.subList(0, Math.min(3, transactions.size()));                   // BUG: a live view, not a copy
}

What goes wrong:

  • The caller's list, maybe a statement in date order, is now sorted by amount.

  • An input built with List.of(...) throws UnsupportedOperationException.

  • The returned subList() is a view; once the caller adds to their list, touching the result throws ConcurrentModificationException.

Fix:

List<Transaction> top3(List<Transaction> transactions) {
    return transactions.stream()
            .sorted(Comparator.comparingDouble(Transaction::getAmount).reversed())
            .limit(3)
            .collect(Collectors.toList());     // a new list; the input is untouched
}

The class-level version of the same bug is a getter that leaks internal state:

public List<Transaction> getTransactions() {
    return transactions;                                // BUG: callers can add, remove or clear
}

// Fix
public List<Transaction> getTransactions() {
    return Collections.unmodifiableList(transactions);  // read-only view
    // or new ArrayList<>(transactions) for an independent copy
}

Test with: check the input order after the call, pass List.of(...), change the input after the call and reuse the result.

26. Incorrect comparator

A comparator must return a consistent negative, zero or positive; never subtract or cast, use Double.compare, Integer.compare or Comparator.comparing*.

Task: sort transactions by amount, smallest first.

transactions.sort((a, b) -> (int) (a.getAmount() - b.getAmount()));
// 10.75 vs 10.25: the difference is 0.5, and (int) 0.5 is 0, so they count as "equal"
// Result: [10.75, 10.25], not ascending

Fix:

transactions.sort(Comparator.comparingDouble(Transaction::getAmount));
// or (a, b) -> Double.compare(a.getAmount(), b.getAmount())

Why: casting a difference to int throws away anything under 1. For int keys, a - b can overflow: -2,000,000,000 minus 2,000,000,000 gives +294,967,296, so the sign flips. Integer.compare(a, b) never overflows.

Second trap: TreeSet and TreeMap treat compare() == 0 as "the same element".

Set<Transaction> byAmount = new TreeSet<>(Comparator.comparingDouble(Transaction::getAmount));
byAmount.add(t1);   // 100.0
byAmount.add(t2);   // also 100.0, but a different transaction
byAmount.size();    // 1: t2 was silently dropped

// Fix: a tie-breaker, so only truly identical elements compare as 0
new TreeSet<>(Comparator.comparingDouble(Transaction::getAmount).thenComparing(Transaction::getId));

Test with: amounts that differ by less than 1, equal amounts, very large and very negative int keys.

27. Duplicate key: composite keys that collide

Gluing fields into one string can make two different keys identical; use a separator that can't appear in the data, or a real key object.

Task: total payments per (customer id, account number) pair, using a simple Payment class with customerId, accountNo and amount.

Map<String, Double> totals = new HashMap<>();
for (Payment p : payments) {
    String key = p.getCustomerId() + p.getAccountNo();   // BUG: "C1" + "23" and "C12" + "3" are both "C123"
    totals.merge(key, p.getAmount(), Double::sum);
}
// Two customers' money lands in one total, and nothing throws

Fix:

// Quick fix: a separator that never appears in ids
String key = p.getCustomerId() + "|" + p.getAccountNo();

// Cleaner: a key with real equals() and hashCode() (pattern 1)
Map<List<String>, Double> totals = new HashMap<>();
totals.merge(Arrays.asList(p.getCustomerId(), p.getAccountNo()), p.getAmount(), Double::sum);

// Java 16+: record PaymentKey(String customerId, String accountNo) {} generates both methods

Why: put() and merge() never complain about a repeated key; they silently overwrite or combine. Only toMap() throws (pattern 5). Arrays.asList is used instead of List.of because List.of rejects null parts.

Test with: ids that are prefixes of each other ("C1" and "C12"), a null part, the same pair twice.

28. Empty stream: allMatch on nothing

allMatch() returns true for an empty stream, so "every item passed" is also true when there were no items.

Task: mark a batch COMPLETE only if every transaction in it succeeded.

String batchStatus(List<Transaction> batch) {
    boolean allOk = batch.stream().allMatch(t -> "SUCCESS".equals(t.getStatus()));
    return allOk ? "COMPLETE" : "INCOMPLETE";
}
// An empty batch (say, the upstream file failed to load) is reported COMPLETE

Fix:

String batchStatus(List<Transaction> batch) {
    if (batch == null || batch.isEmpty()) {
        return "EMPTY";      // or INCOMPLETE: agree it with the business
    }
    boolean allOk = batch.stream().allMatch(t -> "SUCCESS".equals(t.getStatus()));
    return allOk ? "COMPLETE" : "INCOMPLETE";
}

Why: logically, "all of zero items" is vacuously true. noneMatch() is also true on empty input, and anyMatch() is false. Any rule phrased "all", "none" or "every" needs an explicit empty check.

Related: reduce(Double::sum) without an identity returns Optional.empty on empty input, while reduce(0.0, Double::sum) returns 0.0. The full table is in pattern 16.

Test with: an empty batch, a null batch, one FAILED item, all SUCCESS.

29. Incorrect exception handling

Catch the specific exception, as close to the risky line as possible, and never swallow it silently.

Task: total the amount column (third field) of an uploaded CSV. A bad row must not hide problems.

double totalFromCsv(List<String> rows) {
    double total = 0;
    try {
        for (String row : rows) {
            String[] cols = row.split(",");
            total += Double.parseDouble(cols[2]);
        }
    } catch (Exception e) {
        // ignore
    }
    return total;
}
// Rows: "T1,ACC-1,10.50", "T2,ACC-1,abc", "T3,ACC-2", "T4,ACC-2,5.25"
// Returns 10.5: row 2 stops the loop, row 4 is never read, and nobody is told

Fix (skip bad rows and report them):

double totalFromCsv(List<String> rows, List<String> errors) {
    double total = 0;
    for (int i = 0; i < rows.size(); i++) {
        String[] cols = rows.get(i).split(",");
        if (cols.length < 3) {                       // a check, not an exception
            errors.add("Row " + (i + 1) + ": expected 3 columns, got " + cols.length);
            continue;
        }
        try {
            total += Double.parseDouble(cols[2].trim());
        } catch (NumberFormatException e) {          // only the failure we expect
            errors.add("Row " + (i + 1) + ": invalid amount '" + cols[2] + "'");
        }
    }
    return total;
}
// Returns 15.75; errors = [Row 2: invalid amount 'abc', Row 3: expected 3 columns, got 2]

If the business wants all-or-nothing instead, fail fast and keep the cause: throw new InvalidFileException("Row " + (i + 1) + " has an invalid amount", e);.

Rules:

  • Catch the narrowest type (NumberFormatException). Catching Exception also hides real bugs such as NullPointerException.

  • Put the try around the risky line; a try around the whole loop turns one bad row into a silent stop.

  • When you wrap an exception, pass the original as the cause.

  • Log or record context: which row, which id, which value.

  • Close resources with try-with-resources, and never return from a finally block, because it swallows the exception.

Test with: a non-numeric amount, a short row, an empty file, spaces around numbers (Double.parseDouble(" 5.25") works, but Integer.parseInt(" 5") throws).

30. Date and time handling

Use half-open ranges [start, next start), store moments as Instant, and format years with yyyy, never YYYY.

Task: return all transactions on a given date.

List<Transaction> onDate(List<Transaction> transactions, LocalDate date) {
    LocalDateTime start = date.atStartOfDay();
    LocalDateTime end = date.atTime(23, 59, 59);
    return transactions.stream()
            .filter(t -> t.getTimestamp().isAfter(start) && t.getTimestamp().isBefore(end))
            .collect(Collectors.toList());
}
// From 00:00:00, 12:00, 23:59:59 and 23:59:59.5 it keeps only 12:00

Fix:

List<Transaction> onDate(List<Transaction> transactions, LocalDate date) {
    LocalDateTime start = date.atStartOfDay();
    LocalDateTime nextDay = date.plusDays(1).atStartOfDay();
    return transactions.stream()
            .filter(t -> !t.getTimestamp().isBefore(start)      // start included
                      && t.getTimestamp().isBefore(nextDay))    // next day excluded
            .collect(Collectors.toList());
}
// Simpler for one day: t.getTimestamp().toLocalDate().equals(date)

Why: isAfter() and isBefore() are strict, so both ends were dropped, and 23:59:59 can't cover the fractions of the last second. !isBefore(start) means "at or after start". The same shape works for months, from YearMonth.of(2026, 2).atDay(1).atStartOfDay() up to the next month's start, with no 28/30/31-day logic (LocalDateTime.of(2026, 2, 30, 23, 59) throws DateTimeException).

Part C — Extra traps

31. Integer == trap

== on Integer, Long or String compares object references; for integers it happens to work from -128 to 127 because those values are cached, then fails.

Task: flag two accounts that have the same number of transactions.

Map<String, Integer> counts = ...;                   // {ACC-1=500, ACC-2=500}
if (counts.get("ACC-1") == counts.get("ACC-2")) {   // BUG: false for 500
    flagSameActivity();
}

What Java actually does:

Integer a = 127, b = 127;
a == b;        // true: both come from the cache
Integer c = 1000, d = 1000;
c == d;        // false: two different objects
c.equals(d);   // true

Fix:

if (Objects.equals(counts.get("ACC-1"), counts.get("ACC-2"))) {   // compares values, null-safe
    flagSameActivity();
}

Why: autoboxing reuses cached objects for small values only, so tests with small numbers pass and production numbers fail. Long behaves the same way. String has the same problem: literals are shared, but strings from a database, JSON or new String(...) are separate objects (pattern 20).

Also: unboxing a null Integer into an int (int n = counts.get("ACC-9");) throws NullPointerException.

Test with: values above 127, a missing key, strings built at runtime.

32. double vs BigDecimal for money

double can't store most decimal amounts exactly, so totals drift; banking code uses BigDecimal built from strings and compared with compareTo().

Task: add up payments of 0.10 and 0.20.

double total = 0.1 + 0.2;     // 0.30000000000000004
total == 0.3;                 // false
// adding 0.1 ten times gives 0.9999999999999999

Fix:

BigDecimal total = new BigDecimal("0.10").add(new BigDecimal("0.20"));   // 0.30

// Summing a list
BigDecimal sum = amounts.stream().reduce(BigDecimal.ZERO, BigDecimal::add);

33. Removing from a list while looping over it

Never call list.remove() inside a for-each loop over the same list; use removeIf(), an Iterator, or build a new list.

Task: remove FAILED transactions from a working list.

for (Transaction t : transactions) {
    if ("FAILED".equals(t.getStatus())) {
        transactions.remove(t);          // BUG
    }
}

What actually happens:

  • Usually ConcurrentModificationException on the next loop step.

  • Worse: if the removed item is second-to-last, the loop just stops. [A SUCCESS, B FAILED, C FAILED] ends as [A, C], so a FAILED item survives with no error.

The index version fails more quietly:

for (int i = 0; i < transactions.size(); i++) {
    if ("FAILED".equals(transactions.get(i).getStatus())) {
        transactions.remove(i);          // BUG: the next item shifts into slot i and is skipped
    }
}
// [A FAILED, B FAILED, C SUCCESS] ends as [B, C]

Fix:

transactions.removeIf(t -> "FAILED".equals(t.getStatus()));

// or, when each item needs more logic
Iterator<Transaction> it = transactions.iterator();
while (it.hasNext()) {
    if ("FAILED".equals(it.next().getStatus())) {
        it.remove();                     // the iterator's own remove is safe
    }
}

Why: a for-each loop runs a hidden iterator that checks whether the list changed behind its back. Removing by index shifts every later element left by one. Looping backwards by index also works, but removeIf() says what you mean.

Also: maps behave the same way (removing inside a loop over keySet() throws; use map.entrySet().removeIf(...)), and List.of(...) or Collections.unmodifiableList(...) throw UnsupportedOperationException on any removal.

Test with: two FAILED items next to each other, a FAILED item first, a FAILED item last, an immutable list.
