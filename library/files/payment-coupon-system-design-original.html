Entry 01

Scope, requirements aur scale

HLD

Har design ka pehla step numbers hain, boxes nahi. Agar aapko TPS nahi pata, toh aap ye decide hi nahi kar sakte ki Redis chahiye ya nahi.

Problem

Seedha schema likhne lag jaana

Interviewer bola "design a payment system with coupons" aur aapne turant CREATE TABLE payments shuru kar diya. Ab 20 minute baad aapko pata chalta hai ki requirement clear hi nahi thi.

  • Kya hum khud card process kar rahe hain, ya Razorpay/Stripe jaisa PSP use kar rahe hain? (Ye ek sawaal poora PCI-DSS scope badal deta hai.)
  • Coupon ek user ek baar use kar sakta hai, ya global limit hai? Dono ke lock strategy alag hain.
  • Peak traffic kitna? IPL ticket drop ya normal Tuesday?
  • Money loss acceptable hai ya zero-loss guarantee chahiye?
Real failure: Ek team ne coupon limit ko in-memory counter se handle kiya. 3 pods the. Limit thi 1,000. Actual redemptions: 2,940. Har pod apna hi count rakh raha tha. Loss ≈ ₹19 lakh.
Solution

Pehle requirements likho, phir box banao

Functional (kya karega): order banana, coupon validate + apply karna, PSP se payment collect karna, booking confirm karna, refund dena, ledger maintain karna, coupon redemption track karna.

Non-functional (kaise karega): ye asli design drive karta hai.

RequirementTargetDesign pe asar / impact
CorrectnessZero double-chargeIdempotency keys + unique constraints
Availability99.99%PSP failover, async capture
Latency p99< 400 ms (PSP call chhod ke)Coupon validation Redis se
ConsistencyMoney: strong
Booking: eventual		Saga + outbox, 2PC nahi
Auditability7 saal retentionAppend-only double-entry ledger

Back-of-the-envelope

  • 5M bookings/day → 5,000,000 / 86,400 ≈ 58 TPS average.
  • Peak = 10× average → ~600 TPS. Flash sale spike = 40× → ~2,300 TPS for 90 seconds.
  • Payment row ≈ 800 bytes → 4 GB/day, ledger entries 2× → ~12 GB/day total. 7 saal ≈ 30 TB → partitioning zaroori.
  • Coupon validate call payment se 4× zyada hoti hai (log check karte hain, pay nahi karte) → ~2,400 TPS read → cache layer chahiye.
Interview tip: Ye numbers bolne se hi aap "junior" bracket se bahar nikal jaate ho. 600 TPS bolna aur phir "isliye single Postgres primary chal jayega, sharding abhi nahi chahiye" bolna — yahi seniority dikhati hai.
Entry 02

High-level architecture

HLD

Services ko is tarah kaato ki failure ek jagah rahe. Payment ka blast radius booking tak nahi pahunchna chahiye.

Problem

Ek hi transaction mein sab kuch

Common beginner design — Booking Service directly sab karta hai:

BookingService.javaanti-pattern
  1. @Transactional // ← poison
  2. public Booking createBooking(BookingRequest req) {
  3. seatRepository.lockSeats(req.getSeatIds());
  4. couponRepository.decrementUsageCount(req.getCouponCode());
  5. RazorpayResponse r = razorpayClient.charge(req); // 8 sec!
  6. return bookingRepository.save(toBooking(req, r));
  7. }
Kya toota: Line 5 ek network call hai jo 8 second le sakti hai. Tab tak line 3 ka DB row-lock hold hai. 600 TPS pe connection pool 30 second mein khatam. Poora booking system down — sirf isliye ki Razorpay slow tha.

Aur agar line 5 timeout ho gaya toh transaction rollback hoga — coupon count wapas aa jayega, lekin Razorpay ne paisa le liya hoga. Ab DB kehta hai "no payment", bank kehta hai "payment done". Ye money leak hai.
Solution

Orchestrated services + async boundaries

Rule: external network call kabhi bhi DB transaction ke andar nahi. Har external call ke aage ek state persist karo, phir call karo.

Flow — sequence

  • 1. Client → Booking Service: seat hold (TTL 8 min), status PENDING_PAYMENT.
  • 2. Booking → Coupon Service: reserveCoupon() — count abhi hi decrement, TTL ke saath.
  • 3. Booking → Payment Orchestrator: initiatePayment(). Row DB mein CREATED state se save.
  • 4. Payment → PSP Adapter: yahan pehli baar external call hoti hai, transaction ke bahar.
  • 5. PSP → Webhook Ingest: async confirmation. Ye source of truth hai, client ka response nahi.
  • 6. Payment → Kafka payment.captured → Booking confirm, Ledger entry, Notifier.
Yaad rakho: Client ka 200 OK "payment ho gaya" nahi hota. Sirf webhook + reconciliation hi truth hai. Client browser band kar sakta hai, network gir sakta hai — server-to-server webhook nahi girta.
Entry 03

Payment state machine

HLDLLD

Payment ek boolean nahi hai. Ye ek finite state machine hai jismein sirf kuch transitions legal hain — aur illegal transition block karna hi paisa bachata hai.

Problem

boolean isPaid ka jaal

Payment.javaanti-pattern
  1. private boolean isPaid; // sirf 2 states
  2. private double amount; // floating point!

Isse ye sab express hi nahi ho sakta:

  • Authorize ho gaya lekin capture nahi hua (hotel booking pattern).
  • Capture ho gaya lekin bank ne settle nahi kiya.
  • Partially refunded — 2 mein se 1 ticket cancel.
  • Failed, phir retry pe success.
Kya toota: Refund ke baad koi buggy retry job ne dobara isPaid = true set kar diya. System ne user ko ticket wapas de diya, jabki paisa refund ho chuka tha. Kyunki koi transition guard hi nahi tha — koi bhi field ko kuch bhi set kar sakta tha.
Solution

Enum + explicit allowed transitions

State machine ko code mein likho, developer ke dimaag mein nahi. Illegal transition exception throw kare, silently ignore na kare.

PaymentStatus.javaJava 17 · enum FSM
  1. public enum PaymentStatus {
  3. CREATED, AUTHORIZED, CAPTURED, SETTLED,
  4. FAILED, PARTIALLY_REFUNDED, REFUNDED, EXPIRED;
  6. private static final Map<PaymentStatus, Set<PaymentStatus>> ALLOWED = Map.of(
  7. CREATED, EnumSet.of(AUTHORIZED, FAILED, EXPIRED),
  8. AUTHORIZED, EnumSet.of(CAPTURED, FAILED, EXPIRED),
  9. CAPTURED, EnumSet.of(SETTLED, PARTIALLY_REFUNDED, REFUNDED),
  10. SETTLED, EnumSet.of(PARTIALLY_REFUNDED, REFUNDED),
  11. PARTIALLY_REFUNDED, EnumSet.of(PARTIALLY_REFUNDED, REFUNDED),
  12. FAILED, EnumSet.noneOf(PaymentStatus.class),
  13. REFUNDED, EnumSet.noneOf(PaymentStatus.class),
  14. EXPIRED, EnumSet.noneOf(PaymentStatus.class));
  16. public boolean canTransitionTo(PaymentStatus target) {
  17. return ALLOWED.getOrDefault(this, Set.of()).contains(target);
  18. }
  20. public boolean isTerminal() {
  21. return ALLOWED.getOrDefault(this, Set.of()).isEmpty();
  22. }
  23. }
  • 3–4Aath states, do groups mein: forward path (CREATED → SETTLED) aur exit paths (FAILED / refunds / EXPIRED).
  • 6Map<PaymentStatus, Set<PaymentStatus>> — adjacency list. FSM ka poora truth ek jagah, taaki naya developer 10 files na dhoonde.
  • 9Sabse important line. CAPTURED se aap wapas AUTHORIZED nahi jaa sakte. Retry job ab downgrade nahi kar payegi.
  • 11PARTIALLY_REFUNDED → PARTIALLY_REFUNDED allowed hai — self-loop, kyunki multiple partial refunds ho sakte hain.
  • 12–14Terminal states ka set khaali hai. FAILED ke baad kuch nahi — retry hoga toh naya payment row banega, purana update nahi hoga. Ye audit ke liye critical hai.
  • 16–18Guard method. Naam canTransitionTo hai — check() ya valid() nahi. Boolean method ka naam is/has/can se shuru hona chahiye.
  • 20–22isTerminal() derived hai, alag list nahi. Ek source of truth = do lists sync se bahar nahi ja sakti.
PaymentStateMachine.javatransition applier
  1. @Component

  4. private static final Logger log = LoggerFactory.getLogger(PaymentStateMachine.class);
  6. public void applyTransition(Payment payment,
  7. PaymentStatus targetStatus,
  8. String reasonCode) {
  10. PaymentStatus current = payment.getStatus();
  12. if (current == targetStatus) {
  13. log.info("Duplicate transition ignored paymentId={} state={}",
  14. payment.getId(), current);
  15. return; // idempotent no-op

  19. throw new IllegalStateTransitionException(current, targetStatus, payment.getId());

  27. }

  • 18–20Illegal transition pe loud failure. Silent ignore matlab paisa gum hone ka bug 3 mahine baad pata chalega.
  • 24Har transition audit trail mein jaati hai. RBI/PCI audit mein "ye payment REFUNDED kaise hua" ka jawab dena padta hai.

Entry 04

Idempotency — double charge rokna

HLDLLD

Ye payment system ka sabse zyada poocha jaane wala interview topic hai, aur production mein sabse mehnga bug bhi.

Problem

Ek intent, teen charges

Ek hi payment intent teen alag raaston se duplicate ban jaata hai:

  • User: Pay button do baar dabaya (button disable nahi tha, ya lagged).
  • Client: Mobile network timeout pe SDK ne auto-retry kiya. Server ne pehli request process kar li thi, sirf response gaya nahi.
  • PSP: Webhook at-least-once hota hai. Razorpay payment.captured 3 baar bhej sakta hai.
Timeline of a real incident:
10:04:01 user taps Pay → charge ₹1,200 ✓
10:04:09 response timeout, SDK retries
10:04:10 server dobara charge ₹1,200 ✓
10:04:11 user ko ek ticket, bank statement mein do debit
10:41 Twitter pe screenshot. Refund + support cost ≈ 40× transaction value.
Solution

Idempotency key + DB unique constraint

Client har logical operation ke liye ek UUID generate karta hai aur retry pe wahi UUID bhejta hai. Server us key ko unique index mein daalta hai — duplicate insert fail hoga, aur wahi hamari guarantee hai.

Zaroori baat: sirf key match karna kaafi nahi. Agar koi same key ke saath alag amount bhej de? Isliye request ka fingerprint hash bhi store karo.

IdempotencyService.javageneric guard
  1. @Service
  2. @RequiredArgsConstructor
  3. public class IdempotencyService {
  5. private final IdempotencyRecordRepository recordRepository;
  6. private final ObjectMapper objectMapper;
  8. @Transactional
  9. public <T> T executeExactlyOnce(String idempotencyKey,
  10. Object requestPayload,
  11. Class<T> responseType,
  12. Supplier<T> operation) {
  14. String fingerprint = buildRequestFingerprint(requestPayload);
  16. Optional<IdempotencyRecord> existing =
  17. recordRepository.findByIdempotencyKey(idempotencyKey);
  19. if (existing.isPresent()) {
  20. IdempotencyRecord record = existing.get();
  22. if (!record.getRequestFingerprint().equals(fingerprint)) {
  23. throw new IdempotencyKeyReusedException(idempotencyKey); // HTTP 422
  24. }
  25. if (record.getStatus() == RecordStatus.IN_PROGRESS) {
  26. throw new RequestInFlightException(idempotencyKey); // HTTP 409
  27. }
  28. return deserializeStoredResponse(record, responseType); // replay
  29. }
  31. IdempotencyRecord claim = recordRepository.saveAndFlush(
  32. IdempotencyRecord.inProgress(idempotencyKey, fingerprint));
  34. T result = operation.get();
  36. claim.completeWith(serialize(result));
  37. recordRepository.save(claim);
  38. return result;
  39. }
  41. private String buildRequestFingerprint(Object payload) {
  42. String canonicalJson = writeCanonicalJson(payload);
  43. return DigestUtils.sha256Hex(canonicalJson);
  44. }
  45. }
  • 9–12Generic method. Ye sirf payment ke liye nahi — refund, coupon redeem, kisi bhi mutating operation pe reuse hoga. Supplier<T> matlab asli kaam caller deta hai, ye class sirf guard hai.
  • 14Request ka SHA-256 hash. Same key + different body = attack ya bug. Dono case mein reject.
  • 22–23Key reuse pe 422, kyunki request semantically galat hai. Chup-chaap purana response return karna yahan khatarnak hoga.
  • 25–27IN_PROGRESS matlab pehli request abhi chal rahi hai. Client ko 409 do — "thoda ruk ke retry karo", naya charge mat banao.
  • 28Happy replay: stored response wapas. Client ko lagta hai request naye se chali, actually kuch naya nahi hua. Yahi "exactly-once" ka feel hai.
  • 31–32saveAndFlush — flush isliye taaki unique constraint abhi fire ho, transaction commit pe nahi. Race mein doosra thread yahin DataIntegrityViolationException khayega.
  • 34Asli operation. Dhyaan do — ye DB transaction ke andar hai. Agar operation ke andar PSP call hai toh us call ko @Transactional(propagation = NOT_SUPPORTED) ya alag async step mein rakhna hoga.
  • 41Canonical JSON — keys sorted, whitespace normalized. Warna field order badalne se hash badal jayega aur idempotency toot jayegi.

Entry 05

Coupon domain model aur discount calculation

LLD

Coupons ki asli complexity discount ka math nahi hai — rules ka combination hai. Aur ye rules har hafte badalte hain, isliye code ko rules ke liye khula rakhna padta hai.

Problem

if-else ka pahaad

CouponHelper.javaanti-pattern
  1. public double getDiscount(String code, double total, User u) {
  2. if (code.equals("FLAT100")) {
  3. if (total > 500) return 100;
  4. } else if (code.equals("SAVE20")) {
  5. if (u.isNew()) return total * 0.2; // cap kahan hai?
  6. } else if (code.startsWith("BANK_")) {
  7. // 40 more lines...
  8. }
  9. return 0; // silent failure
  10. }

Kya-kya galat hai:

  • double se paisa — 0.1 + 0.2 = 0.30000000000000004. Lakhon transactions pe ye paise leak karta hai.
  • Coupon codes code mein hardcoded. Naya coupon = deployment. Marketing team 2 din wait karegi.
  • Line 5 pe cap nahi hai. ₹50,000 ka order → ₹10,000 discount. Kisi ne socha hi nahi.
  • Line 9: coupon invalid ho toh ₹0 return. User ko pata hi nahi chalega ki coupon laga ya nahi — support ticket.
Kya toota: Ek e-commerce ne percentage coupon bina max-cap ke chhoda. Ek user ne ₹2.4 lakh ka order kiya, 25% off mila = ₹60,000. Terms mein "up to ₹500" likha tha, code mein nahi. Legally honour karna pada.
Solution

Data-driven rules + Strategy pattern

Coupon ek row hai, ek if branch nahi. Rules DB mein, calculation strategy code mein.

  1. public interface DiscountCalculator {
  2. DiscountType supportedType();

  6. @Component

  1. @Service
  2. public class CouponValidationChain {
  4. private final List<CouponRule> rules; // Spring sabhi @Component inject karega

Entry 06

Coupon over-redemption — the race condition

HLDLLD

Ye interview ka favourite trap hai. "1,000 coupons hain, 50,000 log ek saath try karte hain — ensure karo 1,001st na chale."

Problem

Read-then-write race

CouponService.javaanti-pattern
  1. Coupon c = couponRepository.findByCode(code); // T1 reads 999
  2. if (c.getCurrentRedemptionCount() < c.getTotalRedemptionLimit()) {
  3. c.setCurrentRedemptionCount(c.getCurrentRedemptionCount() + 1);
  4. couponRepository.save(c); // T1 writes 1000
  5. }

Do threads, timeline:

TimeThread AThread B
t0read count = 999—
t1—read count = 999
t2999 < 1000 ✓999 < 1000 ✓
t3write 1000write 1000
Result: Do redemptions hue, counter 1000 hi dikha raha hai. 50,000 concurrent users pe ye 1,000 ka limit aaram se 1,340 tak pahunch jaata hai. Har extra redemption = seedha paisa loss.

Aur in-memory counter use kiya toh 3 pods = 3× over-redemption, guaranteed.
Solution

Char options, trade-off ke saath

ApproachThroughputKab use karein
SELECT FOR UPDATEKam — sab serializeLimit chhoti, traffic kam
@Version optimisticTheek — contention pe retryNormal coupons
Conditional UPDATEHigh — 1 round tripDefault choice
Redis token pre-issueBahut highFlash sale, 2,000+ TPS

Best default — atomic conditional UPDATE. Check aur increment ek hi SQL statement mein, isliye race ki koi window hi nahi bachti.

CouponRepository.javaatomic reserve
  1. public interface CouponRepository extends JpaRepository<Coupon, Long> {
  3. @Modifying(clearAutomatically = true)
  4. @Query("""
  5. UPDATE Coupon c
  6. SET c.currentRedemptionCount = c.currentRedemptionCount + 1
  7. WHERE c.code = :code
  8. AND c.currentRedemptionCount < c.totalRedemptionLimit
  9. AND :now BETWEEN c.validFrom AND c.validUntil
  10. """)
  11. int reserveOneRedemption(@Param("code") String code,
  12. @Param("now") Instant now);
  13. }
  • 6Increment DB ke andar hota hai (count = count + 1), Java mein nahi. Java ne value padhi hi nahi, toh stale value ka sawaal hi nahi.
  • 8Ye line poora race khatam karti hai. Postgres row-level lock leta hai UPDATE ke liye; condition lock ke andar evaluate hoti hai. 1,000th ke baad koi row match hi nahi karegi.
  • 9Validity window bhi usi atomic statement mein. Warna validate aur reserve ke beech coupon expire ho sakta hai (TOCTOU bug).
  • 11Return type int = affected rows. 1 = mil gaya, 0 = khatam. Poora concurrency control is ek integer mein.

Entry 07

Booking aur payment ki consistency — Saga + Outbox

HLDLLD

Do alag databases, ek atomic outcome chahiye. 2PC production mein practical nahi — isliye saga.

Problem

Dual write ka gap

PaymentService.javaanti-pattern
  1. @Transactional
  2. public void capturePayment(String paymentId) {
  3. paymentRepository.markCaptured(paymentId); // DB commit
  4. kafkaTemplate.send("payment.captured", paymentId); // ← crash yahan?
  5. }

Line 3 aur line 4 ke beech pod restart ho gaya. Ab:

  • Payment DB: CAPTURED ✓
  • Kafka: koi event nahi ✗
  • Booking Service: kuch nahi pata, seat hold expire ho gaya
Result: User ka paisa kat gaya, seat kisi aur ko chali gayi. Ye dual-write problem hai. Ulta order (Kafka pehle, DB baad mein) bhi utna hi kharab hai — phantom event jiske peeche koi payment hi nahi.

2PC/XA se ho sakta hai theoretically, par Kafka + Postgres ke beech ye operationally nightmare hai: coordinator single point of failure ban jaata hai aur locks lambe hold hote hain.
Solution

Transactional outbox

Trick simple hai: event ko usi database mein, usi transaction mein likho. Ab dual write hai hi nahi — ek hi write hai. Ek separate relay process outbox se padh kar Kafka pe publish karta hai.

Entry 08

Webhooks aur reconciliation

HLDLLD

Payment ka result client se nahi aata. Wo PSP se async aata hai — aur agar wo bhi na aaye, toh reconciliation aakhri safety net hai.

Problem

Client redirect pe bharosa

Classic flow: user PSP page pe jaata hai, pay karta hai, PSP /payment/success pe redirect karta hai, hum booking confirm kar dete hain.

  • User ne pay kiya aur turant app kill kar diya → redirect kabhi nahi aayi. Paisa gaya, booking pending.
  • UPI mandate 40 second baad approve hua → user tab tak ja chuka.
  • Attacker ne khud /payment/success?orderId=BK4471 hit kar diya → free ticket.
Kya toota: Ek startup ne success redirect pe hi booking confirm ki, koi signature verification nahi. Kisi ne URL pattern samajh liya. Do din mein 2,300 free bookings. Ye theoretical nahi hai — ye India mein kai baar ho chuka hai.

Aur agar sirf webhook pe bharosa karein?

  • Webhook endpoint 5 minute down tha → PSP ne retry kiya, phir chhod diya.
  • PSP ka apna bug — event bheja hi nahi.
  • Bank ne settle kiya lekin PSP ne status update late kiya.
Solution

Teen layers: webhook → polling → reconciliation

  • Layer 1 — Webhook (seconds): primary path. Signature verify, dedupe, process.
  • Layer 2 — Polling (minutes): job jo CREATED/AUTHORIZED mein 5 min se zyada atke payments ko PSP se seedha poochta hai.
  • Layer 3 — Reconciliation (T+1): PSP ki settlement file vs hamara ledger vs bank statement. Three-way match.

Entry 09

Refunds, partial refunds aur coupon ka hisaab

LLD

Sabse zyada log yahan phaste hain. "₹1,000 ka order, ₹200 coupon, 2 tickets. Ek cancel kiya. Kitna refund?"

Problem

Discount kis ticket ka tha?

Order: 2 tickets × ₹500 = ₹1,000. Coupon SAVE200 = ₹200 off. Paid = ₹800.

User ek ticket cancel karta hai. Ab teen alag jawab possible hain:

LogicRefundKya galat hai
Full ticket price₹500Company loss — user ne ₹800 diye the, ₹500 wapas + ₹500 ka ticket = ₹200 free
Half of paid₹400Theek lagta hai, par unequal prices pe toot jaata hai
Proportional₹400Sahi — par isko line item level pe calculate karna padta hai
Aur bhi mushkil case: Tickets ₹800 + ₹200 = ₹1,000. Coupon ₹200. Agar ₹200 wala ticket cancel karein aur "half of paid" logic lagayein toh ₹400 refund — jabki us ticket ki actual value ₹160 thi (₹200 − ₹40 ka proportional discount). ₹240 ka direct loss, har aise order pe.

Aur coupon ka kya? Kya wo redemption wapas milegi? Agar full order cancel hua tab? Agar user ne coupon "use" kar liya toh kya wo dobara mil sakta hai?

Solution

Discount ko booking ke waqt hi allocate karo

Refund ke waqt calculate mat karo. Booking ke time har line item pe proportional discount allocate karke store kar do. Refund tab sirf lookup ban jaata hai.

DiscountAllocator.javalargest remainder method
  1. @Component
  2. public class DiscountAllocator {

  5. Money totalDiscount) {

  9. .sum();

  15. OrderLineItem item = lineItems.get(i);
  17. long share = totalDiscount.minorUnits()

  21. distributedMinor += share;
  22. }
  24. OrderLineItem lastItem = lineItems.get(lineItems.size() - 1);

  28. Money.ofMinor(remainderMinor, totalDiscount.currency()));

  31. }
  32. }

HLDLLD

Aakhri layer: paisa kaise store ho, data kaise batein, aur kya cheez aapke database mein kabhi nahi aani chahiye.

Problem

Teen classic blunders

Security checklist

  • Card data: kabhi mat chhuo. PSP-hosted checkout ya PSP SDK tokenization. Aapke DB mein sirf pspToken, last4, network. Isse PCI scope SAQ-D se SAQ-A aa jaata hai — audit cost 90% kam.
  • CVV: authorization ke baad store karna prohibited hai. Encrypted bhi nahi. Ye negotiable nahi hai.
  • Coupon endpoint: per-user 10/min aur per-IP 30/min rate limit. Failed attempts pe exponential backoff. Coupon codes 8+ chars with checksum digit — random guess pe checksum hi fail ho jayega, DB hit hi nahi hoga.
  • Enumeration: "coupon exists but not eligible" aur "coupon doesn't exist" ka same generic message user ko dikhao, alag reason code sirf internal logs mein.
  • Secrets: PSP keys vault mein, env vars mein nahi. Quarterly rotation.
  • Audit log: har state transition, har manual refund, har coupon config change — kisne, kab, kyun. Append-only.
Ek line mein: aap payment system nahi bana rahe — aap ek ledger bana rahe ho jo galti se paisa move karta hai. Sochne ka ye angle badalne se design ke saare decisions clear ho jaate hain.

Mock interview questions

Pehle khud jawab socho, phir kholo. Jawab wahi format mein hain jo aap actually bolenge — pehle direct answer, phir trade-off.

Q11,000 coupons hain aur 50,000 log ek saath try kar rahe hain. 1,001st redemption kaise rokoge?

Short answer: Atomic conditional UPDATE — check aur increment ek hi SQL statement mein, taaki read-then-write ki window bache hi na.

UPDATE coupon SET count = count + 1 WHERE code = ? AND count < limit — affected rows 1 matlab mila, 0 matlab khatam.

Trade-off jo aage bolna hai: ye ek hot row banati hai. 50,000 concurrent pe Postgres us row pe serialize karega — throughput ~500-1,000 TPS tak seemit. Isse aage flash sale ke liye Redis mein tokens pre-load karo aur LPOP se atomically nikaalo, phir async DB mein persist karo.

Jo galat hai: in-memory counter (pods ke beech nahi chalta), aur SELECT phir UPDATE (classic race).

Q2User ne Pay do baar dabaya. Do charges kaise rokoge?

Short answer: Idempotency key + database unique constraint. Client ek UUID generate karta hai, retry pe wahi UUID bhejta hai. Server us key ko unique index wali table mein insert karta hai — duplicate insert fail hoga aur hum stored response replay kar denge.

Jo detail interviewer dhoondh raha hai: guarantee DB unique index se aati hai, application ke if check se nahi. Do threads dono findByKey pe empty pa sakte hain — sirf DB constraint hi ek ko rokega.

Bonus: request ka fingerprint hash bhi store karo. Same key + different amount = 422. Aur IN_PROGRESS state pe 409 do, taaki concurrent duplicate wait kare.

Q3Payment success ho gaya lekin booking DB down hai. Kya karoge?

Short answer: Payment ka result apne DB mein commit karo aur usi transaction mein outbox event likho. Booking confirmation async hoti hai — jab booking DB wapas aayegi, event consume ho jayega.

Kyun outbox: "DB likho phir Kafka bhejo" dual write hai — beech mein crash = event kho gaya. Outbox se sirf ek write hai (same DB, same transaction), aur relay worker baad mein publish karta hai.

Agar booking permanently fail ho jaye (seat kisi aur ko chali gayi): saga compensation chalao — auto-refund initiate karo, user ko notify karo. Isliye capture ko saga ke aakhir mein rakhte hain.

Q4PSP webhook teen baar bhejta hai. Handle kaise karoge?

Short answer: Teen layers — (1) PSP ka eventId unique index wali table mein insert, duplicate pe 200 return karke drop; (2) state machine mein same-state transition ko no-op banao; (3) business handler khud idempotent ho.

Important: duplicate pe error nahi, 200 OK do. Error doge toh PSP aur retry karega — retry storm.

Aur: signature verify karne se pehle kuch bhi mat karo. Raw body string pe HMAC compute karo, parsed DTO pe nahi — re-serialization se signature toot jaayegi.

Q5₹1,000 ka order, ₹200 coupon, 2 tickets. Ek cancel hua. Refund kitna?

Short answer: ₹400. Formula: item amount − us item ko allocated discount = ₹500 − ₹100 = ₹400.

Asli insight: discount ko refund ke waqt calculate mat karo. Booking ke waqt proportionally allocate karke har line item pe store kar do. Refund tab sirf lookup hai, calculation nahi.

Rounding: ₹200 ko teen items mein baato → ₹66.66 × 3 = ₹199.98. Do paise gum. Isliye aakhri item ko remainder do, apna share nahi — total hamesha exact match karega.

Coupon wapas? Sirf full cancel pe. Partial pe nahi — warna user 1 ticket cancel karke coupon reclaim kar lega aur dobara use karega.

Q6Payment amount ke liye kaunsa data type? Kyun?

Short answer: long in minor units (paise/cents). ₹100 = 10000. Java mein BigDecimal bhi chalega, par long tez hai aur rounding ka sawaal hi nahi uthta.

Kabhi nahi: float ya double. 0.1 + 0.2 = 0.30000000000000004. Millions of transactions pe ye reconciliation mismatch hai.

DB mein: BIGINT, ya NUMERIC(19,4) agar exchange rates jaisi sub-paisa precision chahiye. Kabhi FLOAT/DOUBLE PRECISION nahi.

Aur: currency hamesha amount ke saath rakho — ek Money value object mein. Naked long ghoomega toh ek din INR aur USD add ho jayenge.

Q72PC kyun nahi use karte booking aur payment ke beech?

Short answer: 2PC ko coordinator chahiye jo single point of failure hai, aur prepare–commit ke beech resources locked rehte hain. Payment mein wo phase seconds ka ho sakta hai (PSP call), toh 600 TPS pe locks pile up ho jaate hain.

Practical reason: aapka PSP 2PC support hi nahi karta. Razorpay "prepare" phase mein join nahi karega. External system pe rollback hai hi nahi — sirf compensation hai (refund).

Isliye: Saga. Har step ka apna compensating action. Trade-off — beech mein system temporarily inconsistent dikhega (payment done, booking pending). Isko UI mein honestly dikhao: "Confirming your booking…"

Q8Coupon validate API pe 2,400 TPS aa raha hai. Postgres bacha kaise?

Short answer: Read aur write path alag karo. Validation (read-heavy) Redis se — coupon config cache karo 60s TTL ke saath. Reservation (write) hi Postgres tak jaaye.

Ratio: 2,400 validate vs 600 reserve. Matlab 75% traffic DB tak pahunchna hi nahi chahiye.

Stale cache ka kya? Chalega — validation sirf UX hai. Asli correctness atomic reserve se aati hai. Cache "available" bole aur reserve 0 rows de, toh user ko "coupon just ran out" dikhao. Ye acceptable hai; over-redemption acceptable nahi.

Aur: coupon codes pe checksum digit rakho — invalid code cache aur DB dono ko touch kiye bina reject ho jayega.

Q9Ek user ne coupon reserve kiya aur payment page pe hi chhod diya. Coupon?

Short answer: Reservation ka TTL hota hai (typically 10 min, seat hold se thoda zyada). Ek background job expired reservations ko release karke count wapas kar deta hai.

Isliye hum reserveCouponForOrder bolte hain, redeemCoupon nahi. Reserve → payment success → confirm. Reserve → timeout → release. Do alag lifecycle events.

Edge case: job release kar de aur usi waqt payment success ho jaye. Isliye release bhi conditional hona chahiye — WHERE status = 'RESERVED'. Confirm ho chuka hai toh release 0 rows karega, aur wahi sahi hai.

Q10Card details kahan store karoge?

Short answer: Kahin nahi. PSP-hosted checkout ya PSP SDK tokenization use karo. Aapke DB mein sirf pspToken, last4, cardNetwork, expiryMonth/Year.

CVV: authorization ke baad store karna PCI-DSS mein explicitly prohibited hai — encrypted ho tab bhi.

Business reason jo bolna chahiye: agar card data aapke system se guzarta hai toh aap SAQ-D scope mein aate ho — annual audit, network segmentation, quarterly scans. PSP tokenization se SAQ-A mein rehte ho. Ye lakhon ka farq hai, sirf security ka nahi.

Q11Reconciliation kya hai aur kyun chahiye jab webhooks hain hi?

Short answer: Reconciliation T+1 pe PSP ki settlement file ko hamare ledger aur bank statement se match karta hai. Webhooks best-effort hain — endpoint down tha, PSP ne retries chhod diye, ya PSP ka apna bug tha.

Char outcomes: matched ✓; PSP mein hai hamare mein nahi (P1 — user ka paisa gaya, record nahi); hamare mein hai PSP mein nahi (humne galti se capture maana, ya settlement late); amount mismatch (fee/FX/partial capture).

Yahi maturity signal hai: aap maan rahe ho ki distributed system galtiyan karega, aur unhe pakadne ka mechanism hai. Har payment company mein ye hota hai, aur mismatch rate kabhi zero nahi hoti.

Q12Coupon "25% off" hai. Cap kaise lagaoge aur negative amount kaise rokoge?

Short answer: Do guards, dono zaroori:

  • Math.min(rawDiscount, coupon.maxDiscountMinor) — business cap
  • Math.min(capped, orderAmount) — safety cap, taaki payable kabhi negative na ho

Schema level pe: max_discount_minor ko NOT NULL banao. Nullable rakhoge toh ek din koi coupon bina cap ke create ho jayega.

Kyun dono: pehla business rule hai, doosra invariant. ₹100 order pe ₹500 flat coupon — cap toh pass ho jayega, par payable −₹400 ban jayega. Kuch systems us par refund issue kar dete hain. Ye actual exploit hai.

Q13Payment status ke liye enum kyun, boolean kyun nahi?

Short answer: Payment ke kam se kam 8 distinct states hain: CREATED, AUTHORIZED, CAPTURED, SETTLED, FAILED, PARTIALLY_REFUNDED, REFUNDED, EXPIRED. Boolean inme se 6 express hi nahi kar sakta.

Asli fayda: enum ke saath allowed transitions define kar sakte ho. CAPTURED se AUTHORIZED wapas jaana illegal hai — guard method exception throw karega. Boolean ke saath koi bhi kuch bhi set kar sakta hai.

Auth vs capture ka farq: authorize = paisa hold, capture = paisa actually liya. Hotels/rentals authorize karke baad mein capture karte hain. Ek boolean mein ye do-step flow fit hi nahi hota.

Q14Ek user script chala kar 500 coupons redeem kar raha hai. Kaise rokoge?

Layer 1 — DB constraint: unique index on (user_id, coupon_id). Ye asli enforcement hai, application check nahi.

Layer 2 — per-user limit: coupon config mein perUserRedemptionLimit, validation chain mein check.

Layer 3 — rate limit: per-user 10/min, per-IP 30/min. Failed attempts pe exponential backoff.

Layer 4 — velocity rules: naya account + high-value coupon + naya device = manual review. Multiple accounts, ek hi device fingerprint ya payment instrument = block.

Ye bolna important hai: ye ek fraud problem hai, sirf engineering problem nahi. Aap loss ko zero nahi kar sakte — acceptable level tak la sakte ho. Detection ke liye async fraud service rakho jo payment path ko slow na kare.
