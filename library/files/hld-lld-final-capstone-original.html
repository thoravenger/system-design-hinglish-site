🔒 Thread-safe LRU Without Coarse Locks

Problem: Single global lock high QPS pe bottleneck. Contention 1/N karna hai.

Solution: Segmented LRU (Striping) — N segments, har segment ka apna lock + apna LRU. Key hash se segment choose karo.

SegmentedLRU.javaJAVA
class SegmentedLRU<K, V> {
    private static final int SEGMENTS = 16;      // power of 2
    private final Segment<K, V>[] segments;

    @SuppressWarnings("unchecked")
    public SegmentedLRU(int totalCapacity) {
        int perSeg = Math.max(1, totalCapacity / SEGMENTS);
        segments = new Segment[SEGMENTS];
        for (int i = 0; i < SEGMENTS; i++) {
            segments[i] = new Segment<>(perSeg);
        }
    }

    private Segment<K, V> segmentFor(K key) {
        int h = key.hashCode();
        h ^= (h >>> 16);                        // spread bits
        return segments[h & (SEGMENTS - 1)];  // mask for power of 2
    }

    public V get(K key) {
        return segmentFor(key).get(key);
    }

    public void put(K key, V value) {
        segmentFor(key).put(key, value);
    }

    static class Segment<K, V> {
        private final int cap;
        private final Map<K, Node<K,V>> map = new HashMap<>();
        private final Node<K,V> head = new Node<>(null, null);
        private final Node<K,V> tail = new Node<>(null, null);
        private final ReentrantLock lock = new ReentrantLock();

        Segment(int cap) {
            this.cap = cap;
            head.next = tail; tail.prev = head;
        }

        V get(K key) {
            lock.lock();
            try {
                Node<K,V> n = map.get(key);
                if (n == null) return null;
                moveToFront(n);
                return n.v;
            } finally { lock.unlock(); }
        }

        void put(K key, V value) {
            lock.lock();
            try {
                Node<K,V> n = map.get(key);
                if (n != null) { n.v = value; moveToFront(n); return; }
                if (map.size() == cap) {
                    Node<K,V> lru = tail.prev;
                    unlink(lru); map.remove(lru.k);
                }
                Node<K,V> nn = new Node<>(key, value);
                map.put(key, nn); addFirst(nn);
            } finally { lock.unlock(); }
        }

        private void moveToFront(Node<K,V> n) { unlink(n); addFirst(n); }
        private void addFirst(Node<K,V> n) {
            n.next = head.next; n.prev = head;
            head.next.prev = n; head.next = n;
        }
        private void unlink(Node<K,V> n) {
            n.prev.next = n.next; n.next.prev = n.prev;
        }
    }

    static class Node<K,V> {
        K k; V v; Node<K,V> prev, next;
        Node(K k, V v) { this.k = k; this.v = v; }
    }
}
LineExplanation
SEGMENTS = 16Power of 2 — mask se modulo fast. 16 threads tak contention 1/16.
totalCapacity / SEGMENTSCapacity per segment. Total capacity divide hota — LRU global nahi, per-segment.
h ^= (h >>> 16)Bit spread. Java HashMap ka trick — upper bits lower mein mix karo, poor distribution avoid.
h & (SEGMENTS - 1)Mask = fast modulo. Power of 2 hone se AND operation kaam karta hai.
ReentrantLock per segmentLock striping. Har segment independent. 16 threads parallel.
hashCode()Key ka hashCode call. Null key ke liye caller responsible (ya Optional wrapper).
🔑 Key Answer

Trade-off: Exact global LRU accuracy vs throughput. Segmented = approximate LRU, but 16x throughput. Production: Caffeine — W-TinyLFU eviction (better hit ratio than LRU), lock-free reads (ring buffer), concurrent writes. Best of both.

Alternatives: ConcurrentHashMap + per-node locks (complex, deadlock-prone), read-buffer approach (Caffeine-style).

🔐 Concurrent Transfer — Global Lock Ordering

Deadlock scenario: Thread-1 A→B lock karta (A then B), Thread-2 B→A lock karta (B then A). Circular wait = deadlock.

Fix: Hamesha consistent order — accountId ke natural order se chhota pehle.

TransferService.java — Lock OrderingJAVA
void transfer(Account from, Account to, BigDecimal amt) {
    // Deterministic order: chhota ID pehle, bada baad mein
    Account first  = from.id().compareTo(to.id()) < 0 ? from : to;
    Account second = from.id().compareTo(to.id()) < 0 ? to   : from;

    synchronized (first) {
        synchronized (second) {
            // Double-check after acquiring locks (funds race)
            if (from.balance().compareTo(amt) < 0)
                throw new InsufficientFundsException();
            from.debit(amt);
            to.credit(amt);
            ledger.save(Ledger.doubleEntry(from, to, amt));
        }
    }
}
LineExplanation
first / second decideDeterministic order. Dono threads A→B aur B→A ke liye same order follow karenge — circular wait impossible.
synchronized (first)Pehla lock. Chhota ID.
synchronized (second)Dusra lock. Bada ID.
Double-check balanceLocks ke baad. Warna check aur debit ke beech race — dusra thread balance khaali kar sakta.
ledger.saveDouble-entry immutable ledger.
🔑 Key Answer

Global lock ordering: Har thread same order mein locks leta hai. Chhota ID pehle. DB mein bhi: SELECT ... FOR UPDATE ORDER BY id — DB khud order maintain karega, row locks bhi deterministic.

Alternatives: Distributed lock with timeout (Redis/etcd), single-writer per aggregate (saga/event-driven), optimistic concurrency (version column/CAS).

🏆 Top-K Merchants by Total Spend

TopKMerchants.javaJAVA
record Tx(String merchant, BigDecimal amount) {}

List<String> topK(Stream<Tx> stream, int k) {
    // Step 1: aggregate per merchant — O(n)
    Map<String, BigDecimal> totals = stream.collect(
        Collectors.groupingBy(Tx::merchant,
            Collectors.reducing(BigDecimal.ZERO,
                                Tx::amount, BigDecimal::add)));

    // Step 2: min-heap of size k — O(m log k), m = distinct merchants
    PriorityQueue<Map.Entry<String, BigDecimal>> heap =
        new PriorityQueue<>(Comparator.comparing(Map.Entry::getValue));

    for (var e : totals.entrySet()) {
        heap.offer(e);
        if (heap.size() > k) heap.poll();       // smallest out
    }

    // Step 3: extract descending
    List<String> out = new ArrayList<>();
    while (!heap.isEmpty()) out.add(heap.poll().getKey());
    Collections.reverse(out);
    return out;
}
LineExplanation
groupingBy(merchant, reducing(...))Aggregate. Per merchant total. BigDecimal reducing, sum() nahi (primitive only).
PriorityQueue(comparing(value))Min-heap. Sabse chhota value top pe. Size k se zyada nahi hone dena.
heap.offer(e); if(size>k) poll()Top-K trick. K se zyada hone pe sabse chhota nikaal do — final mein top K best bachenge.
Collections.reverse(out)Min-heap se nikalte waqt ascending aata — reverse karo descending ke liye.
🔑 Key Answer

Complexity: O(n + m log k) where n = transactions, m = distinct merchants. Naive sort O(m log m) se better jab k << m. Alternative: Full sort O(m log m) — simpler, jab m chhota ho.

🧹 Normalize + Dedup Account IDs

NormalizeDedup.javaJAVA
List<String> normalize(List<String> raw) {
    if (raw == null) return List.of();
    return raw.stream()
              .filter(Objects::nonNull)
              .map(String::trim)
              .filter(s -> !s.isEmpty())
              .map(s -> s.toUpperCase(Locale.ROOT))
              .distinct()
              .collect(Collectors.toList());
}

// Order preserve karna ho:
Set<String> out = new LinkedHashSet<>();
for (String s : raw) {
    if (s == null) continue;
    String n = s.trim().toUpperCase(Locale.ROOT);
    if (!n.isEmpty()) out.add(n);
}
LineExplanation
Objects::nonNullNull skip. NPE avoid, empty string bhi handle.
String::trimLeading/trailing whitespace hatao.
!s.isEmpty()Trim ke baad khaali strings bhi out.
toUpperCase(Locale.ROOT)Locale.ROOT important. Turkish "i" → "İ" problem avoid. Default locale unpredictable.
distinct()Stream ka dedup. Internal LinkedHashSet use karta — order preserve.

🔤 Group Anagram Reference IDs

AnagramGroups.javaJAVA
List<List<String>> groupAnagrams(List<String> ids) {
    Map<String, List<String>> map = new LinkedHashMap<>();
    for (String s : ids) {
        char[] c = s.toCharArray();
        Arrays.sort(c);
        String key = new String(c);    // sorted chars = canonical
        map.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(map.values());
}
LineExplanation
toCharArray()String → char array. String immutable, array mutable.
Arrays.sort(c)Sort chars. "eat" and "tea" → both "aet". Same canonical form.
new String(c)Array → String. Yeh key ban jaati hai.
computeIfAbsent(...).add(s)Group mein add. List lazy create.
🔑 Key Answer

Complexity: O(n · L log L) where n = number of IDs, L = avg length. Alternative: Character frequency count as key — O(n · L) but longer key.

🌳 Data Structures Decision Guide

Question: Kaunsa data structure use karoon? 1. Key-value lookup chahiye? → Haan → HashMap (unordered) / LinkedHashMap (insertion order) / TreeMap (sorted) → Nahi → Next 2. Ordered sequence + random access? → Haan → ArrayList (fast get/iterate) → Nahi → Next 3. Frequent insert/remove at ends? → ArrayDeque (stack + queue, no null) → LinkedList (agar node reference available ho) 4. Sorted keys + range queries? → TreeMap / TreeSet (O(log n)) 5. Priority / min-max nikalna? → PriorityQueue (min-heap by default, max-heap via comparator reverseOrder) 6. Dedup only? → HashSet (fast) / TreeSet (sorted) / LinkedHashSet (insertion order) 7. Thread-safe concurrent access? → ConcurrentHashMap (better than Collections.synchronizedMap) → CopyOnWriteArrayList (read-heavy, write-rare) → BlockingQueue (producer-consumer) 8. Top-K / Kth largest? → Min-heap of size K (not full sort) 9. Sliding window? → Deque + running sum (bucket approach) 10. LRU? → HashMap + doubly linked list (or LinkedHashMap with accessOrder)

🔑 Key Answer

Cache invalidation = 2 hard problems. Common patterns:

  • TTL: Simplest, eventual staleness accepted. Different TTLs per entity.
  • Event-driven invalidation: DB write → event → cache delete. Fresh, complex.
  • Versioned keys: Cache key includes version. Update = new key. No stale reads.
  • Stampede prevention: Lock on miss (only one thread fetches), OR probabilistic early expiry.

⭐ STAR Framework — Behavioural Questions

S — Situation: Context do. Kahan, kab, kaun involved tha. 20-30 seconds.

T — Task: Tumhara specific role/responsibility. Kya deliver karna tha, kya constraints the. 20-30 seconds.

A — Action: Sabse important. Kya steps liye, kyun, kisne kya kiya. "We" se "I" pe focus. 60-90 seconds.

R — Result: Outcome, metrics, learnings. Quantify karo jahan possible. 30-40 seconds.

🔑 Key Answer

Common behavioural prompts aur kaise approach karo:

  • "Major incident prevent kiya?" — Signals (latency spike, error rate), Action (war room, rollback, mitigation), Outcome (no data loss, post-mortem, runbook update).
  • "Compliance vs delivery timeline conflict?" — Early engagement, risk-based prioritization, phased delivery, escalate clearly documented.
  • "Feature rollback during trading hours?" — Decision criteria (wrong orders, data corruption), feature flag kill switch, communicate, preserve state, audit.
  • "Engineering quality raise kiya regulated env mein?" — Testing gates, code review, CI/CD automation, observability, DORA metrics, blameless post-mortems.

Tip: 2-3 strong STAR stories taiyaar rakho jo multiple questions pe adapt ho jaayein.

🚫 Anti-Patterns — Yeh Mat Karo

1 Distributed Monolith
Microservices ka naam, monolith ka coupling. Saare services ek dusre pe synchronous depend. Ek fail = sab fail. Fix: Bounded contexts, async events, circuit breakers.
2 Shared Database
Multiple services ek hi DB. Schema changes coordinated, coupling tight. Fix: Database per service, API contracts.
3 Synchronous Chain
A→B→C→D saara sync. Latency sum, ek bhi slow = sab slow. Fix: Async where possible, parallel calls, timeout + circuit breaker.
4 Chatty Communication
1000 chhote HTTP calls instead of batch. Network overhead killer. Fix: Batch, gRPC streaming, GraphQL aggregation.
5 Unbounded Everything
Queue, cache, thread pool — sab unbounded. OOM ya cascade. Fix: Bounded + backpressure.
6 Retry Without Backoff
Fail pe turant retry = thundering herd. Downstream maar deta. Fix: Exponential backoff + jitter + circuit breaker.
7 Global Locks
Ek synchronized method se poori service bottleneck. Fix: Lock striping, per-resource locks, optimistic concurrency.
8 No Idempotency
Retry pe duplicate charge/order. Network retry default hai. Fix: Idempotency key + unique constraint.
9 Cache Without Invalidation
Stale data forever. Bug reports "why is old value showing". Fix: TTL + event-driven invalidation + versioned keys.
10 Double-Write
DB write + Kafka publish separately. Ek succeed, dusra fail = inconsistency. Fix: Outbox pattern.
11 Deep Coupling to Vendor
Cloud provider specific APIs har jagah. Migrate impossible. Fix: Abstraction layer, standard protocols (S3 API, SQL).
12 Premature Optimization
Cache + shard + queue jab tak chahiye nahi. Complexity premature. Fix: Measure first, optimize bottleneck. YAGNI.
