1

CPU core aur context switching

Layer: CPU aur thread pool. Example: User profile service, photo resize.

Ek CPU core ek time pe sirf ek thread chala sakta hai. 8 cores matlab ek saath sirf 8 threads ka asli kaam. Baaki threads ya to I/O (DB, network) ka wait kar rahe hote hain, ya CPU ki line me khade hote hain.

✗ Problem

Request thread me hi heavy photo resize

User profile photo upload karta hai aur hum usi Tomcat thread me photo ko 512px me resize karte hain. Resize pura CPU ka kaam hai, lagbhag 300 ms CPU. Server me 8 cores hain, lekin upload spike me 200 threads ek saath resize shuru kar dete hain.

OS har kuch milliseconds me running thread badalta hai (context switching): ek thread ki state save, doosre ki load, aur CPU cache ka fayda bhi kam. Runnable threads jitne zyada, utna CPU switching me waste. CPU 100% dikhta hai, lekin kaam kam hota hai.

Symptoms: CPU 90–100%, tomcat.threads.busy max ke paas, thread dump me zyada tar -exec- threads RUNNABLE aur stack me resize code. Halke APIs (GET profile) bhi slow, kyunki unhe thread hi nahi milta.

  1. Resize Tomcat worker thread pe hi chal raha hai. 200 uploads aaye to 200 threads 8 cores ke liye ladenge, har thread ko thoda-thoda CPU milega aur sab slow honge.
  2. Save bhi isi thread me. Jab tak resize aur save khatam nahi, ye thread doosri request nahi utha sakta.
  3. User ko jawab resize ke baad hi milta hai. CPU full ho to app ka upload spinner 10–20 sec ghoomta rehta hai.
✓ Solution

CPU kaam ko cores jitne workers tak limit karo

CPU-heavy kaam ke liye alag, chhota pool banao jiska size cores ke barabar ho. Tomcat thread sirf upload accept kare aur turant 202 Accepted lautaye. Resize background workers karein. Ab ek time pe maximum 8 resize chalenge, switching kam, aur Tomcat threads baaki requests ke liye free.

CPU-bound pool ≈ cores Mixed (CPU + wait) ≈ cores × (1 + wait time ÷ CPU time) Example 8 × (1 + 450 ms ÷ 50 ms) = 80 threads
  1. @Async annotation tabhi kaam karta hai jab ye switch on ho.
  2. JVM ko jitne cores dikhte hain. Docker/Kubernetes me ye container ki CPU limit follow karta hai, machine ke total cores nahi.
  3. Core aur max dono = cores. Queue bharne pe bhi extra threads nahi banenge, isliye CPU pe kabhi cores se zyada resize nahi chalenge.
  4. Bounded queue. Har queued task photo ke bytes memory me pakde rakhta hai, isliye chhoti rakho (50 × 5 MB = 250 MB).
  5. Thread dump aur logs me turant dikhega ki kaunsa pool CPU kha raha hai.
  6. Queue full ho to naya task reject hota hai aur caller ko TaskRejectedException milta hai. Controller usko 429 me badlega.
  1. Ye method photo-cpu pool ke thread pe chalega, Tomcat thread pe nahi. Call doosre bean (controller) se honi chahiye; same class ke andar se call karne pe @Async bypass ho jata hai.
  2. Resize ke waqt ab koi Tomcat thread block nahi.
  3. Sirf task queue me gaya, call milliseconds me return.
  4. 202 Accepted matlab "request mil gayi, processing chal rahi hai". App thodi der baad photo URL refresh kare.
  5. Overload me imaandari: 429 Too Many Requests. Client thodi der baad retry kare, server ka CPU nahi pisega.

Kab apply karein

  • Kaam CPU-heavy hai: image, PDF, encryption, bada JSON.
  • User ko result isi response me nahi chahiye.

Kab ignore karein

  • CPU kaam chhota hai (10–20 ms): alag pool aur async ka overhead zyada.
  • User ko result turant chahiye: sync rakho, lekin Semaphore se concurrency cores tak limit karo.

Dhyan rakho

  • @Async ki queue memory me hai, restart pe jobs gayab. Zaroori jobs ke liye Kafka/RabbitMQ ya DB outbox.
  • CallerRunsPolicy: task nahi khota, lekin overload me Tomcat thread khud resize karega. AbortPolicy + 429: fast failure, client retry kare.

Tomcat thread vs connection: 8192 ka sach

Layer: Tomcat NIO connector. Example: Order service at 600 req/s.

Tomcat NIO me acceptor thread naye connections leta hai, poller thread dekhta hai kis connection pe data aaya, aur worker thread (http-nio-8080-exec-N) aapka controller chalata hai. Connection kursi hai, worker thread counter.

✗ Problem

Threads aur connections badhaye, app aur slow ho gaya

Order API pe 600 req/s aa rahi hain aur har request 500 ms leti hai. Team ne socha "max-connections 8192 hai, sab handle ho jayega". Slow hua to threads 1000 kar diye.

Throughput = threads ÷ response time 200 ÷ 0.5 s = 400 req/s (aa rahi 600) Har second +200 requests line me 10 sec baad ~2000 waiting, nayi request ~5 sec wait

Threads 1000 karne se kya hua? Har platform thread ke liye ~1 MB stack reserve hota hai, CPU pe 1000 threads ladne lage, aur sab 10 connection wale HikariCP pool pe toot pade. Wait Tomcat se hat ke DB pool pe shift ho gaya.

Symptoms: tomcat.threads.busy = max, response time lagataar badhta hua, load balancer pe 504 timeouts.

  1. Threads kaam nahi karte, CPU aur DB karte hain. Bottleneck CPU ya DB pool hai to 1000 threads bas line lambi karenge.
  2. Zyada connections matlab zyada log andar baith ke wait kar sakte hain. Jawab tez nahi hota.
  3. Bada accept queue matlab overload me client ko jaldi "busy" signal nahi milta. Load balancer doosre instance pe bhej sakta tha, lekin request yahin sadti rahi.
✓ Solution

Pehle hisaab, phir measure, phir tune

Asli fix response time kam karna hai (Topics 3–6). Threads utne hi rakho jitne CPU aur DB pool sambhal saken. Queue chhoti rakho taaki overload me request jaldi fail ho aur load balancer usse healthy instance pe bheje. Capacity ka hisaab code me likho, taaki har release pe dobara check ho.

200 threads pe 600 req/s chahiye: max response time = 200 ÷ 600 = 0.33 s Ya instances: 600 × 1.3 ÷ 160 = 5 instances (160 req/s = 8 cores ÷ 50 ms CPU per request)
  1. 200 default hai. Badhao tabhi jab CPU 70% se kam ho aur DB/HTTP pools me pending na ho.
  2. Idle me bhi 20 threads zinda. Spike pe naye thread banane ki der nahi.
  3. 8192 connections bharne ke baad OS ki queue me sirf 100. Uske baad connection refuse, jo overload me behtar signal hai.
  4. Iske bina Actuator me tomcat.threads.* metrics nahi aate.
  5. /actuator/metrics expose hota hai. Production me isko Spring Security se protect karo.
  1. Duration ko seconds me badla: 500 ms matlab 0.5.
  2. Ek thread 1 sec me 1 ÷ 0.5 = 2 requests nipta sakta hai. 200 threads matlab 400.
  3. Ulta sawaal: 600 req/s chahiye to ek request zyada se zyada kitni der le sakti hai? 333 ms.
  4. 30% headroom: traffic spikes, deploy ke waqt ek instance kam, GC pauses.
  5. Hamesha upar round karo. 4.875 instance nahi hota, 5 chahiye.

Threads kab badhayein

  • Kaam zyada tar I/O wait hai (DB, REST) aur CPU 60–70% se kam.
  • Hikari aur HTTP pools me pending 0 hai.

Kab ignore karein

  • CPU pehle se high hai.
  • hikaricp.connections.pending 0 se upar hai. Threads badhane se wait bas aage shift hoga.

Dhyan rakho

  • Chhota accept-count tabhi achha jab multiple instances + load balancer ho. Single instance pe thoda wait reject se behtar ho sakta hai.
  • Har platform thread ~1 MB stack aur scheduling cost laata hai.
3

HikariCP: connection pool ka jam

Layer: JDBC connection pool. Example: Order service.

DB connection banana mehenga hai: TCP, authentication, session setup. HikariCP pehle se bane connections pool me rakhta hai. Thread connection udhaar leta hai aur kaam ke baad lautata hai. Spring Boot ka default pool maximum 10 connections ka hai.

✗ Problem

200 threads, 10 connections, aur 30 sec ka intezaar

Tomcat ke jitne threads DB touch karte hain, sab inhi 10 connections ke liye line lagate hain. Koi thread connection lekar dheere kaam kare (slow query, lambi transaction, ya connection pakad ke REST call) to baaki threads 30 sec (default connectionTimeout) tak wait karte hain, phir ye error:

Team ne pool 100 kar diya. Ab database hafne laga: 4 instances × 100 = 400 connections, jabki PostgreSQL ka default max_connections 100 hai. Zyada connections matlab DB pe zyada parallel queries, locks aur DB side context switching.

Symptoms: hikaricp.connections.pending lagataar 0 se upar, hikaricp.connections.usage bahut high, logs me SQLTransientConnectionException.

  1. DB ke cores aur disk limited hain. Instances × pool size = DB pe total connections. Pool bada karke bottleneck DB pe shift ho jata hai.
  2. 30 sec tak Tomcat thread block. User tab tak app band kar chuka hoga aur thread bekaar pakda raha.
  3. Open Session In View: pehli query ke baad connection web request ke end tak (REST call aur JSON banne tak) pakda reh sakta hai. Spring Boot startup pe iski warning bhi deta hai.
✓ Solution

Chhota pool, kam holding time, fail fast

Pool size DB ki capacity se decide hota hai, app threads se nahi. HikariCP wiki ka starting formula: (DB cores × 2) + effective disks. 4-core DB pe lagbhag 10. Phir measure karo. connection-timeout chhota rakho, open-in-view band karo, aur leak detection on karo taaki jo code connection wapas nahi karta uska stack trace mile.

Pool size (start) = (DB cores × 2) + effective disks 4-core DB, SSD ≈ (4 × 2) + 1 = 9, round karke 10 Total connections = instances × pool size ≤ DB max_connections
  1. Multiple datasources ho to logs me turant dikhega kaunsa pool atka.
  2. Chhota pool jisme threads thoda wait karein, us bade pool se behtar hai jo DB ko thrash kare.
  3. Overload me 3 sec baad error. Thread free, load balancer ya client retry kar sakta hai.
  4. Default 30 min hai. DB, proxy ya firewall us se pehle connection kaat-te hon to isko thoda kam rakho, taaki Hikari pehle hi naya connection bana le.
  5. Connection 20 sec se zyada bahar raha to Hikari us jagah ka stack trace log karega jahan connection liya gaya tha.
  6. Ab controller ya JSON me lazy loading nahi chalegi (LazyInitializationException). Zaroori data transaction ke andar JOIN FETCH ya DTO se lao.
  1. Spring Boot ka auto-configured DataSource HikariDataSource hi hota hai, isliye seedha inject kiya.
  2. Har 10 sec check. Kisi config class pe @EnableScheduling hona chahiye.
  3. Pool pehli getConnection() pe start hota hai. Usse pehle MXBean null ho sakta hai.
  4. Abhi kitne threads connection ki line me hain. Yahi asli red flag hai.
  5. Production me yahi numbers Actuator se bhi milte hain: hikaricp.connections.active, .idle, .pending.

Pool kab badhayein

  • Pending lagataar 0 se upar hai aur DB ka CPU/IO relaxed hai.
  • Instances × pool size, DB ke max_connections se kam hai.

Kab ignore karein

  • DB pehle se busy hai: pehle slow queries, missing indexes aur lambi transactions theek karo.
  • Instances bahut hain: PgBouncer jaisa external pooler socho.

Dhyan rakho

  • Chhota connection-timeout user-facing APIs ke liye. Batch jobs ke liye alag pool aur lamba timeout.
  • open-in-view: false ke baad LazyInitializationException aaye to wo purana bug hai jo OSIV chhupa raha tha.
4

Save, REST call, update: transaction ki seema

Layer: @Transactional + HikariCP + REST. Example: Order service.

@Transactional method shuru hote hi transaction khulta hai aur pehli query pe pool se connection liya jata hai. Commit ya rollback tak wo connection usi thread ka rehta hai, chahe thread DB ka kaam kare ya na kare.

✗ Problem

@Transactional ke andar payment ki REST call

placeOrder() pe @Transactional laga hai. Andar order save, phir payment service ko REST call (1–3 sec), phir status update. Un 1–3 sec me DB connection idle pada hai lekin pool me wapas nahi gaya. Baaki threads Hikari ki line me.

Consistency ka dhokha bhi hai: payment ho gaya, lekin commit fail ho gaya (deadlock, DB restart). Customer ka paisa kata, order DB me hai hi nahi. Transaction network call ko rollback nahi kar sakta.

Pool capacity = connections ÷ connection hold time 10 ÷ 2 s = 5 orders/sec (connection REST call tak pakda) 10 ÷ 0.02 s = 500 orders/sec (sirf do chhoti transactions)
  1. Poora method ek transaction. Method start pe begin, return ke baad commit.
  2. save() pe HikariCP se connection liya aur INSERT chala. Ab ye connection commit tak isi thread ka.
  3. 1–3 sec ki REST call, connection idle pada hai. Timeout bhi set nahi (Topic 5).
  4. Payment ho chuka, commit abhi baaki. Commit fail hua to paisa kata aur order gayab.
  5. Method return, phir commit, tab jaake connection pool me wapas.
✓ Solution

Do chhoti transactions, beech me bina connection ke REST call

Teen step: (1) chhoti transaction me order PENDING save, (2) bina transaction payment call, (3) chhoti transaction me status update. @Transactional methods alag bean OrderTransactionService me rakho: same class ke andar se call karne pe Spring proxy bypass hota hai aur transaction lagta hi nahi.

Payment timeout ho to "fail" mat maano, "pata nahi" maano: status PAYMENT_PENDING, aur reconciliation job baad me confirm karegi (LLD section dekho).

  1. Yahan @Transactional nahi hai. Ye method sirf steps ko orchestrate karta hai.
  2. Transaction #1 (~10–20 ms): INSERT status=PENDING, commit, connection turant wapas.
  3. Payment call ke waqt is thread ke paas koi DB connection nahi. Iske liye open-in-view: false zaroori hai (Topic 3).
  4. Transaction #2 (~10–20 ms): order load karke status update, commit.
  5. PaymentClient Payment service ko call karta hai. Timeouts, retry aur idempotency key Topics 5–6 me hain; order id hi key banegi.
  6. Timeout ka matlab "pata nahi paisa kata ya nahi". Isliye FAILED nahi, UNKNOWN.
  1. Alag bean me @Transactional, taaki OrderService ki call Spring proxy se guzre aur transaction sach me lage.
  2. save() ke baad method return, commit, connection release.
  3. Fresh load, kyunki pehla transaction band ho chuka hai aur purana object detached hai.
  4. Teeno outcomes handle. Status badalne ke rules Order entity ke methods me hain (LLD).
  5. save() dobara nahi likha: managed entity me change hua hai, commit pe Hibernate dirty checking khud UPDATE chalata hai.

Kab apply karein

  • Jab bhi transaction ke beech network call ho: payment, email, doosri microservice, file upload.

Kab ignore karein

  • Saare steps ek hi DB me hain aur fast hain. Ek transaction simple aur atomic hai; split karne se status aur reconciliation ka kaam badhta hai.

Keemat kya hai

  • Atomicity chali jaati hai: PENDING order ban sakta hai jiska payment fail ho.
  • Isliye saaf statuses, reconciliation job, aur bade systems me Outbox ya Saga pattern.
5

REST call: timeouts aur HTTP connection pool

Layer: HTTP client (RestClient + Apache HttpClient 5). Example: Payment service se external gateway.

Har remote call me teen intezaar hote hain: pool se connection milna, TCP connection banna, aur jawab aana. Teeno ka timeout na ho to ek slow dependency aapke saare threads pakad leti hai.

✗ Problem

Gateway slow hua, poori Payment service ruk gayi

External payment gateway kabhi-kabhi 20–30 sec me jawab deta hai. Hamare client me timeout set hi nahi, to har slow call ek Tomcat thread ko pakad ke baith jati hai. 200 threads kuch seconds me khatam. Health check fail, aur Order service ki calls bhi atakne lagin: cascading failure.

Doosra jaal: Apache HttpClient 5 default settings me ek host ke liye sirf 5 connections deta hai. Gateway fast ho tab bhi baaki threads bas gateway connection ka intezaar karte hain.

Symptoms: http.client.requests ka max bahut bada, thread dump me threads socket read me ya connection pool ke lease pe atke hue.

  1. new RestTemplate(): koi connect ya read timeout nahi, aur Spring ke builder ke bina bana hai to metrics bhi nahi.
  2. Gateway atka to ye line atki. Thread tab tak wapas nahi aata jab tak OS ya gateway connection na tode.
✓ Solution

Teen timeouts, sahi size ka pool, Spring ka builder

Connect timeout (TCP connection kitni der me bane), connection-request timeout (pool se connection kitni der me mile), response timeout (jawab kitni der me aaye). Timeout lagbhag dependency ka p99 + thoda buffer. Pool ka size concurrency se nikalo.

Saath-saath calls ≈ req/s × call duration 200 req/s × 0.4 s = 80, pool 100 (buffer) Response timeout gateway p99 800 ms, isliye 1 s
  1. Spring Boot ka auto-configured builder use kiya, isse http.client.requests metrics aur tracing milti hai.
  2. MaxConnPerRoute = ek host (gateway.example.com) ke liye max connections. Default 5 tha, ab 100.
  3. TCP connection 500 ms me nahi bana to fail. Gateway down ho to jaldi pata chale.
  4. Pool se connection 300 ms me nahi mila to fail. Warna threads pool ke bahar chupchap line lagate.
  5. Gateway 1 sec me jawab na de to chhod do, thread free. Retry ka faisla Topic 6 me.
  6. Apache HttpClient ko RestClient ke neeche lagaya. Bean ka naam paymentGatewayRestClient rakha, taaki doosre clients se confuse na ho.

Chhote timeouts kab

  • User-facing APIs jahan SLA hai.
  • Har dependency ka apna client aur pool (bulkhead), taaki ek slow dependency baaki sabko na roke.

Lambe timeouts kab

  • Known slow kaam: report export, bulk file transfer. Unke liye alag client, alag pool, aur ho sake to async.

Dhyan rakho

  • Bada pool tabhi jab downstream sambhal sake; zyada connections gateway ki rate limit hit kar sakte hain.
  • Andar wala timeout (1 s) bahar wale (Order se Payment, 2.5 s) se chhota hona chahiye.
6

Retry, idempotency key aur circuit breaker

Layer: resilience (Resilience4j). Example: Payment service.

Timeout ke baad sabse bada sawaal: dobara try karein ya nahi? Payment jaisi cheez me galat retry ka matlab customer ka paisa do baar.

✗ Problem

Timeout pe 3 baar retry, paisa 2 baar kata

Gateway ne jawab dene me der ki, to code ne turant dobara try kiya. Lekin timeout ka matlab ye nahi ki charge nahi hua. Ho sakta hai gateway ne paisa kaat liya ho aur sirf response late ya network me kho gaya ho. Retry pe naya charge ban gaya.

Jab gateway poora down hai, har request 3 attempts me threads jalati hai aur gateway pe 3 guna load daalti hai. Saare instances ek saath retry karte hain (retry storm), aur gateway uth hi nahi pata.

  1. Har failure pe 3 attempts. Gateway down ho to uspe load 3 guna.
  2. Idempotency key nahi. Gateway ko pata hi nahi ki ye wahi charge dobara aa raha hai.
  3. Har exception retry: 400 Bad Request (galat card number) bhi, jo kabhi pass nahi hoga.
  4. Bina backoff: saare threads aur instances ek hi pal me dobara hit karte hain.
✓ Solution

Sirf safe retries, same key ke saath, aur circuit breaker

Retry tabhi jab operation idempotent ho. Payment POST ko Idempotency-Key header se idempotent banao: gateway same key dobara dekhe to naya charge nahi banata, pehla result lautata hai. Sirf transient errors retry karo (timeout, network, 5xx), wait ke saath. Circuit breaker: last 20 calls me 50% fail hon to 10 sec tak gateway ko call hi mat karo, turant fallback do, threads bache rahenge.

Worst case latency = attempts × timeout + backoff 2 × 1 s + 0.2 s = 2.2 s, jo Order se Payment ke 2.5 s timeout se kam hai
  1. Resilience4j ka default order: Retry bahar, CircuitBreaker andar. Fallback Retry pe lagao. CircuitBreaker pe lagaya to har failure pe turant fallback return hoga aur retry kabhi chalega hi nahi.
  2. Har attempt circuit breaker se guzarta hai. Circuit OPEN ho to call gateway tak jaati hi nahi, CallNotPermittedException aata hai.
  3. Same order ke saare retries ki key same. Gateway pe ek hi charge banega.
  4. Saare attempts fail ya circuit open: FAILED nahi, UNKNOWN. Order PAYMENT_PENDING, reconciliation baad me.
  1. max-attempts me pehli call bhi ginti me hai. 2 matlab ek retry.
  2. Zyada attempts hon to exponential backoff + jitter rakho (200 ms, 400 ms, 800 ms, thoda random), taaki saare instances ek saath na maarein.
  3. ResourceAccessException = timeout/network, HttpServerErrorException = 5xx. 4xx retry nahi hogi. CallNotPermittedException list me nahi, isliye circuit open ho to seedha fallback.
  4. Kam se kam 10 calls ke baad, last 20 me 50% ya zyada fail hon to circuit OPEN.
  5. 10 sec baad HALF_OPEN: 3 test calls. Pass hui to CLOSED, fail hui to phir OPEN.

Retry kab

  • Idempotent operation: GET, ya POST with idempotency key.
  • Transient errors, aur latency budget me jagah ho.

Kab ignore karein

  • Non-idempotent POST bina key, 4xx errors, ya jab retries × timeout aapke SLA se bada ho.
  • Circuit breaker low traffic internal calls pe: window hi nahi bharega.

Dhyan rakho

  • Retry har layer pe mat lagao. Client, Order service aur gateway SDK teeno 3-3 baar karein to 27 attempts. Ek layer chuno, baaki fail fast.
7

Safe update: lost update aur stale cache

Layer: JPA locking + Spring Cache. Example: User profile service.

Read-modify-write me do requests ek hi row ko ek saath badlein to jo baad me save hua wo jeet-ta hai, aur pehle wale ki change bina kisi error ke gayab. Cache ho to purana data wahan bhi atak sakta hai.

✗ Problem

City badli, phone badla, ek change gayab

User mobile app se city badalta hai, usi waqt support team admin panel se phone number. Dono ne profile ka version 4 padha. Admin ki request baad me commit hui, aur Hibernate ka UPDATE by default saari columns likhta hai, to purani city wapas aa gayi. User ki change gayab, koi error nahi.

Upar se GET profile @Cacheable hai lekin update pe cache evict nahi hota, to app ko der tak purani city dikhti hai.

  1. GET cache me gaya, lekin update ke baad kabhi clear nahi hota: stale data.
  2. Dono concurrent requests same purana data padhti hain. Koi version check nahi.
  3. Client poora form bhejta hai, jisme doosri field ki value purani hai.
  4. Jo baad me commit hua wahi jeeta. Pehle wale ki change chupchap overwrite.
✓ Solution

@Version se conflict pakdo, commit ke baad cache evict

Entity me @Version field lagao. Hibernate UPDATE ... WHERE id = ? AND version = ? chalata hai. Beech me kisi aur ne update kiya to 0 rows update hongi aur optimistic locking exception aayega. Hum 409 Conflict lautayenge, client latest data reload karke dobara try karega. Client jo version padh ke form bhar raha tha, wo bhi request me bheje, taaki form khule rehne ke dauraan hui change bhi pakdi jaye.

Cache evict transaction commit ke baad hona chahiye. Isliye @CacheEvict bahar wali service method pe, aur @Transactional andar wale bean me.

  1. Har successful update pe Hibernate version +1 karta hai aur UPDATE ki WHERE clause me purana version lagata hai.
  2. Client ne form kholte waqt jo version dekha tha, wo abhi wala nahi hai: turant conflict. Ye user ke form bharne wale time ko bhi cover karta hai.
  3. Sirf wahi field badlo jo request me aayi. Null matlab "is field ko mat chhedo".
  1. @CacheEvict method successfully return hone ke baad chalta hai, aur tab tak andar wala transaction commit ho chuka hota hai. Evict pehle hota to beech me koi GET purana data phir cache me daal deta.
  2. Transaction alag bean me: call proxy se guzarti hai aur commit isi call ke return pe ho jata hai.
  3. Version mismatch pe exception. @RestControllerAdvice me OptimisticLockingFailureException pakad ke 409 Conflict lautao.
  4. saveAndFlush UPDATE abhi chalata hai, taaki response me naya version jaye aur client agli baar sahi version bheje.

Optimistic lock kab

  • Conflicts kam hote hain: profile, settings, product catalog edits.

Kab kuch aur chuno

  • Conflicts bahut zyada (stock, seat booking): SELECT ... FOR UPDATE ya atomic SQL jaise UPDATE stock SET qty = qty - 1 WHERE qty > 0. Warna 409 aur retries ki baarish.

Cache pe dhyan

  • Read-heavy data jahan thodi staleness chal jaye, wahi cache karo. Balance, payment status, inventory nahi.
  • Multiple instances me local Caffeine cache har instance ka alag hai, evict sirf ek pe hoga: shared cache (Redis) ya chhota TTL.
8

Virtual threads: kab haan, kab na

Layer: JVM threads (Java 21+, Spring Boot 3.2+). Example: Order service.

Platform thread = OS thread, apna stack, mehenga. Virtual thread = JVM ka halka thread. Jab virtual thread I/O pe block hota hai, JVM use carrier thread se utaar deta hai aur carrier doosra kaam uthata hai.

✗ Problem

CPU 30%, lekin 200 threads full

Order API ka 90% time REST call aur DB ke wait me jaata hai. CPU sirf 30% busy, phir bhi 200 platform threads full, kyunki har waiting request ek poora OS thread pakad ke baithi hai. Threads 2000 karein to memory aur OS scheduling ka kharcha badhta hai.

  1. Blocking I/O wale kaam ke liye platform threads ko hazaron tak le jana mehenga hai. Aur agar CPU ya DB pool bottleneck hai to ye bilkul bekaar.
✓ Solution

I/O-heavy app me virtual threads, guardrails ke saath

Java 21+ aur Spring Boot 3.2+ me ek property se Tomcat har request ko virtual thread pe chalata hai. Hazaron waiting requests sasti ho jaati hain. Chaar baatein yaad rakho:

  1. CPU-bound kaam fast nahi hota, cores utne hi hain.
  2. HikariCP pool ab bhi 10 hai: ab hazaron virtual threads us 10 ke liye line lagayenge.
  3. Downstream (gateway) pe load badh sakta hai, isliye concurrency limit rakho.
  4. Java 21–23 me synchronized ke andar blocking I/O carrier thread ko pin kar deta hai; JDK 24 me ye theek hua.
  1. Tomcat request threads aur Spring Boot ke auto-configured executors virtual threads use karenge. Aapke custom pools (jaise photoProcessingExecutor) platform threads hi rahenge, jo CPU kaam ke liye sahi hai.
  1. Virtual threads lagbhag unlimited ho sakte hain, gateway ki capacity nahi. 100 permits = ek time pe max 100 gateway calls, HTTP pool ke barabar.
  2. 300 ms tak permit ka wait, phir haar maan lo. Pool ke connection-request timeout jaisa.
  3. Overload me fail fast. Order PAYMENT_PENDING me jayega.
  4. Interrupt flag wapas set karo, taaki upar ka code shutdown ya cancel samajh sake.
  5. Release sirf tab jab permit mila tha, warna permits ki ginti bigad jayegi.

Kab apply karein

  • I/O-bound workload, bahut saari concurrent waiting requests, Java 21+.
  • Blocking style code simple rakhna hai, WebFlux ke bina.

Kab ignore karein

  • CPU-bound workload.
  • Bottleneck DB pool hai: virtual threads connections nahi badhate.
  • Java 21–23 pe libraries jo synchronized ke andar blocking I/O karti hain.

Dhyan rakho

  • ThreadLocal me bade objects mat rakho: hazaron virtual threads matlab hazaron copies.
  • jvm.threads.live sirf platform threads ginta hai, virtual threads nahi.

Package structure

Order status machine

PAID aur PAYMENT_FAILED final states hain. PAYMENT_PENDING sirf reconciliation job ya naye payment result se aage badhta hai. Rules Order entity ke andar hain, service me nahi.

placeOrder() sequence: DB connection kab pakda gaya

Domain rules aur reconciliation job

Order entity: status rules ek jagah

  1. Enum ko STRING me save karo. ORDINAL me enum ka order badla to purana data galat matlab dene lagega.
  2. Request thread aur reconciliation job ek hi order ko ek saath update karein to ek ko conflict milega, chupchap overwrite nahi hoga.
  3. JPA ko no-arg constructor chahiye. protected rakha taaki baaki code factory method use kare.
  4. Naam se saaf: naya order hamesha PENDING se shuru hota hai.
  5. Status rules entity ke andar: PAID order dobara PAID ya FAILED nahi ho sakta, chahe koi bhi service call kare.
  6. Galat transition pe turant exception, taaki bug data kharab karne se pehle pakda jaye.

Reconciliation job: PAYMENT_PENDING ka ilaaj

  1. fixedDelay: pichla run khatam hone ke 60 sec baad agla. Runs overlap nahi karenge, jo fixedRate me ho sakta hai.
  2. Sirf 2 min purane pending orders. Jo abhi-abhi bane, unka payment shayad raste me hai.
  3. Ek run me max 100 orders, taaki job khud DB pool aur Payment service pe load na daale.
  4. Idempotency key (order id) se Payment service batata hai ki charge hua ya nahi.
  5. Wahi method jo request flow use karta hai, isliye status rules ek hi jagah. UNKNOWN phir aaya to order pending hi rahega.
  6. Ek order ki galti poori batch na roke. Multiple instances pe job ek saath na chale, iske liye ShedLock ya SELECT ... FOR UPDATE SKIP LOCKED.

Trade-offs: kab lagao, kab chhodo

Koi bhi setting hamesha sahi nahi hoti. Pehle neeche wala order follow karo, phir table se har faisle ka rule dekho.

Mock interview: sawaal aur jawab

Fresher, mid aur senior level mix. Pehle khud jawab socho, phir kholo.

FresherThread aur process me kya fark hai?›

Process ek chalta hua program hai jiska apna memory space hota hai, jaise ek JVM. Thread process ke andar kaam karne wali ek line hai. Ek process ke saare threads heap memory share karte hain, lekin har thread ka apna stack hota hai.

Isliye thread banana process se sasta hai, lekin shared data pe race condition ka dhyan rakhna padta hai.

FresherSpring Boot me default kitne Tomcat threads hote hain, aur kaise badlein?›

server.tomcat.threads.max default 200 aur server.tomcat.threads.min-spare default 10. Dono application.yml me badal sakte ho.

Lekin badhane se pehle dekho ki CPU aur DB pool me jagah hai ya nahi, warna wait bas ek jagah se doosri jagah shift hoga (Topic 2).

Freshermax-connections aur threads.max me kya fark hai?›

max-connections (8192) batata hai kitne TCP connections ek saath khule reh sakte hain, yani kitne log kursi pe baith sakte hain. threads.max (200) batata hai kitni requests pe ek saath kaam ho sakta hai, yani kitne counters hain.

8192 connections ka matlab 8192 requests ek saath process hona nahi hai.

FresherConnection pool kya hai aur kyun chahiye?›

Har query ke liye naya DB connection banana mehenga hai: TCP, authentication, session setup. Pool pehle se bane connections rakhta hai; thread udhaar leta hai aur kaam ke baad lautata hai.

Spring Boot me default pool HikariCP hai, maximum 10 connections.

FresherCPU-bound aur I/O-bound task me kya fark hai? Example do.›

CPU-bound task poore time CPU use karta hai: image resize, encryption, bada JSON parse, calculations. I/O-bound task zyada time wait karta hai: DB query, REST call, file read.

CPU-bound ke liye threads lagbhag cores ke barabar. I/O-bound me zyada threads (ya virtual threads) kaam aate hain, kyunki waiting thread CPU nahi khata.

Fresher@Transactional kya karta hai?›

Method shuru hone pe transaction begin, successful return pe commit, aur RuntimeException pe rollback. Checked exception pe by default rollback nahi hota.

Transaction ke dauraan DB connection usi thread ke paas rehta hai. Ye Spring proxy se kaam karta hai, isliye same class ke andar se call karne pe nahi lagta.

FresherREST call pe timeout kyun set karna chahiye?›

Bina timeout ke slow ya atki hui dependency aapke thread ko minutes tak pakad sakti hai. Kuch hi seconds me saare threads khatam, aur poori app down lagti hai: isko cascading failure kehte hain.

Connect, connection-request aur response, teeno timeouts set karo (Topic 5).

FresherContext switching kya hai?›

Jab runnable threads cores se zyada hote hain, OS ek thread ko rok ke doosra chalata hai. Rukne wale thread ki state save hoti hai, naye ki load hoti hai, aur CPU cache ka fayda bhi kam hota hai.

Thode switch normal hain. Bahut zyada threads hon to CPU ka bada hissa switching me chala jata hai.

Mid200 threads, har request 500 ms. Max throughput kitna? 600 req/s aayein to kya hoga?›

Throughput = threads ÷ response time = 200 ÷ 0.5 = 400 req/s. 600 aayengi to har second 200 requests line me judengi: 10 sec me ~2000 waiting aur nayi request ko ~5 sec extra wait.

Fix: response time 333 ms se kam karo, ya headroom ke saath instances badhao. Threads andhadhundh badhana fix nahi hai.

Mid"Connection is not available, request timed out after 30000ms" ka matlab aur fix?›

HikariCP ke saare connections busy the aur thread 30 sec tak connection nahi le paya. Wajah aksar: slow queries, lambi transactions, transaction ke andar REST call, open-in-view, ya connection leak.

Fix: holding time kam karo, open-in-view: false, leak-detection-threshold on, connection-timeout chhota. Pool tabhi badhao jab DB ke paas capacity ho.

Mid@Transactional method ke andar REST call karna galat kyun hai?›

Transaction ke poore time connection pakda rehta hai, REST call ke seconds bhi. Pool jaldi khatam hota hai. Aur atomicity ka bharosa jhootha hai: remote call rollback nahi hoti. Payment ho gaya lekin commit fail hua to data inconsistent.

Pattern: chhoti transaction me PENDING save, bina transaction REST call, chhoti transaction me status update, aur saath me reconciliation job (Topic 4).

MidSame class ke andar @Transactional method call karne pe transaction kyun nahi lagta?›

Spring bean ke aage ek proxy banata hai, aur transaction ka logic proxy me hota hai. this.method() call proxy ko bypass karke seedha object pe jaati hai.

Fix: method alag bean me rakho (jaise OrderTransactionService), ya TransactionTemplate se programmatic transaction lo. Yahi rule @Async aur @Cacheable pe bhi lagta hai.

MidOptimistic aur pessimistic locking me kya fark hai, kab kya chunoge?›

Optimistic: koi lock nahi, @Version column se UPDATE ke waqt check; conflict pe exception aur 409. Kam conflicts wale data ke liye, jaise profile.

Pessimistic: SELECT ... FOR UPDATE se row lock, doosre wait karte hain. Zyada conflicts wale data ke liye, jaise stock ya seat booking. Counters ke liye atomic SQL (qty = qty - 1) aur bhi behtar.

MidRetry kab safe hai? Idempotency key kya hoti hai?›

Retry tab safe hai jab operation dobara chalne pe result na badle (GET, same data wala PUT) aur error transient ho (timeout, 503). 4xx errors kabhi retry mat karo.

Payment jaise POST ke liye Idempotency-Key header bhejo: server same key dobara dekhe to naya kaam nahi karta, pehla result lautata hai.

MidHikariCP pool size kaise decide karoge?›

App threads se nahi, database ki capacity se. Start: (DB cores × 2) + effective disks, jaise 4-core DB pe ~10. Phir load test me hikaricp.connections.pending aur usage dekho.

Saath me check karo ki instances × pool size, DB ke max_connections se kam ho. Chhota pool jisme thoda wait ho, us bade pool se behtar hai jo DB ko thrash kare.

Mid@Cacheable ke saath stale data kaise avoid karoge?›

Update pe @CacheEvict lagao, aur evict transaction commit ke baad hona chahiye. Safety net ke liye TTL rakho.

Multiple instances hon to local cache har instance me alag hai, isliye shared cache (Redis) ya chhota TTL. Jahan hamesha fresh data chahiye (balance, payment status), wahan cache mat lagao.

SeniorCPU 95% hai aur busy threads 200/200. Threads 500 kar dein?›

Nahi. CPU full hai, to threads ki kami symptom hai, wajah nahi. 500 threads matlab zyada context switching aur memory, throughput aur girega.

Pehle JFR se hot methods dekho, CPU kaam kam karo (algorithm, caching, serialization), CPU-heavy kaam ko cores-size pool me limit karo, aur zaroorat ho to instances badhao. GC time bhi check karo, kyunki high CPU memory ki problem bhi ho sakti hai.

Senior600 req/s ke liye capacity planning kaise karoge?›

Pehle ek request ka profile: CPU time, DB time, downstream time (JFR + metrics). Per instance CPU limit = cores ÷ CPU time, jaise 8 ÷ 0.05 = 160. 30% headroom ke saath instances = 600 × 1.3 ÷ 160 = 5.

Phir har instance ke threads, Hikari pool aur HTTP pool concurrency se nikalo, DB connection budget aur timeout ladder check karo, aur load test se verify karo (HLD table dekho).

SeniorTimeout hierarchy kaise design karoge?›

Bahar wala timeout hamesha andar wale timeouts + retries se bada ho. Example: gateway 1 s × 2 attempts + 200 ms backoff = 2.2 s, isliye Order se Payment 2.5 s, aur API budget 3 s.

Ulta hua (andar 5 s, bahar 2 s) to bahar wala chhod dega lekin andar ka kaam chalta rahega: resources waste aur duplicate side effects.

SeniorRetry aur circuit breaker ek saath lagate waqt kya dhyan rakhoge?›

Resilience4j ka default order Retry(CircuitBreaker(call)) hai. Fallback Retry pe lagao; CircuitBreaker pe lagaya to har failure turant fallback ban jayega aur retry kabhi nahi hoga. Circuit OPEN hone pe CallNotPermittedException retry nahi honi chahiye.

Aur retry sirf ek layer pe. Client, service aur SDK teeno retry karein to attempts multiply ho jaate hain.

SeniorPayment call timeout ho gaya. Order ka kya karoge?›

Timeout ka matlab "unknown" hai, "failed" nahi. Order ko PAYMENT_PENDING rakho aur user ko "processing" dikhao. Reconciliation job idempotency key (order id) se status puchhegi aur PAID ya FAILED karegi.

Andhe me FAILED karke user se naya payment mat lo, warna double charge. Bade systems me Outbox ya Saga se isko reliable banao.

SeniorVirtual threads kab adopt karoge aur kab nahi?›

Adopt: I/O-bound services jahan bahut saari requests REST/DB ka wait karti hain, Java 21+ pe, aur blocking code simple rakhna ho.

Nahi: CPU-bound workload, jahan bottleneck DB pool hai, ya libraries synchronized ke andar blocking I/O karti hain (Java 21–23 pinning, JDK 24 me fix). Adopt karo to downstream ke liye Semaphore/bulkhead aur pool timeouts zaroor rakho.

SeniorMultiple instances me @CacheEvict ki kya problem hai?›

Local cache (Caffeine) har instance ki memory me alag hai. Update jis instance pe aaya, sirf wahan evict hoga; baaki instances purana data dete rahenge.

Solutions: Redis jaisa shared cache, cache invalidation events (pub/sub), ya chhota TTL agar thodi staleness chal jaye.

SeniorOpen Session In View kya hai aur production API me band kyun karte ho?›

OSIV web request ke shuru se end tak persistence context khula rakhta hai, taaki controller ya JSON serialization me lazy loading chal sake. Nuksaan: connection request ke end tak pakda reh sakta hai (REST calls samet), aur serialization ke dauraan chhupi N+1 queries.

spring.jpa.open-in-view=false karo aur zaroori data transaction ke andar JOIN FETCH, @EntityGraph ya DTO projection se lao.

SeniorBulkhead pattern kya hai aur Spring Boot app me kaise lagaoge?›

Jahaz ke alag-alag compartments ki tarah: ek dependency ki problem baaki app ko na duboye. Har dependency ka alag HTTP client aur pool, CPU kaam ka alag executor, aur Semaphore se concurrency limit.

Isse slow payment gateway saare Tomcat threads nahi kha payega, aur profile jaisi baaki APIs chalti rahengi.
