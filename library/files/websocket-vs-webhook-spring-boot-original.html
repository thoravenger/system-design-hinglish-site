Webhook = doorbell

Koi aata hai, bell bajata hai, chala jaata hai. Aapko pata nahi wo kaun tha jab tak aap signature verify na karo. Agar aapne darwaza nahi khola — wo dobara aayega, aur dobara, aur dobara.

WebSocket = phone call

Ek baar line judi, dono bol sakte hain. Line khuli rakhne ka kharcha hai, aur line kat jaaye toh kisi ko dobara dial karna padega — aur wo kaam client ka hai, server ka nahi.

Real system me dono chahiye. Classic case: order/payment tracking.

Dono teal boxes wahi ek Spring Boot app hain — bas alag nodes pe chal rahe hain. Aur yahi Redis ka poora point hai.

Multi-node ka asli problem scale nahi, affinity hai. Webhook load balancer ke through kisi bhi node pe land karega — maan lo node 1. Par us user ka WebSocket node 3 pe khula hai. Bina fan-out ke node 1 ke paas woh session hai hi nahi, aur event chup-chaap gayab ho jaata hai. Staging pe (1 node) sab perfect chalega, production pe randomly fail hoga.

Do raaste hain: sticky sessions (LB user ko hamesha usi node pe bheje — nazuk hai, node marte hi sab toot jaata hai), ya fan-out (Redis pub/sub, ya STOMP broker relay). Fan-out hamesha better hai.

Threads

Yeh section hi asli interview differentiator hai.

Webhook ka lifecycle — Tomcat

  1. Acceptor thread socket accept karta hai, NIO poller ko de deta hai.
  2. Poller ko readable data milta hai → pool se ek worker thread (http-nio-8080-exec-N) uthta hai.
  3. Wahi ek thread poora kaam karta hai: filter chain → security → controller → DB → response write.
  4. Response jaane ke baad thread pool me wapas.
Yahi jagah hai jahan systems marte hain. Agar handler me DB write + fraud API + email hai aur 800ms lagte hain, toh 200 threads ÷ 0.8s ≈ 250 webhooks/sec ka hard ceiling. Uske baad accept queue, phir provider timeout, phir provider retry — aur load double. Death spiral, aur aapne khud invite kiya.

WebSocket ka lifecycle — Tomcat

Handshake ek normal worker thread pe aata hai (Upgrade: websocket header wali HTTP request). Upgrade ke baad connection request thread se detach ho jaata hai aur Tomcat ke NIO poller ke paas chala jaata hai.

Matlab: 1 WebSocket ≠ 1 thread. 50,000 idle connections ho sakte hain aur ek bhi worker thread busy nahi. Thread sirf tab lagta hai jab actual frame aata hai. Asli cost memory hai — per-connection buffers, session object, aur aapka subscription state.

Teen models, ek nazar me

Tomcat (Spring MVC)
200 platform threads, blocking
Har blocking call ek slot khaa jaati hai. Pool khatam = requests queue me.
Virtual threads
Java 21+, Boot 3.2+
Blocking model wahi, cost gayab. JVM virtual thread ko carrier se unmount kar deta hai.
WebFlux (Netty)
1 event loop per CPU core
Ek blocking call ek loop rok degi — aur us loop pe baithe hazaaron connections freeze.
I/O pe blocked kaam kar raha hai

Virtual threads ke caveats

  • synchronized block ke andar blocking karoge toh carrier thread pin ho jaata hai. JDK 24 (JEP 491) ne ise kaafi had tak fix kiya — purane JDKs pe ReentrantLock use karo.
  • DB connection pool ab bhi aapka asli bottleneck hai. 10,000 virtual threads ek 10-connection HikariCP pool se kuch nahi bana sakte.
  • Thread-local pe heavily depend karne wali purani libraries (kuch APM agents, kuch ORMs) abhi bhi surprise de sakti hain. Load test karke hi enable karo.
Practical faisla: naya project, blocking drivers, team reactive nahi jaanti → Spring MVC + virtual threads. Sabse aasaan raasta, 90% fayda. WebFlux tab chuno jab high-frequency streams pe backpressure chahiye ho — jaise per-second thousands of price ticks.

Webhook — receive

Teen cheezein har webhook endpoint me honi chahiye: replay window, raw-bytes signature, aur idempotency. Phir turant 200.

byte[] kyun, DTO kyun nahi? Signature raw bytes par HMAC hota hai. Agar aap @RequestBody PaymentDto lete ho, Jackson deserialize karke phir se serialize karega — key order aur whitespace badal jaayenge, aur signature hamesha fail hoga. Yeh webhook integrations ka #1 bug hai. JSON parse baad me karo, async processor ke andar.

Webhook — process

WebSocket — setup

Auth handshake pe hoti hai, session me nahi. Handshake reject hua toh session banta hi nahi — sabse sasta rejection.

Dono ko jodne wala bridge

Redis pub/sub fire-and-forget hai. Agar us waqt user ka socket band tha, message chala gaya. Isliye reconnect ke baad client ko hamesha current state HTTP se fetch karni chahiye — WebSocket sirf deltas ke liye. Guaranteed delivery chahiye toh Redis Streams ya ek proper broker use karo.

Interview

Wo sawaal jo aksar aate hain, aur woh jawab jo alag dikhate hain.

Ek line me farq batao
Webhook HTTP ke upar server-to-server push hai — stateless, provider-retried, at-least-once. WebSocket TCP ke upar persistent full-duplex pipe hai — stateful, no retries, ack aur resume aapko khud banana padta hai.
Kya har WebSocket connection ek thread leta hai?
Nahi. Tomcat NIO pe handshake ke baad connection request thread se detach ho jaata hai aur poller ke paas chala jaata hai. Thread sirf tab lagta hai jab frame aata hai. 50,000 idle connections me ek bhi worker thread busy nahi hoga. Asli cost memory hai — per-connection buffers, session object, subscription state.
Webhook handler dheema ho toh kya hota hai?
Har request ek Tomcat worker thread block karti hai. 200 threads × 800ms handler ≈ 250 req/sec ka ceiling. Uske baad accept queue bharti hai, provider timeout karta hai, aur phir retry karta hai — yaani load double ho jaata hai jab aap pehle hi doob rahe ho. Isliye pattern hai: verify, persist, 200 OK, phir async process.
Do nodes hain, webhook node 1 pe aaya, user ka socket node 3 pe hai. Kya karoge?
Yeh connection affinity ka problem hai. Node 1 ke paas session hai hi nahi. Do options: sticky sessions (nazuk — node marte hi sab toot jaata hai) ya fan-out. Fan-out better hai — Redis pub/sub par channel order.<userId>, har node subscribe karta hai, jiske paas session hai wahi push karta hai. STOMP use kar rahe ho toh enableStompBrokerRelay() se RabbitMQ seedha yeh kaam kar deta hai.
Webhook idempotent kaise banaoge?
Provider ke event ID par database unique index. In-memory cache ya Redis SETNX kaafi nahi — restart ya node change pe duplicate nikal jaayega. Duplicate aane par 200 lautao, error nahi — warna provider retry karta rahega. Aur raw body store karo taaki failure ke baad reprocess kar sako.
WebSocket auth kaise karoge? Browser headers set nahi kar sakta.
Sahi — browser ki WebSocket API custom headers allow nahi karti. Normal HTTP se ek short-lived ticket lo (30 second TTL, single use), usse query param me bhejo, aur HandshakeInterceptor me verify karo. Long-lived JWT URL me mat daalo — wo access logs, proxy logs aur referrer headers me chhap jaata hai. Handshake reject karna sabse sasta rejection hai, kyunki session banta hi nahi.
Virtual threads se WebFlux ki zaroorat khatam ho gayi?
Zyadatar cases me haan. Virtual threads blocking I/O ka cost khatam kar dete hain bina programming model badle — yaani 90% fayda, 10% mehnat. WebFlux tab bhi jeetta hai jab aapko backpressure chahiye: fast producer, slow consumer, aur aapko flow control chahiye. Per-second thousands of price ticks WebSocket pe bhejna exactly aisa case hai. Baki sab ke liye MVC + virtual threads accha hai.
Aapka WebSocket har 60 second pe disconnect ho raha hai. Kya problem hai?
Load balancer ka idle timeout — AWS ALB pe default 60 seconds hai. WebSocket khula toh hai par usme traffic nahi hai, toh LB use idle samajh kar kaat deta hai. Fix: client-side heartbeat 25–30 second par, LB timeout se kam. Saath me server ka maxSessionIdleTimeout heartbeat se zyada rakho, warna server pehle kaat dega.
Client WebSocket read nahi kar raha aur messages aate ja rahe hain. Kya hoga?
Slow consumer problem. Server-side send buffer bharta jaayega aur aakhir me memory khaa jaayega. Isliye ConcurrentWebSocketSessionDecorator me sendTimeLimit aur bufferSizeLimit hain — limit cross hui toh OverflowStrategy.TERMINATE session band kar dega. Ek slow client ko poora node girane dena sabse bada operational risk hai.
WebSocket ki jagah kab SSE use karoge?
Jab traffic sirf server se client ki taraf ho. SSE plain HTTP par chalta hai, proxies ke saath better behave karta hai, auto-reconnect aur Last-Event-ID se resume built-in hai, aur Spring me bas SseEmitter ya Flux<ServerSentEvent> lautana hai. WebSocket tab chuno jab client bhi bol raha ho.
