Split the dataData ko baanto

Who owns which data, and how to read and write across services.Kaunsa data kiska hai, aur services ke paar kaise padhein aur likhein.

01

Database per service

Give every service its own private database.Har service ko uska apna private database do.

Use whenKab use karein

  • Several teams need to deploy and scale independently.Kai teams ko alag-alag deploy aur scale karna ho.
  • Services need different kinds of storage (relational, search, key-value).Services ko alag type ki storage chahiye (relational, search, key-value).

Avoid whenKab avoid karein

  • One small team and an early product. Split later, when the boundaries are clear.Ek chhoti team aur shuruaati product. Boundaries clear hon tab baad me split karo.
  • Most operations need one ACID transaction across the same entities.Zyaadatar operations ko same entities pe ek ACID transaction chahiye.

Pick another pattern whenDoosra pattern kab lein

  • Still early: a modular monolith with one schema per module, on one server with separate credentials.Abhi shuruaat hai: modular monolith, har module ka alag schema, ek server pe alag credentials ke saath.
  • One screen needs data from several services: API composition.Ek screen ko kai services ka data chahiye: API composition.
  • A change must stay consistent across services: Saga with an Outbox.Change ko services ke paar consistent rehna hai: Saga aur Outbox.
02

API composition

Join data from several services in the API layer.Kai services ka data API layer me jodo.

Use whenKab use karein

  • A screen combines two to four services and needs live data.Ek screen do se chaar services ka data jodti hai aur live data chahiye.
  • The response is small: one order, one user, one cart.Response chhota hai: ek order, ek user, ek cart.

Avoid whenKab avoid karein

  • You must filter, sort or join large data sets across services, such as all orders with failed payments in March.Services ke paar bade data sets filter, sort ya join karne hon, jaise March ke saare failed payment wale orders.
  • A very hot endpoint, where fanning out multiplies the load on every service.Bahut hot endpoint, jahan fan-out har service ka load kai guna kar deta hai.

Pick another pattern whenDoosra pattern kab lein

  • Large or complex cross-service queries: a CQRS read model.Bade ya complex cross-service queries: CQRS read model.
  • The same data is asked for constantly: Caching.Same data baar-baar maanga jaata hai: Caching.
03

CQRS

Use separate models for writing and for reading.Likhne aur padhne ke liye alag models use karo.

Use whenKab use karein

  • Reads and writes differ a lot in shape or volume.Reads aur writes ka shape ya volume bahut alag hai.
  • Many screens, dashboards or search features each need their own view of the data.Kai screens, dashboards ya search ko data ka apna alag view chahiye.

Avoid whenKab avoid karein

  • Simple CRUD, where the screens look like the tables.Simple CRUD, jahan screens tables jaisi hi dikhti hain.
  • Users must see their own change instantly everywhere.Users ko apna change har jagah turant dikhna zaroori hai.

Pick another pattern whenDoosra pattern kab lein

  • You only need more read capacity with the same shape: Read replicas.Sirf same shape me zyada read capacity chahiye: Read replicas.
  • You also need the full history: Event sourcing.Poori history bhi chahiye: Event sourcing.
  • A few items are read constantly: Caching.Kuch items baar-baar padhe jaate hain: Caching.
04

Event sourcing

Store what happened, not just the latest value.Sirf latest value nahi, jo hua woh store karo.

Use whenKab use karein

  • Ledgers, payments and audits, where what happened and why matters.Ledgers, payments aur audits, jahan kya hua aur kyun hua, yeh important hai.
  • You need past state as of a date, or want to build new views from old history.Kisi date ki purani state chahiye, ya purani history se naye views banane hain.

Avoid whenKab avoid karein

  • CRUD apps and schemas that change often. Every event version lives forever.CRUD apps aur baar-baar badalte schemas. Har event version hamesha ke liye rehta hai.
  • Personal data that must be fully deleted on request.Personal data jo request pe poori tarah delete karna padta hai.

Pick another pattern whenDoosra pattern kab lein

  • You only need an audit trail: an audit table, or change history through CDC.Sirf audit trail chahiye: audit table, ya CDC se change history.
  • You only need separate read views: CQRS without event sourcing.Sirf alag read views chahiye: event sourcing ke bina CQRS.

Keep data consistentData ko consistent rakho

Moving changes between services without losing them or applying them twice.Services ke beech changes bhejna, bina khoye aur bina do baar apply kiye.

05

Transactional outbox

Save the event in the same transaction as the data.Event ko data ke saath same transaction me save karo.

Use whenKab use karein

  • A database change must reliably produce an event or a message.Database change se pakka ek event ya message nikalna chahiye.
  • You own the service code and can add an outbox table.Service ka code tumhara hai aur outbox table add kar sakte ho.

Avoid whenKab avoid karein

  • Nothing needs to be published.Kuch publish karna hi nahi hai.
  • Never replace it with two separate writes to the database and the broker.Iski jagah database aur broker me do alag writes kabhi mat karo.

Pick another pattern whenDoosra pattern kab lein

  • You can't change the code, or don't want a poller: CDC. CDC can also relay the outbox itself.Code badal nahi sakte, ya poller nahi chahiye: CDC. CDC khud outbox ko bhi relay kar sakta hai.
  • Events are the source of truth: Event sourcing.Events hi source of truth hain: Event sourcing.
  • Always pair it with an Idempotent consumer, because resends happen.Hamesha Idempotent consumer ke saath use karo, kyunki resends hote hain.
06

Change data capture (CDC)

Turn the database log into a stream of events.Database log ko events ki stream bana do.

Use whenKab use karein

  • Legacy or third-party systems whose code you can't change.Legacy ya third-party systems jinka code tum badal nahi sakte.
  • Keeping caches, search and analytics in sync, or relaying an outbox without polling.Caches, search aur analytics ko sync rakhna, ya bina polling ke outbox relay karna.

Avoid whenKab avoid karein

  • It would expose raw internal tables to other teams as if they were a public API.Isse raw internal tables doosri teams ko public API ki tarah dikhne lagengi.
  • Low volume where a simple poller is enough, or you have no access to the database log.Kam volume jahan simple poller kaafi hai, ya database log ka access hi nahi hai.

Pick another pattern whenDoosra pattern kab lein

  • You own the code and want a clean event contract: Outbox, relayed by CDC.Code tumhara hai aur saaf event contract chahiye: Outbox, CDC se relay.
  • You need a queryable copy shaped for reads: a CQRS read model.Reads ke shape me queryable copy chahiye: CQRS read model.
07

Idempotent consumer

Process each message once, even if it arrives twice.Har message ek baar process karo, chahe do baar aaye.

Use whenKab use karein

  • Every consumer of at-least-once messages: Kafka, SQS, RabbitMQ.At-least-once messages ka har consumer: Kafka, SQS, RabbitMQ.
  • Every API that clients may retry, using an idempotency key.Har API jise client retry kar sakta hai, idempotency key ke saath.

Avoid whenKab avoid karein

  • The operation is already naturally idempotent, like an upsert by key or setting a status.Operation pehle se naturally idempotent hai, jaise key se upsert ya status set karna.
  • Pure reads.Sirf reads.

Pick another pattern whenDoosra pattern kab lein

  • Kafka-to-Kafka stream processing: Kafka transactions give exactly-once inside Kafka.Kafka-to-Kafka stream processing: Kafka transactions Kafka ke andar exactly-once dete hain.
  • Messages get lost on the sending side: Outbox.Bhejne wali side pe messages kho jaate hain: Outbox.
08

Saga: choreography

Services react to each other's events and compensate on failure.Services ek doosre ke events pe react karti hain aur failure pe compensate karti hain.

Use whenKab use karein

  • A business flow spans two to four services with simple, linear steps.Business flow do se chaar services me hai, simple aur seedhe steps ke saath.
  • Teams want loose coupling: services share only event names.Teams ko loose coupling chahiye: services sirf event names share karti hain.

Avoid whenKab avoid karein

  • Long or branching flows, timeouts, or frequent questions like where is my order.Lambe ya branching flows, timeouts, ya baar-baar aane wala sawaal ki mera order kahan hai.
  • The whole change fits in one service and one database.Poora change ek service aur ek database me fit ho jaata hai.

Pick another pattern whenDoosra pattern kab lein

  • Complex flows: Saga orchestration.Complex flows: Saga orchestration.
  • Everything lives in one database: a plain ACID transaction, the best option of all.Sab kuch ek database me hai: simple ACID transaction, sabse behtar option.
  • Two-phase commit only inside one database or a few XA resources you fully control.Two-phase commit sirf ek database ke andar ya kuch XA resources ke saath jo poori tarah tumhare control me hon.
09

Saga: orchestration

A central coordinator drives every step and every compensation.Ek central coordinator har step aur har compensation chalata hai.

Use whenKab use karein

  • Many steps, branches, timeouts, retries, or flows that run for days.Bahut steps, branches, timeouts, retries, ya dinon tak chalne wale flows.
  • You need one place to see and audit the state of every flow.Har flow ki state dekhne aur audit karne ke liye ek jagah chahiye.

Avoid whenKab avoid karein

  • Two or three simple steps. Choreography is lighter.Do ya teen simple steps. Choreography halki hai.
  • The orchestrator starts holding other services' business rules.Orchestrator doosri services ke business rules apne andar rakhne lage.

Pick another pattern whenDoosra pattern kab lein

  • Simple flows: Saga choreography.Simple flows: Saga choreography.
  • Very long flows with human steps: a workflow engine such as Temporal or Camunda.Human steps wale bahut lambe flows: Temporal ya Camunda jaisa workflow engine.

Scale the dataData ko scale karo

More reads, more writes, and less load on each database.Zyada reads, zyada writes, aur har database pe kam load.

10

Replication (read replicas)

Copy the database to spread reads and survive failures.Reads baantne aur failure jhelne ke liye database ki copies banao.

Use whenKab use karein

  • Read-heavy traffic, around 70% reads or more, that can accept a little lag.Read-heavy traffic, lagbhag 70% ya zyada reads, jo thoda lag seh sake.
  • You need high availability and a standby to fail over to.High availability aur fail over ke liye ek standby chahiye.

Avoid whenKab avoid karein

  • Writes are the bottleneck. Every replica has to apply every write.Bottleneck writes hain. Har replica ko har write apply karna padta hai.
  • A read must always be perfectly fresh. Send that read to the primary.Read hamesha bilkul fresh chahiye. Woh read primary pe bhejo.

Pick another pattern whenDoosra pattern kab lein

  • A few hot keys cause the load: Caching.Load kuch hot keys se aa raha hai: Caching.
  • Too many writes or too much data: Sharding.Bahut zyada writes ya bahut zyada data: Sharding.
  • Reads need a different shape: CQRS.Reads ko alag shape chahiye: CQRS.
11

Sharding

Split the data across many databases by a key.Ek key ke hisaab se data kai databases me baanto.

Use whenKab use karein

  • Writes or data size exceed one machine, after the cheaper fixes.Saste fixes ke baad bhi writes ya data size ek machine se bahar hai.
  • A natural key, such as customer_id or tenant_id, appears in almost every query.customer_id ya tenant_id jaisi natural key lagbhag har query me hai.

Avoid whenKab avoid karein

  • The data still fits one machine. Tune queries, scale up and partition first.Data abhi ek machine me fit hai. Pehle queries tune karo, scale up karo aur partition karo.
  • Heavy joins across entities and ad-hoc analytics.Entities ke beech heavy joins aur ad-hoc analytics.

Pick another pattern whenDoosra pattern kab lein

  • The load is mostly reads: Replication or Caching.Load zyaadatar reads ka hai: Replication ya Caching.
  • You want sharding handled for you: distributed SQL such as Citus, Vitess or CockroachDB.Sharding koi aur handle kare: Citus, Vitess ya CockroachDB jaisa distributed SQL.
  • Analytics across all the data: a CQRS read model or a data warehouse.Saare data pe analytics: CQRS read model ya data warehouse.
12

Caching (cache-aside)

Serve hot reads from memory.Hot reads memory se serve karo.

Use whenKab use karein

  • Read-heavy data that may be slightly stale: catalogs, profiles, settings.Read-heavy data jo thoda stale chal jaaye: catalogs, profiles, settings.
  • A few hot keys take most of the traffic.Zyaadatar traffic kuch hot keys pe aata hai.

Avoid whenKab avoid karein

  • Values used for decisions must be exact, like a balance or the stock at checkout.Decision wali values bilkul exact honi chahiye, jaise balance ya checkout pe stock.
  • Keys change more often than they are read.Keys padhne se zyada baar badalti hain.

Pick another pattern whenDoosra pattern kab lein

  • Broad read load across many rows: Read replicas.Bahut saari rows pe faila read load: Read replicas.
  • Many writers make invalidation hard: invalidate from the log with CDC.Kai writers ki wajah se invalidation mushkil: CDC se log se invalidate karo.
  • Complex read shapes: CQRS.Complex read shapes: CQRS.
