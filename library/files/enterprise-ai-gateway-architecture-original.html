Enterprise AI Gateway & Orchestrator — Architecture Guide

High-Level Design, Low-Level Design and Architecture Decisions

Status: implemented. The code in this repository follows this design, and where implementation refined a decision the text says so. Stack verified on 16 September 2026 against the Spring Boot v4.1.1 and Spring AI v2.0.1 source trees.

This guide is written for the engineer who has to defend every line of the system in front of a customer or an interviewer. Sections 1 to 3 are the design you would draw on a whiteboard in the first ten minutes. Section 4 is the low-level design as implemented, with the class names you will find in the code; section 12 maps each part to its source and tests. Section 5 records each decision together with the alternatives that were rejected, because experienced interviewers probe the rejected options harder than the chosen one. Major sections end with an Interview lens note that says what a Forward Deployed Engineer (FDE) or AI Developer interviewer is really testing.

1. Context and goals

1.1 The problem

Most enterprises no longer buy from one model vendor. Legal wants data residency, finance wants predictable cost, product teams want the best model for each task, and security wants to know exactly which data left the building. When every team calls OpenAI, Anthropic and Google directly, the result is duplicated SDK code, keys scattered across services, no failover when a vendor has an incident, no single view of token spend, and answers that cannot see internal documents.

The gateway is one governed entry point. It routes each request to the right provider and model, grounds answers in private documents through retrieval-augmented generation (RAG), keeps conversation memory, lets models call approved tools (native Java methods and Model Context Protocol servers), and makes every token observable. It is deliberately a modular monolith: a single deployable with strict package boundaries. That is the right starting shape for a small team, and the same boundaries become the seams if the system is ever split into services.

1.3 Assumptions and constraints

Tenancy is demonstration-grade: the tenant comes from an X-Tenant-Id header, and it must be replaced by a claim from an authenticated principal before any real deployment. Secrets arrive only as environment variables. Embeddings are pinned to OpenAI (ADR-005), so RAG needs an OpenAI key even when chat is routed to Claude or Gemini. Each provider can be switched off on its own with OPENAI_ENABLED, ANTHROPIC_ENABLED or GEMINI_ENABLED set to false, and startup fails fast only for providers that are enabled but have no key. PostgreSQL with the pgvector extension and Redis Stack 7+ run in Docker locally and as managed services in production.

3.3 The four core flows

Chat. A client posts a message. The API layer resolves the tenant and a server-side conversation ID, the routing policy plans an ordered list of targets, and the orchestrator runs the advisor chain on that provider's ChatClient. Tokens stream back as SSE events. If the provider fails before the first token, the orchestrator replays the same request on the next candidate.

Ingestion. An administrator uploads a file. The service hashes it and skips documents that have not changed. Otherwise it reads, splits and tags the text, embeds the chunks, upserts them under deterministic IDs, and prunes chunks left over from the previous version.

Outbound tools. When the model asks for a tool, ToolCallingAdvisor executes it only if the tool was attached to that request, whether it is a native method or backed by an MCP server, and it loops until the model produces an answer or a call cap is reached.

Inbound MCP. An IDE agent connects to /mcp and calls a published tool, such as knowledge search, which runs through the same tenant filters as the REST API.

Interview lens. Interviewers listen for the boundary between what the framework does (provider calls, the tool loop, vector maths) and what your gateway owns: policy about who may use which model, tool and data, and what happens when something fails. That policy layer is the product; everything else is plumbing you chose not to write.

Four choices in this diagram deserve an explanation.

RoutingPolicy is an interface because routing rules are where customers differ. A bank pins regulated tenants to one vendor, a retailer routes by cost, a research team routes by capability. Much real FDE work is writing exactly this kind of customer-specific policy, and the tier-plus-fallback-order implementation is only the default.

RouteDecision is an immutable record that carries its hop count and whether it was pinned. Failover then becomes a pure function of the plan, the error and two facts about the turn (has a token been sent, has a tool run), so every rule in §4.3 can be unit-tested without HTTP, containers or API keys.

ChatClientFactory exists because spring.ai.chat.client.enabled is false (several ChatModel beans make the auto-configured builder ambiguous), so nothing builds ChatClients for us. The one-argument ChatClient.builder(chatModel) uses a no-op ObservationRegistry; the factory calls the overload that takes the real registry, otherwise ChatClient and advisor spans quietly disappear from traces.

ModelInvoker is a port in the hexagonal sense. The orchestrator streams framework-free ModelChunk records, and SpringAiModelInvoker is the only class that turns a routing decision into ChatClient calls: model override, memory key, tenant filter, tools. Swapping Spring AI for something else, or scripting providers in a test, touches nothing in the failover logic.

A related rule governs request options. Per-request overrides use exactly one portable ChatOptions field: the model. Even the token limit stays in per-provider defaults, because OpenAI reasoning models reject max_tokens in favour of max_completion_tokens. Provider-native settings such as OpenAI reasoning effort, Gemini thinking level or Anthropic inference geography live in each provider's defaults, because a request that carries OpenAI-only options cannot be replayed on Claude when failover happens.

Pinned means pinned. A provider pinned by the caller or by tenant policy, for example to keep EU data with one vendor, never fails over. Quietly sending regulated data to a different vendor is a compliance incident, so the gateway returns a retryable error and lets a human decide. A caller asking for a different provider than the tenant's pin gets a 403, never a silent re-route.

Failover only before the first token. Once text has reached the user, switching providers would splice two models' answers into one response with different styles and possibly contradictory facts. After the first token the gateway emits an SSE error event instead, and the client may retry the whole turn.

Only fail over when another provider could succeed. Rate limits (429), server errors (5xx), timeouts, connection failures and a missed first-token deadline qualify. Validation and authentication errors do not, because they either fail identically everywhere or indicate a bug in the gateway.

Two different clocks. The first-token deadline (gateway.routing.first-token-timeout, 20 s) is separate from the SDK's whole-request timeout (120 s). A long answer that is streaming normally must never be cut off, while a request that has produced nothing after 20 seconds is almost certainly stuck. The worst case for an unpinned request is therefore about three first-token deadlines; a typical 429 or 5xx fails over in well under a second.

No failover once a tool has run. A model can call a tool and then fail before producing text. Replaying the turn elsewhere would run the tool again, so the orchestrator treats any tool execution as the point of no return. Tool time also pauses the first-token clock, because a slow tool is not a stuck provider.

Cooldown instead of hammering. A provider that just failed is skipped for a short cooldown, tracked in ProviderRegistry. When every enabled provider is cooling down, they are tried anyway: a cooldown is a hint, not proof of an outage. This is a deliberately small circuit breaker; Resilience4j is the upgrade path if half-open probing and sliding windows are needed.

4.4 Advisor chain order

In Spring AI, advisors with lower order values run first on the way in and last on the way out. The order below is part of the design, not a style preference: getting it wrong produces correct-looking answers with hidden cost and data-handling bugs.

Order Advisor Runs Why it sits here
HIGHEST_PRECEDENCE + 100 GuardrailAdvisor (ours) Once per turn Size limits, prompt-injection heuristics and redaction policy block a request before any token is spent
HIGHEST_PRECEDENCE + 200 ConversationMemoryAdvisor (ours) Once per turn Loads the history window before the call; stores the user message and final answer together, only after the turn succeeds
HIGHEST_PRECEDENCE + 250 (set explicitly) TenantRetrievalAdvisor (ours) wrapping QuestionAnswerAdvisor Once per turn Retrieves once per user turn with a server-side tenant filter; degrades or fails according to the RAG mode
HIGHEST_PRECEDENCE + 300 (default) ToolCallingAdvisor (auto-registered) Loops Executes tool calls and re-invokes the advisors after it on every iteration

Prompt logging in the local profile uses Spring AI's observation settings rather than a logging advisor, so nothing extra runs inside the tool loop.

Three facts make this order necessary.

First, ToolCallingAdvisor is recursive. On each tool iteration it re-runs only the advisors ordered after it. QuestionAnswerAdvisor has a default order of 0, which places it after the tool loop; left at its default it would issue a fresh embedding call and vector search on every tool iteration and re-augment the prompt each time. Setting it to +250 makes retrieval happen once per user turn.

Second, memory runs before retrieval, so the stored user message is the original question rather than the question inflated with retrieved chunks. Persisting retrieved text into memory would bloat every later prompt, keep stale document versions alive after re-ingestion, and copy confidential passages into a second store with a different retention policy.

Third, memory is written only when a turn succeeds. Spring AI's built-in MessageChatMemoryAdvisor stores the user message in before(), ahead of the model call; with cross-provider failover a failed attempt would leave the question in memory and the replay would store it again. The gateway's advisor loads history first and writes the question and the final answer together afterwards. It sits outside the tool loop, so intermediate tool calls and results never reach memory, which is right for a gateway because tool results are often large and sensitive. One wiring trap sits next to it: the memory window must not be published as a ChatMemory bean, because the Redis repository auto-configuration backs off whenever one exists.

Interview lens. Advisor order is an excellent question to answer well, because it separates people who have run an LLM system in production from people who have read a tutorial. Explain the recursive tool loop, then show the cost bug that a default order creates.

The client sees a small, stable event contract regardless of which provider answered:

SSE event Sent when Payload
route Before the first token, and again after a failover Provider, model, tier, hop
token For each text delta Text fragment
tool A tool starts or finishes (reported by GovernedToolCallback) Tool name and status only, never arguments
error Any failure that ends the turn: after the first token, not failover-eligible, or no candidate left HTTP-style status, stable code, message, retryable, and partial when text was already sent
done Stream completed Conversation ID, provider, model, hops, usage (input, output, cached input), finish reason, first-token and total latency, ragUsed, memoryUsed

SSE comment lines are sent every 15 seconds while tools run, so proxies and load balancers do not close a connection that is quiet but healthy. The stream is requested with POST rather than GET, because prompts do not belong in URLs, browser history or access logs. The browser EventSource API only supports GET, so the dashboard reads the POST response body with fetch() and a stream reader.

  end

Hash before anything else. Embedding is the dominant ingestion cost, so re-uploading an unchanged 300-page PDF should cost zero tokens. The registry lookup makes ingestion idempotent from the caller's point of view.

Deterministic chunk IDs. PgVectorStore writes with INSERT ... ON CONFLICT (id) DO UPDATE. Chunk IDs derived from tenant, source and chunk index with UUID.nameUUIDFromBytes (a name-based UUID, because the id column is a UUID) make retries safe and let a new version overwrite the old one in place.

Upsert, then prune. Deleting the old chunks first would leave the document missing from search if embedding fails halfway through. Writing first means readers always see either the complete old version or a partly updated one, and a final filtered delete removes chunks whose docHash no longer matches, such as the tail of a document that got shorter.

Know when to go asynchronous. Tika parsing runs on the request thread for simplicity. The first scaling step is to return 202 Accepted with a job ID and move parsing and embedding to a worker, which is also why the Tika dependency is flagged in pom.xml as a candidate for a separate service.

Both tables are created by the Flyway migration V1__vector_store_and_document_registry.sql, in every environment, and PgVectorStore only validates the schema at startup. vector_store follows Spring AI's schema (a UUID key, the chunk text, a vector(1536) column with an HNSW index using cosine distance, and the same index name) with one deliberate change: metadata is jsonb rather than json. PgVectorStore writes metadata as ?::jsonb and its schema validator checks column names only, so the change is invisible to the framework. The relationship lives in metadata rather than a foreign key, because the vector table is owned by the framework and should stay replaceable.

Two retrieval details matter at scale. Metadata filters compile to metadata::jsonb @@ '<jsonpath>'::jsonpath; on the jsonb column a GIN index with jsonb_path_ops can serve that operator, which also speeds up the filtered deletes that prune old document versions. More importantly, an HNSW search applies the filter to the candidates it finds, so a selective filter such as a small tenant inside a large table can return fewer than top-k results. The mitigations, in order of effort, are pgvector 0.8's iterative index scans and partitioning by tenant.

4.9 Configuration design

Configuration has two layers. spring.ai.* configures the framework, and gateway.* is our own contract, bound to validated @ConfigurationProperties records. Framework keys reference our keys, for example spring.ai.openai.chat.model: ${gateway.providers.openai.models.balanced}, so each fact has exactly one home.

Provider keys use a sentinel default (not-configured). Without it, auto-configuration for a provider you have no key for would stop the application during startup, before our code runs. With it, every bean starts, and ProviderRegistry fails fast with a readable message only when a provider is enabled but still has no credentials. Switching a provider off is one environment variable.

Profiles add rather than replace. The base document holds production-safe defaults: no prompt logging, no schema creation, no unauthenticated MCP endpoint. The local profile turns on developer conveniences, and the prod profile adds requirements such as a mandatory Redis password and a mandatory gateway API key. A secret with no default, like ${REDIS_PASSWORD}, is deliberate: a missing secret should stop the deployment, not produce a gateway that half works.

Interview lens. Expect "what happens when a key is missing?" and "how do you roll out a new model?" Good answers are mechanical: sentinel plus validator for the first, a one-line tier mapping change behind a canary for the second.

5. Architecture decision records

Each record states the context, the decision, the options that lost and why, and the consequences you accept. All are Accepted as of 16 September 2026.

ADR-001 — Java 25 and Spring MVC on virtual threads, not WebFlux

Context. The workload is dominated by waiting. A model call takes seconds, retrieval waits on an embedding API and PostgreSQL, memory waits on Redis, and Tika parsing is blocking by nature. The gateway must hold many concurrent streams without turning every dependency call into reactive code.

Decision. Spring MVC with spring.threads.virtual.enabled: true on Java 25. Streaming endpoints return Flux, which Spring MVC adapts to an asynchronous response.

Option Why it lost
WebFlux end to end Best raw efficiency for extreme fan-out, but JDBC, Jedis and Tika block, so each call needs a hop to a bounded elastic scheduler; debugging and context propagation get harder
Platform threads with a large pool Each thread reserves a large stack, so concurrent streams hit memory and pool limits long before CPU does
Java 21 Has virtual threads, but still pins carrier threads inside synchronized, which drivers and SDKs use internally; fixed only from JDK 24

Consequences. Imperative code stays easy to read, debug and test. Because threads are now cheap, the scarce resources move: the HikariCP pool (20 connections) becomes the real bulkhead in front of PostgreSQL, and each vendor SDK's HTTP client has its own concurrency limits that must be load-tested. One example to check early is OkHttp, used by the Anthropic SDK, whose default dispatcher allows only five concurrent asynchronous requests per host unless the SDK raises it. Revisit if one instance must hold tens of thousands of concurrent streams.

ADR-002 — A router facade over one ChatClient per provider

Context. Three ChatModel beans exist, while Spring AI's auto-configured ChatClient.Builder assumes one. The gateway needs per-request provider choice, failover, and one set of policies applied to every provider.

Decision. Disable the auto-configured builder. ChatClientFactory builds one ChatClient per enabled provider with shared advisors, tools and the real ObservationRegistry, and the orchestrator picks among them for each attempt in the routing plan.

Option Why it lost
External LLM proxy (LiteLLM or a cloud AI gateway) Quick and language-neutral, but it would decide failover without knowing whether tokens already reached the user or a tool already ran, and memory, RAG and tool policy would live in a different system
spring.ai.model.chat selection Picks one provider at startup; no runtime routing at all
Calling vendor SDKs directly Full control, at the price of re-implementing memory, retrieval, the tool loop and observations three times

Consequences. Adding a provider means a starter, a properties block and an enum constant. We own the ChatClient observability wiring, which the factory makes explicit. Revisit if non-JVM teams need the same routing; a thin proxy in front of this gateway would then be reasonable, but the policies stay here.

ADR-003 — A bounded retry and failover budget

Context. Retries multiply across layers: SDK retries, framework retries and gateway failover hops. The defaults are generous. OpenAI's SDK retries three times, and Spring AI's RetryTemplate defaults to ten attempts with backoff up to three minutes. For interactive chat, a user waiting minutes is worse than a fast, clear error, and a retry storm against a vendor that is already rate-limiting makes the incident worse.

Decision. One SDK retry per provider attempt. spring.ai.retry.max-attempts: 2 with at most five seconds of backoff for Gemini. Cross-provider failover only before the first token, at most two hops, a 20-second first-token deadline, and a short cooldown for a provider that just failed.

Option Why it lost
Keep the defaults Minutes of silent waiting before an error or a failover
No retries at all Momentary network blips become user-visible errors
Fail over at any point in the stream Spliced answers from two models and duplicated tool side effects

Consequences. Worst-case latency is predictable and written down. Rate-limit incidents shift load to other vendors instead of amplifying it. One subtle rule follows: a model can call a tool and then fail before producing text, so replaying the turn on another provider would run the tool twice. The implementation takes the conservative reading: failover is disabled for a turn once any tool has run, and side-effecting tools are additionally idempotent per conversation, as the demo ticket tool shows.

ADR-004 — PostgreSQL with pgvector, not a dedicated vector database

Context. Retrieval needs similarity search plus metadata filtering, tenant isolation, backups and operational familiarity, at a scale of up to low tens of millions of chunks for a first customer.

Decision. pgvector with an HNSW index and cosine distance through PgVectorStore, in the same PostgreSQL that holds the document registry.

Option Why it lost
Pinecone, Weaviate, Qdrant or Milvus Stronger at very large scale with richer hybrid search, but a second datastore to secure, back up, pay for and keep consistent with the registry
Redis vector search Already deployed for memory, but a memory-priced store is expensive for large corpora
Elasticsearch or OpenSearch Excellent lexical and hybrid ranking; heavy to operate unless the customer already runs it

Consequences. Registry and vectors share one transactional store, SQL is available for debugging, and existing backup and HA tooling applies. HNSW on the vector type supports up to 2,000 dimensions, which constrains future embedding models; larger ones need halfvec or reduced dimensions. Filtered search needs the care described in §4.7. Revisit beyond roughly 50 million chunks, or when hybrid lexical and vector ranking becomes a core requirement.

ADR-005 — One pinned embedding model, independent of chat routing

Context. Chat routing can change on every request, but the vector index cannot. Vectors from different embedding models live in different spaces. A query embedded by one model and compared with chunks embedded by another returns confident nonsense and no error at all.

Decision. All ingestion and retrieval use OpenAI text-embedding-3-small at 1,536 dimensions, selected once in configuration and never routed.

Option Why it lost
Route embeddings like chat Silently corrupts retrieval the first time a fallback provider embeds a query
Gemini embeddings A valid choice; OpenAI was chosen because its 1,536 dimensions fit HNSW limits and the model is inexpensive
Self-hosted embeddings Removes an external dependency and per-token cost, but adds capacity planning for inference hardware

Consequences. RAG depends on OpenAI availability even when Claude or Gemini answers, so an embedding outage must degrade gracefully (§9). Changing the embedding model is a migration: re-embed into a new table, compare results in shadow mode, then switch. The embedding model name is stored in chunk metadata so a mixed index can be detected.

ADR-006 — Redis-backed windowed memory with a TTL

Context. Memory must survive restarts, be shared by every instance, stay small enough to keep prompts cheap, and expire.

Decision. RedisChatMemoryRepository behind MessageWindowChatMemory (last 20 messages), a 7-day TTL, gateway-specific key prefix and index name, conversation IDs built on the server from the tenant, read and written by the gateway's own ConversationMemoryAdvisor (§4.4), and Spring AI 2.0.1 as the minimum version.

Option Why it lost
In-memory repository Lost on restart and wrong as soon as there are two instances
JDBC memory in PostgreSQL Durable and queryable with one less datastore, but no native expiry and a heavier write on every turn
Vector-store memory Useful for very long histories, but adds an embedding call per message and makes recall fuzzy

Consequences. Reads and writes are fast and expiry is automatic. Two Redis clients exist, Spring Data Redis for the health check and Jedis for memory, and both point at one configured instance. The memory auto-configuration maps only host, port and credentials, so TLS to a managed Redis requires declaring our own RedisClient bean. Spring AI 2.0.1 fixed a RediSearch tag-injection flaw that could expose other conversations, which is why the version floor belongs to this decision. Revisit when Spring AI 2.1 delivers the session-aware memory it has announced as the successor to ChatMemory.

ADR-007 — MCP and tools behind explicit allow-lists

Context. The gateway is an MCP client, calling tools on downstream servers, and an MCP server, offering capabilities to IDE agents. Tools turn text into actions, which means prompt injection becomes a way to act rather than only a way to talk.

Decision. The server publishes only explicit @McpTool methods (tool-callback-converter: false), never re-exports downstream tools (expose-mcp-client-tools: false), uses Streamable HTTP, is disabled by default, and sits behind the gateway API key when enabled. Tools are attached per request from a tenant allow-list, the global resolution fallback stays off, and tool calls are capped at 12 per turn and 5 per tool.

Option Why it lost
Auto-publish every ToolCallback bean Any internal tool becomes remotely callable the moment someone adds a bean
Re-export downstream MCP tools A confused deputy: an external caller borrows the gateway's credentials to reach systems it could not reach directly
Default call limits (150 per turn, 40 per tool) Sized for long batch agents; in chat a runaway loop burns tokens for minutes before anyone notices

Consequences. Every remotely callable capability is a deliberate code change that shows up in review, and tool payloads stay out of spans. The shared API key is the first layer on /mcp; the production path is OAuth2, where Spring AI's WebMvc transport hands lower-cased header names to its security validator, plus the server-session caps added in 2.0.1. Tool context is never forwarded to downstream MCP servers, because Spring AI's MCP callbacks send it as _meta by default.

ADR-008 — Privacy-first observability

Context. Prompts, completions, tool arguments and retrieved chunks routinely contain personal and confidential data. Logs and traces are copied to more systems, kept longer and read by more people than the primary stores.

Decision. Content capture is off in the base profile: prompt and completion logging, tool content in spans, and vector query responses are all disabled. Only the local profile turns prompt and completion logging on. Metrics carry provider, model, tier and outcome, never content.

Option Why it lost
Log everything and redact later Redaction is never complete, and the copies already exist
No AI-specific observability Cost, latency and failover behaviour become impossible to explain to a customer

Consequences. Investigating a production answer needs a deliberate, audited path such as a time-boxed debug flag per tenant. Tenant is used as a metric tag only while the number of tenants is small, because high-cardinality tags overload Prometheus.

ADR-009 — Environment secrets and fail-fast configuration

Context. Keys leak through repositories, container images and logs, and Spring Boot misconfiguration fails silently by default.

Decision. Secrets only from environment variables; sentinel defaults so auto-configuration can start; typed and validated gateway.* records; a startup check in ProviderRegistry that fails for enabled providers without credentials; production secrets with no default at all.

Option Why it lost
Keys in application.yml or a committed .env The most common leak in public portfolio repositories
A secret manager integration from day one Right for production but heavy for this stage; the environment-variable contract lets any platform inject secrets from Vault or a cloud manager later

Consequences. Local setup needs a documented set of variables, and misconfiguration shows up at startup with a clear message instead of at the first customer request.

7. Security and multi-tenancy

Tenant identity comes from a claim on the authenticated principal in any real deployment; the X-Tenant-Id header exists only for demonstrations. Once resolved, the tenant is enforced at four points, and none of them trusts the client.

The retrieval filter tenantId == '<tenant>' is built on the server and combined with any narrowing filter the client is allowed to send, so a client can restrict results but never widen them. Conversation IDs are composed on the server from the tenant and a validated UUID, so guessing an ID reveals nothing. Tools receive the tenant through Spring AI's tool context and authorise their own actions. The MCP server's tools call the same tenant-filtered retrieval service as the REST API, so a capability published to IDE agents inherits the same isolation; for now its tenant is fixed per API key.

Retrieved documents and tool results are untrusted input, because anyone who can write a document can try to write instructions for the model. The mitigations are layered rather than absolute: tools are attached per request from an allow-list, the resolution fallback that could run unadvertised tools is off, calls are capped, side-effecting tools require idempotency keys or explicit confirmation, and the system prompt tells the model that retrieved text is reference data, not instructions. Staying on Spring AI 2.0.1 or later is part of the security posture: that release fixed seven CVEs, three of them in components this design relies on (Redis chat memory, tool dispatch and MCP server sessions).

10. What to revisit as the system grows

The first split is ingestion: parsing and embedding move to an asynchronous worker fed by a queue, which also removes the heavy Tika dependency from the request-serving service. Retrieval quality improves next with hybrid lexical and vector search, a re-ranking step and query rewriting on the fast tier. Per-tenant rate limits and token budgets in Redis protect shared provider quotas, and a semantic response cache can remove repeated calls for frequent questions, provided its keys are tenant-scoped. Distributed tracing with OpenTelemetry joins gateway spans to provider latency. Finally, memory should move to the session-aware model planned for Spring AI 2.1 once it is released, and routing policies could become data managed per tenant instead of configuration.

11. Interview questions this design prepares you for

Why not put LiteLLM or a cloud AI gateway in front of the providers and stop there? A proxy solves key management and basic fallback, but it cannot see what the application already did. It does not know whether tokens reached the user, whether a tool ran, or which tenant's documents were retrieved, so it cannot apply the failover rules in §4.3 or the tenant rules in §7. Those policies belong where the context lives.

OpenAI returns 429 halfway through a streamed answer. What happens? Nothing is spliced. Because the first token has been sent, the gateway stops, emits an error event marked retryable, and records the failure so the provider cools down. Had the 429 arrived before the first token, the router would have replayed the turn on Anthropic, unless the tenant was pinned to OpenAI.

How do you guarantee one tenant never sees another tenant's documents? The tenant filter is added on the server to every similarity search and cannot be removed by the client, conversation IDs are built from the tenant, and tools authorise with the tenant from the tool context. At scale, selective tenant filters can under-fill results, so iterative index scans or per-tenant partitions keep answers complete as well as isolated.

Why does advisor order matter? Because the tool loop is recursive. Anything ordered after ToolCallingAdvisor runs on every tool iteration, so a retrieval advisor at its default order embeds and searches repeatedly. Memory placed after retrieval would persist retrieved chunks. Both bugs pass functional tests and show up only on the invoice or in a data-handling review.

How do you control cost? In layers: tier routing so most traffic uses balanced or fast, per-provider output caps, tool-call caps, a bounded retry budget, hash-based ingestion so unchanged documents cost nothing, a 20-message memory window, and cost metrics that make overspend visible within minutes.

Why virtual threads instead of WebFlux for a streaming product? The system mostly waits on blocking dependencies. Virtual threads give high concurrency with ordinary code, and JDK 24 removed the pinning problem that made Java 21 risky. The trade-off is that limits move to connection pools and SDK HTTP clients, which have to be sized and load-tested.

What are the risks of MCP, and how are they mitigated here? Remote callers invoking tools they should not see, confused-deputy access through re-exported tools, prompt injection that triggers actions, and runaway loops. The design publishes only explicit @McpTool methods, never re-exports, attaches tools per request from allow-lists, caps calls, keeps tool content out of telemetry, never forwards tool context to remote servers, and puts the endpoint behind the gateway API key.

The team wants to switch embedding models. What breaks? Every stored vector becomes incomparable with new query vectors, and nothing throws an error. It is a data migration: embed into a new table, compare retrieval quality on a golden question set, switch reads, then retire the old index. Storing the model name in chunk metadata makes accidental mixing detectable.
