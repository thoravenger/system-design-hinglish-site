01

Redis kya hai, aur interview me ise kab uthana hai

Foundation. Yahan galti karoge to poora HLD hil jayega. Redis ek in-memory, single-threaded, key-value data structure server hai — sirf “ek cache” nahi.

Problem samasya · what breaks

Ek product-catalog service hai. Har page view par Postgres se same 200 rows padhi jaati hain. Traffic 500 RPS se 12,000 RPS chala gaya, aur ab:

  • Har read = network hop + planner + B-tree index lookup + disk/page-cache read. p99 62 ms ho gaya.
  • Connection pool (HikariCP, size 50) exhausted — threads pool ka wait kar rahe hain, not the DB.
  • DB CPU 91%. Vertical scaling costly hai aur read replica lag 3s de raha hai.
  • Read:write ratio ~200:1 hai. Matlab hum same answer baar-baar compute kar rahe hain.

English: we are paying full database cost for an answer that almost never changes.

p99 read62 ms
DB CPU91%
Reads wasted~99%

Solution hal · what to do

Beech me ek in-memory layer lagao. Redis RAM me data rakhta hai, ek hi thread par commands execute karta hai (no lock contention), aur intra-datacenter 0.1–0.5 ms me jawab deta hai.

  • Data structure server: String, Hash, List, Set, Sorted Set, Bitmap, HyperLogLog, Stream, Geo — operations server-side hote hain, isliye network round trips bachte hain.
  • Atomicity free: single-threaded execution ki wajah se INCR, SETNX, Lua script sab atomic hain.
  • TTL built-in: har key par expiry, so memory self-cleaning hai.
  • Roles: cache, session store, rate limiter, distributed lock, leaderboard, queue/stream, dedupe filter.

English: Redis is not “just a cache”. It is a low-latency data structure server you can also use as a cache.

package com.example.cache.config;

import com.fasterxml.jackson.annotation.JsonTypeInfo;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.jsontype.impl.LaissezFaireSubTypeValidator;
import io.lettuce.core.ClientOptions;
import io.lettuce.core.SocketOptions;
import io.lettuce.core.TimeoutOptions;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.connection.RedisStandaloneConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceClientConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.StringRedisSerializer;

import java.time.Duration;

@Configuration
public class RedisConfig {

    /**
     * Lettuce = netty based, thread-safe, non-blocking. Jedis ke jaisa
     * har thread ke liye alag connection nahi chahiye.
     */
    @Bean
    public RedisConnectionFactory redisConnectionFactory() {

        RedisStandaloneConfiguration serverConfig =
                new RedisStandaloneConfiguration("redis-primary.internal", 6379);

        SocketOptions socketOptions = SocketOptions.builder()
                .connectTimeout(Duration.ofMillis(300))   // TCP connect budget
                .keepAlive(true)
                .build();

        ClientOptions clientOptions = ClientOptions.builder()
                .socketOptions(socketOptions)
                .autoReconnect(true)
                // Redis down ho to command queue me infinite mat rakho -> fail fast
                .disconnectedBehavior(ClientOptions.DisconnectedBehavior.REJECT_COMMANDS)
                .timeoutOptions(TimeoutOptions.enabled(Duration.ofMillis(150)))
                .build();

        LettuceClientConfiguration clientConfig = LettuceClientConfiguration.builder()
                .clientOptions(clientOptions)
                .commandTimeout(Duration.ofMillis(150))   // cache ke liye 150ms bahut hai
                .build();

        return new LettuceConnectionFactory(serverConfig, clientConfig);
    }

    /**
     * Key hamesha plain String rakho -> redis-cli me debug karna aasan.
     * Value JSON rakho -> language-agnostic aur human readable.
     */
    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory connectionFactory) {

        ObjectMapper objectMapper = new ObjectMapper();
        objectMapper.activateDefaultTyping(
                LaissezFaireSubTypeValidator.instance,
                ObjectMapper.DefaultTyping.NON_FINAL,
                JsonTypeInfo.As.PROPERTY);

        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(connectionFactory);
        template.setKeySerializer(new StringRedisSerializer());
        template.setHashKeySerializer(new StringRedisSerializer());
        template.setValueSerializer(new GenericJackson2JsonRedisSerializer(objectMapper));
        template.setHashValueSerializer(new GenericJackson2JsonRedisSerializer(objectMapper));
        template.afterPropertiesSet();
        return template;
    }
}
Har line ka matlab — what each line is actually doing
connectTimeout(300ms)
TCP handshake ka budget. Isse zyada lagta hai to node hi sick hai — wait karne ka fayda nahi.
REJECT_COMMANDS
Sabse important line. Redis disconnect ho to Lettuce by default commands ko queue karta hai; wo queue memory kha jaati hai aur latency chhupa deti hai. Reject karoge to exception turant aayega aur fallback-to-DB path chalega.
commandTimeout(150ms)
Cache ka kaam hai fast fail. Agar Redis 150ms me jawab nahi de paaya, DB call karna hi sasta hai. Interview me yeh number defend karna aata hai: it must be smaller than your upstream SLO.
StringRedisSerializer for keys
Default JdkSerializationRedisSerializer keys ko binary bana deta hai. Phir redis-cli KEYS me kuch samajh nahi aata aur cross-language clients tut jaate hain.
GenericJackson2JsonRedisSerializer
JSON + type info. Debuggable hai. Trade-off: JDK serialization se bada payload, Protobuf/Kryo se slow. High-throughput par isko replace karna pehla optimization hota hai.
activateDefaultTyping
Polymorphic objects ko wapas correct class me deserialize karne ke liye. Security note: LaissezFaireSubTypeValidator untrusted data ke liye safe nahi — sirf apne likhe hue values par use karo.

Kab lagayein (apply)

  • Read:write ratio 10:1 se zyada ho.
  • Thoda staleness chalega (seconds tolerable).
  • Access skewed ho — 20% keys 80% traffic lein.
  • Tight latency SLO (p99 < 10 ms) ho.
  • Aisa computation ho jo mehnga hai par deterministic (aggregations, feed, pricing).

Kab chhod dein (ignore)

  • Write-heavy, read-rare data — cache hamesha cold rahega.
  • Strong read-after-write consistency mandatory ho (ledger balance, seat inventory ka final commit).
  • Dataset uniform-random access ho — koi hot set hi nahi, hit ratio 15% aayega.
  • Dataset RAM me fit hi nahi hota aur cost DB scaling se zyada padta hai.
  • Sirf 500 RPS hai — ek extra moving part ka ops cost justify nahi hota.

Faisla kaise lein (why)

Cache ek bet hai: aap kehte ho “yeh answer dobara maanga jayega, tab tak galat nahi hoga.” Agar dono me se koi ek shart nahi hai, cache profit nahi, sirf ek naya failure mode hai.

English: a cache trades correctness-freshness for latency. Only take the trade when reuse is likely and staleness is survivable.

02

Sahi data structure chunna — 90% Redis interviews yahin phaste hain

Ek hi problem String, Hash aur Sorted Set teeno se ban sakti hai. Interviewer yeh dekhta hai ki aapne kyun chuna, memory aur time complexity samajh kar ya guess maar kar.

Problem samasya · what breaks

Team ne har cheez ko JSON string bana ke SET user:1042 <3 KB JSON> kar diya. Ab:

  • Sirf lastSeenAt update karna hai → GET (3 KB) → deserialize → mutate → SET (3 KB). Ek field ke liye 6 KB network.
  • Do requests parallel aayin → read-modify-write race → ek update chup-chaap gayab (lost update).
  • Leaderboard banane ke liye saare users GET karke JVM me sort ho raha hai — O(N log N) app side, har request par.
  • Unique daily visitors count karne ke liye ek Set me 8 crore IDs — ~4 GB RAM.
Bytes per field update6 KB
Leaderboardapp-side sort
DAU set RAM~4 GB

Solution hal · what to do

Redis ke structures ko access pattern ke hisaab se map karo, data ke shape ke hisaab se nahi:

  • String — blob, counter, flag, lock. INCRBY, SET NX PX. O(1).
  • Hash — object jiske fields alag-alag update hote hain. HSET/HINCRBY O(1) per field. Chhote hashes ziplist me pack hote hain → bahut memory-efficient.
  • List — FIFO/LIFO, simple queue. LPUSH+BRPOP. Timeline capped via LTRIM.
  • Set — uniqueness, membership, tags. SADD, SISMEMBER O(1), SINTER for “mutual friends”.
  • Sorted Set (ZSet) — ranking, priority queue, sliding-window rate limit, time-series index. O(log N) insert, ZREVRANGE top-K.
  • Bitmap — per-user boolean by day. 8 crore users = 10 MB, not 4 GB.
  • HyperLogLog — approx unique count, fixed 12 KB, ~0.81% error.
  • Stream — durable append-only log + consumer groups + ack.

repository/UserActivityRedisRepository.java — structure per access pattern 
package com.example.cache.repository;

import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.ZSetOperations;
import org.springframework.stereotype.Repository;

import java.time.Duration;
import java.time.LocalDate;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Set;

@Repository
public class UserActivityRedisRepository {

    private final RedisTemplate<String, Object> redisTemplate;
    private final StringRedisTemplate stringRedisTemplate;

    public UserActivityRedisRepository(RedisTemplate<String, Object> redisTemplate,
                                       StringRedisTemplate stringRedisTemplate) {
        this.redisTemplate = redisTemplate;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    /* ---------- HASH: object jiske fields independently badalte hain ---------- */

    public void updateUserProfileField(long userId, String fieldName, String value) {
        // Poora object nahi bhejte, sirf ek field. O(1), ~40 bytes on the wire.
        redisTemplate.opsForHash().put(buildUserProfileKey(userId), fieldName, value);
    }

    public long incrementUserLoginCount(long userId) {
        // Atomic. Read-modify-write race yahan possible hi nahi hai.
        return redisTemplate.opsForHash().increment(buildUserProfileKey(userId), "loginCount", 1L);
    }

    /* ---------- SORTED SET: ranking / leaderboard ---------- */

    public void addScoreToLeaderboard(String boardName, long userId, double scoreDelta) {
        // ZINCRBY: score badhao aur ranking automatically maintain ho jaye. O(log N)
        redisTemplate.opsForZSet()
                     .incrementScore(buildLeaderboardKey(boardName), String.valueOf(userId), scoreDelta);
    }

    public Map<String, Double> fetchTopPlayers(String boardName, int limit) {
        Set<ZSetOperations.TypedTuple<Object>> tuples = redisTemplate.opsForZSet()
                .reverseRangeWithScores(buildLeaderboardKey(boardName), 0, limit - 1L);

        Map<String, Double> ranked = new LinkedHashMap<>();   // order matter karta hai
        if (tuples == null) return ranked;
        tuples.forEach(t -> ranked.put(String.valueOf(t.getValue()), t.getScore()));
        return ranked;
    }

    /* ---------- BITMAP: 1 bit per user per day ---------- */

    public void markUserActiveToday(long userId) {
        // offset = userId. 80M users -> 10 MB, not 4 GB.
        stringRedisTemplate.opsForValue().setBit(buildDailyActiveKey(LocalDate.now()), userId, true);
    }

    public long countDailyActiveUsers(LocalDate day) {
        return stringRedisTemplate.execute(
                (org.springframework.data.redis.core.RedisCallback<Long>) connection ->
                        connection.stringCommands().bitCount(
                                buildDailyActiveKey(day).getBytes()));
    }

    /* ---------- HYPERLOGLOG: approx unique count, fixed 12 KB ---------- */

    public void recordUniqueVisitor(String pageId, String visitorFingerprint) {
        stringRedisTemplate.opsForHyperLogLog().add(buildUniqueVisitorKey(pageId), visitorFingerprint);
    }

    public long estimateUniqueVisitors(String pageId) {
        return stringRedisTemplate.opsForHyperLogLog().size(buildUniqueVisitorKey(pageId));
    }

    /* ---------- LIST: capped timeline ---------- */

    public void pushToUserTimeline(long userId, String postId, int maxItems) {
        String key = buildTimelineKey(userId);
        stringRedisTemplate.opsForList().leftPush(key, postId);
        stringRedisTemplate.opsForList().trim(key, 0, maxItems - 1L);   // unbounded growth se bachao
        stringRedisTemplate.expire(key, Duration.ofDays(30));
    }

    /* ---------- key naming: ek jagah, taaki collision aur typo na ho ---------- */

    private String buildUserProfileKey(long userId)          { return "app:v1:user:" + userId + ":profile"; }
    private String buildLeaderboardKey(String boardName)     { return "app:v1:lb:" + boardName; }
    private String buildDailyActiveKey(LocalDate day)        { return "app:v1:dau:" + day; }
    private String buildUniqueVisitorKey(String pageId)      { return "app:v1:uv:" + pageId; }
    private String buildTimelineKey(long userId)             { return "app:v1:timeline:" + userId; }
}
Har line ka matlab — what each line is actually doing
opsForHash().put(...)
Ek field ka surgical update. JSON-string approach me yahi 3 KB read + 3 KB write hota tha.
opsForHash().increment(...)
HINCRBY server par atomic hai. Isliye counter ke liye kabhi GET→+1→SET mat likhna.
opsForZSet().incrementScore(...)
ZINCRBY: score update + re-rank ek hi O(log N) operation me. App me sort karna band.
reverseRangeWithScores(0, limit-1)
ZREVRANGE key 0 9 WITHSCORES. Top-K nikalne ke liye poora set nahi padhna padta.
LinkedHashMap
Leaderboard me insertion order = rank order. HashMap use kiya to rank shuffle ho jayega — chhoti si baat, par interview me pakdi jaati hai.
setBit(key, userId, true)
Bitmap. Memory = maxUserId/8 bytes. Condition: user IDs dense hone chahiye. Sparse UUIDs par bitmap bekaar hai.
opsForHyperLogLog()
Exact count nahi chahiye, sirf “kitne unique” chahiye — to 12 KB me kaam ho jata hai. 0.81% standard error accept karna padega.
opsForList().trim(key, 0, max-1)
Har push ke baad trim. Yeh line na ho to list infinitely badhegi — classic “big key” incident.
build*Key() private methods
Key format ek hi jagah. app:v1: prefix version bump se poora cache invalidate karne deta hai bina FLUSH ke.

Kab lagayein (apply)

  • Hash tab jab fields alag update hote hon aur object < ~1000 fields ho.
  • ZSet tab jab ordering ya range-by-score chahiye.
  • Bitmap tab jab IDs dense integers hon.
  • HLL tab jab cardinality approximate chal jaye.
  • Stream tab jab replay + ack + consumer group chahiye.

Kab chhod dein (ignore)

  • Hash mat use karo agar hamesha poora object hi chahiye — tab ek JSON string sasta aur simple hai.
  • ZSet mat use karo sirf list store karne ke liye — per-entry overhead List se kaafi zyada hai.
  • Bitmap mat use karo sparse/UUID keys par — memory phat jayegi.
  • HLL mat use karo billing ya compliance counts ke liye — approximate hai.
  • Streams mat use karo agar aapko Kafka-level retention, partitions aur ecosystem chahiye.

Faisla kaise lein (why)

Rule: pehle access pattern likho, phir structure chuno. “Mujhe top 10 chahiye” → ZSet. “Mujhe pata karna hai maujood hai ya nahi” → Set/Bloom. “Mujhe ek field badalna hai” → Hash. “Mujhe kitne unique” → HLL.

English: pick the structure from the query you must answer, never from how the data happens to look.

03

Caching patterns — cache-aside, read-through, write-through, write-behind

Interview classic. Naam sabko yaad hote hain; farq yeh padta hai ki aap failure order aur race condition samjha pao.

Problem samasya · what breaks

Cache-aside likha gaya tha, par yeh sequence chal gaya:

  • Thread A: cache miss → DB se price = 100 padha → abhi tak SET nahi kiya (GC pause).
  • Thread B: DB me price = 150 likha → cache key delete ki.
  • Thread A wapas aaya → SET price 100.

Ab cache me 100 hai, DB me 150 — aur TTL 1 ghanta hai. Stale for an hour. Doosra issue: write-through lagaya to har write ab do systems par depend karti hai; Redis down = write fail.

Stale windowup to TTL
Raceread-then-write flip

Solution hal · what to do

Cache-aside (lazy loading) — app cache ko manage karta hai. Read: miss → DB → populate. Write: DB → delete key (update nahi). Default choice.

Read-through — cache library khud DB se load karti hai. App code saaf, par loader cache layer me chala jata hai.

Write-through — write cache aur DB dono me synchronously. Cache hamesha fresh, par write latency = DB + Redis, aur ek extra failure point.

Write-behind (write-back) — write cache me, DB me async flush. Sabse fast writes, par crash = data loss. Sirf tab jab loss tolerable ho (view counts, analytics).

Refresh-ahead — TTL khatam hone se pehle background me recompute. Hot keys ke liye best, cold keys ke liye waste.

Race ka fix: delete, update nahi + short TTL + zaroorat pade to delayed double delete.

service/ProductCacheAsideService.java — cache-aside done properly 
package com.example.cache.service;

import com.example.cache.model.Product;
import com.example.cache.repository.ProductJpaRepository;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

import java.time.Duration;
import java.util.Optional;
import java.util.concurrent.ThreadLocalRandom;

@Service
public class ProductCacheAsideService {

    private static final Logger log = LoggerFactory.getLogger(ProductCacheAsideService.class);
    private static final Duration BASE_TTL = Duration.ofMinutes(10);

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductJpaRepository productJpaRepository;

    public ProductCacheAsideService(RedisTemplate<String, Object> redisTemplate,
                                    ProductJpaRepository productJpaRepository) {
        this.redisTemplate = redisTemplate;
        this.productJpaRepository = productJpaRepository;
    }

    /* ============================ READ PATH ============================ */

    public Optional<Product> findProductById(long productId) {
        String cacheKey = buildProductKey(productId);

        // 1) Cache pehle. Redis fail ho to request fail nahi honi chahiye.
        try {
            Product cached = (Product) redisTemplate.opsForValue().get(cacheKey);
            if (cached != null) {
                return Optional.of(cached);
            }
        } catch (RuntimeException redisFailure) {
            log.warn("Redis read failed, falling back to DB. key={}", cacheKey, redisFailure);
        }

        // 2) Miss -> source of truth
        Optional<Product> fromDatabase = productJpaRepository.findById(productId);

        // 3) Populate. Miss ko bhi cache karo (null caching) warna penetration attack chalega.
        writeThroughSafely(cacheKey, fromDatabase.orElse(null));
        return fromDatabase;
    }

    /* ============================ WRITE PATH ============================ */

    public Product updateProductPrice(long productId, double newPrice) {
        Product updated = productJpaRepository.updatePrice(productId, newPrice);   // DB = truth, pehle

        // Cache ko UPDATE mat karo -> DELETE karo. Do concurrent writers ka
        // order flip ho sakta hai; delete idempotent hai, stale value nahi chhodta.
        evictAfterCommit(buildProductKey(productId));
        return updated;
    }

    /**
     * Transaction commit ke BAAD evict karo. Agar commit se pehle delete kiya
     * aur transaction rollback ho gaya, to cache khali + DB purana = confusion.
     */
    private void evictAfterCommit(String cacheKey) {
        if (!TransactionSynchronizationManager.isSynchronizationActive()) {
            redisTemplate.delete(cacheKey);
            return;
        }
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() {
                redisTemplate.delete(cacheKey);
                scheduleDelayedSecondDelete(cacheKey);
            }
        });
    }

    /**
     * Delayed double delete: agar koi reader purani value abhi likhne wala tha,
     * yeh doosra delete usko saaf kar dega.
     */
    @Async
    public void scheduleDelayedSecondDelete(String cacheKey) {
        try {
            Thread.sleep(500);
            redisTemplate.delete(cacheKey);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    /* ============================ HELPERS ============================ */

    private void writeThroughSafely(String cacheKey, Product value) {
        try {
            if (value == null) {
                // Negative cache: chhota TTL, warna deleted product 10 min tak 404 dega
                redisTemplate.opsForValue().set(cacheKey, NullProduct.INSTANCE, Duration.ofSeconds(30));
            } else {
                redisTemplate.opsForValue().set(cacheKey, value, computeTtlWithJitter());
            }
        } catch (RuntimeException redisFailure) {
            log.warn("Cache populate failed, ignoring. key={}", cacheKey, redisFailure);
        }
    }

    /** Sab keys ek hi second par expire na hon -> +/- 20% randomness. */
    private Duration computeTtlWithJitter() {
        long baseSeconds = BASE_TTL.getSeconds();
        long jitter = ThreadLocalRandom.current().nextLong(-baseSeconds / 5, baseSeconds / 5);
        return Duration.ofSeconds(baseSeconds + jitter);
    }

    private String buildProductKey(long productId) {
        return "app:v1:product:" + productId;
    }
}
Har line ka matlab — what each line is actually doing
try/catch around cache read
Cache optional hona chahiye. Agar Redis exception poore request ko fail kara de, to aapne availability ghata di hai, badhai nahi.
productJpaRepository.findById
Source of truth. Cache miss par yeh path chalta hai — isi path ko topic 05 me stampede se bachana hai.
DB pehle, cache baad me (write path)
Hamesha durable store pehle. Ulta karoge to Redis me likha aur DB fail — phantom data.
delete, not update
Do writers agar dono cache update karein, network reorder se purana value baad me land kar sakta hai. Delete idempotent hai.
afterCommit()
Spring transaction synchronization. Rollback hua to eviction hi nahi hoga — exactly right behaviour.
scheduleDelayedSecondDelete
In-flight reader jo purana value SET karne wala tha, usko 500ms baad clean kar dete hain. Yeh “delayed double delete” pattern hai.
NullProduct.INSTANCE with 30s TTL
Negative caching. Non-existent IDs bhi cache hote hain, warna attacker random IDs maar ke har request DB tak pahucha dega (cache penetration).
computeTtlWithJitter()
Ek hi deploy me bani saari keys ek saath expire hoti hain → avalanche. ±20% jitter usko smear kar deta hai.

Kab lagayein (apply)

  • Cache-aside: 90% cases ka default — simple, resilient, cache down ho to bhi app chalta hai.
  • Read-through: jab bahut saare call sites hon aur duplication rok‑ni ho.
  • Write-through: jab read-after-write freshness zaroori ho aur write volume kam ho.
  • Write-behind: counters, view counts, analytics — jahan thoda loss chalta hai.
  • Refresh-ahead: chhoti hot key set (top 500 products) ke liye.

Kab chhod dein (ignore)

  • Write-through mat lagao high write volume par — aapne har write me ek extra dependency daal di.
  • Write-behind mat lagao paise/orders par — crash = data gone.
  • Refresh-ahead mat lagao long-tail keys par — aap wo cheez refresh karoge jo koi nahi maangega.
  • “Update cache on write” mat karo unless aap ordering (version/CAS) handle kar rahe ho.

Faisla kaise lein (why)

Poochho: ek stale read ka nuqsaan kitna hai? Product description stale → koi baat nahi. Wallet balance stale → incident. Nuqsaan jitna bada, cache utna hi patla (short TTL) ya bilkul nahi.

English: choose the pattern by the cost of a stale read and the cost of a lost write — not by which one sounds most advanced.

Invalidation aur TTL — “two hard things” wala hissa

Cache me data daalna aasan hai. Use sahi waqt par hatana — wahin par systems tootte hain.

Problem samasya · what breaks

Teen alag incidents, ek hi root cause — expiry strategy ki kami:

  • No TTL: promo keys bina expiry ke likhi gayin. 3 hafte baad used_memory 58 GB, maxmemory 60 GB. Evictions shuru, hit ratio 40% par gir gaya.
  • Same TTL: deploy ke waqt 200k keys warm ki gayin, sabka TTL exactly 3600s. Ek ghante baad ek hi second me 200k expiry → DB par spike → avalanche.
  • Orphan keys: schema badla, ab cached JSON me ek field missing hai. Deserialization exception har request par, aur puraani keys 24 ghante tak zinda.

  • Versioned namespace: app:v1:product:42. Schema change → v2 → puraana set apne aap TTL se mar jayega. FLUSHDB ki zaroorat nahi (production me FLUSH = outage).

  • Tiered TTL: hot data chhota TTL + refresh-ahead; cold data bada TTL.
  • Do TTL types samjho: Redis lazy expiry (access par) + active expiry (background sampling) dono karta hai. Isliye “expired” key kuch der memory me reh sakti hai.

package com.example.cache.key;

import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

@Component
public class TtlPolicy {

    private static final double JITTER_RATIO = 0.20;   // +/- 20%

    /** Hot, frequently changing: chhota TTL. */
    public Duration forVolatileData()  { return applyJitter(Duration.ofSeconds(60)); }

    /** Normal entity read: 10 min. */
    public Duration forEntityData()    { return applyJitter(Duration.ofMinutes(10)); }

    /** Reference data (countries, categories): lamba TTL chalega. */
    public Duration forReferenceData() { return applyJitter(Duration.ofHours(12)); }

    /** Negative cache: bahut chhota, warna deleted item lamba 404 dega. */
    public Duration forMissingEntity() { return Duration.ofSeconds(30); }

    /**
     * Base ke aas-paas randomize karo taaki 200k keys ek hi second par expire na hon.
     */
    private Duration applyJitter(Duration base) {
        long seconds = base.getSeconds();
        long spread = (long) (seconds * JITTER_RATIO);
        long offset = ThreadLocalRandom.current().nextLong(-spread, spread + 1);
        return Duration.ofSeconds(Math.max(1, seconds + offset));
    }
}

  • Negative caching: jab miss ratio high ho ya IDs public hon.

  • Bahut chhota TTL mat rakho hot key par — wo effectively cache hata deta hai aur stampede badhata hai.
  • KEYS pattern* se bulk delete mat karo — server block ho jayega. SCAN + UNLINK use karo.

Stampede, penetration, avalanche, hot key, big key — paanch classic failures

Yeh section interview me sabse zyada differentiate karta hai. Naam yaad rakhna kaafi nahi — har ek ka mechanism aur fix alag hai.

Problem samasya · what breaks

  • Cache stampede / thundering herd: ek viral product ki key expire hui. Usi millisecond me 40,000 requests miss hueen, sabne DB par same query maari. DB connections khatam, p99 8s, cascading failure.
  • Cache penetration: attacker /product/{random} maar raha hai. Woh IDs exist hi nahi karte, isliye kabhi cache nahi hote — har request DB tak.
  • Cache avalanche: Redis node restart hua / bahut saari keys ek saath expire hueen → hit ratio 0 → poora load DB par.
  • Hot key: ek celebrity profile key 60k RPS le rahi hai. Cluster me wo ek hi shard par hai — baaki shards idle, wo shard CPU 100%.
  • Big key: ek Hash me 4 million fields. HGETALL ne single thread 900ms block kar diya — poore cluster ke liye timeout.

Solution hal · what to do

  • Stampede → single-flight: per-key mutex (SET lock NX PX). Ek thread rebuild kare, baaki thoda ruk kar cache dobara padhein ya stale value serve karein.
  • Stampede → logical expiry: value ke andar expiresAt rakho, Redis TTL bahut lamba rakho. Expiry paar hone par stale value turant return karo aur background me refresh trigger karo. Zero user-facing latency spike.
  • Penetration → negative cache + Bloom filter: known-ID Bloom filter se pehle check, phir 30s negative TTL.
  • Avalanche → TTL jitter + warmup: restart ke baad top-N keys pre-load, aur DB ke aage circuit breaker/bulkhead.
  • Hot key → L1 local cache + key sharding: Caffeine me 1–5s ka in-process cache (Redis tak jaana hi band), ya key ko key:#0..#9 replicas me todo.
  • Big key → split: hash ko buckets me todo, HGETALL ki jagah HSCAN/HMGET, delete ke liye UNLINK (async free).

service/StampedeSafeCacheService.java — single-flight + logical expiry 
package com.example.cache.service;

import com.example.cache.key.CacheKeyFactory;
import com.example.cache.key.TtlPolicy;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.core.task.TaskExecutor;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.UUID;
import java.util.function.Supplier;

@Service
public class StampedeSafeCacheService {

    private static final Logger log = LoggerFactory.getLogger(StampedeSafeCacheService.class);

    /** Physical TTL logical TTL se kaafi lamba: value expire hone ke baad bhi serve kar sakein. */
    private static final Duration PHYSICAL_TTL_MULTIPLIER = Duration.ofHours(6);
    private static final Duration REBUILD_LOCK_TTL = Duration.ofSeconds(10);
    private static final long WAITER_BACKOFF_MILLIS = 50L;
    private static final int WAITER_MAX_ATTEMPTS = 6;

    private final RedisTemplate<String, Object> redisTemplate;
    private final CacheKeyFactory cacheKeyFactory;
    private final TtlPolicy ttlPolicy;
    private final TaskExecutor cacheRefreshExecutor;
    private final DefaultRedisScript<Long> releaseLockScript;

    public StampedeSafeCacheService(RedisTemplate<String, Object> redisTemplate,
                                    CacheKeyFactory cacheKeyFactory,
                                    TtlPolicy ttlPolicy,
                                    TaskExecutor cacheRefreshExecutor) {
        this.redisTemplate = redisTemplate;
        this.cacheKeyFactory = cacheKeyFactory;
        this.ttlPolicy = ttlPolicy;
        this.cacheRefreshExecutor = cacheRefreshExecutor;
        this.releaseLockScript = buildReleaseLockScript();
    }

    /**
     * Main entry point.
     * Stale value milte hi return kar deta hai aur refresh background me karta hai,
     * isliye user ko kabhi rebuild ka wait nahi karna padta.
     */
    public <T> T getWithLogicalExpiry(String cacheKey, Class<T> type, Supplier<T> databaseLoader) {

        CachedEnvelope envelope = (CachedEnvelope) redisTemplate.opsForValue().get(cacheKey);

        // Case 1: bilkul khali (cold start) -> blocking rebuild, par sirf ek thread
        if (envelope == null) {
            return loadWithSingleFlight(cacheKey, type, databaseLoader);
        }

        // Case 2: fresh -> seedha return
        if (Instant.now().isBefore(envelope.getLogicalExpiryAt())) {
            return type.cast(envelope.getPayload());
        }

        // Case 3: stale -> abhi purana do, peeche refresh chalao
        triggerAsyncRefresh(cacheKey, databaseLoader);
        return type.cast(envelope.getPayload());
    }

    /* -------------------- single flight (mutex) -------------------- */

    private <T> T loadWithSingleFlight(String cacheKey, Class<T> type, Supplier<T> databaseLoader) {
        String lockKey = cacheKeyFactory.rebuildLockKey(cacheKey);
        String lockToken = UUID.randomUUID().toString();

        if (tryAcquireRebuildLock(lockKey, lockToken)) {
            try {
                T freshValue = databaseLoader.get();      // sirf yeh ek thread DB tak jata hai
                storeWithLogicalExpiry(cacheKey, freshValue);
                return freshValue;
            } finally {
                releaseRebuildLock(lockKey, lockToken);
            }
        }
        // Lock nahi mila -> winner ka intezaar karo, DB ko mat maaro
        return awaitRebuiltValue(cacheKey, type, databaseLoader);
    }

    private boolean tryAcquireRebuildLock(String lockKey, String lockToken) {
        Boolean acquired = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, lockToken, REBUILD_LOCK_TTL);   // SET key val NX PX 10000
        return Boolean.TRUE.equals(acquired);
    }

    private void releaseRebuildLock(String lockKey, String lockToken) {
        // Compare-and-delete: sirf apna hi lock hatao, kisi aur ka nahi.
        redisTemplate.execute(releaseLockScript, List.of(lockKey), lockToken);
    }

    private <T> T awaitRebuiltValue(String cacheKey, Class<T> type, Supplier<T> databaseLoader) {
        for (int attempt = 0; attempt < WAITER_MAX_ATTEMPTS; attempt++) {
            sleepQuietly(WAITER_BACKOFF_MILLIS);
            CachedEnvelope envelope = (CachedEnvelope) redisTemplate.opsForValue().get(cacheKey);
            if (envelope != null) {
                return type.cast(envelope.getPayload());
            }
        }
        // Winner mar gaya? Tab last resort: khud DB se padho.
        log.warn("Rebuild wait timed out, loading directly. key={}", cacheKey);
        return databaseLoader.get();
    }

    /* -------------------- write + async refresh -------------------- */

    private <T> void storeWithLogicalExpiry(String cacheKey, T value) {
        Instant logicalExpiry = Instant.now().plus(ttlPolicy.forEntityData());
        CachedEnvelope envelope = new CachedEnvelope(value, logicalExpiry);
        redisTemplate.opsForValue().set(cacheKey, envelope, PHYSICAL_TTL_MULTIPLIER);
    }

    private <T> void triggerAsyncRefresh(String cacheKey, Supplier<T> databaseLoader) {
        String lockKey = cacheKeyFactory.rebuildLockKey(cacheKey);
        String lockToken = UUID.randomUUID().toString();
        if (!tryAcquireRebuildLock(lockKey, lockToken)) {
            return;   // koi aur pehle se refresh kar raha hai
        }
        cacheRefreshExecutor.execute(() -> {
            try {
                storeWithLogicalExpiry(cacheKey, databaseLoader.get());
            } catch (RuntimeException e) {
                log.error("Async cache refresh failed. key={}", cacheKey, e);
            } finally {
                releaseRebuildLock(lockKey, lockToken);
            }
        });
    }

    private DefaultRedisScript<Long> buildReleaseLockScript() {
        String lua =
                "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "  return redis.call('del', KEYS[1]) " +
                "else return 0 end";
        return new DefaultRedisScript<>(lua, Long.class);
    }

    private void sleepQuietly(long millis) {
        try { Thread.sleep(millis); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Kab lagayein (apply)

  • Single-flight lock: jab rebuild mehnga ho (>50 ms) ya key hot ho.
  • Logical expiry: top hot keys ke liye — best user experience.
  • Bloom filter: jab ID space public/guessable ho aur miss ratio high ho.
  • L1 Caffeine: jab ek key 5k+ RPS le rahi ho.
  • Key sharding: sirf tab jab ek shard CPU-bound ho gaya ho.

Kab chhod dein (ignore)

  • Logical expiry mat lagao har key par — stale-serve semantics har data ke liye acceptable nahi.
  • Bloom filter mat lagao chhote ID sets par — ek Redis Set hi kaafi hai.
  • L1 cache mat lagao agar cross-node consistency chahiye — local caches invalidate karna mushkil hai (pub/sub broadcast chahiye).
  • Key sharding mat lagao pehle se — pehle measure karo ki hot key hai bhi ya nahi.
  • Lock mat lagao sasti rebuild par — lock ka round trip hi rebuild se mehnga pad jayega.

Faisla kaise lein (why)

Decision rule: rebuild cost × concurrency. Rebuild 5ms hai to 1000 concurrent misses bhi theek hain. Rebuild 800ms hai to 50 misses hi DB gira denge — tab single-flight zaroori hai.

Aur yaad rakho: L1 cache consistency kharab karta hai bajaye latency ke. Wo trade tabhi lo jab hot key ka dard sach me ho.

Persistence — RDB, AOF, hybrid, aur “cache ko persist karna chahiye ya nahi”

Yahan sahi jawab “AOF hamesha” nahi hai. Sahi jawab yeh hai: data ka role kya hai — cache, ya source of truth?

Problem samasya · what breaks

  • Cache node restart: Redis restart hua, memory khali. Hit ratio 0 se shuru → DB par 12k RPS ek saath → avalanche → outage. Persistence hoti to warm start milta.
  • Session store crash: sessions sirf memory me the. Node gaya, 400k users ek saath logged out.
  • AOF `always` on: kisi ne durability badhane ke liye appendfsync always laga diya. Har write par fsync → throughput 120k → 9k ops/s.
  • RDB fork spike: 40 GB dataset, BGSAVE ke waqt fork + copy-on-write → memory 1.6×, aur write-heavy load par latency spike.
Cold start0% hit

Fork memoryup to 2×

Solution hal · what to do

RDB (snapshot) — point-in-time binary dump, background fork se. Restart fast, file compact, backup-friendly. Nuksaan: snapshots ke beech ka data loss ho sakta hai (minutes).

AOF (append-only file) — har write command log hoti hai. appendfsync: always (safe, slow), everysec (default, ~1s loss), no (OS decide kare). AOF rewrite file ko compact karta hai.

Hybrid (Redis 4+) — aof-use-rdb-preamble yes: AOF file ka pehla hissa RDB snapshot, uske baad incremental commands. Fast load + chhota loss window. Yeh aaj ka default recommendation hai.

Role ke hisaab se faisla:

  • Pure cache → persistence off ya sirf RDB (warm restart ke liye). Truth DB me hai.
  • Session / lock / rate-limit state → AOF everysec + replica.
  • Primary datastore (Redis as DB) → hybrid + replica + backups, aur seriously reconsider karo ki Redis hi sahi choice hai.

package com.example.cache.warmup;

import com.example.cache.key.CacheKeyFactory;
import com.example.cache.service.StampedeSafeCacheService;
import com.example.cache.repository.ProductJpaRepository;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.ApplicationArguments;
import org.springframework.stereotype.Component;

import java.util.List;

/**
 * Node up hote hi top-N hot keys pre-load karo.
 * Bina iske, cold Redis = 0% hit ratio = DB par poora traffic.
 */
@Component
public class CacheWarmupRunner implements ApplicationRunner {

    private static final Logger log = LoggerFactory.getLogger(CacheWarmupRunner.class);
    private static final int WARMUP_BATCH_SIZE = 200;

    private final ProductJpaRepository productJpaRepository;
    private final StampedeSafeCacheService cacheService;
    private final CacheKeyFactory cacheKeyFactory;

    public CacheWarmupRunner(ProductJpaRepository productJpaRepository,
                             StampedeSafeCacheService cacheService,
                             CacheKeyFactory cacheKeyFactory) {
        this.productJpaRepository = productJpaRepository;
        this.cacheService = cacheService;
        this.cacheKeyFactory = cacheKeyFactory;
    }

    @Override
    public void run(ApplicationArguments args) {
        warmMostRequestedProducts(2000);
    }

    /**
     * Batch me warm karo, ek saath nahi -> DB par apna hi mini-stampede mat banao.
     */
    public void warmMostRequestedProducts(int topN) {
        List<Long> hottestProductIds = productJpaRepository.findTopViewedProductIds(topN);

        for (int start = 0; start < hottestProductIds.size(); start += WARMUP_BATCH_SIZE) {
            int end = Math.min(start + WARMUP_BATCH_SIZE, hottestProductIds.size());
            List<Long> batch = hottestProductIds.subList(start, end);

            batch.forEach(this::warmSingleProduct);
            pauseBetweenBatches(100);
        }
        log.info("Cache warmup finished for {} products", hottestProductIds.size());
    }

    private void warmSingleProduct(Long productId) {
        String key = cacheKeyFactory.productDetailKey(productId);
        cacheService.getWithLogicalExpiry(key, Object.class,
                () -> productJpaRepository.findById(productId).orElse(null));
    }

    private void pauseBetweenBatches(long millis) {
        try { Thread.sleep(millis); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Memory aur eviction — maxmemory, LRU vs LFU, aur OOM se bachna

Problem samasya · what breaks

Ek node par maxmemory set hi nahi tha. Traffic badha, keys badhi, aur:

  • used_memory host RAM cross kar gaya → swap → latency 0.3ms se 400ms.

  • Doosre node par policy noeviction thi → memory full hone par saari writes OOM command not allowed se fail hone lagi, reads chalte rahe — aadha-tuta system.
  • Teesre node par allkeys-lru tha par workload scan-heavy tha — ek batch job ne poore working set ko evict kar diya (cache pollution).

    private static final double HIT_RATIO_FLOOR  = 0.80;

    private final StringRedisTemplate stringRedisTemplate;
    private final MeterRegistry meterRegistry;

                                      MeterRegistry meterRegistry) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.meterRegistry = meterRegistry;

        long usedMemory      = parseLong(info, "used_memory");
        long maxMemory       = parseLong(info, "maxmemory");
        long evictedKeys     = parseLong(info, "evicted_keys");
        long keyspaceHits    = parseLong(info, "keyspace_hits");
        long keyspaceMisses  = parseLong(info, "keyspace_misses");

                ? Health.up()
                : Health.down();

                .withDetail("memoryUsageRatio", round(memoryRatio))
                .withDetail("cacheHitRatio", round(hitRatio))
                .withDetail("evictedKeys", evictedKeys)
                .withDetail("fragmentationRatio", fragmentation)
                .build();
    }

     * maxmemory == 0 ka matlab hai "unlimited" -> yeh production me
     * ek configuration bug hai, isliye ise unhealthy maano.

        if (maxMemory == 0) return false;
        return memoryRatio < MEMORY_WARN_RATIO && hitRatio > HIT_RATIO_FLOOR;
    }

    private double computeHitRatio(long hits, long misses) {
        long total = hits + misses;
        return total == 0 ? 1.0 : (double) hits / total;
    }

    private void publishMetrics(double memoryRatio, double hitRatio,
                                long evictedKeys, double fragmentation) {
        meterRegistry.gauge("redis.memory.usage.ratio", memoryRatio);
        meterRegistry.gauge("redis.cache.hit.ratio", hitRatio);
        meterRegistry.gauge("redis.keys.evicted.total", evictedKeys);
        meterRegistry.gauge("redis.memory.fragmentation.ratio", fragmentation);
    }

    private Properties readServerInfo() {
        RedisConnectionFactory factory = stringRedisTemplate.getRequiredConnectionFactory();
        return stringRedisTemplate.execute((RedisCallback<Properties>) connection ->
                connection.serverCommands().info());
    }

    private long parseLong(Properties p, String key) {
        return Long.parseLong(p.getProperty(key, "0"));
    }

    private double parseDouble(Properties p, String key) {
        return Double.parseDouble(p.getProperty(key, "0"));
    }

package com.example.cache.service;

import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;

import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

@Service
public class BulkRedisOperationsService {

    private static final int SCAN_BATCH_SIZE = 500;

    private final StringRedisTemplate stringRedisTemplate;
    private final DefaultRedisScript<Long> compareAndSetScript;

    public BulkRedisOperationsService(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.compareAndSetScript = buildCompareAndSetScript();
    }

    /* ---------------- 1. SCAN instead of KEYS ---------------- */

    /**
     * KEYS poore keyspace par ek hi baar me ghoomta hai aur server block karta hai.
     * SCAN cursor deta hai: har call O(1)-ish, beech me doosre clients chal sakte hain.
     * Guarantee: jo key poore scan ke dauran maujood rahi, wo zaroor milegi.
     */
    public void deleteKeysMatchingPattern(String matchPattern) {
        ScanOptions options = ScanOptions.scanOptions()
                .match(matchPattern)
                .count(SCAN_BATCH_SIZE)      // hint, exact batch size nahi
                .build();

        try (Cursor<String> cursor = stringRedisTemplate.scan(options)) {
            List<String> batch = new ArrayList<>(SCAN_BATCH_SIZE);
            while (cursor.hasNext()) {
                batch.add(cursor.next());
                if (batch.size() >= SCAN_BATCH_SIZE) {
                    unlinkBatch(batch);
                    batch.clear();
                }
            }
            if (!batch.isEmpty()) unlinkBatch(batch);
        }
    }

    /** UNLINK: key turant unreachable, memory background thread free karta hai. */
    private void unlinkBatch(List<String> keys) {
        stringRedisTemplate.unlink(keys);
    }

    /* ---------------- 2. Pipelining: N round trips -> 1 ---------------- */

    /**
     * 350 alag GET = 350 RTT. Pipeline me sab ek TCP write me jaate hain.
     * Dhyan: yeh atomic NAHI hai. Beech me doosre clients ke commands ghus sakte hain.
     */
    public List<Object> fetchManyValuesInOneRoundTrip(List<String> cacheKeys) {
        return stringRedisTemplate.executePipelined((RedisCallback<Object>) connection -> {
            for (String key : cacheKeys) {
                connection.stringCommands().get(key.getBytes(StandardCharsets.UTF_8));
            }
            return null;   // pipeline me har command ka result baad me collect hota hai
        });
    }

    /**
     * Ek hi shape ke keys ho to MGET aur bhi simple hai (cluster me same slot chahiye).
     */
    public List<String> fetchManyValuesWithMget(List<String> cacheKeys) {
        return stringRedisTemplate.opsForValue().multiGet(cacheKeys);
    }

    /* ---------------- 3. Lua: atomic read-modify-write ---------------- */

    /**
     * "Agar current value expected hai to naya value set karo" \u2014 ek atomic step me.
     * Java me GET + if + SET likhoge to do requests ke beech race hoga.
     */
    public boolean compareAndSetValue(String key, String expectedValue, String newValue, long ttlSeconds) {
        Long changed = stringRedisTemplate.execute(
                compareAndSetScript,
                List.of(key),
                expectedValue, newValue, String.valueOf(ttlSeconds));
        return Long.valueOf(1L).equals(changed);
    }

    private DefaultRedisScript<Long> buildCompareAndSetScript() {
        String lua =
            "local current = redis.call('GET', KEYS[1]) " +
            "if current == ARGV[1] then " +
            "  redis.call('SET', KEYS[1], ARGV[2], 'EX', tonumber(ARGV[3])) " +
            "  return 1 " +
            "end " +
            "return 0";
        return new DefaultRedisScript<>(lua, Long.class);
    }
}

package com.example.cache.lock;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.List;
import java.util.UUID;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.function.Supplier;

@Component
public class RedisDistributedLock {

    private static final Logger log = LoggerFactory.getLogger(RedisDistributedLock.class);
    private static final Duration DEFAULT_LEASE = Duration.ofSeconds(30);

    private final StringRedisTemplate stringRedisTemplate;
    private final ScheduledExecutorService leaseRenewalScheduler;
    private final DefaultRedisScript<Long> releaseScript;
    private final DefaultRedisScript<Long> renewScript;

    public RedisDistributedLock(StringRedisTemplate stringRedisTemplate,
                                ScheduledExecutorService leaseRenewalScheduler) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.leaseRenewalScheduler = leaseRenewalScheduler;
        this.releaseScript = buildReleaseScript();
        this.renewScript = buildRenewScript();
    }

    /**
     * Sabse safe public API: lock lo, kaam karo, guaranteed release karo.
     * Lock na mile to kaam skip \u2014 exception nahi, kyunki dusra pod kar hi raha hai.
     */
    public <T> LockOutcome<T> runExclusively(String lockName, Duration lease, Supplier<T> criticalSection) {
        String lockKey = "lock:" + lockName;
        String ownerToken = UUID.randomUUID().toString();

        if (!tryAcquireLock(lockKey, ownerToken, lease)) {
            return LockOutcome.notAcquired();
        }

        ScheduledFuture<?> renewalTask = startLeaseRenewal(lockKey, ownerToken, lease);
        try {
            return LockOutcome.completed(criticalSection.get());
        } finally {
            renewalTask.cancel(false);
            releaseLock(lockKey, ownerToken);
        }
    }

    /* ---------------- acquire ---------------- */

    /**
     * SET lockKey token NX PX lease  -> ek hi atomic command.
     * SETNX + EXPIRE alag-alag mat likhna: beech me crash = TTL-less deadlock.
     */
    public boolean tryAcquireLock(String lockKey, String ownerToken, Duration lease) {
        Boolean acquired = stringRedisTemplate.opsForValue()
                .setIfAbsent(lockKey, ownerToken, lease);
        return Boolean.TRUE.equals(acquired);
    }

    /* ---------------- renew (watchdog) ---------------- */

    private ScheduledFuture<?> startLeaseRenewal(String lockKey, String ownerToken, Duration lease) {
        long everyMillis = Math.max(1000L, lease.toMillis() / 3);   // lease ka 1/3 \u2014 safe margin
        return leaseRenewalScheduler.scheduleAtFixedRate(
                () -> renewLeaseIfStillOwner(lockKey, ownerToken, lease),
                everyMillis, everyMillis, TimeUnit.MILLISECONDS);
    }

    /** Lease sirf tabhi badhao jab token abhi bhi aapka ho. */
    public boolean renewLeaseIfStillOwner(String lockKey, String ownerToken, Duration lease) {
        Long renewed = stringRedisTemplate.execute(
                renewScript, List.of(lockKey), ownerToken, String.valueOf(lease.toMillis()));
        if (!Long.valueOf(1L).equals(renewed)) {
            log.warn("Lease renewal failed \u2014 lock no longer owned. key={}", lockKey);
            return false;
        }
        return true;
    }

    /* ---------------- release ---------------- */

    /** Compare-and-delete. Kisi aur ka lock kabhi delete nahi hoga. */
    public boolean releaseLock(String lockKey, String ownerToken) {
        Long released = stringRedisTemplate.execute(releaseScript, List.of(lockKey), ownerToken);
        return Long.valueOf(1L).equals(released);
    }

    /* ---------------- fencing token ---------------- */

    /**
     * Har successful acquire ke saath ek badhta hua number do.
     * Downstream (DB) purane number wali write reject kar de -> yeh asli safety hai.
     */
    public long issueFencingToken(String lockName) {
        Long token = stringRedisTemplate.opsForValue().increment("fence:" + lockName);
        return token == null ? 0L : token;
    }

    /* ---------------- scripts ---------------- */

    private DefaultRedisScript<Long> buildReleaseScript() {
        String lua =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('DEL', KEYS[1]) " +
            "else return 0 end";
        return new DefaultRedisScript<>(lua, Long.class);
    }

    private DefaultRedisScript<Long> buildRenewScript() {
        String lua =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('PEXPIRE', KEYS[1], tonumber(ARGV[2])) " +
            "else return 0 end";
        return new DefaultRedisScript<>(lua, Long.class);
    }
}

@Component

    private final StringRedisTemplate stringRedisTemplate;
    private final DefaultRedisScript<List> slidingWindowScript;

    public SlidingWindowRateLimiter(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.slidingWindowScript = buildSlidingWindowScript();
    }

    /**
     * Ek call = ek atomic decision.
     * Purane entries hatao -> count karo -> allow/deny -> allow hua to add karo.
     * Yeh saara Redis ke andar hota hai, isliye race possible hi nahi.
     */
    @SuppressWarnings("unchecked")
    public RateLimitDecision tryConsume(String clientIdentifier, int maxRequests, Duration window) {

        String key = buildRateLimitKey(clientIdentifier);
        long nowMillis = System.currentTimeMillis();
        long windowMillis = window.toMillis();
        String uniqueMember = nowMillis + "-" + UUID.randomUUID();

        List<Long> result = stringRedisTemplate.execute(
                slidingWindowScript,
                List.of(key),
                String.valueOf(nowMillis),
                String.valueOf(windowMillis),
                String.valueOf(maxRequests),
                uniqueMember);

        boolean allowed        = result.get(0) == 1L;
        long currentCount      = result.get(1);
        long retryAfterMillis  = result.get(2);

        return new RateLimitDecision(allowed,
                                     Math.max(0, maxRequests - currentCount),
                                     Duration.ofMillis(retryAfterMillis));
    }

    /**
     * Lua:
     *   KEYS[1] = rate limit key
     *   ARGV[1] = now (ms), ARGV[2] = window (ms), ARGV[3] = limit, ARGV[4] = unique member
     */
    private DefaultRedisScript<List> buildSlidingWindowScript() {
        String lua =
            "local key      = KEYS[1] \n" +
            "local now      = tonumber(ARGV[1]) \n" +
            "local window   = tonumber(ARGV[2]) \n" +
            "local limit    = tonumber(ARGV[3]) \n" +
            "local member   = ARGV[4] \n" +
            // 1) window se bahar ke entries hata do
            "redis.call('ZREMRANGEBYSCORE', key, 0, now - window) \n" +
            // 2) ab window ke andar kitne hain
            "local count = redis.call('ZCARD', key) \n" +
            "if count < limit then \n" +
            // 3) allow: entry add karo aur key ka TTL refresh karo
            "  redis.call('ZADD', key, now, member) \n" +
            "  redis.call('PEXPIRE', key, window) \n" +
            "  return {1, count + 1, 0} \n" +
            "end \n" +
            // 4) deny: sabse purani entry kab window se bahar jayegi = retry-after
            "local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES') \n" +
            "local retryAfter = window \n" +
            "if oldest[2] then retryAfter = (tonumber(oldest[2]) + window) - now end \n" +
            "redis.call('PEXPIRE', key, window) \n" +
            "return {0, count, retryAfter}";
        return new DefaultRedisScript<>(lua, List.class);
    }

    private String buildRateLimitKey(String clientIdentifier) {
        return "rl:sw:" + clientIdentifier;
    }
}

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Component;

import java.util.List;

@Component
public class TokenBucketRateLimiter {

    private final StringRedisTemplate stringRedisTemplate;
    private final DefaultRedisScript<Long> tokenBucketScript;

    public TokenBucketRateLimiter(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.tokenBucketScript = buildTokenBucketScript();
    }

    /**
     * capacity  = bucket kitna bharega (burst size)
     * refillPerSecond = tokens per second
     * Lazy refill: hum timer nahi chalate, elapsed time se calculate karte hain.
     */
    public boolean tryConsumeToken(String clientIdentifier, int capacity, double refillPerSecond) {
        Long allowed = stringRedisTemplate.execute(
                tokenBucketScript,
                List.of(buildBucketKey(clientIdentifier)),
                String.valueOf(capacity),
                String.valueOf(refillPerSecond),
                String.valueOf(System.currentTimeMillis()));
        return Long.valueOf(1L).equals(allowed);
    }

    private DefaultRedisScript<Long> buildTokenBucketScript() {
        String lua =
            "local key       = KEYS[1] \n" +
            "local capacity  = tonumber(ARGV[1]) \n" +
            "local refillPs  = tonumber(ARGV[2]) \n" +
            "local now       = tonumber(ARGV[3]) \n" +
            "local bucket    = redis.call('HMGET', key, 'tokens', 'updatedAt') \n" +
            "local tokens    = tonumber(bucket[1]) \n" +
            "local updatedAt = tonumber(bucket[2]) \n" +
            "if tokens == nil then tokens = capacity; updatedAt = now end \n" +
            // lazy refill: jitna time beeta, utne tokens wapas
            "local elapsedSec = math.max(0, (now - updatedAt) / 1000) \n" +
            "tokens = math.min(capacity, tokens + elapsedSec * refillPs) \n" +
            "local allowed = 0 \n" +
            "if tokens >= 1 then tokens = tokens - 1; allowed = 1 end \n" +
            "redis.call('HMSET', key, 'tokens', tokens, 'updatedAt', now) \n" +
            // idle bucket apne aap saaf ho jaye
            "redis.call('PEXPIRE', key, math.ceil((capacity / refillPs) * 2000)) \n" +
            "return allowed";
        return new DefaultRedisScript<>(lua, Long.class);
    }

    private String buildBucketKey(String clientIdentifier) {
        return "rl:tb:" + clientIdentifier;
    }
}

Pub/Sub vs Streams — messaging kab Redis se karein, kab Kafka se

Pub/Sub fire-and-forget hai. Agar aapko delivery guarantee chahiye aur aapne Pub/Sub chuna, to design galat hai.

Problem samasya · what breaks

Order events Redis Pub/Sub par publish ho rahe the. Consumer service deploy ke liye 40 second down thi.

  • Un 40 seconds ke saare events permanently gayab — Pub/Sub me buffer/retention hai hi nahi.
  • Consumer crash hua processing ke beech me → message already “delivered” maana gaya → redelivery nahi.
  • Do consumer instances chalaye → dono ko har message mila (broadcast), load share nahi hua — duplicate processing.
  • Slow consumer ka output buffer bhar gaya → Redis ne client disconnect kar diya.

Solution hal · what to do

Redis Streams use karo (Redis 5+): append-only log with IDs, retention, consumer groups aur explicit ack.

  • XADD stream * field value — event append, ID auto (ms-seq).
  • XGROUP CREATE — consumer group. Group ke andar har message ek consumer ko jata hai (load sharing).
  • XREADGROUP — read + PEL (Pending Entries List) me daalo.
  • XACK — processed. Bina ack ke message PEL me pada rahega.
  • XAUTOCLAIM / XPENDING — mara hua consumer ka kaam doosra uthaye (idle time ke basis par).
  • XADD ... MAXLEN ~ 1000000 — trim, warna stream infinitely badhega.

Pub/Sub tab bhi sahi hai: cache invalidation broadcast, live presence, WebSocket fanout — jahan message ka miss ho jana theek hai.

package com.example.cache.stream;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.data.domain.Range;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.connection.stream.*;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.stream.StreamMessageListenerContainer;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.Map;

@Component
public class OrderEventStreamConsumer implements InitializingBean, DisposableBean {

    private static final Logger log = LoggerFactory.getLogger(OrderEventStreamConsumer.class);

    private static final String STREAM_KEY   = "stream:orders:v1";
    private static final String GROUP_NAME   = "order-projection-service";
    private static final Duration POLL_TIMEOUT = Duration.ofSeconds(2);
    private static final Duration CLAIM_AFTER  = Duration.ofSeconds(60);

    private final StringRedisTemplate stringRedisTemplate;
    private final RedisConnectionFactory connectionFactory;
    private final OrderProjectionHandler orderProjectionHandler;

    private StreamMessageListenerContainer<String, MapRecord<String, String, String>> container;
    private final String consumerName = "consumer-" + java.util.UUID.randomUUID();

    public OrderEventStreamConsumer(StringRedisTemplate stringRedisTemplate,
                                    RedisConnectionFactory connectionFactory,
                                    OrderProjectionHandler orderProjectionHandler) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.connectionFactory = connectionFactory;
        this.orderProjectionHandler = orderProjectionHandler;
    }

    @Override
    public void afterPropertiesSet() {
        createConsumerGroupIfMissing();
        startListening();
    }

    /** Group pehle se ho to BUSYGROUP error aata hai \u2014 usko safely ignore karo. */
    private void createConsumerGroupIfMissing() {
        try {
            stringRedisTemplate.opsForStream()
                    .createGroup(STREAM_KEY, ReadOffset.from("0"), GROUP_NAME);
        } catch (Exception alreadyExists) {
            log.debug("Consumer group already present: {}", GROUP_NAME);
        }
    }

    private void startListening() {
        var options = StreamMessageListenerContainer
                .StreamMessageListenerContainerOptions.builder()
                .pollTimeout(POLL_TIMEOUT)
                .build();

        container = StreamMessageListenerContainer.create(connectionFactory, options);

        container.receive(                                  // auto-ack NAHI: hum khud ack karenge
                Consumer.from(GROUP_NAME, consumerName),
                StreamOffset.create(STREAM_KEY, ReadOffset.lastConsumed()),
                this::handleRecord);

        container.start();
    }

    /**
     * Process -> tabhi ack. Exception aaya to ack nahi hoga,
     * message PEL me rahega aur XAUTOCLAIM se dobara uthaya jayega.
     */
    private void handleRecord(MapRecord<String, String, String> record) {
        Map<String, String> payload = record.getValue();
        String eventId = record.getId().getValue();
        try {
            // Idempotency: at-least-once delivery hai, isliye handler ko
            // duplicate ke liye taiyaar hona chahiye.
            orderProjectionHandler.applyOrderEvent(eventId, payload);
            acknowledgeProcessed(record.getId());
        } catch (RuntimeException processingFailure) {
            log.error("Order event processing failed, leaving unacked. id={}", eventId, processingFailure);
        }
    }

    private void acknowledgeProcessed(RecordId recordId) {
        stringRedisTemplate.opsForStream().acknowledge(STREAM_KEY, GROUP_NAME, recordId);
    }

    /**
     * Jo consumer mar gaya uske pending messages 60s baad utha lo.
     * Scheduler se har 30s call karo.
     */
    public void reclaimStalledMessages() {
        PendingMessages pending = stringRedisTemplate.opsForStream()
                .pending(STREAM_KEY, GROUP_NAME, Range.unbounded(), 100L);

        pending.forEach(message -> {
            if (message.getElapsedTimeSinceLastDelivery().compareTo(CLAIM_AFTER) > 0) {
                stringRedisTemplate.opsForStream().claim(
                        STREAM_KEY, GROUP_NAME, consumerName,
                        org.springframework.data.redis.core.StreamOperations.XClaimOptions
                                .minIdle(CLAIM_AFTER).ids(message.getId()));
                log.warn("Reclaimed stalled message id={}", message.getId());
            }
        });
    }

    @Override
    public void destroy() {
        if (container != null) container.stop();
    }
}

package com.example.cache.consistency;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.time.Duration;

@Service
public class CriticalWriteService {

    private static final Logger log = LoggerFactory.getLogger(CriticalWriteService.class);
    private static final int REQUIRED_REPLICA_ACKS = 1;
    private static final long WAIT_TIMEOUT_MILLIS = 100L;

    private final StringRedisTemplate stringRedisTemplate;

    public CriticalWriteService(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    /**
     * Write karo, phir WAIT se confirm karo ki kam se kam 1 replica ke paas
     * pahunch gaya. Yeh failover par data loss ka window chhota karta hai.
     *
     * Dhyan: WAIT consensus NAHI hai. Yeh sirf batata hai ki kitne replicas ne
     * abhi tak acknowledge kiya. Partition me yeh bhi galat ho sakta hai.
     */
    public boolean writeWithReplicaAcknowledgement(String key, String value, Duration ttl) {
        stringRedisTemplate.opsForValue().set(key, value, ttl);

        Long acknowledgedReplicas = stringRedisTemplate.execute(
                (RedisCallback<Long>) connection ->
                        connection.serverCommands()
                                  .waitForReplicaOf(REQUIRED_REPLICA_ACKS, WAIT_TIMEOUT_MILLIS));

        boolean durable = acknowledgedReplicas != null && acknowledgedReplicas >= REQUIRED_REPLICA_ACKS;
        if (!durable) {
            // Yahan decide karo: retry, alert, ya DB-only path par fallback
            log.warn("Write not replicated within {} ms. key={} acks={}",
                     WAIT_TIMEOUT_MILLIS, key, acknowledgedReplicas);
        }
        return durable;
    }

    /**
     * Read-after-write: jis session ne abhi likha hai use replica se mat padhao.
     * Chhota marker rakho; jab tak marker zinda hai, primary se padho.
     */
    public void markSessionAsRecentWriter(String sessionId) {
        stringRedisTemplate.opsForValue()
                .set(recentWriterKey(sessionId), "1", Duration.ofSeconds(5));
    }

    public boolean shouldReadFromPrimary(String sessionId) {
        return Boolean.TRUE.equals(stringRedisTemplate.hasKey(recentWriterKey(sessionId)));
    }

    private String recentWriterKey(String sessionId) {
        return "rw:" + sessionId;
    }
}

Timeout chhota rakho. WAIT blocking hai — bada timeout aapke p99 ko seedha kha jayega.

Silent failure sabse bura hai. Kam se kam metric/alert nikalo taaki failover ke baad pata ho kitna risk tha.

Simple read-your-writes trick: haal hi me likhne wale session ko 5 second tak primary par bhejo. 5s ≈ typical replication lag ka safe upper bound.

Kab lagayein (apply)

  • WAIT: chhoti si critical writes (idempotency marker, lock fence) par.
  • min-replicas-to-write: jab silent data loss se availability zyada important nahi.
  • Primary-pinned reads: sirf recent writers ke liye.
  • Idempotency keys: har at-least-once path par — hamesha.

Kab chhod dein (ignore)

  • WAIT mat lagao har write par — aapne Redis ko slow synchronous system bana diya, phir Redis ka point hi khatam.
  • Redis se linearizability ki ummeed mat rakho — wo design goal hi nahi hai.
  • Redlock ko distributed consensus mat samjho — uske liye etcd/ZooKeeper hai.
  • Financial ledger Redis me mat rakho — Postgres + outbox pattern sahi jawab hai.

Faisla kaise lein (why)

Ek line me poori philosophy: Redis speed ke badle guarantees bechta hai. Agar aapko dono chahiye, to aap Redis ko cache/index ki tarah use karo aur guarantees uske peeche ke durable store se lo. Interview me yeh samajh dikhana “maine Redis use kiya hai” se kaafi zyada value rakhta hai.

HLD walkthrough — 50,000 RPS product read path, board par kaise banayein

Yeh poora design round hai: requirements, back-of-envelope math, layers, write path, failure modes. Isi order me bolna hai.

Problem samasya · what breaks

Requirement: e-commerce product detail page. Peak 50,000 RPS reads, 800 RPS writes. p99 < 120 ms end-to-end. 20 million products. Traffic Zipf-distributed: top 2% products 70% traffic lete hain. Price change 5 second ke andar dikhna chahiye; description 5 minute me chalega.

Bina cache ke: 50k RPS × 3 queries per page = 150k QPS Postgres par. Ek Postgres node ~8k QPS deta hai. Matlab ~19 nodes sirf reads ke liye — cost aur operational load dono unacceptable.

Naive cache ke saath bhi problem: ek Redis node ~100k ops/s. 50k RPS × 3 keys = 150k ops/s — ek node se zyada. Aur hot key (viral product) ek hi shard par 35k RPS daal degi.

Solution hal · what to do

Back-of-envelope (yeh zaroor bolna):

  • Cacheable working set = top 2% × 20M = 400k products. Avg value 4 KB → ~1.6 GB + overhead ≈ 2.5 GB. Ek node me aaram se fit.
  • Target hit ratio 97% → DB par bachta hai 50k × 0.03 × 3 = 4.5k QPS → ek primary + ek replica kaafi.
  • Redis ops = 150k/s → 3-shard cluster (50k/s per shard, headroom ke saath).

Layers:

  • L0 — CDN/edge: anonymous traffic ke liye 30s micro-cache. Sabse sasta hit.
  • L1 — in-process Caffeine: per pod, 10k entries, TTL 3 s. Hot keys yahin absorb ho jaati hain, Redis tak jaati hi nahi.
  • L2 — Redis Cluster: 3 shards × 1 replica. Logical expiry + single-flight (topic 05).
  • L3 — Postgres: source of truth, read replica reporting ke liye.

Write path: Postgres transaction → outbox row (same txn) → Debezium/CDC → Kafka → invalidation consumer → DEL Redis key + Redis Pub/Sub broadcast → har pod apna L1 entry evict kare. Price ke liye 5s SLA isse pura hota hai.

Failure modes: Redis down → circuit breaker → L1 + DB with bulkhead; cold start → warmup job; hot key → L1 pehle hi bacha leta hai.

package com.example.cache.service;

import com.example.cache.key.CacheKeyFactory;
import com.example.cache.model.Product;
import com.example.cache.repository.ProductJpaRepository;
import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerRegistry;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.util.Optional;
import java.util.concurrent.TimeUnit;
import java.util.function.Supplier;

@Service
public class LayeredProductReadService {

    private static final Logger log = LoggerFactory.getLogger(LayeredProductReadService.class);

    /** L1 ka TTL jaan boojh kar chhota: staleness 3s tak hi rahe. */
    private static final Duration LOCAL_CACHE_TTL = Duration.ofSeconds(3);
    private static final int LOCAL_CACHE_MAX_ENTRIES = 10_000;

    private final Cache<String, Product> localCache;
    private final StampedeSafeCacheService distributedCache;
    private final ProductJpaRepository productJpaRepository;
    private final CacheKeyFactory cacheKeyFactory;
    private final CircuitBreaker redisCircuitBreaker;

    public LayeredProductReadService(StampedeSafeCacheService distributedCache,
                                     ProductJpaRepository productJpaRepository,
                                     CacheKeyFactory cacheKeyFactory,
                                     CircuitBreakerRegistry circuitBreakerRegistry) {
        this.distributedCache = distributedCache;
        this.productJpaRepository = productJpaRepository;
        this.cacheKeyFactory = cacheKeyFactory;
        this.redisCircuitBreaker = circuitBreakerRegistry.circuitBreaker("redis-read");
        this.localCache = Caffeine.newBuilder()
                .maximumSize(LOCAL_CACHE_MAX_ENTRIES)
                .expireAfterWrite(LOCAL_CACHE_TTL.toMillis(), TimeUnit.MILLISECONDS)
                .recordStats()                      // metrics ke liye
                .build();
    }

    /**
     * Read order: L1 (in-process) -> L2 (Redis) -> DB.
     * Har layer neeche wali layer ka load kam karti hai.
     */
    public Optional<Product> findProductForDetailPage(long productId) {
        String cacheKey = cacheKeyFactory.productDetailKey(productId);

        // ---- L1: same JVM, ~50 nanoseconds, hot key yahin ruk jaati hai
        Product fromLocal = localCache.getIfPresent(cacheKey);
        if (fromLocal != null) {
            return Optional.of(fromLocal);
        }

        // ---- L2: Redis, ~0.3 ms. Redis sick ho to breaker isko skip kara dega.
        Product fromRedis = readFromDistributedCacheSafely(cacheKey, productId);
        if (fromRedis != null) {
            localCache.put(cacheKey, fromRedis);
            return Optional.of(fromRedis);
        }

        // ---- L3: source of truth
        Optional<Product> fromDatabase = productJpaRepository.findById(productId);
        fromDatabase.ifPresent(product -> localCache.put(cacheKey, product));
        return fromDatabase;
    }

    /**
     * Redis call ko circuit breaker me lapeto.
     * Redis slow ho jaye to hum har request par 150ms nahi ganwayenge \u2014
     * breaker open hote hi seedha DB path chalega.
     */
    private Product readFromDistributedCacheSafely(String cacheKey, long productId) {
        Supplier<Product> guarded = CircuitBreaker.decorateSupplier(redisCircuitBreaker,
                () -> distributedCache.getWithLogicalExpiry(
                        cacheKey, Product.class,
                        () -> productJpaRepository.findById(productId).orElse(null)));
        try {
            return guarded.get();
        } catch (RuntimeException redisUnavailable) {
            log.debug("Redis path skipped: {}", redisUnavailable.getMessage());
            return null;
        }
    }

    /** Invalidation consumer isko Pub/Sub message par call karta hai. */
    public void evictLocalEntry(String cacheKey) {
        localCache.invalidate(cacheKey);
    }
}

/**
 * Problem: L1 cache har pod ke andar alag hai. Redis key delete karne se
 * pods ke local copies nahi hatti.
 * Solution: invalidation ko Pub/Sub par broadcast karo; har pod apna L1 saaf kare.
 *
 * Yeh wahi ek jagah hai jahan Pub/Sub sahi choice hai \u2014 message miss ho jaye
 * to bhi L1 ka 3 second TTL usko theek kar dega.
 */
@Component

    private static final Logger log = LoggerFactory.getLogger(CacheInvalidationSubscriber.class);
    public static final String INVALIDATION_CHANNEL = "cache:invalidate:v1";

    private final LayeredProductReadService layeredProductReadService;

    public CacheInvalidationSubscriber(LayeredProductReadService layeredProductReadService) {
        this.layeredProductReadService = layeredProductReadService;
    }

    @Override
    public void onMessage(Message message, byte[] pattern) {

        layeredProductReadService.evictLocalEntry(invalidatedKey);

package com.example.cache.core;

import com.example.cache.api.CacheService;
import com.example.cache.codec.CacheCodec;
import com.example.cache.metrics.CacheMetricsRecorder;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import java.util.function.Supplier;

@Service
public class RedisCacheService implements CacheService {

    private static final Logger log = LoggerFactory.getLogger(RedisCacheService.class);
    private static final int SCAN_BATCH = 500;

    private final StringRedisTemplate redis;
    private final CacheCodec codec;
    private final CacheMetricsRecorder metrics;

    public RedisCacheService(StringRedisTemplate redis,
                             CacheCodec codec,
                             CacheMetricsRecorder metrics) {
        this.redis = redis;
        this.codec = codec;
        this.metrics = metrics;
    }

    @Override
    public <T> Optional<T> find(String key, Class<T> type) {
        try {
            String raw = redis.opsForValue().get(key);
            if (raw == null) {
                metrics.recordMiss(type);
                return Optional.empty();
            }
            metrics.recordHit(type);
            return Optional.of(codec.decode(raw, type));
        } catch (RuntimeException cacheFailure) {
            // Deserialization fail bhi yahin aata hai (schema change ke baad).
            // Us case me key ko hata dena sabse safe hai.
            metrics.recordError(type);
            log.warn("Cache read failed, treating as miss. key={}", key, cacheFailure);
            evictQuietly(key);
            return Optional.empty();
        }
    }

    @Override
    public <T> void put(String key, T value, Duration ttl) {
        try {
            redis.opsForValue().set(key, codec.encode(value), ttl);
        } catch (RuntimeException cacheFailure) {
            // Cache me na likh paana kabhi bhi request fail karne ki wajah nahi hai.
            log.warn("Cache write failed, ignoring. key={}", key, cacheFailure);
        }
    }

    /**
     * Ekhi failure policy, ek hi jagah:
     *   hit  -> value
     *   miss -> loader
     *   error-> loader
     * Caller ko kabhi cache ka exception nahi milega.
     */
    @Override
    public <T> T getOrLoad(String key, Class<T> type, Duration ttl, Supplier<T> loader) {
        Optional<T> cached = find(key, type);
        if (cached.isPresent()) {
            return cached.get();
        }
        T loaded = loader.get();
        if (loaded != null) {
            put(key, loaded, ttl);
        }
        return loaded;
    }

    @Override
    public void evict(String key) {
        try {
            redis.unlink(key);
        } catch (RuntimeException cacheFailure) {
            log.warn("Cache evict failed. key={}", key, cacheFailure);
        }
    }

    /** SCAN + UNLINK. KEYS kabhi nahi \u2014 wo server block karta hai. */
    @Override
    public void evictByPrefix(String keyPrefix) {
        ScanOptions options = ScanOptions.scanOptions().match(keyPrefix + "*").count(SCAN_BATCH).build();
        try (Cursor<String> cursor = redis.scan(options)) {
            List<String> batch = new ArrayList<>(SCAN_BATCH);
            while (cursor.hasNext()) {
                batch.add(cursor.next());
                if (batch.size() >= SCAN_BATCH) { redis.unlink(batch); batch.clear(); }
            }
            if (!batch.isEmpty()) redis.unlink(batch);
        } catch (RuntimeException cacheFailure) {
            log.warn("Prefix evict failed. prefix={}", keyPrefix, cacheFailure);
        }
    }

    private void evictQuietly(String key) {
        try { redis.unlink(key); } catch (RuntimeException ignored) { /* best effort */ }
    }
}

  • Embedded/mock Redis par mat rely karo Lua aur TTL tests ke liye.

Faisla kaise lein (why)

LLD round me interviewer teen cheezein dekh raha hai: seams (kahan se test/replace kar sakte ho), failure policy (ek hi consistent rule), aur naming (method ka naam padh ke kaam samajh aaye). Design pattern ka naam bolna optional hai; yeh teen cheezein nahi.

Tradeoff framework — kaunsa apply karein, kaunsa ignore karein, aur kyun

Yeh section aapke poore answer ka spine hai. Interviewer ko yahi sunna hai: aap options jaante ho, aur unme se chunna bhi jaante ho.

Problem samasya · what breaks

Do tarah ke candidates fail hote hain:

  • Buzzword candidate: “Redis Cluster lagayenge, Redlock lagayenge, Bloom filter, write-behind, CDC, L1+L2+L3.” Requirement 400 RPS ki thi. Yeh over-engineering hai — aur interviewer turant poochta hai “kyun?”, jawab nahi hota.
  • One-trick candidate: “Redis me daal denge, TTL 5 minute.” Interviewer poochta hai stampede, invalidation, hot key — aur design girta hai.

Beech ka raasta yaad rakhna mushkil hai kyunki har technique alag lagti hai. Isiliye ek framework chahiye.

Failure Bno failure modes

Solution hal · what to do

Paanch sawaal, isi order me. Har design decision inhi se nikalta hai:

  • 1. Staleness ka nuqsaan kitna hai? → TTL length aur invalidation strategy decide hoti hai. Cents me nuqsaan → lamba TTL. Rupaye/compliance → event-driven ya cache hi nahi.
  • 2. Rebuild kitna mehnga hai? → stampede protection chahiye ya nahi. <10 ms → kuch nahi chahiye. >100 ms + hot → single-flight + logical expiry.
  • 3. Access distribution kaisa hai? → uniform → cache ka fayda kam, LRU theek. Skewed (Zipf) → L1 cache + LFU + hot key handling.
  • 4. Data ka role kya hai — copy ya truth? → copy → eviction on, persistence optional. Truth → noeviction, AOF, replicas, aur ek dobara soch.
  • 5. Redis gir jaye to kya ho? → jawab hamesha “degrade” hona chahiye, “down” nahi. Isliye circuit breaker + DB fallback + bulkhead.

Problem samasya · what breaks

package com.example.cache.guard;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

/**
 * Rules ko documentation me likhne se koi nahi padhta.
 * Inko code me daalo, phir violation build ya metric me dikhega.
 */
@Component
public class CacheEligibilityPolicy {

    private static final Logger log = LoggerFactory.getLogger(CacheEligibilityPolicy.class);

    private static final int MAX_VALUE_BYTES        = 100 * 1024;   // 100 KB hard limit
    private static final int WARN_VALUE_BYTES       = 10 * 1024;    // 10 KB se upar shak karo
    private static final int MAX_COLLECTION_ENTRIES = 10_000;

    /**
     * Bada value cache karne se rok do. Ek 2 MB ka page cache karna
     * memory aur network dono kharab karta hai.
     */
    public boolean isValueSizeAcceptable(String cacheKey, byte[] serializedValue) {
        int size = serializedValue.length;

        if (size > MAX_VALUE_BYTES) {
            log.error("Refusing to cache oversized value. key={} bytes={}", cacheKey, size);
            return false;
        }
        if (size > WARN_VALUE_BYTES) {
            log.warn("Large cache value \u2014 consider splitting. key={} bytes={}", cacheKey, size);
        }
        return true;
    }

    /** Collection ko bounded rakho, warna ek din wo "big key" incident banega. */
    public boolean isCollectionSizeAcceptable(String cacheKey, long elementCount) {
        if (elementCount > MAX_COLLECTION_ENTRIES) {
            log.error("Collection too large for a single key. key={} elements={}", cacheKey, elementCount);
            return false;
        }
        return true;
    }

    /**
     * TTL-less write ko block karo. Yeh ek line lakhon orphan keys rok deti hai.
     */
    public boolean hasValidExpiry(String cacheKey, long ttlSeconds) {
        if (ttlSeconds <= 0) {
            log.error("Cache write without TTL is not allowed. key={}", cacheKey);
            return false;
        }
        return true;
    }

    /**
     * Hit ratio observe karo: jo prefix consistently miss karta hai,
     * usko cache karna sirf memory aur latency ka waste hai.
     */
    public boolean isWorthCaching(String keyPrefix, double observedHitRatio, long callsPerMinute) {
        boolean worthIt = observedHitRatio > 0.25 && callsPerMinute > 10;
        if (!worthIt) {
            log.info("Caching not paying off. prefix={} hitRatio={} callsPerMin={}",
                     keyPrefix, observedHitRatio, callsPerMinute);
        }
        return worthIt;
    }
}

Mock interview questions — jawab ke saath

Pehle khud jawab sochiye, phir kholiye. Har jawab me wahi structure hai jo topic 16 me tha: signal, choice, price, rejected alternative.

basics1. Redis single-threaded hai to itna fast kaise hai?

Speed ka source thread count nahi hai:

  • RAM access — disk seek nahi, sab memory me.
  • No lock contention — ek thread matlab mutex, context switch aur cache-line bouncing ka kharcha zero.
  • I/O multiplexing — epoll/kqueue se ek thread hazaaron connections handle karta hai.
  • Optimized data structures — chhote objects ke liye ziplist/listpack, bade ke liye skiplist/hashtable.
  • Simple protocol — RESP parse karna sasta hai.

Redis 6+ me I/O threads sirf socket read/write parallel karte hain; command execution ab bhi single-threaded hai. Isliye ek slow O(N) command aaj bhi sabko block karta hai.

basics2. SET key val EX 60 aur SETEX key 60 val me kya farq hai?

Result same hai. SET modern, flexible form hai — usme NX, XX, GET, KEEPTTL, EX/PX/EXAT sab options milte hain, aur sab ek atomic command me.

Practical advice: hamesha SET use karo. SETEX/SETNX legacy hain, aur SETNX alag se EXPIRE maangta hai — wahi do-command wala deadlock bug paida karta hai.

basics3. TTL expire hone par Redis key turant delete karta hai kya?

Nahi. Do mechanism hain:

  • Lazy (passive) expiry — jab key access hoti hai tab check hota hai; expired hui to delete aur “not found” return.
  • Active expiry — background me har 100ms par random sample uthata hai; agar 25% se zyada expired mile to dobara sample karta hai.

Iska matlab: expired key kuch der tak memory me ho sakti hai. Isliye used_memory logical dataset se bada dikh sakta hai, aur isliye TTL akela memory control nahi karta — maxmemory policy bhi chahiye.

basics4. Cache hit ratio kitna “achha” hai?

Absolute number ka matlab nahi — workload par depend karta hai. Practical bands:

  • >95% — healthy read cache.
  • 80–95% — kaam kar raha hai, par TTL ya working set tune karne ki gunjaish hai.
  • 50–80% — investigate karo: TTL bahut chhota? eviction ho rahi hai? key cardinality bahut zyada?
  • <50% — cache apni memory ki keemat nahi nikaal raha.

Zyada important baat: hit ratio ke saath evicted_keys dekho. High hit ratio + high evictions matlab aap capacity ki seema par ho.

basics5. DEL aur UNLINK me kya farq hai?

DEL memory ko main thread par free karta hai — ek 500 MB ka hash delete karoge to server utni der block ho jayega.

UNLINK key ko keyspace se turant hata deta hai (client ko O(1) lagta hai) aur asli memory reclaim background thread karta hai.

Rule: chhoti keys par dono barabar; badi collections par hamesha UNLINK. Config me lazyfree-lazy-* options isi behaviour ko eviction aur expiry ke liye bhi on kar dete hain.

mid-level6. Cache stampede kya hai aur aap use kaise rokoge?

Ek popular key expire hoti hai, aur usi instant me saare concurrent readers miss hote hain — sab ek saath DB par same query maarte hain. DB gir jata hai.

Teen layered defence:

  • Single-flight lock — SET rebuildLock token NX PX 10000. Jeetne wala DB se load kare, baaki thoda ruk kar cache dobara padhein.
  • Logical expiry (stale-while-revalidate) — value ke andar expiresAt, Redis TTL bahut lamba. Expiry ke baad purana value turant return karo aur background me refresh karo. Users ko latency spike milta hi nahi.
  • TTL jitter — keys ek saath expire na hon.

Kaunsa? Rebuild cost dekho: <10 ms → kuch nahi chahiye. >100 ms + hot key → logical expiry sabse achha UX deta hai.

mid-level7. Cache penetration aur cache avalanche me farq batao.
  • Penetration — requests aisi keys maangti hain jo exist hi nahi karti. Cache kabhi populate nahi hoga, isliye har request DB tak jayegi. Aksar attack ya buggy client. Fix: negative caching (short TTL) + Bloom filter + input validation.
  • Avalanche — bahut saari keys ek saath unavailable ho jaati hain (mass expiry ya Redis restart). Cache tha, ab nahi hai. Fix: TTL jitter, warmup on start, replica/HA, DB ke aage circuit breaker + rate limit.

Yaad rakhne ka tareeka: penetration = “data kabhi tha hi nahi”. Avalanche = “data tha, ek saath gaya”. Stampede = “ek key gayi, bheed lag gayi”.

mid-level8. Write ke waqt cache update karein ya delete?

Delete karo. Reason ordering hai.

Do concurrent writers agar dono cache update karein, to network reorder ki wajah se purana value baad me land kar sakta hai — aur wo TTL tak stuck rahega. Delete idempotent hai: do delete = ek delete, aur agla read fresh value laayega.

Sequence bhi important hai: pehle DB commit, phir cache delete (transaction ke afterCommit me). Aur agar aap ekdum paranoid ho, delayed double delete — 500 ms baad ek aur delete, taaki koi in-flight reader purana value na chhod jaye.

Exception: agar value bahut mehngi hai aur aapke paas version number/CAS hai, to conditional update (Lua se) bhi theek hai — par tab aapko ordering khud handle karni hogi.

mid-level9. Redis Cluster me multi-key operation kyun fail hoti hai, aur fix kya hai?

Cluster me keyspace 16384 hash slots me bata hai; slot = CRC16(key) mod 16384. Har master kuch slots owns karta hai. Multi-key command (MGET, SUNION, MULTI, Lua with multiple KEYS) tabhi chal sakti hai jab saari keys ek hi slot me hon — warna CROSSSLOT error.

Fix — hash tags: key me {...} daalo; sirf braces ke andar ka hissa hash hoga.

user:{1042}:profile
user:{1042}:cart      ← dono ka slot same

Caution: hash tag har jagah mat lagao. Agar sab keys ek hi tag share karengi to sab ek shard par chali jayengi aur aapne cluster ka poora point khatam kar diya. Related keys ko group karo, unrelated ko nahi.

mid-level10. Redis se rate limiter banao — 100 requests per minute per user.

Teen options, badhti hui accuracy ke saath:

  1. Fixed window: INCR user:{id}:{minute} + EXPIRE 60. Sabse sasta. Problem: window boundary par 2× burst possible (12:00:59 par 100 + 12:01:00 par 100).
  2. Sliding window log: ZSet me har request ka timestamp. ZREMRANGEBYSCORE se purane hatao, ZCARD se count, limit se kam ho to ZADD. Bilkul exact, par memory = limit × users.
  3. Sliding window counter: current + previous window ka weighted estimate. Do counters, accuracy kaafi achhi. Public API ka best default.

Non-negotiable: poora decision ek Lua script me ho. Java me GET → if → INCR likhoge to concurrent requests limit tod dengi. Aur response me Retry-After zaroor bhejo.

mid-level11. @Cacheable use karein ya manual RedisTemplate?

@Cacheable tab: simple CRUD read caching, prototype, ya jahan cache logic me kuch special nahi hai. Boilerplate zero.

Manual tab: jab chahiye — per-key dynamic TTL, stampede protection (single-flight), logical expiry, negative caching with different TTL, partial invalidation, ya custom serialization per type.

Gotchas jo interview me poochhe jaate hain:

  • @Cacheable Spring proxy par chalta hai — same class ke andar se method call karoge to cache bypass ho jayega (self-invocation).
  • Default key generator saare params ka hash leta hai — debugging mushkil.
  • Exception handling ke liye alag se CacheErrorHandler configure karna padta hai, warna Redis down = request fail.
mid-level12. Pub/Sub aur Streams me kab kya chunoge?

Pub/Sub — fire and forget. Koi retention nahi, koi ack nahi, offline subscriber ke liye kuch store nahi hota, aur ek message saare subscribers ko jata hai (broadcast).
Sahi use: cache invalidation broadcast, presence/typing indicators, WebSocket fanout, config reload signal. In sab me ek message ka miss ho jana recoverable hai.

Streams — append-only log with IDs, consumer groups, PEL aur explicit XACK. Ek message group ke andar ek consumer ko jata hai (load sharing), aur crash par XAUTOCLAIM se dusra utha leta hai.
Sahi use: order events, job queue, outbox delivery, kuch bhi jisme delivery matter karti hai.

Ek line ka rule: agar message ka gum jana bug hai, Pub/Sub mat use karo.

senior13. Redlock ke baare me kya sochte ho? Distributed lock ke liye Redis use karoge?

Redlock antirez ka multi-master algorithm hai: N independent Redis masters par lock lo, N/2+1 par safal hone par lock mila maano, aur elapsed time lease se kam ho.

Martin Kleppmann ka objection: yeh timing par depend karta hai. Client GC pause me chala jaye ya clock drift ho jaye, to lease expire ho sakti hai jabki client sochta hai ki lock uske paas hai — do owners ek saath. Asynchronous model me yeh mutual exclusion guarantee nahi de sakta.

Mera practical stance (aur yehi interview me bolna chahiye):

  • Redis lock ek efficiency lock hai — “duplicate kaam na ho, CPU/paisa bache”. Iske liye SET NX PX + Lua release bilkul kaafi hai.
  • Correctness ke liye Redis par mat tango. Downstream par fencing token (monotonic INCR, DB me WHERE fence < :incoming) ya idempotency key rakho.
  • Agar sach me consensus chahiye — etcd/ZooKeeper (Raft/ZAB) use karo. Wo isi kaam ke liye bane hain.
  • Single Redis deployment par Redlock lagane ka koi fayda nahi — wo multi-master algorithm hai.
senior14. Failover ke waqt Redis writes kho sakta hai? Explain.

Haan, aur yeh design ka hissa hai.

Replication asynchronous hai. Primary client ko OK bhejta hai replica ke ack ka intezaar kiye bina. Agar us microsecond me primary crash ho jaye, wo write kabhi replicate nahi hui — aur Sentinel/Cluster jab replica ko promote karega, wo write gayab ho jayegi. Client ke paas OK tha.

Split brain me aur bhi: partition ke minority side par purana primary writes leta rahega; heal hone par wo replica ban jayega aur uska diverged data discard ho jayega.

Mitigation (poora fix nahi):

  • WAIT n timeout — n replicas tak pahunchne ka confirm. Consensus nahi hai, par window chhoti karta hai.
  • min-replicas-to-write + min-replicas-max-lag — minority primary writes reject kare.
  • AOF everysec — node-level crash recovery.
  • Design level: Redis ko truth mat banao. Jo data kho nahi sakta wo durable DB me rakho.
senior15. Ek key par 60,000 RPS aa rahi hai aur wo ek shard ko maar rahi hai. Kya karoge?

Order of attack — sasta se mehnga:

  1. Confirm karo ki hot key hai: redis-cli --hotkeys (LFU on hona chahiye), per-shard ops/sec, INFO commandstats.
  2. L1 in-process cache (Caffeine, TTL 1–5 s) — sabse zyada return. 20 pods × 3s TTL matlab Redis par ~7 RPS bachte hain instead of 60k. Keemat: staleness 3s aur cross-pod invalidation ke liye Pub/Sub broadcast.
  3. Key replication/sharding — key#0 se key#9 tak N copies, read par random pick. Load N shards me bat jata hai. Keemat: invalidation ab N keys par.
  4. Read replicas — us shard ke replicas se padho (READONLY). Keemat: stale reads.
  5. Client-side batching/pipelining — agar same request repeatedly aa rahi hai to request coalescing.

Interview me yeh line add karo: “Main L1 se shuru karunga kyunki wo network hop hi khatam kar deta hai; key sharding tab jab L1 ki staleness acceptable na ho.”

senior16. Cache aur DB ke beech consistency kaise maintain karoge multi-service architecture me?

Multi-service me har service ka apna delete call karna reliable nahi hai — ek service bhool jaye ya fail ho jaye to stale data reh jata hai. Ek hi reliable path chahiye:

  1. Transactional outbox — business write aur outbox row ek hi DB transaction me. Ab “DB likha par event nahi gaya” possible hi nahi.
  2. CDC (Debezium) outbox table ko tail kare → Kafka topic.
  3. Invalidation consumer → Redis DEL + L1 ke liye Pub/Sub broadcast.
  4. TTL safety net — pipeline kabhi fail ho to bhi data TTL par khud theek ho jayega.
  5. Version/monotonic guard — value ke saath version rakho; purani version wali write ignore karo (out-of-order events se bachav).

Kab yeh sab mat karo: agar ek hi service writer hai — seedha commit ke baad delete kar do. Yeh poora pipeline sirf tab justify hota hai jab multiple writers hon ya freshness SLA seconds me ho. Interview me yeh caveat bolna zaroori hai, warna over-engineering lagega.

senior17. Redis ke liye capacity planning kaise karoge? Numbers dikhao.

Chaar steps, board par likhne layak:

  1. Working set: total entities × hot fraction. Example: 20M products × 2% = 400k keys.
  2. Memory: (avg value size + key size + overhead) × keys. Redis overhead ~50–100 B per key (dictEntry, robj, expire entry). 400k × (4 KB + 100 B) ≈ 1.7 GB. Fragmentation + replication buffer + COW headroom ke liye ×1.5 ≈ 2.5 GB. Provision 4 GB.
  3. Throughput: ek node realistically 80k–120k ops/s (pipelining aur value size par depend). 150k ops/s chahiye → 3 shards headroom ke saath.
  4. Network: 150k ops/s × 4 KB = 600 MB/s — yeh 10 Gbps NIC ka aadha hai. Bade values par network hi pehla bottleneck banta hai, CPU nahi. Yeh point bahut kam candidates uthate hain.

Aur yeh add karo: “maxmemory usable RAM ka 70–75% rakhunga” — kyunki fork/COW, client output buffers aur replication backlog ko bhi jagah chahiye.

senior18. Redis down ho jaye to aapka system kya karega?

Jawab hamesha “degrade, not down” hona chahiye. Layers:

  • Circuit breaker (Resilience4j) Redis calls ke around — breaker open hote hi hum har request par 150 ms timeout nahi ganwate, seedha DB path.
  • Bulkhead / semaphore DB path par — warna 50k RPS seedha DB par jayegi aur wo bhi gir jayega. Concurrency cap + queue + fast 503 for overflow.
  • L1 in-process cache — Redis ke bina bhi hot keys serve karta rahega.
  • Load shedding + rate limiting — gateway par, taaki priority traffic bache.
  • Stale-if-error — agar L1 me purana data hai to usko serve karo aur header me mark kar do.
  • Recovery: Redis wapas aane par sab ek saath cache warm karne mat lag jao — warna DB par apna hi stampede bana doge. Gradual warmup + single-flight.

Ek line jo interviewer ko pasand aati hai: “Cache failure ka blast radius DB par padta hai, isliye DB ke aage bulkhead cache ke jitna hi zaroori hai.”

senior19. Aap ek URL shortener design kar rahe ho. Redis kahan aur kyun?

Redis kahan lagega:

  • Read cache (main use): short:{code} → longUrl. Redirect path ka p99 sabse important hai; 99% traffic reads hoti hai. TTL 24 h + jitter, negative cache 30 s for invalid codes.
  • ID generation: INCR se counter, phir base62 encode. Ya batch me range allocate karo (INCRBY 1000) taaki har request par Redis hit na ho.
  • Rate limiting: per-IP creation limit, spam rokne ke liye.
  • Analytics buffer: click counts HINCRBY se, periodically DB me flush (write-behind — yahan thoda loss acceptable hai).
  • Bloom filter: custom alias ki availability check, DB hit se pehle.

Redis kahan NAHI: mapping ka source of truth Redis nahi hoga — wo durable DB me. Redis kho jaye to links kaam karte rahenge, bas dheeme.

Tradeoff line: “Deleted/expired link cache me 24 ghante tak zinda reh sakta hai, isliye delete par explicit eviction karunga aur TTL ko safety net ki tarah rakhunga.”

tradeoff20. RDB, AOF, ya dono? Kaise decide karoge?

Data ke role se decide hota hai, ideology se nahi:

  • Pure cache node → halka RDB (save 900 1) ya kuch bhi nahi. Truth DB me hai; AOF ka disk I/O aur fsync jitter yahan sirf kharcha hai. RDB rakhne ka ek hi fayda: restart par warm start, jo avalanche rokta hai.
  • Session / lock / rate-limit state → AOF everysec + aof-use-rdb-preamble yes + replica. ~1 s ka loss window acceptable hai, throughput lagbhag full rehta hai.
  • Redis as primary store → hybrid + replicas + offsite backups — aur saath me yeh sawaal ki kya Redis sahi choice hai.

Kya ignore karna hai: appendfsync always — 10–15× throughput cost. Aur write-heavy node par frequent RDB — fork + copy-on-write memory 2× tak le ja sakta hai aur latency spike deta hai.

Aur ek important line: persistence ≠ HA. Persistence crash recovery hai; HA replica + automatic failover hai. Interview me yeh distinction bolna chahiye.

tradeoff21. LRU vs LFU — kaunsa evict policy chunoge?

LRU (allkeys-lru) — “haal hi me use hua”. Traffic pattern badalne par jaldi adapt karta hai. General cache ka safe default.

LFU (allkeys-lfu) — “kitni baar use hua” (counter decay ke saath). Do jagah clearly behtar:

  • Strongly skewed (Zipf) traffic — asli hot set stable rehta hai.
  • Scan pollution — nightly report job poore table par ghoomti hai. LRU us data ko “recent” maan kar aapka hot set nikal dega; LFU nahi, kyunki wo data sirf ek baar chhua gaya.

Ignore karne wali baat: perfect LRU. Redis approximate LRU karta hai — maxmemory-samples (default 5) keys ka sample uthata hai. 10 karne se quality badhti hai aur CPU bhi; 5 se 10 tak jaana theek hai, 100 karna bekaar hai.

Mixed workload (cache + durable state ek node par) → volatile-lru, taaki bina TTL wali keys safe rahein. Par behtar solution yeh hai ki unhe alag instance par rakho.

tradeoff22. Interview me kab bolna chahiye “yahan cache nahi lagayenge”?

Yeh bolna aksar cache add karne se zyada marks deta hai. Situations:

  • Write-heavy, read-rare — cache hamesha cold rahega, hit ratio 10%.
  • Uniform random access — koi hot set nahi. 20M products me se har request random → cache sirf memory kha raha hai.
  • Strong read-after-write — wallet balance, seat inventory ka final state, OTP verification.
  • Data ek baar hi padha jayega — one-time tokens, download links.
  • Query already fast hai — primary-key lookup on an indexed table with warm buffer pool ~1 ms hai. Uske aage cache lagana network hop + invalidation complexity add karta hai, fayda lagbhag zero.
  • Traffic hi kam hai — 500 RPS par ek naya moving part justify nahi hota.

Bolne ka tareeka: “Is path par main cache nahi lagaunga kyunki access uniform hai aur hit ratio 15% se upar nahi jayega — wo memory main hot product path ko dunga.”

tradeoff23. Consistency chahiye par latency bhi — kaise balance karoge?

“Dono” ka jawab granularity hai: alag data ko alag treatment do.

  • Tier 1 (must be exact): balance, inventory count at checkout, auth state → cache nahi, ya sirf primary se read. Latency yahan zyada nahi bhi ho to chalega, kyunki volume kam hai.
  • Tier 2 (seconds stale OK): price, stock badge, recommendations → Redis + short TTL + event invalidation.
  • Tier 3 (minutes stale OK): description, images, category tree → lamba TTL + CDN.

Aur specific tools: read-after-write ke liye us session ko kuch second primary par pin karo; critical writes par WAIT 1 100; aur har jagah idempotency taaki retry safe rahe.

Interview line: “Main poore system ke liye ek consistency model nahi chunuunga — main data ko tiers me baatunga aur har tier ko uska apna budget dunga.”

coding24. Lua script kyun chahiye jab MULTI/EXEC pehle se hai?

MULTI/EXEC commands ko queue karke atomically chalata hai — par beech me koi decision nahi le sakta, kyunki queue hone ke waqt pichle command ka result available hi nahi hota.

Jahan bhi “agar X hai to Y karo” chahiye, wahan Lua chahiye:

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else return 0 end

Yeh lock release hai — GET, compare aur DEL ek atomic unit me. Java me likhoge to GET aur DEL ke beech lock expire ho sakta hai aur aap kisi aur ka lock delete kar denge.

Alternative: WATCH + MULTI (optimistic locking) — kaam karta hai par contention par retry loop chahiye. Lua simpler aur ek round trip me.

Caution: Lua bhi single thread par chalti hai. Script chhoti rakho — 100k iteration ka loop wahi KEYS wali blocking problem dobara bana dega. Aur cluster me script ki saari keys same slot me honi chahiye.

coding25. Spring Boot me Redis timeout aur connection pool kaise configure karoge?

Timeouts — sabse important config:

  • commandTimeout 100–200 ms. Rule: yeh aapke upstream SLO se kaafi chhota hona chahiye, warna cache hi aapka bottleneck ban jayega.
  • connectTimeout ~300 ms.
  • DisconnectedBehavior.REJECT_COMMANDS — warna Lettuce disconnect ke dauran commands queue karta rahega, memory badhegi aur latency chhup jayegi.

Pooling: Lettuce netty-based aur thread-safe hai — ek shared connection zyadatar cases me kaafi hai, pool ki zaroorat nahi. Pool (commons-pool2) tab chahiye jab aap blocking commands (BLPOP), transactions, ya SELECT use karte ho — kyunki wo connection ko occupy karte hain. Jedis me har thread ko connection chahiye, isliye wahan pool mandatory hai.

Bonus point: Micrometer se Lettuce ki command latency expose karo — client-side latency me network shaamil hota hai, isliye wo server-side INFO commandstats se zyada sach batata hai.

coding26. Cache key design ke rules kya hain?
  • Namespace + version + entity + id: shop:v3:product:1042. Version bump = poora purana keyspace apne aap retire (bina FLUSH ke).
  • Ek hi jagah se generate karo — CacheKeyFactory. Inline string concatenation se teen alag formats ban jaate hain aur teeno stale rehte hain.
  • Query caches me har parameter daalo — page, sort, filters. Ek param chhoot gaya to do alag queries ek key share karengi.
  • Keys chhoti rakho — key khud memory leti hai. 400k keys × 60 extra bytes = 24 MB sirf naam par.
  • Cluster: related keys ko {hashTag} se group karo, unrelated ko bilkul nahi.
  • Human-readable — redis-cli me SCAN karke samajh aana chahiye. Hash-only keys debugging namumkin bana dete hain.
  • PII kabhi nahi — email/phone key me mat daalo; logs aur SLOWLOG me leak ho jata hai. Hash kar do.
coding27. Ek hot key ko atomically increment karna hai aur limit bhi check karni hai. Code kaise likhoge?

Java me GET → if → INCR mat likhna — wo race hai. Ek Lua script:

local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local limit   = tonumber(ARGV[1])
if current >= limit then
  return -1
end
local updated = redis.call('INCR', KEYS[1])
if updated == 1 then
  redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))
end
return updated

Java side:

public long incrementIfUnderLimit(String key, long limit, long ttlSeconds) {
    Long result = stringRedisTemplate.execute(
            limitedIncrementScript, List.of(key),
            String.valueOf(limit), String.valueOf(ttlSeconds));
    return result == null ? -1 : result;
}

Do details jo interviewer dhoondta hai: (1) EXPIRE sirf tab jab counter naya bana (updated == 1) — warna har increment TTL reset kar dega aur window kabhi khatam hi nahi hogi. (2) -1 ek explicit “denied” signal hai, exception nahi — rate limiting ek normal outcome hai, error nahi.

coding28. Cache ka unit test kaise likhoge?

Teen levels, teeno alag cheez verify karte hain:

  • Unit test — CacheService ka in-memory fake inject karo. Yahan aap business logic test kar rahe ho, Redis nahi. Fast, koi container nahi.
  • Integration test — Testcontainers se asli redis:7.2-alpine. Yahan TTL expiry, Lua scripts, serialization aur maxmemory behaviour verify hota hai — embedded/mock Redis inme se kuch bhi theek se emulate nahi karta.
  • Concurrency test — CountDownLatch se 50 threads ek saath chhodo aur assert karo ki loader sirf ek baar chala. Yehi single-flight ka asli test hai.

Assert kya karna hai: sirf “value wapas aayi” nahi. Asli contract yeh hai ki doosri call par DB nahi gaya — isliye loader invocation count karo. Aur TTL test me actual expiry ka intezaar karo, mock clock se nahi (Redis ka apna clock hai).

coding29. SCAN ki guarantee kya hai? KEYS se kyun behtar hai?

KEYS poore keyspace par ek hi call me ghoomta hai — O(N) with N = total keys, aur us dauran server block rehta hai. 12M keys par yeh seconds le sakta hai, matlab har client ka timeout.

SCAN cursor-based hai: har call thoda kaam karti hai aur cursor return karti hai. Beech me doosre clients chal sakte hain.

Guarantees (yeh exactly bolna):

  • Jo key poore iteration ke dauran maujood rahi, wo zaroor at least ek baar milegi.
  • Jo key poore iteration ke dauran maujood nahi thi, wo nahi milegi.
  • Iteration ke beech me add/delete hui keys mil bhi sakti hain, nahi bhi.
  • Ek key ek se zyada baar mil sakti hai — isliye aapka handler idempotent hona chahiye.

COUNT ek hint hai, guarantee nahi — 100–1000 practical range hai. Aur MATCH filtering server par scan ke baad hoti hai, isliye ek call zero results bhi de sakti hai; cursor 0 hone tak loop chalana zaroori hai.
