Meta Common Patterns — Sab Answers Ka Core

Agar aap 124 questions ke answers ko dhyan se dekho, toh 10 patterns baar-baar repeat hote hain. Interview mein yeh patterns pehchano — 80% answers inhi se ban jaate hain.

🔗 Sab Answers Ka Common Thread

Har design mein yeh 4 sawaal poocho:

  • Consistency chahiye ya availability? → CAP trade-off decide karo. Banking = CP, social feed = AP.
  • Duplicate request aaye toh? → Idempotency key + result replay. Har mutating API pe.
  • Ek cheez fail ho jaaye toh? → Retry with jitter, circuit breaker, fallback, degrade gracefully.
  • Scale kaise karega? → Stateless app tier, sharded data, cached reads, async writes, bounded queues.

In 4 sawaalon ke jawab se 90% HLD design khud ban jaata hai. Baaki 10% domain-specific details hain.

💳 Payment Platform — End-to-End

Requirements: User A se B ko paisa transfer. Exactly-once (double charge nahi), ledger consistent (paise gayab nahi), audit trail, PCI compliant, multi-region HA.

┌──────────┐ ┌──────────┐ ┌──────────────┐ ┌──────────┐ ┌─────────┐ │ Client │──▶│ API GW │──▶│ Payment Svc │──▶│ Ledger │──▶│ Bank │ └──────────┘ └──────────┘ └──────┬───────┘ └────┬─────┘ └─────────┘ │ │ ┌──────▼───────┐ ┌────▼─────┐ │ Idempotency │ │ Outbox │ │ Table │ │ Table │ └──────────────┘ └────┬─────┘ │ ┌───────▼────────┐ │ Kafka │ └───────┬────────┘ │ ┌─────────────▼─────────────┐ │ Notification / Audit / │ │ Reconciliation consumers │ └────────────────────────────┘

Data Flow (step by step):

Client requestHeader mein Idempotency-Key: uuid bhejta hai. Yeh client generate karta hai, retry pe same key.
Idempotency guardPayment service pehle INSERT INTO idempotency(key, status) karta hai. Duplicate key pe unique violation → purana result return. Yeh exactly-once ka core hai.
Lock accounts (ordered)SELECT ... FOR UPDATE chhote ID pehle. Deadlock impossible.
Business rules + double-entryBalance check → debit A → credit B → 2 ledger rows (debit + credit). Sum = 0, hamesha.
Outbox insertSame DB transaction mein outbox(event) row. Atomic — ya dono ya koi nahi.
Mark completed + commitIdempotency record COMPLETED + response store. Ek hi transaction commit.
Outbox dispatcher (async)Background poller outbox rows padhta hai, Kafka pe publish karta hai, SENT mark karta hai. Crash-safe.
ConsumersNotification, audit log, reconciliation — sab idempotent (event id se dedup).
🔑 Key Answer

Exactly-once = at-least-once delivery + idempotent processing. Network pe true exactly-once impossible hai. Isliye:

  • Idempotency key se duplicate suppress karo (unique constraint DB-level pe)
  • Outbox se event loss rokо (DB tx + event atomic)
  • Consumer-side dedup (event id table) se double processing rokо

Failure modes & handling:

Crash after commit, before Kafka publishOutbox row DB mein hai. Restart pe dispatcher uthata hai. Event lost nahi.

💬 Real-time Chat — WhatsApp/Slack Class

Requirements: 1:1 + group chat, delivery/read receipts, media, presence, multi-device sync, E2E encryption, millions of concurrent connections.

┌─────────┐ WSS ┌──────────────┐ ┌──────────────┐ │ Client │◀──────────▶│ WS Gateway │───▶│ Chat Service│ └─────────┘ │ (Netty) │ └──────┬───────┘ └──────┬───────┘ │ │ │ ┌──────▼───────┐ ┌──────▼───────┐ │ Presence │ │ Kafka │ │ (Redis) │ │ (events) │ └──────────────┘ └──────┬───────┘ │ ┌──────────────────────────┼──────────────────┐ │ │ │ ┌─────▼─────┐ ┌───────▼──────┐ ┌──────▼──────┐ │ Cassandra │ │ Fan-out Svc │ │ Push Svc │ │ (messages)│ │ (per conv) │ │ (FCM/APNs) │ └───────────┘ └──────────────┘ └─────────────┘

Key design decisions:

DecisionChoiceKyun
TransportWebSocket (WSS)Full-duplex, low overhead. Polling wasteful, long-polling connection churn.
Message storeCassandra / ScyllaDBWrite-heavy, time-series, partition by conversation_id. Linear scale.

🔑 Key Answer

Chat ka core trade-off: Fan-out cost vs read latency.

  • Fan-out on write: Write mehnga (N copies), read sasta (ek lookup). Small groups ke liye best.
  • Fan-out on read: Write sasta (1 copy), read mehnga (N lookups). Large groups ke liye best.
  • Hybrid: Threshold (e.g. 500 members) ke aage read fan-out. Real systems yahi karte hain.

Connection state: Millions of WebSocket connections = stateful gateways. Sticky routing by user_id. Gateway crash = reconnect storm — exponential backoff + jitter chahiye.

Distributed implementation (Redis):

Lua script — atomic token bucket in RedisLUA
-- KEYS[1] = bucket key, ARGV = capacity, refill_rate, now, requested
local tokens = redis.call('HGET', KEYS[1], 'tokens')
local last   = redis.call('HGET', KEYS[1], 'ts')
if not tokens then tokens = ARGV[1]; last = ARGV[3] end

-- refill: elapsed seconds * rate, capped at capacity
local elapsed = ARGV[3] - last
local refill  = elapsed * ARGV[2]
tokens = math.min(ARGV[1], tokens + refill)

-- consume or reject
if tokens >= ARGV[4] then
  tokens = tokens - ARGV[4]
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
  return 1                    -- allowed
else
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
  return 0                    -- rejected
end

Kyun Lua? Redis single-threaded hai, Lua script atomically chalti hai. Read-modify-write race khatam. Warna two clients simultaneously read karke dono consume kar lete.

🔑 Key Answer

Distributed rate limiter ka core: Atomicity. Redis + Lua script se read-modify-write atomic hota hai. Alternatives:

  • Redis INCR + EXPIRE: Simple counter, but boundary burst issue. Sliding window ke liye 2 keys.
  • Local + global hybrid: Har node pe local limit (fast), plus periodic global sync. Approximate but cheap.
  • Central limiter service: Alag service, but ek aur hop = latency. Sirf jab strict global limit chahiye.
  • Fail-open vs fail-closed: Redis down ho toh? Fail-open (allow) = risk, fail-closed (deny) = outage. Usually fail-open with local fallback limit.

🕵️ Real-time Fraud Detection Pipeline

Requirements: Har transaction pe <100ms mein fraud score. Rules + ML combine. Fail-safe (fail hone pe allow karo, block nahi — false positive costly). Auditability.

Transaction ──▶ ┌─────────────┐ │ Ingestion │ └──────┬──────┘ │ ┌───────────────┼───────────────┐ │ │ │ ┌─────▼─────┐ ┌──────▼──────┐ ┌────▼─────┐ │ Rules │ │ ML Model │ │ Feature │ │ Engine │ │ (online) │ │ Store │ └─────┬─────┘ └──────┬──────┘ └────┬─────┘ │ │ │ └───────┬───────┴───────────────┘ │ ┌──────▼──────┐ │ Decision │──▶ ALLOW / REVIEW / BLOCK │ Combiner │ └──────┬──────┘ │ ┌──────▼──────┐ │ Audit Log │ (immutable, hash-chained) └─────────────┘

Components:

  • Rules engine: Velocity checks (10 tx in 1 min), geo anomaly, amount threshold, blacklist. Fast, explainable, easy to update.
  • ML model: Gradient boosted trees / neural net. Features: historical spend, device, merchant category, time-of-day. Sub-50ms inference (ONNX/TensorRT).
  • Feature store: Online (Redis/DynamoDB) for real-time features, offline (S3/warehouse) for training. Consistency critical — same features training aur serving mein.
  • Decision combiner: Rules + ML score → final action. Thresholds tunable per merchant/region.
  • Audit log: Har decision + features + model version + score. Immutable, hash-chained. Regulatory requirement.
🔑 Key Answer

Fraud pipeline ka core: Fail-safe behaviour + auditability.

  • Fail-open: ML service down ho toh rules pe fall back. Rules bhi down ho toh allow with flag for review. Block karna false positive se zyada costly hai.
  • Latency budget: 100ms total. Rules 10ms, features 20ms, ML 50ms, overhead 20ms. Har component ka budget fixed.
  • Explainability: Har decision ke saath top features + rule hits log karo. Regulator aur customer support ke liye.
  • Model versioning: Kaunsa model kis decision pe chala — trace. Rollback easy.
  • Feedback loop: Chargebacks / confirmed fraud → training data. Careful: label delay + class imbalance.

📦 LRU Cache — Line by Line

Design: HashMap<Key, Node> + doubly linked list. Map O(1) lookup, DLL O(1) move-to-front + O(1) tail removal. Dummy head/tail sentinels se null checks khatam.

LRUCache.javaJAVA
class LRUCache {
    class Node { int k, v; Node prev, next;
        Node(int k, int v){ this.k=k; this.v=v; } }

    private final int cap;
    private final Map<Integer,Node> map = new HashMap<>();
    private final Node head = new Node(0,0), tail = new Node(0,0);

    public LRUCache(int capacity){
        this.cap = capacity;
        head.next = tail; tail.prev = head;
    }

    private void addFirst(Node n){
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
    private void remove(Node n){
        n.prev.next = n.next; n.next.prev = n.prev;
    }

    public int get(int key){
        Node n = map.get(key);
        if(n == null) return -1;
        remove(n); addFirst(n);
        return n.v;
    }

    public void put(int key, int value){
        Node n = map.get(key);
        if(n != null){ n.v = value; remove(n); addFirst(n); return; }
        if(map.size() == cap){
            Node lru = tail.prev;
            remove(lru); map.remove(lru.k);
        }
        Node node = new Node(key,value);
        map.put(key,node); addFirst(node);
    }
}
LineExplanation
class Node { int k, v; Node prev, next; }DLL ka node. Key bhi store karte hain — eviction ke waqt map se remove karne ke liye key chahiye. Agar sirf value store kare toh eviction pe map se key nikaalna impossible.
Map<Integer,Node> mapKey → Node reference. O(1) lookup. Node ke andar value + DLL pointers.
head, tail sentinelsDummy nodes. Real head/tail ke null checks khatam. addFirst aur remove mein koi if-null nahi. Clean code.
head.next = tail; tail.prev = head;Constructor mein empty DLL link karo. Ab hamesha valid structure.
addFirst: n.next=head.next; n.prev=head;Naye node ke pointers set karo. Pehle n ke pointers, phir neighbours ke.
head.next.prev=n; head.next=n;Purane first node ka prev update, phir head ka next. Order matter karta hai — warna purana link tod jaata.
remove: n.prev.next=n.next; n.next.prev=n.prev;Node ko DLL se unlink. Sentinels ki wajah se null checks nahi chahiye.
get: map.get(key)O(1) lookup. Null pe -1 return (problem spec).
remove(n); addFirst(n);Move to front — most recently used. Yeh LRU ordering maintain karta hai.
put: existing node checkKey already hai toh value update + move to front. Naya node nahi banate.
if(map.size() == cap)Capacity full. Evict karna padega.
Node lru = tail.prevLRU node = tail ke just pehle. Kyunki addFirst se MRU head ke paas, LRU tail ke paas.
remove(lru); map.remove(lru.k);DLL se hatao + map se hatao. Dono zaroori — warna memory leak.
map.put(key,node); addFirst(node);Naya node map mein + DLL ke front pe.
🔑 Key Answer

Complexity: get O(1) avg, put O(1) avg, eviction O(1). Space O(capacity).

Thread-safety: Yeh single-threaded version hai. Concurrent chahiye toh ConcurrentHashMap + per-node locks (complex), ya segmented LRU (N segments, har segment apna lock), ya Caffeine library (W-TinyLFU, lock-free reads).

🚧 Bounded Blocking Queue — Line by Line

Design: ReentrantLock + 2 Conditions (notFull, notEmpty). Producer-consumer ka classic pattern.

BoundedQueue.javaJAVA
class BoundedQueue<T> {
    private final Object[] buf;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedQueue(int cap){ buf = new Object[cap]; }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (count == buf.length) notFull.await();
            buf[tail] = item;
            tail = (tail + 1) % buf.length;
            count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T item = (T) buf[head];
            buf[head] = null;
            head = (head + 1) % buf.length;
            count--;
            notFull.signal();
            return item;
        } finally { lock.unlock(); }
    }
}
LineExplanation
Object[] bufCircular buffer. Array = O(1) index access. Generic type erasure ki wajah se Object[].
int head, tail, counthead = next take index, tail = next put index, count = current size. Count alag rakhte hain — head==tail ambiguous hai (empty ya full?).
ReentrantLock lockEk lock jo dono conditions ko guard karta hai. Single lock kyun? Kyunki head/tail/count shared state hai — alag locks se race conditions.
Condition notFull, notEmptyDo alag wait queues. Producer notFull pe wait, consumer notEmpty pe. signal() sirf relevant waiters ko uthata hai. Ek hi condition hoti toh thundering herd.
while (count == buf.length) await()While loop, if nahi. Spurious wakeup possible hai. Uthne ke baad dobara check karo. Yeh #1 interview trap hai.
buf[tail] = itemCircular buffer mein write.
tail = (tail + 1) % buf.lengthModulo se wrap-around. O(1), no shifting.
notEmpty.signal()Ek waiting consumer ko uthao. signalAll nahi — wasteful. Ek item daala, ek consumer kaafi hai.
finally { lock.unlock() }Hamesha finally mein unlock. Exception aaye toh bhi lock release. Warna deadlock.
buf[head] = nullNull out karo — warna GC ko reference dikhta rahega, memory leak.
notFull.signal()Ek waiting producer ko uthao — jagah ban gayi.
Common bugs: if instead of while (spurious wakeup), signalAll instead of signal (thundering herd), unlock bhool jaana (deadlock), null out na karna (memory leak).

🪣 Token Bucket Rate Limiter — Line by Line

TokenBucket.javaJAVA
class TokenBucket {
    private final long capacity;
    private final double refillPerSec;
    private double tokens;
    private long lastRefillNanos;

    public TokenBucket(long capacity, double refillPerSec) {
        this.capacity = capacity;
        this.refillPerSec = refillPerSec;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean allow(long n) {
        refill();
        if (tokens >= n) {
            tokens -= n;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        double elapsedSec = (now - lastRefillNanos) / 1_000_000_000.0;
        tokens = Math.min(capacity, tokens + elapsedSec * refillPerSec);
        lastRefillNanos = now;
    }
}
LineExplanation
long capacityMax tokens = max burst size. Bucket isse zyada nahi bhar sakta.
double refillPerSecSustained rate. E.g. 100 QPS = 100 tokens/sec refill.
double tokensCurrent tokens. double kyun, int nahi? Fractional refill ke liye. 10ms mein 0.5 token bhi add ho sakta hai.
long lastRefillNanosLast refill ka timestamp. nanoTime, currentTimeMillis nahi. nanoTime monotonic hai — clock skew se safe.
tokens = capacity (constructor)Bucket full start hota hai — pehla burst allowed.
synchronized allow()Critical section. Read-modify-write tokens — race condition se bachne ke liye. Single node pe synchronized kaafi, distributed mein Redis+Lua.
refill() pehleHar allow() se pehle refill karo. Lazy refill — background thread nahi chahiye.
tokens >= nEnough tokens? Consume karo, warna reject.
elapsedSec = (now - last) / 1e9Nanoseconds → seconds. Double division, precision theek hai.
Math.min(capacity, tokens + ...)Cap at capacity. Warna idle time ke baad bucket overflow ho jaata, unlimited burst allow hota.
lastRefillNanos = nowTimestamp update. Warna next refill double-count karega.
🔑 Key Answer

Token bucket vs Leaky bucket:

  • Token bucket: Bursts allowed (up to capacity). Average rate = refill rate. Most APIs yahi use karte hain.
  • Leaky bucket: Output rate fixed, bursts smooth out. Queue-based. Bursts ke liye buffer chahiye.

Distributed: Redis + Lua script se atomic. Local bucket + periodic global sync = approximate but fast. Strict global = central Redis, latency cost.

🗄️ Generic Repository — Line by Line

Repository.javaJAVA
interface BaseEntity<ID> {
    ID getId();
    void setId(ID id);
}

interface Repository<T extends BaseEntity<ID>, ID extends Serializable> {
    T save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
    void deleteById(ID id);
    Page<T> findAll(Pageable pageable);
}

class Page<T> {
    private final List<T> content;
    private final int page, size;
    private final long totalElements;
    // constructor, getters
    public int totalPages() {
        return (int) Math.ceil((double) totalElements / size);
    }
}

class JpaUserRepository implements Repository<User, Long> {
    private final EntityManager em;
    public JpaUserRepository(EntityManager em){ this.em = em; }

    public User save(User u) {
        if (u.getId() == null) { em.persist(u); return u; }
        return em.merge(u);
    }

    public Optional<User> findById(Long id) {
        return Optional.ofNullable(em.find(User.class, id));
    }

    public List<User> findAll() {
        return em.createQuery("SELECT u FROM User u", User.class)
                 .getResultList();
    }

    public void deleteById(Long id) {
        findById(id).ifPresent(em::remove);
    }

    public Page<User> findAll(Pageable p) {
        List<User> content = em.createQuery("SELECT u FROM User u", User.class)
                .setFirstResult(p.page() * p.size())
                .setMaxResults(p.size())
                .getResultList();
        long total = em.createQuery("SELECT COUNT(u) FROM User u", Long.class)
                       .getSingleResult();
        return new Page<>(content, p.page(), p.size(), total);
    }
}
LineExplanation
BaseEntity<ID>Marker interface. Har entity ka id hona chahiye. Generic repository ko id access chahiye — yeh contract deta hai.
Repository<T extends BaseEntity<ID>, ID extends Serializable>Two type params. T = entity type, ID = id type. extends bounds ensure karte hain ki T mein getId() hai aur ID serializable hai (DB ke liye).
Optional<T> findByIdOptional, null nahi. Null return karne se caller bhool sakta hai. Optional explicit hai — caller ko handle karna padega.
Page<T> findAll(Pageable)Pagination. Pageable = page number + size + sort. Ek object mein sab.
totalPages()Math.ceil se round up. 101 elements, size 10 → 11 pages. Ceil zaroori, warna last page gayab.
save: if id == null persist else mergeInsert vs update. Null id = naya entity = persist. Non-null = existing = merge (update). JPA ka standard pattern.
Optional.ofNullable(em.find(...))em.find null return karta hai missing pe. Optional mein wrap karo.
deleteById: findById().ifPresent(remove)Safe delete. Exist nahi karta toh silently skip. Alternative: exception throw karo — depends on semantics.
setFirstResult / setMaxResultsOffset pagination. page * size = offset. Simple but deep pages slow (OFFSET 1000000 = scan). Cursor pagination better for large datasets.
Separate COUNT queryDo queries. Ek content ke liye, ek total ke liye. Count query alag se optimize kar sakte ho (index-only scan).
Offset pagination ka problem: Page 1,00,000 pe OFFSET 1000000 — DB ko 1M rows scan karke skip karne padte hain. Cursor/keyset pagination better: WHERE id > :lastId ORDER BY id LIMIT 10. Index seek, O(log n).

class OrderBook {
    record Order(long id, BigDecimal price, long qty, long seq) {}

    private final TreeMap<BigDecimal, Deque<Order>> bids =
        new TreeMap<>(Comparator.reverseOrder());
    private final TreeMap<BigDecimal, Deque<Order>> asks =
        new TreeMap<>();
    private final AtomicLong seqGen = new AtomicLong();

    void submit(Order o) {
        Order order = new Order(o.id(), o.price(), o.qty(), seqGen.incrementAndGet());
        if (isBuy(order)) matchBuy(order);
        else matchSell(order);
    }

    private void matchBuy(Order buy) {
        while (buy.qty() > 0 && !asks.isEmpty()) {
            Map.Entry<BigDecimal, Deque<Order>> bestAsk = asks.firstEntry();
            if (bestAsk.getKey().compareTo(buy.price()) > 0) break;
            Deque<Order> q = bestAsk.getValue();
            Order sell = q.peekFirst();
            long fill = Math.min(buy.qty(), sell.qty());
            // trade record, qty reduce, remove filled orders...
        }
        if (buy.qty() > 0) bids.computeIfAbsent(buy.price(), k -> new ArrayDeque<>()).addLast(buy);
    }
}

🔑 Key Answer

Price-time priority: Pehle best price, same price pe earliest order. TreeMap price levels ke liye, Deque per level time priority ke liye.

Real systems: LMAX Disruptor, Aeron — lock-free ring buffers, single-writer principle. Millions of orders/sec.

public TransferResult transfer(String key, String from, String to,

    }

        throw new InsufficientFundsException();
    f.debit(amt);
    t.credit(amt);

@TransactionalPoora method ek DB transaction. Koi bhi exception = full rollback. Idempotency record bhi rollback.

🔑 Key Answer

Exactly-once ka 3-layer defence:

  • Layer 1 — Idempotency key: DB unique constraint se duplicate request block. Same key = same result replay.
  • Layer 2 — Transaction: Debit + credit + ledger + outbox + idempotency complete — sab atomic. Partial state impossible.
  • Layer 3 — Outbox + consumer dedup: Event loss nahi (outbox), double processing nahi (consumer event id check).

Deadlock prevention: Lock ordering (chhota ID pehle). Ya SELECT ... FOR UPDATE ORDER BY id — DB khud order maintain karega.

🔑 10 Golden Rules (Sab Answers Mein Repeat)

🔑 Yaad Rakho
  1. Idempotency key har mutating API pe. Duplicate = replay, not re-execute.
  2. Lock ordering (chhota ID pehle) se deadlock khatam.
  3. Cache-aside + TTL — read scaling ka sasta tareeka.
  4. Outbox pattern — DB write + event publish atomic.
  5. Bounded everything — queue, pool, cache. Backpressure se stability.
  6. Consistent hashing — sharding ka default, smooth rebalance.
  7. Async + queue — latency kam, throughput zyada, retry easy.
  8. Append-only — ledger, audit, events. Immutable = audit-friendly.
  9. Circuit breaker + retry + bulkhead — cascading failure rokо.
  10. CQRS — write normalized, read denormalized. Alag optimize.
