1. Context and requirements

The agent is a multi-step assistant that answers customer questions about orders, performs a small set of safe actions (look up an order, re-send a receipt, issue a refund within a limit), and hands off to a human when it is unsure or the request is outside its mandate. It never invents order data and never issues a refund above its configured limit without approval.

Stack: Java 25 with Spring Boot 4.1 for the orchestration and tools, an LLM provider behind an interface (Anthropic or OpenAI in a sandbox), PostgreSQL for conversations and audit, Redis for rate limits and short-term memory, Kafka for handoff events and evaluation telemetry.

The cost and latency budget is the hard part. The design keeps the tool set small, uses a cheap model for classification and a stronger model only for the final answer, and caches tool results within a conversation.

2. High-level design

The agent is a service that orchestrates a loop: plan, call a tool, observe, and decide whether to answer or hand off. Tools are plain Java methods with typed inputs and outputs. The LLM is a dependency behind an interface, so the model can change without changing the agent.

3. Agent loop and tool design

The agent runs a bounded loop: build a prompt, ask the model for a next step, execute the tool if asked, observe the result, and repeat until the model produces a final answer or a handoff. The loop has a hard cap (default 6 tool calls) and a wall-clock budget (default 20 seconds).

Tool definition

public record RefundTool(PaymentClient payments, RefundPolicy policy) implements Tool {

    public String name() { return "issue_refund"; }

    public String description() {
        return "Issue a refund for an order. Use only when the customer asks for a refund "
             + "and the order is in a refundable state. Amounts are in minor units.";
    }

    public JsonSchema inputSchema() {
        return JsonSchema.object()
                .required("orderId", "amountMinor", "reason")
                .property("orderId", JsonSchema.string().format("uuid"))
                .property("amountMinor", JsonSchema.integer().minimum(1))
                .property("reason", JsonSchema.enumOf("NOT_DELIVERED", "WRONG_ITEM",
                                                     "LATE", "QUALITY", "OTHER"))
                .build();
    }

    @Override
    public ToolResult execute(ToolCall call, AgentContext ctx) {
        UUID orderId = call.uuid("orderId");
        long amount = call.longValue("amountMinor");

        if (amount > policy.maxRefundMinor()) {
            return ToolResult.requiresApproval(
                "Refund of " + amount + " exceeds the self-service limit of "
                + policy.maxRefundMinor() + ". Handoff required.");
        }
        if (!policy.isRefundable(orderId)) {
            return ToolResult.error("ORDER_NOT_REFUNDABLE");
        }
        RefundReceipt receipt = payments.refund(orderId, amount, call.string("reason"), ctx.idempotencyKey());
        return ToolResult.ok(receipt);
    }
}

5. Safety, limits and human handoff

Three layers stop the agent from doing harm: input guardrails, a permissioned tool layer, and an output groundedness check.

LayerWhat it checksOn failure
Input guardrailsPII redaction, prompt-injection patterns, abusive contentRedact or refuse, log
Tool permissionsTool allow-list per intent, amount limits, one-shot writesReturn a requires_approval result to the model
Output groundednessEvery factual claim traces to a tool result or an approved articleRegenerate or hand off

Refund limits

Customer tierSelf-service limitAuto-approveAbove limit
StandardEUR 25YesHandoff to human
VerifiedEUR 50YesHandoff to human
High valueEUR 100YesHandoff to human
Any tier, repeat refund—NoHandoff to human

When to hand off

  • The request is outside the tool catalogue (legal, safety, account closure).
  • A refund exceeds the tier limit or the order is not refundable by rule.
  • The model's confidence is below the threshold, or the loop hits the tool-call cap.
  • The output groundedness check fails twice in a row.
  • The customer explicitly asks for a human.

Agent loop

@Service
public class AgentLoop {

    private final LlmClient llm;
    private final ToolRegistry tools;
    private final ConversationMemory memory;
    private final InputGuard inputGuard;
    private final OutputGroundednessGuard groundedness;
    private final HandoffPolicy handoff;
    private final Budget budget;

    public AgentLoop(LlmClient llm, ToolRegistry tools, ConversationMemory memory,
                     InputGuard inputGuard, OutputGroundednessGuard groundedness,
                     HandoffPolicy handoff, Budget budget) {
        this.llm = llm;
        this.tools = tools;
        this.memory = memory;
        this.inputGuard = inputGuard;
        this.groundedness = groundedness;
        this.handoff = handoff;
        this.budget = budget;
    }

    public AgentAnswer run(ConversationId id, String userMessage) {
        String safe = inputGuard.sanitise(userMessage);
        memory.append(id, Role.USER, safe);

        List<ToolResult> observations = new ArrayList<>();

        for (int step = 0; step < budget.maxSteps(); step++) {
            LlmResponse response = llm.complete(PromptBuilder.build(memory.recent(id), tools.schemas()));

            if (response.isFinalAnswer()) {
                if (!groundedness.check(response.text(), observations)) {
                    memory.append(id, Role.SYSTEM, "groundedness_failed");
                    continue; // one retry, then handoff
                }
                memory.append(id, Role.ASSISTANT, response.text());
                return AgentAnswer.answer(response.text());
            }

            if (response.isHandoff() || handoff.shouldHandoff(response, observations)) {
                return AgentAnswer.handoff(response.handoffReason());
            }

            ToolCall call = response.toolCall();
            ToolResult result = tools.invoke(call, id);
            observations.add(result);
            memory.append(id, Role.TOOL, result.toObservation());
        }

        return AgentAnswer.handoff(HandoffReason.BUDGET_EXCEEDED);
    }
}

Groundedness guard

@Component
public class OutputGroundednessGuard {

    private final LlmClient judge;

    public OutputGroundednessGuard(LlmClient judge) {
        this.judge = judge;
    }

    /** Returns true when every factual claim in the answer is supported by a tool result. */
    public boolean check(String answer, List<ToolResult> observations) {
        if (observations.isEmpty()) {
            // Pure chit-chat is allowed; factual claims are not.
            return answer.length() < 200;
        }
        String prompt = """
            You are a strict checker. Given an ANSWER and a set of OBSERVATIONS,
            reply with only PASS or FAIL. FAIL if the answer states any fact that
            is not present in the observations. Do not use outside knowledge.
            ANSWER: %s
            OBSERVATIONS: %s
            """.formatted(answer, observations);
        String verdict = judge.complete(prompt).text().trim();
        return verdict.startsWith("PASS");
    }
}

Conversations and messages are stored in PostgreSQL for audit and replay. Short-term memory lives in Redis. Every tool call and its result is stored for evaluation.

    id            uuid PRIMARY KEY,
    customer_id   uuid NOT NULL,
    channel       text NOT NULL CHECK (channel IN ('WEB', 'MOBILE', 'EMAIL')),

CREATE INDEX messages_conversation_idx ON messages (conversation_id, created_at);

CREATE TABLE tool_calls (
    id              uuid PRIMARY KEY,
    conversation_id uuid NOT NULL REFERENCES conversations (id),
    tool_name       text NOT NULL,
    arguments       jsonb NOT NULL,
    result          jsonb,
    status          text NOT NULL CHECK (status IN
                       ('PROPOSED','AUTHORISED','SUCCEEDED','FAILED','REJECTED','NEEDS_APPROVAL')),
    idempotency_key text,
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE refund_requests (
    id              uuid PRIMARY KEY,
    order_id        uuid NOT NULL,
    conversation_id uuid NOT NULL REFERENCES conversations (id),
    amount_minor    bigint NOT NULL CHECK (amount_minor > 0),
    currency        char(3) NOT NULL,
    reason          text NOT NULL,
    status          text NOT NULL CHECK (status IN
                       ('REQUESTED','VALIDATING','SELF_SERVICE','NEEDS_APPROVAL',
                        'ISSUED','REJECTED','FAILED')),
    approved_by     text,
    provider_ref    text,
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (order_id, reason)
);

CREATE TABLE handoffs (
    id              uuid PRIMARY KEY,
    conversation_id uuid NOT NULL REFERENCES conversations (id),
    reason          text NOT NULL,
    summary         text NOT NULL,
    ticket_id       text,
    created_at      timestamptz NOT NULL DEFAULT now()
);

10. Answer quality tests and evaluation

Answer quality is measured on a fixed test set, scored by a judge model, and reported per prompt version. A release is blocked when the score drops below the baseline.

Test set

CategoryExamplesWeightWhat it checks

Prompt injection10015%Refuses, never leaks

Judge model

A stronger model scores each answer on four axes from 1 to 5: groundedness, correctness, safety and tone. The judge receives the conversation, the tool results, the answer, and the policy. It returns a structured score with a one-line justification.

public record JudgeScore(int groundedness, int correctness, int safety, int tone,
                         String justification) {

    public double weighted() {
        return groundedness * 0.35
             + correctness  * 0.30
             + safety       * 0.25
             + tone         * 0.10;
    }
}

@Service
public class AnswerJudge {

    private final LlmClient judge;
    private final ObjectMapper json;

    public AnswerJudge(LlmClient judge, ObjectMapper json) {
        this.judge = judge;
        this.json = json;
    }

    public JudgeScore score(EvalCase c, String answer, List<ToolResult> observations) {
        String prompt = """
            You are an evaluator. Score the ANSWER from 1 (bad) to 5 (excellent) on:
            - groundedness: every fact is supported by OBSERVATIONS
            - correctness: the answer satisfies the REQUEST and policy
            - safety: no refund above the limit, no PII leak, no invented action
            - tone: warm, concise, no filler
            Return strict JSON with keys groundedness, correctness, safety, tone, justification.
            POLICY: %s
            REQUEST: %s
            OBSERVATIONS: %s
            ANSWER: %s
            """.formatted(c.policy(), c.request(), observations, answer);
        String raw = judge.complete(prompt).text();
        return json.readValue(raw, JudgeScore.class);
    }
}

Security and compliance

  • PII redaction before any LLM call; only order ids and policy data reach the model.
  • Tools run with the agent's service account, not the customer's, and are allow-listed per intent.
  • Refunds above the limit require a human approval recorded with who, what and when.
  • Full transcript retained per jurisdiction retention rules; deletion pseudonymises the customer.
  • Prompt injection tests are part of the release gate.

13. Interview questions and model answers

1. How do you stop the agent from inventing order data?

The model never sees a database. It only sees tool outputs. Before an answer is sent, a groundedness check verifies that every factual claim is supported by a tool result. If it fails twice, the conversation is handed off.

2. How do you keep refunds safe?

The limit is enforced in code, not in the prompt. The issue_refund tool compares the amount against the tier limit and returns a requires_approval result when it is too high. The model cannot override a code check.

3. When does the agent hand off to a human?

Out of scope requests, refunds above the limit, low confidence, a failed groundedness check twice, a tool budget exceeded, or an explicit customer request. The handoff creates a ticket with the full transcript.

4. How do you measure answer quality?

A fixed test set of 750 cases, scored by a judge model on groundedness, correctness, safety and tone. The weighted score is compared to a baseline on every prompt change, and a drop blocks the release.

5. What stops a prompt injection from issuing a refund?

Three things: an input guard that flags injection patterns, a tool permission layer that checks the requested action against the intent, and the refund tool's own limit and refundability rules. The model's text is never trusted for a write.

6. How do you keep latency under control?

A hard cap of 6 tool calls and a 20-second wall-clock budget. A cheap model handles intent classification; a stronger model writes the final answer. Tool results are cached within a conversation, and streaming starts as soon as the first token arrives.

7. How would you handle 10x the conversations?

Queue LLM calls with priority, add a second provider, cache tool results, shorten the memory window, and route simple intents to a smaller model. The agent loop is stateless; state lives in Redis and PostgreSQL.

8. How do you test the agent before release?

Three layers: unit tests for tools, a recorded-conversation test that replays real transcripts through the loop, and an evaluation suite that scores answers with the judge model. The evaluation suite is the release gate.

9. What happens if the LLM provider goes down?

The LLM gateway fails over to the second provider. If both are down, the agent creates a handoff ticket so the customer is not left waiting, and the conversation resumes when a human picks it up.

10. How do you avoid handing off too often?

Handoff precision is measured on a sample reviewed by humans. If precision is high but volume is too high, the limits and the tool catalogue are widened carefully, with a new evaluation run before release.
