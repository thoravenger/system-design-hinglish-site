Startup: app khada kaise hota hai

Request aane se pehle Spring teen kaam kar chuka hota hai — context bana, beans bane aur proxy lag gaye, aur Tomcat port pe baith gaya. Ye teen cheezein samajh lo toh request-time ka 70% khud clear ho jaata hai.

@Component
public class SlowQueryLoggingBeanPostProcessor implements BeanPostProcessor {

  private static final long SLOW_THRESHOLD_MS = 200;

  @Override
  public Object postProcessAfterInitialization(Object bean, String beanName) {
    if (!isJpaRepository(bean)) return bean;

    return Proxy.newProxyInstance(
        bean.getClass().getClassLoader(),
        bean.getClass().getInterfaces(),
        (proxy, method, args) -> invokeAndLogIfSlow(bean, beanName, method, args));
  }

  private Object invokeAndLogIfSlow(Object target, String beanName,
                                     Method method, Object[] args) throws Throwable {
    long startNanos = System.nanoTime();
    try {
      return method.invoke(target, args);
    } finally {
      long elapsedMs = (System.nanoTime() - startNanos) / 1_000_000;
      if (elapsedMs > SLOW_THRESHOLD_MS) {
        log.warn("slow-repo bean={} method={} tookMs={}", beanName, method.getName(), elapsedMs);
      }
    }
  }

  private boolean isJpaRepository(Object bean) {
    return bean instanceof Repository<?, ?>;
  }
}

Gotcha — @EnableWebMvc Boot mein lagbhag hamesha galti hai

@EnableWebMvc lagate hi WebMvcAutoConfiguration band ho jaata hai (uspe @ConditionalOnMissingBean(WebMvcConfigurationSupport.class) laga hai). Matlab Boot ke saare defaults chale gaye — static resource handling, message converters ki configuration, error handling, content negotiation.

Tradeoff — starter banayein ya sirf @Configuration?

Ignore karo single application ke andar. Wahan plain @Configuration zyada readable hai — koi condition magic nahi, jo likha hai wahi chalega. Auto-config ka poora point redistribution hai, organisation nahi.

STAGE 04 · PROBLEM

Request ko thread milta kahan se hai? http-nio-8080-exec-7 kaun banata hai?

"200 concurrent users aaye toh kya hoga?" — is sawaal ka jawaab Spring mein nahi, Tomcat ke connector mein hai.

Tomcat NIO connector mein teen alag role hote hain. Ek hi thread sab kuch nahi karta — yahi NIO ka poora point hai.

Production maths — ye number samjho

max-connections: 8192 matlab 8192 log connected ho sakte hain. threads.max: 200 matlab sirf 200 ek saath kaam karwa sakte hain. Baaki 7992 Poller pe park hain — free.

Agar har request 500 ms DB pe blocked hai → throughput = 200 / 0.5s = 400 req/sec. Bas. CPU idle padi rahegi. Isliye slow downstream call pe thread block karna sabse mehnga mistake hai.

Tradeoff — thread pool badhayein ya async karein?

threads.max badhao tab jab kaam I/O-bound ho aur thread stack memory affordable ho (~1 MB/thread → 800 threads ≈ 800 MB). Simple, zero code change. 500–800 tak theek hai.

Virtual threads on karo (spring.threads.virtual.enabled=true, Boot 3.2+, Java 21+) agar blocking I/O hi bottleneck hai. Code same rehta hai, blocking sasta ho jaata hai. Par dhyaan do: synchronized block carrier thread pin kar deta hai, aur thread-pool-based rate limiting ka natural backpressure khatam ho jaata hai.

WebFlux pe mat jao sirf throughput ke liye — poora stack reactive karna padega (driver, security, tracing sab). Ignore karo jab tak aap 10k+ concurrent connections ya streaming na kar rahe ho.

Filter · correlation id + MDC, OncePerRequestFilter se
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

  private static final String HEADER = "X-Correlation-Id";
  private static final String MDC_KEY = "correlationId";

  @Override
  protected void doFilterInternal(HttpServletRequest request,
                                  HttpServletResponse response,
                                  FilterChain chain) throws ServletException, IOException {
    String correlationId = resolveOrGenerateCorrelationId(request);
    MDC.put(MDC_KEY, correlationId);
    response.setHeader(HEADER, correlationId);
    try {
      chain.doFilter(request, response);   // ★ isse aage ka POORA stack andar hai
    } finally {
      MDC.remove(MDC_KEY);   // ★ ThreadLocal saaf karo — thread pool mein reuse hoga
    }
  }

  private String resolveOrGenerateCorrelationId(HttpServletRequest request) {
    String incoming = request.getHeader(HEADER);
    return StringUtils.hasText(incoming) ? incoming : UUID.randomUUID().toString();
  }
}

protected HandlerMethod lookupHandlerMethod(String lookupPath, HttpServletRequest request) {
  List<Match> matches = new ArrayList<>();
  List<RequestMappingInfo> direct = this.mappingRegistry.getMappingsByDirectPath(lookupPath); // O(1) hash hit
  if (direct != null) addMatchingMappings(direct, matches, request);
  if (matches.isEmpty()) addMatchingMappings(allMappings, matches, request); // {id} wale patterns

  if (matches.isEmpty()) return handleNoMatch(...);   // → 404
  matches.sort(comparator);                              // sabse specific pehle
  if (matches.size() > 1 && comparator.compare(m0, m1) == 0) {
    throw new IllegalStateException("Ambiguous handler methods mapped for '" + lookupPath + "'");
  }
  return matches.get(0).getHandlerMethod();
}
Matching kis order mein hoti hai

Ek RequestMappingInfo mein 7 condition hote hain aur sab match hone chahiye: path → method (GET/POST) → params → headers → consumes (Content-Type) → produces (Accept) → custom.

Isiliye galat Content-Type pe 415 milta hai aur galat Accept pe 406 — 404 nahi. Path toh match ho gaya tha, condition fail hui.

Version gotcha — path matching Spring 5.3 mein badla

AntPathMatcher → PathPatternParser (Boot 2.6 se default). Ab /api/users aur /api/users/ alag hain, aur ** sirf pattern ke end mein aa sakta hai. Purana behaviour: spring.mvc.pathmatch.matching-strategy=ant_path_matcher (Boot 3.x mein deprecated, 4.x mein hata diya gaya).

  HandlerExecutionChain mappedHandler = null;
  boolean multipartRequestParsed = false;
  Exception dispatchException = null;
  ModelAndView mv = null;

  try {
    // ── 1. multipart? request ko MultipartHttpServletRequest se wrap karo
    processedRequest = checkMultipart(request);
    multipartRequestParsed = (processedRequest != request);

    // ── 2. handler dhoondo → controller + uske interceptors ka bundle
    mappedHandler = getHandler(processedRequest);
    if (mappedHandler == null) { noHandlerFound(...); return; }   // → 404

    // ── 3. is handler ko chala sakne wala adapter dhoondo
    HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());

    // ── 4. PRE-HANDLE : forward order mein 1,2,3...
    if (!mappedHandler.applyPreHandle(processedRequest, response)) {
      return;   // ★ koi false bola → handler NAHI chalega. Lekin usse pehle wale
    }           //   interceptors ka afterCompletion ANDAR hi trigger ho chuka hai.

    // ── 5. ★ CONTROLLER YAHAN CHALTA HAI (args resolve + reflection invoke + return handle)
    mv = ha.handle(processedRequest, response, mappedHandler.getHandler());

    // ── 6. async shuru ho gaya? toh abhi kuch mat karo, thread chhod do
    if (asyncManager.isConcurrentHandlingStarted()) {
      return;   // ★ postHandle SKIP. Baad mein dobara dispatch hoga.
    }

    applyDefaultViewName(processedRequest, mv);

    // ── 7. POST-HANDLE : REVERSE order mein 3,2,1
    mappedHandler.applyPostHandle(processedRequest, response, mv);
  }
  catch (Exception ex)  { dispatchException = ex; }
  catch (Throwable err) { dispatchException = new NestedServletException("Handler failed", err); }

  // ── 8. view render YA exception resolve — dono yahin
  processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
  //      ↑ iske andar: HandlerExceptionResolverComposite → ViewResolver → view.render()
  //        aur end mein mappedHandler.triggerAfterCompletion(...)

  finally {
    if (asyncManager.isConcurrentHandlingStarted()) {
      mappedHandler.applyAfterConcurrentHandlingStarted(...);
    } else if (multipartRequestParsed) {
      cleanupMultipart(processedRequest);   // temp files delete
    }
  }
}

  @ExceptionHandler(SkuNotFoundException.class)
  public ProblemDetail handleSkuNotFound(SkuNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    problem.setTitle("SKU not found");
    problem.setType(URI.create("https://api.acme.com/errors/sku-not-found"));
    problem.setProperty("sku", ex.getSku());
    problem.setProperty("correlationId", MDC.get("correlationId"));
    return problem;
  }

  // @Valid failure ko readable banao
  @Override
  protected ResponseEntity<Object> handleMethodArgumentNotValid(
      MethodArgumentNotValidException ex, HttpHeaders headers,
      HttpStatusCode status, WebRequest request) {

    ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
    problem.setTitle("Validation failed");
    problem.setProperty("fieldErrors", toFieldErrorMap(ex));
    return ResponseEntity.badRequest().body(problem);
  }

  private Map<String, String> toFieldErrorMap(MethodArgumentNotValidException ex) {
    return ex.getBindingResult().getFieldErrors().stream()
        .collect(Collectors.toMap(FieldError::getField,
                                  fe -> Objects.requireNonNullElse(fe.getDefaultMessage(), "invalid"),
                                  (a, b) -> a));
  }
}

Architecture-level calls

MVC vs WebFlux

MVC chuno — default. Debuggable stack traces, blocking JDBC, har library compatible, poori team samajhti hai. Virtual threads ne iski scalability ka gap lagbhag khatam kar diya hai.

WebFlux tabhi — 10k+ concurrent connections, SSE/streaming, ya poora stack already reactive (R2DBC + reactive Redis + reactive security). Ek bhi blocking call event loop pe poora app gira degi.

Auto-config vs explicit @Configuration

Auto-config — shared library, 3+ consumer teams, zero-config chahiye. Cost: conditions test karne padte hain, debugging gehri.

Explicit — single app ke andar hamesha. "Jo likha hai wahi chalega" > "pata nahi kya load hua".

Field vs constructor injection

Constructor — hamesha. final fields, immutable, new se test ho jaata hai, circular dependency compile/startup pe pakdi jaati hai.

Field injection ignore karo — chhupi hui dependencies, test mein reflection chahiye, aur circular dependency chup chaap pass ho jaati hai (Boot 2.6 se wo bhi by default fail hoti hai).

Thread pool vs virtual threads

Platform threads — jab load predictable ho aur pool size hi aapka backpressure ho. Simple, proven.

Virtual threads — I/O-heavy, high concurrency, Java 21+. Pehle audit karo: synchronized blocks, ThreadLocal-heavy libraries, aur pool-based rate limiting — teeno assumption tootengi.

Ek meta-rule — interview mein ye bolo

"Main default simplest option chunta hoon, aur complexity tabhi add karta hoon jab measured problem ho. Har abstraction ka ek debugging cost hota hai jo naya joining dev pay karta hai — isliye magic tabhi justified hai jab wo repetition ko meaningfully khatam kare, sirf clever dikhne ke liye nahi."

Ye line har tradeoff question ka safe aur honest jawaab hai.

// mock interview

26 questions — pehle khud socho, phir kholo

Har jawaab wahi hai jo ek interviewer sunna chahta hai: pehle ek line ka direct answer, phir uske peeche ka mechanism. Tap karke expand karo.

basic · 0–2 yrs core · 3–6 yrs deep · 7+ yrs
Q1basic@SpringBootApplication ke andar kya hai?+

Teen annotations ka meta-annotation: @SpringBootConfiguration (khud @Configuration hai), @ComponentScan (current package aur usse neeche scan), aur @EnableAutoConfiguration.

Teesra sabse important — wo @Import(AutoConfigurationImportSelector.class) karta hai jo AutoConfiguration.imports file padh ke conditional beans register karta hai.

Follow-up jo aayega: "Main class ko root package mein kyun rakhte hain?" — kyunki @ComponentScan ka base package wahi hai. Bahar rakh doge toh aapke beans scan hi nahi honge.

Q2basicEmbedded server ka fayda kya hai? WAR se kya farak?+

App khud apna server leke chalti hai — java -jar app.jar bas. Server ka version aapke build mein pinned hai, "mere laptop pe Tomcat 8 tha" wala problem khatam.

Fat jar ki structure: BOOT-INF/classes + BOOT-INF/lib + org/springframework/boot/loader. JarLauncher ek custom classloader banata hai jo nested jars padh sakta hai — normal Java ye nahi kar sakta.

Kab WAR chahiye: jab existing corporate app server (WebLogic/WebSphere) mandatory ho. Tab SpringBootServletInitializer extend karo.

Q3basicFilter aur Interceptor mein difference?+

Ek line: Filter Servlet spec ka hai aur DispatcherServlet ke bahar chalta hai; Interceptor Spring MVC ka hai aur andar chalta hai — isliye usse HandlerMethod pata hota hai.

Practical difference: Filter request/response ko wrap kar sakta hai (body cache, compression) — Interceptor nahi. Interceptor controller ki annotations padh sakta hai — Filter nahi.

Filter ke teen callbacks nahi hote, ek doFilter hai jisme aap chain.doFilter() ke around code likhte ho. Interceptor ke teen hooks hain: preHandle, postHandle, afterCompletion.

Q4coredoDispatch() mein exact sequence batao+

checkMultipart → getHandler (HandlerExecutionChain) → getHandlerAdapter → applyPreHandle (forward order) → ha.handle() (args resolve + invoke + return value handle) → async check → applyDefaultViewName → applyPostHandle (reverse order) → processDispatchResult (exception resolve ya view render) → triggerAfterCompletion (reverse) → finally cleanupMultipart.

Do jagah log phaste hain: postHandle reverse order mein chalta hai, aur async start hone pe postHandle bilkul skip ho jaata hai.

Q5corepreHandle false return kare toh afterCompletion chalega?+

Jis interceptor ne false bola, uska afterCompletion nahi chalega. Lekin usse pehle wale jitne interceptors successfully pass ho chuke the, un sabka chalega.

Mechanism: HandlerExecutionChain ek interceptorIndex rakhta hai. preHandle loop mein har success pe index badhta hai. False milte hi triggerAfterCompletion() call hota hai jo interceptorIndex se ulta 0 tak jaata hai — matlab current wala included nahi.

Logic: "tumne khud rok diya, toh cleanup bhi tum khud kar lo".

Q6coreSame class mein @Transactional method call kiya, kaam nahi kiya. Kyun?+

Self-invocation. Spring AOP proxy-based hai — annotation ka effect tabhi hota hai jab call proxy se hoke jaaye. this.method() raw object pe seedha jaata hai, proxy bypass ho jaata hai.

Fix (priority order): 1) method ko alag bean mein nikalo — sabse saaf. 2) @Lazy self-injection. 3) TransactionTemplate programmatically. 4) AopContext.currentProxy() — kaam karta hai par exposeProxy=true chahiye aur code gandha hota hai.

Follow-up: "AspectJ load-time weaving se kaam karega?" — Haan, kyunki wahan bytecode modify hota hai, proxy nahi banta. Par setup cost zyada hai, 99% projects mein justified nahi.

Q7coreCircular dependency Spring kaise solve karta hai?+

Three-level cache se, aur sirf setter/field injection ke liye:

singletonObjects (L1 — poore bane beans) · earlySingletonObjects (L2 — adhoore, exposed) · singletonFactories (L3 — ObjectFactory jo zaroorat padne pe early reference deta hai).

A bana → L3 mein factory daali → A ko B chahiye → B bana → B ko A chahiye → L3 se A ka adhoora reference mila → B poora hua → A poora hua. L3 isliye chahiye kyunki agar A pe proxy lagna hai toh early reference bhi proxy hona chahiye — factory wo decide karti hai.

Constructor injection mein solve nahi hota — object bina dependency ke exist hi nahi kar sakta. Aur Boot 2.6 se circular references by default fail karti hain. Ye feature nahi, warning hai — fix design karo, flag mat lagao.

Q8coreBeanFactoryPostProcessor vs BeanPostProcessor+

BFPP — BeanDefinition (recipe) badalta hai, object banne se pehle. refresh() step 5. Example: ConfigurationClassPostProcessor, placeholder resolver.

BPP — bana hua object badalta/wrap karta hai. Har bean ke init ke around chalta hai. Example: AutowiredAnnotationBeanPostProcessor, AnnotationAwareAspectJAutoProxyCreator (AOP proxy), CommonAnnotationBeanPostProcessor (@PostConstruct).

Memory trick: BFPP = blueprint edit karta hai. BPP = bana hua ghar repaint karta hai.

Q9coreBean scopes kaunse hain? Singleton mein prototype inject karo toh?+

singleton (default), prototype, aur web scopes: request, session, application, websocket.

Trap: singleton mein prototype inject karoge toh wo sirf ek baar inject hoga — singleton khud ek hi baar banta hai. Har call pe naya chahiye toh: ObjectProvider<T> (modern, best), @Lookup method, ya @Scope(proxyMode = TARGET_CLASS).

ObjectProvider isliye best hai kyunki wo optional aur multiple beans bhi handle karta hai, aur test mein mock karna trivial hai.

Q10coreAuto-configuration ne mera bean override kyun nahi kiya?+

Kiya hi nahi jaana chahiye — aapka bean hamesha jeetega. Wajah: AutoConfigurationImportSelector ek DeferredImportSelector hai, jo aapke saare @Configuration parse hone ke baad chalta hai. Tab tak aapka bean registered hai, isliye @ConditionalOnMissingBean false ho jaata hai.

Agar ulta ho raha hai (aapka bean nahi ban raha), toh check karo: bean same type ka hai? Component scan range mein hai? --debug chalao aur negative matches padho.

Force override: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) ya spring.autoconfigure.exclude property.

Q11core@RequestBody se JSON POJO kaise ban jaata hai?+

RequestResponseBodyMethodProcessor (ek HandlerMethodArgumentResolver) Content-Type dekhta hai, matching HttpMessageConverter chunta hai — JSON ke liye MappingJackson2HttpMessageConverter — aur Jackson ka ObjectMapper.readValue() chalta hai.

Important side-effect: yahin request input stream consume ho jaata hai. Isiliye aage koi bhi body dobara nahi padh sakta, aur filter mein body log karne ke liye ContentCachingRequestWrapper chahiye.

ObjectMapper customize karne ka sahi tareeka: Jackson2ObjectMapperBuilderCustomizer bean — ObjectMapper ko poora replace mat karo, warna Boot ki saari default settings chali jaayengi.

Q12core@ControllerAdvice filter ki exception kyun nahi pakadta?+

Kyunki filter DispatcherServlet ke bahar hai. @ControllerAdvice ExceptionHandlerExceptionResolver ke through kaam karta hai, jo processDispatchResult() ke andar call hota hai — matlab DispatcherServlet ke andar.

Filter ki exception seedha Tomcat tak jaati hai → container /error pe naya dispatch karta hai → BasicErrorController default response deta hai.

Fix options: filter mein khud try/catch karke JSON likho; Spring Security ke liye AuthenticationEntryPoint/AccessDeniedHandler; ya ErrorController override karke /error customize karo.

Q13coresave() call kiya — SQL turant chala?+

Nahi (zyadatar). save() entity ko persistence context mein daalta hai. SQL flush pe generate hota hai, jo commit se just pehle hota hai.

Exception: IDENTITY generation strategy mein Hibernate ko ID chahiye hoti hai, isliye INSERT turant chal jaata hai — aur isi wajah se JDBC batching kaam nahi karti. High-volume inserts ke liye SEQUENCE + allocationSize use karo.

Update ke liye save() zaroori nahi — managed entity pe setter kaafi hai, dirty checking flush pe UPDATE bana degi.

Q14coreTransaction propagation types samjhao — REQUIRED vs REQUIRES_NEW+

REQUIRED (default) — tx chal rahi hai toh usi mein join karo, warna nayi banao. Matlab inner method ki exception poori outer tx rollback kar degi.

REQUIRES_NEW — outer tx suspend karo, nayi banao, commit karo, phir outer resume. Do alag connections use hote hain. Audit log ke liye perfect — main operation fail ho toh bhi log bacha rahe.

Deadlock warning: REQUIRES_NEW ke andar wahi row lock karne ki koshish ki jo outer ne lock kar rakhi hai → guaranteed deadlock, kyunki dono alag connection hain.

Baaki: SUPPORTS, NOT_SUPPORTED (suspend karke bina tx chalao), MANDATORY (tx nahi hai toh exception), NEVER, NESTED (savepoint — sirf JDBC, JPA mein reliable nahi).

Q15coreChecked exception pe rollback kyun nahi hota?+

Spring ki default rule: rollback sirf RuntimeException aur Error pe. Checked exception ko Spring "expected business outcome" maanta hai — aapne declare kiya hai, matlab aap handle kar rahe ho.

Fix: @Transactional(rollbackFor = Exception.class).

Bada trap: agar aapne khud try/catch mein exception nigal li, toh rollbackFor bhi bekar hai — Spring ko exception dikhi hi nahi. Tab TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() manually call karo.

Q16coreTomcat thread pool kaise kaam karta hai? 200 threads, 1000 users?+

Teen roles: Acceptor (socket accept), Poller (selector pe hazaron idle connections hold), Worker pool (asli kaam, http-nio-8080-exec-N).

1000 users aaye: sab connect ho jaayenge (max-connections 8192 tak), par sirf 200 ek saath process honge. 201st request accept-count queue mein wait karegi. Queue bhar gayi toh connection refuse.

Math: har request 500ms → 200/0.5 = 400 req/s ceiling. Latency badhi toh throughput proportionally girega. Isiliye p99 latency aur throughput ek hi cheez ke do naap hain.

Q17coreThreadLocal thread pool mein kyun khatarnak hai?+

Threads reuse hote hain. Agar aapne MDC/SecurityContext/tenant set kiya aur clear nahi kiya, toh agla request — jo kisi aur user ka ho sakta hai — wahi value dekhega.

Ye sirf memory leak nahi, data leakage bug hai. Real production incident pattern: user A ka tenant id user B ke response mein.

Rule: har ThreadLocal.set() ke saath ek finally { remove(); }. Spring apne saare context holders ke liye ye khud karta hai — aapko sirf apne wale sambhalne hain. @Async ke saath ho toh TaskDecorator use karo context propagate karne ke liye (Boot 4.1 mein ye built-in ho gaya hai).

Q18deepApna Spring Boot starter kaise banayein?+

Do modules: acme-x-spring-boot-autoconfigure (logic) aur acme-x-spring-boot-starter (sirf dependencies, koi code nahi). Naming convention important hai — spring-boot-starter-x Spring ke apne starters ke liye reserved hai.

Steps: 1) @AutoConfiguration class + @ConditionalOnClass/@ConditionalOnProperty 2) har bean pe @ConditionalOnMissingBean (user override kar sake) 3) @ConfigurationProperties typed config ke liye 4) class name META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports mein 5) spring-boot-configuration-processor add karo — IDE mein autocomplete milega.

Test: ApplicationContextRunner — har condition ka positive aur negative case. Ye starter ka sabse important test hai.

Q19deepGraceful shutdown internally kya karta hai?+

server.shutdown=graceful pe SIGTERM aane par: 1) connector naye connections accept karna band kar deta hai 2) chal rahi requests ko spring.lifecycle.timeout-per-shutdown-phase (default 30s) tak complete hone ka time milta hai 3) phir SmartLifecycle.stop() phases reverse order mein 4) @PreDestroy → DisposableBean.destroy() 5) connection pools band.

Kubernetes ke saath: readiness probe ko shutdown se pehle fail hona chahiye, warna load balancer naye requests bhejta rahega. Isliye preStop hook mein 5–10 second sleep daalo — LB ko endpoint hatane ka time mil jaata hai. Ye sabse common "deploy pe 502" ka fix hai.

Q20deep@Async method ki exception kahan jaati hai?+

Return type pe depend karta hai. void return → exception chup chaap gayab ho jaati hai (default SimpleAsyncUncaughtExceptionHandler sirf log karta hai). CompletableFuture/Future return → exception future ke andar wrap ho jaati hai, get() pe milegi.

Custom handling: AsyncConfigurer implement karke getAsyncUncaughtExceptionHandler() override karo.

Do aur gotchas: @Async + @Transactional ek hi method pe — naya thread, naya tx context, outer tx se koi relation nahi. Aur @Async bhi proxy-based hai — self-invocation pe silently synchronous chal jaayega.

Q21deepVirtual threads on karne se pehle kya check karoge?+

Teen cheezein:

1. synchronized blocks jo I/O ke around hain — wo carrier thread ko pin kar dete hain, poora fayda khatam. ReentrantLock se replace karo. (Java 24+ mein ye kaafi improve hua hai, par legacy libraries ab bhi issue hain.)

2. ThreadLocal-heavy code — ab har request pe naya virtual thread hai, toh pooling assumptions toot jaayengi. Memory usage pattern badlega.

3. Backpressure — pehle thread pool hi aapka natural rate limiter tha. Virtual threads unbounded hain — matlab 50,000 concurrent requests aapke DB pool pe seedha gir sakti hain. Explicit semaphore/bulkhead lagana zaroori hai.

Flag: spring.threads.virtual.enabled=true, Boot 3.2+, Java 21+. Pin detect karne ke liye: -Djdk.tracePinnedThreads=full.

Q22deepBoot 2.7 se 3.x migration mein kya-kya todega?+

1. javax.* → jakarta.* — sabse bada. Har servlet, validation, persistence import. OpenRewrite se automate karo.

2. Java 17 minimum — build toolchain, aur reflection-heavy libraries check karo.

3. spring.factories se auto-config band — custom starters ki registration file badalni padegi.

4. Spring Security 6 — WebSecurityConfigurerAdapter gone, antMatchers() → requestMatchers(), lambda DSL mandatory.

5. Third-party libs — jo bhi javax.servlet pe depend karti hai, uska Jakarta-compatible version chahiye. Ye aksar blocker hota hai.

Strategy: pehle 2.7 pe jao aur saare deprecation warnings zero karo. 3.0 pe jaate waqt sirf jakarta + Java 17 karo, aur kuch nahi. Ek PR, ek concern.

Q23deepBoot 4.0 ka modularization kya tod sakta hai?+

Ek spring-boot-autoconfigure jar ~70 modules mein split ho gaya. Consequence: jo feature pehle "free" mein aa jaati thi, ab uska apna starter chahiye. Classic symptom — H2 console ya koi auto-config upgrade ke baad chupchap band.

Package names bhi badle: org.springframework.boot.autoconfigure.amqp → org.springframework.boot.amqp.autoconfigure. Custom auto-config jo Boot ki internal classes reference karti hai, wo compile fail hogi.

Do-step strategy: pehle spring-boot-starter-classic + spring-boot-starter-test-classic daal ke app chalao (sab available ho jaayega). Phir broken imports fix karo, phir classic hatao aur specific starters add karo. OpenRewrite recipe: ...boot4.MigrateToModularStarters.

Saath mein: Jackson 3.x API change, JSpecify nullability se compile errors (Kotlin mein zyada).

Q24deepFilter mein request body do baar kaise padhein?+

ServletInputStream ek baar hi padha ja sakta hai. Solution: ContentCachingRequestWrapper se request wrap karo — wo bytes internally buffer karta hai.

public class RequestBodyLoggingFilter extends OncePerRequestFilter {
  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                  FilterChain chain) throws IOException, ServletException {
    ContentCachingRequestWrapper cachedRequest = new ContentCachingRequestWrapper(req);
    ContentCachingResponseWrapper cachedResponse = new ContentCachingResponseWrapper(res);
    try {
      chain.doFilter(cachedRequest, cachedResponse);
    } finally {
      logPayloads(cachedRequest, cachedResponse);
      cachedResponse.copyBodyToResponse();  // ★ bhoole toh client ko EMPTY body milegi
    }
  }
}

Do warnings: (1) ContentCachingRequestWrapper body tabhi cache karta hai jab wo actually padhi jaaye — isliye getContentAsByteArray() hamesha chain.doFilter() ke baad call karo. (2) Poora body memory mein aata hai — large uploads pe size limit lagao warna OOM.

Q25deepEk endpoint slow ho gaya. Kaise debug karoge?+

Layer by layer, upar se neeche — ye structure interviewer ko impress karta hai:

1. Confirm karo kahan slow hai — Actuator /actuator/metrics/http.server.requests se p50/p95/p99 dekho. Average jhooth bolta hai.

2. Thread pool saturated hai? — tomcat.threads.busy vs tomcat.threads.config.max. Agar busy ≈ max, toh problem is endpoint mein nahi, kisi aur endpoint mein hai jo threads kha raha hai.

3. Connection pool? — hikaricp.connections.pending aur ...acquire timer. Pending > 0 matlab threads DB connection ka wait kar rahe hain.

4. SQL? — N+1 query sabse common. spring.jpa.properties.hibernate.generate_statistics=true ya Hypersistence/datasource-proxy se query count. Fix: @EntityGraph ya JOIN FETCH.

5. Thread dump — jcmd <pid> Thread.print. Saare http-nio-*-exec-* threads ek hi line pe blocked dikhenge — wahi aapka culprit hai.

6. Distributed? — Micrometer Tracing se span breakdown, dekho kaunsi downstream call kha rahi hai.

Q26deepSpring Boot app ki startup slow hai. Kya karoge?+

Measure pehle: -Ddebug se condition report, aur ApplicationStartup API (BufferingApplicationStartup) + /actuator/startup — har step ka exact time.

Common wins:

1. Component scan narrow karo — @ComponentScan ka base package specific ho, poora com.company nahi.
2. Unused auto-config exclude karo — condition report se dekho kya load ho raha hai jo chahiye hi nahi.
3. Lazy initialization — spring.main.lazy-initialization=true. Dev mein acchi, prod mein risky — first request slow hogi aur config errors startup ke bajaye runtime pe milenge.
4. CDS (Boot 3.3+) — class loading time ~30% kam.
5. AOT + GraalVM native — startup milliseconds mein. Cost: build time badhta hai, reflection ke liye hints chahiye, debugging mushkil.
6. Bean background initialization (Boot 3.4+) — slow beans parallel mein banenge.

Honest answer: serverless ya frequent-scaling ke alawa startup time zyadatar optimize karne layak nahi hota. Pehle poocho — "ye actually problem hai ya lag raha hai?"
