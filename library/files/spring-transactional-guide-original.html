What is @Transactional?

@Transactional is a declarative way to wrap a method (or entire class) inside a database transaction. Spring opens a transaction before the method runs, and either commits on success or rolls back on an exception — without you writing a single line of connection/commit/rollback code.

✓ Without @Transactional (manual)

You manage everything yourself — verbose and error-prone.

✓ With @Transactional

Spring handles begin / commit / rollback via AOP proxy.

// ─── MANUAL (without @Transactional) ───────────────────────────────
public void transferManual(Long from, Long to, BigDecimal amount) {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        conn.setAutoCommit(false);

        // debit
        accountDao.debit(conn, from, amount);
        // credit
        accountDao.credit(conn, to, amount);

        conn.commit();
    } catch (Exception e) {
        if (conn != null) conn.rollback(); // easy to forget!
        throw new RuntimeException(e);
    } finally {
        if (conn != null) conn.close();   // easy to forget!
    }
}

// ─── WITH @Transactional ────────────────────────────────────────────
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    accountRepository.debit(from, amount);   // Spring handles everything
    accountRepository.credit(to, amount);
}

How the Proxy Works Internally

Spring does NOT modify your class. Instead, it wraps it in a proxy object at startup using AOP (Aspect Oriented Programming). Every call goes through the proxy first.

Caller / Controller
──▶
Spring AOP Proxy
──▶
Your Real Bean
↓ intercepts call

──▶
Execute Method
──▶
Commit / Rollback
JDK Dynamic Proxy

Used when your class implements an interface. Spring creates a proxy implementing the same interface.

  • Default when interface exists
  • Slightly lighter weight
  • java.lang.reflect.Proxy
CGLIB Proxy

Used when your class has no interface. Spring subclasses your concrete class at runtime using bytecode generation.

  • Default in Spring Boot (always CGLIB)
  • Requires non-final class + methods
  • Bytecode weaving at startup
// ─── What Spring generates behind the scenes (conceptually) ─────────

// Your real class:
@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        // business logic
    }
}

// Conceptual proxy Spring wraps around it:
public class OrderService$$SpringCGLIB extends OrderService {

    private final TransactionInterceptor interceptor;

    @Override
    public void placeOrder(Order order) {
        TransactionStatus status = interceptor.beginTransaction();
        try {
            super.placeOrder(order);            // calls YOUR real method
            interceptor.commit(status);
        } catch (RuntimeException ex) {
            interceptor.rollback(status);
            throw ex;
        }
    }
}

🚨
Self-invocation pitfall: If method A calls method B within the same class, the call bypasses the proxy — @Transactional on B is ignored. This is the #1 most common mistake.
@Service
public class PaymentService {

    // ❌ BROKEN — self-invocation bypasses proxy
    public void process(Payment p) {
        save(p);   // calls this.save(), NOT proxy.save()
    }

    @Transactional
    public void save(Payment p) {
        // @Transactional has NO effect here when called from process()
    }

    // ✅ FIX — put @Transactional on the public entry point
    @Transactional
    public void processFixed(Payment p) {
        paymentRepo.save(p);
    }
}

Transaction Lifecycle

Understanding the exact sequence Spring follows helps you debug subtle issues.

1. Caller invokes proxy method
↓
2. TransactionInterceptor checks propagation rules
↓
3. DataSourceTransactionManager gets Connection from pool
↓
4. Sets autoCommit = false, binds Connection to current Thread
↓
5. Your real method runs (all repos use the same Connection)
↓
6a. Success → conn.commit() → release back to pool
6b. RuntimeException → conn.rollback() → release back to pool
// Spring binds the Connection to the current thread via ThreadLocal:
// TransactionSynchronizationManager.bindResource(dataSource, conn)
//
// All Spring Data JPA / JDBC calls on the same thread get the SAME
// connection — this is how atomicity is guaranteed.

@Transactional
public void createOrderWithAudit(OrderRequest req) {

    // Both of these use the SAME db connection / transaction
    Order order = orderRepository.save(
        Order.builder()
            .customerId(req.customerId())
            .total(req.total())
            .build()
    );

    auditRepository.save(
        AuditLog.builder()
            .action("ORDER_CREATED")
            .entityId(order.getId())
            .build()
    );

    // If auditRepository.save() throws → BOTH inserts are rolled back
}

Rollback Rules
  • Rolls back by default: RuntimeException and its subclasses, Error
  • Does NOT roll back by default: checked exceptions (e.g. IOException)
  • Override with: rollbackFor = Exception.class or noRollbackFor = MyException.class
// Rollback for checked exceptions too:
@Transactional(rollbackFor = Exception.class)
public void processFile(MultipartFile file) throws IOException {
    var data = parseFile(file);     // throws IOException (checked)
    recordRepository.saveAll(data); // rolled back if parseFile throws
}

// Don't rollback for business exceptions:
@Transactional(noRollbackFor = InsufficientFundsException.class)
public void withdraw(Long accountId, BigDecimal amount) {
    var account = accountRepository.findById(accountId).orElseThrow();
    // save failed attempt log even when funds are insufficient
    attemptLog.save(new WithdrawAttempt(accountId, amount, "FAILED"));
    if (account.getBalance().compareTo(amount) < 0) {
        throw new InsufficientFundsException(); // log is committed!
    }
}

Propagation Types — All 7 Explained

Propagation controls what happens when a @Transactional method is called while a transaction already exists (or doesn't).

Type Existing Tx? No Existing Tx? Use Case
REQUIRED ⭐ default Join it Create new Most service methods
REQUIRES_NEW Suspend old, create new Create new Audit log, email sending
NESTED Savepoint inside existing Create new Partial rollback scenarios
SUPPORTS Join it No transaction Read-only helpers
NOT_SUPPORTED Suspend old, run without tx No transaction Bulk reads, reporting
MANDATORY Join it ❌ Exception Internal APIs that must be called in tx
NEVER ❌ Exception No transaction Methods that must NOT be in a tx 
@Service
public class OrderService {

    private final OrderRepository  orderRepo;
    private final AuditService     auditService;
    private final NotifyService    notifyService;

    // ─── REQUIRED (default) ─────────────────────────────────────────
    @Transactional                        // propagation = REQUIRED
    public void placeOrder(Order order) {
        orderRepo.save(order);            // joins outer tx or creates one
        auditService.log(order);          // see REQUIRES_NEW below
        notifyService.notifyUser(order);  // see NOT_SUPPORTED below
    }
}

@Service
public class AuditService {

    // ─── REQUIRES_NEW ───────────────────────────────────────────────
    // Outer (order) tx is SUSPENDED. Audit always committed separately.
    // Even if placeOrder() rolls back, the audit log is preserved.
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(Order order) {
        auditRepo.save(new AuditEntry("ORDER_PLACED", order.getId()));
    }
}

@Service
public class NotifyService {

    // ─── NOT_SUPPORTED ──────────────────────────────────────────────
    // Sends email — no tx needed. Outer tx is suspended temporarily.
    @Transactional(propagation = Propagation.NOT_SUPPORTED)
    public void notifyUser(Order order) {
        emailClient.send(order.getEmail(), "Order confirmed!");
    }
}

// ─── NESTED — savepoints for partial rollback ────────────────────────

@Transactional
public void importProducts(List<Product> products) {

    for (Product p : products) {
        try {
            importSingle(p);              // NESTED tx — has savepoint
        } catch (Exception e) {
            // Only this product's savepoint is rolled back
            // Other products already imported stay committed
            log.warn("Skipped product {}: {}", p.getId(), e.getMessage());
        }
    }
}

@Transactional(propagation = Propagation.NESTED)
public void importSingle(Product p) {
    productRepo.save(p);
    validateAndEnrich(p);             // may throw — rolls back savepoint only
}

Isolation Levels

Isolation controls how your transaction sees data being modified by concurrent transactions. Higher isolation = fewer anomalies but more locking and lower performance.

Level Dirty Read Non-Repeatable Read Phantom Read Use Case
READ_UNCOMMITTED ✗ possible ✗ possible ✗ possible Analytics, rarely used
READ_COMMITTED ✓ safe ✗ possible ✗ possible PostgreSQL default
REPEATABLE_READ ✓ safe ✓ safe ✗ possible MySQL default, financial reads
SERIALIZABLE ✓ safe ✓ safe ✓ safe Critical operations, slow 
// ─── Isolation examples ──────────────────────────────────────────────

// READ_COMMITTED — safe for most use cases
@Transactional(isolation = Isolation.READ_COMMITTED)
public List<Order> getActiveOrders() {
    return orderRepo.findByStatus(OrderStatus.ACTIVE);
}

// REPEATABLE_READ — balance must not change mid-transaction
@Transactional(isolation = Isolation.REPEATABLE_READ)
public BigDecimal calculateMonthlyStatement(Long accountId) {
    var openBal  = accountRepo.getBalance(accountId);
    var txns     = txnRepo.findThisMonth(accountId);
    var closeBal = accountRepo.getBalance(accountId); // guaranteed same as openBal
    return compute(openBal, txns, closeBal);
}

// SERIALIZABLE — seat reservation (prevent phantom rows)
@Transactional(isolation = Isolation.SERIALIZABLE)
public void bookSeat(Long flightId, String seat) {
    long count = seatRepo.countBySeatAndFlight(seat, flightId);
    if (count > 0) throw new SeatTakenException();
    seatRepo.save(new Booking(flightId, seat));  // no phantom inserts possible
}

What Happens Without @Transactional?

⚠️
Without @Transactional, each repository call uses its own auto-committed connection. A failure halfway through leaves your database in a partial / corrupt state.
@Service
public class TransferService {

    // ❌ NO @Transactional — data corruption risk
    public void transferBroken(Long fromId, Long toId, BigDecimal amount) {

        Account from = accountRepo.findById(fromId).orElseThrow();
        from.debit(amount);
        accountRepo.save(from);   // ← committed immediately (auto-commit)

        // 💥 Exception here (network, constraint, NPE...)
        // from account is debited but to account never credited
        // Money is LOST. Database is corrupted.

        Account to = accountRepo.findById(toId).orElseThrow();
        to.credit(amount);
        accountRepo.save(to);    // ← never reached
    }

    // ✅ WITH @Transactional — atomic, all or nothing
    @Transactional
    public void transferSafe(Long fromId, Long toId, BigDecimal amount) {

        Account from = accountRepo.findById(fromId).orElseThrow();
        from.debit(amount);
        accountRepo.save(from);   // staged — not yet committed

        // 💥 Exception here → BOTH saves rolled back automatically
        // from account is NOT debited — data stays consistent

        Account to = accountRepo.findById(toId).orElseThrow();
        to.credit(amount);
        accountRepo.save(to);
    }
}

Java 17
Other effects of missing @Transactional
  • Lazy loading fails: JPA proxy tries to load associations after the session closes → LazyInitializationException
  • Dirty checking disabled: JPA won't auto-save changed entity fields — you must call save() explicitly
  • Multiple connections: Each repo call borrows a separate connection from the pool — inefficient
  • No first-level cache: Same entity loaded twice hits the DB twice
// LazyInitializationException example without @Transactional

@Service
public class CustomerService {

    // ❌ Lazy load FAILS — no open session
    public List<Order> getOrdersBroken(Long customerId) {
        Customer c = customerRepo.findById(customerId).orElseThrow();
        return c.getOrders();  // 💥 LazyInitializationException!
    }

    // ✅ Session stays open for the whole method
    @Transactional(readOnly = true)
    public List<Order> getOrdersSafe(Long customerId) {
        Customer c = customerRepo.findById(customerId).orElseThrow();
        return c.getOrders();  // ✅ works fine
    }
}

Common Pitfalls

❌ Pitfall 1 — Self-invocation

Calling a @Transactional method from within the same bean bypasses the proxy.

❌ Pitfall 2 — private methods

Proxies can't intercept private or final methods — annotation silently ignored.

❌ Pitfall 3 — Swallowing exceptions

Catching exceptions without re-throwing prevents Spring from triggering rollback.

❌ Pitfall 4 — Long transactions

Holding a transaction open during slow I/O (HTTP calls, file uploads) exhausts the connection pool.

@Service
public class PitfallExamples {

    // ─── Pitfall 1: Self-invocation ──────────────────────────────────
    public void doWorkBad() {
        saveData();    // ❌ bypasses proxy, no transaction!
    }

    @Transactional
    public void saveData() { repo.save(new Entity()); }

    // Fix: annotate the public entry point instead
    @Transactional
    public void doWorkGood() {
        repo.save(new Entity());
    }

    // ─── Pitfall 2: Private method (silently ignored) ────────────────
    @Transactional  // ❌ has NO effect on private methods
    private void privateMethod() { repo.save(new Entity()); }

    // ─── Pitfall 3: Swallowing exceptions → no rollback ─────────────
    @Transactional
    public void saveBad(Data d) {
        try {
            repo.save(d);
            throw new RuntimeException("something failed");
        } catch (Exception e) {
            log.error("error", e); // ❌ exception swallowed → COMMITS!
        }
    }

    // Fix: rethrow or use TransactionAspectSupport
    @Transactional
    public void saveGood(Data d) {
        try {
            repo.save(d);
            throw new RuntimeException("something failed");
        } catch (Exception e) {
            log.error("error", e);
            TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        }
    }

    // ─── Pitfall 4: Long transaction with external I/O ───────────────
    @Transactional  // ❌ holds DB connection during HTTP call!
    public void processOrderBad(Order order) {
        orderRepo.save(order);
        paymentGateway.charge(order);  // slow external API call
    }

    // Fix: do I/O outside transaction
    public void processOrderGood(Order order) {
        PaymentResult result = paymentGateway.charge(order); // I/O first
        saveOrderResult(order, result);                       // tx last
    }

    @Transactional
    public void saveOrderResult(Order order, PaymentResult result) {
        order.setPaymentStatus(result.status());
        orderRepo.save(order);                  // short, fast tx
    }
}

Best Practices

// ─── 1. Use readOnly = true for queries ─────────────────────────────
//    - Tells JPA to skip dirty checking (faster)
//    - Some DBs route to read replica automatically
//    - Prevents accidental writes

@Transactional(readOnly = true)
public Page<ProductDTO> searchProducts(String query, Pageable page) {
    return productRepo.searchByName(query, page)
                      .map(productMapper::toDTO);
}

// ─── 2. Annotate at Service layer, not Repository ────────────────────
//    - Repository methods already have @Transactional from Spring Data
//    - Business logic belongs in Service

@Service
public class SubscriptionService {

    @Transactional
    public void subscribe(Long userId, Long planId) {
        var user = userRepo.findById(userId).orElseThrow();
        var plan = planRepo.findById(planId).orElseThrow();

        user.setPlan(plan);
        userRepo.save(user);

        billingRepo.save(new Invoice(user, plan, LocalDate.now()));
    }
}

// ─── 3. Keep transactions short ──────────────────────────────────────
//    Fetch → process → save. Don't hold the tx open during slow work.

@Transactional
public ReportResult generateReport(Long reportId) {
    var reportData = reportRepo.findById(reportId).orElseThrow();
    var result     = reportEngine.compute(reportData);  // fast, in-memory
    reportRepo.markComplete(reportId);
    return result;
    // NOT: hold tx open while emailing result to 10,000 users
}

// ─── 4. Specify timeout for critical operations ──────────────────────

@Transactional(timeout = 5)  // 5 seconds max, then rollback
public void processPayment(PaymentRequest req) {
    paymentRepo.save(buildPayment(req));
}

// ─── 5. Use @Transactional on interface (Spring recommends class) ────
// Don't do this — CGLIB proxies can't read interface annotations cleanly
// Annotate concrete classes or methods directly.

Real-World Examples

Example A — E-Commerce Order Placement

Multiple writes that must all succeed or all fail together.

@Service
public class OrderPlacementService {

    private final OrderRepository     orderRepo;
    private final InventoryRepository inventoryRepo;
    private final PaymentRepository   paymentRepo;
    private final AuditService        auditService;  // REQUIRES_NEW

    @Transactional(
        rollbackFor = Exception.class,
        timeout     = 10
    )
    public OrderConfirmation placeOrder(PlaceOrderRequest request) {

        // 1. Reserve inventory (inside main tx)
        request.items().forEach(item ->
            inventoryRepo.reserve(item.productId(), item.quantity())
        );

        // 2. Create the order
        Order order = orderRepo.save(
            Order.builder()
                .customerId(request.customerId())
                .items(request.items())
                .status(OrderStatus.PENDING)
                .build()
        );

        // 3. Record payment intent
        paymentRepo.save(
            Payment.builder()
                .orderId(order.getId())
                .amount(order.total())
                .status(PaymentStatus.INITIATED)
                .build()
        );

        // 4. Audit log in its OWN transaction (always committed)
        auditService.log(order.getId(), "ORDER_PLACED");

        return new OrderConfirmation(order.getId(), order.total());

        // If ANY step above throws → inventory + order + payment ALL rolled back
        // But the audit log is safe (committed in its own tx)
    }
}

Example B — Batch Import with Partial Rollback

Use NESTED to skip bad records and continue with the rest.

@Service
public class ProductImportService {

    private final ProductRepository productRepo;
    private final ImportLogRepository logRepo;

    // Outer transaction: commits at the end with all successful products
    @Transactional
    public ImportSummary importCsv(List<ProductRow> rows) {

        int success = 0, failed = 0;

        for (ProductRow row : rows) {
            try {
                importRow(row);   // NESTED tx
                success++;
            } catch (Exception e) {
                failed++;
                // savepoint rolled back — outer tx still alive
                logRepo.save(ImportLog.failure(row.sku(), e.getMessage()));
            }
        }

        return new ImportSummary(success, failed);
    }

    // NESTED: creates a savepoint; partial rollback on failure
    @Transactional(propagation = Propagation.NESTED)
    public void importRow(ProductRow row) {
        Product p = Product.builder()
            .sku(row.sku())
            .name(row.name())
            .price(new BigDecimal(row.price()))   // may throw
            .build();
        productRepo.save(p);
    }
}

Example C — Read-Only Service with Optimized Queries
@Service
@Transactional(readOnly = true)  // default for all methods in this class
public class ReportingService {

    // All reads benefit from: no dirty checking, possible read-replica routing

    public DashboardDTO getDashboard(Long merchantId) {
        var orders   = orderRepo.findTodaysByMerchant(merchantId);
        var revenue  = orderRepo.sumTodayRevenue(merchantId);
        var topItems = orderRepo.findTopProducts(merchantId, Pageable.ofSize(5));
        return new DashboardDTO(orders.size(), revenue, topItems);
    }

    public List<CustomerDTO> getTopCustomers(Long merchantId) {
        return customerRepo.findTopByMerchant(merchantId, Pageable.ofSize(10))
                           .stream()
                           .map(customerMapper::toDTO)
                           .toList();
    }

    // This one DOES write — override the class-level readOnly
    @Transactional  // readOnly = false overrides class-level
    public void refreshCache(Long merchantId) {
        var snapshot = getDashboard(merchantId);
        cacheRepo.save(new DashboardCache(merchantId, snapshot));
    }
}

Example D — Event Outbox Pattern (Reliable Messaging)

Save the domain event in the same transaction as the business data — prevents "saved to DB but never published" bugs.

@Service
public class UserRegistrationService {

    @Transactional
    public User register(RegisterRequest req) {

        // 1. Save the user
        User user = userRepo.save(
            User.builder()
                .email(req.email())
                .passwordHash(hash(req.password()))
                .build()
        );

        // 2. Save outbox event IN THE SAME TRANSACTION
        // If user save fails → event is not saved either
        // If event save fails → user is not saved either
        outboxRepo.save(
            OutboxEvent.builder()
                .type("USER_REGISTERED")
                .payload(toJson(user))
                .status(OutboxStatus.PENDING)
                .build()
        );

        return user;

        // A separate @Scheduled job later reads PENDING outbox events
        // and publishes them to Kafka/RabbitMQ — guaranteed at-least-once
    }
}

Golden rule: Put @Transactional on service layer methods that represent a single business operation. Keep transactions as short as possible and as wide as necessary. Use readOnly = true on every read path.
