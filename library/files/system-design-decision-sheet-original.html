01

Functional vs Non-functional requirements kaise decide karein

FR = system kya karega. NFR = system kitna achha karega. 90% log FR to bata dete hain, marks NFR pe milte hain — kyunki poori architecture NFR se banti hai.

Problemjo actually hota hai

"Design Instagram." — Bas itna hi bola gaya.

  • Scope infinite hai. Feed, stories, DM, reels, ads, search… sab banaoge to 45 min me kuch complete nahi hoga.
  • Candidate turant boxes banana shuru kar deta hai — ye galti sabse mehngi hai, kyunki bina numbers ke box choose karna guess hai.
  • NFR miss ho jaata hai: "kitne users?", "read heavy ya write heavy?", "stale data chalega?" — inke bina DB/cache choose karna coin-toss hai.
  • Production me yahi galti: team pehle Kafka + microservices laga deti hai, requirement thi sirf 50 RPS ki.
Red flagAgar aap 5 minute me diagram bana rahe ho aur ek bhi number nahi poocha — interviewer already mark laga chuka hai.
Decision rule5 min · fixed script

FR nikalne ka formula: Actor + Action + Object. "User uploads a photo", "Follower views feed". Jitne actor-action pair banenge, utne hi API endpoints banenge. Isse LLD apne aap nikal aata hai.

Top-3 rule: Interviewer se bolo — "Main teen core flows pe focus karunga: upload, feed read, follow. Baaki out of scope, agar time bacha to touch karenge." Ye scope-cut hi seniority ka signal hai.

NFR nikalne ke 7 sawaal (ye ratt lo, har design me same hain):

  1. Scale: DAU kitne? Peak QPS? Read:write ratio?
  2. Latency: p99 target? (read <200ms, write <500ms typical)
  3. Consistency: Stale data acceptable? Kitne second tak?
  4. Availability: 99.9% (8.7 hr/yr down) ya 99.99% (52 min/yr)?
  5. Durability: Data kho sakta hai? Payment me kabhi nahi, "typing…" indicator me bilkul chalega.
  6. Data retention & size: 5 saal ka data? Object kitna bada?
  7. Security/compliance: PII, GDPR, audit log, multi-region residency?
RuleHar NFR ko ek number do. "Highly available" ek opinion hai, "99.95%, max 2 min RTO" ek requirement hai. Number ke bina NFR sirf decoration hai.

02

Numbers: NFR ko design me convert karna

Estimation ka maksad accuracy nahi, order of magnitude hai — taaki pata chale ek machine chahiye ya sau. Yahi decide karta hai ki sharding chahiye ya nahi.

Problemkahan atakte hain

"Kitna traffic handle karega?" — aur candidate bolta hai "scale kar denge, horizontally".

  • Estimation ke bina pata nahi chalta ki single Postgres kaafi hai ya sharding chahiye — dono ke design me zameen-aasmaan ka farq hai.
  • Log storage bhool jaate hain: 5 saal ka data 60 TB ho gaya to ek node pe fit hi nahi hoga.
  • Peak vs average gadbad: average 1k QPS but peak 10k QPS (IPL match, sale) — capacity peak pe plan hoti hai.
Decision rule3 min · back of envelope

Sirf 4 numbers nikalo:

  1. Write QPS = daily writes ÷ 86,400. Peak = 3× average maan lo.
  2. Read QPS = write QPS × read:write ratio (social: 100:1, banking: 5:1).
  3. Storage/day = writes/day × row size. ×365×years = total.
  4. Bandwidth = QPS × payload size (images/video me yahi asli cost hai).

Yaad rakhne wale thumb rules (interview me confidently bolne ke liye):

  • 1 well-tuned SQL node ≈ 5k–10k simple QPS, ~10–20k with read replicas.
  • Redis single node ≈ 80k–100k+ ops/sec, sub-ms latency.
  • 1 app pod (8 core) ≈ 1k–3k QPS normal JSON API ke liye.
  • Ek WebSocket server ≈ 50k–100k idle connections (tuned, ~10 KB/conn memory).
  • Kafka partition ≈ 10 MB/s comfortably; parallelism = partition count.
RuleNumber nikaal ke turant conclusion bolo: "2k write QPS aur 40 TB data → single node nahi chalega → shard by user_id." Number ka kaam decision justify karna hai, dikhawa nahi.
03

Tradeoff engine: kaunsa lena, kaunsa chhodna

Tradeoff ka matlab hai: do achhi cheezein ek saath nahi mil sakti. Interview me poore marks tab milte hain jab aap dono side bolo, phir requirement ke basis pe ek side chuno — "it depends" bol ke ruk jaana zero marks hai.

Problemconfusion ka source

"CAP theorem batao" / "Yahan consistency chahiye ya availability?"

  • Log CAP ko galat samajhte hain: network partition ke waqt hi choose karna padta hai. Normal time me aapko C aur A dono milte hain.
  • Har cheez "strongly consistent" bana dete hain → latency aur cost dono double.
  • Ya har cheez eventual bana dete hain → paisa duplicate cut jaata hai.
  • Tradeoff bolte hain par decide nahi karte. Interviewer ko decision chahiye, lecture nahi.
Decision rulebolne ka template

4-line tradeoff template — har tradeoff isi tarike se bolo:

  1. Option A dega: … cost: …
  2. Option B dega: … cost: …
  3. Humari requirement: (NFR se ek line quote karo)
  4. Isliye main A choose karta hoon, aur B ka nuksan is tarike se kam karta hoon.

PACELC yaad rakho, CAP se aage ki baat hai: partition (P) ho to A ya C chuno; Else (normal din) latency (L) ya consistency (C) chuno. Asli life me 99.9% time aap L vs C hi choose kar rahe ho.

RuleMoney, inventory, auth = consistency. Feed, count, recommendation, analytics = availability + eventual. Ek hi system me dono ho sakte hain — per-flow decide karo, per-system nahi.

04

Database kaise choose karein

DB choose karne ka faisla "SQL vs NoSQL" nahi hota. Faisla hota hai: access pattern, consistency need, aur data size — teeno milkar DB batate hain.

Problemgalat sawaal

"Aap kaunsa database lenge?" → "MongoDB, kyunki scalable hai."

  • Ye answer fail hai — reason feature-based hai, requirement-based nahi.
  • Log "NoSQL = fast" maan lete hain. Reality: NoSQL fast tab hai jab query aapke partition key ke through jaaye. Warna scatter-gather aur SQL se bhi slow.
  • Ek hi DB me sab thoosne ki koshish: search bhi, analytics bhi, transaction bhi.
  • Sharding ka faisla late kiya jata hai — migration production me sabse dardnaak kaam hai.
Decision rule4 sawaal · fixed order
  1. Query pattern kya hai? "user ke last 20 orders" (key-based) vs "pichle mahine top 10 categories" (analytical). Query pehle likho, DB baad me chuno.
  2. Multi-row / multi-entity transaction chahiye? Haan → relational (Postgres/MySQL) ya NewSQL (CockroachDB, Spanner, TiDB).
  3. Data volume + growth? < ~2 TB aur linear growth → single Postgres + replicas kaafi hai, seedhe bolo. 100 TB+ → Cassandra/DynamoDB/HBase.
  4. Access shape? Time-series → Timescale/Influx. Graph traversal (friend-of-friend) → Neo4j. Full-text → Elasticsearch. Blob/media → S3 + CDN, DB me sirf URL.
RuleDefault se shuru karo: Postgres + read replica + Redis. Ye 95% products ke liye kaafi hai. Isse hatne ka reason ek number hona chahiye, feeling nahi.
Polyglot ka asli cost3 DB = 3 backup strategy, 3 monitoring, 3 failure mode, 3 on-call runbook. Naya DB tabhi lo jab purana measurably fail ho raha ho.

Problemsharding kab

"Data bahut ho gaya, ab kya?"

Log turant shard bol dete hain. Sharding aapke saare joins, transactions aur unique constraints tod deti hai. Ye last resort hai, first move nahi.

Decision ruleescalation ladder

Isi order me upar chadho, jump mat karo:

  1. Index + query fix (80% "DB slow hai" yahin theek ho jaata hai)
  2. Read replica — read scale, write nahi
  3. Cache (Redis) — hot key ka load hatao
  4. Vertical scale — bada machine, sabse sasta engineering time
  5. Partitioning (same DB, table by date/range)
  6. Archive/cold storage — 2 saal purana data S3 me
  7. Sharding — ab bhi problem hai tab. Key chuno: high cardinality, even distribution, aur query me hamesha present (usually user_id/tenant_id).
05

Redis: lagana kab hai, kaunsa pattern, aur kaunsa data type

Redis "fast bana deta hai" — ye adhoora jawab hai. Redis ek choice hai jiska cost hai: stale data, ek aur failure point, aur invalidation logic. Isliye reason clear hona chahiye.

Problemreal production pain

"Redis kyun? Kya cache karoge? Invalidate kaise karoge?"

  • Stale read: DB update ho gaya, cache purana de raha hai. User ko purana price dikh gaya.
  • Cache stampede: ek popular key expire hui, 10,000 request ek saath DB pe gir gayi.
  • Hot key: ek celebrity ka profile 40% traffic le raha hai, ek hi shard garam ho gaya.
  • Memory bhar gayi: eviction policy set hi nahi thi, Redis ne random keys nikaal di ya OOM ho gaya.
  • Cache ko source of truth maan liya — restart pe data gaya. Redis persistence (RDB/AOF) ke baad bhi cache cache hi hai.
Decision rulekab · kya · kaise

Redis tab lagao jab teeno sach hon:

  1. Read:write ratio > 10:1
  2. Kuch second ka staleness acceptable hai (ya aap explicitly invalidate kar sakte ho)
  3. Same data baar baar maanga jaata hai (skewed access, Pareto)

Pattern chuno:

  • Cache-aside (lazy loading) — 90% cases. App: read cache → miss → DB → cache me daalo. Default yahi bolo.
  • Write-through — write ke waqt cache bhi likho. Consistent, par har write slow.
  • Write-behind — cache me likho, DB me async. Fast, par crash pe data loss. Sirf counters/metrics ke liye.
  • Read-through — cache library khud DB se load kare (Caffeine + Redis 2-level).
RuleUpdate pe cache DELETE karo, UPDATE mat karo. Do concurrent writers cache me alag order me likh sakte hain (lost update). Delete karne se next read fresh value laayegi. Delete idempotent hai, update nahi.

Problem3 classic failures

Cache stampede / thundering herd — hot key expire, sab DB pe.

Cache penetration — jo ID exist hi nahi karti uske liye har baar DB hit (attack vector bhi hai).

Cache avalanche — deploy ke baad saari keys ek hi TTL pe expire, ek saath.

Decision rulefix
  • Stampede → per-key mutex/lock: ek thread DB jaaye, baaki wait karein. Ya "logical expiry" — value ke andar expiry timestamp rakho, stale serve karo aur background me refresh.
  • Penetration → null result ko bhi cache karo chhoti TTL (30–60s) ke saath, ya Bloom filter lagao.
  • Avalanche → TTL me jitter daalo: 300 + random(0,60) sec.
  • Memory → maxmemory + allkeys-lru (pure cache) ya volatile-lru (mixed use). Ye interview me bahut kam log bolte hain.
  • Hot key → key ko N copies me split karo (post:123:v{0..9}) ya app ke andar local cache (Caffeine) 1–2s ke liye.
06

Gateway, load balancer, BFF: kaunsa kahan

"API Gateway laga denge" — par kaunsa layer, aur usme kya rakhna hai? Gateway ka kaam hai cross-cutting concerns ek jagah rakhna, business logic nahi.

Problemjo galat hota hai

"Client 5 services ko alag alag call kar raha hai."

  • Auth har service me duplicate — ek service bhool gayi to security hole.
  • Mobile app 6 round trips kar raha hai ek screen ke liye; 3G pe screen 4 second me khulti hai.
  • Rate limiting kahin nahi — ek buggy client poora cluster gira deta hai.
  • Ulta problem: gateway me business logic ghusa di gayi → gateway hi monolith ban gaya aur single point of failure.
Decision rulelayer by layer

Layer 4 LB (NLB, HAProxy TCP) — sirf IP:port dekhta hai. Fast, TLS pass-through. WebSocket, gRPC, ya raw TCP ke liye achha.

Layer 7 LB / reverse proxy (Nginx, ALB, Envoy) — HTTP header/path dekh sakta hai. Path routing, TLS termination, retry, compression.

API Gateway (Kong, APISIX, Spring Cloud Gateway, AWS API GW) — L7 ke upar: authN/authZ, rate limit, quota, request validation, API key, versioning, aggregation, observability.

BFF (Backend for Frontend) — har client type ke liye alag thin layer: mobile-bff, web-bff. Jab mobile ko chhota payload chahiye aur web ko bada.

Service mesh (Istio, Linkerd) — service-to-service (east-west) traffic: mTLS, retry, circuit breaking, tracing. Gateway north-south ke liye hai, mesh east-west ke liye.

RuleGateway me sirf wahi cheez rakho jo har request pe same tarike se honi hai aur jiska business domain se koi lena-dena nahi. Agar aap gateway me "if order.amount > 10000" likh rahe ho — galat jagah hai.

07

Real-time connection: polling, SSE, WebSocket ya raw TCP

"Socket laga do" bolna aasan hai. Pehle ye decide karo ki data kis direction me aur kitni frequency se jaata hai — usi se protocol nikalta hai.

Problemdecide kya karna hai

"Order status live update chahiye. Kaise karoge?"

  • Polling har 2 second = 1M users × 30 req/min = 500k QPS sirf "kuch naya hai kya?" poochne ke liye. 99% response empty.
  • WebSocket lagane pe naye problem: stateful connections, load balancer ko sticky karna padta hai, deploy pe saare connections tootenge, aur pod A ka message pod B ke user tak kaise jaayega?
  • Auth: WebSocket handshake ke baad browser custom header nahi bhej sakta — token kahan se aayega?
  • Backpressure: slow client ko fast producer maar dega — server memory bhar jaayegi.
Decision ruledirection + frequency
  • Server → client only, update har kuch second: SSE (Server-Sent Events). HTTP hi hai, auto-reconnect built-in, proxy friendly. Notification, live score, progress bar ke liye best aur sabse sasta.
  • Dono taraf, low latency, high frequency: WebSocket. Chat, collaborative editing, trading, multiplayer.
  • Update rare (minute me ek baar): long polling ya normal polling — connection ka kharcha bachao.
  • Browser nahi hai — device/IoT/service-to-service, custom binary protocol: raw TCP socket (ya gRPC streaming, jo HTTP/2 pe hai).
RuleSabse pehle poocho: "kya user ko turant push chahiye, ya thodi der baad pata chal jaaye to chalega?" Agar chalega — SSE ya polling lo. WebSocket free nahi hai, uska ops cost hai.

Har method ka naam intention batata hai (registerRealtimeEndpoints, handleClientConnection) — LLD round me naming pe alag se marks milte hain. Code me (1) jaise marker hain, unka matlab neeche list me hai.

StompBrokerConfig.javaJava 21 · spring-boot-starter-websocket
package com.example.orders.realtime;

@Configuration
@EnableWebSocketMessageBroker
public class StompBrokerConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")                                 // (1)
                .setAllowedOriginPatterns("https://app.example.com")  // (2)
                .addInterceptors(new HandshakeAuthInterceptor())     // (3)
                .withSockJS();                                        // (4)
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic", "/queue")              // (5)
                .setHeartbeatValue(new long[]{10_000, 10_000})       // (6)
                .setTaskScheduler(brokerHeartbeatScheduler());
        registry.setApplicationDestinationPrefixes("/app");          // (7)
        registry.setUserDestinationPrefix("/user");                  // (8)
    }

    @Override
    public void configureWebSocketTransport(WebSocketTransportRegistration reg) {
        reg.setMessageSizeLimit(64 * 1024)                            // (9)
           .setSendBufferSizeLimit(512 * 1024)
           .setSendTimeLimit(20_000);
    }

    @Bean
    public TaskScheduler brokerHeartbeatScheduler() {
        var scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(2);
        scheduler.setThreadNamePrefix("stomp-heartbeat-");
        return scheduler;
    }
}

Line by line — kya aur kyun

  1. 1Handshake URL. Client yahin HTTP se connect karta hai, phir protocol Upgrade: websocket ho jaata hai. Ek hi TCP connection reuse hota hai.
  2. 2Origin whitelist. WebSocket pe CORS lagu nahi hota — isliye ye check zaroori hai, warna koi bhi site aapke socket se connect kar legi (CSWSH attack).
  3. 3Auth handshake pe. Browser WS me custom header nahi bhej sakta, isliye token ?token= query param, cookie, ya pehle STOMP CONNECT frame se lo aur yahin verify karke Principal set karo.
  4. 4SockJS fallback. Purane corporate proxy WS block karte hain; SockJS XHR-streaming pe gir jaata hai. Public consumer app me rakho, internal tool me hata sakte ho.
  5. 5Simple in-memory broker. Ye single-pod hai. Multi-pod pe RabbitMQ/ActiveMQ relay chahiye — tab StompBrokerRelay use hota hai (tab D dekho).
  6. 6Heartbeat 10s. Dead connection detect karne ke liye. Bina iske load balancer idle connection chupchaap kaat dega aur client ko pata bhi nahi chalega.
  7. 7App prefix. Client /app/... pe bhejta hai → aapke @MessageMapping method pe jaata hai. /topic pe seedha broker.
  8. 8User destination. /user/queue/orders — Spring isko internally per-session unique queue me convert karta hai. Isse "sirf isi user ko bhejo" free me mil jaata hai.
  9. 9Backpressure limits. Slow client ke liye buffer cap. Limit cross hui to Spring session close kar deta hai — yahi behaviour aapko chahiye, memory bharne se behtar.

public class OrderRealtimeNotifier {

    private final SimpMessagingTemplate messagingTemplate;

    public OrderRealtimeNotifier(SimpMessagingTemplate messagingTemplate) {
        this.messagingTemplate = messagingTemplate;
    }

    /** Ek hi user ko private update — /user/queue/orders. */
    public void notifyOrderStatusChanged(String userId, OrderStatusEvent event) {
        messagingTemplate.convertAndSendToUser(                       // (1)
                userId, "/queue/orders", event);
    }

    /** Sab subscriber ko broadcast — /topic/orders.{id} */
    public void broadcastOrderTimeline(String orderId, OrderStatusEvent event) {
        messagingTemplate.convertAndSend("/topic/orders." + orderId, event);
    }
}

@Controller
public class OrderStreamController {

    private final OrderQueryService orderQueryService;

    public OrderStreamController(OrderQueryService orderQueryService) {
        this.orderQueryService = orderQueryService;
    }

    @MessageMapping("/orders.subscribe")                            // (2)
    @SendToUser("/queue/orders")                                    // (3)
    public OrderSnapshot handleInitialSnapshotRequest(
            SubscribeCommand command, Principal principal) {

        String userId = principal.getName();                          // (4)
        return orderQueryService.loadSnapshotForUser(userId, command.orderId());
    }

    @MessageExceptionHandler(AccessDeniedException.class)              // (5)
    @SendToUser("/queue/errors")
    public ErrorPayload handleAccessDenied(AccessDeniedException ex) {
        return new ErrorPayload("FORBIDDEN", ex.getMessage());
    }
}

Line by line

  1. 1convertAndSendToUser — object ko JSON me convert karke us user ke private queue me daal deta hai. Aapko session dhoondhna nahi padta, Spring karta hai.
  2. 2@MessageMapping — client ne /app/orders.subscribe pe frame bheja to yahi method chalega. REST ka @PostMapping ka socket version samajh lo.
  3. 3@SendToUser — return value automatically usi caller ko chala jaata hai. Pehla snapshot bhejna zaroori hai: client ko current state chahiye, phir usme delta apply hote rahenge.
  4. 4Principal handshake me set hua tha — isse authorization karo. Client ke bheje hue userId pe kabhi bharosa mat karo.
  5. 5Error channel. Socket me HTTP status code nahi hota; error alag destination pe bhejna padta hai warna client ko sirf silence milega.

        sessionsByUser.computeIfAbsent(userId, key -> ConcurrentHashMap.newKeySet())
                      .add(session);
        log.info("ws.connected userId={} sessionId={} total={}",
                 userId, session.getId(), countOpenSessions());

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message)
            throws Exception {

        ClientCommand command = objectMapper.readValue(                 // (4)
                message.getPayload(), ClientCommand.class);

        switch (command.type()) {                                       // (5)
            case PING  -> sendJson(session, new ServerEvent("PONG", null));
            case ACK   -> acknowledgeDelivery(command.eventId());
            default    -> sendJson(session,
                            new ServerEvent("ERROR", "unknown command"));
        }
    }

    /** Business layer isko call karti hai jab order status badle. */
    public void pushOrderStatusToUser(String userId, OrderStatusEvent event) {
        Set<WebSocketSession> sessions =
                sessionsByUser.getOrDefault(userId, Set.of());          // (6)
        for (WebSocketSession session : sessions) {
            if (session.isOpen()) {
                sendJson(session, new ServerEvent("ORDER_STATUS", event));
            }
        }
    }

    private void sendJson(WebSocketSession session, Object payload) {
        try {
            session.sendMessage(new TextMessage(
                    objectMapper.writeValueAsString(payload)));
        } catch (IOException | IllegalStateException ex) {              // (7)
            log.warn("ws.send.failed sessionId={} reason={}",
                     session.getId(), ex.toString());
            closeQuietly(session);
        }
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        String userId = resolveUserId(session);
        sessionsByUser.computeIfPresent(userId, (key, set) -> {          // (8)
            set.remove(session);
            return set.isEmpty() ? null : set;
        });
    }

    @Override
    public void handleTransportError(WebSocketSession session, Throwable ex) {
        log.warn("ws.transport.error sessionId={}", session.getId(), ex);
        closeQuietly(session);

@Component
public class TcpOrderFeedServer implements SmartLifecycle {

    private static final Logger log = LoggerFactory.getLogger(TcpOrderFeedServer.class);
    private static final int MAX_FRAME_BYTES = 64 * 1024;

    private final int port;
    private final OrderCommandService orderCommandService;
    private final ExecutorService connectionExecutor =
            Executors.newVirtualThreadPerTaskExecutor();               // (1)
    private volatile ServerSocket serverSocket;
    private volatile boolean running;

    public TcpOrderFeedServer(@Value("${feed.tcp.port:9099}") int port,
                              OrderCommandService orderCommandService) {
        this.port = port;
        this.orderCommandService = orderCommandService;
    }

    @Override
    public void start() {
        running = true;
        Thread.ofVirtual().name("tcp-acceptor").start(this::runAcceptLoop); // (2)
    }

    private void runAcceptLoop() {
        try (ServerSocket socket = new ServerSocket(port, 512)) {         // (3)
            this.serverSocket = socket;
            log.info("tcp.feed.listening port={}", port);
            while (running) {
                Socket client = socket.accept();                        // (4)
                connectionExecutor.submit(() -> handleClientConnection(client));
            }
        } catch (IOException ex) {
            if (running) log.error("tcp.accept.failed", ex);
        }
    }

    private void handleClientConnection(Socket client) {
        try (client;                                                    // (5)
             var in  = new DataInputStream(
                           new BufferedInputStream(client.getInputStream()));
             var out = new DataOutputStream(
                           new BufferedOutputStream(client.getOutputStream()))) {

            client.setTcpNoDelay(true);                                  // (6)
            client.setSoTimeout(60_000);                                // (7)
            client.setKeepAlive(true);

            while (running && !client.isClosed()) {
                byte[] frame = readLengthPrefixedFrame(in);             // (8)
                if (frame == null) break;                              // clean EOF
                byte[] response = processFeedCommand(frame);
                writeLengthPrefixedFrame(out, response);
                out.flush();                                            // (9)
            }
        } catch (SocketTimeoutException ex) {
            log.info("tcp.idle.timeout remote={}", client.getRemoteSocketAddress());
        } catch (IOException ex) {
            log.warn("tcp.connection.error remote={}",
                     client.getRemoteSocketAddress(), ex);
        }
    }

    /** 4-byte big-endian length + payload. TCP stream hai, message boundary khud banani padti hai. */
    private byte[] readLengthPrefixedFrame(DataInputStream in) throws IOException {
        int length;
        try {
            length = in.readInt();
        } catch (EOFException eof) {
            return null;
        }
        if (length <= 0 || length > MAX_FRAME_BYTES) {                  // (10)
            throw new IOException("invalid frame length: " + length);
        }
        byte[] payload = new byte[length];
        in.readFully(payload);                                          // (11)
        return payload;
    }

    private void writeLengthPrefixedFrame(DataOutputStream out, byte[] payload)
            throws IOException {
        out.writeInt(payload.length);
        out.write(payload);
    }

    private byte[] processFeedCommand(byte[] frame) {
        String command = new String(frame, StandardCharsets.UTF_8);
        String result  = orderCommandService.applyDeviceCommand(command);
        return result.getBytes(StandardCharsets.UTF_8);
    }

    @Override
    public void stop() {                                              // (12)
        running = false;
        try { if (serverSocket != null) serverSocket.close(); }
        catch (IOException ignored) { }
        connectionExecutor.shutdown();
    }

    @Override
    public boolean isRunning() { return running; }
}

@Service
public class OrderCommandService {

    private static final Duration IDEMPOTENCY_TTL = Duration.ofHours(24);
    private static final String CACHE_KEY_PREFIX = "order:v1:";

    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository;
    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    public OrderCommandService(OrderRepository orderRepository,
                               OutboxRepository outboxRepository,
                               StringRedisTemplate redisTemplate,
                               ObjectMapper objectMapper) {
        this.orderRepository = orderRepository;
        this.outboxRepository = outboxRepository;
        this.redisTemplate = redisTemplate;
        this.objectMapper = objectMapper;
    }

    /**
     * CREATE. Same idempotencyKey ke saath do baar call hone par
     * sirf ek order banega — retry aur double-click dono safe.
     */
    @Transactional
    public OrderView placeOrder(PlaceOrderCommand command, String idempotencyKey) {

        boolean firstAttempt = reserveIdempotencyKey(idempotencyKey);     // (1)
        if (!firstAttempt) {
            return orderRepository.findByIdempotencyKey(idempotencyKey)   // (2)
                    .map(OrderView::from)
                    .orElseThrow(() -> new DuplicateInFlightException(idempotencyKey));
        }

        OrderEntity order = new OrderEntity();
        order.setId(UUID.randomUUID());
        order.setUserId(command.userId());
        order.setAmountMinor(command.amountMinor());
        order.setStatus(OrderStatus.CREATED);
        order.setIdempotencyKey(idempotencyKey);
        order.setVersion(0L);                                             // (3)

        orderRepository.save(order);                                      // (4)
        outboxRepository.save(OutboxEvent.of(                             // (5)
                "ORDER_CREATED", order.getId().toString(), toJson(order)));

        registerCacheInvalidationAfterCommit(order.getId());              // (6)
        return OrderView.from(order);
    }

    /**
     * UPDATE. Optimistic locking se lost-update se bachte hain:
     * do parallel update me ek jeetega, doosre ko 409 milega.
     */
    @Transactional
    public OrderView updateOrderStatus(UUID orderId, OrderStatus newStatus,
                                       long expectedVersion) {

        int updatedRows = orderRepository.updateStatusIfVersionMatches(     // (7)
                orderId, newStatus, expectedVersion);

        if (updatedRows == 0) {
            throw new StaleObjectException(orderId, expectedVersion);      // (8)
        }

        OrderEntity fresh = orderRepository.getById(orderId);
        outboxRepository.save(OutboxEvent.of(
                "ORDER_STATUS_CHANGED", orderId.toString(), toJson(fresh)));

        registerCacheInvalidationAfterCommit(orderId);                    // (9)
        return OrderView.from(fresh);
    }

    /** Redis SET NX EX — atomic "pehla jeete" check. */
    private boolean reserveIdempotencyKey(String idempotencyKey) {
        Boolean acquired = redisTemplate.opsForValue()
                .setIfAbsent("idem:" + idempotencyKey, "1", IDEMPOTENCY_TTL);
        return Boolean.TRUE.equals(acquired);
    }

    /** Cache delete COMMIT ke baad — pehle karoge to rollback pe cache galat ho jaayega. */
    private void registerCacheInvalidationAfterCommit(UUID orderId) {
        TransactionSynchronizationManager.registerSynchronization(
                new TransactionSynchronization() {
                    @Override
                    public void afterCommit() {
                        redisTemplate.delete(CACHE_KEY_PREFIX + orderId); // (10)
                    }
                });
    }
}

  2. 2Duplicate ka jawab bhi 200 hona chahiye (naya order nahi), purana result laut ao. Retry ko error dena galat design hai.
  3. 3version column — optimistic locking ki jaan. Har update pe +1.
  4. 4Order insert. Yahan tak sab ek hi DB transaction me hai.
  5. 5Outbox — sabse important trick. Event ko usi transaction me table me likhte hain. Agar seedha Kafka pe bhejte aur commit fail ho jaata, to duniya ko "order created" pata chal jaata jabki order hai hi nahi. Dual-write problem yahin marta hai.
  6. 6Side-effect ko commit ke baad schedule karo — abhi mat karo.
  7. 7Conditional update: UPDATE orders SET status=?, version=version+1 WHERE id=? AND version=?. Ek hi statement me check + write, isliye atomic.
  8. 80 rows = kisi aur ne pehle update kar diya. Client ko 409 Conflict do, wo fresh state le kar retry kare. Silently overwrite karna data loss hai.

  10. 10afterCommit. Delete before commit karoge to: cache khali → koi read aayi → DB se purani value padhi → cache me purani value wapas → phir aapka commit hua. Cache permanently stale. Ye classic race hai; replication lag ho to "delayed double delete" (500ms baad ek aur delete) bhi lagate hain.

    public Optional<OrderView> findOrderById(UUID orderId) {
        String cacheKey = CACHE_KEY_PREFIX + orderId;

        String cached = redisTemplate.opsForValue().get(cacheKey);        // (1)
        if (cached != null) {
            return Optional.of(readJson(cached, OrderView.class));       // HIT
        }

        Optional<OrderView> fromDb = orderReadRepository                  // (2)
                .findById(orderId)
                .map(OrderView::from);

        fromDb.ifPresentOrElse(
                view -> cacheWithJitteredTtl(cacheKey, writeJson(view)),  // (3)
                ()   -> cacheNegativeResult(cacheKey));                   // (4)

        return fromDb;
    }

    /** TTL me randomness — sab keys ek saath expire na hon (avalanche). */
    private void cacheWithJitteredTtl(String cacheKey, String payload) {
        int ttl = BASE_TTL_SECONDS
                + ThreadLocalRandom.current().nextInt(60);                // (5)
        redisTemplate.opsForValue().set(cacheKey, payload, Duration.ofSeconds(ttl));
    }

    /** Jo id exist hi nahi karti uske liye chhoti TTL — cache penetration se bachav. */
    private void cacheNegativeResult(String cacheKey) {
        redisTemplate.opsForValue().set(cacheKey, "__MISSING__",
                Duration.ofSeconds(30));                                  // (6)
    }
}

Line by line

  1. 1Cache pehle. Hit hua to DB tak jaana hi nahi — yahi 90% load kam karta hai.
  2. 2Miss pe replica se padho, primary se nahi. Read traffic ko primary se door rakho. Par dhyaan: replica lag hota hai — "apna hi abhi kiya hua order" primary se padho (read-your-writes).
  3. 3Cache fill. Cache-aside ka "aside" yahi hai — application decide karta hai, DB nahi.
  4. 4Negative caching. Attacker random IDs maang ke har baar DB hit karwa sakta hai.
  5. 5Jitter. 300 ± 60s. Bina jitter ke deploy ke 5 min baad saari keys ek saath expire hoti hain aur DB spike karta hai.
  6. 6Sentinel value. "__MISSING__" ko read karte waqt Optional.empty() maano — null aur "cached null" me farq rakho.

Tradeoff triage: kya apply karna, kya ignore, kya defer

Seniority ka asli test ye hai: kya nahi banaya aur uska reason. Sab kuch add karna easy hai; usse system bhi slow hota hai aur interview bhi.

Hamesha apply karocheap, non-negotiable
  • Timeouts har network call pe. Default infinite timeout production ka #1 killer hai.
  • Idempotency har write API pe jo retry ho sakti hai.
  • Pagination har list API pe (cursor-based, offset nahi).
  • Structured logs + request id/trace id.
  • Input validation aur rate limit edge pe.
  • Backup + restore drill (restore test kiya nahi to backup nahi hai).
  • Index query pattern ke hisaab se.
Default me ignore karo (jab tak number na bole)premature
  • Sharding — jab tak single node + replica bear kar raha hai.
  • Microservices — chhoti team ke saath.
  • Multi-region active-active — jab tak compliance/latency requirement na ho. Cost aur conflict resolution dono bhaari hain.
  • Kafka — 100 events/sec ke liye Postgres table + poller kaafi hai.
  • Service mesh — 5 services pe overkill.
  • Exactly-once delivery — practically at-least-once + idempotent consumer hi answer hai.
  • Custom framework — jo managed service se ho jaaye.

    HLDDesign a URL shortener. 100M new links/day, 10B redirects/day.

    FR: shorten(longUrl, customAlias?, ttl?), redirect(code), basic analytics. NFR: redirect p99 < 50 ms, 99.99% availability, links immutable, read:write ≈ 100:1.

    Numbers: writes ≈ 1.2k/s (peak 4k/s), reads ≈ 115k/s. 7-char base62 = 3.5 trillion combos. 100M/day × 500 B ≈ 50 GB/day ≈ 18 TB/year.

    Design: ID generation ke 3 option — (a) random 7-char + collision check, (b) counter → base62, (c) pre-generated key pool. Main counter/segment approach lunga: har app instance Redis/Zookeeper se 10k IDs ka range leta hai, phir memory se serve karta hai — koi coordination nahi, no collision. Storage: key-value (DynamoDB/Cassandra) with code as partition key, kyunki query hamesha exact key se hai, koi join nahi. Redirect path: CDN/edge cache → Redis (hot links, 20% links = 80% traffic) → DB. Redirect me 301 vs 302 tradeoff: 301 cacheable hai (server load kam) par analytics khatam ho jaati hai; isliye 302 + async analytics event Kafka pe.

    Tradeoff bola: eventual consistency for analytics counts (Redis INCR + periodic flush), strong nahi chahiye. Custom alias ke liye unique constraint DB me — wahan conditional write (IF NOT EXISTS).

    HLDInterviewer ne sirf ek line di: "Design a notification system." Aap pehle 5 minute me kya karoge?

    Scope cut + numbers. Bolo: "Main teen channel lunga — push, SMS, email. In-app inbox out of scope rakhta hoon."

    FR: send(userId, template, channel), user preference honor karna, dedup, retry, delivery status.
    NFR: 50M notifications/day (≈600/s avg, 5k/s peak — sale/match), transactional OTP p99 < 2s, marketing me 5 min delay OK, at-least-once with dedup, no duplicate OTP.

    Ye split hi asli answer hai: OTP aur marketing ek hi queue me mat daalo. Alag topic, alag priority, alag rate limit — warna marketing burst OTP ko block kar dega (noisy neighbour). Fan-out: API → Kafka topic per priority → per-channel workers → provider (with circuit breaker + fallback provider). Dedup: SETNX notif:{userId}:{templateId}:{bucket}. Preference + quiet hours check worker me, API me nahi.

    TradeoffPayment system me CAP me se kya chunoge? PACELC me kya?

    CAP: partition ke time C over A. Debit fail ho jaana theek hai; do baar debit hona nahi. Practically: write ko single primary region me rakho; partition me minority side write reject kare (503), read allowed.

    PACELC: Else branch me bhi C over L — thoda extra latency (sync replication, quorum) accept karunga.

    Par poora system nahi: balance display, transaction history, notification — ye eventual chal jaayenge cache se. Consistency per-flow decide hoti hai, per-system nahi — yahi line interviewer sunna chahta hai.

    DBTable me 500M rows, query 8 second le raha hai. Step by step kya karoge?
    1. EXPLAIN ANALYZE — seq scan hai ya index scan? Kitne rows estimate vs actual?
    2. Composite index query order me banao: (user_id, created_at DESC). Covering index se index-only scan mil jaata hai.
    3. SELECT * hatao, sirf needed columns. Offset pagination hatao → keyset/cursor: WHERE (created_at, id) < (?, ?) LIMIT 20. OFFSET 100000 hamesha slow rahega, index ho ya na ho.
    4. N+1 hai to batch/join karo.
    5. Read replica pe bhejo agar staleness chalega.
    6. Cache karo agar same query repeat hoti hai.
    7. Purana data partition/archive karo (monthly partition + drop old).
    8. Ab bhi problem hai to shard.

    90% baar step 1–3 me hi khatam ho jaata hai. Jo candidate seedha "shard kar denge" bolta hai, wo yahin loose kar deta hai.

    RedisCache aur DB inconsistent ho gaye. Kaunse race conditions possible hain?
    • Update-before-commit: cache delete kiya, phir txn rollback ho gaya → cache to sahi hai par agar aapne cache set kiya tha to permanently galat value. Fix: afterCommit me hi cache touch karo.
    • Read-then-write race: Reader ne DB se purani value padhi, usi beech writer ne DB update + cache delete kiya, phir reader ne purani value cache me daal di. Fix: delayed double delete (commit ke baad, aur ~500 ms baad phir se delete), ya versioned cache key, ya short TTL.
    • Replica lag: write primary pe, read replica se → cache me stale value bhar gayi. Fix: cache fill hamesha primary se, ya read-your-writes window me primary se padho.
    • Two writers: dono ne cache set kiya alag order me. Fix: set mat karo, delete karo.

    Final safety net: TTL. TTL har bug ki upper bound hai — isliye infinite TTL kabhi mat rakho.

    Socket1M concurrent chat users. WebSocket layer kaise design karoge?

    Connection tier alag: "gateway/edge" pods sirf sockets hold karein (50k–100k per pod → ~15–20 pods + headroom). Business logic alag services me — connection tier ko patla rakho taaki deploy kam ho.

    Routing: Redis me user:{id} → podId presence map (TTL + heartbeat). Message aane pe target pod ko direct bhejo (Redis pub/sub channel per pod, ya gRPC). Broadcast-to-all-pods sirf tab jab presence map miss ho.

    Delivery guarantee: message pehle DB/Kafka me persist, phir push. Client ACK bheje; ACK nahi aaya to reconnect pe lastMessageId se replay. Ordering per conversation — Kafka key = conversationId.

    Ops: heartbeat 20s (LB idle timeout se kam), graceful shutdown me server "please reconnect" frame bheje aur staggered close kare (warna 50k reconnect ek saath), client pe exponential backoff + jitter. L4 LB use karo, L7 me har connection ka overhead zyada hai.

    CodeTCP me "message boundary" problem kya hai? Java me kaise solve karte ho?

    TCP ek byte stream hai, message-oriented nahi. Aapne 3 messages bheje — receiver ko ek hi read() me sab mil sakte hain (coalescing), ya ek message do read() me tut sakta hai (fragmentation).

    Solution — framing: (a) length prefix — 4-byte big-endian length + payload, (b) delimiter — \n ya null byte (text protocols me), (c) fixed-size frames.

    Java me: DataInputStream.readInt() se length lo, validate karo (max frame size warna OOM attack), phir readFully(byte[]) — ye poora buffer bharne tak block karta hai. Plain read() partial data deta hai, aur yahi silent production bug banta hai. Netty me ye kaam LengthFieldBasedFrameDecoder karta hai.

    LLDPayment API idempotent kaise banaoge? Code-level design bolo.

    Contract: client har logical operation ke liye ek Idempotency-Key header bhejta hai (UUID, retry pe same).

    Storage: idempotency_records(key PK, request_hash, status, response_body, created_at) — DB me, sirf Redis me nahi (Redis evict kar sakta hai; paise me ye risk nahi lete).

    Algorithm: (1) INSERT ... ON CONFLICT DO NOTHING with status=IN_PROGRESS — insert hua to aap owner ho. (2) Insert nahi hua aur status=DONE → stored response wapas kar do (same status code). (3) status=IN_PROGRESS → 409 ya 425, client retry kare. (4) Kaam khatam hone pe usi txn me status=DONE + response save.

    Edge cases: same key par alag payload → 422 (request_hash mismatch se pata chalta hai). Key ka TTL 24h. Aur asli baat: idempotency downstream tak jaani chahiye — PSP ko bhi wahi reference bhejo, warna aapka record theek rahega par bank do baar charge kar dega.

    LLDOptimistic vs pessimistic locking — kab kaunsa? Ek example do.

    Optimistic (version column, compare-and-set): conflict rare ho tab. Koi lock hold nahi hota, throughput best. Fail hone pe 409 → client retry. Example: user profile update, order status.

    Pessimistic (SELECT ... FOR UPDATE): conflict common ho aur retry mehnga ho. Example: 100 log ek hi concert seat pe. Row lock le lo, warna 99 log fail hoke retry karenge — wo optimistic se bhi mehnga pad jaata hai.

    Distributed lock (Redis/Zookeeper) tab jab resource DB me hai hi nahi (external API call, file). Par yaad rakho: Redis lock guarantee nahi deta (GC pause, clock skew) — critical section me fencing token lagao. Jahan possible ho, DB constraint hi asli lock hai.

    MicroOrder aur Payment alag services hain. Atomic kaise banaoge? 2PC kyun nahi?

    2PC nahi kyunki: coordinator single point of failure hai, participants prepare phase me lock hold karte hain (throughput gir jaata hai), aur zyadatar modern datastores/queues XA support hi nahi karte.

    Saga: chain of local transactions + compensations.
    Orchestration (ek OrderSaga service steps chalati hai) — debug aasan, flow ek jagah dikhta hai; central component ban jaata hai.
    Choreography (har service event sun ke react karti hai) — loosely coupled, par 8 services ke baad flow samajhna mushkil.

    Rule: 3–4 step tak choreography, usse zyada steps ya paisa involved → orchestration. Compensation likhna mat bhoolo: payment fail → releaseInventory, cancelOrder, user ko notify. Aur har step idempotent, kyunki retry hoga hi.

    MicroTransactional outbox kyun chahiye? Bina uske kya tootega?

    Dual-write problem: aapko DB me likhna hai aur Kafka pe event bhejna hai. Dono alag systems hain, ek hi transaction me nahi aate.

    • DB commit hua, Kafka publish fail → downstream ko kabhi pata nahi chala. Silent data divergence — sabse khatarnaak bug, kyunki alert bhi nahi bajta.
    • Kafka publish hua, DB rollback → duniya ko phantom order dikh gaya.

    Outbox: event ko usi txn me outbox table me likho. Ek relay (poller ya Debezium CDC) commit hue rows ko Kafka pe bhejta hai aur mark kar deta hai. Guarantee at-least-once hai — isliye consumer idempotent hona chahiye (event_id dedup). Exactly-once ka peecha mat karo; at-least-once + idempotency hi practical answer hai.

    LLDDistributed rate limiter design karo — 1M users, 100 req/min per user.

    Algorithm choice: fixed window simple hai par boundary pe 2× burst deta hai. Sliding window log accurate hai par memory bhaari. Token bucket lunga — burst allow karta hai, memory O(1) per user, aur "refill rate" business language me samjhaana aasan hai.

    State: Redis me per user HASH {tokens, lastRefillMs}. Check + decrement ek Lua script me — atomic, ek round trip. GET phir SET karoge to race condition me limit bypass ho jaayegi.

    Scale: 1M users × ~50 B ≈ 50 MB — ek Redis node ke liye kuch bhi nahi. Redis down ho to fail-open (traffic allow) ya fail-closed? Public API → fail-open + local in-memory fallback limit; paid quota/abuse control → fail-closed.

    LLD shape: RateLimiter interface with tryAcquire(key, permits); TokenBucketLimiter, SlidingWindowLimiter implementations (strategy pattern); RateLimitFilter jo 429 + Retry-After header set kare.

    HLDTicket booking me double booking kaise rokoge?

    Teen layer:

    1. Reservation with TTL: seat ko 10 min ke liye "HELD" mark karo (row me held_until). Payment complete → CONFIRMED, warna background job release kar de. Cart me daalna hi booking nahi hai.
    2. Atomic claim: UPDATE seats SET status='HELD', held_by=?, held_until=? WHERE seat_id=? AND status='AVAILABLE' — 1 row updated to aapko mila, 0 to kisi aur ne le liya. Ye conditional update hi asli lock hai.
    3. Constraint: DB me unique constraint (event_id, seat_no) on confirmed bookings — last line of defence, code me bug ho tab bhi DB galat data nahi lene dega.

    Scale: ek popular show pe 100k log ek saath — waiting room/queue lagao (token issue karo), warna DB pe lock contention se sab timeout honge. Cache se kabhi seat availability final mat batao — display ke liye theek hai, claim hamesha DB pe.

    InfraKafka, RabbitMQ, Redis Streams, ya SQS — kab kya?
    • Kafka: high throughput, replay chahiye, multiple independent consumers same data padhein, ordering per key. Event sourcing, analytics, CDC. Ops bhaari hai.
    • RabbitMQ: classic task queue, per-message ack, complex routing (topic/fanout exchange), priority queue, delayed message. Ordering aur replay weak.
    • Redis Streams: already Redis hai aur volume medium — consumer group + ack mil jaata hai bina naya system laaye. Durability Kafka jitni nahi.
    • SQS/managed: team chhoti hai, ops nahi chahiye, at-least-once + DLQ built-in kaafi hai. Zyadatar startups ke liye sahi jawab yahi hai.

    Decide karne ka sawaal: "Kya mujhe same message ko dobara padhna padega (replay)?" Haan → Kafka/Streams. Nahi → queue kaafi hai.

    TradeoffTraffic 10× ho gaya. Pehla bottleneck kya milega aur order kya hoga?

    Usually isi order me: (1) DB connections → pool exhausted, app threads wait. Fix: pooling (PgBouncer), connection cap per pod, timeout. (2) DB writes/IOPS → primary saturate. Fix: batch writes, async non-critical writes, phir sharding. (3) Hot keys/rows → ek partition garam. Fix: key splitting, local cache. (4) N+1 aur serialization CPU app tier me. (5) Cross-service chattiness → 1 request me 30 downstream calls.

    Answer ka structure yahi hona chahiye: "measure kya karunga" → "kaunsa metric limit dikhaayega" → "phir kya fix". Sirf "aur pods add kar denge" bolna galat hai — stateless tier scale ho jaata hai, DB nahi.

    BasicsGateway, load balancer aur service mesh me farq ek-ek line me?

    Load balancer: traffic ko N healthy instances me baantta hai (L4 = IP/port, L7 = HTTP-aware).

    API Gateway: north-south (bahar se andar) traffic ka single door — auth, rate limit, routing, aggregation, API versioning.

    Service mesh: east-west (service-to-service) traffic — sidecar proxy se mTLS, retry, timeout, circuit breaking, tracing, bina app code badle.

    Chhote setup me mesh ki zaroorat nahi; Resilience4j + gateway kaafi hai. Mesh ka faayda tab hai jab 20+ services aur multiple languages hon.
