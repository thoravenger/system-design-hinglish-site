Part 1

Stream methods to learn first

Twenty-one methods, each with what it does, two examples, the common mistake and a mini exercise.

How a stream works

A stream reads a collection, passes each element through a chain of steps, and produces one result; it never changes the original collection.

Every stream has three parts:

  1. A source: txns.stream().
  2. Zero or more intermediate operations, such as filter, map or sorted. Each one returns a new stream, and nothing runs yet.
  3. Exactly one terminal operation, such as collect, count, sum or findFirst. It runs the whole chain and produces the result.
List<String> debitIds = txns.stream()                    // source
        .filter(t -> "DEBIT".equals(t.getType()))        // intermediate
        .map(Transaction::getId)                         // intermediate
        .collect(Collectors.toList());                   // terminal
// [T2, T3, T5, T6]

Three rules to remember:

  1. The source list is never changed; the result is always new.
  2. A stream can be used only once. Using it again throws IllegalStateException: stream has already been operated upon or closed.
  3. Without a terminal operation, nothing happens at all.

t -> t.getId() and Transaction::getId mean the same thing; the second form is called a method reference.

Every method section below has the same shape: what it does, a simple example, a transaction example, the common mistake, and a mini exercise with its expected result. Write your answer first, then tap Show answer to check it.

Sample data used in every example

List<Integer> nums = List.of(5, 3, 8, 3, 10, 1);
List<String> names = List.of("Asha", "Ben", "Chen", "Ben", "Dev");

// Transaction(id, accountId, type, amount, status, tags)
List<Transaction> txns = List.of(
    new Transaction("T1", "ACC-1", "CREDIT", 500.00, "SUCCESS", List.of("salary")),
    new Transaction("T2", "ACC-1", "DEBIT",  120.50, "SUCCESS", List.of("rent", "monthly")),
    new Transaction("T3", "ACC-2", "DEBIT",   75.25, "FAILED",  List.of("bills")),
    new Transaction("T4", "ACC-2", "CREDIT", 900.00, "SUCCESS", null),
    new Transaction("T5", "ACC-3", "DEBIT",  300.00, "PENDING", List.of("rent")),
    new Transaction("T6", "ACC-1", "DEBIT",   45.00, "SUCCESS", List.of("monthly"))
);

This Transaction is a smaller version of the class used in Part 2, with a getter for every field. Outputs show transactions by id (T1, T2, and so on) to keep them short. Imports: java.util.* and java.util.stream.*.

Intermediate operations: they return a new stream

1. filter()

Keeps the elements that pass a test and drops the rest.

How to call it: filter(element -> condition), where the condition returns true (keep) or false (drop).

Example 1, numbers:

List<Integer> big = nums.stream()
        .filter(n -> n > 4)
        .collect(Collectors.toList());
// [5, 8, 10]

Example 2, successful debits:

List<Transaction> successfulDebits = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .collect(Collectors.toList());
// [T2, T6]

Two filter() calls in a row mean AND. An OR rule must sit inside one filter: .filter(t -> isA(t) || isB(t)).

Common mistake: writing txns.stream().filter(...) without collect(). Nothing runs, and txns doesn't change. Also compare strings with "SUCCESS".equals(...), never ==.

Mini exercise 1: return the transactions whose status is FAILED or PENDING. Expected: [T3, T5].

Show answerHide answer
List<Transaction> failedOrPending = txns.stream()
        .filter(t -> "FAILED".equals(t.getStatus()) || "PENDING".equals(t.getStatus()))
        .collect(Collectors.toList());
// [T3, T5]

The OR has to sit inside one filter. Two filters in a row would mean FAILED and PENDING at the same time, which matches nothing.

2. map()

Turns each element into another value: one element in, one element out.

How to call it: map(element -> newValue). The new value can be a different type, for example a Transaction turning into a String.

Example 1, numbers:

List<Integer> doubled = nums.stream()
        .map(n -> n * 2)
        .collect(Collectors.toList());
// [10, 6, 16, 6, 20, 2]

Example 2, transactions:

List<String> accounts = txns.stream()
        .map(Transaction::getAccountId)
        .collect(Collectors.toList());
// [ACC-1, ACC-1, ACC-2, ACC-2, ACC-3, ACC-1]

List<String> labels = txns.stream()
        .map(t -> t.getId() + ":" + t.getStatus())
        .collect(Collectors.toList());
// [T1:SUCCESS, T2:SUCCESS, T3:FAILED, T4:SUCCESS, T5:PENDING, T6:SUCCESS]

Common mistake: filtering after you have mapped the field away. After .map(Transaction::getAmount) the stream holds plain numbers, so .filter(t -> "SUCCESS".equals(t.getStatus())) won't compile: filter first, then map. And never call setters inside map(); that changes the original objects.

Mini exercise 2: for SUCCESS transactions only, return strings like "T1=500.0". Expected: [T1=500.0, T2=120.5, T4=900.0, T6=45.0].

Show answerHide answer
List<String> idAmounts = txns.stream()
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .map(t -> t.getId() + "=" + t.getAmount())
        .collect(Collectors.toList());
// [T1=500.0, T2=120.5, T4=900.0, T6=45.0]

Filter first, while the status is still available, then map.

3. flatMap()

Use it when each element holds a list (or produces several items) and you want one flat stream of all of them: one element in, many out.

How to call it: flatMap(element -> a stream), usually flatMap(List::stream) after mapping to the inner list.

Example 1, nested lists:

List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3), List.of(4, 5));

List<Integer> flat = nested.stream()
        .flatMap(List::stream)
        .collect(Collectors.toList());
// [1, 2, 3, 4, 5]

Example 2, every tag on every transaction:

List<String> allTags = txns.stream()
        .map(Transaction::getTags)
        .filter(Objects::nonNull)        // T4 has no tags
        .flatMap(List::stream)
        .collect(Collectors.toList());
// [salary, rent, monthly, bills, rent, monthly]

It also splits text: Stream.of("rent,bills", "salary").flatMap(s -> Arrays.stream(s.split(","))) gives [rent, bills, salary].

Common mistake: using map() instead, which gives a stream of lists (List<List<String>>). And skipping the null filter: T4's null tag list makes flatMap(t -> t.getTags().stream()) throw NullPointerException.

Mini exercise 3: return every tag used on DEBIT transactions, duplicates included. Expected: [rent, monthly, bills, rent, monthly].

Show answerHide answer
List<String> debitTags = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .map(Transaction::getTags)
        .filter(Objects::nonNull)
        .flatMap(List::stream)
        .collect(Collectors.toList());
// [rent, monthly, bills, rent, monthly]

No DEBIT transaction here has null tags, but keep the null filter anyway; the next data set might have one.

4. distinct()

Removes duplicates and keeps the first occurrence of each value, in the original order.

How to call it: distinct(), with no arguments. It decides what counts as a duplicate with equals() and hashCode().

Example 1, numbers:

List<Integer> unique = nums.stream()
        .distinct()
        .collect(Collectors.toList());
// [5, 3, 8, 10, 1]

Example 2, the accounts that appear in the data:

List<String> accounts = txns.stream()
        .map(Transaction::getAccountId)
        .distinct()
        .collect(Collectors.toList());
// [ACC-1, ACC-2, ACC-3]

Common mistake: distinct() on your own objects removes nothing unless the class overrides equals() and hashCode(). To dedupe by a field, map to that field first (as above), or keep one object per key with toMap() (section 18).

Mini exercise 4: return the distinct statuses in the order they first appear. Expected: [SUCCESS, FAILED, PENDING].

Show answerHide answer
List<String> statuses = txns.stream()
        .map(Transaction::getStatus)
        .distinct()
        .collect(Collectors.toList());
// [SUCCESS, FAILED, PENDING]

5. sorted()

Sorts the stream: sorted() uses natural order, and sorted(comparator) uses your own rule.

Natural order means numbers smallest first and strings A to Z. Objects with no natural order, like Transaction, always need a comparator (section 6 shows how to build one).

Example 1, numbers and names:

nums.stream().sorted().collect(Collectors.toList());
// [1, 3, 3, 5, 8, 10]

nums.stream().sorted(Comparator.reverseOrder()).collect(Collectors.toList());
// [10, 8, 5, 3, 3, 1]

names.stream().sorted().collect(Collectors.toList());
// [Asha, Ben, Ben, Chen, Dev]

Example 2, transactions by amount, highest first:

List<String> byAmountDesc = txns.stream()
        .sorted(Comparator.comparingDouble(Transaction::getAmount).reversed())
        .map(Transaction::getId)
        .collect(Collectors.toList());
// [T4, T1, T5, T2, T3, T6]

Common mistake: txns.stream().sorted() with no comparator throws ClassCastException (Transaction cannot be cast to Comparable), because Java doesn't know how to order transactions.

Mini exercise 5: return transaction ids sorted by account A to Z, then by amount, highest first, within each account. Expected: [T1, T2, T6, T4, T3, T5].

Show answerHide answer
List<String> sortedIds = txns.stream()
        .sorted(Comparator.comparing(Transaction::getAccountId)
                .thenComparing(Comparator.comparingDouble(Transaction::getAmount).reversed()))
        .map(Transaction::getId)
        .collect(Collectors.toList());
// [T1, T2, T6, T4, T3, T5]

The .reversed() sits inside thenComparing, so only the amount is reversed.

6. Comparator

A Comparator is a sorting rule; build it from fields with Comparator.comparing... instead of writing compare() by hand.

You want Write
Ascending by a field Comparator.comparing(Transaction::getAccountId)
A number field Comparator.comparingDouble(Transaction::getAmount) (also comparingInt, comparingLong)
Descending add .reversed()
A second field for ties .thenComparing(Transaction::getId)
Only the second field descending .thenComparing(Comparator.comparingDouble(Transaction::getAmount).reversed())
Nulls at the end Comparator.comparing(Transaction::getAccountId, Comparator.nullsLast(Comparator.naturalOrder()))
Natural or reverse order Comparator.naturalOrder(), Comparator.reverseOrder()

Example 1, names by length, then A to Z:

names.stream()
        .sorted(Comparator.comparingInt(String::length).thenComparing(Comparator.naturalOrder()))
        .collect(Collectors.toList());
// [Ben, Ben, Dev, Asha, Chen]

Example 2, a business order (PENDING first, then FAILED, then SUCCESS; ties by id):

static int rank(String status) {
    if ("PENDING".equals(status)) return 0;
    if ("FAILED".equals(status)) return 1;
    return 2;
}

txns.stream()
        .sorted(Comparator.comparingInt((Transaction t) -> rank(t.getStatus()))
                .thenComparing(Transaction::getId))
        .map(t -> t.getId() + ":" + t.getStatus())
        .collect(Collectors.toList());
// [T5:PENDING, T3:FAILED, T1:SUCCESS, T2:SUCCESS, T4:SUCCESS, T6:SUCCESS]

The lambda is written (Transaction t) -> because it starts a chain; without the type, Java can't tell what t is and the code won't compile.

Common mistake: a .reversed() at the end of a chain flips every field. comparingInt(String::length).thenComparing(Comparator.naturalOrder()).reversed() gives [Chen, Asha, Dev, Ben, Ben]: longest first, but also Z to A. And never write (a, b) -> a - b or cast a difference to int.

Mini exercise 6: sort the names longest first, then A to Z. Expected: [Asha, Chen, Ben, Ben, Dev].

Show answerHide answer
List<String> byLengthDesc = names.stream()
        .sorted(Comparator.comparingInt(String::length).reversed()
                .thenComparing(Comparator.naturalOrder()))
        .collect(Collectors.toList());
// [Asha, Chen, Ben, Ben, Dev]

Here .reversed() comes before thenComparing, so it flips only the length rule.

7. limit() / skip()

limit(n) keeps the first n elements and skip(n) drops the first n; after sorted(), they give you "top N" and paging.

Both are safe when the stream has fewer elements than n: limit(100) on 6 elements simply returns all 6.

Example 1, numbers:

nums.stream().limit(3).collect(Collectors.toList());   // [5, 3, 8]
nums.stream().skip(4).collect(Collectors.toList());    // [10, 1]

Example 2, the top 2 transactions by amount, and page 2 of the ids (2 per page):

List<String> top2 = txns.stream()
        .sorted(Comparator.comparingDouble(Transaction::getAmount).reversed())
        .limit(2)
        .map(Transaction::getId)
        .collect(Collectors.toList());
// [T4, T1]

List<String> page2 = txns.stream()
        .map(Transaction::getId)
        .skip(2)        // skip page 1
        .limit(2)       // take one page
        .collect(Collectors.toList());
// [T3, T4]

For page p (starting at 1) of size s: .skip((long) (p - 1) * s).limit(s).

Common mistake: the order matters. limit(3) before sorted() takes the first 3 and then sorts them: nums.stream().limit(3).sorted(Comparator.reverseOrder()) gives [8, 5, 3], while the real top 3 is [10, 8, 5] (sorted first, then limit).

Mini exercise 7: return the 3 smallest DEBIT amounts, smallest first. Expected: [45.0, 75.25, 120.5].

Show answerHide answer
List<Double> smallestDebits = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .map(Transaction::getAmount)
        .sorted()
        .limit(3)
        .collect(Collectors.toList());
// [45.0, 75.25, 120.5]

Sort first, then limit; the other way round would take the first three debits in list order.

Terminal operations that return one value

8. count()

Returns how many elements reach the end of the stream, as a long.

Example 1:

long bigCount = nums.stream()
        .filter(n -> n > 4)
        .count();
// 3

Example 2:

long successCount = txns.stream()
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .count();
// 4

Common mistake: int c = stream.count(); doesn't compile, because count() returns long. Also, collect(Collectors.toList()).size() builds a whole list just to count it, where count() is simpler. To count per group, use groupingBy(..., counting()) (section 19).

Mini exercise 8: how many different accounts have at least one DEBIT? Expected: 3.

Show answerHide answer
long debitAccounts = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .map(Transaction::getAccountId)
        .distinct()
        .count();
// 3

9. sum()

sum() exists only on number streams, so first convert with mapToInt(), mapToLong() or mapToDouble().

Example 1:

int total = nums.stream()
        .mapToInt(Integer::intValue)
        .sum();
// 30

Example 2, the total of successful debits:

double successfulDebitTotal = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .mapToDouble(Transaction::getAmount)
        .sum();
// 165.5   (T2 120.50 + T6 45.00)

The sum of an empty stream is 0. To sum per group, use groupingBy(..., summingDouble(...)) (section 19).

Common mistake: .map(Transaction::getAmount).sum() doesn't compile, because Stream<Double> has no sum(). And mapToInt(t -> (int) t.getAmount()) silently drops the pence: 1940 instead of 1940.75 for all six transactions.

Mini exercise 9: the total amount of successful CREDIT transactions. Expected: 1400.0.

Show answerHide answer
double successfulCredits = txns.stream()
        .filter(t -> "CREDIT".equals(t.getType()))
        .filter(t -> "SUCCESS".equals(t.getStatus()))
        .mapToDouble(Transaction::getAmount)
        .sum();
// 1400.0   (T1 500.00 + T4 900.00)

10. average()

average() on a number stream returns an OptionalDouble, because an empty stream has no average.

Example 1:

double avg = nums.stream()
        .mapToInt(Integer::intValue)
        .average()          // OptionalDouble[5.0]
        .orElse(0.0);
// 5.0

Example 2, the average amount for ACC-2:

double acc2Average = txns.stream()
        .filter(t -> "ACC-2".equals(t.getAccountId()))
        .mapToDouble(Transaction::getAmount)
        .average()
        .orElse(0.0);
// 487.625   ((75.25 + 900.00) / 2)

Common mistake: .getAsDouble() on an empty result throws NoSuchElementException: No value present, for example for an account that doesn't exist. Use orElse(...), or return the OptionalDouble and let the caller decide. The result is always a double, even for whole numbers: 5.0, not 5.

Mini exercise 10: the average DEBIT amount, or 0.0 if there are none. Expected: 135.1875.

Show answerHide answer
double averageDebit = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .mapToDouble(Transaction::getAmount)
        .average()
        .orElse(0.0);
// 135.1875   (540.75 / 4)

11. max() / min()

Return the largest or smallest element by a comparator, wrapped in an Optional because the stream might be empty.

Example 1:

nums.stream().max(Comparator.naturalOrder());       // Optional[10]
nums.stream().min(Comparator.naturalOrder());       // Optional[1]
nums.stream().mapToInt(Integer::intValue).max();    // OptionalInt[10]

Example 2:

Optional<Transaction> biggest = txns.stream()
        .max(Comparator.comparingDouble(Transaction::getAmount));
// Optional[T4]   (900.00)

String smallestDebitId = txns.stream()
        .filter(t -> "DEBIT".equals(t.getType()))
        .min(Comparator.comparingDouble(Transaction::getAmount))
        .map(Transaction::getId)
        .orElse("NONE");
// T6   (45.00)

Common mistake: calling .get() straight away, which throws NoSuchElementException when nothing matched. Also mixing up the direction: "oldest" is min() of a date and "newest" is max().

Mini exercise 11: return the id of the largest transaction that is PENDING or FAILED, or "NONE". Expected: T5.

Show answerHide answer
String largestProblem = txns.stream()
        .filter(t -> "PENDING".equals(t.getStatus()) || "FAILED".equals(t.getStatus()))
        .max(Comparator.comparingDouble(Transaction::getAmount))
        .map(Transaction::getId)
        .orElse("NONE");
// T5   (300.00 beats T3's 75.25)

12. findFirst() / findAny()

Return the first element that reaches the end of the stream, as an Optional, and stop as soon as one is found.

findFirst() respects the list order. findAny() may return any match; it exists for parallel streams, so use findFirst() whenever the answer must be predictable.

Example 1:

nums.stream().filter(n -> n > 6).findFirst();     // Optional[8]
nums.stream().filter(n -> n > 100).findFirst();   // Optional.empty

Example 2, the first FAILED transaction:

String firstFailedId = txns.stream()
        .filter(t -> "FAILED".equals(t.getStatus()))
        .findFirst()
        .map(Transaction::getId)
        .orElse("NONE");
// T3

Common mistake: .findFirst().get() throws NoSuchElementException when nothing matches. Also, findFirst() throws NullPointerException if the element it finds is null.

Mini exercise 12: find the first transaction of ACC-3 and return its status, or "NOT FOUND". Expected: PENDING.

Show answerHide answer
String acc3Status = txns.stream()
        .filter(t -> "ACC-3".equals(t.getAccountId()))
        .findFirst()
        .map(Transaction::getStatus)
        .orElse("NOT FOUND");
// PENDING

13. anyMatch() / allMatch() / noneMatch()

Yes/no questions about the stream; each returns a boolean and stops as soon as the answer is known.

Method True when
anyMatch(test) at least one element passes
allMatch(test) every element passes
noneMatch(test) no element passes

Example 1:

nums.stream().anyMatch(n -> n > 9);    // true  (10)
nums.stream().allMatch(n -> n > 0);    // true
nums.stream().noneMatch(n -> n < 0);   // true

Example 2:

boolean anyFailed    = txns.stream().anyMatch(t -> "FAILED".equals(t.getStatus()));   // true
boolean allPositive  = txns.stream().allMatch(t -> t.getAmount() > 0);                 // true
boolean noneOver1000 = txns.stream().noneMatch(t -> t.getAmount() > 1000);             // true

Common mistake: allMatch() and noneMatch() return true for an empty stream, so "every payment succeeded" is also true when there were no payments; check for empty first. And filter(...).count() > 0 works but scans everything, while anyMatch() stops at the first hit.

Mini exercise 13: does every transaction of ACC-1 have status SUCCESS? Expected: true (and false for ACC-2).

Show answerHide answer
boolean acc1AllSuccess = txns.stream()
        .filter(t -> "ACC-1".equals(t.getAccountId()))
        .allMatch(t -> "SUCCESS".equals(t.getStatus()));
// true; the same check for ACC-2 gives false because of T3

An account with no transactions at all would also give true, so check for empty first when that matters.

14. reduce()

Combines all elements into one value by applying an operation again and again, such as adding two numbers.

Two forms:

  • reduce(identity, operation) returns a plain value. The identity is the starting value and also the answer for an empty stream: 0 for sums, 1 for products.
  • reduce(operation) returns an Optional, because an empty stream has no answer.

Example 1:

nums.stream().reduce(0, Integer::sum);           // 30
nums.stream().reduce(1, (a, b) -> a * b);        // 3600
nums.stream().reduce(Integer::max);              // Optional[10]

Example 2, the total of all amounts, and the money-safe version:

double total = txns.stream()
        .map(Transaction::getAmount)
        .reduce(0.0, Double::sum);
// 1940.75

BigDecimal exactTotal = txns.stream()
        .map(t -> BigDecimal.valueOf(t.getAmount()))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
// 1940.75

reduce is how you add up BigDecimal values, because there's no BigDecimal stream with a sum().

Common mistake: a wrong identity changes the answer, so nums.stream().reduce(10, Integer::sum) gives 40, not 30. When sum(), max() or count() exist, prefer them; they're clearer.

Mini exercise 14: using reduce, return the longest name; the first one wins a tie. Expected: Optional[Asha].

Show answerHide answer
Optional<String> longest = names.stream()
        .reduce((a, b) -> b.length() > a.length() ? b : a);
// Optional[Asha]

Using > rather than >= keeps the earlier name on a tie, so Asha beats Chen.

Optional

15. Optional

An Optional is a box that holds one value or nothing; findFirst(), max(), min() and reduce(op) return one, so you must decide what "nothing" means.

Method What it does
isPresent(), isEmpty() check whether a value is there (isEmpty() is Java 11+)
ifPresent(x -> ...) run code only when a value is there
map(f) transform the value if present; empty stays empty
filter(test) keep the value only if it passes
orElse(default) the value, or a default (the default is always evaluated)
orElseGet(() -> default) the value, or a default computed only when needed
orElseThrow(() -> new SomeException(...)) the value, or an exception
Optional.ofNullable(x) wrap a value that might be null

Example 1:

Optional<String> c = names.stream().filter(n -> n.startsWith("C")).findFirst();

c.isPresent();                      // true

19. groupingBy()

Collectors.groupingBy() puts elements into groups by a key. By default each group is a List, and a second collector (the downstream collector) changes what each group holds.

Example 1:

Map<Integer, List<String>> byLength = names.stream()
        .collect(Collectors.groupingBy(String::length));
// {3=[Ben, Ben, Dev], 4=[Asha, Chen]}

Example 2:

Map<String, List<String>> idsByAccount = txns.stream()
        .collect(Collectors.groupingBy(
                Transaction::getAccountId,
                TreeMap::new,                                                  // sorted keys
                Collectors.mapping(Transaction::getId, Collectors.toList())));
// {ACC-1=[T1, T2, T6], ACC-2=[T3, T4], ACC-3=[T5]}

        .collect(Collectors.groupingBy(Transaction::getStatus, Collectors.counting()));
// {SUCCESS=4, FAILED=1, PENDING=1}   (order not guaranteed)

The three-argument form takes the key, the map type, then the downstream collector; use it when you want the keys sorted.

Downstream collectors, grouped by account unless noted:

Downstream collector Each group becomes Result on the sample data
none List<Transaction> {ACC-1=[T1, T2, T6], ACC-2=[T3, T4], ACC-3=[T5]}
counting() Long {ACC-1=3, ACC-2=2, ACC-3=1}

averagingDouble(Transaction::getAmount) an average by type: {CREDIT=700.0, DEBIT=135.1875}
mapping(Transaction::getId, Collectors.toList()) a list of one field {ACC-1=[T1, T2, T6], ACC-2=[T3, T4], ACC-3=[T5]}

Common mistakes:

  • A group with no elements has no key at all: countByStatus.get("CANCELLED") returns null, and unboxing it into a long throws NullPointerException. Use getOrDefault("CANCELLED", 0L).

21. Streaming a Map: Map → List

A Map has no stream() method, so stream one of its three views: entrySet() for keys and values together, keySet() for keys, values() for values.

Example 1:

        .filter(e -> e.getValue() > 0)
        .map(Map.Entry::getKey)
        .sorted()
        .collect(Collectors.toList());
// [apple, fig]

Example 2, accounts ranked by total, highest first:

        .collect(Collectors.groupingBy(Transaction::getAccountId,
                 Collectors.summingDouble(Transaction::getAmount)));

// 1940.75

For sorting entries, use Map.Entry.comparingByKey() and Map.Entry.comparingByValue(), each optionally with a comparator such as Comparator.reverseOrder().

Part 2

Bug-fix patterns

Thirty-three bugs that come up in live bug-fix rounds. Find the bug in the code first, then open the fix and the rule behind it.

How to use this guide

Every pattern has the same parts: a task, the buggy code, and a hidden fix with the rule behind it. Read the buggy code, name the bug out loud, then tap Show the fix.

Code targets Java 11+ and uses only the standard library. Amounts are double to keep the stream code readable; pattern 32 shows why real banking code uses BigDecimal.

The 60-second bug-hunt checklist

Run these ten questions against any method before you change a line.

  1. Inputs: can the list, an element, or a field be null? What happens with an empty list or a single item?
  2. Conditions: is every > / >= right at the exact boundary value? Are && and || grouped the way the rule says?
  3. Loops and indexes: does the loop stop at size() - 1? Can get() or subList() go out of range?
  4. Equality: is == used on String or Integer? Does the class override both equals() and hashCode()?
  5. Maps: can a key repeat? What does get() return for a key that is missing?
  6. Streams: is the stream result actually used? Does get() or getAsDouble() assume a value exists?
  7. Ordering and mutation: does the result need an order? Does the method change the caller's list?
  8. Numbers: integer division, (int) casts, overflow, double used for money?
  9. Exceptions: is anything swallowed, or caught too broadly?
  10. Dates: are range ends inclusive or exclusive? Which time zone? Is now() called inside the logic?

Part A: the 20 core patterns

1. equals() / hashCode()

Task: two Customer objects with the same id are the same customer, so a HashSet should hold only one.

class Customer {
    private final String id;
    private final String name;
    // constructor and getters omitted

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Customer)) return false;
        Customer other = (Customer) o;
        return id.equals(other.id);
    }
}

Set<Customer> customers = new HashSet<>();
customers.add(new Customer("C1", "Asha"));
customers.add(new Customer("C1", "Asha"));
customers.size();   // 2, expected 1
Show the fixHide the fix

If you override equals(), override hashCode() with the same fields, or hash-based collections keep "duplicates".

Fix:

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Customer)) return false;
    Customer other = (Customer) o;
    return Objects.equals(id, other.id);   // null-safe
}

@Override
public int hashCode() {
    return Objects.hash(id);               // same field(s) as equals()
}

Why: a HashSet or HashMap uses hashCode() to pick a bucket first, and only calls equals() inside that bucket. Without hashCode(), each object gets an identity hash, lands in a different bucket, and equals() is never called.

Also watch for:

  • public boolean equals(Customer other) is an overload, not an override, so collections ignore it and the set still holds 2. Always equals(Object o) with @Override.
  • Don't use mutable fields in hashCode() for objects stored in sets or used as map keys. If the field changes after insertion, contains() returns false.

Test with: same id with a different name, a null id, the same instance added twice, the object used as a HashMap key.

2. List → Map with a loop

Task: group transactions by account.

Map<String, List<Transaction>> byAccount = new HashMap<>();
for (Transaction t : transactions) {
    List<Transaction> list = new ArrayList<>();
    list.add(t);
    byAccount.put(t.getAccountId(), list);
}
// ACC-1 had T1 and T2, but the map holds only [T2]
Show the fixHide the fix

When you build a map of lists or counts in a loop, use computeIfAbsent() or merge(); a plain put() overwrites what was there.

Fix:

Map<String, List<Transaction>> byAccount = new HashMap<>();
for (Transaction t : transactions) {
    byAccount.computeIfAbsent(t.getAccountId(), k -> new ArrayList<>()).add(t);
}

Same family, counting per key:

// BUG: get() returns null the first time an account appears → null + 1 → NullPointerException
counts.put(t.getAccountId(), counts.get(t.getAccountId()) + 1);

// Fix
counts.merge(t.getAccountId(), 1, Integer::sum);
// or: counts.put(id, counts.getOrDefault(id, 0) + 1);

Why: put() always replaces the existing value. computeIfAbsent() creates the list only for a new key and returns the existing list otherwise. merge() inserts 1 for a new key, or adds 1 to the old value.

Stream equivalent: groupingBy(Transaction::getAccountId) (pattern 6). Test with: one account with several transactions, an empty list.

3. Map → List

Task: return the 3 accounts with the highest balance, highest first.

List<String> top3(Map<String, Double> balances) {
    List<String> result = new ArrayList<>(balances.keySet());
    return result.subList(0, 3);
}
Show the fixHide the fix

A HashMap has no order, so "the first N keys" means nothing; sort the entries, then limit().

Fix:

List<String> top3(Map<String, Double> balances) {
    return balances.entrySet().stream()
            .sorted(Map.Entry.comparingByValue(Comparator.reverseOrder()))
            .limit(3)
            .map(Map.Entry::getKey)
            .collect(Collectors.toList());
}

Why: streaming over entrySet() keeps each key next to its value while you sort. limit(3) is safe when only 2 entries exist, while subList(0, 3) throws IndexOutOfBoundsException: toIndex = 3.

Also watch for:

  • Ties: if equal balances must come out in a fixed order, add a key tie-breaker. It needs a type hint: Map.Entry.<String, Double>comparingByValue(Comparator.reverseOrder()).thenComparing(Map.Entry.comparingByKey()).
  • keySet(), values() and entrySet() are live views of the map. Copy them with new ArrayList<>(...) before you change either side.

Test with: an empty map, fewer than 3 entries, ties, a null balance (comparingByValue throws on null).

4. toMap()

Task: build a lookup of transaction id → currency. Some old records have no currency.

Map<String, String> currencyById = transactions.stream()
        .collect(Collectors.toMap(Transaction::getId, Transaction::getCurrency));
// NullPointerException as soon as one currency is null
Show the fixHide the fix

Collectors.toMap() throws NullPointerException if any value is null, even though a plain HashMap accepts null values.

Fix: decide what a missing value means, then say it in code.

// Option A: skip records with no currency
Map<String, String> currencyById = transactions.stream()
        .filter(t -> t.getCurrency() != null)
        .collect(Collectors.toMap(Transaction::getId, Transaction::getCurrency));

// Option B: keep them with a default
Map<String, String> currencyById = transactions.stream()
        .collect(Collectors.toMap(
                Transaction::getId,
                t -> t.getCurrency() == null ? "UNKNOWN" : t.getCurrency()));

Why: toMap() rejects null values internally, so one bad record kills the whole collect(). If you truly need null values in the map, use a plain loop with HashMap.put().

Also: toMap() promises no key order. If order matters, use the 4-argument form with LinkedHashMap::new (insertion order) or TreeMap::new (sorted), shown in pattern 5.

Test with: a null value, an empty list, a repeated id (pattern 5).

5. Duplicate keys in toMap()

Task: keep the latest transaction for each account.

Map<String, Transaction> latestByAccount = transactions.stream()
        .collect(Collectors.toMap(Transaction::getAccountId, t -> t));
// IllegalStateException: Duplicate key ACC-1 (attempted merging values ...)
Show the fixHide the fix

Before every toMap(), ask "can this key repeat?" If yes, you need a merge function, and it has to match the business rule.

The tempting fix is still wrong:

.collect(Collectors.toMap(Transaction::getAccountId, t -> t, (a, b) -> b));
// keeps the LAST one in the list, which is the latest only if the list is sorted by time

Fix:

Map<String, Transaction> latestByAccount = transactions.stream()
        .collect(Collectors.toMap(
                Transaction::getAccountId,
                t -> t,
                (a, b) -> b.getTimestamp().isAfter(a.getTimestamp()) ? b : a));

Pick the merge function from the rule:

Rule Merge function
Total per key Double::sum
Keep the first seen (a, b) -> a
Keep the latest by time (a, b) -> b.getTimestamp().isAfter(a.getTimestamp()) ? b : a
Keep the largest BinaryOperator.maxBy(Comparator.comparingDouble(Transaction::getAmount))
Need every value not toMap(): use groupingBy() (pattern 6)

Need sorted keys as well: Collectors.toMap(Transaction::getAccountId, Transaction::getAmount, Double::sum, TreeMap::new).

Test with: two transactions for one account in reverse time order, a single transaction, equal timestamps.

6. groupingBy / partitioningBy

Task: show the number of FAILED transactions on a dashboard.

Map<String, Long> countByStatus = transactions.stream()
        .collect(Collectors.groupingBy(Transaction::getStatus, Collectors.counting()));

long failed = countByStatus.get("FAILED");   // NullPointerException on a day with no failures
Show the fixHide the fix

groupingBy() only creates keys that actually occur, so a group with zero items has no key and get() returns null.

Fix:

long failed = countByStatus.getOrDefault("FAILED", 0L);

For a yes/no split, partitioningBy() always returns both keys, even when one side is empty:

Map<Boolean, Long> bySize = transactions.stream()
        .collect(Collectors.partitioningBy(t -> t.getAmount() >= 10_000, Collectors.counting()));
// {false=4, true=0}, so bySize.get(true) is safe

Also watch for:

  • A null classifier result (a null status) throws NullPointerException: element cannot be mapped to a null key. Filter nulls first, or map them to "UNKNOWN".
  • counting() returns Long, so assigning to Map<String, Integer> won't compile.
  • Pick the downstream collector from the question: counting(), summingDouble(), averagingDouble(), mapping(f, Collectors.toList()), or maxBy(cmp), which gives an Optional per group.

Test with: a status that never occurs, a null status, an empty list.

7. filter

Task: keep only successful transactions.

List<Transaction> successfulOnly(List<Transaction> transactions) {
    transactions.stream().filter(t -> "SUCCESS".equals(t.getStatus()));
    return transactions;   // still has FAILED and PENDING
}
Show the fixHide the fix

Streams never change the list they came from; if you don't collect the result, the filter did nothing.

Fix:

List<Transaction> successfulOnly(List<Transaction> transactions) {
    return transactions.stream()
            .filter(t -> "SUCCESS".equals(t.getStatus()))
            .collect(Collectors.toList());
}

Why: filter() returns a new stream, and nothing runs until a terminal operation such as collect(). To change the list in place, use transactions.removeIf(t -> !"SUCCESS".equals(t.getStatus())), but only when the caller expects their list to change.

Also watch for:

  • Write string checks as "SUCCESS".equals(t.getStatus()). The literal on the left can never be null.
  • Two .filter() calls in a row mean AND. An OR rule must sit inside one filter: .filter(t -> isA(t) || isB(t)).
  • removeIf() on List.of(...) throws UnsupportedOperationException, even when nothing matches.

Test with: no successful transactions, a null status, an immutable input list.

8. map

Task: show amounts in USD (rate 1.25) without touching the stored GBP data.

List<Transaction> toUsd(List<Transaction> transactions) {
    return transactions.stream()
            .map(t -> { t.setAmount(t.getAmount() * 1.25); return t; })
            .collect(Collectors.toList());
}
// Call it twice: the stored 100.0 becomes 156.25
Show the fixHide the fix

map() should turn each element into a new value; calling setters inside map() corrupts the original data.

Fix:

List<Double> toUsd(List<Transaction> transactions) {
    return transactions.stream()
            .map(t -> t.getAmount() * 1.25)    // a new value; the original stays 100.0
            .collect(Collectors.toList());
}

Why: the stream holds references to the same objects the caller owns, so a setter inside map() edits shared data. If the caller needs whole objects, build new ones (a DTO or a copy) inside map().

Also watch for:

  • map(Transaction::getAmount) gives Stream<Double>, which has no sum(). Use mapToDouble() for number work.
  • Filter before you map away the fields you need: after .map(Transaction::getAmount), the status is gone.
  • map() is one in, one out. One in, many out is flatMap() (pattern 9).

Test with: calling the method twice on the same list, then checking the original amounts.

13. Comparator: business ordering

Task: the support queue shows PENDING first, then FAILED, then SUCCESS. Unknown or missing statuses go last.

// gives FAILED, PENDING, SUCCESS, and a null status throws NullPointerException
Show the fixHide the fix

Alphabetical order is rarely the business order; when the spec gives a priority, encode it explicitly.

Fix:

private static int priority(String status) {
    if ("PENDING".equals(status)) return 0;
    if ("FAILED".equals(status))  return 1;
    if ("SUCCESS".equals(status)) return 2;
    return 3;                                   // unknown or null go last
}

transactions.sort(Comparator.comparingInt(t -> priority(t.getStatus())));
// PENDING, FAILED, SUCCESS, null

Why: comparing(Transaction::getStatus) uses String's natural, alphabetical order. A rank function makes the rule visible, handles null safely, and puts unknown values somewhere on purpose. In production code an enum with a priority field does the same job.

Also watch for:

  • List.of(...).indexOf(null) and Map.of(...).get(null) throw NullPointerException, so rank lookups built on them break on a null status.
  • Highest first is .reversed(), for example Comparator.comparingDouble(Transaction::getAmount).reversed().

14. Multi-field comparator

Task: sort by account A→Z, then by amount, highest first.

        .thenComparingDouble(Transaction::getAmount)
        .reversed());
// ACC-2 500, ACC-2 50, ACC-1 300, ACC-1 100
Show the fixHide the fix

A .reversed() at the end of a chain reverses every field in it; reverse a single field inside its own thenComparing().

The accounts came out Z→A as well, not just the amounts.

Fix:

        .thenComparing(Comparator.comparingDouble(Transaction::getAmount).reversed()));
// ACC-1 300, ACC-1 100, ACC-2 500, ACC-2 50

18. Duplicate records

Task: upstream sometimes sends the same transaction twice (same id). Keep the first occurrence and the original order.

20. Fix a method so all hidden edge cases pass

Task: for each account, return the average amount of SUCCESSFUL DEBIT transactions, rounded to 2 decimals, sorted by account id.

    Map<String, Double> result = new HashMap<>();
    for (Transaction t : transactions) {
        if (t.getType() == "DEBIT") {
            result.put(t.getAccountId(), (result.get(t.getAccountId()) + t.getAmount()) / 2);
        }
    }
    return result;
}
Show the fixHide the fix

Hidden tests hit the same dozen cases every time; list them before you touch the code, then fix everything in one pass.

Bugs, in the order you would say them:

  1. t.getType() == "DEBIT" compares references. It passes with literal test data and fails with strings read from a database or JSON.
  2. result.get(...) is null the first time, so the addition throws NullPointerException.
  3. (old + new) / 2 is not an average: for 10, 20, 60 it gives 37.5 instead of 30.

            .filter(t -> "SUCCESS".equals(t.getStatus()))

                    Transaction::getAccountId,
                    TreeMap::new,                                         // sorted keys

21. Wrong condition: && vs ||

Task: retry a transaction unless it is SUCCESS or CANCELLED.

boolean shouldRetry(Transaction t) {
    return !t.getStatus().equals("SUCCESS") || !t.getStatus().equals("CANCELLED");
}
// shouldRetry() returns true even for a SUCCESS payment
Show the fixHide the fix

To negate "A or B" you need "not A and not B"; read every compound condition aloud with one concrete value.

The condition is always true, so a SUCCESS payment gets retried: a double charge.

Fix:

boolean shouldRetry(Transaction t) {
    return !"SUCCESS".equals(t.getStatus()) && !"CANCELLED".equals(t.getStatus());
}

Why: De Morgan's law says !(A || B) equals !A && !B. Plug in SUCCESS: "not SUCCESS" is false, "not CANCELLED" is true, and false OR true is true. One concrete value exposes the bug in seconds.

Also watch for:

  • && binds tighter than ||, so a || b && c means a || (b && c). Add brackets whenever you mix them.
  • Set.of("SUCCESS", "CANCELLED").contains(status) reads well but throws NullPointerException for a null status.
  • Inverted checks copied from a neighbouring line: if (!isValid) vs if (isValid), < vs >.

Test with: every status once, plus null.

22. Off-by-one

Task: return the last N transactions from a list sorted oldest to newest.

List<Transaction> lastN(List<Transaction> transactions, int n) {
    List<Transaction> result = new ArrayList<>();
    for (int i = transactions.size() - n; i <= transactions.size(); i++) {
        result.add(transactions.get(i));
    }
    return result;
}
// 5 items, n = 2: IndexOutOfBoundsException, index 5 for length 5
// 5 items, n = 7: index -2
Show the fixHide the fix

Valid indexes run from 0 to size() - 1, and subList(from, to) excludes to; clamp both ends.

Fix:

List<Transaction> lastN(List<Transaction> transactions, int n) {
    if (n <= 0) {
        return new ArrayList<>();
    }
    int start = Math.max(0, transactions.size() - n);
    return new ArrayList<>(transactions.subList(start, transactions.size()));
}
// n = 2 gives [T4, T5]; n = 7 gives all 5; an empty list gives []

Why: index loops use i < size(), and <= runs one past the end. Math.max(0, ...) clamps the start when n is bigger than the list. Copying the subList() into a new ArrayList detaches the result from the caller's list (pattern 25).

Quick rules: n items run i = 0; i < n. The last element is get(size() - 1). "First k" is subList(0, Math.min(k, size())). A page numbered from 1 starts at index (page - 1) * pageSize.

Test with: n = 0, n = 1, n = size, n > size, negative n, an empty list.

25. Mutation bug

26. Incorrect comparator

Task: sort transactions by amount, smallest first.

transactions.sort((a, b) -> (int) (a.getAmount() - b.getAmount()));
// Result: [10.75, 10.25], not ascending
Show the fixHide the fix

A comparator must return a consistent negative, zero or positive; never subtract or cast, use Double.compare, Integer.compare or Comparator.comparing*.

10.75 and 10.25 differ by 0.5, and (int) 0.5 is 0, so the comparator calls them equal.

Fix:

// or (a, b) -> Double.compare(a.getAmount(), b.getAmount())

    return allOk ? "COMPLETE" : "INCOMPLETE";
}

Why: logically, "all of zero items" is vacuously true. noneMatch() is also true on empty input, and anyMatch() is false. Any rule phrased "all", "none" or "every" needs an explicit empty check.

Related: reduce(Double::sum) without an identity returns Optional.empty on empty input, while reduce(0.0, Double::sum) returns 0.0. The full table is in pattern 16.

Test with: an empty batch, a null batch, one FAILED item, all SUCCESS.

29. Incorrect exception handling

Task: total the amount column (third field) of an uploaded CSV. A bad row must not hide problems.

    try {
        for (String row : rows) {
            String[] cols = row.split(",");
            total += Double.parseDouble(cols[2]);
        }

// Returns 10.5, expected 15.75, and reports nothing
Show the fixHide the fix

Catch the specific exception, as close to the risky line as possible, and never swallow it silently.

Row 2 stops the loop, row 4 is never read, and nobody is told.

Fix (skip bad rows and report them):

double totalFromCsv(List<String> rows, List<String> errors) {
    double total = 0;
    for (int i = 0; i < rows.size(); i++) {
        String[] cols = rows.get(i).split(",");
        if (cols.length < 3) {                       // a check, not an exception
            errors.add("Row " + (i + 1) + ": expected 3 columns, got " + cols.length);
            continue;
        }
        try {
            total += Double.parseDouble(cols[2].trim());
        } catch (NumberFormatException e) {          // only the failure we expect
            errors.add("Row " + (i + 1) + ": invalid amount '" + cols[2] + "'");
        }
    }
    return total;
}
// Returns 15.75; errors = [Row 2: invalid amount 'abc', Row 3: expected 3 columns, got 2]

If the business wants all-or-nothing instead, fail fast and keep the cause: throw new InvalidFileException("Row " + (i + 1) + " has an invalid amount", e);.

Rules:

  • Catch the narrowest type (NumberFormatException). Catching Exception also hides real bugs such as NullPointerException.
  • Put the try around the risky line; a try around the whole loop turns one bad row into a silent stop.
  • When you wrap an exception, pass the original as the cause.
  • Log or record context: which row, which id, which value.
  • Close resources with try-with-resources, and never return from a finally block, because it swallows the exception.

Test with: a non-numeric amount, a short row, an empty file, spaces around numbers (Double.parseDouble(" 5.25") works, but Integer.parseInt(" 5") throws).

30. Date and time handling

Task: return all transactions on a given date.

Show the fixHide the fix

Use half-open ranges [start, next start), store moments as Instant, and format years with yyyy, never YYYY.

Fix:

List<Transaction> onDate(List<Transaction> transactions, LocalDate date) {
    LocalDateTime start = date.atStartOfDay();
    LocalDateTime nextDay = date.plusDays(1).atStartOfDay();
    return transactions.stream()
            .filter(t -> !t.getTimestamp().isBefore(start)      // start included
                      && t.getTimestamp().isBefore(nextDay))    // next day excluded
            .collect(Collectors.toList());
}
// Simpler for one day: t.getTimestamp().toLocalDate().equals(date)

31. Integer == trap

Task: flag two accounts that have the same number of transactions.

Map<String, Integer> counts = ...;                   // {ACC-1=500, ACC-2=500}
if (counts.get("ACC-1") == counts.get("ACC-2")) {   // false, even though both are 500
    flagSameActivity();
}
Show the fixHide the fix

== on Integer, Long or String compares object references; for integers it happens to work from -128 to 127 because those values are cached, then fails.

What Java actually does:

Integer a = 127, b = 127;
a == b;        // true: both come from the cache
Integer c = 1000, d = 1000;
c == d;        // false: two different objects
c.equals(d);   // true

Fix:

if (Objects.equals(counts.get("ACC-1"), counts.get("ACC-2"))) {   // compares values, null-safe
    flagSameActivity();
}

Why: autoboxing reuses cached objects for small values only, so tests with small numbers pass and production numbers fail. Long behaves the same way. String has the same problem: literals are shared, but strings from a database, JSON or new String(...) are separate objects (pattern 20).

Also: unboxing a null Integer into an int (int n = counts.get("ACC-9");) throws NullPointerException.

Test with: values above 127, a missing key, strings built at runtime.

33. Removing from a list while looping over it

Task: remove FAILED transactions from a working list.

for (Transaction t : transactions) {
    if ("FAILED".equals(t.getStatus())) {
        transactions.remove(t);
    }
}
Show the fixHide the fix

Never call list.remove() inside a for-each loop over the same list; use removeIf(), an Iterator, or build a new list.

What actually happens:

  • Usually ConcurrentModificationException on the next loop step.
  • Worse: if the removed item is second-to-last, the loop just stops. [A SUCCESS, B FAILED, C FAILED] ends as [A, C], so a FAILED item survives with no error.

The index version fails more quietly:

for (int i = 0; i < transactions.size(); i++) {
    if ("FAILED".equals(transactions.get(i).getStatus())) {
        transactions.remove(i);          // BUG: the next item shifts into slot i and is skipped
    }
}
// [A FAILED, B FAILED, C SUCCESS] ends as [B, C]

Fix:

transactions.removeIf(t -> "FAILED".equals(t.getStatus()));

// or, when each item needs more logic
Iterator<Transaction> it = transactions.iterator();
while (it.hasNext()) {
    if ("FAILED".equals(it.next().getStatus())) {
        it.remove();                     // the iterator's own remove is safe
    }
}

Why: a for-each loop runs a hidden iterator that checks whether the list changed behind its back. Removing by index shifts every later element left by one. Looping backwards by index also works, but removeIf() says what you mean.

Also: maps behave the same way (removing inside a loop over keySet() throws; use map.entrySet().removeIf(...)), and List.of(...) or Collections.unmodifiableList(...) throw UnsupportedOperationException on any removal.

Test with: two FAILED items next to each other, a FAILED item first, a FAILED item last, an immutable list.

    // constructor omitted

    @Override

Bugs to find: 1, and give two reasons it is wrong. Study patterns: 1.

Show answerHide answer

The bug: hashCode() uses balance, a field that equals() ignores and that changes, so contains(acc) returns false after the deposit.

Two reasons it's wrong:

  1. Contract break: two accounts with the same number but different balances are equals() but have different hash codes.
  2. Mutable hash: deposit() changes the hash after insertion, so the set looks in the wrong bucket.

Bugs:

D10. Latest retry per payment id

Task: every retry creates a new row with the same id and a higher retryCount. Keep only the latest attempt for each id, in the order the ids first appeared.

List<Payment> latestAttempts(List<Payment> payments) {

Bugs to find: 2. Hint: input P7 (retry 0), P2, P7 (retry 1), P9, P7 (retry 2) should give P7 (retry 2), P2, P9. Study patterns: 5, 18, 24.

Show answerHide answer

Bugs:

  1. putIfAbsent() keeps the first attempt (retry 0), not the latest.
  2. A HashMap doesn't keep first-seen order; the buggy result came out P2, P7 (retry 0), P9.

Fix:

List<Payment> latestAttempts(List<Payment> payments) {
    Map<String, Payment> byId = new LinkedHashMap<>();    // keeps the first-seen order of ids
    for (Payment p : payments) {

    return new ArrayList<>(byId.values());
}

}

Bugs to find: 4. Hint: with 5 payments and page size 2, pages 1, 2, 3 and 4 should return [P1, P2], [P3, P4], [P5] and []. Study patterns: 17, 22, 25.

Show answerHide answer

Bugs:

  1. Pages start at 1, so from must be (pageNumber - 1) * pageSize; page 1 currently returns P3 and P4.
  2. to can run past the end: page 3 throws IndexOutOfBoundsException: toIndex = 8 instead of returning [P5].
  3. A page past the end must return an empty list, not throw.
  4. No validation: page 0, negative values and a page size of 0 are all accepted.

Bonus point: subList() returns a live view of the caller's list, not a copy (pattern 25).

Fix:

List<Payment> page(List<Payment> payments, int pageNumber, int pageSize) {
    if (pageNumber < 1 || pageSize < 1) {
        throw new IllegalArgumentException("pageNumber and pageSize must be at least 1");
    }
    long from = (long) (pageNumber - 1) * pageSize;   // long: huge inputs can't overflow
    if (from >= payments.size()) {
        return new ArrayList<>();
    }
    int to = (int) Math.min(from + pageSize, payments.size());
    return new ArrayList<>(payments.subList((int) from, to));
}
// pages 1 to 4 with size 2: [P1, P2], [P3, P4], [P5], []

Edge cases: the last partial page, exactly one full page, a page past the end, a page size bigger than the list, very large numbers (in int, (pageNumber - 1) * pageSize can overflow into a negative index).

D12. Retry eligibility

Task: a payment can be retried if its status is REJECTED or PENDING, and its retryCount is less than 3, and it was created within the last 24 hours.

boolean eligibleForRetry(Payment p, LocalDateTime now) {
    return p.getStatus().equals("REJECTED") || p.getStatus().equals("PENDING")
            && p.getRetryCount() <= 3
            && p.getCreatedAt().isAfter(now.minusHours(24));
}

Bugs to find: 3. Hint: what does it return for a REJECTED payment with 10 retries, created 5 days ago? Study patterns: 15, 17, 21.

Show answerHide answer

Bugs:

  1. && binds tighter than ||, so the code means REJECTED OR (PENDING and under the limit and recent). A REJECTED payment with 10 retries from 5 days ago returns true: an endless retry loop.
  2. retryCount <= 3 allows a fourth retry; the rule says less than 3.
  3. p.getStatus().equals(...) throws on a null status, and a null createdAt throws as well.

Fix:

boolean eligibleForRetry(Payment p, LocalDateTime now) {
    boolean retryableStatus = "REJECTED".equals(p.getStatus()) || "PENDING".equals(p.getStatus());
    boolean underLimit = p.getRetryCount() < 3;
    boolean recent = p.getCreatedAt() != null && p.getCreatedAt().isAfter(now.minusHours(24));
    return retryableStatus && underLimit && recent;
}

Named booleans make each rule readable and testable on its own. Ask the interviewer: does a payment created exactly 24 hours ago still count as "within the last 24 hours"?

Edge cases: retryCount 2 and 3, exactly 24 hours old, COMPLETED with 0 retries, a null status.

D13. PaymentService

Task: the service owns its payment list. Callers can read the list, and can ask for the 5 biggest payments without changing anything.

class PaymentService {

    public List<Payment> getPayments() {
        return payments;
    }

    public List<Payment> biggestFive() {
        payments.sort((a, b) -> (int) (b.getAmount() - a.getAmount()));

    }
}

Bugs to find: 4. Study patterns: 25, 26, 22.

Show answerHide answer

Bugs:

  1. getPayments() returns the internal list, so any caller can add, remove or clear() the service's data.
  2. biggestFive() sorts the service's own list, changing the order every other reader sees (and racing with other threads).
  3. (int) (b.getAmount() - a.getAmount()) treats amounts less than 1 apart as equal: 10.75 vs 10.25 gives 0.
  4. subList(0, 5) throws IndexOutOfBoundsException with fewer than 5 payments, and returns a live view rather than a copy.

Fix:

class PaymentService {
    private final List<Payment> payments = new ArrayList<>();

    public List<Payment> getPayments() {
        return Collections.unmodifiableList(payments);    // read-only view
    }

    public List<Payment> biggestFive() {
        return payments.stream()
                .sorted(Comparator.comparingDouble(Payment::getAmount).reversed())
                .limit(5)
                .collect(Collectors.toList());            // a new list; nothing internal changes
    }
}

Edge cases: fewer than 5 payments, amounts a few pence apart, a caller calling clear() on the returned list (it now throws UnsupportedOperationException).

D14. Batch sending

Task: send every payment through the gateway. One failure must not stop the batch, and the caller needs to know which payments failed and why. gateway.send() throws a checked GatewayException on failure.

int processAll(List<Payment> payments, PaymentGateway gateway) {
    int processed = 0;
    try {
        for (Payment p : payments) {
            gateway.send(p);
            processed++;
        }
    } catch (Exception e) {
        System.out.println("error");
    }
    return processed;
}

Bugs to find: 3. Then extend: return a result object holding the succeeded ids and a map of failed id to reason. Study patterns: 29.

Show answerHide answer

Bugs:

  1. The try wraps the whole loop, so the first failure stops every payment after it. With P2 failing, P3 is never sent and the method returns 1.
  2. catch (Exception e) also swallows real bugs such as NullPointerException.
  3. Nothing records which payment failed or why; printing "error" loses the id, the message and the stack trace.

Fix, with the extension:

class BatchResult {
    final List<String> succeeded = new ArrayList<>();
    final Map<String, String> failed = new LinkedHashMap<>();   // payment id -> reason
}

BatchResult processAll(List<Payment> payments, PaymentGateway gateway) {
    BatchResult result = new BatchResult();
    for (Payment p : payments) {
        try {
            gateway.send(p);
            result.succeeded.add(p.getId());
        } catch (GatewayException e) {                          // only the failure we expect
            log.warn("Payment {} failed: {}", p.getId(), e.getMessage(), e);
            result.failed.put(p.getId(), e.getMessage());
        }
    }
    return result;
}
// succeeded = [P1, P3], failed = {P2=Insufficient funds}

log is an SLF4J-style logger. Two follow-ups interviewers like: should an unexpected RuntimeException stop the batch or be recorded too? And if the whole batch is retried, how do you avoid sending P1 twice? (Idempotency keys, a Level 4 topic.)

D15. Ledger reconciliation

Task: remove every payment whose amount doesn't match the ledger, then print "Reconciled" if the remaining count equals the expected count. Ledger amounts look like new BigDecimal("250.00"); a typical day has a few hundred payments.

void reconcile(List<Payment> payments, Map<String, BigDecimal> ledger, Map<String, Integer> expected) {
    for (Payment p : payments) {
        BigDecimal ledgerAmount = ledger.get(p.getId());
        if (!ledgerAmount.equals(new BigDecimal(p.getAmount()))) {
            payments.remove(p);
        }
    }
    Integer remaining = payments.size();
    if (remaining == expected.get("count")) {
        System.out.println("Reconciled");
    }
}

Bugs to find: 5. Study patterns: 23, 31, 32, 33.

Show answerHide answer

Bugs:

  1. payments.remove(p) inside a for-each loop throws ConcurrentModificationException (or silently skips an item).
  2. new BigDecimal(p.getAmount()) builds from a double: 250.0 becomes 250, and amounts like 0.1 become long binary fractions.
  3. BigDecimal.equals() compares scale, so 250 and 250.00 count as different and matching payments get removed.
  4. ledger.get(...) returns null for a payment missing from the ledger, so ledgerAmount.equals(...) throws NullPointerException.
  5. Integer == Integer compares references: with a few hundred payments, 200 == 200 is false, so "Reconciled" never prints.

Fix:

void reconcile(List<Payment> payments, Map<String, BigDecimal> ledger, Map<String, Integer> expected) {
    payments.removeIf(p -> {
        BigDecimal ledgerAmount = ledger.get(p.getId());
        return ledgerAmount == null                                         // not in the ledger: a mismatch (confirm)
                || ledgerAmount.compareTo(BigDecimal.valueOf(p.getAmount())) != 0;
    });
    if (Objects.equals(payments.size(), expected.get("count"))) {
        System.out.println("Reconciled");
    }
}

Ask: should payments missing from the ledger be removed, kept, or reported? Better still, store payment amounts as BigDecimal from the start.

Edge cases: more than 127 payments, an amount like 0.10, a payment missing from the ledger, a missing "count" key.

Bugs:

  1. Day 30 doesn't exist in February: LocalDateTime.of(2026, 2, 30, ...) throws DateTimeException.
  2. 31-day months lose the 31st.
  3. isAfter(start) is strict, so a payment at exactly 00:00 on the 1st is excluded.

public double closingBalance(double opening, List<Payment> payments, String account) {

    for (Payment p : payments) {
        if (p == null || !"COMPLETED".equals(p.getStatus())) {
            continue;
        }
        if (account.equals(p.getToAccount())) {
            balance += p.getAmount();      // money in
        }
        if (account.equals(p.getFromAccount())) {
            balance -= p.getAmount();      // money out
        }
    }
    return balance;

public Optional<Payment> largestOutgoing(List<Payment> payments, String account) {

            .filter(Objects::nonNull)

public Map<String, Double> netFlowByCounterparty(List<Payment> payments, String account) {
    Map<String, Double> net = new TreeMap<>();                           // sorted by account
    for (Payment p : payments) {
        if (p == null || !"COMPLETED".equals(p.getStatus())) {
            continue;
        }
        if (account.equals(p.getToAccount()) && p.getFromAccount() != null) {
            net.merge(p.getFromAccount(), p.getAmount(), Double::sum);   // they paid us
        }
        if (account.equals(p.getFromAccount()) && p.getToAccount() != null) {
            net.merge(p.getToAccount(), -p.getAmount(), Double::sum);    // we paid them
        }
    }
    return net;
}
// {ACC-2=-125.0, ACC-3=50.0}

public List<String> accountsWithRepeatedRejections(List<Payment> payments) {
    Map<String, Map<LocalDate, Long>> rejectionsByAccountAndDay = payments.stream()
            .filter(Objects::nonNull)
            .filter(p -> "REJECTED".equals(p.getStatus()))
            .filter(p -> p.getFromAccount() != null && p.getCreatedAt() != null)
            .collect(Collectors.groupingBy(
                    Payment::getFromAccount,
                    Collectors.groupingBy(p -> p.getCreatedAt().toLocalDate(), Collectors.counting())));
    return rejectionsByAccountAndDay.entrySet().stream()
            .filter(e -> e.getValue().values().stream().anyMatch(count -> count >= 3))
            .map(Map.Entry::getKey)
            .sorted()
            .collect(Collectors.toList());
}

The nested map (account, then day, then count) avoids string keys like account + date, which can collide (pattern 27).

K2. LimitChecker

This round adds the questions a senior interviewer asks next: what changes when the clock moves, and when two requests arrive at once.

Part 1: find and fix the bugs (aim for 10 minutes).

class LimitChecker {
    private static final double DAILY_LIMIT = 5000;
    private final Map<String, Double> spentToday = new HashMap<>();

    // Approves and records the payment if it keeps the account within today's limit.
    public boolean tryPay(String account, double amount) {
        double spent = spentToday.get(account);
        if (spent + amount < DAILY_LIMIT) {
            spentToday.put(account, spent + amount);
            return true;
        }
        return false;
    }
}

Bugs to find: 5. Hint: a payment that takes the total to exactly 5,000 is allowed, and this object lives for weeks inside a web service.

Part 2: add two methods (aim for 10 minutes).

  1. double remainingToday(String account): how much the account can still pay today.
  2. List<String> accountsNearLimit(double percent): accounts that have used at least percent of today's limit, highest usage first.

Part 3 (talk, don't code): the service now runs on 3 servers behind a load balancer. What breaks, and how would you fix it?

Show answerHide answer

Part 1 bugs:

  1. spentToday.get(account) is null for an account's first payment, and unboxing it into a double throws NullPointerException.
  2. < rejects a payment that brings the total to exactly 5,000; the limit allows it, so use <=.
  3. Zero and negative amounts are accepted, and a payment of -1,000 would raise the remaining limit.
  4. "Today" never resets: the map grows forever, and yesterday's spending blocks today's payments.
  5. Not thread-safe: two requests can both read the same spent, both pass the check, and together exceed the limit (a check-then-act race).

Also worth saying: real money should be BigDecimal, and the clock should be injected so tests can control "today".

Fixed, with both extensions:

class LimitChecker {
    private static final double DAILY_LIMIT = 5000;
    private final Map<String, Double> spentToday = new HashMap<>();
    private final Clock clock;               // injected, so tests can move time
    private LocalDate currentDay;

    LimitChecker(Clock clock) {
        this.clock = clock;
    }

    public synchronized boolean tryPay(String account, double amount) {
        if (account == null || amount <= 0) {
            throw new IllegalArgumentException("account is required and amount must be positive");
        }
        resetIfNewDay();
        double spent = spentToday.getOrDefault(account, 0.0);
        if (spent + amount <= DAILY_LIMIT) {
            spentToday.put(account, spent + amount);
            return true;
        }
        return false;
    }

    // Extension 1
    public synchronized double remainingToday(String account) {
        resetIfNewDay();
        return DAILY_LIMIT - spentToday.getOrDefault(account, 0.0);
    }

    // Extension 2
    public synchronized List<String> accountsNearLimit(double percent) {
        resetIfNewDay();
        double threshold = DAILY_LIMIT * percent / 100;
        return spentToday.entrySet().stream()
                .filter(e -> e.getValue() >= threshold)
                .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
                .map(Map.Entry::getKey)
                .collect(Collectors.toList());
    }

    private void resetIfNewDay() {
        LocalDate today = LocalDate.now(clock);
        if (!today.equals(currentDay)) {
            spentToday.clear();
            currentDay = today;
        }
    }
}

Checked behaviour: 3,000 then 2,000 is approved (exactly the limit), 0.01 more is refused, -100 throws, and on the next day the counter starts again from zero. tryPay and remainingToday are O(1); accountsNearLimit is O(a log a) for a accounts.

Part 3, three servers:

  • Each server keeps its own in-memory map, so one account can spend up to 5,000 on each server: 15,000 a day.
  • A restart or deployment wipes every counter.
  • synchronized only protects one JVM, not three.

The fix is to keep the counter in shared storage and make check-and-add one atomic step, for example a single conditional SQL update:

UPDATE daily_spend
SET spent = spent + :amount
WHERE account_id = :account
  AND day = :today
  AND spent + :amount <= 5000;
-- 1 row updated: approved. 0 rows: refused (create the day's row first if it doesn't exist).

Alternatives are a row lock (SELECT ... FOR UPDATE inside a transaction) or an atomic check-and-increment in Redis. Also make payments idempotent, so a retried request isn't counted twice.
