Layer 1

Foundations — the four ideas everything else sits on

Agar ye chaar clear ho gaye, baaki 80% khud samajh aa jaata hai. Interview me bhi yahin se depth check hoti hai.

T1

Why a single SQL box eventually stops scaling

Beginner
▲ PROBLEM

One primary node owns all writes. You add RAM, then NVMe, then a bigger box — and the wall arrives anyway: a single write-ahead log, a single lock manager, a single failure domain.

Ek hi primary node saare writes leta hai. RAM badhao, SSD badhao, machine badi karo — deewar phir bhi aayegi, kyunki WAL ek hai, lock manager ek hai, aur mar jaaye toh poora system down.

  • Read replicas help reads, not writes.
  • Vertical scaling cost is super-linear; 2× machine ≠ 2× price.
  • Failover takes 30–120s and needs a human or an orchestrator.
  • Cross-region writes pay full round-trip latency to the primary.

Read replica sirf padhne me help karta hai. Writes ka bottleneck waisa ka waisa. Aur failover ke time 30–120 second ka downtime almost guaranteed hai.

● SOLUTION

Cassandra removes the primary entirely. Every node is a peer that can accept a write; data is partitioned by a hash of the partition key and replicated RF times around a token ring.

Cassandra me koi master hi nahi hai. Har node peer hai, koi bhi write le sakta hai. Data partition key ke hash se ring me baant diya jaata hai aur RF baar copy hota hai.

  • Write throughput scales roughly linearly with node count.
  • Node loss = no downtime, only reduced redundancy.
  • Multi-DC replication is a keyspace setting, not a project.
Cost of this choice

You give up joins, cross-partition transactions, ad-hoc queries and referential integrity. That's not a bug — that's the trade you signed.

Iske badle joins, cross-partition transaction, ad-hoc query aur foreign key sab chale jaate hain. Ye bug nahi, deal ka hissa hai.

T2

CAP is the interview answer; PACELC is the real one

BeginnerSDE-2
▲ PROBLEM

"Cassandra is AP, Postgres is CP" is where most candidates stop — and it's shallow. Network partitions are rare; latency is constant. CAP says nothing about the 99.9% of the time when the network is healthy.

Zyada log yahin ruk jaate hain: "Cassandra AP hai, Postgres CP hai." Ye bahut surface-level hai. Partition kabhi-kabhi hota hai, par latency hamesha hoti hai — aur CAP uske baare me kuch nahi bolta.

Second trap: people call CAP a per-database property. It isn't. In Cassandra it's a per-query property, decided by the consistency level you pass.

● SOLUTION

Use PACELC: if Partition → A or C, Else → L or C. Cassandra is PA/EL by default — available under partition, latency-optimised otherwise. Postgres is PC/EC.

PACELC bolo: Partition ho toh A ya C, warna (Else) L ya C. Cassandra default me PA/EL hai, Postgres PC/EC.

Then show the dial: in Cassandra you move along the C↔A axis per statement.

Statement CLYou getYou pay
ONELowest latency, survives 2/3 downStale reads likely
QUORUMR+W>RF ⇒ read-your-writeSlower, survives 1/3 down
LOCAL_QUORUMStrong in-DC, no WAN hopOther DC may be stale
ALLStrongest readOne node down = query fails

Yaad rakho: R + W > RF hone par hi strong consistency milti hai. RF=3 me W=QUORUM(2) + R=QUORUM(2) = 4 > 3 ✔

T3

Normalise for SQL, model-per-query for Cassandra

Beginner
▲ PROBLEM

Teams port a 3NF schema straight into Cassandra: users, orders, order_items. Then they discover there is no join, so the app does N+1 round trips and p99 explodes.

Log seedha 3NF schema Cassandra me daal dete hain. Phir pata chalta hai join hai hi nahi, app N+1 call maarne lagti hai, aur p99 latency phat jaati hai.

The tell

If your service loops over IDs issuing one SELECT each, your data model is wrong — no amount of tuning fixes it.

Agar service loop me ek-ek ID par SELECT maar rahi hai, toh model galat hai. Tuning se ye theek nahi hoga.

● SOLUTION

Invert the process. In SQL you model entities and derive queries. In Cassandra you list the queries first and create one table per query shape, duplicating data freely.

Process ulta karo. SQL me entity pehle, query baad me. Cassandra me query pehle likho, phir har query ke liye alag table banao — data duplicate karne se mat daro.

T4

The primary key is a physical layout instruction

BeginnerSDE-2
▲ PROBLEM

In SQL a primary key is a uniqueness constraint. People carry that mental model over and write PRIMARY KEY (customer_id, ordered_at) thinking it only means "unique pair". It actually decides which machine the data lands on and the on-disk sort order.

SQL me primary key sirf uniqueness hai. Cassandra me wo decide karta hai data kis machine par jayega aur disk par kis order me baithega. Yehi confusion sabse zyada production incidents deta hai.

  • Wrong partition key ⇒ hot node, one machine at 100% CPU while others idle.
  • No clustering column ⇒ you can never range-scan inside a partition.
  • Query without the full partition key ⇒ ALLOW FILTERING ⇒ cluster-wide scan.
● SOLUTION

Read the key as two jobs: partition key = which node, clustering columns = sort order inside that node.

anatomyPRIMARY KEY ((A,B), C, D)


1PRIMARY KEY ( (customer_id, region), ordered_at, order_id )


2                └── composite ──┘  └── clustering ──┘


3                    partition key


4// token(customer_id, region) → owning node on the ring


5// rows inside that partition sorted by ordered_at, then order_id

Partition key = "kis node par". Clustering key = "us node ke andar kis order me". Bas itna yaad rakho aur aadhe design questions nikal jaayenge.

Sizing rule you can quote

Target a partition under 100 MB and under 100,000 rows. Above that, add a bucket component to the partition key.

Ek partition 100 MB aur 1 lakh rows se neeche rakho. Upar jaaye toh partition key me bucket (jaise month) jod do.

Layer 2

Internals — why writes are cheap and reads are the hard part

Yahan se SDE-2 / SDE-3 wala depth start hota hai. Interviewer yahin poochta hai "internally kya hota hai?" — aur yahi Machine Room animation me chalta dikhega.

T5

Write path: append, don't seek

SDE-2
▲ PROBLEM

A B-tree write must first find the page, possibly split it, then rewrite it. That is a random I/O per write plus lock contention on hot pages. Under heavy write load the disk head (or SSD write amplification) becomes the ceiling.

B-tree me har write pehle page dhoondhta hai, zarurat pade toh split karta hai, phir wapas likhta hai — matlab random I/O aur hot page par lock fight. Heavy write load me disk hi bottleneck ban jaati hai.

Also: an UPDATE ... WHERE in SQL is a read-modify-write. You cannot avoid reading before writing.

● SOLUTION

Cassandra never reads before writing and never seeks. Every mutation is an append:

  1. CommitLog — sequential append to disk, gives durability.
  2. Memtable — same mutation applied to a sorted in-memory structure per table.
  3. Ack — client is told "written" once CL is satisfied.
  4. Flush — memtable full ⇒ written out as an immutable SSTable; commitlog segment recycled.
  5. Compaction — background merge of SSTables, keeping the newest cell per column.

CommitLog → Memtable → Ack → Flush → SSTable → Compaction. Poora path sequential hai, isiliye writes itni tez hain. Aur write se pehle read nahi hota — yahi Cassandra ki asli superpower hai.

What "UPDATE" really means

There is no update. An UPDATE is an INSERT of the changed columns with a newer timestamp. On read, the newest cell per column wins (last-write-wins).

Cassandra me UPDATE hota hi nahi. Jo column badla, uska naya cell naye timestamp ke saath likh diya jaata hai. Read ke time sabse naya cell jeet jaata hai.

T6

Read path: one row may live in six places at once

SDE-2Architect
▲ PROBLEM

Because writes only append, a single logical row can be scattered across the memtable plus N SSTables. A naive read would open every file. Reads are therefore Cassandra's expensive side — the exact opposite of an RDBMS, where the index makes reads cheap.

Writes sirf append karte hain, isliye ek logical row memtable + N SSTables me bikhri hoti hai. Agar seedha padho toh har file kholni padegi. Isiliye Cassandra me read mehnga hai — RDBMS ka bilkul ulta.

Worse: a query without the partition key has no idea which node to ask, so it fans out to the entire cluster.

● SOLUTION

A layered filter chain eliminates files before touching disk:

  1. Row cache (optional) — full partition already in RAM? return it.
  2. Memtable — newest un-flushed data.
  3. Bloom filter per SSTable — "definitely not here" is exact; "maybe here" costs a lookup. False positives only, never false negatives.
  4. Key cache → partition summary → partition index → byte offset.
  5. Merge surviving fragments by cell timestamp, newest wins; tombstones mask older cells.

Row cache → Memtable → Bloom filter → Key cache → Partition index → SSTable → merge by timestamp. Bloom filter sabse important hai: wo "yahan nahi hai" pakka bata deta hai, "shayad hai" me hi disk chhuni padti hai.

Metric to name in an interview

Watch SSTables per read. Healthy is 1–3. If p99 shows 10+, your compaction strategy or your data model is wrong.

Ek number yaad rakho: SSTables per read. 1–3 theek hai. 10+ dikh raha hai toh compaction strategy ya data model galat hai.

T7

Compaction: pick the wrong strategy, pay 10× disk

SDE-2Architect
▲ PROBLEM

SSTables accumulate forever. Without merging, read amplification grows unbounded and deleted data is never reclaimed. But merging costs CPU and, briefly, extra disk.

SSTables badhte hi jaate hain. Merge nahi karoge toh read amplification infinite ho jaayega aur delete kiya data disk se kabhi hatega hi nahi. Par merge karne me CPU aur temporary disk dono lagti hai.

Default STCS on a time-series workload is a classic production mistake: old and new data get merged together forever, so a TTL expiry never frees a whole file.

Simple rule: time-series + TTL → TWCS, same row baar-baar update ho raha ho + read heavy → LCS, write dump + kam read → STCS.

T8

Delete creates data. Tombstones and the queue anti-pattern

SDE-2Architect
▲ PROBLEM

A DELETE writes a tombstone — a marker saying "this is deleted as of timestamp T". It must survive at least gc_grace_seconds (default 10 days) so a node that was offline cannot resurrect the row.

DELETE actually ek tombstone likhta hai — matlab "ye timestamp T par delete ho gaya". Ye kam se kam gc_grace_seconds (default 10 din) tak zinda rehta hai, warna offline node purana data wapas le aayega.

The killer pattern: using a partition as a queue — insert, read, delete, repeat. Reads must now step over thousands of tombstones. At 1,000 you get a warning; at 100,000 the query is aborted with TombstoneOverwhelmingException.

Also produces tombstones (people forget)

Inserting NULL into a column. Overwriting a whole collection. TTL expiry. All of them.

Column me NULL daalna, poori collection overwrite karna, TTL expire hona — teeno tombstone banate hain.

● SOLUTION
  • Prefer TTL over DELETE — expiry is scheduled, predictable and TWCS can drop an entire file at once.
  • Never build a queue in Cassandra — use Kafka, SQS or Pulsar. This is the single most repeated architectural mistake.
  • Bucket by time so old partitions are dropped whole rather than row-by-row.
  • Don't write NULLs — omit the column in the prepared statement instead (use unset).
  • Lower gc_grace_seconds only if repair runs reliably inside that window.

T9

Tunable consistency: R + W > RF, and when to ignore it

SDE-2Architect
▲ PROBLEM

Two failure modes, opposite causes. Team A sets everything to ALL "to be safe" — now a single slow node fails every request and they've built a system less available than the Postgres they left. Team B sets everything to ONE — users update a profile and see the old value on refresh.

Do tarah ki galtiyan. Team A sab kuch ALL kar deti hai "safety ke liye" — ab ek slow node poore system ko gira deta hai. Team B sab ONE rakh deti hai — user profile update karta hai aur refresh par purana data dikhta hai.

Third trap: assuming QUORUM gives you a transaction. It does not. Two concurrent writers both succeed; the later timestamp silently wins.

● SOLUTION

Choose CL per query class, not per application.

Query classWrite CLRead CLWhy
Payment / balanceQUORUMQUORUM2+2>3, read-your-write guaranteed
User profile editLOCAL_QUORUMLOCAL_QUORUMStrong in home DC, no WAN latency
Activity feed / analyticsONEONEStale by 50ms is invisible to a user
Unique username claimLWT (SERIAL)SERIALNeeds real compare-and-set, not CL

Formula: R + W > RF. RF=3 par QUORUM=2, toh 2+2=4 > 3 ✔. Agar W=ONE aur R=ONE ho, 1+1=2 < 3 ✘ — stale read milega.

When to deliberately ignore R+W>RF

Ignore it when staleness is cheaper than latency: view counters, "last seen", recommendation feeds, telemetry. Say this out loud in an interview — it shows you optimise for the product, not the textbook.

Jab purana data dikhna sasta ho aur latency mehengi ho — view count, last seen, feed, telemetry — tab jaan-bujh kar ONE use karo. Interview me ye bolna score karta hai.

T10

Replication repair: hinted handoff, read repair, anti-entropy

Architect
▲ PROBLEM

If a replica is down when a QUORUM write succeeds, that replica is now permanently stale. Nothing in the write path fixes it. Do this for a month and replicas diverge badly enough that a QUORUM read can return old data.

QUORUM write ke time agar ek replica down thi, wo hamesha ke liye purani reh jaayegi. Write path apne aap use theek nahi karta. Mahina bhar aisa chala toh replicas itni alag ho jaayengi ki QUORUM read bhi purana data de sakti hai.

● SOLUTION

Three repair mechanisms, three time horizons:

  • Hinted handoff (seconds–3h): coordinator stores the missed mutation as a hint and replays it when the node returns. Bounded by max_hint_window_in_ms; beyond that, hints are dropped.
  • Read repair (on access): on a QUORUM read, digests are compared; a mismatch pushes the newest version to the stale replica. Only fixes data you actually read.
  • Anti-entropy repair (scheduled): nodetool repair builds Merkle trees and reconciles everything, including never-read rows. Must complete within gc_grace_seconds.

Hinted handoff = short-term patch. Read repair = jo padha wahi theek hua. nodetool repair = asli safai, aur ye gc_grace_seconds ke andar poora hona chahiye warna deleted data zinda ho jaayega.

The zombie-data question

"What happens if repair doesn't finish within gc_grace_seconds?" — Tombstones get compacted away on live nodes while an offline replica still holds the original row. When it rejoins, the deleted row resurrects. This is the single best answer to give at architect level.

Agar repair gc_grace ke andar poora nahi hua: live nodes par tombstone compact ho jaayega, par offline replica ke paas purani row abhi bhi hai. Wo wapas aayi toh deleted data zinda ho jaayega. Ye answer architect round me alag hi impression banata hai.

T11

Secondary index vs materialized view vs a second table

SDE-2Architect
▲ PROBLEM

"I need to query users by email but the partition key is user_id." The instinct from SQL is to add an index. In Cassandra a plain secondary index on a high-cardinality column is a distributed disaster: the coordinator must ask every node, because the index is local to each node's own data.

"Email se query karni hai par partition key user_id hai." SQL wali aadat kehti hai index laga do. Cassandra me high-cardinality column par secondary index matlab coordinator ko har node se poochna padega — kyunki index har node ke apne data tak hi seemit hai.

Materialized views look like the clean answer, but they are asynchronous, can drift from the base table, and have carried an "experimental" warning for years.

T12

Correctness without ACID: LWT, Saga, Outbox

Architect
▲ PROBLEM

"Debit A, credit B, both or neither." Cassandra has no multi-partition transaction, no rollback, no isolation across partitions. Even a BATCH only gives atomicity in the sense of "eventually all applied" — other clients can observe a partial state mid-flight.

"A se paisa kato, B ko do — dono ya koi nahi." Cassandra me multi-partition transaction hai hi nahi, rollback nahi, isolation nahi. BATCH bhi sirf itna deta hai ki "eventually sab apply ho jaayega" — beech me doosra client aadha state dekh sakta hai.

The LWT trap

Lightweight transactions do work — via Paxos — but cost ~4 network round trips instead of 1. Put LWT on your hot path and throughput drops by an order of magnitude.

LWT kaam karta hai (Paxos se), par 1 ke bajaye ~4 round trip leta hai. Hot path par LWT laga diya toh throughput 10× gir jaayega.

● SOLUTION

Pick the weakest mechanism that is still correct:

  1. Idempotent writes — make retry safe and most "transaction" needs disappear.
  2. LWT for rare uniqueness/claim operations: username reservation, seat booking, leader election. Low volume only.
  3. Single-partition BATCH — genuinely atomic and isolated, because it's one partition on one replica set. Free.
  4. Saga for cross-service workflows: a sequence of local commits, each with a compensating action.
  5. Transactional outbox so the local commit and the event publish cannot diverge.
  6. Keep the money in Postgres. Polyglot persistence is a valid answer — ledger in an RDBMS, feed and telemetry in Cassandra.

Sabse important line jo interview me bolni hai: "Main paisa Cassandra me nahi rakhunga." Ledger Postgres me, feed/telemetry Cassandra me. Ye weakness nahi, maturity hai.

T13

BATCH is not a performance feature

SDE-2
▲ PROBLEM

Coming from JDBC, everyone reaches for batching to reduce round trips. In Cassandra a multi-partition LOGGED BATCH makes one coordinator responsible for writes belonging to many nodes, and writes a batchlog entry to two extra nodes first. It is slower than issuing the statements in parallel.

JDBC ki aadat se log batch use karte hain round trip bachane ke liye. Cassandra me multi-partition LOGGED BATCH ek hi coordinator par bojh daal deta hai, aur pehle do extra nodes par batchlog likhta hai. Ye parallel individual writes se slow hai.

● SOLUTION
  • Same partition ⇒ BATCH is correct and free. Use it for atomicity within one partition.
  • Different partitions ⇒ send async statements in parallel and join the futures.
  • UNLOGGED BATCH only when all statements share a partition key — otherwise you lose atomicity and gain nothing.
  • Denormalised multi-table writes: accept eventual consistency, or use a logged batch knowingly and cap it at a handful of statements.

Rule: ek hi partition = BATCH use karo. Alag partitions = parallel async writes karo. Batch ko speed ka tool mat samjho, atomicity ka tool samjho.

T14

Counters: the only mutable thing, and it lies a little

SDE-2
▲ PROBLEM

Counter columns break the append-only rule — an increment is a read-modify-write internally, so it is far slower, cannot be mixed with normal columns in a table, cannot have a TTL, and is not idempotent. A client-side retry after a timeout may double-count.

Counter column append-only rule todta hai — andar se read-modify-write hota hai. Isliye slow hai, normal columns ke saath ek table me nahi aa sakta, TTL nahi le sakta, aur idempotent nahi hai. Timeout ke baad retry kiya toh count double ho sakta hai.

● SOLUTION
  • Fine for approximate metrics: view counts, likes, impressions.
  • Never for money, inventory, or anything reconciled later.
  • For exact counts: write immutable event rows and aggregate in a stream processor (Flink / Kafka Streams) into a materialised total.
  • Consider Redis INCR + periodic flush when you need both speed and exactness-with-a-window.

Approx cheezon ke liye counter theek hai — likes, views. Paisa aur inventory kabhi nahi. Exact chahiye toh event rows likho aur stream processor se total nikaalo.

T15

Hot partitions and the bucketing fix

SDE-2Architect
▲ PROBLEM

Three classic hot-partition designs, all of which look reasonable on a whiteboard:

  • PRIMARY KEY ((country), ts) — India partition is 500× the size of Iceland.
  • PRIMARY KEY ((day), ts) — every write in the cluster hits one node today.
  • PRIMARY KEY ((celebrity_id), ts) — one user with 90M followers.

Teen classic galtiyan: country se partition (India vs Iceland), day se partition (aaj ka poora traffic ek node par), aur celebrity_id se partition (ek banda 9 crore followers ka).

● SOLUTION

Add a bounded, derivable component to the partition key so it splits — but only one you can reconstruct at read time.

bucketing.cqltime bucket + deterministic shard


1CREATE TABLE sensor_readings_by_bucket (


2  sensor_id   uuid,


3  day_bucket  date,      -- derivable from the query's time range


4  shard_no    tinyint,   -- hash(sensor_id) % 8, deterministic


5  reading_at  timestamp,


6  celsius     float,


7  PRIMARY KEY ((sensor_id, day_bucket, shard_no), reading_at)


8) WITH CLUSTERING ORDER BY (reading_at DESC)


9  AND compaction = {'class':'TimeWindowCompactionStrategy',


10                 'compaction_window_unit':'DAYS',


11                 'compaction_window_size':1}


12  AND default_time_to_live = 2592000;  -- 30 days
Never use a random salt

A random shard number spreads writes beautifully and makes reads impossible — you'd have to query all shards. Derive it from data you already have at read time.

Random salt mat lagana. Write toh spread ho jaayega, par read ke time saare shards query karne padenge. Shard hamesha aisi cheez se banao jo read ke time already pata ho.

T16

Sharding in microservices: database-per-service, outbox, saga

Architect
▲ PROBLEM

Teams split the code into services but leave one shared database. Now every service can read every table, schema changes need cross-team coordination, and one bad query takes down all of them. This is a distributed monolith — the worst of both worlds.

Code toh services me toot gaya par database ek hi rehta hai. Ab har service har table padh sakti hai, schema change ke liye teen team ka approval chahiye, aur ek kharaab query sabko gira deti hai. Isko distributed monolith kehte hain — dono duniya ka bura.

Then when they do split the databases, the next problem lands: "order created" must reliably become "inventory reserved", but you can no longer wrap both in one transaction.

Dual-write bug

Commit to the DB, then publish to Kafka. The process dies between the two. The order exists and nobody was told. This happens in production more often than anyone admits.

Pehle DB me commit, phir Kafka par publish — beech me process mar gaya. Order ban gaya, kisi ko pata hi nahi chala. Production me ye bug jitna common hai, utna koi maanta nahi.

● SOLUTION

Four rules, in order:

  1. Database per service. The service owns its schema; everyone else goes through its API or its events.
  2. Pick the right engine per service. Orders/payments → Postgres (ACID). Feed, activity, telemetry → Cassandra. Sessions/rate limits → Redis. Search → OpenSearch.
  3. Shard inside a service, not across services. For Postgres: shard by tenant or by hash of the aggregate id, with a routing layer (Citus / Vitess / app-level). For Cassandra: the partition key is the shard — you get it free.
  4. Transactional outbox + CDC. Write the domain row and the outbox row in one local transaction; a connector (Debezium) tails the log and publishes. Consumers must be idempotent.

Char rule: (1) har service ka apna DB, (2) har service ke liye sahi engine, (3) sharding service ke andar — Cassandra me partition key hi shard hai, (4) dual-write ki jagah outbox + CDC.

Saga in one sentence

A long-running workflow is a chain of local transactions where each step has a compensating step; there is no rollback, only a deliberate undo written by you.

Saga matlab: lambi workflow ko chhote local transactions me todo, aur har step ka ek "undo" step likho. Rollback nahi hota — compensation hota hai.

HLD

Worked high-level design: activity feed + order platform

Ek hi system me dono duniya. Orders me ACID chahiye, feed me scale. Yahi polyglot persistence ka classic interview answer hai.

REQ

Requirements and back-of-envelope numbers

▲ CONSTRAINTS
  • 50M users, 5M daily active.
  • Feed writes: each action fans out to ~200 followers ⇒ ~400M feed rows/day ⇒ ~5k writes/s average, 25k peak.
  • Feed reads: 5M DAU × 12 opens ⇒ ~700 reads/s, p99 < 150 ms.
  • Orders: 200k/day, must never be lost or double-charged.

ARC

Fan-out on write vs fan-out on read

▲ PROBLEM

Fan-out on write is fast to read but a celebrity with 90M followers creates 90M rows from a single post — a write storm and a hot producer.

Fan-out on write me read fast hota hai, par 9 crore follower wale celebrity ki ek post 9 crore rows bana degi. Write storm.

Fan-out on read is cheap to write but a user following 2,000 accounts needs 2,000 partition reads per feed open.

● SOLUTION — hybrid
  • Normal authors: fan-out on write into feed_by_user, one partition per follower.
  • Celebrity authors (followers > threshold): skip fan-out, store once in posts_by_author.
  • At read time, merge the user's precomputed feed with the small set of celebrities they follow, sort by time in the service.
  • Cap the stored feed at ~1,000 rows per user with TTL so partitions stay bounded.

Hybrid: aam log ke liye write par fan-out, celebrity ke liye read par merge. Ye exact answer Twitter/X, Instagram sab jagah use hota hai — aur interview me yahi expected hai.

Round 1 — fundamentals

Q1Why is Cassandra fast at writes but comparatively slow at reads?Beginner

Writes are pure sequential appends: commitlog plus an in-memory memtable, with no read-before-write and no seek. Reads must reconcile a row that may be split across the memtable and several immutable SSTables, so they pay a merge cost plus filter lookups.

Write sirf append hai — commitlog + memtable, na read-before-write na seek. Read me ek row memtable aur kai SSTables me bikhri ho sakti hai, isliye merge aur filter lookup ka cost lagta hai.

Q2What exactly does the partition key do?Beginner

It is hashed by the partitioner (Murmur3) into a token, and the token determines which node on the ring owns the data and which RF−1 neighbours replicate it. It also defines the unit of atomicity and the unit of a single-node read.

Partition key ka Murmur3 hash token banta hai, aur token decide karta hai data kis node par jaayega aur kaun si RF−1 nodes copy rakhengi. Atomicity aur single-node read ka unit bhi yahi hai.

Q3Difference between partition key and clustering column?Beginner

Partition key decides which machine. Clustering columns decide the sort order within that machine's partition and enable range scans. Together they form the primary key, which must be unique.

Partition key = kaunsi machine. Clustering column = us machine ke andar kis order me baithega aur range scan possible karta hai. Dono milkar unique primary key banate hain.

Q4Can you do a JOIN in Cassandra? What do you do instead?Beginner

No. A join would require coordinating across arbitrary nodes, which is exactly what the design refuses to do. Instead you denormalise: write the same data into one table per query shape, and keep the copies in sync from the application or from a stream processor.

Nahi. Join ke liye alag-alag nodes coordinate karni padengi — jo Cassandra jaan-bujh kar nahi karta. Iski jagah denormalise karo: har query ke liye ek table, aur copies app ya stream processor se sync rakho.

Q5What is ALLOW FILTERING and why is it dangerous?Beginner

It tells Cassandra to fetch rows and discard non-matching ones after the fact. Without the partition key the coordinator cannot compute a token, so it queries every node and every SSTable. It works on 10k rows in dev and takes the cluster down at 10M in production.

Ye Cassandra se kehta hai "sab utha lo, phir chhaant lena". Partition key ke bina token nahi banta, toh har node aur har SSTable query hoti hai. Dev me 10 hazaar rows par chal jaayega, prod me 1 crore par cluster gira dega.

Q6RF=3, CL=QUORUM. How many nodes can fail before writes stop?Beginner

QUORUM with RF=3 is ⌊3/2⌋+1 = 2. So one of the three replicas for a given partition can be down. A second failure in the same replica set makes writes to that partition fail — other partitions with healthy replicas keep working.

RF=3 par QUORUM = 2. Matlab us partition ki 3 replicas me se 1 down chal jaayegi. Dusri bhi gir gayi toh us partition ke writes fail honge — baaki partitions chalte rahenge.

Q7What does the R + W > RF formula guarantee?BeginnerSDE-2

That the read replica set and the write replica set overlap by at least one node, so at least one responding replica has the latest write. It gives read-your-writes and monotonic reads. It does not give isolation, atomicity across partitions, or protection from concurrent conflicting writes.

Read aur write ke replica sets me kam se kam ek node common hoga, matlab latest write kisi na kisi respond karne wali replica ke paas hogi. Isse read-your-write milta hai. Isolation ya cross-partition atomicity nahi milti.

Q8SQL vs NoSQL in one minute.Beginner

SQL gives you a relational model, joins, ACID and query flexibility on a single logical machine, and scales up. NoSQL trades those for horizontal scale, availability and a fixed access pattern. The real answer in a system design round is that you use both, split by data type.

SQL deta hai relational model, join, ACID aur query flexibility — par ek logical machine par. NoSQL ye sab chhod kar horizontal scale aur availability deta hai. System design round ka asli jawab: dono use karo, data ke type par baant kar.

Round 2 — internals

Q9Walk me through the write path.SDE-2

Client → coordinator (any node) → token computed from the partition key → mutation sent to RF replicas. On each replica: append to commitlog (durability), apply to memtable (sorted, in RAM), ack. Once CL replicas ack, the client gets success. When the memtable crosses its threshold it flushes to an immutable SSTable and the commitlog segment is recycled. Compaction merges SSTables later.

Client → coordinator → partition key se token → RF replicas ko mutation. Har replica par: commitlog me append, memtable me apply, ack. Jitni CL chahiye utni ack aate hi client ko success. Memtable bhar gaya toh flush hokar immutable SSTable ban jaata hai aur commitlog segment free ho jaata hai. Baad me compaction merge karta hai.

Q10Walk me through the read path.SDE-2

Coordinator computes the token and asks CL replicas. On a replica: row cache → memtable → for each SSTable, bloom filter (skip if "definitely not") → key cache → partition summary → partition index → compression offset → read the partition. Fragments from the memtable and surviving SSTables are merged cell-by-cell, newest timestamp wins, tombstones mask older values. If replicas disagree, read repair pushes the newest version.

Coordinator token nikaalta hai, CL replicas se poochta hai. Replica par: row cache → memtable → har SSTable ka bloom filter (nahi hai toh skip) → key cache → partition summary → partition index → offset → read. Sab fragments cell-by-cell merge hote hain, sabse naya timestamp jeetta hai, tombstone purane values chhupa deta hai. Mismatch mila toh read repair.

Q11Can a bloom filter give a false negative?SDE-2

No — only false positives. "Not present" is always exact, "maybe present" may waste a lookup. That asymmetry is exactly what makes it safe as a skip filter. Lower bloom_filter_fp_chance means fewer wasted lookups but more heap.

Nahi — sirf false positive hota hai. "Nahi hai" hamesha pakka sach hai, "shayad hai" me lookup bekaar ja sakta hai. Yehi asymmetry use safe skip filter banati hai. fp_chance kam karoge toh lookups bachenge par heap badhega.

Q12What is a tombstone and why can't it be deleted immediately?SDE-2

A tombstone is a delete marker with a timestamp. It must survive gc_grace_seconds because a replica that was offline during the delete still holds the original row. If the tombstone were purged before that replica came back and was repaired, the row would resurrect.

Tombstone ek delete marker hai timestamp ke saath. Ye gc_grace_seconds tak zinda rehna zaroori hai kyunki jo replica delete ke waqt offline thi uske paas purani row abhi bhi hai. Tombstone pehle hata diya toh wo row wapas zinda ho jaayegi.

Q13Hinted handoff vs read repair vs anti-entropy repair.SDE-2Architect
  • Hinted handoff — coordinator saves a missed mutation and replays it when the node returns; bounded by the hint window (default 3 h).
  • Read repair — during a read, digest mismatch triggers pushing the newest data to stale replicas; only repairs what is read.
  • Anti-entropy — nodetool repair compares Merkle trees and reconciles everything, including cold data; must run within gc_grace.

Hinted handoff = short-term patch (3 ghante ki window). Read repair = jo padha wahi theek. nodetool repair = poori safai, aur ye gc_grace ke andar chalna hi chahiye.

Q14Which compaction strategy for 30-day IoT metrics with TTL?SDE-2

TWCS with a 1-day window and default_time_to_live of 30 days. Each day's data lands in its own SSTable, and when the window fully expires the entire file is dropped without compaction. STCS here would mix old and new data forever so nothing would ever be reclaimed cleanly.

TWCS, 1-din ki window, 30 din ka TTL. Har din ka data apni SSTable me, window expire hote hi poori file drop — compaction ki zarurat hi nahi. STCS lagate toh purana-naya data hamesha mix hota rehta aur disk kabhi saaf nahi hoti.

Q15How does an UPDATE work internally?SDE-2

It doesn't update anything. Only the columns you name are written as new cells with a newer write timestamp, appended to the memtable. On read, the merge picks the newest cell per column. Nothing is overwritten until compaction discards the older cell. This also means an UPDATE on a non-existent row simply creates it (upsert).

Update hota hi nahi. Sirf jo columns tumne likhe, unke naye cells naye timestamp ke saath memtable me append ho jaate hain. Read ke time har column ka sabse naya cell jeetta hai. Compaction tak kuch overwrite nahi hota. Isi wajah se non-existent row par UPDATE karne se row ban jaati hai — upsert.

Q16Two clients write the same column at the same millisecond. Who wins?Architect

Last-write-wins by cell write-time, which has microsecond resolution. On an exact tie, the value with the lexically greater byte representation wins — deterministic but arbitrary. There is no conflict detection and no error. If that outcome is unacceptable, you need an LWT or a different store.

Last-write-wins, cell ke write-time (microsecond) se. Bilkul tie ho gaya toh bytes ki lexical comparison se decide hota hai — deterministic hai par arbitrary. Na conflict detect hota hai na error milta hai. Ye acceptable nahi hai toh LWT chahiye ya dusra database.

Round 3 — design and tradeoffs

Q17Design the schema for a chat application's message history.SDE-2

Queries first: "last N messages of a conversation, newest first" and "scroll older". So PRIMARY KEY ((conversation_id, month_bucket), sent_at, message_id) with CLUSTERING ORDER BY (sent_at DESC). The month bucket keeps busy group chats under the partition ceiling; the client walks buckets backwards while scrolling. Add TWCS if you retain by time, and a separate conversations_by_user table for the inbox list.

Pehle queries: "conversation ke last N messages" aur "purane scroll karo". Toh key hogi ((conversation_id, month_bucket), sent_at, message_id), DESC order me. Month bucket busy group chats ko partition limit ke andar rakhta hai. Inbox list ke liye alag conversations_by_user table banao.

Q18You must query users by both id and email. How?SDE-2

Two tables: users_by_id and users_by_email, written together by the application. Email is high cardinality, so a secondary index would scatter-gather across the whole cluster. If email must be unique, claim it with an IF NOT EXISTS LWT on users_by_email first, then write the profile row.

Do tables: users_by_id aur users_by_email, dono app se likho. Email high cardinality hai isliye secondary index poore cluster par scatter-gather karega. Unique chahiye toh pehle users_by_email par LWT se claim karo, phir profile likho.

Q19Would you store an e-commerce order in Cassandra?Architect

The order history yes; the order lifecycle no. Payment, stock decrement and refunds need multi-row atomicity, rollback and an auditable ledger — that's Postgres. Once the order is terminal, project it into Cassandra for high-volume history and analytics reads. This split is the answer the interviewer is listening for.

Order ki history haan, order ka lifecycle nahi. Payment, stock kam karna, refund — inme multi-row atomicity aur rollback chahiye, matlab Postgres. Order final ho jaaye toh use Cassandra me project kar do history/analytics ke liye. Interviewer yahi split sunna chahta hai.

Q20How do you handle a celebrity user in a fan-out design?Architect

Hybrid. Below a follower threshold, fan out on write into each follower's feed partition. Above it, skip fan-out and store the post once; at read time merge the user's precomputed feed with posts from the handful of celebrities they follow. Cap the stored feed length and TTL it so partitions stay bounded.

Hybrid model. Threshold se kam followers = write par fan-out. Celebrity = fan-out skip, post ek jagah store, aur read ke time merge kar do. Feed ki length cap karo aur TTL lagao taaki partitions bounded rahein.

Q21How would you shard a Postgres database in a microservices setup?Architect

First split vertically: database per service, so each service owns its schema. Only then shard horizontally inside the service that needs it — by tenant id for a B2B product, or by hash of the aggregate root id otherwise, using Citus, Vitess or an app-level routing layer. Keep the shard key in every query, avoid cross-shard joins, and use an outbox for cross-service consistency.

Pehle vertical split: har service ka apna DB. Uske baad jis service ko zarurat ho usi ke andar horizontal shard karo — B2B me tenant id se, warna aggregate root id ke hash se (Citus/Vitess/app routing). Shard key har query me rakho, cross-shard join se bacho, aur cross-service consistency ke liye outbox.

Q22Migrate one hot table from Postgres to Cassandra with zero downtime.Architect
  1. Model the Cassandra tables from the actual queries, not the existing schema.
  2. Dual-write behind a feature flag: Postgres stays authoritative, Cassandra writes are async and failures only log.
  3. Backfill history in batches, throttled, resumable by primary key range.
  4. Shadow-read: serve from Postgres, also read Cassandra, compare, emit a mismatch metric.
  5. Flip reads per-percentage. Then flip writes. Keep dual-write for one rollback window, then remove.

Model → dual-write (flag ke peeche) → throttled backfill → shadow read + mismatch metric → percentage se read flip → write flip → ek rollback window ke baad purana hatao. Isi ko strangler-fig pattern kehte hain.

Q23When would you actively recommend against Cassandra?Architect

Data under a few TB; access patterns still changing; strong transactional needs; a small team with no ops capacity for repairs, compaction tuning and multi-node upgrades; or a reporting-heavy product. Cassandra's cost is operational, and it is paid every week, not once.

Data thoda hai (kuch TB), access pattern abhi badal rahe hain, transactions chahiye, ya team chhoti hai jo repair/compaction/upgrade nahi sambhal sakti, ya product reporting-heavy hai. Cassandra ka cost operational hai — ek baar nahi, har hafte lagta hai.

Q24Multi-region active-active. Which consistency level and why?Architect

LOCAL_QUORUM in each region with NetworkTopologyStrategy and RF=3 per DC. You get strong consistency within the region without paying a cross-ocean round trip on every request; the other region converges asynchronously. Use EACH_QUORUM only for the small set of writes that truly must be globally durable before ack — and expect the latency.

Har region me LOCAL_QUORUM, NetworkTopologyStrategy ke saath RF=3 per DC. Region ke andar strong consistency milti hai bina samundar paar ka round trip diye. EACH_QUORUM sirf un chand writes ke liye jo globally durable honi hi chahiye — aur uski latency ke liye taiyaar raho.

Round 4 — traps

Q25"Just set consistency to ALL and you get ACID." What's wrong?Architect

Almost everything. CL=ALL improves the freshness of a single-row read/write; it provides no atomicity across rows, no isolation, no rollback, and no protection from two concurrent writers overwriting each other. It also makes the query fail if any single replica is slow or down — you lose availability without gaining transactions.

Sab kuch galat. CL=ALL sirf ek row ki freshness sudhaarta hai — na atomicity, na isolation, na rollback, na concurrent writers se bachav. Upar se ek bhi replica slow hui toh query fail. Availability gayi, transaction phir bhi nahi mila.

Q26Your DELETE-heavy job made reads slow. Diagnose it.SDE-2

Tombstone accumulation. Reads must scan past deleted cells within the partition; tombstone_warn_threshold logs at 1,000 and tombstone_failure_threshold aborts at 100,000. Confirm with nodetool tablestats and query tracing. Fix by switching to TTL + TWCS, bucketing so whole partitions expire, avoiding NULL inserts, and only then considering a lower gc_grace with reliable repair.

Tombstone jama ho gaye. Read ko partition ke andar delete kiye cells ke upar se guzarna padta hai; 1,000 par warning, 1,00,000 par query abort. nodetool tablestats aur tracing se confirm karo. Fix: TTL + TWCS, bucketing, NULL insert band, aur uske baad hi gc_grace ghatane ki baat karo.

Q27You added a random salt to fix a hot partition. What did you break?SDE-2

Reads. A random salt is not reproducible, so to fetch a logical row you must query every possible salt value and merge — turning one partition read into N. Salts must be derivable from data you already hold at read time, such as hash(sensor_id) % 8 or a date bucket.

Read tod diya. Random salt reproduce nahi hota, toh ek logical row ke liye saare salt values query karke merge karna padega — ek read ab N reads. Salt hamesha aisi cheez se banao jo read ke time pata ho, jaise hash(sensor_id) % 8 ya date bucket.

Q28Repair hasn't run in three weeks and gc_grace is 10 days. What now?Architect

Deleted data may resurrect: tombstones have been compacted away on the nodes that saw them, while a replica that missed the delete still holds the original row. Do not simply run repair and hope — first stop the bleeding by raising gc_grace_seconds so no more tombstones are purged, then run a full repair, then reconcile any resurrected rows at the application level, then lower gc_grace back and schedule incremental repair (Reaper or equivalent) so this can't recur.

Deleted data zinda ho sakta hai — jin nodes ne tombstone dekha wahan wo compact ho gaya, par jis replica ne delete miss kiya uske paas purani row abhi bhi hai. Seedha repair mat chalao: pehle gc_grace badhao taaki aur tombstone purge na ho, phir full repair, phir application level par resurrected rows reconcile karo, phir gc_grace wapas neeche laakar Reaper se scheduled repair lagao.
