Pagination that stays fast on page 5,000Pagination jo page 5,000 pe bhi fast rahe

OFFSET vs keyset (cursor) pagination.OFFSET vs keyset (cursor) pagination.

Problem

Q. Why does page 5,000 take 4 seconds, and why do users see the same item twice while scrolling?Q. Page 5,000 pe 4 second kyun lagte hain, aur scroll karte waqt same item do baar kyun dikhta hai?

  • Slow: OFFSET still walks and throws away every skipped row, so page N costs O(N).Slow: OFFSET har skip kiye row ko padh ke phenk deta hai, isliye page N ka cost O(N) hai.
  • Duplicates: a new order at the top shifts everything down by one, so the last item of page 1 appears again on page 2.Duplicates: top pe naya order aaya toh sab ek position neeche khisak gaya, isliye page 1 ka last item page 2 pe phir dikhta hai.
  • Skips: a delete shifts rows up, and one row is never shown.Skips: delete hone pe rows upar khisakti hain, aur ek row kabhi dikhti hi nahi.
  • Unstable order: created_at alone isn't unique, so ties can come back in any order.Unstable order: sirf created_at unique nahi hai, same timestamp wale rows kisi bhi order me aa sakte hain.
  • "Page 1 of 9,812" needs COUNT(*), another full scan on every request."Page 1 of 9,812" ke liye COUNT(*) chahiye, har request pe ek aur full scan.
Solution

HLD: keyset (seek) paginationHLD: keyset (seek) pagination

Remember where the last page ended and ask for rows strictly after it. The index jumps straight there, so every page costs the same.Yaad rakho pichhla page kahan khatam hua, aur uske strictly baad wale rows maango. Index seedha wahan jump karta hai, isliye har page ka cost same hai.

Client ?cursor=…→Decode cursor→Index seek→size + 1 rows→Next cursor

LLD: an opaque cursorLLD: opaque cursor

  1. The cursor is the sort key of the last row: (created_at, id). The id breaks ties, so the order is total and stable.Cursor bas last row ki sort key hai: (created_at, id). id tie todta hai, isliye order total aur stable hai.
  2. The first page uses a sentinel "after the end of time", so one query shape serves every page.First page ek sentinel use karta hai, "time ke end ke baad", taaki ek hi query shape har page ke liye chale.
  3. The next cursor is built from the last row actually returned, never from page number times page size.Next cursor usi last row se banta hai jo actually return hua, page number × size se kabhi nahi.
  4. URL-safe Base64 keeps the cursor opaque, so clients can't build or edit it. Instant.toString() keeps full precision; truncating to seconds would skip rows.URL-safe Base64 cursor ko opaque rakhta hai, client use bana ya badal nahi sakta. Instant.toString() full precision rakhta hai; seconds tak truncate kiya toh rows skip hongi.
  5. A garbage token must become a 400, not a 500, so every parse error maps to InvalidCursorException.Kachra token 400 banna chahiye, 500 nahi, isliye har parse error InvalidCursorException ban jaata hai.
  1. Native SQL, because JPQL can't express a row-value comparison portably.Native SQL, kyunki JPQL row-value comparison portable tareeke se nahi likh sakta.
  2. (created_at, id) < (a, b) means "strictly after the last row" in descending order, and Postgres serves it straight from the composite index. On MySQL, write created_at < a OR (created_at = a AND id < b).(created_at, id) < (a, b) ka matlab descending order me "last row ke strictly baad", aur Postgres ise seedha composite index se chalata hai. MySQL me created_at < a OR (created_at = a AND id < b) likho.
  3. ORDER BY must match the index exactly, same columns and same directions, or the database sorts in memory.ORDER BY index se exactly match hona chahiye, same columns aur same direction, warna database memory me sort karega.
  4. The service passes limit as page size + 1.Service limit me page size + 1 bhejti hai.
  1. Read-only lets the routing data source send this to a replica (topic 02) and skips Hibernate dirty checking.Read-only hone se routing data source ise replica pe bhej sakta hai (topic 02), aur Hibernate dirty checking skip hoti hai.
  2. Clamp the page size. A client asking for a million rows is a denial of service.Page size clamp karo. Million rows maangne wala client ek tarah ka denial of service hai.
  3. Ask for one extra row. If it comes back, there is a next page, with no COUNT(*).Ek extra row maango. Agar aayi toh next page hai, bina COUNT(*) ke.
  4. Drop the extra row and build the next cursor from the real last row. null means end of list.Extra row hatao aur asli last row se next cursor banao. null matlab list khatam.

Need "jump to page 37" on an admin screen? Keep OFFSET with a max page, or use a deferred join: fetch only ids with OFFSET from a covering index, then join. In Elasticsearch use search_after with a point-in-time instead of from/size, which stops at 10,000 hits.Admin screen pe "page 37 pe jao" chahiye? Max page ke saath OFFSET rakho, ya deferred join: covering index se OFFSET ke saath sirf ids lao, phir join karo. Elasticsearch me from/size (10,000 hits pe ruk jaata hai) ki jagah point-in-time ke saath search_after use karo.

Apply whenKab apply karein

Feeds, infinite scroll, mobile APIs, exports and batch jobs over large tables.Feeds, infinite scroll, mobile APIs, exports aur bade tables pe batch jobs.

Ignore whenKab ignore karein

Small tables, or admin screens that truly need random page jumps. OFFSET with a max page is fine there.Chhote tables, ya admin screens jinhe sach me random page jump chahiye. Wahan max page ke saath OFFSET theek hai.

Why it worksKyun kaam karta hai

Every page is one index seek, O(log n) at any depth, and it stays stable while rows are inserted or deleted.Har page ek index seek hai, kitna bhi deep jao O(log n), aur inserts ya deletes ke beech bhi stable rehta hai.

What it costsIski keemat

No "go to page N". Cursors break if the sort changes, and the sort key must be unique, so add the id."Page N pe jao" nahi milta. Sort badla toh cursors toot jaate hain, aur sort key unique honi chahiye, isliye id add karo.

Problem

One primary serves everything, then replicas return stale dataEk primary sab kuch serve karta hai, phir replicas purana data dete hain

95% of traffic is reads: product pages, order history. A single primary takes every read and write, so CPU is saturated, and if that one machine dies the whole service is down. After adding asynchronous read replicas, a new bug appears: a user updates their address, the page reloads from a replica that is 800 ms behind, and the old address shows up. "My update was lost!"

95% traffic reads hai: product pages, order history. Ek hi primary har read aur write le raha hai, CPU full hai, aur agar wo ek machine mari toh poori service down. Async read replicas add kiye toh naya bug aaya: user ne address update kiya, page ek aise replica se reload hua jo 800 ms peeche hai, aur purana address dikh gaya. "Mera update kho gaya!"

  • Primary CPU high even though most queries are SELECTsZyada tar queries SELECT hain phir bhi primary CPU high
  • Stale reads right after a write (replication lag)Write ke turant baad stale reads (replication lag)
  • A comment appears, then disappears on refresh: two replicas at different lagComment dikhta hai, refresh pe gayab: do replicas alag-alag lag pe
  • Failover with async replication loses the last few commitsAsync replication ke saath failover pe last kuch commits kho jaate hain
Solution

Leader–follower replication with read/write routing and read-your-writesLeader–follower replication, read/write routing aur read-your-writes ke saath

All writes go to the primary, which streams its write-ahead log (WAL, or binlog in MySQL) to replicas. Reads go to replicas. Route in code with Spring's AbstractRoutingDataSource: read-only transactions use a replica, everything else uses the primary. Fix stale reads with read-your-writes: after a user writes, pin that user's reads to the primary for a window longer than your p99 lag.

Saare writes primary pe jaate hain, jo apna write-ahead log (WAL, MySQL mein binlog) replicas ko stream karta hai. Reads replicas pe jaate hain. Code mein Spring ke AbstractRoutingDataSource se route karo: read-only transactions replica pe, baaki sab primary pe. Stale reads ko read-your-writes se fix karo: user ke write ke baad, uske reads ko p99 lag se lambi window tak primary pe pin karo.

Sharding: shard keys, consistent hashing, global IDsSharding: shard keys, consistent hashing, global IDs

HLDLLD
Problem

One primary can't take any more writesEk primary ab aur writes nahi le sakta

The orders table is 4 TB, grows 50 GB a day and takes 40K writes per second. Read replicas don't help, because every write still lands on one primary, and you're already on the biggest machine. The data has to be split across independent databases (shards). That raises new questions: which shard holds customer 42? When you add a fifth shard, does all the data move? And auto-increment IDs now collide across shards.

Orders table 4 TB ka hai, roz 50 GB badhta hai aur har second 40K writes aate hain. Read replicas se kuch nahi hoga, kyunki har write abhi bhi ek hi primary pe girta hai, aur aap pehle se sabse badi machine pe ho. Data ko alag-alag independent databases (shards) mein todna padega. Naye sawaal: customer 42 kis shard pe hai? Paanchwa shard add kiya toh kya saara data move hoga? Aur auto-increment IDs ab shards ke beech collide karenge.

  • Primary write IOPS and CPU maxed out, even after tuningTuning ke baad bhi primary ka write IOPS aur CPU full
  • Backups and restores take hours; indexes don't fit in RAMBackup aur restore mein ghante lagte hain; indexes RAM mein fit nahi
  • hash % N routing: going from 4 to 5 shards remaps about 80% of keyshash % N routing: 4 se 5 shards karne pe ~80% keys remap hoti hain
  • A hot shard: one celebrity or big tenant gets 30% of the trafficHot shard: ek celebrity ya bade tenant pe 30% traffic
Solution

A good shard key, consistent hashing, and Snowflake IDsAchhi shard key, consistent hashing, aur Snowflake IDs

A good shard key is present in almost every query, spreads load evenly, and keeps data that is read together on the same shard. For orders, customer_id works: "my orders" touches one shard. Route with consistent hashing and virtual nodes so adding a shard moves only about 1/N of the keys. Generate IDs with Snowflake (time + machine + sequence): unique across shards and roughly time-ordered.

Achhi shard key lagbhag har query mein hoti hai, load barabar baant-ti hai, aur jo data saath padha jaata hai use ek hi shard pe rakhti hai. Orders ke liye customer_id sahi hai: "my orders" sirf ek shard ko touch karta hai. Consistent hashing aur virtual nodes se route karo taaki naya shard add karne pe sirf ~1/N keys move hon. IDs Snowflake se banao (time + machine + sequence): shards ke across unique aur roughly time-ordered.

Q1Design pagination for an infinite feed with 50 million posts.50 million posts wale infinite feed ke liye pagination design karo.Pagination

Keyset pagination on (created_at, id) with a composite index, an opaque Base64 cursor, and LIMIT size + 1 to detect the next page, with no COUNT(*). If the feed is ranked, the cursor carries (score, id) plus a snapshot id so the ranking doesn't shift under the user. In Elasticsearch, use search_after with a point-in-time.

(created_at, id) pe keyset pagination, composite index ke saath, opaque Base64 cursor, aur next page pata karne ke liye LIMIT size + 1, bina COUNT(*). Feed ranked hai toh cursor me (score, id) aur ek snapshot id, taaki user ke neeche ranking na hile. Elasticsearch me point-in-time ke saath search_after.

Q2Users see the same item twice while scrolling. Why?Scroll karte waqt user ko same item do baar dikhta hai. Kyun?Pagination

Offset pagination plus new inserts: a new row at the top shifts every row down, so the last item of page 1 becomes the first item of page 2. A non-unique sort key does it too, because ties come back in random order. Fix it with keyset pagination and a unique tie-breaker (id).

Offset pagination + naye inserts: top pe nayi row aayi toh har row neeche khisak gayi, aur page 1 ka last item page 2 ka pehla item ban gaya. Non-unique sort key bhi yahi karti hai, kyunki ties random order me aate hain. Fix: keyset pagination aur unique tie-breaker (id).

Q3A user updates their profile, refreshes, and sees the old data. Fix it.User profile update karta hai, refresh karta hai, aur purana data dikhta hai. Fix karo.Replication

The read went to a lagging async replica. Options: pin the user to the primary for a few seconds after a write (a Redis key with a TTL); record the commit LSN and only use a replica that has replayed past it; or always read "my own profile" from the primary. For monotonic reads, keep each user on one replica.

Read ek lagging async replica pe gaya. Options: write ke baad user ko kuch seconds primary pe pin karo (TTL wali Redis key); commit LSN note karo aur sirf woh replica use karo jo usse aage replay kar chuka ho; ya "apni profile" hamesha primary se padho. Monotonic reads ke liye har user ko ek hi replica pe rakho.

Q4Synchronous or asynchronous replication for a payments database?Payments database ke liye synchronous ya asynchronous replication?Replication

Neither extreme. Commit with quorum (semi-sync) to at least one standby in the same region, so a failover loses nothing (RPO = 0), at the cost of one extra round trip per commit. Add async replicas in other regions for disaster recovery and reads. Fully synchronous replication to every replica lets one slow replica stall every payment.

Koi bhi extreme nahi. Same region me kam se kam ek standby tak quorum (semi-sync) commit, taaki failover pe kuch lose na ho (RPO = 0); keemat hai har commit pe ek extra round trip. Doosre regions me async replicas, disaster recovery aur reads ke liye. Har replica tak fully synchronous replication me ek slow replica har payment rok dega.

Q5How do you choose a shard key for an orders table?Orders table ke liye shard key kaise chunoge?Sharding

customer_id: high cardinality, present in most queries ("my orders"), and it keeps one customer's orders on one shard. Lookups by order_id then need the shard, so embed the shard id in the order id or keep a small lookup table. Avoid created_at, which sends every new write to one hot shard, and low-cardinality keys such as country.

customer_id: high cardinality, zyaadatar queries me hota hai ("mere orders"), aur ek customer ke saare orders ek shard pe rehte hain. Phir order_id se lookup ke liye shard chahiye, toh order id me shard id embed karo ya ek chhota lookup table rakho. created_at se bacho, jo har naya write ek hot shard pe bhejta hai, aur country jaisi low-cardinality keys se bhi.

Q6Why consistent hashing instead of hash % N?hash % N ki jagah consistent hashing kyun?Sharding

With hash % N, going from 4 to 5 shards moves about 80% of keys. On a hash ring, a new shard only takes the arcs just before its points, about 1/N of the keys. Virtual nodes (100 to 200 per shard) even out the load. A common alternative is many fixed logical shards (say 1,024) mapped onto physical nodes, as Vitess- and Citus-style systems do.

hash % N me 4 se 5 shards karne pe lagbhag 80% keys move hoti hain. Hash ring pe naya shard sirf apne points se just pehle wale arcs leta hai, lagbhag 1/N keys. Virtual nodes (har shard ke 100 se 200) load barabar karte hain. Common alternative: bahut saare fixed logical shards (jaise 1,024) jo physical nodes pe map hote hain, jaise Vitess aur Citus style systems karte hain.

Q7One shard is hot because of one huge tenant. What do you do?Ek bade tenant ki wajah se ek shard hot hai. Kya karoge?Sharding

Confirm it with per-shard and per-key metrics. Short term: cache that tenant's hot reads and rate-limit abusive traffic. For hot counters, split the key (key#0 to key#15) and sum on read. Long term: move the tenant to a dedicated shard with a directory override in the router.

Per-shard aur per-key metrics se confirm karo. Short term: us tenant ke hot reads cache karo aur abusive traffic rate-limit karo. Hot counters ke liye key split karo (key#0 se key#15) aur read pe sum karo. Long term: router me directory override se tenant ko dedicated shard pe le jao.

Q8When would you pick Cassandra over Postgres?Postgres ki jagah Cassandra kab chunoge?Data modeling

Very high write throughput, data modeled around a few known queries (one table per query), always-on writes across datacenters, and time-series or chat-like data. Not for ad-hoc queries, joins, multi-row transactions, or invariants such as "the balance never goes below zero".

Bahut high write throughput, kuch known queries ke hisaab se model kiya data (har query ki ek table), datacenters ke paar always-on writes, aur time-series ya chat jaisa data. Ad-hoc queries, joins, multi-row transactions, ya "balance kabhi zero se neeche nahi jaayega" jaise invariants ke liye nahi.

Q9A customer was charged twice. Walk through the fix.Customer se do baar paise kat gaye. Fix step by step batao.Consistency

First find the source: a client retry after a timeout, a double submit, or a consumer redelivery. Then add layers:

Pehle source dhoondo: timeout ke baad client retry, double submit, ya consumer redelivery. Phir layers lagao:

  • An idempotency key claimed with a unique insert; retries get the stored response.Unique insert se claim hone wali idempotency key; retry ko stored response milta hai.
  • The same key sent to the payment provider.Wahi key payment provider ko bhi.
  • An inbox table in every consumer, and a unique constraint on the business key (one successful payment per order).Har consumer me inbox table, aur business key pe unique constraint (har order ki ek hi successful payment).
  • A daily reconciliation job against the provider's report, then refund the duplicate.Provider ki report ke against daily reconciliation job, phir duplicate ka refund.
Q10What is the dual-write problem, and how does the outbox fix it?Dual-write problem kya hai, aur outbox ise kaise fix karta hai?Consistency

Writing to the database and publishing to Kafka are two separate operations; one can succeed while the other fails. With an outbox, the event is inserted into an outbox table in the same local transaction as the business row, and a relay (a poller or Debezium CDC) publishes it afterwards. Delivery becomes at-least-once, so consumers must be idempotent.

Database me likhna aur Kafka pe publish karna do alag operations hain; ek succeed aur doosra fail ho sakta hai. Outbox me event business row ke saath same local transaction me outbox table me insert hota hai, aur baad me relay (poller ya Debezium CDC) use publish karta hai. Delivery at-least-once ho jaati hai, isliye consumers idempotent hone chahiye.

Q11Saga or two-phase commit?Saga ya two-phase commit?Consistency

2PC gives atomicity but holds locks across the network, blocks when the coordinator fails, and isn't supported by Kafka or most NoSQL stores. A saga is a chain of local transactions with compensating actions. It is eventually consistent, so you need idempotent steps and visible in-between states such as PAYMENT_PENDING.

2PC atomicity deta hai par network ke paar locks pakde rakhta hai, coordinator fail ho toh block ho jaata hai, aur Kafka ya zyaadatar NoSQL use support nahi karte. Saga local transactions ki chain hai, compensating actions ke saath. Yeh eventually consistent hai, isliye idempotent steps aur PAYMENT_PENDING jaise beech ke visible states chahiye.

Q12Choreography or orchestration for a saga?Saga ke liye choreography ya orchestration?Consistency

Choreography, where services react to each other's events, suits two or three simple steps and keeps services decoupled, but the flow is hard to see and debug. Orchestration, where one component sends commands and tracks state, suits long or branching flows with timeouts and retries, and shows in one place where every order is.

Choreography, jisme services ek doosre ke events pe react karti hain, 2–3 simple steps ke liye theek hai aur services decoupled rehti hain, par flow dekhna aur debug karna mushkil hai. Orchestration, jisme ek component commands bhejta hai aur state track karta hai, lambe ya branching flows, timeouts aur retries ke liye behtar hai, aur ek hi jagah dikhata hai ki har order kahan hai.

Q13After a price update the cache still shows the old price. Why, and how do you fix it?Price update ke baad bhi cache purana price dikha raha hai. Kyun, aur fix kaise?Caching

Usual causes: the cache was changed before the commit, one code path forgot to invalidate, or a reader re-cached an old row it read from a lagging replica. Fix: delete the key after commit, add a delayed second delete or CDC-based invalidation from the WAL, keep a TTL as a safety net, and bump the key version when the cached shape changes.

Aam wajahein: cache commit se pehle badal diya, kisi code path me invalidate bhool gaye, ya kisi reader ne lagging replica se purani row padh ke dobara cache kar di. Fix: commit ke baad key delete karo, delayed second delete ya WAL se CDC-based invalidation lagao, safety net ke liye TTL rakho, aur cached shape badle toh key version bump karo.

Q14What is a cache stampede and how do you prevent it?Cache stampede kya hai aur ise kaise rokte hain?Caching

A hot key expires and thousands of concurrent requests miss together and hit the database. Prevent it with a per-key lock (SET NX with an expiry) so only one request reloads, request coalescing inside each pod, early probabilistic refresh or stale-while-revalidate, and TTL jitter so keys don't expire together.

Ek hot key expire hoti hai aur hazaaron concurrent requests ek saath miss karke database pe girti hain. Bachav: per-key lock (expiry ke saath SET NX) taaki sirf ek request reload kare, har pod ke andar request coalescing, early probabilistic refresh ya stale-while-revalidate, aur TTL jitter taaki keys ek saath expire na hon.

Q15When should you not use CQRS or event sourcing?CQRS ya event sourcing kab use nahi karna chahiye?System design

Simple CRUD domains, small teams, and screens that need read-after-write everywhere. Event sourcing adds event versioning, replay time, snapshots and hard deletes (personal data needs crypto-shredding). A plain relational model plus one denormalized read table often gives most of the benefit.

Simple CRUD domains, chhoti teams, aur aisi screens jinhe har jagah read-after-write chahiye. Event sourcing ke saath event versioning, replay time, snapshots aur mushkil deletes aate hain (personal data ke liye crypto-shredding). Aksar plain relational model + ek denormalized read table se zyaadatar fayda mil jaata hai.

Q16An endpoint runs 201 queries for 200 orders. How do you detect and fix it in Spring?Ek endpoint 200 orders ke liye 201 queries chala raha hai. Spring me detect aur fix kaise karoge?Performance

It's N+1 from lazy loading inside a loop. Detect it by logging SQL or Hibernate statistics in development and asserting a query count in integration tests. Fix it by paging over IDs, then loading those rows with a fetch join or @EntityGraph; set default_batch_fetch_size as a safety net; use DTO projections for read-only screens; turn off open-in-view.

Yeh loop ke andar lazy loading se N+1 hai. Detect: development me SQL ya Hibernate statistics log karo aur integration tests me query count assert karo. Fix: pehle IDs page karo, phir un rows ko fetch join ya @EntityGraph se load karo; safety net ke liye default_batch_fetch_size; read-only screens ke liye DTO projections; open-in-view band karo.

Q17A query suddenly takes 9 seconds. How do you debug it?Ek query achanak 9 second le rahi hai. Debug kaise karoge?Performance

Find it in pg_stat_statements or the slow query log, then run EXPLAIN (ANALYZE, BUFFERS). Look for sequential scans on big tables, estimated and actual rows far apart (stale statistics, so run ANALYZE), sorts spilling to disk, and nested loops with huge loop counts. Fix it with the right composite, expression, partial or covering index, or rewrite the query.

pg_stat_statements ya slow query log me dhoondo, phir EXPLAIN (ANALYZE, BUFFERS) chalao. Dekho: bade tables pe sequential scan, estimated aur actual rows me bada farq (stale statistics, toh ANALYZE chalao), disk pe spill hote sorts, aur bahut bade loop count wale nested loops. Fix: sahi composite, expression, partial ya covering index, ya query rewrite.

Q18Two users buy the last item at the same moment. How do you prevent overselling?Do users ek hi pal me last item khareedte hain. Overselling kaise rokoge?Consistency

With read-then-write in application code, both read 1 and both succeed. Use a conditional atomic UPDATE (SET stock = stock - 1 WHERE sku = ? AND stock >= 1) and check the row count; use SELECT … FOR UPDATE when the logic is complex; or optimistic locking with a retry when contention is low. For flash sales, add expiring reservations or a per-SKU queue.

Application code me read-then-write ho toh dono 1 padhte hain aur dono succeed. Conditional atomic UPDATE use karo (SET stock = stock - 1 WHERE sku = ? AND stock >= 1) aur row count check karo; logic complex ho toh SELECT … FOR UPDATE; contention kam ho toh retry ke saath optimistic locking. Flash sale ke liye expire hone wali reservations ya per-SKU queue.

Q19How do you generate unique IDs across shards?Shards ke paar unique IDs kaise banate ho?Sharding

Snowflake-style IDs (timestamp, node id, sequence): 64-bit, roughly time-ordered, with no coordination per ID. Or UUIDv7, which is time-ordered and needs no node ids. Avoid random UUIDv4 as a clustered primary key, because random inserts split B-tree pages. Per-shard sequences with a step (id % N) work but make resharding painful.

Snowflake-style IDs (timestamp, node id, sequence): 64-bit, lagbhag time-ordered, har ID ke liye koi coordination nahi. Ya UUIDv7, jo time-ordered hai aur node ids nahi maangta. Random UUIDv4 ko clustered primary key mat banao, random inserts B-tree pages split karte hain. Step wale per-shard sequences (id % N) chalte hain par resharding mushkil kar dete hain.
