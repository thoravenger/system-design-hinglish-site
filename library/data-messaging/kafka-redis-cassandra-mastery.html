Topic & Partitions

A topic is a logical stream of records. Split into partitions — the unit of parallelism. Each partition is an append-only log, ordered by offset.

  • Records within a partition are totally ordered
  • Across partitions — only ordering if same key
  • Partition count = max parallelism
Replication & ISR

Each partition has 1 leader + N-1 followers. Replication factor controls durability. ISR (In-Sync Replicas) = followers caught up with leader.

  • replication.factor=3 → survives 2 broker failures
  • min.insync.replicas=2 → needs 2 acks to commit
  • Leader fails → one ISR promoted
Offset & Log

Each message has a monotonically increasing offset per partition. Consumers track their own offset. Kafka retains messages by time or size — not by consumption.

  • auto.offset.reset=earliest/latest
  • Replay possible by resetting offset
  • Compacted topics — keep last per key

@Bean
public KafkaProducer<String, String> sharedProducer() {
    Properties props = new Properties();
    props.put("bootstrap.servers",  "broker1:9092,broker2:9092");
    props.put("key.serializer",     "...StringSerializer");
    props.put("value.serializer",   "...StringSerializer");

    // Throughput tuning
    props.put("batch.size",         65536);   // 64 KB batch
    props.put("linger.ms",          10);      // wait 10ms to fill batch
    props.put("compression.type",   "snappy");// compress batches
    props.put("buffer.memory",       33554432);// 32MB accumulator buffer

    // Reliability tuning
    props.put("acks",               "all");   // wait for all ISR to ack
    props.put("retries",            Integer.MAX_VALUE);
    props.put("enable.idempotence", true);    // exactly-once at producer
    props.put("max.in.flight.requests.per.connection", 5);

    return new KafkaProducer<>(props);
}

// Multiple app threads safely sharing ONE producer:
class OrderEventPublisher {
    private final KafkaProducer<String, String> producer; // shared, thread-safe

    public Future<RecordMetadata> send(Order order) {
        ProducerRecord<String, String> rec =
            new ProducerRecord<>("orders", order.id(), toJson(order));

        // Async send with callback
        return producer.send(rec, (metadata, ex) -> {
            if (ex != null) {
                log.error("Send failed: {}", ex.getMessage());
            } else {
                log.debug("Sent to partition={} offset={}",
                    metadata.partition(), metadata.offset());
            }
        });
    }
}

// ── Consumer — NOT thread-safe, multi-thread patterns ────────────────

// Pattern 1: One consumer per thread (simplest, recommended)
class ConsumerRunnable implements Runnable {
    private final KafkaConsumer<String, String> consumer;

    ConsumerRunnable(String groupId) {
        Properties props = new Properties();
        props.put("bootstrap.servers",         "broker1:9092");
        props.put("group.id",                  groupId);
        props.put("key.deserializer",           "...StringDeserializer");
        props.put("value.deserializer",         "...StringDeserializer");
        props.put("auto.offset.reset",          "earliest");
        props.put("enable.auto.commit",         false);     // manual commit!
        props.put("max.poll.records",           500);       // batch size
        props.put("max.poll.interval.ms",       300000);    // 5 min processing time
        props.put("session.timeout.ms",         45000);
        props.put("heartbeat.interval.ms",      15000);
        consumer = new KafkaConsumer<>(props);
    }

    @Override
    public void run() {
        consumer.subscribe(List.of("orders"));
        try {
            while (!Thread.currentThread().isInterrupted()) {
                ConsumerRecords<String, String> records =
                    consumer.poll(Duration.ofMillis(100));

                for (ConsumerRecord<String, String> record : records) {
                    process(record);  // must finish before max.poll.interval.ms
                }

                // Manual commit AFTER processing
                consumer.commitSync();  // or commitAsync()
            }
        } finally {
            consumer.close();  // triggers rebalance, commits offsets
        }
    }
}

// Pattern 2: Consumer + Worker thread pool (decouple I/O from processing)
class ConsumerWithWorkers {
    private final ExecutorService workers = Executors.newFixedThreadPool(8);

    void run() {
        while (true) {
            ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
            // ⚠️  Do NOT commit until workers finish — track futures!
            List<Future<?>> futures = new ArrayList<>();
            for (ConsumerRecord<String, String> r : records)
                futures.add(workers.submit(() -> process(r)));
            for (Future<?> f : futures) f.get(); // wait all workers done
            consumer.commitSync();
        }
    }
}

// Strategy 1: Ordered producer (same key → same partition)
class OrderedProducer {
    private final KafkaProducer<String, String> producer;

    void sendOrder(Order order) {
        // Same customerId → same partition → ordered delivery for that customer
        producer.send(new ProducerRecord<>(
            "orders",
            order.customerId(),   // KEY determines partition
            toJson(order)
        ));
    }
}

// Strategy 2: Transactional producer (exactly-once)
class TransactionalProducer {
    private final KafkaProducer<String, String> producer;

    TransactionalProducer() {
        Properties p = new Properties();
        p.put("transactional.id", "order-producer-1"); // unique per producer
        p.put("enable.idempotence", true);
        p.put("acks", "all");
        producer = new KafkaProducer<>(p);
        producer.initTransactions();
    }

    void sendAtomically(List<Order> orders) {
        producer.beginTransaction();
        try {
            for (Order o : orders) {
                producer.send(new ProducerRecord<>("orders", o.id(), toJson(o)));
                producer.send(new ProducerRecord<>("audit", o.id(), "CREATED"));
            }
            producer.commitTransaction(); // atomic: all or nothing
        } catch (Exception e) {
            producer.abortTransaction();  // none visible to consumers
            throw e;
        }
    }
}

// ── Dead Letter Queue pattern ─────────────────────────────────────────
void processWithDLQ(ConsumerRecord<String, String> record) {
    try {
        processRecord(record);
    } catch (NonRetryableException e) {
        // Send to DLQ for human inspection
        producer.send(new ProducerRecord<>(
            "orders.DLQ",
            record.key(),
            record.value()
        ));
        log.error("Sent to DLQ: key={} error={}", record.key(), e.getMessage());
    }
}

@Configuration
public class KafkaConfig {

    @Bean
    public ConsumerFactory<String, OrderEvent> consumerFactory() {
        Map<String, Object> config = new HashMap<>();
        config.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG,  "broker1:9092");
        config.put(ConsumerConfig.GROUP_ID_CONFIG,           "order-service");
        config.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG,   "earliest");
        config.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG,  false);
        config.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG,    100);
        return new DefaultKafkaConsumerFactory<>(config,
            new StringDeserializer(),
            new JsonDeserializer<>(OrderEvent.class));
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> listenerFactory() {
        var factory = new ConcurrentKafkaListenerContainerFactory<String, OrderEvent>();
        factory.setConsumerFactory(consumerFactory());
        factory.setConcurrency(3);   // 3 consumer threads = 3 KafkaConsumer instances
        factory.getContainerProperties().setAckMode(AckMode.MANUAL_IMMEDIATE);

        // Error handler with retry + DLQ
        factory.setCommonErrorHandler(
            new DefaultErrorHandler(
                new DeadLetterPublishingRecoverer(kafkaTemplate), // send to .DLT topic
                new FixedBackOff(1000L, 3)  // retry 3 times, 1s apart
            )
        );
        return factory;
    }
}

// ── @KafkaListener — all options ─────────────────────────────────────

@Service
public class OrderConsumer {

    // Basic listener
    @KafkaListener(topics = "orders", groupId = "order-service")
    public void consume(OrderEvent event) {
        processOrder(event);
    }

    // Manual ack + full record access
    @KafkaListener(
        topics = "orders",
        groupId = "order-service",
        concurrency = "3"   // overrides factory — 3 threads for THIS listener
    )
    public void consumeWithAck(
            @Payload  OrderEvent       event,
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
            @Header(KafkaHeaders.OFFSET) long offset,
            Acknowledgment ack) {
        try {
            processOrder(event);
            ack.acknowledge(); // commit only on success
        } catch (Exception e) {
            log.error("Failed partition={} offset={}", partition, offset, e);
            // Don't ack → will be redelivered
        }
    }

    // Batch listener
    @KafkaListener(topics = "orders", containerFactory = "batchListenerFactory")
    public void consumeBatch(List<OrderEvent> events) {
        processInBatch(events);     // up to max.poll.records at once
    }
}

Redis Architecture — Data Types & Commands

String

Binary-safe, max 512 MB. Integers auto-detected for INCR/DECR.

Use: cache, counters, feature flags, sessions

List

Doubly-linked list. O(1) push/pop at both ends. O(n) random access.

Use: queues, timelines, recent items

Hash

Field-value map inside one key. Up to 4B fields.

Use: objects, user profiles, configs

Set

Unordered unique strings. O(1) add/remove/contains. Set operations.

Use: tags, unique visitors, follows

Sorted Set (ZSet)

Unique members each with float score. Sorted by score. O(log n) ops.

Use: leaderboards, rate limiting, range queries

Stream

Append-only log with consumer groups. Like Kafka inside Redis.

Use: event sourcing, activity feeds, logs

@Service
public class RedisService {
    private final RedisTemplate<String, Object> redis;
    private final StringRedisTemplate               srt;

    // ── String ops ──────────────────────────────────────────────────
    void stringOps() {
        ValueOperations<String, Object> ops = redis.opsForValue();
        ops.set("user:1", user, Duration.ofHours(1));   // with TTL
        Object val = ops.get("user:1");
        ops.increment("counter:visits");              // atomic INCR
        ops.setIfAbsent("lock:order", "1", Duration.ofSeconds(30)); // SETNX
    }

    // ── Hash ops ────────────────────────────────────────────────────
    void hashOps() {
        HashOperations<String, String, Object> hash = redis.opsForHash();
        hash.put("user:1:profile", "name", "Alice");
        hash.put("user:1:profile", "age", 30);
        hash.multiSet("user:1:profile", Map.of("city","NY","plan","PRO"));
        Map<String,Object> all = hash.entries("user:1:profile");
        hash.increment("user:1:stats", "logins", 1);
    }

    // ── Sorted Set — Leaderboard ─────────────────────────────────────
    void leaderboard() {
        ZSetOperations<String, Object> zset = redis.opsForZSet();
        zset.add("game:scores", "Alice", 9500.0);
        zset.incrementScore("game:scores", "Alice", 100.0);
        Set<Object> top10 = zset.reverseRange("game:scores", 0, 9);
        Long rank = zset.reverseRank("game:scores", "Alice");
    }

    // ── List — Message Queue ─────────────────────────────────────────
    void queue() {
        ListOperations<String, Object> list = redis.opsForList();
        list.rightPush("task:queue", task);         // enqueue
        Object task = list.leftPop("task:queue", Duration.ofSeconds(5)); // blocking pop
    }
}

// ── Redis Replication — how data syncs between servers ───────────────
//
// 1. FULL SYNC (initial or after long disconnect):
//    Primary → BGSAVE → RDB snapshot → send to replica
//    Replica → load RDB → ready
//
// 2. PARTIAL SYNC (replication backlog):
//    Primary keeps a replication buffer (default 1MB)
//    Replica reconnects → sends replication offset
//    Primary sends only missed commands (no full RDB)
//
// 3. Command propagation:
//    Every write command → logged in replication stream
//    Sent to ALL replicas asynchronously
//
// CONSISTENCY: Redis replication is ASYNCHRONOUS by default!
// Primary can acknowledge a write BEFORE replica has it
// If primary crashes → replica missing last writes = DATA LOSS
//
// WAIT command — make replication synchronous for specific writes:
// WAIT 1 1000   → wait for 1 replica to ack, timeout 1000ms
// Returns number of replicas that acknowledged

// Spring Data — using WAIT for critical writes:
void criticalWrite(String key, Object value) {
    redis.opsForValue().set(key, value);
    // Ensure at least 1 replica has the data before confirming
    redis.execute(RedisServerCommands::wait, 1, 1000);
}

@Service
public class ConsistentRedisService {

    // Pattern 1: Write to primary, read from primary (strong consistency)
    @Autowired
    private RedisTemplate<String, Object> primaryTemplate;    // write here
    @Autowired
    private RedisTemplate<String, Object> replicaTemplate;   // read here (eventual)

    public void write(String key, Object val) {
        primaryTemplate.opsForValue().set(key, val, Duration.ofMinutes(30));
    }

    public Object readFromReplica(String key) {
        // May return stale data if replication lagging
        return replicaTemplate.opsForValue().get(key);
    }

    // Pattern 2: Cache-Aside — database is source of truth
    public User getUser(long id) {
        String key = "user:" + id;
        User cached = (User) primaryTemplate.opsForValue().get(key);
        if (cached != null) return cached;

        User user = userRepo.findById(id).orElseThrow();
        primaryTemplate.opsForValue().set(key, user, Duration.ofMinutes(10));
        return user;
    }

    // Cache invalidation — delete from BOTH nodes to maintain consistency
    public void invalidate(String key) {
        primaryTemplate.delete(key);
        // Replica will sync automatically, but if you have direct replica access:
        replicaTemplate.delete(key); // belt-and-suspenders approach
    }
}

Redis Atomicity — Transactions, Lua Scripts & Patterns

🔑
Redis atomicity insight: Redis is single-threaded for command execution. This means individual commands are ALWAYS atomic. The challenge is making multiple commands atomic together.
// ── Individual commands are atomic ────────────────────────────────────
// INCR key          → atomic read-modify-write, no race condition
// SETNX key value   → atomic check-then-set
// GETSET key value  → atomic get old + set new
// GETDEL key        → atomic get + delete
// LPUSH + LLEN      → NOT atomic together (two separate commands)

// ── MULTI/EXEC — Redis transactions ──────────────────────────────────
// MULTI → queue commands
// EXEC  → execute all atomically (no other commands can interleave)
// DISCARD → abort the transaction
//
// ⚠️  NOT the same as SQL transactions!
// - No rollback on runtime errors (wrong type etc)
// - If one command fails, rest STILL execute
// - No isolation between MULTI and EXEC (other clients can write)

// Spring Data Redis — MULTI/EXEC:
List<Object> results = redis.execute(new SessionCallback<>() {
    @Override
    public List<Object> execute(RedisOperations ops) {
        ops.multi();                              // BEGIN transaction
        ops.opsForValue().set("balance:alice", -100);
        ops.opsForValue().set("balance:bob", +100);
        return ops.exec();                        // EXECUTE atomically
    }
});

// ── WATCH — Optimistic locking (CAS pattern) ─────────────────────────
// WATCH keys → if any key changes before EXEC → EXEC returns null (abort)
// Retry in application code

boolean debit(String accountKey, long amount) {
    int maxRetries = 5;
    for (int i = 0; i < maxRetries; i++) {
        List<Object> results = redis.execute(new SessionCallback<>() {
            public List<Object> execute(RedisOperations ops) {
                ops.watch(List.of(accountKey));           // WATCH
                long balance = (Long) ops.opsForValue().get(accountKey);
                if (balance < amount) return null;        // insufficient funds
                ops.multi();
                ops.opsForValue().decrement(accountKey, amount);
                return ops.exec();                        // null if WATCH triggered
            }
        });
        if (results != null) return true;   // success
        // null → someone else modified → retry
    }
    return false; // too many conflicts
}

// ── Lua Scripts — truly atomic, no interleaving possible ─────────────
// Lua runs as a single atomic operation — BEST for complex atomic logic

private static final String TRANSFER_SCRIPT = """
    local from_bal = tonumber(redis.call('GET', KEYS[1]))
    local amount   = tonumber(ARGV[1])
    if from_bal < amount then
        return {err = 'insufficient_funds'}
    end
    redis.call('DECRBY', KEYS[1], amount)
    redis.call('INCRBY', KEYS[2], amount)
    return 1
    """;

void transfer(String from, String to, long amount) {
    DefaultRedisScript<Long> script = new DefaultRedisScript<>(TRANSFER_SCRIPT, Long.class);
    Long result = redis.execute(script,
        List.of("balance:" + from, "balance:" + to),
        amount.toString()
    );
    if (result == null) throw new InsufficientFundsException();
}

// ── Distributed Lock with Lua (Redlock pattern) ──────────────────────
private static final String UNLOCK_SCRIPT = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    else
        return 0
    end
    """;

@Service
public class RedisDistributedLock {

    public boolean tryLock(String lockKey, String lockValue, long ttlMs) {
        Boolean acquired = redis.opsForValue()
            .setIfAbsent(lockKey, lockValue, Duration.ofMillis(ttlMs));
        return Boolean.TRUE.equals(acquired);
    }

    public void unlock(String lockKey, String lockValue) {
        // Lua ensures we only delete OUR lock (not one acquired by another process)
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(UNLOCK_SCRIPT, Long.class);
        redis.execute(script, List.of(lockKey), lockValue);
    }

    // Use Redisson for production distributed locks:
    public void withRedisson(RedissonClient redisson) throws Exception {
        RLock lock = redisson.getLock("order:lock:123");
        lock.lock(10, TimeUnit.SECONDS);    // auto-expire after 10s
        try {
            processOrder();
        } finally {
            lock.unlock();
        }
    }
}

Cassandra Architecture — How Data is Stored

Cassandra Cluster — Ring Architecture (Masterless)
Node 1 (tokens: 0-25%)
Node 4 (tokens: 75-100%)
⟳
Node 2 (tokens: 25-50%)
Node 3 (tokens: 50-75%)
All nodes equal — no master. Gossip protocol for cluster state.
// ── How data is written to Cassandra ─────────────────────────────────
//
// Step 1: Client sends write to ANY node (Coordinator)
// Step 2: Coordinator hashes partition key → determines replica nodes
// Step 3: Coordinator sends write to ALL replica nodes
// Step 4: Each replica node:
//   a. Writes to Commit Log (WAL — sequential, always on disk)
//   b. Writes to MemTable (in-memory sorted structure)
//   c. Returns ACK when BOTH done
// Step 5: MemTable flushes to SSTable (disk) when full
// Step 6: SSTables compacted periodically (remove tombstones, merge)
// Step 7: Coordinator waits for W replica ACKs (consistency level)

// ── How data is READ from Cassandra ──────────────────────────────────
// Step 1: Client sends read to Coordinator
// Step 2: Coordinator determines replicas for partition key
// Step 3: Coordinator sends digest request to R replicas
// Step 4: All replicas check MemTable → Row cache → Block cache → SSTable
// Step 5: If digests match → return data
// Step 6: If digests differ → read repair: fetch full data from all, merge

// ── SSTable structure ─────────────────────────────────────────────────
// Data.db     — actual column data
// Index.db    — partition key → offset in Data.db
// Filter.db   — Bloom filter (is partition key in this file?)
// Summary.db  — sparse index of Index.db
// Statistics.db — partition size, column stats
// Bloom filter prevents disk reads for non-existent keys (O(1) probably-no)

// ── CQL Data Model ────────────────────────────────────────────────────
-- Primary key = Partition key + Clustering columns
CREATE TABLE orders (
    customer_id  UUID,              -- partition key (which node?)
    order_id     TIMEUUID,          -- clustering col (sort order within partition)
    created_at   TIMESTAMP,
    total        DECIMAL,
    status       TEXT,
    PRIMARY KEY ((customer_id), order_id)  -- (()) = partition key
) WITH CLUSTERING ORDER BY (order_id DESC);  -- latest orders first

-- All orders for a customer → ONE partition (collocated, fast)
SELECT * FROM orders WHERE customer_id = ? LIMIT 10;

-- Bad: full scan (no partition key) → scatter gather → slow!
SELECT * FROM orders WHERE status = 'PENDING';  -- ❌ requires ALLOW FILTERING

Consistent Hashing — How Cassandra Routes Data

Token Ring — Murmur3 Partitioner (default)
Token range: -2^63 to +2^63 (-9223372036854775808 to +9223372036854775807)
Node A owns: -9223... to -4611... | Node B owns: -4611... to 0
Node C owns: 0 to +4611... | Node D owns: +4611... to +9223...
Write("order:123") → murmur3("order:123") = -2847362... → falls in Node A's range → route to Node A (+ replicas B, C) 
// ── Partitioner types ─────────────────────────────────────────────────
//
// Murmur3Partitioner (DEFAULT, recommended)
// - hash = murmur3(partition_key)
// - Uniform distribution, fast
// - NOT ordered → cannot do range queries on partition key
//
// ByteOrderedPartitioner (NOT recommended)
// - Stores data in key order (lexicographic)
// - Allows range queries on partition key
// - Problem: hot spots — sequential keys all go to same node
//   e.g. timestamps: 2024-01-01, 2024-01-02, ... all to same few nodes
//
// RandomPartitioner (legacy)
// - MD5 hash — deprecated, use Murmur3

// ── Virtual nodes (vnodes) — why they matter ──────────────────────────
//
// WITHOUT vnodes (old way):
// Each physical node owns ONE contiguous token range
// Add a node → must manually rebalance half the ring → slow, manual
//
// WITH vnodes (default since Cassandra 1.2):
// Each physical node owns MANY small token ranges (256 by default)
// Add a node → it takes a few vnodes from each existing node → automatic
// Better load distribution even with heterogeneous hardware
//
// num_tokens: 256   ← in cassandra.yaml (vnodes per node)

// ── Replication Strategy ──────────────────────────────────────────────
--
-- SimpleStrategy (single datacenter only)
CREATE KEYSPACE myapp WITH replication = {
    'class': 'SimpleStrategy',
    'replication_factor': 3   -- 3 copies on next 3 clockwise nodes
};

-- NetworkTopologyStrategy (production, multi-DC)
CREATE KEYSPACE myapp WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'dc1': 3,   -- 3 replicas in datacenter 1
    'dc2': 2    -- 2 replicas in datacenter 2
};
-- Ensures replicas spread across racks within each DC

// ── Consistency Levels — tunable per operation ────────────────────────
//
// ANY    — accept write even if only hinted handoff succeeds (low durability)
// ONE    — 1 replica acks write / responds read
// QUORUM — majority of replicas: ceil(RF/2) + 1
// LOCAL_QUORUM — quorum within local DC (multi-DC deployments)
// ALL    — ALL replicas must respond (highest consistency, lowest availability)
//
// Strong consistency: W + R > RF
// With RF=3: QUORUM write (2) + QUORUM read (2) = 4 > 3 ✅ strongly consistent
// With RF=3: ONE write + ONE read = 2 < 3 ❌ may read stale data

Cassandra Scaling — Add & Remove Nodes Dynamically

Adding a Node (Scale Out)
  1. Start new node pointing to any seed node
  2. Node joins ring, gets assigned token ranges (vnodes)
  3. Streaming begins: existing nodes stream data to new node
  4. New node starts serving reads/writes for its ranges
  5. Run nodetool cleanup on old nodes to remove migrated data

Zero downtime — cluster serves traffic throughout

Removing a Node (Scale In)
  1. nodetool decommission on the node being removed
  2. Node streams its data to remaining nodes
  3. Node leaves the ring once streaming complete
  4. For dead nodes: nodetool removenode <host-id>
  5. Run nodetool repair to ensure full consistency

Zero downtime — data re-distributed automatically

// ── Cassandra Anti-Patterns — what NOT to do ─────────────────────────

// ❌ Unbounded partitions — millions of rows in one partition
// Partition too large → single node becomes hot spot
// Fix: bucket by time period
CREATE TABLE events_by_day (
    user_id    UUID,
    day        DATE,          -- bucket: partition per user per day
    event_id   TIMEUUID,
    data       TEXT,
    PRIMARY KEY ((user_id, day), event_id)  -- compound partition key
);

// ❌ Secondary index on high-cardinality columns
// Secondary index → scatter-gather across all nodes = slow
// Fix: create a separate lookup table (denormalization is OK in Cassandra)
CREATE TABLE orders_by_status (
    status     TEXT,          -- partition key: limited cardinality
    order_id   TIMEUUID,
    customer_id UUID,
    PRIMARY KEY (status, order_id)
);

// ❌ ALLOW FILTERING — forces coordinator to scan all nodes
SELECT * FROM orders WHERE total > 100 ALLOW FILTERING;  // ❌ never in prod

// ❌ Using BATCH for performance (Cassandra BATCH ≠ SQL BATCH)
// Cassandra BATCH is only for atomicity on SAME partition
// Multi-partition BATCH → coordinator bottleneck → slower than individual writes
// Use LOGGED BATCH only for same-partition mutations needing atomicity

// ── Data modeling rules for Cassandra ───────────────────────────────
// 1. Model by query (not by entities) — design tables for access patterns
// 2. Denormalize aggressively — storage is cheap, JOIN is impossible
// 3. One table per query pattern — if you have 3 queries, you may need 3 tables
// 4. Keep partitions under 100MB / 100K rows (sweet spot)
// 5. Partition key should have high cardinality + uniform distribution
