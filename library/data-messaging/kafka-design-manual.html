00

Kafka kyu chahiye? Sync coupling ka dard

Har system design interview yahi se shuru hota hai: "aapko Kafka kyu laga?" Agar aapka jawab "scalable hai" hai, to interview wahi ruk jaata hai. Real answer coupling aur backpressure ke baare me hai.

Problem

Order service directly 6 downstream services ko call karti hai

Checkout ke ek HTTP request me: inventory reserve, payment capture, email, SMS, analytics, fraud-check. Sab synchronous.

  • Email service 3s slow hui → checkout latency 3s badh gayi.
  • Analytics down → order fail ho gaya, jabki analytics business-critical hi nahi tha.
  • Naya consumer add karna hai → order service ka code change + redeploy.
  • Traffic spike me har downstream service ko same peak QPS jhelna pada.
  • Retry logic 6 jagah duplicate, har jagah alag bug.
Simple meinEk aadmi ke fail hone se poori line ruk jaati hai. Failure isolate nahi hai, aur speed sabse slow service decide karti hai.
Solution

Order service sirf ek event likhti hai: OrderCreated

Producer broker ko event deta hai aur turant return karta hai. Consumers apni speed se padhte hain, apne offsets khud track karte hain.

  • Decoupling: producer ko pata hi nahi kitne consumers hain.
  • Buffering: spike disk pe absorb hota hai, downstream pe nahi.
  • Replay: naya service purane offset se poora history padh sakta hai.
  • Fan-out: ek write, N independent consumer groups.
  • Durability: event disk pe replicated hai, memory queue ki tarah gayab nahi hota.
Simple meinOrder service bolti hai "yeh hua", aur aage badh jaati hai. Kisko-kya-karna-hai wo consumer ka problem hai, producer ka nahi.

Apply when

Multiple independent consumers, replay ki zarurat, spiky traffic, event history hi ek asset hai (audit, ML training, CDC).

Ignore when

Caller ko turant answer chahiye (auth check, price quote). Request-response ko event bana dena latency + complexity dono badhata hai. 2 services, 50 msg/sec → SQS ya ek DB table kaafi hai.

Cost you pay

Eventual consistency, duplicate handling, ordering sirf partition ke andar, aur ek naya distributed system jise on-call support karna padega.

Interview line"Kafka mainly do problem solve karta hai: producer ko consumers se decouple karna, aur consumption ko durable buffer ke peeche rakhna taaki slow consumer producer ko block na kare. Agar in dono ki zarurat nahi hai, Kafka overkill hai."
01

Topic, partition, offset — poora Kafka isi teen se bana hai

Kafka ka core data structure ek append-only file hai. Baaki sab (replication, consumer groups, compaction) isi file ke upar layers hain.

Problem

Traditional queue: message padha, message gaya

RabbitMQ/ActiveMQ style broker me broker har consumer ke liye per-message state rakhta hai — delivered, acked, in-flight.

  • Broker ko har message ka status track karna padta hai → memory + random I/O.
  • Message consume hote hi delete → replay impossible.
  • Do alag teams ko same message chahiye? Broker-side fan-out queues banao.
  • Throughput broker ke bookkeeping se bandha hua hai.
Simple meinQueue ek "postbox" hai — letter uthaya to khatam. Aap kal wapas aakar wahi letter dobara nahi padh sakte.
Solution

Log + client-side cursor

Topic ko N partitions me toda jaata hai. Har partition ek ordered, immutable, append-only sequence hai. Har record ka ek offset hota hai — bas ek badhta hua number.

  • Broker per-message state nahi rakhta — sirf file me append karta hai (sequential write, bahut fast).
  • "Kahan tak padha" ye consumer ka offset hai, broker ka nahi.
  • Read = file me ek position se sequential scan. Delete = time/size based, consumption based nahi.
  • Partitions = parallelism ki unit. 12 partitions → max 12 consumers ek group me.
Simple meinKafka ek notebook hai jisme sirf aage likha jaata hai. Har reader apna bookmark khud rakhta hai. Isliye 10 log same page alag-alag time pe padh sakte hain.

Apply when

Partition count = expected peak throughput ÷ per-partition throughput, phir 2–3x headroom. Ordering key-wise chahiye to key hashing pe bharosa karo, global order pe nahi.

Ignore when

"Safety ke liye 1000 partitions bana dete hain" — mat karo. Har partition = open file handles, memory, replication traffic, aur rebalance time. Partitions badhana easy hai, ghatana nahi.

Cost you pay

Global ordering chali gayi. Sirf ek partition ke andar order guarantee hai. Agar poore topic ka strict order chahiye to 1 partition = 1 consumer = koi parallelism nahi.

02

Key hashing — kaunsa record kis partition me jaayega

Ordering ka poora control isi ek line pe hai: partition = murmur2(key) % numPartitions. Interview me yahi sabse zyada pucha jaata hai.

Problem

Same order ke events alag-alag partitions me chale gaye

Team ne key null chhod di. Kafka ne round-robin (sticky) partitioning kar di.

  • OrderCreated P0 me, OrderCancelled P3 me.
  • Consumer-A ne P3 pehle process kar liya → cancel pehle, create baad me.
  • Result: cancelled order dobara active ho gaya. Classic race condition.
  • Doosri taraf: kisi ne key = country rakhi. India ne 70% traffic diya → ek partition garam, baaki idle. Hot partition.
Simple meinBina key ke Kafka aapke events ko random lanes me daal dega. Aur galat key rakhoge to sab traffic ek hi lane me ghus jaayega.
Solution

Key ko entity-id banao, aur cardinality check karo

Kafka same key ko hamesha same partition me bhejta hai (jab tak partition count na badle). Isliye key = wo entity jiske andar order matter karta hai.

  • key = orderId → ek order ke saare events ek hi partition, perfect order.
  • Cardinality high honi chahiye (lakhs of orders), taaki distribution even rahe.
  • Hot key hai (ek celebrity seller)? Composite key: sellerId + "#" + (hash(userId) % 8) — 8 sub-lanes.
  • Partition count badalne se mapping toot jaati hai — isliye topic ka partition count din ek se soch ke rakho.
Simple meinKey wo cheez hai jiske andar sequence bigadna nahi chahiye. Order ke events? orderId. User ka wallet? userId. Aur dhyaan rakho ki wo key thodi si nahi, lakhon values leti ho.

Apply when

Per-entity ordering business ke liye zaroori ho — payments, wallet ledger, order lifecycle, CDC per row.

Ignore when

Pure telemetry/logs/metrics — wahan ordering matter nahi karta. Key null rakho, sticky partitioner batching better karega aur throughput zyada milega.

Cost you pay

Keyed traffic skew la sakta hai. Ek slow key poore partition ko block karti hai (head-of-line blocking) — us partition ka consumer atka to peeche sab atke.

GotchaJava client murmur2 hash use karta hai, Python/Go clients thodi alag default de sakte hain. Multi-language producers ek hi topic me likh rahe hain to explicit partitioner likho, warna same key alag partition me jaa sakti hai.
03

Producer internals — "save karo, ruko mat"

Producer ka send() network call nahi hai. Wo ek in-memory buffer me record daalta hai aur Future return kar deta hai. Poori throughput story yahi buffer hai.

Problem

Har event pe send().get() — blocking write

Developer ne "safe" rehne ke liye har send ke baad .get() laga diya.

  • Har message = ek alag network round trip. 1 record per request.
  • Throughput ~2k msg/s pe atak gaya, jabki hardware 200k+ handle kar sakta tha.
  • Checkout API ki p99 latency broker ke p99 se bandh gayi.
  • Broker slow hua to poora request thread pool bhar gaya → app down.
Simple meinHar chitthi ke liye alag courier bhejna. Courier late hua to aap bhi khade rahoge. Yahi .get() karta hai.
Solution

Async send + callback, batching broker ke bahar hoti hai

Internally: Serializer → Partitioner → RecordAccumulator (per-partition batches) → Sender thread → broker.

  • batch.size (default 16KB): batch bhar gaya to turant jaayega.
  • linger.ms (default 0): thoda ruk kar aur records jodna. 5–20ms rakho — throughput 5–10x jump karta hai.
  • compression.type=lz4/zstd: batch pe compress hota hai, isliye badi batch = better ratio.
  • buffer.memory (32MB) bhar gaya to send() khud block karega — yahi natural backpressure hai.
  • Result callback me handle karo, main thread free rakho.
Simple meinSab chitthiyan ek bori me daalo, bori bhar jaaye ya 10ms ho jaaye — tab ek hi courier bhej do. Aap tab tak agla kaam karte raho, delivery ka SMS (callback) baad me aa jaayega.

Apply when

High-throughput pipelines: clickstream, logs, IoT, CDC. linger.ms=10–50, batch.size=64KB–256KB, compression=zstd.

Ignore when

Low-volume, latency-critical control events (fraud block signal). Wahan linger.ms=0 rakho — batching ka faayda hi nahi milega, sirf delay lagega.

Cost you pay

Async ka matlab hai in-flight data. Process crash hua to buffer ke records gaye. Isliye critical events pe acks=all + callback me DB outbox fallback, aur shutdown pe flush().

acks ka matlabacks=0 fire-and-forget (metrics). acks=1 sirf leader ne likha (leader crash = data loss window). acks=all + min.insync.replicas=2 = production default for anything you cannot lose.
04

Idempotent producer & exactly-once — duplicate kaise rukta hai

Retry hamesha duplicate banata hai. Kafka isko broker-side sequence numbers se solve karta hai, na ki "trust the client" se.

Problem

Ack raaste me kho gaya, producer ne retry kiya

Broker ne record likh liya, phir ack bhejte waqt network blip ho gaya. Producer ko lagta hai fail hua, wo dobara bhejta hai.

  • Same payment event 2 baar log me → user ka 2 baar paisa kata.
  • retries>0 + max.in.flight=5 ke saath order bhi bigad sakta hai: batch-1 fail, batch-2 pass, batch-1 retry — sequence ulta.
  • App-level dedupe har consumer me alag se likhna pada.
Simple meinAapne paisa bhej diya, receipt nahi mili, aapne dobara bhej diya. Bank ke paas do entries hain. Kafka bina idempotency ke exactly aisa hi karta hai.
Solution

PID + per-partition sequence number

enable.idempotence=true (Kafka 3.x me default) karte hi:

  • Producer ko broker se ek Producer ID (PID) milta hai.
  • Har (PID, partition) ke liye ek monotonic sequence number chalta hai.
  • Broker last 5 sequence yaad rakhta hai. Duplicate seq aaya → chup-chaap drop, ack wapas. Dedupe broker pe hota hai.
  • Out-of-order seq aaya → error, isliye retries ke baad bhi order safe hai.
  • Isse acks=all, retries=MAX, max.in.flight≤5 automatically set hote hain.
Simple meinHar producer ko ek ID milti hai aur har message pe ek ginti. Broker bolta hai "yeh ginti to already aa chuki hai, dobara nahi likhunga" — aur phir bhi OK bol deta hai taaki producer khush rahe.

Apply when

Hamesha on rakho — cost near-zero hai. Poora exactly-once (transactions) tab jab Kafka-to-Kafka processing ho: read → transform → write, ek atomic unit me.

Ignore when

Transactions ko external side-effects ke liye mat use karo. Kafka transaction aapke HTTP call ya third-party payment API ko rollback nahi kar sakta. Wahan consumer-side idempotency hi asli jawab hai.

Cost you pay

Transactions ~3–20% throughput leti hain, consumer ko read_committed chahiye, aur LSO (last stable offset) ki wajah se latency badhti hai. Idempotency alone almost free hai.

Sabse important nuanceIdempotent producer sirf ek producer session ke retries ka duplicate rokta hai. Agar aapki app crash hokar restart hui aur wahi event dobara bheja, to woh naya PID hai — Kafka ko pata nahi chalega. Isliye end-to-end safety ke liye consumer side pe business-key dedupe (eventId unique index) rakhna hi padta hai.
05

Replication, ISR aur leader election

Durability ka poora khel do numbers pe hai: replication.factor aur min.insync.replicas. Interview me inka combination pucha jaata hai, individual value nahi.

Problem

RF=3 tha, phir bhi data chala gaya

Team ne replication.factor=3 set kiya aur maan liya ki safe hain.

  • acks=1 tha → leader ne likha, followers ne copy nahi kiya, leader mar gaya. Data gone.
  • min.insync.replicas=1 tha → 2 followers lag gaye, ISR shrink hokar 1 ho gaya, phir bhi writes accept hote rahe. Single point of failure.
  • unclean.leader.election.enable=true tha → out-of-sync follower leader ban gaya, uske paas jo records nahi the wo permanently gaye.
Simple meinTeen copies hone ka matlab yeh nahi ki teeno me likha gaya. Kitni copies me likhna zaroori hai — wo alag setting hai.
Solution

RF=3 + min.insync.replicas=2 + acks=all + unclean=false

Har partition ka ek leader hota hai; followers usse fetch karte hain (pull model). Jo followers leader ke kaafi paas hain wo ISR (In-Sync Replicas) me hain.

  • Write tabhi commit hoti hai jab saare ISR members ne likha ho.
  • ISR < min.insync.replicas → producer ko NotEnoughReplicas error. Write fail hoti hai, data loss nahi hota.
  • Consumer sirf high watermark tak padh sakta hai — yani jo replicate ho chuka. Isliye uncommitted data kabhi dikhta nahi.
  • Leader mara → controller ISR me se hi naya leader chunta hai, koi data peeche nahi chhutta.
  • RF=3 me 1 broker ka loss tolerate hota hai bina availability khoye.
Simple meinRF = kitni copies rakhni hain. min.insync = kitni copies me likhna zaroori hai. acks=all = "jab tak zaroori copies na ho jaayein, mujhe OK mat bolna." Teeno chahiye, ek akela kaafi nahi.

Apply when

Financial / order / audit data: RF=3, min.insync=2, acks=all, unclean=false. Multi-AZ me rack awareness on karo taaki 3 copies 3 AZ me jaayein.

Ignore when

Ephemeral metrics ya reprocessable logs: RF=2, acks=1 chalega. 3x storage aur 2x cross-AZ network cost bachega — aur us data ko dobara generate kiya jaa sakta hai.

Cost you pay

acks=all = higher p99 latency (slowest ISR member ka intezaar). min.insync=2 ka matlab: 2 brokers down = writes band. Aapne availability ko durability ke liye trade kiya hai — yeh conscious choice honi chahiye.

KRaft noteNaye clusters me ZooKeeper nahi hai. Metadata khud ek Kafka log (__cluster_metadata) me rehta hai aur controller quorum Raft se chalta hai. Faayda: faster leader election, 1M+ partitions scale, ek hi process type manage karna.
06

Disk pe kya hota hai — segments, page cache, retention, compaction

"Kafka fast hai kyunki memory me hai" — galat. Kafka disk pe likhta hai, aur phir bhi fast hai. Wajah: sequential I/O, OS page cache aur zero-copy.

Problem

Ek partition = ek giant file? Aur wo bharti hi jaayegi?

  • Purana data delete karne ke liye poori file rewrite karni padegi.
  • Offset 5,00,000 dhoondhne ke liye poori file scan karni padegi.
  • Broker JVM heap me messages cache kare to GC pauses aur OOM.
  • Disk se read karke user-space me laao, phir socket me copy karo — 4 copies + 4 context switches per message.
  • Compacted state (jaise "har user ka latest profile") rakhna ho to log infinite badhta rahega.
Simple meinEk hi rejister me poori zindagi likhoge to na purana kaat paoge, na kuch dhoondh paoge.
Solution

Log segments + sparse index + page cache + zero-copy

  • Partition = kai segments. Ek active segment jisme append hota hai, baaki sealed. Files: .log, .index (offset→byte position), .timeindex.
  • Retention = poora sealed segment delete kar do (retention.ms, retention.bytes). Rewrite nahi, sirf unlink.
  • Index sparse hai (har 4KB pe entry) → memory-mapped, chhota, fast binary search.
  • Cache OS page cache me hai, JVM heap me nahi → GC pressure zero, aur broker restart pe cache warm rehta hai.
  • Zero-copy (sendfile): disk page cache se seedha NIC pe. User-space copy hi nahi.
  • Log compaction (cleanup.policy=compact): har key ka sirf latest value rakho. Isse topic ek "table" ban jaata hai — perfect for CDC, config, profiles, Kafka Streams state.
Simple meinRejister ko chhoti-chhoti copies me toda gaya. Purani copy poori ki poori phenk do. Har copy ke shuru me ek chhota index. Aur OS jo pages already RAM me rakhe hue hai, unhe seedha network pe bhej do — beech me kuch copy mat karo.

Apply when

delete policy: events/streams (7 din default). compact policy: latest-state topics — user profile, inventory count, Streams changelog, Debezium CDC snapshot.

Ignore when

Compaction ko "delete ka replacement" mat samjho. Compaction sirf duplicate keys hataata hai, size guarantee nahi deta. Agar har key unique hai to compaction kuch nahi hataayega.

Cost you pay

Compaction background CPU + disk I/O leti hai, aur tombstone (null value) delete ke baad delete.retention.ms tak dikhta hai. Chhote segments = zyada open file handles aur zyada frequent cleaning.

Zero-copy toot jaata hai jabbroker ko data ko chhoona pade — SSL/TLS encryption on ho, ya broker-side format conversion ho (purana client, naya message format). Isliye TLS on karne ke baad throughput drop dikhta hai. Ye interview me strong answer hai.
07

Consumer group, rebalance aur heartbeat — pods kaise coordinate karte hain

Kubernetes pe 6 pods chal rahe hain, topic me 12 partitions hain. Kaun kya padhega? Kaun decide karta hai? Aur ek pod mar jaaye to kya hota hai?

Problem

Rebalance storm — consumers baar-baar restart ho rahe hain

Pods deploy hue, aur lag 4 million pe chala gaya. Logs me bas Attempt to heartbeat failed aur "revoking partitions".

  • Stop-the-world: purane eager protocol me rebalance pe saare consumers apne partitions chhod dete hain. Poora group ruk jaata hai.
  • max.poll.interval.ms (default 5 min) cross ho gaya kyunki ek record process karne me 6 min lage → group ne consumer ko dead maan liya → rebalance → wahi record dobara → infinite loop.
  • Rolling deploy me har pod restart = ek rebalance. 6 pods = 6 rebalances.
  • 12 partitions, 20 pods → 8 pods bilkul idle baithe hain, paisa jal raha hai.
Simple meinGroup me koi bhi aaye ya jaaye, sab kaam rok kar dobara baat-baat karte hain "kaun kya karega". Agar ek pod slow hai to group use mara hua samajh leta hai — aur yahi cycle chalti rehti hai.
Solution

Cooperative sticky + static membership + sahi timeouts

Group coordinator (ek broker) group manage karta hai. Ek member group leader banta hai jo assignment compute karta hai.

  • Do alag threads: heartbeat thread background me chalta hai (heartbeat.interval.ms=3s, session.timeout.ms=45s) — ye batata hai "main zinda hu". max.poll.interval.ms batata hai "main progress kar raha hu".
  • partition.assignment.strategy=CooperativeStickyAssignor → sirf zaroori partitions move hote hain, baaki consumers chalte rehte hain. No stop-the-world.
  • group.instance.id (static membership) → pod restart pe uska session.timeout tak wait hota hai, rebalance hota hi nahi. Rolling deploys smooth.
  • Slow processing hai? max.poll.records ghatao (500 → 50) ya heavy kaam ko worker pool pe daalo aur pause()/resume() use karo.
  • Consumers ≤ partitions rakho. Extra consumers standby hain, throughput nahi badhate.
Simple meinHeartbeat = "main saans le raha hu". max.poll.interval = "main kaam bhi kar raha hu". Dono alag hain. Aur cooperative assignor ka matlab: jab naya banda team me aaye, sab log apna kaam chhod kar meeting me nahi jaate — sirf utna kaam transfer hota hai jitna zaroori hai.

Apply when

Har production consumer pe: cooperative sticky + static membership. Partitions = peak parallelism ka 2–3x taaki baad me pods scale kar sako bina repartition kiye.

Ignore when

session.timeout.ms ko bahut bada mat karo (jaise 5 min) sirf rebalance rokne ke liye — tab genuinely-dead pod ko detect hone me 5 min lagenge aur uske partitions tab tak ruke rahenge.

Cost you pay

Static membership me crashed pod ka partition session.timeout tak blocked rehta hai. Cooperative rebalance 2 rounds leta hai (thoda slow, par non-blocking). Dono me availability vs stability ka trade hai.

Interview trap"Consumers badha do, throughput badh jaayega" — sirf tab tak jab tak consumers ≤ partitions. Uske baad extra consumers idle rahenge. Throughput badhane ke liye partitions badhao (ya processing per record fast karo).
08

Offset commit — "updating" ka asli matlab

Kafka me kuch bhi update nahi hota. Log immutable hai. Jo "update" hota hai wo sirf ek pointer hai: consumer ka committed offset, jo __consumer_offsets naam ke compacted topic me likha jaata hai.

Problem

Auto-commit on tha, aur messages gayab ho gaye

enable.auto.commit=true, auto.commit.interval.ms=5000. Poll ne 500 records diye, auto-commit ne 5 second baad offset commit kar diya, phir record #200 pe pod crash ho gaya.

  • Restart pe consumer offset 500 se shuru hua → records 200–500 kabhi process hi nahi hue. Silent data loss (at-most-once).
  • Doosri team ne ulta kiya: process karke commit kiya, par commit se pehle crash → sab records dobara process hue → duplicate emails gaye.
  • Kisi ne commitSync() har record pe laga diya → throughput 50 msg/s.
Simple meinBookmark ko kaam khatam hone se pehle aage badha diya. Crash hone pe wo page dobara khula hi nahi.
Solution

Manual commit after processing + consumer-side dedupe

  • enable.auto.commit=false. Pehle process, phir commit. Ye at-least-once deta hai.
  • Batch ke end pe commitSync(), ya throughput ke liye commitAsync() + shutdown pe ek final commitSync().
  • Duplicates ab guaranteed hain — isliye processing idempotent banao: INSERT ... ON CONFLICT DO NOTHING on event_id, ya UPDATE ... WHERE version < :incoming.
  • Committed offset = agla offset jo padhna hai (last processed + 1). Ye interview me pucha jaata hai.
  • __consumer_offsets compacted hai — har (group, topic, partition) ka sirf latest offset rehta hai. Yahi "update" ka mechanism hai.
Simple meinBookmark tabhi badhao jab page sach me padh liya ho. Aur maan ke chalo ki kabhi-kabhi ek page dobara padhna padega — isliye dobara padhne se kuch bigadna nahi chahiye.

Apply when

Default choice: at-least-once + idempotent consumer. Ye 95% real systems ka answer hai, aur exactly-once se simple aur sasta hai.

Ignore when

At-most-once (auto-commit) sirf tab jab data loss acceptable ho — debug logs, sampled metrics. Kabhi bhi payments/orders pe nahi.

Cost you pay

Exactly-once (transactional read-process-write) throughput kam karta hai aur sirf Kafka-to-Kafka ke andar kaam karta hai. External DB/API ke saath aapko phir bhi dedupe key chahiye.

Offset resetNaye group ya expired offset pe auto.offset.reset decide karta hai: latest (sirf naye events — dashboards) ya earliest (poora history — backfill, replay). Production incident me galat value se ya to poora history dobara process ho jaata hai ya beech ka data skip.
09

Consumer lag, poison pills, retries aur DLQ

Production me Kafka ka 80% operational pain sirf do cheezon se aata hai: lag badh raha hai, aur ek record process nahi ho raha.

Problem

Ek corrupt record ne poora partition rok diya

Ek message ka JSON malformed tha. Consumer ne exception phenka, offset commit nahi hua, wahi record dobara aaya. Infinite retry loop.

  • Us partition ka lag 8 million ho gaya, baaki partitions theek chal rahe the.
  • Team ne "fix" kiya: catch karke exception nigal liya → ab genuine failures bhi silently gum ho rahe hain.
  • Blocking retry (Thread.sleep loop) lagaya → max.poll.interval.ms cross → rebalance storm.
  • Downstream DB down tha, aur consumer ne 2 lakh failed records DLQ me daal diye — DLQ hi asli backlog ban gaya.
Simple meinEk kharab page pe atak gaye, aur poori kitaab wahi ruk gayi. Fir usko chhod diya to pata hi nahi chala kya-kya chhoot gaya.
Solution

Error ko classify karo: retryable vs non-retryable

  • Non-retryable (bad schema, validation fail, unknown enum) → seedha DLQ, offset commit, aage badho. Retry se kabhi theek nahi hoga.
  • Retryable (DB timeout, 503, lock conflict) → exponential backoff ke saath retry. Blocking retry sirf chhote intervals ke liye.
  • Lambe wait ke liye non-blocking retry topics: orders.retry.5s → orders.retry.1m → orders.retry.10m → orders.DLT. Main partition kabhi block nahi hota.
  • DLQ record me original topic, partition, offset, exception aur stack trace headers me daalo — warna DLQ ek black hole hai.
  • Downstream down hai to DLQ mat bharo — pause the consumer (circuit breaker) aur recover hone pe resume karo.
  • Monitor: records-lag-max per partition (sirf total nahi), rebalance rate, DLQ ingress rate.
Simple meinDo tarah ki galtiyan hoti hain: "yeh kabhi theek nahi hoga" (side me rakho) aur "abhi nahi ho raha, thodi der me hoga" (dobara try karo). Dono ka ilaaj alag hai. Aur agar poora downstream hi down hai, to consumer ko rok do — DLQ me mat pheko.

Apply when

Retry topics tab jab per-record failure independent ho (ek order fail, baaki theek). DLQ + alert + replay tooling day one se banao.

Ignore when

Strict per-key ordering chahiye to retry topic mat use karo — record ko side me daalne se us key ka order toot jaayega. Wahan partition block karna hi sahi hai.

Cost you pay

Retry topics = zyada topics, zyada consumers, ordering loss, aur DLQ ka apna lifecycle (kaun replay karega, kab tak rakhenge). Operational surface badhta hai.

10

HLD sizing — interview me numbers bolna aana chahiye

"Design a notification system with Kafka" pucha jaaye to interviewer numbers sunna chahta hai. Yahan ek reusable calculation hai.

Problem

"Kitne partitions aur kitne brokers?" — "umm, kaafi saare"

  • Bina number ke design ek diagram hai, architecture nahi.
  • Team ne 6 partitions banaye, 6 mahine baad traffic 5x hua — repartition karna pada, keys ka mapping toot gaya.
  • Retention 30 din rakh diya bina disk calculate kiye → brokers full, cluster read-only ho gaya.
Simple meinPehle likho: kitne events per second, har event kitna bada, kitne din rakhna hai. Baaki sab isi se nikal aata hai.
Solution

Ek back-of-envelope model

Maan lo: 50,000 events/sec peak, avg event 1 KB, retention 7 din, RF 3.

  • Ingress: 50k × 1KB = 50 MB/s. Din ka ~4.3 TB raw.
  • Storage: 4.3 TB × 7 din × 3 (RF) = ~90 TB. Compression (zstd, ~4x) ke baad ~23 TB. +30% headroom → ~30 TB.
  • Partitions: ek partition realistically 10–20 MB/s. Consumer side pe agar ek consumer 5k msg/s handle karta hai, to 50k/5k = 10 consumers → minimum 10 partitions. 2–3x headroom → 24–30 partitions.
  • Brokers: ek broker comfortably ~10–15 TB aur ~100–150 MB/s. 30 TB / 10 TB ≈ 3, par HA + rolling restart + hot spare ke liye 6 brokers, 3 AZ me 2-2.
  • Network out: 3 consumer groups → 50 MB/s × 3 = 150 MB/s egress + replication 100 MB/s. NIC 10 Gbps pe aaram se.
Simple meinFormula: events/sec × size = MB/s. MB/s × seconds × RF = storage. Partitions consumer ki speed se decide hote hain. Brokers disk aur network se.

Apply when

Har design interview me. Assumption bol kar likho — interviewer number ki accuracy nahi, method dekhta hai.

Ignore when

Over-provisioning: 100 partitions "future ke liye" mat banao. Rebalance time, metadata size aur end-to-end latency sab badh jaate hain.

Cost you pay

Zyada retention = zyada disk = zyada paisa. Long-term history chahiye to tiered storage (S3) ya lake me offload karo, brokers pe 7 din hi rakho.

Kafka vs baaki — aur kab Kafka nahi lena chahiye

Sabse strong senior signal yeh hai ki aap Kafka ko "na" bol sako jab wo fit nahi hai.

Problem

Kafka ko hammer bana diya

  • Per-message TTL / delayed jobs chahiye the ("30 min baad reminder bhejo") — Kafka me per-message delay hai hi nahi.
  • Per-message ack aur selective redelivery chahiye tha — Kafka offset-based hai, individual message nack nahi hota.
  • Complex routing (topic exchange, header-based) chahiye tha — wo RabbitMQ ka kaam hai.
  • Request-response RPC Kafka pe banaya — correlation IDs, timeouts, reply topics... poora RPC framework dobara likhna pad gaya.
  • 3 services, 20 msg/sec ke liye 6-broker cluster + on-call rotation.
Simple meinKafka log hai, task queue nahi. Agar aapko "yeh kaam is bande ko do, 30 min baad, aur fail ho to doosre ko do" chahiye — wo Kafka ka model hi nahi hai.
Solution

Sahi tool chuno

  • Kafka: high throughput event streaming, replay, multiple independent consumers, stream processing, CDC, event sourcing.
  • RabbitMQ: per-message ack/nack, priority, TTL, dead-letter exchange, complex routing, task queues, lower volume.
  • SQS/SNS: zero ops, simple decoupling, AWS-native. SQS FIFO chhoti scale pe ordering deta hai.
  • Pulsar: Kafka jaisa log + queue semantics + multi-tenancy + tiered storage built-in.
  • Redis Streams: low latency, chhota footprint, durability requirements halke ho tab.
  • Temporal / Celery / Sidekiq: scheduled jobs, workflows, retries with state — wo Kafka ka kaam nahi hai.
Simple meinData ka "stream" chahiye to Kafka. "Kaam ki list" chahiye to task queue. Dono ko mila mat do.

Apply when

>10k msg/s, ya replay, ya 3+ independent consumers, ya stream processing/joins/aggregations — Kafka clearly jeetta hai.

Ignore when

<1k msg/s, ek consumer, no replay, chhoti team, no platform team. Managed SQS/RabbitMQ me jaao. Kafka ka asli cost licensing nahi, operations hai.

Cost you pay

Kafka ke saath aata hai: schema registry, monitoring stack, partition planning, upgrade cycles, aur 3am pe ISR shrink debug karna. MSK/Confluent isko kam karta hai, khatam nahi.

Q&A

Mock interview — 24 questions with answers

Level select karo aur khud se pehle jawab socho, phir kholo. Answers wahi length me likhe hain jitni ek real interview me boli jaati hai — 30 se 90 second.

Kafka queue hai ya pub-sub? beginner

Dono, kyunki ye asal me na queue hai na pub-sub — ye ek distributed commit log hai. Ek consumer group ke andar partitions members me bant jaate hain, to wo queue jaisa behave karta hai (har record ek member ko). Alag-alag consumer groups same data independently padhte hain, to wo pub-sub jaisa behave karta hai.

Ek hi log, do reading patterns. Group ke andar → queue. Groups ke beech → pub-sub.
Partition kya hai aur offset kya hai? beginner

Partition ek topic ka ordered, immutable, append-only sub-log hai — parallelism ki unit. Offset us partition ke andar record ki position hai, ek monotonically increasing integer. Offset partition ke andar unique hai, poore topic me nahi.

Topic = kitaab, partition = us kitaab ka ek chapter, offset = us chapter ka page number.
Consumer group kya karta hai? beginner

Ek group ke andar har partition exactly ek consumer ko assign hota hai. Isse work bant jaata hai bina duplicate processing ke. Group coordinator (broker) membership manage karta hai; group leader (ek consumer) assignment compute karta hai.

Consumers > partitions ho to extra consumers idle rehte hain.

Group = ek team jo mil kar topic padhti hai. Har chapter ek hi bande ko milta hai.
Kafka messages consume hone ke baad delete kar deta hai? beginner

Nahi. Retention time-based ya size-based hai (retention.ms, retention.bytes) — consumption se koi lena dena nahi. Isliye replay possible hai: offset ko peeche set karo aur dobara padho.

Padhne se page fatta nahi hai. Purani copy time hone pe hi phenki jaati hai.
acks=0, 1 aur all me kya fark hai? beginner
  • 0 — producer wait hi nahi karta. Fastest, sabse zyada loss risk.
  • 1 — leader ne local log me likh liya. Leader crash before replication = loss.
  • all — saare in-sync replicas ne likh liya. Sabse safe, sabse slow.

Par acks=all akela kaafi nahi — min.insync.replicas=2 ke saath hi asli guarantee milti hai.

Producer key deni chahiye ya nahi? beginner

Key tab do jab us entity ke events ka order matter karta ho — same key hamesha same partition me jaati hai. Key null ho to sticky partitioner batch-friendly round-robin karta hai, jo throughput ke liye better hai.

Order chahiye → key do. Sirf speed chahiye → key mat do.
Kafka disk pe likhta hai phir bhi itna fast kaise hai? mid
  • Sequential I/O — append-only writes, random seeks nahi. Sequential disk write random memory access se bhi tez ho sakta hai.
  • OS page cache — JVM heap me cache nahi, isliye GC pressure nahi aur restart pe cache warm rehta hai.
  • Zero-copy (sendfile) — page cache se seedha NIC, user-space copy skip.
  • Batching + compression — per-message overhead amortize ho jaata hai.
Fast isliye nahi ki memory me hai, fast isliye ki wo disk ko theek se use karta hai.
ISR kya hai aur shrink kab hota hai? mid

ISR = In-Sync Replicas — wo replicas jo leader ke saath sync me hain. Agar koi follower replica.lag.time.max.ms (default 30s) tak fetch nahi karta ya peeche reh jaata hai, use ISR se nikal diya jaata hai.

Commit tabhi hota hai jab saare ISR ne likh liya ho. ISR min.insync.replicas se neeche gaya to producer ko NotEnoughReplicasException milta hai — write fail, par data loss nahi.

ISR shrink hone ka matlab: ya broker slow hai, ya network, ya disk. Ye alert-worthy metric hai.
Exactly-once Kafka me kaise achieve karte ho? mid

Teen alag layers hain, aur inhe alag rakhna zaroori hai:

  • Idempotent producer — retry ke duplicates broker pe dedupe (PID + sequence).
  • Transactions — multiple partitions pe atomic write + offset commit, consumer read_committed. Sirf Kafka-to-Kafka ke andar.
  • Consumer-side idempotency — business key pe unique constraint. External DB/API ke liye yahi asli answer hai.
Kafka transaction aapke third-party payment API ko rollback nahi kar sakta. Isliye practical systems me at-least-once + idempotent consumer likha jaata hai.
Rebalance storm ko kaise rokoge? mid
  • CooperativeStickyAssignor — stop-the-world khatam, sirf zaroori partitions move hote hain.
  • group.instance.id (static membership) — rolling restarts pe rebalance trigger hi nahi hota.
  • max.poll.records ghatao ya processing ko async worker pool pe daalo taaki max.poll.interval.ms cross na ho.
  • Retry backoff ka total time max.poll.interval.ms se kam rakho.
session.timeout.ms aur max.poll.interval.ms me fark? mid

session.timeout.ms heartbeat thread ke liye hai — "consumer process zinda hai kya". Background thread har heartbeat.interval.ms pe ping bhejta hai.

max.poll.interval.ms application thread ke liye hai — "consumer progress kar raha hai kya". Do poll() calls ke beech ka max gap.

Ek batata hai saans chal rahi hai, doosra batata hai kaam ho raha hai. Slow processing pehla nahi, doosra trigger karti hai.
Poison pill message ko kaise handle karoge? mid

Sabse pehle error classify karo. Non-retryable (bad schema, validation) → seedha DLT bhejo aur offset commit karo. Retryable (DB timeout) → bounded exponential backoff, phir DLT.

ErrorHandlingDeserializer use karo taaki deserialization failure poore container ko na maare. DLT record me original topic/partition/offset aur exception headers me daalo, warna replay impossible hai.

Retry karne se bad JSON theek nahi hoga. Usse side me rakho aur aage badho.
Consumer lag badh raha hai — debug kaise karoge? mid
  1. Lag per partition dekho, total nahi — akele ek partition ka lag hot key ya stuck consumer batata hai.
  2. Consumers < partitions? Pods scale karo (partitions tak hi faayda hoga).
  3. Rebalance rate high? Static membership + cooperative assignor.
  4. Processing slow? Downstream DB/API ka p99 dekho — 90% baar problem Kafka me nahi hoti.
  5. GC pauses, fetch.min.bytes, aur max.poll.records tune karo.
  6. Producer spike hai? Tab lag temporary hai, drain hone do.
Ordering guarantee kya hai Kafka me? mid

Ordering sirf ek partition ke andar guaranteed hai. Topic-wide ordering nahi hai. Same key → same partition → us key ke events ordered.

Ye guarantee toot sakti hai agar: idempotence off ho aur max.in.flight>1 ke saath retries ho, ya partition count change ho jaaye, ya aap retry topic me record ko side me daal do.

Log compaction kab use karoge, delete kab? mid

delete — event streams jahan history matter karti hai aur data time ke baad useless ho jaata hai (clicks, orders, logs).

compact — jahan aapko sirf har key ka latest state chahiye: user profile, inventory count, feature flags, Kafka Streams changelog, Debezium CDC. Compacted topic ek "table" hai jise kabhi bhi replay karke state rebuild kiya jaa sakta hai.

Delete karne ke liye tombstone (null value) bhejo.

Topic me partitions badha sakte ho? Ghata sakte ho? mid

Badha sakte ho, ghata nahi sakte. Aur badhane ka side effect serious hai: hash(key) % N me N badal gaya, to same key ab alag partition me jaayegi — per-key ordering toot jaayegi aur purane events purane partition me hi padhe rahenge.

Safe approach: naya topic (orders.v2) zyada partitions ke saath, dual-write ya migrate, phir cutover.

50k events/sec, 1KB avg, 7 din retention — cluster size batao architect
  • Ingress: 50k × 1KB = 50 MB/s, ~4.3 TB/din raw.
  • Storage: 4.3 × 7 × 3 (RF) = ~90 TB; zstd ~4x → ~23 TB; +30% headroom → ~30 TB.
  • Partitions: consumer 5k msg/s handle karta hai → 10 consumers minimum; 2–3x headroom → 24–30 partitions.
  • Brokers: ~10 TB/broker → 3 minimum; HA + rolling restart ke liye 6 brokers, 3 AZ.
  • Network: 3 consumer groups → 150 MB/s egress + ~100 MB/s replication. 10 Gbps NIC pe comfortable.

Hot partition ka problem kaise solve karoge? architect

Pehle confirm karo ki skew key cardinality se hai ya traffic distribution se. Options:

  • Composite key: sellerId + "#" + (hash(userId) % 8) — ek hot seller 8 partitions me spread. Per-seller total order chala jaayega, per-user bacha rahega.
  • Custom partitioner jo known hot keys ko dedicated partitions de.
  • Hot entity ko alag topic pe route karo, dedicated consumers ke saath.
  • Agar ordering zaroori nahi → key hata do.
Har solution me ordering ka kuchh na kuchh trade hai. Pehle poocho: kis level pe order chahiye — seller, user, ya bilkul nahi?
Multi-region Kafka kaise design karoge? architect

Stretch cluster (ek cluster, 3 AZ ek region me) — RF=3 rack-aware. Simple, par cross-region latency inter-broker traffic ko maar deti hai.

MirrorMaker 2 / Cluster Linking — har region ka apna cluster, async replication. Offsets translate hote hain, par lag aur duplicate possible hain. DR ke liye standard.

Key decision: active-active (conflict resolution chahiye, topic prefixing se loop rokna) vs active-passive (simple, failover pe RPO > 0).

Cross-region synchronous replication almost hamesha galat choice hai — latency budget khatam ho jaata hai.
Schema evolution kaise handle karoge? architect

Schema Registry + Avro/Protobuf, aur compatibility mode explicitly set karo:

  • BACKWARD — naya schema purana data padh sakta hai. Consumers pehle upgrade karo.
  • FORWARD — purana schema naya data padh sakta hai. Producers pehle upgrade karo.
  • FULL — dono. Sirf optional fields with defaults add karo.

Rules: field kabhi remove mat karo (deprecate karo), required field mat add karo (default do), enum me naya value add karna forward-compatible nahi hota.

Breaking change chahiye? Naya topic version: orders.v2.

Kafka + database ke beech consistency kaise? (dual write problem) architect

DB me likhna aur Kafka me publish karna — do alag systems, koi distributed transaction nahi. Beech me crash = inconsistency.

Transactional Outbox: business row aur outbox row ek hi DB transaction me likho. Ek relay process (ya Debezium CDC) outbox se padh kar Kafka me publish karta hai.

CDC-first: app sirf DB me likhti hai, Debezium binlog se events banata hai. Zero dual-write, par events DB schema ke shape me aate hain.

Golden rule: ek transaction, ek system. Doosre system tak baat ek asynchronous relay se pahunchni chahiye.
Kafka kab NOT use karoge? architect
  • Request-response RPC — correlation IDs aur reply topics ka matlab hai aap ek bura RPC framework dobara likh rahe ho.
  • Per-message delay / scheduling — Kafka me per-message TTL ya delay hai hi nahi. Temporal, SQS delay queues, ya scheduler use karo.
  • Per-message ack / selective redelivery — RabbitMQ ka model.
  • Complex routing (header/topic exchanges) — RabbitMQ.
  • Chhoti scale — 3 services, 50 msg/s ke liye 6 brokers + on-call rotation justified nahi.
Kafka ka asli cost license nahi, operations hai. Wo cost tabhi worth hai jab volume, replay ya multiple consumers ho.
KRaft ne ZooKeeper ko kyu replace kiya? architect

ZooKeeper ke saath metadata ek alag system me tha — do cluster manage karo, do failure modes, aur controller ko startup pe poora metadata ZK se load karna padta tha (bade clusters me minutes).

KRaft me metadata khud ek Kafka log hai (__cluster_metadata) aur controllers Raft quorum chalate hain. Faayde: leader election seconds nahi milliseconds me, millions of partitions tak scale, ek hi binary/process model, aur simpler security surface.

Aapke Kafka consumer ka p99 latency 8s hai. Kahan dekhoge? architect

End-to-end latency ko todo, guess mat karo:

  1. Producer side: linger.ms kitna hai? Batch full hone ka wait? buffer.memory pressure?
  2. Broker side: acks=all ke saath slowest ISR ka wait; ISR shrink events; disk write latency; TLS ki wajah se zero-copy off.
  3. Fetch side: fetch.min.bytes + fetch.max.wait.ms — low traffic pe consumer khud wait karta hai.
  4. Processing: max.poll.records bada hai to batch ka last record poori batch ka time jhelta hai.
  5. Rebalances: har rebalance me processing rukti hai — p99 wahi se aata hai.
Latency budget likho: produce → commit → fetch → process. Har step ka apna metric hona chahiye, warna aap andhere me tune kar rahe ho.
