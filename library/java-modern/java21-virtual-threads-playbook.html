01 — High level design

What the system looks like from 10,000 feet

Same architecture, same boxes, same code shape. The only thing that changes is who holds the OS thread while a box waits for another box. Yehi ek line poore migration ka summary hai — aur yehi HLD ka pehla answer hona chahiye.

virtual thread / heap bounded resource unchanged by migration the actual delta

HLD answer you can say out loud

“Architecture identical rahi — same services, same DB, same Kafka topology. Humne sirf execution model badla: thread-per-request ab OS thread ke bajaye heap-allocated virtual thread par chalta hai. Isse admission capacity badhi, lekin service capacity utni hi rahi, kyunki wo DB connection pool aur partition count se bandhi hai. Isliye migration ka half kaam Java upgrade tha, aur baaki half downstream limits ko re-tune karna tha.”

02 — Low level design

What actually happens inside the JVM

Interview mein HLD sabko aata hai. Difference LLD par banta hai: continuation, stack chunk, scheduler, aur unmount ka exact trigger. Yeh section un chaar cheezon ko line by line kholta hai.

LLD answer you can say out loud

“Ek virtual thread JVM ke liye ek Runnable plus ek Continuation hai. Jab blocking call aati hai, JDK internally Continuation.yield() call karta hai — carrier ke native stack se frames uthakar heap par StackChunk objects ki form mein save kar diye jaate hain, aur carrier turant doosra virtual thread le leta hai. I/O complete hone par thread wapas scheduler ki FIFO queue mein submit hota hai aur kisi bhi free carrier par remount ho jata hai. Isliye Thread.currentThread() same rehta hai lekin carrier badal sakta hai — aur isliye thread identity par based caching ab galat assumption hai.”

T1

Where the stack lives

Platform thread ka stack OS ke paas tha. Virtual thread ka stack heap par hai. Baaki sab isi ek fact se nikalta hai.

problem · java 17

1 Java thread = 1 OS thread, forever

  • Har thread ke liye OS 1 MB stack reserve karta hai (-Xss default). Reserve virtual memory hai, commit lazy hota hai — par reservation address space aur container accounting dono kha jaata hai.
  • Thread create karna syscall hai. ~1 ms tak lag sakta hai. Isliye pooling majboori thi.
  • Blocking call par OS thread park ho jaata hai. CPU 8% par, threads 100% exhausted — yeh classic Java 17 graph hai.
  • Context switch kernel mode mein hota hai: register save, TLB pressure, scheduler run-queue churn.
Hinglish: thread mahanga tha, isliye hum use gin-gin kar kharch karte the. Aur jab wo DB ka wait karta tha, to wo poora 1 MB aur ek OS slot leke baitha rehta tha — kaam kuch nahi.
solution · java 21

Stack heap par, carrier OS ke paas

  • Virtual thread ka stack StackChunk objects ki form mein heap par rehta hai — deep call chain par grow, return par shrink.
  • Create karna object allocation hai, syscall nahi. Microseconds.
  • Blocking call par stack heap par save, carrier free. Kernel involve hi nahi hota.
  • Thread khatam → GC use collect kar leta hai. Koi explicit cleanup nahi.
Hinglish: ab thread ek normal Java object hai. Sasta hai, isliye har request ke liye naya bana sakte ho aur baad mein fenk sakte ho — pool ki zaroorat khatam.

T2

Executors: pool ab anti-pattern hai

ExecutorService abhi bhi chahiye. Fixed thread pool ab nahi chahiye — aur wo actively nuksan karta hai.

problem · java 17

Pool size = permanent guess

  • newFixedThreadPool(20) ek concurrency limit hai jo aapne resource cost ki wajah se lagayi thi, business reason se nahi.
  • 21st task queue mein baithta hai. Latency tab tak dikhti nahi jab tak queue lamba na ho jaaye — P99 suddenly cliff karti hai.
  • Pool app ke poore lifetime tak RAM aur OS threads hold karta hai, chaahe traffic zero ho.
  • Nested pools = deadlock. Pool A ka task pool B ka wait kare aur B full ho → system freeze.
Hinglish: pool ek permanent dhakkan tha. Usse throughput control nahi hota tha, bas queue chhupti thi.
solution · java 21

Per-task executor + explicit limit

  • newVirtualThreadPerTaskExecutor() har task ke liye naya thread banata hai. Koi queue nahi, koi starvation nahi.
  • try-with-resources par close() saare submitted tasks ke complete hone tak block karta hai.
  • Agar aapko limit chahiye, use Semaphore — ab limit business decision hai, thread cost nahi.
  • Virtual threads ko kabhi pool mat karo. Pooling ka matlab hai unhe mahanga maan lena.
Hinglish: pehle thread mahanga tha isliye limit lagti thi. Ab thread sasta hai — limit sirf wahan lagao jahan downstream sach mein limited ho.

apply when

Fan-out kaam hai: N independent I/O calls, sab ka result chahiye. Per-task executor + Future drain.

skip when

Task purely CPU-bound hai. Wahan newFixedThreadPool(cores) ya parallel stream hi sahi hai — platform threads ke saath.

T3

Turning it on in Spring Boot

Ek property. Lekin wo property kya-kya chhoo rahi hai, yeh pata hona interview ka asli sawal hai.

problem · before

Tuning ke teen alag knobs

  • server.tomcat.threads.max=200 — HTTP capacity.
  • Custom TaskExecutor bean — @Async ke liye alag pool.
  • spring.kafka.listener.concurrency — listener threads.
  • Teeno ko alag-alag guess karna padta tha, aur teeno galat set hone par alag symptom dete the.
Hinglish: teen dials the, teeno ka rishta samajh nahi aata tha. Load test se number nikalte the, samajh se nahi.

Hinglish: flag on karna 5 minute ka kaam hai. Asli migration uske baad shuru hoti hai — T4 se T9 tak.

T4

Thread pinning

Wo ek word jo poore migration ka fayda chup-chaap kha jaata hai — aur jiska answer 2026 mein badal chuka hai.

problem · java 21

synchronized + blocking = carrier stuck

  • Java 21 mein synchronized monitor ka ownership carrier thread se juda hota hai. Andar blocking call aayi to virtual thread unmount nahi kar sakta.
  • Ab wo carrier thread bhi block hai — yaani aapne Java 17 wali problem wapas bana di, bas ab wo invisible hai.
  • 4 cores par 4 pinned threads = poora scheduler dead. FJP maxPoolSize (256) tak grow karega, lekin tab tak latency spike ho chuki hogi.
  • Sabse khatarnak jagah: aapka apna code nahi, puraane JDBC drivers aur connection pools.
Hinglish: pinning ka sabse bura hissa yeh hai ki app crash nahi hoti. Wo bas dheere ho jaati hai, aur aapko lagta hai virtual threads kaam hi nahi karte.
solution

ReentrantLock, drivers, aur Java 24+

  • Apne code mein synchronized → ReentrantLock. ReentrantLock virtual-thread-aware hai, wo yield karta hai.
  • Drivers upgrade karo. PostgreSQL 42.5.1+ aur HikariCP ke recent versions ne apne internal synchronized hata diye.
  • Detect karo: JFR event jdk.VirtualThreadPinned. Yeh production-safe hai.
  • 2026 update: JEP 491 (Java 24) ne synchronized ki pinning problem largely khatam kar di. Java 25 LTS par yeh ab mostly a non-issue hai — lekin native/JNI frames abhi bhi pin karte hain.
Hinglish: agar aap aaj Java 21 par ho to lock replace karna zaroori hai. Agar Java 25 LTS par ja rahe ho, to yeh problem bahut had tak apne aap solve ho jaati hai — aur interview mein yeh bolna aapko alag dikhata hai.

T5

The bottleneck just moved

Virtual threads ne queue delete nahi ki. Usse Tomcat se uthakar HikariCP par rakh diya.

problem · after enabling

Backpressure gayab ho gaya

  • Java 17 mein Tomcat ki 200-thread limit ek accidental rate limiter thi. Usne aapke DB ko bachaya hua tha.
  • Flag on karte hi 10,000 requests andar aa gayin, aur sab 30 connections ke liye line mein khadi hain.
  • Symptom badal jaata hai: pehle “connection refused” aata tha, ab SQLTransientConnectionException: timeout after 30000ms aata hai — 10,000 baar.
  • Client side par timeouts aur retries → load aur badhta hai → retry storm.
Hinglish: aapne darwaza chauda kar diya, kamra utna hi bada hai. Bheed ab andar hai, bahar nahi — aur andar ki bheed zyada khatarnak hai.
solution

Backpressure ab explicit banao

  • Pool size formula se nikaalo: connections ≈ cores × 2 + effective_spindles. Blindly badhana DB ko maar dega.
  • connection-timeout chhota karo (2–3 s). Fail fast, queue mat karo.
  • Entry par Semaphore ya bulkhead lagao — jitne DB connections hain, utni hi concurrent requests andar aane do.
  • DB-bound endpoints par rate limit lagao. Ab yeh optional nahi hai.
Hinglish: pehle limit accidental thi, ab aapko jaan-boojh kar lagani padegi. Yeh migration ka sabse bada — aur sabse zyada ignore kiya jaane wala — kaam hai.

Koi bhi endpoint jo shared bounded resource (DB, gateway, legacy SOAP) chhoo raha ho. Bulkhead mandatory hai.

skip when

T6

Kafka: partitions, concurrency, ordering

5 pods se 2 pods — ho sakta hai. Lekin ordering ka jo guarantee tha, wo chup-chaap toot sakta hai.

problem

Partition count aapki asli concurrency hai

  • Kafka rule: ek consumer group mein ek partition = ek consumer. Virtual threads is rule ko nahi badal sakte.
  • 5 partitions par concurrency: 8 set karne se 3 threads permanently idle rehte hain.
  • Agar aap ek partition ke messages ko fan out karke parallel process karte ho, to per-key ordering toot jaati hai. order-created aur order-cancelled ulte order mein apply ho sakte hain.
  • Poll loop aage bhaag gaya aur processing peeche → max.poll.interval.ms cross → rebalance storm.
Hinglish: parallel processing se speed milti hai, par correctness ki keemat par. Aur Kafka mein correctness wapas laana bahut mehnga padta hai.
solution

Key ke andar sequence, keys ke beech parallel

  • Batch uthao, use message key se group karo, har group ko ek virtual thread do.
  • Ek group ke andar messages sequentially chalenge → per-key ordering bachi rahi.
  • Alag keys parallel chalenge → throughput mila.
  • Pods ab HA ke liye rakho, capacity ke liye nahi. 5 partitions → 2 pods × concurrency 3 = 6 threads, ek pod gira to baaki sambhal lega.
Hinglish: yeh wo jawab hai jo interviewer sunna chahta hai. ‘Virtual threads se parallel kar diya’ adhoora hai — ‘key ke hisaab se parallel kiya’ poora hai.

Do not say this in an interview

“Virtual threads se hum 5 partitions ko 5000 threads se consume kar sakte hain.” — Yeh galat hai. Partition count hi consumer parallelism ka hard limit hai. Virtual threads sirf ek partition ke andar processing parallelize karne mein madad karte hain, aur wo bhi ordering ki keemat par.

apply when

Messages ka natural key hai (orderId, userId) aur ordering sirf key ke andar chahiye. Yeh 80% event streams hain.

skip when

Poore partition ka strict global order chahiye, ya processing already fast hai (<5 ms). Wahan fan-out sirf complexity hai.

watch out

Hot key: agar 90% messages ek hi key ke hain to fan-out ka koi fayda nahi. Wahan partitioning strategy hi galat hai.

T7

@Async + manual commit = silent data loss

Yeh poore page ka sabse important section hai. Code compile hota hai, test pass hote hain, aur production mein messages gayab ho jaate hain.

problem · two ways to lose data

Commit aur completion ka rishta toot jaata hai

  • Trap 1 — commit too early. Listener ne @Async method call kiya aur turant ack.acknowledge() kar diya. Background thread fail hua → offset commit ho chuka hai → message gaya.
  • Trap 2 — commit out of order. @Async method ke andar ack kiya. Message 2 pehle khatam hua, usne offset 2 commit kiya. Message 1 fail ho gaya. Kafka ke liye 1 bhi ho chuka hai → message gaya.
  • Trap 3 — the quiet one. try-with-resources use kiya, lekin Future drain nahi kiya. close() wait to karta hai, par task ki exception throw nahi karta. catch block chala hi nahi, ack ho gaya → message gaya.
Hinglish: teeno cases mein log clean dikhte hain, alert nahi bajta, aur consumer lag zero rehta hai. Pata tab chalta hai jab koi customer bolta hai ‘mera order update nahi hua’.
solution

Listener thread hi commit karega, verify ke baad

  • Kafka listener par @Async mat lagao. Virtual threads ke saath uska koi fayda nahi, sirf risk hai.
  • Fan-out per-task executor se karo, Future collect karo, aur har Future par get() karke verify karo.
  • Ack sirf listener thread karega, tab jab sab confirmed ho. Ek bhi fail → nack aur replay.
  • Processing idempotent banao — replay hone par duplicate side-effect nahi hona chahiye.
Hinglish: rule simple hai — jo thread commit karta hai, usi ko pata hona chahiye ki kaam sach mein hua ya nahi. @Async yeh rishta tod deta hai.

apply when

Manual ack ke saath koi bhi parallel processing. Future drain karna mandatory hai, optional nahi.

skip when

Processing 1–2 ms leti hai. Sequential loop hi sabse fast aur sabse safe hai — fan-out ka overhead ulta padega.

watch out

max.poll.interval.ms. Agar batch processing usse lambi ho gayi, consumer group se nikaal diya jaayega aur rebalance loop shuru ho jaayega.

T8

Logging, tracing, ThreadLocal

Thread name ab disposable hai. Jis cheez se aap 10 saal se debug kar rahe the, wo bekaar ho gayi.

problem

Grep karne layak kuch bacha hi nahi

  • Pehle [http-nio-8080-exec-7] grep karke poori request trace ho jaati thi. Ab har request ka naam VirtualThread[#84213] hai — ek baar use hua, phir gayab.
  • jstack virtual threads dikhata hi nahi. Aapka purana thread-dump playbook kaam nahi karta.
  • ThreadLocal per-thread hai. Ab threads lakhon mein hain — har ek mein bhaari object rakha to heap pressure banega.
  • Executor ke andar submit karne par MDC context copy nahi hota. Child virtual thread ke logs bina traceId ke aayenge.
Hinglish: yeh wo problem hai jo migration ke din 1 par nahi dikhti. Wo pehli production incident par dikhti hai, jab aapko kuch trace hi nahi kar paate.
solution

traceId hi naya thread name hai

  • Har request par traceId generate karo, MDC mein daalo, log pattern mein %X{traceId} add karo.
  • Executor mein submit karte waqt MDC snapshot manually copy karo. Yeh automatic nahi hota.

5 pods se 2 pods jaana sahi hai — lekin us decision ka kaaran capacity nahi, redundancy hai.

problem

Galat signal par scale ho rahe the

  • HPA CPU par scale karta tha, lekin asli problem thread exhaustion thi. CPU 20% par aur pods 8 — yeh classic mismatch hai.

Hinglish: hum wo cheez scale kar rahe the jo bottleneck thi hi nahi. Paisa kharch ho raha tha, latency wahi thi.

Pods = HA. Capacity = downstream.

04 — The tradeoff call

When to apply, when to ignore, and why

Interview mein “virtual threads accha hai” sabse kamzor answer hai. Strongest answer yeh hai: “yeh un cases mein apply karta hoon, un cases mein nahi, aur yeh raha kyun.” Neeche wahi decision table hai.

Situation Virtual threads? Reason — the one line that matters Agar galat chuna to
Blocking REST + JDBC service
thread-per-request, Tomcat		 Apply Yahi wo exact case hai jiske liye Loom bana. Code same rehta hai, admission capacity 50× ho jaati hai. Thread pool exhaustion, CPU idle, pods over-scaled.
Fan-out to N services
aggregate response		 Apply N parallel blocking calls without N threads. CompletableFuture ka pura chain hat jaata hai. Callback hell, ya pool size N se chhota to serial execution.
CPU-bound: encryption, image resize, parsing Ignore Virtual threads waiting hataate hain, computing nahi. Cores se zyada parallel kaam nahi ho sakta. Context switching overhead, GC pressure, throughput gir sakta hai.
App already on WebFlux Ignore Reactive already non-blocking hai. Do models mix karna sirf debugging aur mental overhead hai. Event loop par virtual threads — do schedulers ladte hain, latency unpredictable.
Legacy lib with native / JNI calls Isolate Native frames aaj bhi carrier pin karte hain, Java 24+ par bhi. JEP 491 ne sirf synchronized fix kiya. Chupke se scheduler starvation. Latency badhti hai, koi error nahi aata.
Heavy ThreadLocal usage
security context, tenant, caches		 Audit first Per-thread copy × lakhon threads = heap blowup. Pehle size audit karo, phir flag on karo. OutOfMemoryError peak traffic par — yaani sabse bure waqt par.
Kafka consumer, strict global ordering Ignore fan-out Parallel processing ordering todti hai. Sequential rakho, aur partitions badhao. Silent data corruption. Yeh production mein hafton baad pakda jaata hai.
Kafka consumer, per-key ordering Apply, grouped Key se group karo, group ko ek virtual thread. Ordering bachi, throughput mila. Bina grouping ke fan-out — events ulte order mein apply honge.
Scheduled / cron jobs Low value Fixed, small concurrency. Platform threads bilkul theek hain. Kuch nahi tootega, bas koi fayda bhi nahi. Change karne ka risk lene ka reason nahi.
Downstream already saturated
DB pool 100% busy		 Won’t help alone Aap queue ko move kar rahe ho, khatam nahi. Pehle downstream capacity ya caching fix karo. Timeout ka pahaad + retry storm. Java 17 se bhi bura ho sakta hai.
gRPC / Netty based service Ignore Netty already non-blocking event loop par hai. Virtual threads sirf blocking code ke liye hain. Event loop thread par blocking call — poora server freeze.
Batch job: 2M rows, DB writes Bounded apply Virtual threads + Semaphore(pool size). Unbounded fan-out DB ko gira dega. Connection pool exhausted, lock escalation, aur possible replica lag.

The one-sentence framework

Virtual threads waiting ka cost kam karte hain, working ka nahi. Isliye har decision ka test ek hi sawal hai: “is thread ka zyada waqt wait mein jaata hai ya compute mein?” Wait → apply. Compute → ignore. Aur agar wait kisi bounded resource ka hai, to pehle us resource ko theek karo — virtual threads usse nahi bachayenge.

05 — Numbers you can actually defend

Jo figures internet par ghoomte hain, unme se aadhe galat hain

Agar aap interview mein “200 bytes per thread” ya “60% cost saving guaranteed” bologe, to ek achha interviewer turant kured dega. Yeh raha defensible version — caveat ke saath.

Claim you’ll hearRealityWhat to say instead
“Virtual thread takes 200 bytes” Thread object chhota hai, par stack chunks call depth ke saath badhte hain. Spring + Hibernate + security chain ke saath realistically 1–10 KB. “Footprint stack depth par depend karta hai — typical Spring request par few KB. Platform thread ke 1 MB reservation se phir bhi do order of magnitude kam.”
“200 platform threads = 200 MB RAM” 1 MB reserved virtual memory hai, committed nahi. Actual RSS usually bahut kam. Lekin address space aur container accounting par asar padta hai. “Reservation 1 MB per thread hai, commit lazy. Real saving NMT se measure ki, guess nahi ki.”
“try-with-resources = structured concurrency” Nahi. Wo ExecutorService ka AutoCloseable behaviour hai. Asli StructuredTaskScope Java 21 mein preview API hai. “Humne per-task executor + explicit Future drain use kiya. StructuredTaskScope preview tha, isliye production mein nahi liya.”
“@KafkaListener(batch="true")” Aisa koi attribute hai hi nahi. Batch mode spring.kafka.listener.type=batch ya factory.setBatchListener(true) se aata hai. “Batch listener container factory level par configure hota hai, annotation par nahi.”
“8 pods → 2 pods, 60–70% cost cut” Possible hai I/O-bound workload par, guaranteed nahi. CPU-bound par pod count barabar rehta hai. “Humare I/O-bound service par load test ke baad 8 se 3 pods par aaye. Minimum 3 HA ke liye rakha, capacity ke liye nahi.”
“synchronized is a permanent problem” Java 21 mein haan. JEP 491 (Java 24) ne ise largely khatam kar diya; Java 25 LTS par yeh mostly non-issue hai. “Java 21 par humne ReentrantLock migrate kiya. Java 24+ par JEP 491 ke baad yeh zaroorat kaafi kam ho gayi — native frames ab bhi pin karte hain.”
“Millions of threads” Technically sach, practically meaningless — kyunki aapka DB pool 30 hai. Million threads ka matlab million pending tasks, million completed nahi. “Concurrency ab heap-bound hai, thread-bound nahi. Lekin effective throughput downstream capacity se decide hota hai.”
“File I/O is non-blocking now” Nahi. Most platforms par file I/O carrier ko block karta hai — wo offload hota hai, truly async nahi. “Isliye humne sync file appenders ko AsyncAppender se replace kiya.”
