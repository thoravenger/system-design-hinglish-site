Thread kahan rehta hai aur kaise chalta hai

  • Java ka normal (platform) thread OS ka ek asli thread hota hai. OS ka scheduler use CPU core pe chalata hai.
  • Threads cores se zyada hon toh OS unhe bari-bari chalata hai. Ek se doosre pe switch karna context switch kehlata hai, aur iski bhi keemat hai.
  • Local variables stack pe hote hain, isliye har thread ki apni copy hoti hai aur woh safe hain. Problem sirf shared objects mein aati hai.
  • Virtual threads (Java 21): JVM inhe manage karta hai, ye bahut halke hote hain aur lakhon mein ban sakte hain. Blocking IO (DB, HTTP) mein fayda hai, CPU-heavy kaam mein nahi.

Race condition aur visibility

Race condition: count++ ek step nahi, teen steps hai (read, add, write). Do threads beech mein ghus gaye toh ek update gayab ho jaata hai. Iska animation bhi Animation tab mein hai.

Visibility: Ek thread ne jo value likhi, woh doosre thread ko turant dikhe, iski guarantee nahi hai. CPU cache aur compiler optimization value ko purana dikha sakte hain. volatile ye guarantee deta hai:

volatile ke bina aisa ho sakta hai ki loop kabhi na ruke, kyunki worker thread purani value hi dekhta rahe.

Happens-before: lock chhodna aur phir wahi lock lena, volatile likhna aur phir padhna, start() aur thread ka kaam, thread ka khatam hona aur join() ka return. In jodon mein pehle wale ke changes baad wale ko dikhne ki guarantee hai.

synchronized

Executor framework

Thread pool kya hai, kaunsa pool kab lena hai, andar kaunse data structures hain, aur apna thread pool kaise banaate hain.

Thread pool kyun chahiye

Har task ke liye naya thread banana mehnga hai: OS thread banta hai, uska stack memory leta hai, aur 10,000 requests pe 10,000 threads app ko gira sakte hain.

Thread pool ek restaurant jaisa hai: cook (threads) gine-chune hain aur reuse hote hain, orders (tasks) ek line (queue) mein lagte hain. Jo cook free hota hai, woh agla order uthata hai.

Framework ke hisse aur basic use

execute vs submit: execute mein exception thread ko khatam karke uncaught handler tak jaata hai. submit mein exception Future ke andar chhup jaata hai, aur get() karne pe hi dikhta hai.

ThreadPoolExecutor andar se kaise kaam karta hai

Naya task aane pe pool ye faisla karta hai:

  1. Running threads < corePoolSize?Haan: naya thread banao aur task use do
  2. Queue mein jagah hai?Haan: task queue mein daalo, koi free thread uthayega
  3. Threads < maximumPoolSize?Haan: extra thread banao
  4. Kuch nahi bachaRejection policy chalegi

Surprise point: extra threads (core se upar) tabhi bante hain jab queue full ho. Unbounded queue ke saath pool kabhi core size se aage nahi badhega.

Apna thread pool banao

Teen hisse chahiye: tasks ki queue, N worker threads jo loop mein queue se task nikaal ke chalate hain, aur shutdown ka tareeka. Shutdown ke liye "poison pill" use kiya hai: har worker ke liye ek khaas task, jise dekh ke woh band ho jaata hai. Queue FIFO hai, isliye pill se pehle ke saare tasks pehle chal jaate hain.

Asli ThreadPoolExecutor isse aage ye sab karta hai: core aur max threads, idle threads ko band karna, rejection policies, Future se result, aur beforeExecute/afterExecute hooks.

CompletableFuture

Background mein kaam chalao, aur pehle se bata do ki result aane par kya karna hai. Main thread free rehta hai.

Future kaafi kyun nahi

  • Future.get() thread ko rok deta hai, result aane tak.
  • "Result aaye toh ye karna" jaisa chain nahi bana sakte.
  • Do futures ke results jodne ka seedha tareeka nahi.
  • Error aane pe fallback dene ka callback nahi.

CompletableFuture ye sab deta hai: chaining, combine, error handling, aur timeout.

Banana aur apna executor dena

Dhyan: executor nahi diya toh ForkJoinPool.commonPool() use hota hai, jisme lagbhag cores jitne threads hote hain. Usme DB ya HTTP jaisa blocking kaam daala toh poori app ka async kaam slow ho jaayega.

Deadlock

Deadlock kyun hota hai, kaise rokein, aur chalti app mein kaise pata karein ki deadlock hai ya nahi.

Deadlock aur uski 4 conditions

Do ya zyada threads ek doosre ke pakde hue lock ka hamesha ke liye wait karte rehte hain. Exception nahi aata, app bas atak jaati hai. Deadlock ke liye ye chaaron conditions ek saath honi chahiye. Ek bhi todo, deadlock nahi hoga.

Example aur fix

Kaise pata karein ki deadlock hai ya nahi

1. Lakshan pehchano

  • App ya API hang, requests timeout, par logs mein koi error nahi.
  • CPU low hai. Atke threads CPU nahi khaate. CPU 100% ho toh infinite loop ya livelock ka shak karo.

2. Thread dump lo

3. Dump ke end mein ye dhoondo

T2 ko T1 ka lock chahiye aur T1 ko T2 ka, yaani circle. Demo.java:17 woh line hai jahan thread atka hai. synchronized wale threads BLOCKED dikhte hain, ReentrantLock wale WAITING mein "waiting for ownable synchronizer" ke saath.

4. GUI tools

JConsole ke Threads tab mein "Detect Deadlock" button hai. VisualVM Threads tab mein khud "Deadlock detected!" dikhata hai. IntelliJ debug mode mein "Get Thread Dump" bhi kaam karta hai.

5. Code se khud pakdo (production watchdog)

Spring Boot mein /actuator/threaddump endpoint se bhi dump le sakte ho. JVM andar se ek wait-for graph banata hai (kaun kiska wait kar raha hai) aur usme circle dhoondhta hai.

Limitation: ye tools sirf locks ka circle pakadte hain. Threads await(), wait(), CountDownLatch ya future.get() pe hamesha ke liye atke hon, toh "Found deadlock" nahi aayega. Aise mein 5-10 second ke gap pe 3 dumps lo. Wahi threads har baar same line pe atke hain, toh wahi culprit hai.

DSA + Interview

Concurrency wale coding questions kaise sochein aur solve karein, concurrent collections andar se kaise bane hain, aur interview ke common sawaal.

Aise questions solve karne ka tareeka

  1. Shared state dhoondo: kaunsa data kai threads chhoo rahe hain?
  2. Rule likho: kab rukna hai? (queue full ho toh producer ruke, odd ki baari ho toh even ruke)
  3. Tool chuno: lock + condition, BlockingQueue, Atomic, Semaphore.
  4. Wait hamesha while mein, aur state badalne ke baad signal ya notify karo.
  5. Test karo: bahut saare threads chalao, aur har line pe socho "agar yahan thread switch ho gaya toh?"

Q1. Producer-Consumer

Ek thread cheezein banata hai, doosra use karta hai. Beech mein limited jagah hai. Sabse aasaan solution BlockingQueue hai, kyunki rukne aur jagne ka kaam woh khud karti hai.

Q2. Bounded Blocking Queue khud banao

Interview mein aksar kehte hain "BlockingQueue use mat karo, khud banao". Ek lock aur do Conditions: notFull pe producer sota hai, notEmpty pe consumer. Java ki ArrayBlockingQueue bhi andar se bilkul aisi hi hai.

Q3. Do threads se odd-even baari-baari print

Shared state: n. Rule: jiski baari nahi, woh wait kare. Print karke n++ aur doosre ko jagao.

3 threads, 1 se N tak sequence mein? Same idea: har thread ka id 0, 1, 2 rakho, aur baari tab hai jab n % 3 == id. Baaki sab wait karein.

Q4. Thread-safe Singleton

volatile kyun? Uske bina doosre thread ko object ka reference mil sakta hai, jabki constructor abhi poora chala hi nahi. Isse aadha-bana object dikh sakta hai.

Q5. Thread-safe LRU cache

Background data structure: LinkedHashMap = HashMap + doubly linked list. Access order mode mein har get entry ko list ke end pe le jaata hai, aur sabse purani entry list ke shuru mein rehti hai.

Trap: sirf put ko synchronized karna kaafi nahi. Access order mein get bhi andar ki list badalta hai, isliye woh bhi lock mein chahiye.

Q6. Parallel word count

Trap: if (!map.containsKey(k)) map.put(k, 1) jaisa check-then-act ConcurrentHashMap ke saath bhi race hai. merge, compute ya putIfAbsent use karo.

Interview ke common sawaal

wait() vs sleep()?

wait() lock chhodta hai aur sirf synchronized ke andar chalta hai. sleep() lock pakde rehta hai aur kahin bhi chalta hai.

Runnable vs Callable?

Runnable.run() kuch return nahi karta aur checked exception throw nahi kar sakta. Callable.call() value return karta hai aur exception throw kar sakta hai.

shutdown() vs shutdownNow()?

shutdown() naye task lena band karta hai, par queue ke saare task poore hone deta hai. shutdownNow() chal rahe threads ko interrupt karta hai aur queue ke bache task list mein wapas deta hai.

HashMap vs synchronizedMap vs ConcurrentHashMap?

HashMap thread-safe nahi hai. Collections.synchronizedMap poore map pe ek lock lagata hai, isliye slow. ConcurrentHashMap sirf us bucket ko lock karta hai jisme likh raha hai, aur read bina lock ke hote hain.

ConcurrentHashMap null kyun allow nahi karta?

get(k) ne null diya toh ye pata nahi chalega ki key nahi hai ya value hi null hai. Single-thread mein containsKey se check kar lete, par concurrent map mein dono calls ke beech map badal sakta hai.

volatile se count++ safe kyun nahi hota?

volatile sirf latest value dikhane ki guarantee deta hai. count++ teen steps hai, aur do threads beech mein ghus sakte hain. Iske liye AtomicInteger ya lock chahiye.

Deadlock vs livelock vs starvation?

Deadlock mein sab ruke hain. Livelock mein sab busy hain par progress zero. Starvation mein ek thread ki baari hi nahi aati.

Thread pool ka size kaise decide karein?

CPU wale kaam ke liye lagbhag cores jitna. IO wale kaam ke liye cores × (1 + wait time / compute time). Queue hamesha bounded rakho, aur load test se final karo.
