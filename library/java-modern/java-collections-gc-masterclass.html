01

Array vs ArrayList

basics

problem

Ek report endpoint 10 lakh integers return karta hai. Junior ne int[] likha, dusre service mein ArrayList<Integer> tha. Profiler mein memory ka farak 4–5x nikla. Kyun?

Interviewer ka asli sawaal: kya tum jaante ho ki ArrayList andar se hai kya, aur boxing ka cost kya hai?

  • Dono ka memory footprint compare karo.
  • ArrayList full ho jaaye to kya hota hai?
  • Kab array better, kab list?

solution

Object[] elementDatagrowth = 1.5xautoboxing

Array ek contiguous memory block hai jiska size creation ke time fix ho jaata hai, aur ye primitives (int, long) directly store kar sakta hai — 1 million ints = ~4 MB, ek hi allocation.

ArrayList andar se ek Object[] elementData hai. Ye sirf references rakh sakta hai, primitives nahi. Isliye har int ek Integer object ban jaata hai: 16 byte header + 4 byte value + padding ≈ 16 B, plus array slot mein 4–8 B ka reference. Result: ~4 MB ka data ~20 MB ka ho gaya, aur 1 million chhote objects GC ke liye kaam badha gaye.

Jab array bhar jaata hai, ArrayList naya bada array banata hai (oldCapacity + (oldCapacity >> 1) = 1.5x), purana data copy karta hai, aur purana array garbage ban jaata hai. Ye logic hum khud likh kar dekhte hain:

line 11
Har write se pehle capacity check — yahi ArrayList.add() ka pehla kaam hai (ensureCapacityInternal).
line 18–20
oldCapacity >> 1 yaani divide-by-2 (bit shift, division se sasta). 10 → 15 → 22 → 33 → 49… Ye amortized O(1) append deta hai: n appends ke liye total copy work O(n) hi rehta hai.
line 20
Arrays.copyOf andar System.arraycopy use karta hai — JIT ka intrinsic, memory-block level pe copy, loop se kai guna fast.
line 25–26
Growth ke baad array mein khali slack bachti hai. toTrimmedArray() = ArrayList.trimToSize() ka equivalent; long-lived list ke liye memory wapas milti hai.

Gotcha: list.remove(1) index 1 hataata hai, list.remove(Integer.valueOf(1)) value 1 hataata hai. Overload resolution boxing se pehle hota hai — production bug ka classic source.

apply karo

  • Hot numeric path, fixed size, ya millions of primitives → int[] / long[].
  • Size pata ho to new ArrayList<>(expectedSize) — resize copies bach jaate hain.
  • API boundary pe hamesha List<T> expose karo, array nahi (arrays mutable + covariant hain).

ignore karo

  • 200 elements ke liye boxing ka rona — yahan readability jeetegi, difference microseconds ka hai.
  • trimToSize() short-lived lists pe — ek aur copy ka kharcha, faida zero.
  • Manual arrays sirf "fast lagta hai" isliye — pehle measure karo, phir optimize.
02

List family: ArrayList, LinkedList, CopyOnWrite

basics → intermediate

problem

Textbook kehti hai LinkedList ka insert O(1) hai aur ArrayList ka O(n). Phir bhi real production code mein LinkedList kabhi kabhaar hi dikhta hai. Kyun?

Aur second part: ek event system hai jismein 50,000 reads/sec hain lekin listener register/unregister din mein 10 baar hota hai. Kaunsi list?

  • Big-O jhooth kab bolta hai?
  • CopyOnWriteArrayList kab sahi hai?
  • Vector aur Stack ka kya karein?

solution

cache line = 64 Bread-mostlylegacy: Vector

Big-O sirf operations ginta hai, memory access ka cost nahi. LinkedList ka O(1) insert tabhi milta hai jab tumhare paas node ka reference pehle se ho. Practically tum add(index, e) karte ho, jismein pehle O(n) traversal hota hai — aur har hop ek naye memory address pe jump hai, yaani CPU cache miss. ArrayList ka O(n) shift ek single contiguous System.arraycopy hai jo hardware ko bahut pasand hai. Isliye 10,000 elements tak ArrayList aksar LinkedList se tez nikalta hai, insert ke liye bhi.

Upar se har LinkedList node = object header + item + next + prev ≈ 40 bytes, sirf ek element rakhne ke liye. Ye GC pe seedha pressure hai.

Read-mostly case ke liye CopyOnWriteArrayList banaya gaya hai: read bilkul lock-free hai (bas ek volatile array read), aur har write poore array ki copy banata hai.

Field ka type List hai, implementation CopyOnWriteArrayList — "program to the interface". Kal ko strategy badalni ho to ek hi line badlegi.
line 15
addIfAbsent duplicate registration rokta hai atomically. Normal contains() + add() race-prone hota.
line 23–26
Iterator poore array ka snapshot leta hai. Isliye publish ke beech mein koi unregister kare to ConcurrentModificationException nahi aayega — bas wo listener ko is round mein event mil jaayega. Ye "weakly consistent" behaviour hai.
line 30

Vector aur Stack kyun chhodein? Har method pe synchronized hai, lekin compound operation (if (!v.contains(x)) v.add(x)) phir bhi race-prone hai — yaani cost bhi bhugto aur safety bhi na milay. apply karo

  • Default hamesha ArrayList. Justify tab karo jab kuch aur chuno.
  • Read:write ratio > 100:1 aur list chhoti (< few hundred) → CopyOnWriteArrayList.
  • FIFO/LIFO chahiye → ArrayDeque, LinkedList nahi.

ignore karo

  • "LinkedList insert fast hai" wali theory — measure karo, wo sirf iterator-based bulk edits mein jeetta hai.
  • Collections.synchronizedList se concurrency solve karna — compound ops phir bhi tootenge.
  • CopyOnWrite jab list badi ho ya writes frequent — har write ek full copy = GC storm.

HashMap internals: bucket, collision, treeify, resize

core interview

problem

Ek attacker aise 100k keys bhejta hai jinke hashCode same hain. Tumhara HashMap lookup O(1) tha — ab kya hoga? Java 8 ne is attack ko kaise kam kiya?

Follow-up jo hamesha aata hai: default capacity 16 aur load factor 0.75 kyun? Resize ke waqt entries kaise move hoti hain?

  • hash spreading ka kaam kya hai?
  • Bucket index kaise nikalta hai?
  • Treeify kab hota hai, kab nahi?

solution

cap 16load 0.75TREEIFY 8MIN_TREEIFY_CAP 64UNTREEIFY 6

HashMap ek Node<K,V>[] table hai. Har Node mein hash, key, value, next hote hain — yaani har bucket ek singly linked list ka head hai.

Pehla step — hash spreading. Index nikalne ke liye (n-1) & hash use hota hai, jo sirf lower bits dekhta hai. Agar keys ke hashCode ke sirf upper bits alag hon, sab ek hi bucket mein gir jaate. Isliye Java h ^ (h >>> 16) karta hai: upper 16 bits ko lower 16 pe XOR karke mix kar deta hai — ek sasta sa "avalanche".

Dusra step — collision handling. Same bucket mein 8 nodes ho jaayein aur table size ≥ 64 ho, to wo chain ek red-black tree ban jaati hai: worst case O(n) se O(log n). Agar table 64 se chhota hai to treeify ke bajaye resize hota hai (kyunki chhoti table mein collision ka asli ilaaj zyada buckets hain). Tree shrink hoke 6 nodes pe wapas list ban jaati hai — 8/6 ka gap hysteresis hai, taaki border pe baar-baar convert na ho.

line 8–9
null key allowed hai (ek hi), aur uska hash 0 hota hai → hamesha bucket 0. Hashtable aur ConcurrentHashMap mein null key/value allowed nahi.
line 12
>>> unsigned right shift hai — sign bit copy nahi hota. XOR se upper bits ka information lower bits mein aa jaata hai.
line 17
(n-1) & hash tabhi sahi kaam karta hai jab n power of two ho — tabhi n-1 ek all-ones mask banta hai (16-1 = 0b1111). Isliye HashMap tumhari di hui capacity ko upar wale power-of-two pe round karta hai.
line 22
Resize pe table double hoti hai, isliye ek entry ka naya index ya to same rehta hai ya oldCapacity jitna aage shift hota hai. Ye check ek hi bit dekh ke bata deta hai — poora rehash nahi karna padta. Isi wajah se Java 8 ka resize O(n) aur order-preserving hai.
line 31–32
10,000 entries expect kar rahe ho? new HashMap<>(13334) do. Warna 16 se shuru hoke ~10 resize honge, har baar poori table dobara link karni padegi.

Sabse bada gotcha: key ko map mein daalne ke baad mutate mat karo. Uska hash badal jaayega, entry purane bucket mein padi rahegi, aur get() naye bucket mein dhoondhega — value hamesha ke liye kho gayi, aur GC bhi use free nahi karega.

apply karo

  • Bade maps ke liye initial capacity do (expected / 0.75).
  • Keys immutable rakho — record, String, enum, wrapper.
  • User-controlled keys pe collision-heavy input ka soch ke rakho (treeify + randomized order isse handle karta hai).

ignore karo

  • Load factor tuning — 0.75 space/time ka acha compromise hai; 1.0 karoge to chains badhengi.
  • "Prime number bucket" wali purani salaah — Java power-of-two + spreading use karta hai.
  • Chhote maps (< 100) ke liye capacity math — waqt ki barbaadi.
04

Map family: LinkedHashMap, TreeMap, ConcurrentHashMap

intermediate

problem

Ek in-process cache chahiye: max 10,000 entries, LRU eviction, aur 200 threads isko hit karenge. Kaunsa Map lagega — aur kyun sirf ek Map kaafi nahi?

Interviewer ye bhi poochega: Hashtable, Collections.synchronizedMap, aur ConcurrentHashMap mein farak kya hai?

  • LRU sabse kam code mein kaise?
  • Sorted / range queries kaunsa Map deta hai?
  • Concurrency ka asli cost kahan hai?

solution

accessOrder=trueCAS + bin lockNavigableMap

LinkedHashMap HashMap extend karta hai aur har node mein before/after pointers add karta hai — yaani ek doubly-linked list saare entries ke upar. accessOrder=true pe har get() us node ko list ke end pe move kar deta hai. Iske saath removeEldestEntry() override karo aur LRU cache 10 line mein ready.

ConcurrentHashMap (Java 8+) mein segment lock nahi hote. Khali bucket pe insert ek CAS se hota hai (lock-free), aur non-empty bucket pe sirf us bucket ke head node pe synchronized lagta hai. Yaani 64 buckets = practically 64 independent locks. Resize ke waqt threads mil ke kaam batt lete hain (helpTransfer), aur migrate ho chuke bucket pe ForwardingNode lag jaata hai.

Hathtable / synchronizedMap poore map pe ek hi lock lagate hain — 200 threads matlab 199 wait kar rahe hain.

line 10–11
Capacity aise chuni gayi hai ki map kabhi resize hi na kare — bound already pata hai, to resize sirf waste hoga.
line 13
Teesra argument accessOrder = true — yahi LRU ka switch hai. false (default) hota to insertion order milta.
line 15–17
removeEldestEntry har put ke baad call hota hai. true return karo to sabse purani (least-recently-used) entry apne aap hat jaati hai. Tumhein eviction code likhna hi nahi padta.
line 19
Wrapping zaroori hai kyunki get() bhi structure modify karta hai (recency reorder), isliye read bhi thread-safe nahi hai. Lekin ye ek global lock hai — 200 threads pe ye bottleneck banega.
line 31–32
computeIfAbsent atomic hai: miss hone pe loader chalega aur result store hoga, bina "check-then-act" race ke. LinkedHashMap ke andar loader ke andar usi map ko mat chhuo — ConcurrentModificationException ya infinite loop mil sakta hai.
Scale ka sach: 200 threads + LRU = synchronizedMap se kaam nahi chalega. Production mein Caffeine use karo — wo ConcurrentHashMap ke upar ring-buffer se access record karta hai aur eviction ko async kar deta hai, isliye read path lock-free rehta hai. Interview mein: "LinkedHashMap se LRU banata hoon, par high-concurrency pe Caffeine/W-TinyLFU" — ye jawab mature lagta hai.

  • Shared mutable map → seedha ConcurrentHashMap, koi bahes nahi.
  • Enum key hai → EnumMap (bit-level fast, zero hashing).

  • Hashtable aur synchronizedMap naye code mein.
  • CHM ka size() exact maan ke logic likhna — wo approximate/weakly-consistent hai.
  • TreeMap sirf isliye ki "sorted acha lagta hai" — hashing ke muqable har op O(log n) aur 2–3x slow.

Set family: HashSet, LinkedHashSet, TreeSet, EnumSet

basics

problem

"HashSet andar se kya hai?" — aur agar wo Map hai, to har element ke liye value kya store hoti hai? Memory waste nahi hota?

Practical part: ek Kafka consumer duplicate message IDs bhej raha hai. Last 1 hour ke IDs yaad rakhne hain, memory blow-up ke bina. Kya use karoge?

  • Set ki 4 varieties ka farak?
  • EnumSet itna fast kyun hai?
  • Unbounded dedup set = memory leak?

solution

Set = Map ka wrapperEnumSet = bit vectorunbounded = leak

HashSet andar se ek HashMap hi hai. Har element key ban jaata hai aur value ki jagah ek shared static dummy object (PRESENT) rakha jaata hai. Yaani sabhi entries ek hi object ko point karti hain — waste sirf reference slot ka hai, poore object ka nahi. Isliye HashSet ka behaviour bilkul HashMap jaisa hai: O(1) average, treeify, resize, sab kuch.

EnumSet alag hi cheez hai — wo elements ko ek long bitmask mein store karta hai (64 tak enum constants ek long mein). add/contains/union sab bitwise operations ban jaate hain. Jab keys enum hon, iske aage koi Set nahi tik sakta.

Dedup wale case mein asli khatra unbounded growth hai: set kabhi shrink nahi hoga, aur GC use collect nahi kar sakta kyunki reference strong hai. Isliye set ko time ya size se bound karna padega:

line 9
Ek hi PRESENT object saare entries share karte hain — exactly jo HashSet andar karta hai. Naya object per entry banate to memory 10x ho jaati.
line 15
Yahan accessOrder = false hai: hum insertion order chahte hain (FIFO window), LRU nahi. Dedup mein "kab aaya" matter karta hai, "kab dobara dekha" nahi.
line 17–19
Yahi line memory leak ko rokti hai. Bina iske ye set unbounded badhta rahega aur ek din OutOfMemoryError dega.
line 24–25
put() purani value return karta hai — null matlab key nayi thi. Ek hi atomic call mein "check + insert" ho gaya; contains() phir add() karna race condition hoti.
line 29–30
Snapshot lene ke liye explicit synchronized block chahiye. synchronizedMap individual calls ko safe karta hai, iteration ko nahi — ye documented requirement hai.

  • TreeSet jab sorting ki zarurat sirf output pe ho — tab list bana ke ek baar sort kar lo.
  • HashSet ka memory overhead optimize karna jab tak wo profiler mein na dikhe.
06

Trees: BST, Red-Black, TreeMap & sorted views

intermediate → advanced

problem

Sorted keys 1, 2, 3, … 1,00,000 ek plain BST mein daalo — search O(log n) rehta hai ya nahi? Aur TreeMap isse kaise bachta hai?

Real scenario: ek pricing engine hai jahan "is timestamp se pehle wala latest rate" nikalna hai, lakhon baar per second. HashMap kaam nahi karega — kyun?

  • Balanced tree ki guarantee kya hai?
  • floor / ceiling / headMap ka matlab?
  • Concurrent sorted map ka jawab?

solution

plain BST → O(n)RB tree → O(log n)NavigableMap

Plain BST sorted input pe linked list ban jaata hai — har naya element right child ban jaata hai, height n, search O(n). Isiliye TreeMap ek red-black tree hai: har insert/delete ke baad recolouring aur rotation se height ≤ 2·log₂(n+1) guarantee hoti hai.

Red-black rules yaad rakhne layak hain: (1) har node red ya black, (2) root black, (3) red node ke dono children black — yaani do red lagatar nahi, (4) kisi bhi node se leaf tak har path pe black nodes ki ginti barabar. Insert hamesha red node se hota hai (kyunki red add karne se rule 4 nahi tootta), phir violation ko rotation/recolour se upar push kiya jaata hai.

Pricing engine wala sawaal HashMap se solve nahi ho sakta kyunki hashing order destroy kar deti hai. "Is key se chhoti sabse badi key" wali query ke liye ordered structure chahiye — yahi NavigableMap ka kaam hai.

line 11–12
Declared type NavigableMap hai — isse TreeMap aur ConcurrentSkipListMap ke beech switch karna ek line ka kaam hai. Skip list lock-free hai: multi-level linked lists jo probabilistically balance hoti hain, isliye rotations ki zarurat hi nahi padti (rotation concurrent-friendly nahi hota).
line 19–20
floorEntry(k) = "k se chhoti ya barabar sabse badi key". Uska ulta ceilingEntry hai. Ye O(log n) hai — HashMap mein yahi kaam O(n) scan maangta.
line 26
subMap ek view return karta hai, copy nahi — memory allocate nahi hoti aur backing map ke changes yahan dikhte hain.
line 31–33
View mutable hai: headMap(...).clear() asli map se wo entries delete kar deta hai. Retention/TTL cleanup ka sabse saaf idiom yahi hai.

07

Queue, Deque aur PriorityQueue (binary heap)

intermediate

problem

"Top 10 trending items" nikalne hain 5 crore events se. Sab sort karoge to O(n log n) aur poora data memory mein. Better tareeka?

Saath mein: PriorityQueue ko for loop se print karo to sorted kyun nahi aata? Aur Stack ki jagah aaj kya use hota hai?

  • Heap array mein kaise store hota hai?
  • ArrayDeque circular buffer kya hai?
  • peek O(1) par iteration random kyun?

solution

heap = arrayoffer/poll O(log n)iteration unordered

PriorityQueue ek binary min-heap hai jo array mein rehta hai. Index i ke children 2i+1 aur 2i+2 pe hote hain, parent (i-1)/2 pe. Koi node objects nahi, koi pointers nahi — sirf ek Object[]. Insert (offer) element ko end pe rakh ke siftUp karta hai; poll root nikaal ke last element ko root pe rakhta hai aur siftDown karta hai. Dono O(log n), aur peek O(1) kyunki minimum hamesha index 0 pe hai.

Iteration random kyun? Heap sirf parent ≤ children ka invariant maintain karta hai, siblings ke beech koi order nahi. Array ko seedha padhoge to woh partial order dikhega. Sorted chahiye to baar-baar poll() karo.

Top-K ke liye trick: size K ka min-heap rakho aur K se bada hone pe root nikaal do. Memory O(K), time O(n log K) — 5 crore events bhi stream mein handle ho jaate hain.

line 14
Heap "min" hai ranking order ke hisaab se, isliye root hamesha "sabse kamzor jise humne rakha hai" hota hai — top-K ka natural eviction candidate.
line 22–24
Jab tak capacity nahi bhari, sab andar. Ye warm-up phase O(K log K) hai.
line 26–29
Yahi asli optimization hai: peek() O(1) hai, isliye 99% events ek comparison ke baad hi reject ho jaate hain — na allocation, na sift.
line 34–40
Heap khud sorted nahi hai, isliye ordered output ke liye poll karke reverse karna padta hai. Ye O(K log K) hai — K chhota hai to negligible.

ArrayDeque ka design: ek array + head/tail index. Front pe add karna matlab head ko peeche ghumana (wrap-around), koi shifting nahi. Capacity hamesha power-of-two rakhi jaati hai taaki index wrap (i + 1) & (len - 1) se ho jaaye — modulo se tez. null isliye allowed nahi kyunki null "empty slot" ka marker hai.
Gotcha: PriorityQueue.remove(Object) O(n) hai (linear search), aur agar element ka priority baad mein badal gaya to heap invariant chup-chaap toot jaata hai. Priority badalni ho to remove karke dobara offer karo.

apply karo

  • Stack/Queue dono ke liye ArrayDeque.
  • Top-K, scheduling, Dijkstra, merge-K-lists → PriorityQueue.
  • Bounded top-K rakho, poora dataset sort mat karo.

ignore karo

  • Stack aur Vector — legacy.
  • PriorityQueue ko sorted collection samajhna — ye sirf "next best" deta hai.
  • Fibonacci heap type exotica — JDK mein hai hi nahi, interview mein binary heap kaafi.
08

BlockingQueue: producer-consumer aur backpressure

advanced

problem

Producer 10,000 msg/sec bana raha hai, consumer sirf 2,000 handle kar paata hai. Queue LinkedBlockingQueue hai (default unbounded). 30 minute baad kya hoga?

Aur: ThreadPoolExecutor ko unbounded queue doge to maximumPoolSize ka kya hota hai?

  • Bounded vs unbounded ka asli farak?
  • put / offer / add mein kya antar?
  • SynchronousQueue ka use kya hai?

solution

unbounded = OOMbounded = backpressure2-lock design

30 minute baad OutOfMemoryError. Unbounded queue ka matlab hai ki tum apni system ki speed mismatch ko heap mein jama kar rahe ho. Queue ek shock absorber hai, storage nahi. Bounded queue lagate hi put() block hone lagta hai aur ye slowness producer tak wapas pahunchti hai — isi ko backpressure kehte hain.

ThreadPoolExecutor ka rule: naye threads sirf tab bante hain jab queue full ho. Unbounded queue kabhi full nahi hoti, isliye pool kabhi corePoolSize se aage nahi badhta aur maximumPoolSize dead config ban jaata hai. Ye Executors.newFixedThreadPool ka chhupa hua khatra hai.

problem

G1 = defaultParallel = throughputZGC = <1 msCMS = removed

pehle khud socho, phir kholo
1. HashMap ka default capacity 16 aur load factor 0.75 kyun?

16 power-of-two hai, isliye bucket index (n-1) & hash se nikal aata hai — modulo ki zarurat nahi. 0.75 space aur time ka balance hai: kam rakhoge to memory waste aur resize jaldi-jaldi, zyada rakhoge to chains lambi aur lookups slow. Threshold = 16 × 0.75 = 12, yaani 13vi entry par table 32 ho jaati hai.

2. Java 8 ne HashMap mein kya badla?

Teen cheezein. (a) Ek bucket mein 8+ nodes aur table ≥ 64 ho to chain red-black tree ban jaati hai — worst case O(n) se O(log n). (b) Nayi entry chain ke tail pe judti hai (pehle head pe), jisse resize ke waqt banne wala infinite-loop race khatam ho gaya. (c) Resize mein rehash nahi hota — (hash & oldCapacity) == 0 se entry lo-list ya hi-list mein chali jaati hai, relative order preserve karte hue.

3. ConcurrentHashMap Hashtable se tez kyun hai?

Hashtable poore map par ek lock lagata hai — ek waqt mein ek hi thread. CHM (Java 8+) mein khaali bucket par insert CAS se hota hai (bilkul lock-free) aur bhare bucket par sirf us bucket ke head node par synchronized lagta hai. Yaani effectively bucket-count jitne independent locks. Reads to poori tarah lock-free hain kyunki Node.val aur next volatile hain.

4. ConcurrentHashMap mein null key/value allowed kyun nahi?

Ambiguity ki wajah se. Single-threaded map mein get(k) == null ka matlab tum containsKey se resolve kar sakte ho. Concurrent map mein get aur containsKey ke beech map badal sakta hai, isliye "key nahi hai" aur "value null hai" mein farak karna asambhav ho jaata. Doug Lea ne isko design se hi hata diya.

5. fail-fast aur fail-safe iterator mein farak?

Fail-fast (ArrayList, HashMap) modCount track karta hai aur structural change dikhte hi ConcurrentModificationException phenkta hai — ye best-effort hai, guarantee nahi. Fail-safe (asal naam "weakly consistent" — CopyOnWriteArrayList, ConcurrentHashMap) ya to snapshot par chalta hai ya live structure par tolerantly; exception nahi aata, par data thoda stale ho sakta hai.

6. Single thread mein ConcurrentModificationException kaise aa sakta hai?

Naam bhramit karta hai. Ye "concurrent access" nahi, "concurrent modification with respect to the iterator" detect karta hai. For-each loop ke andar list.remove(x) karoge to modCount badhta hai par iterator ka expectedModCount purana rehta hai — agle next() par CME. Fix: Iterator.remove() ya removeIf.

7. HashSet andar se kya hai, aur uska memory overhead?

Ek HashMap jahan har element key hai aur value ek shared static final Object PRESENT hai. Isliye overhead per element = HashMap Node (~32–48 bytes) + array slot, na ki ek extra value object — PRESENT sabhi entries ke liye ek hi hai.

8. LinkedHashMap se LRU cache kaise banate hain?

Constructor mein accessOrder = true pass karo (teesra parameter), phir removeEldestEntry(eldest) override karke size() > maxEntries return karo. get() automatically entry ko order-list ke end pe le jaata hai aur har put() ke baad JDK khud eldest entry hata deta hai.

9. ArrayList grow kaise hoti hai, aur amortized O(1) ka matlab?

Full hone par newCapacity = oldCapacity + (oldCapacity >> 1), yaani 1.5x, aur Arrays.copyOf se data copy. Ek individual add O(n) ho sakta hai, lekin n appends ka total copy work O(n) rehta hai (geometric series), isliye per-append average O(1) — yahi amortized O(1) hai.

10. equals override kiya, hashCode nahi — kya tootega?

Hash-based collections. Do "equal" objects ke hashCode alag honge, isliye wo alag buckets mein jaayenge: HashSet mein duplicates ghus jaayenge aur map.get(equalKey) null dega. List.contains aur TreeMap phir bhi kaam karte rahenge — isliye bug aksar der se pakda jaata hai.

11. Comparable aur Comparator mein kab kya?

Comparable class ke andar hai aur ek hi natural order deta hai (compareTo) — jaise String ka alphabetical. Comparator bahar se aata hai, ek hi class ke liye kitne bhi ho sakte hain, aur third-party class pe bhi lag jaata hai. Rule: agar order "obvious aur ek hi" hai to Comparable, warna Comparator.

12. TreeSet mein element "gayab" kaise ho sakta hai?

TreeSet duplicate ka faisla compareTo/Comparator se karta hai, equals se nahi. Agar comparator sirf ek field compare karta hai (jaise sirf salary), to alag-alag objects "equal" maane jaayenge aur chup-chaap add hi nahi honge. Isliye comparator ko equals-consistent rakho ya aakhir mein unique tie-breaker lagao.

13. ArrayDeque LinkedList se behtar kyun hai queue ke liye?

ArrayDeque circular array hai: contiguous memory, cache-friendly, per-element koi node object nahi. LinkedList har element pe ~40 byte ka node banata hai — memory bhi zyada aur GC pressure bhi. Javadoc khud kehti hai ki ArrayDeque stack aur queue dono ke liye faster hai.

14. PriorityQueue ko iterate karo to sorted kyun nahi aata?

Wo binary heap hai, sorted array nahi. Heap sirf itna guarantee karta hai ki parent apne children se chhota (ya bada) hai — siblings ke beech koi order nahi. Sorted output chahiye to baar-baar poll() karo, ya list bana ke sort() kar lo.

15. Unbounded BlockingQueue kyun khatarnaak hai?

Wo speed mismatch ko heap mein jama karti hai. Producer consumer se tez hai to queue tab tak badhegi jab tak OutOfMemoryError na aa jaaye. Aur ThreadPoolExecutor mein unbounded queue kabhi full nahi hoti, isliye pool corePoolSize se aage badhta hi nahi — maximumPoolSize bekaar ho jaata hai. Hamesha bounded queue + rejection policy.

16. put, offer aur add mein farak?

add = space na ho to IllegalStateException. offer = turant false return. offer(e, timeout, unit) = utni der wait karke phir false. put = jagah banne tak block. Similarly consumer side: remove throws, poll returns null, take blocks.

17. Java mein memory leak possible hai? Kaise?

Haan — "unwanted reachability" ke roop mein. GC sirf unreachable objects hataati hai; agar tumhara static map, listener list, ya thread pool ka ThreadLocal us object ko strongly hold kiye hue hai to wo kabhi collect nahi hoga. Top patterns: unbounded static cache, unregistered listeners, ThreadLocal without remove(), mutable keys, aur redeploy pe ClassLoader leak.

18. Weak, soft aur phantom reference mein kya farak?

Weak: agli GC cycle mein clear (canonical maps, WeakHashMap, ThreadLocal keys). Soft: sirf memory pressure par clear, OOM se pehle (memory-sensitive cache). Phantom: object finalize hone ke baad enqueue hota hai, get() hamesha null deta hai — sirf cleanup notification ke liye (Cleaner, DirectByteBuffer).

19. Minor GC aur Major/Full GC mein farak?

Minor GC sirf Young generation (Eden + Survivors) collect karti hai — copying algorithm, live objects hi copy hote hain, isliye tez. Major GC Old generation ko collect karti hai (mark-sweep-compact ya G1 ka mixed collection) — bada region, zyada live data, isliye kaafi lambi. Full GC pooora heap + Metaspace, aur ye aksar failure ka signal hai (promotion failure, humongous allocation, ya System.gc()).

20. "Garbage First" naam ka matlab kya hai?

G1 heap ko barabar size ke regions mein baant deta hai aur concurrent marking se har region ka garbage percentage jaan leta hai. Collection ke waqt wo sabse zyada garbage wale regions pehle uthata hai — kam kaam mein sabse zyada jagah. Tumhara pause target (-XX:MaxGCPauseMillis) decide karta hai ki ek baar mein kitne regions ka collection set banega.

21. ZGC sub-millisecond pause kaise deta hai jabki objects move ho rahe hote hain?

Coloured pointers aur load barriers. Reference ke unused bits mein GC state (marked / remapped) store hota hai. Jab application koi reference load karti hai, ek chhota barrier chalta hai jo check karta hai ki object relocate hua ya nahi, aur zaroorat par reference ko naye address pe theek kar deta hai (self-healing). Isliye marking aur relocation dono application ke saath concurrently ho sakte hain; stop-the-world sirf chhote root-scanning ke liye hota hai.

22. Card table aur write barrier kya hai?

Minor GC ko sirf Young gen scan karni hai, par Old gen ka object Young ke object ko point kar sakta hai. Poori Old gen scan karna mehnga hoga, isliye JVM heap ko ~512-byte "cards" mein baant kar ek byte-array (card table) rakhta hai. Har reference write par ek chhota write barrier chalta hai jo us card ko "dirty" mark kar deta hai. Minor GC sirf dirty cards scan karti hai. G1 mein iska region-wise version remembered set kehlata hai.

23. 8 GB heap wali service ka p99 500 ms hai. Debug kaise karoge?

Pehle GC log on karo (-Xlog:gc*,safepoint) aur confirm karo ki latency GC se hi aa rahi hai. Phir dekho: (a) pause GC ka hai ya time-to-safepoint ka, (b) Minor GC frequent hai (allocation rate high) ya Major (promotion rate high), (c) har Full GC ke baad live set badh raha hai kya — to ye leak hai, flag se theek nahi hoga. Fix ka order: allocation kam karo → heap/region size theek karo → tabhi collector badlo (jaise G1 se generational ZGC).

24. Immutable collection ke fayde GC ke hisaab se kya hain?

Immutable object kabhi apne se naye objects ko point nahi karta, isliye wo Old gen mein hote hue bhi Young gen ko reference nahi kar sakta — card table dirty nahi hota aur Minor GC ka scan kaam kam hota hai. Saath hi safe publication free milti hai (final fields), defensive copies ki zarurat khatam, aur cache mein rakhna nirdhokh ho jaata hai. Cost: har "change" ek nayi copy = allocation churn, isliye tight loops mein avoid karo.

25. Ek collection choose karne ke liye 30-second framework batao.

Chaar sawaal: (1) Access — index, key, order, ya "best element"? (2) Order — insertion, sorted, ya koi nahi? (3) Concurrency — kitne threads, read-heavy ya write-heavy? (4) Bound — worst case kitna bada? Answer na pata ho to bound lagao. Inke jawab se pick lagbhag automatic ho jaata hai, aur phir ek line mein cost bolo: "iska cost X hai, aur Y condition badle to Z pe jaana padega."

Padhne ke baad dekhna zaroori hai. Internal architecture — bucket, node, rotation, heap generation, GC phases — sab animated form mein: Animation lab kholo.
