Collections — Array, ArrayList, LinkedList & More

Array

  • Fixed size at creation
  • Stores primitives OR objects
  • O(1) random access
  • No utility methods
  • Memory contiguous

ArrayList

  • Dynamic size (grows 1.5×)
  • Objects only (autoboxing)
  • O(1) get, O(n) insert/delete mid
  • Rich API via List
  • Backed by array internally

LinkedList

  • Dynamic, doubly-linked nodes
  • Objects only
  • O(1) insert/delete at ends
  • O(n) random access
  • More memory per element
// ── Array — fixed, fast, supports primitives ─────────────────────────
int[]      nums    = new int[5];           // primitives — zero GC overhead
String[]   names   = {"Alice", "Bob"};      // object array
int[][]    matrix  = new int[3][4];         // 2D array
Arrays.sort(nums);                           // O(n log n)
Arrays.binarySearch(nums, 3);              // O(log n) — must be sorted
Arrays.copyOfRange(nums, 1, 4);            // subarray copy
int[] copy = Arrays.copyOf(nums, nums.length * 2); // grow

// ── ArrayList — best for: read-heavy, random access ─────────────────
List<String> list = new ArrayList<>(16);   // pre-size avoids resizing
list.add("Alice");
list.add(0, "Bob");                        // O(n) — shifts elements right
list.set(1, "Carol");                      // O(1) — direct index set
list.remove(0);                            // O(n) — shifts left
list.get(0);                               // O(1)
Collections.sort(list);
List<String> immutable = List.of("A","B"); // Java 9+ unmodifiable

// ── LinkedList — best for: queue/deque, frequent head/tail ops ───────
LinkedList<String> ll = new LinkedList<>();
ll.addFirst("Alice");                      // O(1)
ll.addLast("Bob");                       // O(1)
ll.removeFirst();                          // O(1)
ll.peekFirst();                            // O(1) no remove
ll.get(3);                                 // O(n) — traverses nodes
ll.offerFirst("Carol");                   // use as Deque

ArrayList vs LinkedList: For 99% of use cases, ArrayList is faster — CPU cache locality of contiguous memory beats LinkedList's pointer chasing. Use LinkedList only when you need O(1) head/tail ops as a Deque.
// ── Internal workings of HashMap ─────────────────────────────────────
// 1. key.hashCode() computed
// 2. Hash spread: (hash ^ (hash >>> 16)) — reduces collisions
// 3. Bucket index: hash & (capacity - 1)
// 4. If bucket occupied → linked list (Java 7) or tree (Java 8, ≥8 nodes)
// 5. At 75% load factor → resize to 2x, rehash all entries
//
// Java 8 improvement: bucket list → Red-Black Tree when size ≥ 8
// Worst-case lookup: O(n) → O(log n) after treeification

// Always override BOTH hashCode AND equals for map keys:
public record OrderKey(long id, String region) {
    // Record auto-generates hashCode + equals from all components ✅
}

// Wrong — only overriding equals breaks HashMap contract!
public class BadKey {
    int id;
    @Override public boolean equals(Object o) { return true; }
    // ❌ missing hashCode → equal objects in different buckets → broken!
}

JVM — Java Virtual Machine

The runtime engine that executes Java bytecode. Provides: class loading, bytecode verification, JIT compilation, memory management (GC), and security sandboxing.

Platform-specific binary. Turns .class files into native machine code.

  • ClassLoader subsystem
  • Execution Engine (JIT)
  • GC (memory management)
  • Runtime data areas
JRE — Java Runtime Environment

JVM + Java class libraries. Everything needed to run a Java program. No compilers or development tools.

What end users install to run Java apps. Deprecated as standalone since Java 11 — JDK now serves both.

  • JVM
  • Core class libraries (java.lang, java.util…)
  • java command
  • No javac, javadoc
JDK — Java Development Kit

JRE + development tools. Everything needed to write, compile, debug, and run Java programs.

What developers install. Available as OpenJDK (free) or vendor builds (Eclipse Temurin, Amazon Corretto, GraalVM).

  • JRE (JVM + libraries)
  • javac — compiler
  • javadoc, jdb, jcmd
  • jconsole, jmap, jstat
// ── How your code travels: source → bytecode → native ────────────────

// Step 1: Developer writes source code
// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello World");

// Step 2: javac (JDK tool) compiles → Hello.class (platform-neutral bytecode)

// Step 3: JVM loads + verifies Hello.class via ClassLoader

// Step 6: Subsequent calls use native code directly → near C speed

// Tier 0: Interpreter

// Tier 2: C1 with profiling — monitors call freq, branch patterns

Heap — shared, GC managed

Where all objects and arrays live. Shared across all threads. Subject to GC. Split into Young and Old generations.

  • All new allocations go here
  • Instance variables stored here
  • Controlled by -Xms / -Xmx
  • OOM = java.lang.OutOfMemoryError: Java heap space
Stack — per thread, LIFO

Each thread has its own stack. Holds stack frames — one per method call. Each frame has: local variables, operand stack, frame data.

  • Primitive local variables stored here
  • Object references stored here (object itself on heap)
  • Auto-deallocated when method returns
  • Overflow = StackOverflowError
Metaspace — class metadata

Stores class structure: method bytecode, field names, constant pool, annotations. Replaced PermGen in Java 8. Uses native memory (outside heap).

  • Grows automatically (no hard limit by default)
  • Set -XX:MaxMetaspaceSize=256m
  • OOM = OutOfMemoryError: Metaspace
  • Class loader leak → Metaspace growth
PC Register + Native Stack

PC Register: one per thread. Points to the current JVM instruction being executed.

Native Method Stack: for native (C/C++) methods called via JNI. Separate from Java stack.

// ── Where does each thing live? ──────────────────────────────────────

public class MemoryDemo {

    // ── Static fields: Metaspace (Java 8+) ──────────────────────────
    static int    STATIC_INT = 42;           // value in Metaspace
    static String STATIC_STR = "hello";     // ref in Metaspace, obj in Heap/Pool

    // ── Instance fields: Heap (inside the object) ───────────────────
    int    instanceInt = 10;                  // inside the object on Heap
    String instanceStr = "world";            // ref on Heap, value in String Pool

    public void method() {
        // ── Local variables: Stack frame ─────────────────────────────
        int    localInt = 5;                  // primitive: ON the Stack
        String localStr = "local";           // reference ON Stack, object in Pool
        Object obj      = new Object();     // reference ON Stack, object ON Heap

        // ── Arrays: always on Heap ───────────────────────────────────
        int[] arr = new int[100];            // arr ref: Stack, int[]: Heap
    }
}

// ── StackOverflowError: too many nested calls ────────────────────────
void infinite() { infinite(); }  // each call adds a new frame → stack overflows

// ── Escape analysis: objects that don't "escape" may be stack-allocated
public String format(int x) {
    StringBuilder sb = new StringBuilder(); // JIT may put this on Stack!
    sb.append("value=").append(x);
    return sb.toString();  // only the String escapes — sb stays local
}

// ── Custom functional interfaces ─────────────────────────────────────

@FunctionalInterface
interface ThrowingFunction<T, R> {
    R apply(T t) throws Exception;   // allows checked exceptions

    static <T,R> Function<T,R> wrap(ThrowingFunction<T,R> fn) {
        return t -> {
            try { return fn.apply(t); }
            catch (Exception e) { throw new RuntimeException(e); }
        };
    }
}

// Use in streams that throw checked exceptions:
List<String> urls = List.of("https://a.com", "https://b.com");
List<String> bodies = urls.stream()
    .map(ThrowingFunction.wrap(url -> fetchBody(url))) // throws IOException
    .toList();

// Proper interrupt handling pattern:
public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            doWork();
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // ✅ restore interrupt flag
            break;                               // clean exit
        }
    }
}

// ── Locks — all types ────────────────────────────────────────────────

// 1. synchronized — simplest, intrinsic lock (monitor)
synchronized (this) { /* critical section */ }
synchronized (MyClass.class) { /* static lock */ }

// 2. ReentrantLock — more control than synchronized
ReentrantLock lock = new ReentrantLock(true); // true = fair (FIFO order)
lock.lock();
try {
    /* critical section */
} finally {
    lock.unlock(); // always in finally!
}
boolean got = lock.tryLock(100, TimeUnit.MILLISECONDS); // non-blocking try
lock.lockInterruptibly();                               // responds to interrupt

// 3. ReadWriteLock — many readers OR one writer
ReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();   // multiple threads can hold readLock simultaneously
try { readData(); } finally { rwLock.readLock().unlock(); }

rwLock.writeLock().lock();  // exclusive — no readers or other writers
try { writeData(); } finally { rwLock.writeLock().unlock(); }

// 4. StampedLock (Java 8) — fastest, optimistic reads
StampedLock sl = new StampedLock();
long stamp = sl.tryOptimisticRead();  // no lock — just a stamp
int val = sharedVal;
if (!sl.validate(stamp)) {           // did a write happen? retry with read lock
    stamp = sl.readLock();
    try { val = sharedVal; } finally { sl.unlockRead(stamp); }
}

// 5. Semaphore — limit concurrent access to N
Semaphore sem = new Semaphore(3); // max 3 concurrent
sem.acquire();  // blocks if 0 permits
try { useResource(); } finally { sem.release(); }

// 6. CountDownLatch — wait for N events
CountDownLatch latch = new CountDownLatch(3);
// 3 threads each call latch.countDown() when done
latch.await(); // blocks until count reaches 0

private static final ThreadLocal<Connection> CTX = new ThreadLocal<>();

String Pool & String Constant Pool

String is immutable and heavily used. The JVM maintains a String Pool (intern pool) in the Heap (moved from PermGen in Java 7) to deduplicate string literals and save memory.

// ── String creation: literal vs new ─────────────────────────────────

// Literal → goes through String Pool (interned automatically)
String a = "hello";   // stored in String Pool, reused if already there
String b = "hello";   // SAME object from pool → a == b is TRUE

// new String() → always creates new object on Heap (bypasses pool)
String c = new String("hello");   // NEW object, NOT in pool
String d = new String("hello");   // ANOTHER new object

System.out.println(a == b);      // true  — same pool reference
System.out.println(a == c);      // false — c is a different heap object
System.out.println(c == d);      // false — both different heap objects
System.out.println(a.equals(c)); // true  — ALWAYS use equals() for content!

// intern() — manually move a heap String to the pool
String e = c.intern();           // returns pool reference for "hello"
System.out.println(a == e);      // true — e now points to pool object

// Compile-time constants → automatically pooled
String f = "hel" + "lo";         // compiler folds → "hello" → pool
System.out.println(a == f);      // true

// Runtime concatenation → NOT pooled (creates new object)
String part = "hel";
String g = part + "lo";          // runtime → new StringBuilder().append().toString()
System.out.println(a == g);      // false — g is a new heap object

volatile & synchronized Keywords

volatile — visibility guarantee
  • Reads/writes go directly to main memory
  • Thread caches (CPU caches) are bypassed
  • Guarantees visibility but NOT atomicity
  • No locking — faster than synchronized
  • Use for: flags, single-value state, double-checked locking
synchronized — atomicity + visibility
  • Only one thread at a time in the block
  • Acquires monitor lock on entry, releases on exit
  • Guarantees both visibility AND atomicity
  • Can cause deadlock if locks taken in wrong order
  • Use for: compound operations (check-then-act, read-modify-write)
// ── volatile: visibility — not atomicity ────────────────────────────

class StatusChecker {

    // Without volatile: running may stay true in thread's CPU cache
    // even after main thread sets it to false
    private volatile boolean running = true; // ✅ all threads see latest value

    public void run() {
        while (running) {         // reads from main memory every iteration
            doWork();
        }
    }

    public void stop() {
        running = false;          // write visible to all threads immediately
    }
}

// ❌ volatile is NOT enough for compound operations
private volatile int count = 0;

void badIncrement() {
    count++;    // ❌ NOT atomic! This is: read count, add 1, write back
                // Two threads can both read 5, both write 6 → lost update
}

// ✅ Fix 1: synchronized
synchronized void syncIncrement() { count++; }

// ✅ Fix 2: AtomicInteger
AtomicInteger atomicCount = new AtomicInteger(0);
atomicCount.incrementAndGet();   // atomic — no lock needed

// ── synchronized: all forms ──────────────────────────────────────────

class Counter {
    private int count = 0;

    // 1. Synchronized instance method — locks on 'this'
    public synchronized void increment() { count++; }
    public synchronized int  get()       { return count; }

    // 2. Synchronized static method — locks on Counter.class
    private static int globalCount = 0;
    public static synchronized void globalIncrement() { globalCount++; }

    // 3. Synchronized block — finer granularity (better performance)
    private final Object lock = new Object(); // dedicated lock object

    public void fineGrained() {
        // do non-critical stuff here — NOT locked
        synchronized (lock) {
            count++;  // only critical section is locked
        }
        // more non-critical stuff here
    }
}

// ── Deadlock: two threads, two locks, opposite order ─────────────────

class DeadlockDemo {
    private final Object lockA = new Object();
    private final Object lockB = new Object();

    // Thread 1: acquires A, waits for B
    void method1() {
        synchronized (lockA) {
            synchronized (lockB) { /* work */ }  // ❌ deadlock possible
        }
    }

    // Thread 2: acquires B, waits for A
    void method2() {
        synchronized (lockB) {
            synchronized (lockA) { /* work */ }  // ❌ deadlock possible
        }
    }

    // ✅ Fix: always acquire locks in the SAME order
    void method1Fixed() { synchronized(lockA) { synchronized(lockB) {} } }
    void method2Fixed() { synchronized(lockA) { synchronized(lockB) {} } }
}

// ── Double-checked locking with volatile (thread-safe singleton) ─────
class Singleton {
    private static volatile Singleton INSTANCE; // volatile required!

    public static Singleton getInstance() {
        if (INSTANCE == null) {                  // 1st check (no lock)
            synchronized (Singleton.class) {
                if (INSTANCE == null) {          // 2nd check (with lock)
                    INSTANCE = new Singleton();
                }
            }
        }
        return INSTANCE;
    }
}

final vs finally vs finalize

final — keyword

Applies to variables, methods, classes. Means "cannot change/override".

finally — block

Part of try-catch. Always executes (except System.exit()). Used for cleanup.

finalize — method

Called by GC before object collection. Deprecated since Java 9. Never use it.

// ── final: 4 use cases ───────────────────────────────────────────────

// 1. final variable — value cannot change after assignment
final int MAX = 100;
// MAX = 200;  ❌ compile error

final List<String> list = new ArrayList<>();
list.add("hello");  // ✅ CONTENTS can change
// list = new ArrayList<>();  ❌ REFERENCE cannot change

// 2. final method — cannot be overridden by subclasses
class Base {
    public final void doSecure() { /* cannot be overridden */ }
}

// 3. final class — cannot be subclassed
public final class ImmutableValue { // e.g. String, Integer are final
    private final int value;
    ImmutableValue(int v) { this.value = v; }
}

// 4. effectively final (Java 8+) — variable not declared final
// but never reassigned — can be used in lambdas
int x = 10;  // effectively final
Runnable r = () -> System.out.println(x); // ✅ works

// ── finally: always runs ─────────────────────────────────────────────
try {
    return "from try";  // finally STILL runs before this return
} catch (Exception e) {
    throw new RuntimeException(e); // finally runs before this throw
} finally {
    closeResources();   // ✅ ALWAYS executes
    // ❌ EXCEPTION: System.exit() or JVM crash skips finally
    // ❌ EXCEPTION: if finally itself throws, original exception lost
}

// finally with return — the return in finally overrides try/catch returns
int tricky() {
    try { return 1; }
    finally { return 2; }  // ❌ bad practice — returns 2, hides try's return
}

// ── finalize: deprecated — DO NOT USE ───────────────────────────────
class OldResource {
    @Override
    @Deprecated
    protected void finalize() throws Throwable {
        // ❌ Called by GC finalizer thread — unpredictable timing
        // ❌ Needs 2 GC cycles to collect objects with finalizers
        // ❌ No guarantee it ever runs
        // ❌ Can cause object resurrection
    }
}

// ✅ Use AutoCloseable + try-with-resources instead
class GoodResource implements AutoCloseable {
    @Override
    public void close() {
        cleanup();  // deterministic, immediate, no GC involvement
    }
}
try (var r = new GoodResource()) { use(r); }

// ── Encapsulation — hide implementation, expose interface ────────────
public class BankAccount {
    private BigDecimal balance;     // hidden — can't set directly
    private String     owner;

    public BankAccount(String owner, BigDecimal initial) {
        this.owner   = owner;
        this.balance = initial;

String == vs .equals()Always use .equals() for content comparison. == compares references.
intern()Moves String to pool. Useful for deduplication. Don't intern unique strings.
finalVariable = immutable ref. Method = no override. Class = no subclass.
finalize()Deprecated since Java 9. Use AutoCloseable + try-with-resources instead.
staticNo this. One per class. Can't access instance members. Static block runs once on load.
Memory leaksStatic collections, ThreadLocal, no-eviction caches, listeners not removed.
