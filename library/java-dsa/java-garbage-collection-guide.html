What is Garbage Collection?

Garbage Collection (GC) is the JVM's automatic process of finding objects in heap memory that are no longer reachable from any live thread and reclaiming that memory. You never call free() — the JVM does it for you, periodically, in the background.

Manual Memory (C/C++)
  • Developer calls malloc() / free()
  • Forget to free → memory leak
  • Free too early → use-after-free crash
  • Free twice → double-free corruption
Automatic GC (Java / JVM)
  • Allocate with new — JVM handles reclamation
  • No dangling pointers possible
  • No double-free bugs
  • Trade-off: GC pauses + tuning required
The core GC algorithm — 3 phases
1. Mark
→
2. Sweep / Compact
→
3. Return to pool
Mark: trace from GC roots (stack, statics) to find all live objects
Sweep: identify unreachable objects and reclaim memory
Compact (optional): slide live objects together to eliminate fragmentation 
// ─── What "reachable" means ──────────────────────────────────────────

public class GcRootsExample {

    static Config appConfig = new Config();  // GC root → always reachable

    public void process() {

        Order order = new Order();            // on stack → reachable
        List<Item> items = order.getItems(); // reachable via order

        String temp = new String("temp");    // reachable (on stack)

        Order old = new Order();
        order = new Order();                  // old Order → unreachable → GC

    } // end of method → 'order' goes out of scope → entire graph GC-able
}

Young Generation

Eden: All new objects are allocated here. Small, fills fast.

S0 / S1: Objects that survived at least one Minor GC bounce between these.

GC here = Minor GC. Fast (milliseconds). Frequent.

Old Generation (Tenured)

Objects that survived enough Minor GCs are promoted here.

Long-lived: caches, singletons, static data.

GC here = Major/Full GC. Slow (seconds). Infrequent.

Metaspace

Stores class metadata (method bytecode, field names, constant pool).

Replaced PermGen in Java 8. Uses native memory — no hard heap cap by default.

Set -XX:MaxMetaspaceSize to prevent unbounded growth.

// Object lifecycle through the heap ─────────────────────────────────

//  1. New object → allocated in EDEN
//  2. Eden full → Minor GC triggers
//     Live objects → copied to Survivor 0 (age = 1)
//     Dead objects → swept
//  3. Next Minor GC
//     Survivors in S0 → age++ → copied to S1
//     Dead Eden objects → swept
//  4. When age >= MaxTenuringThreshold (default 15)
//     Object PROMOTED to Old Gen
//  5. Old Gen full → Major / Full GC triggers (STW pause)

// View flags controlling this:
// -XX:NewRatio=2            Old:Young ratio (2 = Old is 2x Young)
// -XX:SurvivorRatio=8       Eden:Survivor ratio (8 = Eden is 8x S0)
// -XX:MaxTenuringThreshold=15  Age before promotion to Old

Object Lifecycle
ℹ️
Generational Hypothesis: The core insight behind Java's GC design — most objects die young. Studies show 80–98% of objects become unreachable within a few hundred milliseconds. Separating short-lived (Young) from long-lived (Old) objects makes GC vastly more efficient.

Full GC — The worst case (stop everything)

A Full GC collects all generations and compacts the heap. The entire JVM pauses — no requests are served. Can take seconds on large heaps.

Triggered by: Old Gen full, Metaspace full, explicit System.gc(), allocation failure when no region available, promotion failure.

Modern GCs (G1, ZGC, Shenandoah) are designed to avoid Full GC entirely under normal operation.

// ─── What "Stop-The-World" (STW) means ──────────────────────────────
//
// ALL application threads pause. GC runs alone. Then app resumes.
// This is what causes "GC pauses" visible in your latency charts.
//
// Minor GC STW:  1 – 10 ms   (small Eden → fast)
// G1 GC STW:     10 – 200 ms  (concurrent, low pause target)
// Full GC STW:   1 – 30 sec   (entire heap, compact — avoid this!)
//
// ZGC / Shenandoah: STW < 10 ms regardless of heap size (sub-ms goal)

// ─── Reference types — affect GC behavior ───────────────────────────

import java.lang.ref.*;

// Strong reference (default) — GC cannot collect
Object strong = new Object();

// SoftReference — collected only when JVM is LOW on memory
// Perfect for memory-sensitive caches
SoftReference<byte[]> softCache =
    new SoftReference<>(new byte[1024 * 1024]); // 1MB cache
byte[] data = softCache.get(); // null if GC collected it

// WeakReference — collected at NEXT GC, regardless of memory
// Use in WeakHashMap for keys that shouldn't prevent GC
WeakReference<Session> weakSession = new WeakReference<>(session);

// PhantomReference — notified AFTER object finalized (advanced cleanup)
ReferenceQueue<Resource> queue    = new ReferenceQueue<>();
PhantomReference<Resource> phantom = new PhantomReference<>(res, queue);

GC Collectors — All Major Algorithms

Java ships with 6 garbage collectors. Each makes different trade-offs between throughput, latency, and complexity.

CollectorJavaPauseThroughputUse CaseStatus
Serial GC1+ High Low Single-core, tiny heaps, embedded Niche
Parallel GC1+ Medium High Batch jobs, throughput-focused Active
CMS4–14 Low Medium Low-latency servers (old way) Removed J14
G1 GC ⭐9+ Low High Most server apps. Default since Java 9 Default
ZGC15+ (prod) < 1 ms Medium Ultra-low latency, large heaps (TB) Production
Shenandoah12+ < 10 ms Medium Consistent low latency, any heap size Production
G1 GC — Garbage First
Default since Java 9

Divides heap into equal-sized regions (1–32 MB each). Collects regions with most garbage first (hence "Garbage First"). Aims for a configurable pause target.

-XX:+UseG1GC
-XX:MaxGCPauseMillis=200     # target (not guarantee)
-XX:G1HeapRegionSize=16m     # region size
-XX:G1NewSizePercent=20      # min Young Gen %
-XX:G1MaxNewSizePercent=60   # max Young Gen %
ZGC — Z Garbage Collector
Java 15+ production-ready

Concurrent coloring using load barriers and colored pointers. Does almost all work concurrently — STW pauses are < 1 ms regardless of heap size (even terabyte heaps).

-XX:+UseZGC
-XX:ZCollectionInterval=5     # force GC every 5s if idle
-XX:ZAllocationSpikeTolerance=2 # spike buffer factor
Shenandoah
RedHat / OpenJDK 12+

Concurrent evacuation — moves objects while the app runs. Uses read/write barriers. Achieves consistent low latency. Heap size doesn't affect pause time.

-XX:+UseShenandoahGC
-XX:ShenandoahGCHeuristics=adaptive  # or: compact, aggressive
Parallel GC
Best for batch / throughput

Uses multiple threads for both Minor and Major GC. Accepts longer pauses in exchange for maximum throughput — ideal for batch jobs, data pipelines, Kafka consumers.

-XX:+UseParallelGC
-XX:ParallelGCThreads=8      # GC thread count
-XX:GCTimeRatio=99           # 99% time on app, 1% on GC
💡
Which collector should you use?
  • Default Spring Boot microservice: G1 (already the default) — no flag needed
  • Latency-sensitive (trading, gaming, real-time API): ZGC (-XX:+UseZGC) on Java 17+
  • Batch processing / ETL / data pipelines: Parallel GC (-XX:+UseParallelGC)
  • Large heap > 16 GB with low-latency requirement: ZGC or Shenandoah

Reading GC Logs

GC logs are the most reliable source of truth about your application's memory behaviour. Here's how to read them.

# ─── Typical G1 GC log output (Java 17 unified logging) ─────────────

# Format: [time][uptime][pid][level][tag] message

# Minor GC (Young collection)
[2024-01-15T10:30:45.123+0000][12.456s][1][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 512M->128M(2048M) 8.234ms
#                                                              ├──── type ──────────────┤ ├before┤  ├after┤  ├─max─┤  ├─pause─┤

# Concurrent Mark (no STW)
[2024-01-15T10:30:55.456+0000][22.789s][1][info][gc] GC(43) Concurrent Mark Cycle

# Mixed GC (Young + some Old regions)
[2024-01-15T10:31:05.789+0000][32.122s][1][info][gc] GC(44) Pause Young (Mixed) (G1 Evacuation Pause) 1024M->256M(2048M) 45.123ms

# Full GC (BAD — should be rare/never)
[2024-01-15T10:31:30.000+0000][57.333s][1][warn][gc] GC(45) Pause Full (G1 Evacuation Failure) 1900M->1800M(2048M) 4532.456ms
#                                            ├── reason: heap almost full ──┤ ├────── 4.5 seconds pause ──────┤

# What to look for:
# ✅ Young GC pause: 5-20ms — normal
# ✅ Mixed GC pause: 20-200ms — normal for G1
# ⚠️  Pause > 500ms — investigate
# ❌  Full GC — almost always a problem
# ❌  Heap after GC not shrinking — memory leak likely

GC Log Analysis
// ─── Programmatic GC monitoring in your app ──────────────────────────

@Component
public class GcMonitor implements NotificationListener {

    @PostConstruct
    public void registerListeners() {
        ManagementFactory.getGarbageCollectorMXBeans()
            .forEach(gcBean ->
                ((NotificationEmitter) gcBean)
                    .addNotificationListener(this, null, gcBean)
            );
    }

    @Override
    public void handleNotification(Notification notif, Object handback) {

        if (!notif.getType().equals(GarbageCollectionNotificationInfo.GARBAGE_COLLECTION_NOTIFICATION))
            return;

        var info   = GarbageCollectionNotificationInfo.from(
            (CompositeData) notif.getUserData()
        );
        var gcInfo = info.getGcInfo();
        long durationMs = gcInfo.getDuration();

        log.info("GC [{}] action={} cause={} duration={}ms",
            info.getGcName(),
            info.getGcAction(),
            info.getGcCause(),
            durationMs
        );

        // Alert if GC pause exceeds SLA
        if (durationMs > 500) {
            alertService.warn("GC pause {}ms exceeds 500ms SLA", durationMs);
        }

        // Record as Micrometer metric for Grafana
        Metrics.timer("jvm.gc.pause",
            "gc", info.getGcName(),
            "cause", info.getGcCause()
        ).record(durationMs, TimeUnit.MILLISECONDS);
    }
}

What Goes Wrong Without Proper GC Tuning

💀 OutOfMemoryError

JVM cannot allocate any more objects. Heap is full and GC couldn't reclaim enough. App crashes.

Causes: memory leak, undersized heap, too many large objects.

🧊 GC Thrashing

GC runs almost constantly, reclaiming tiny amounts each time. App spends >98% of time in GC → effectively frozen.

JVM throws: "GC overhead limit exceeded"

⏱ Long STW Pauses

Full GC taking 5–30 seconds. All requests timeout. Kubernetes kills the pod (liveness probe fails). Service restarts.

Causes: wrong collector, oversized heap, promotion failure.

// ─── Common memory leak patterns that break GC ───────────────────────

@Component
public class MemoryLeakExamples {

    // ❌ Leak 1: Static collection that grows forever
    private static final List<Event> EVENT_HISTORY = new ArrayList<>();

    public void trackEvent(Event e) {
        EVENT_HISTORY.add(e);   // ❌ never removed → OLD GEN fills → Full GC
    }

    // Fix: use bounded collection
    private static final Deque<Event> EVENT_HISTORY_FIXED =
        new ArrayDeque<>();

    public void trackEventFixed(Event e) {
        if (EVENT_HISTORY_FIXED.size() >= 1000) {
            EVENT_HISTORY_FIXED.removeFirst();  // bounded
        }
        EVENT_HISTORY_FIXED.addLast(e);
    }

    // ❌ Leak 2: ThreadLocal not removed → leaks in thread pool environments
    private static final ThreadLocal<Context> CTX = new ThreadLocal<>();

    public void handleRequestBad() {
        CTX.set(new Context());
        doWork();
        // ❌ Missing CTX.remove() → thread pool thread keeps Context alive
    }

    // Fix: always remove in finally
    public void handleRequestGood() {
        CTX.set(new Context());
        try {
            doWork();
        } finally {
            CTX.remove();   // ✅ always clean up
        }
    }

    // ❌ Leak 3: Cache with no eviction policy
    private final Map<String, Result> cache = new HashMap<>();

    public Result getResultBad(String key) {
        return cache.computeIfAbsent(key, this::compute);  // ❌ grows forever
    }

    // Fix: use Caffeine with size + time eviction
    private final Cache<String, Result> cacheFixed =
        Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(10))
            .build();

    public Result getResultGood(String key) {
        return cacheFixed.get(key, this::compute);  // ✅ bounded
    }
}

// ─── Object allocation pitfalls ──────────────────────────────────────

// ❌ Autoboxing in hot path → millions of Integer objects per second
public long sumBad(List<Integer> nums) {
    Long total = 0L;           // ❌ Long not long — boxes every addition
    for (Integer n : nums) {
        total += n;             // ❌ unbox n, add, rebox to Long = 2 objects
    }
    return total;
}

// ✅ Use primitives in hot paths
public long sumGood(List<Integer> nums) {
    long total = 0L;           // primitive — zero allocation
    for (int n : nums) {
        total += n;             // primitive — no boxing
    }
    return total;
}

// ❌ String concatenation in loop → N temporary String objects
public String buildBad(List<String> parts) {
    String result = "";
    for (String p : parts) {
        result += p;            // ❌ creates new String every iteration
    }
    return result;
}

// ✅ StringBuilder reuses buffer
public String buildGood(List<String> parts) {
    var sb = new StringBuilder();
    parts.forEach(sb::append);  // ✅ one object, no copies
    return sb.toString();
}

Common GC Pitfalls

// ─── Pitfall 1: Calling System.gc() manually ─────────────────────────

// ❌ NEVER do this in production code
public void afterBatchJob() {
    processAllRecords();
    System.gc();   // ❌ hint → JVM may do a Full GC → 5+ second pause
                   // Makes things worse, not better
}

// Fix: add -XX:+DisableExplicitGC to JVM flags to ignore all System.gc()

// ─── Pitfall 2: Finalizers blocking GC ──────────────────────────────

// ❌ Finalizers are deprecated and dangerous
public class ResourceBad {
    @Override
    protected void finalize() { // ❌ deprecated since Java 9
        close();   // Objects with finalizers need 2 GC cycles to collect
    }  // Finalizer queue backup = major GC pressure
}

// ✅ Use try-with-resources and AutoCloseable instead
public class ResourceGood implements AutoCloseable {
    @Override
    public void close() { cleanup(); }
}

// Called like this:
try (var res = new ResourceGood()) {
    res.use();
}  // close() called deterministically, no GC involvement

// ─── Pitfall 3: Xms != Xmx causes heap resizing overhead ────────────

// ❌ JVM starts small, resizes up → causes GC during resizing
// -Xms512m -Xmx4g   → multiple pauses as heap grows

// ✅ Set Xms = Xmx to pre-allocate heap, eliminate resize pauses
// -Xms4g -Xmx4g

// ─── Pitfall 4: Large objects bypassing Young Gen ───────────────────

// Objects larger than G1HeapRegionSize/2 are "humongous" objects
// G1 places them directly in Old Gen → skip Young entirely
// They're only collected during concurrent GC cycles → live too long

// ❌ Reading huge byte[] without chunking
byte[] hugeArray = Files.readAllBytes(path); // 200MB → direct to Old Gen

// ✅ Stream in chunks
try (var is = Files.newInputStream(path)) {
    byte[] chunk = new byte[8192];   // 8KB → stays in Young Gen, dies fast
    int read;
    while ((read = is.read(chunk)) != -1) {
        process(chunk, read);
    }
}

// ─── Pitfall 5: Metaspace leak (class loader leak) ──────────────────

// Hot-deployed apps / dynamic code generation → classes never unloaded
// Each redeploy loads more class metadata → Metaspace fills → OOM

// Diagnose:
// jcmd  VM.metaspace
// Look for: Non-class space growing unboundedly

Java 17 — GC Pitfalls
❌ Pitfall 6 — Holding references in closures

Lambda / anonymous classes capture their enclosing scope. If a long-lived object captures a large parent object, the parent can never be GC'd.

// ❌ service (large object) captured by lambda
Runnable task = () -> service.doWork();
scheduler.scheduleForever(task); // service NEVER GC'd

// ✅ capture only what you need
WorkHandle handle = service.getHandle();
Runnable task = () -> handle.execute();
❌ Pitfall 7 — Inner class retaining outer class

Non-static inner classes hold an implicit reference to their outer class instance. Common in listeners registered on long-lived objects.

// ❌ Inner class holds ref to outer Page object
class Page {
    class ClickListener { /* implicit Page.this ref */ }
}

// ✅ Static inner class — no outer reference
class Page {
    static class ClickListener { }
}

Best Practices

// ─── 1. Object pooling for expensive short-lived objects ─────────────

// Creating & GC-ing thousands of heavy objects per second wastes CPU.
// Pool and reuse them instead (e.g. Jackson ObjectMapper, ByteBuffer)

@Component
public class ObjectMapperPool {

    private final ThreadLocal<ObjectMapper> pool =
        ThreadLocal.withInitial(ObjectMapper::new);

    public String toJson(Object obj) throws JsonProcessingException {
        return pool.get().writeValueAsString(obj);  // reuses mapper per thread
    }
}

// ─── 2. Use stream / lazy evaluation to avoid materializing large lists

// ❌ Loads all 10M records into memory at once
List<Order> all = orderRepo.findAll();
long revenue = all.stream().mapToLong(Order::getTotal).sum();

// ✅ Stream directly from DB without loading everything into heap
try (Stream<Order> stream = orderRepo.streamAll()) {
    long revenue = stream.mapToLong(Order::getTotal).sum();
}  // stream auto-closed → DB cursor released

// Spring Data JPA repository:
public interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("SELECT o FROM Order o")
    @QueryHints(@QueryHint(name = "org.hibernate.fetchSize", value = "1000"))
    Stream<Order> streamAll();
}

// ─── 3. Off-heap memory for large caches ─────────────────────────────
// Caffeine, Redis, Ehcache support off-heap (direct ByteBuffer)
// Data lives outside GC-managed heap → zero GC pressure

Cache<String, byte[]> offHeapCache =
    Caffeine.newBuilder()
        .maximumWeight(500 * 1024 * 1024)   // 500 MB weight cap
        .weigher((String k, byte[] v) -> v.length)
        .expireAfterAccess(Duration.ofMinutes(30))
        .build();

// ─── 4. Prefer value types in Java 17+ (Records) ────────────────────
// Records are compact, final — JIT can optimise them aggressively

@Transactional(readOnly = true)
public List<OrderSummary> getSummaries() {
    return orderRepo.findAll().stream()
        .map(o -> new OrderSummary(o.getId(), o.getTotal()))  // record
        .toList();
}

// Record: compact, immutable, less overhead than mutable POJO
public record OrderSummary(long id, BigDecimal total) {}

Java 17 — Best Practices
✅ Allocation-friendly code
  • Use primitives over boxed types in hot paths
  • Pre-size collections: new ArrayList<>(1000)
  • Reuse StringBuilder in loops
  • Prefer String.format → formatted() or text blocks
  • Pool heavy objects (parsers, formatters) per-thread
✅ Monitoring must-haves
  • Enable GC logging in ALL environments
  • -XX:+HeapDumpOnOutOfMemoryError always on
  • Track jvm_gc_pause_seconds in Prometheus/Grafana
  • Alert on heap usage > 80% after Full GC
  • Use jcmd <pid> GC.heap_info for live inspection

# ─── Live heap diagnosis commands ───────────────────────────────────

# 1. Find the JVM process ID
jps -lv

# 2. Print heap summary (live, no dump needed)
jcmd <pid> GC.heap_info

# 3. Check class histogram (what's eating memory?)
jcmd <pid> GC.class_histogram | head -30
# Output: num  bytes   class name
#  1:   8765432  [B    byte[] arrays (often Strings)
#  2:   4321000  java.util.HashMap$Node
#  3:   3210000  com.myapp.CachedResult  ← suspiciously large!

# 4. Trigger heap dump (live)
jcmd <pid> GC.heap_dump /tmp/heap.hprof

# 5. Analyze with Eclipse Memory Analyzer (MAT) or JProfiler
#    Look for: "Leak Suspects" report → points to the culprit

# 6. Check Metaspace for class loader leaks
jcmd <pid> VM.metaspace

Quick Reference Summary

TopicKey Rule
Default collectorG1 since Java 9. You don't need to set it explicitly for most apps.
Ultra-low latencyUse ZGC (-XX:+UseZGC) on Java 17+ for <1ms pauses
Max throughput (batch)Use Parallel GC (-XX:+UseParallelGC) — accepts longer pauses
Heap sizingSet -Xms = -Xmx to eliminate heap resize pauses
ContainersUse -XX:MaxRAMPercentage=75 instead of fixed -Xmx in Docker/K8s
Full GCFull GC is almost always a problem. Investigate immediately.
System.gc()Never call it. Add -XX:+DisableExplicitGC to JVM flags.
FinalizersDeprecated since Java 9. Use AutoCloseable + try-with-resources.
Memory leaksStatic collections, ThreadLocal without remove(), caches without eviction
Large objectsObjects > G1RegionSize/2 go directly to Old Gen — avoid in hot paths
MetaspaceAlways set -XX:MaxMetaspaceSize to prevent unbounded growth
Production must-haves-XX:+HeapDumpOnOutOfMemoryError + GC logging always enabled
💡
Golden rules:
  • Start with G1 defaults — only tune after you have GC log data proving a problem
  • Most GC problems are application bugs (memory leaks, huge objects) — not GC tuning problems
  • Always enable GC logging and heap dump on OOM in production
  • Move to ZGC if p99 latency is > 200ms and heap size is > 4 GB
