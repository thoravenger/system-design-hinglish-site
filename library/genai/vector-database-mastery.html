What is a Vector Database?

A Vector Database stores data as high-dimensional numerical vectors (embeddings) and enables similarity search — finding the most semantically similar items without exact matching. Traditional databases ask "does this row equal X?". Vector databases ask "what is most similar to X?"

Traditional DB

Stores structured rows/documents. Queries use exact match, range, or full-text.

  • Query: WHERE name = 'cat'
  • Returns: exact matches only
  • "kitten" ≠ "cat" in a SQL query
  • No concept of "meaning" or "similarity"
Vector DB

Stores vectors (embeddings). Queries find nearest neighbors in vector space.

  • Query: find nearest to [0.2, -0.8, 0.5, ...]
  • Returns: semantically similar items
  • "kitten" ≈ "cat" ≈ "feline" (close in space)
  • Works across languages, modalities

// 100M docs    = 600 GB — need efficient storage + search

// ── The core problem: k-Nearest Neighbor (kNN) search ────────────────
// Given a query vector q, find k most similar vectors in dataset
//
// Brute force: compare q to EVERY vector → O(n*d)
// n=1M vectors, d=1536 dims → 1.5B multiplications per query
// Too slow! → Need Approximate Nearest Neighbor (ANN) algorithms
// ANN: trade tiny accuracy loss for 100-1000x speed gain

// Maven: com.theokanning.openai-gpt3-java:service:0.18.2
@Service
public class EmbeddingService {

    private final OpenAiService openAiService;

    // Single text embedding
    public float[] embed(String text) {
        EmbeddingRequest req = EmbeddingRequest.builder()
            .model("text-embedding-3-small")
            .input(List.of(text))
            .build();
        EmbeddingResult result = openAiService.createEmbeddings(req);
        List<Double> embedding = result.getData().get(0).getEmbedding();
        // Convert to float[] for storage efficiency
        float[] vec = new float[embedding.size()];
        for (int i = 0; i < embedding.size(); i++) vec[i] = embedding.get(i).floatValue();
        return vec;
    }

    // Batch embedding — more efficient
    public List<float[]> embedBatch(List<String> texts) {
        EmbeddingRequest req = EmbeddingRequest.builder()
            .model("text-embedding-3-small")
            .input(texts)
            .build();
        return openAiService.createEmbeddings(req)
            .getData().stream()
            .map(e -> toFloatArray(e.getEmbedding()))
            .toList();
    }
}

Java 17 — Embeddings
Chunking Strategy

Long documents must be split into chunks before embedding. Chunk size matters enormously.

  • Fixed size: 512 tokens, 50% overlap
  • Semantic: split at sentences/paragraphs
  • Recursive: try paragraph → sentence → word
  • Overlap prevents context loss at boundaries
Normalization

Most models output vectors that benefit from L2 normalization (unit length = 1).

  • Normalized: cosine similarity = dot product
  • Faster: no sqrt needed in distance calc
  • Always normalize for cosine similarity
  • Don't normalize for Euclidean distance
Dimensionality
  • 384 dims: fast, small, good for simple tasks
  • 768 dims: balanced, most popular
  • 1536 dims: high quality, OpenAI default
  • 3072 dims: best quality, 2x storage cost
  • Matryoshka models: truncate to smaller dim!

Similarity Metrics — Cosine, Dot Product, Euclidean

// ── The 3 main distance/similarity metrics ───────────────────────────

// ── 1. Cosine Similarity ─────────────────────────────────────────────
// Measures ANGLE between vectors (ignores magnitude)
// Range: -1 (opposite) to +1 (identical)
// Best for: text similarity, semantic search
// Formula: cos(θ) = (A·B) / (|A| * |B|)

double cosineSimilarity(float[] a, float[] b) {
    double dot = 0, normA = 0, normB = 0;
    for (int i = 0; i < a.length; i++) {
        dot   += a[i] * b[i];
        normA += a[i] * a[i];
        normB += b[i] * b[i];
    }
    return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
// If vectors are normalized (|v| = 1):
// cosine_similarity = dot_product  (faster!)

// ── 2. Dot Product ────────────────────────────────────────────────────
// Measures BOTH angle AND magnitude
// Range: -∞ to +∞
// Best for: when magnitude matters (e.g. popularity + similarity)
// FASTEST computation — pure multiply-add

double dotProduct(float[] a, float[] b) {
    double sum = 0;
    for (int i = 0; i < a.length; i++) sum += a[i] * b[i];
    return sum;
}

// ── 3. Euclidean Distance (L2) ────────────────────────────────────────
// Straight-line distance between two points in vector space
// Range: 0 (identical) to +∞
// Best for: image embeddings, geographic coordinates

double euclidean(float[] a, float[] b) {
    double sum = 0;
    for (int i = 0; i < a.length; i++) {
        double diff = a[i] - b[i];
        sum += diff * diff;
    }
    return Math.sqrt(sum);
}

// ── Choosing the right metric ─────────────────────────────────────────
// Text search / RAG          → Cosine (direction = meaning)
// Recommendation with scores → Dot Product (magnitude = relevance score)
// Image/spatial similarity   → Euclidean (actual distance matters)
// When in doubt              → Cosine with normalized vectors

ANN Index Algorithms — How Fast Search Works

Approximate Nearest Neighbor (ANN) algorithms sacrifice a tiny bit of accuracy for massive speed gains. Here are the 5 main approaches:

AlgorithmTypeBuild SpeedQuery SpeedMemoryRecall@10Best For
HNSWGraphSlowFastestHigh95-99%Low-latency, high-accuracy
IVF (Flat)ClusterMediumFastMedium85-95%Large datasets, batch search
IVF+PQCluster+CompressSlowFastVery low80-90%Billion-scale, GPU
LSHHashFastMediumMedium75-85%High-dim sparse vectors
Flat (brute force)NoneInstantSlowestLowest100%<10K vectors, exact results
ScaNNTree+PQSlowVery fastMedium93-97%Google-scale, GPU optimized
 
// ── IVF (Inverted File Index) — Cluster then Search ──────────────────
//
// Step 1 BUILD: K-means cluster all vectors into nlist clusters (e.g. 1024)
//               Store centroid for each cluster
//               Assign each vector to its nearest cluster
//
// Step 2 QUERY: Embed query → find nearest nprobe centroids (e.g. 16)
//               Search only those nprobe clusters (not all nlist)
//               Return top-k from searched clusters
//
// nlist=1024, nprobe=16 → search 16/1024 = 1.5% of data
// Tuning: higher nprobe → better recall but slower query
// Rule of thumb: nprobe = sqrt(nlist)

// ── LSH (Locality Sensitive Hashing) — Similar → Same Bucket ─────────
//
// Hash function designed so SIMILAR vectors → SAME hash bucket
// For cosine: random hyperplane projections
// sign(v · r) = 0 or 1 for each random vector r
// K such projections → K-bit hash
// Vectors with same K-bit hash are likely similar
// Multiple hash tables → reduce false negatives
//
// Good for: very high dimensions (10K+), sparse vectors
// Not good for: dense low-dim vectors (HNSW beats it)

// ── Product Quantization (PQ) — Compress Vectors ─────────────────────
//
// 1536-dim float32 vector = 6 KB
// Split into M=8 sub-vectors of 192 dims each
// For each sub-vector: k-means into 256 centroids (8-bit code)
// Store only centroid index: 8 × 8 bits = 8 bytes per vector!
// Compression: 6144 bytes → 8 bytes = 768x smaller
// Distance computed from lookup tables (very fast)
// Recall penalty: ~5-15% compared to exact search

HNSW — Hierarchical Navigable Small World (Deep Dive)

HNSW is the dominant algorithm used by Qdrant, Weaviate, Milvus, and pgvector. It builds a multi-layer graph where upper layers navigate quickly to the neighborhood and lower layers refine the search.

HNSW Multi-Layer Graph
Layer 2 (top) — few nodes, long-range connections (highway)
A ←————————————————————————→ F
Layer 1 (mid) — more nodes, medium connections
A ←——→ B ←——→ D ←——————→ F
Layer 0 (bottom) — all nodes, short connections (local search)
A-B-C-D-E-F-G-H-I-J (dense graph, all neighbors)
Search: Enter at Layer 2, navigate to neighborhood → Layer 1 refine → Layer 0 exact top-k 
// ── HNSW Build Parameters ─────────────────────────────────────────────
//
// M (connections per node): 4-64, default 16
// Higher M → better recall, more memory, slower build
// Memory per vector ≈ M * 8 bytes * 2 layers = M*16 bytes extra
// For 1M vectors, M=16: 256 MB extra for graph structure
//
// ef_construction (candidate list during build): 100-500, default 200
// Higher ef_construction → better recall, slower build (one-time cost)
//
// ef (search width, query-time): 10-500, default 50
// Higher ef → better recall, slower query (tune per request or globally)

// ── How HNSW Search Works Step by Step ───────────────────────────────
//
// 1. Start at the entry point (top layer, fixed per index)
// 2. Greedy search on top layer: follow edges toward query
// 3. When local minimum found: descend one layer
// 4. Continue greedy search on new layer
// 5. At layer 0: beam search with ef candidates
// 6. Return top-k from candidates
//
// Complexity: O(log N) layers × O(M * ef) nodes per layer
// In practice: 1-5ms for 1M vectors at recall@10 > 95%

// ── HNSW in Qdrant — configuration ───────────────────────────────────
// See Qdrant section below for full Java code
// hnsw_config:
//   m: 16               # connections per node
//   ef_construct: 200   # build quality
//   full_scan_threshold: 10000  # use flat search for small collections

HNSW Internals
When HNSW is Best
  • Low query latency required (<10ms)
  • High recall needed (>95%)
  • Dataset fits in RAM (graph must be in memory)
  • Frequent inserts (supports incremental)
  • Up to ~100M vectors
When NOT to Use HNSW
  • Billions of vectors (memory won't fit)
  • Memory constrained environment
  • Batch-only queries (IVF+PQ better)
  • Cold start — build is slow for large datasets
  • Use IVF+PQ or ScaNN for billion-scale

@Service
public class QdrantService {

    private final QdrantClient    client;
    private final EmbeddingService embedder;
    private static final String   COLLECTION = "documents";

    // ── Create collection with HNSW config ───────────────────────────
    public void createCollection() throws ExecutionException, InterruptedException {
        client.createCollectionAsync(
            CreateCollection.newBuilder()
                .setCollectionName(COLLECTION)
                .setVectorsConfig(VectorsConfig.newBuilder()
                    .setParams(VectorParams.newBuilder()
                        .setSize(1536)                        // OpenAI dimensions
                        .setDistance(Distance.Cosine)
                        .build())
                    .build())
                .setHnswConfig(HnswConfigDiff.newBuilder()
                    .setM(16)                               // connections per node
                    .setEfConstruct(200)                   // build quality
                    .build())
                .setQuantizationConfig(QuantizationConfig.newBuilder()
                    .setScalar(ScalarQuantization.newBuilder()
                        .setType(QuantizationType.Int8)    // 4x memory reduction
                        .setAlwaysRam(true)
                        .build())
                    .build())
                .build()
        ).get();
    }

    // ── Upsert points (insert or update) ─────────────────────────────
    public void upsertDocuments(List<Document> docs) throws Exception {
        List<PointStruct> points = docs.stream().map(doc -> {
            float[] vec = embedder.embed(doc.getContent());
            return PointStruct.newBuilder()
                .setId(PointId.newBuilder().setUuid(doc.getId().toString()).build())
                .setVectors(Vectors.newBuilder()
                    .setVector(VectorsFactory.vectors(vec)).build())
                .putAllPayload(Map.of(
                    "title",    value(doc.getTitle()),
                    "category", value(doc.getCategory()),
                    "source",   value(doc.getSource()),
                    "created",  value(doc.getCreatedAt().toString())
                ))
                .build();
        }).toList();

        client.upsertAsync(COLLECTION,
            UpsertPoints.newBuilder()
                .setCollectionName(COLLECTION)
                .addAllPoints(points)
                .build()
        ).get();
    }

    // ── Vector search with metadata filter ────────────────────────────
    public List<SearchResult> search(String query, String category, int topK)
            throws Exception {

        float[] queryVec = embedder.embed(query);

        List<ScoredPoint> results = client.searchAsync(
            SearchPoints.newBuilder()
                .setCollectionName(COLLECTION)
                .addAllVector(toList(queryVec))
                .setLimit(topK)
                .setWithPayload(WithPayloadSelector.newBuilder()
                    .setEnable(true).build())
                .setFilter(Filter.newBuilder()
                    .addMust(Condition.newBuilder()
                        .setField(FieldCondition.newBuilder()
                            .setKey("category")
                            .setMatch(Match.newBuilder()
                                .setKeyword(category).build())
                            .build())
                        .build())
                    .build())
                .setParams(SearchParams.newBuilder()
                    .setEf(128)              // higher ef → better recall
                    .setExact(false)         // ANN (not brute force)
                    .build())
                .build()
        ).get();

        return results.stream().map(sp -> new SearchResult(
            sp.getPayloadMap().get("title").getStringValue(),
            sp.getScore()
        )).toList();
    }

    // ── Scroll — iterate all points (no query vector) ─────────────────
    public void scrollAll() throws Exception {
        ScrollResponse response = client.scrollAsync(
            ScrollPoints.newBuilder()
                .setCollectionName(COLLECTION)
                .setLimit(100)
                .build()
        ).get();
        // response.getNextPageOffset() for pagination
    }

    // ── Delete by filter ──────────────────────────────────────────────
    public void deleteByCategory(String category) throws Exception {
        client.deleteAsync(
            DeletePoints.newBuilder()
                .setCollectionName(COLLECTION)
                .setPoints(PointsSelector.newBuilder()
                    .setFilter(Filter.newBuilder()
                        .addMust(matchKeyword("category", category))
                        .build())
                    .build())
                .build()
        ).get();
    }
}

pgvector — Vector Search Inside PostgreSQL

-- ── pgvector setup ────────────────────────────────────────────────────
CREATE EXTENSION IF NOT EXISTS vector;

-- Create table with vector column
CREATE TABLE documents (
    id          BIGSERIAL     PRIMARY KEY,
    content     TEXT          NOT NULL,
    category    VARCHAR(50),
    source      VARCHAR(255),
    embedding   vector(1536) NOT NULL,  -- 1536-dim vector
    created_at  TIMESTAMPTZ   DEFAULT NOW()
);

-- ── Create HNSW index (pgvector 0.5+) ─────────────────────────────────
CREATE INDEX idx_documents_hnsw ON documents
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 200);
-- ops: vector_cosine_ops | vector_l2_ops | vector_ip_ops

-- ── Create IVFFlat index (older, smaller memory) ─────────────────────
CREATE INDEX idx_documents_ivf ON documents
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);  -- lists = sqrt(row count)
-- For IVF: SET ivfflat.probes = 10;  -- higher = better recall but slower

-- ── Similarity search ─────────────────────────────────────────────────
-- Cosine distance (lower = more similar)
SELECT id, content, category,
       embedding <=> '[0.1,0.2,...,0.9]' AS distance
FROM   documents
WHERE  category = 'tech'              -- SQL filter!
ORDER BY embedding <=> '[0.1,0.2,...]'
LIMIT  10;

-- Operators:
-- <=> cosine distance   (use for cosine similarity: 1 - distance)
-- <-> L2/Euclidean distance
-- <#> negative inner product (for dot product similarity: negate result)

-- Cosine SIMILARITY (not distance):
SELECT id, content, 1 - (embedding <=> '[...]') AS similarity
FROM documents
WHERE 1 - (embedding <=> '[...]') > 0.8  -- min similarity threshold
ORDER BY similarity DESC LIMIT 10;

-- Hybrid search: vector + full-text + filters
SELECT
    d.id, d.content,
    ts_rank(to_tsvector('english', d.content), plainto_tsquery('english', 'machine learning')) AS text_score,
    1 - (d.embedding <=> '[...]') AS vector_score
FROM documents d
WHERE
    d.category = 'tech'
    AND to_tsvector('english', d.content) @@ plainto_tsquery('english', 'machine learning')
ORDER BY
    (0.7 * (1 - (d.embedding <=> '[...]')) + 0.3 * ts_rank(...)) DESC
LIMIT 10;

// ── Spring Boot + pgvector (JPA) ─────────────────────────────────────

@Entity
@Table(name = "documents")
public class DocumentEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(columnDefinition = "text")
    private String content;

    @Column(columnDefinition = "vector(1536)")
    private float[] embedding;  // pgvector maps float[] ↔ vector
}

@Repository
public interface DocumentRepository extends JpaRepository<DocumentEntity, Long> {

    @Query(value = """
        SELECT * FROM documents
        WHERE category = :category
        ORDER BY embedding <=> CAST(:queryVector AS vector)
        LIMIT :limit
        """, nativeQuery = true)
    List<DocumentEntity> findSimilar(
        @Param("queryVector") String queryVector,  // "[0.1,0.2,...]"
        @Param("category")    String category,
        @Param("limit")       int    limit
    );
}

// Service layer:
public List<DocumentEntity> searchSimilar(String query, String category) {
    float[] embedding = embedder.embed(query);
    String vecStr = toVectorString(embedding); // "[0.23,-0.84,...]"
    return documentRepository.findSimilar(vecStr, category, 10);
}

// ── Recommendation System — product similarity ────────────────────────
@Service
public class ProductRecommendationService {

    public List<Product> recommend(String productId, int topK) throws Exception {
        // 1. Get the product's embedding (already stored)
        var existing = qdrantClient.retrieveAsync(
            GetPoints.newBuilder()
                .setCollectionName("products")
                .addIds(PointId.newBuilder().setUuid(productId).build())
                .setWithVectors(WithVectorsSelector.newBuilder().setEnable(true).build())
                .build()
        ).get();

        // 2. Use "recommend by id" — Qdrant feature: no need to re-embed
        var results = qdrantClient.recommendAsync(
            RecommendPoints.newBuilder()
                .setCollectionName("products")
                .addPositive(PointId.newBuilder().setUuid(productId).build()) // similar to this
                .setLimit(topK + 1)   // +1 to exclude self
                .setWithPayload(WithPayloadSelector.newBuilder().setEnable(true).build())
                .build()
        ).get();

        return results.stream()
            .filter(r -> !r.getId().getUuid().equals(productId)) // exclude self
            .map(this::toProduct)
            .toList();
    }

    // Negative example — "more like this but NOT like that"
    public List<Product> recommendWithNegative(String likeId, String notLikeId) throws Exception {
        return qdrantClient.recommendAsync(
            RecommendPoints.newBuilder()
                .setCollectionName("products")
                .addPositive(PointId.newBuilder().setUuid(likeId).build())
                .addNegative(PointId.newBuilder().setUuid(notLikeId).build())
                .setLimit(10)
                .build()
        ).get().stream().map(this::toProduct).toList();
    }
}

RAG Pattern — Retrieval Augmented Generation

RAG solves the problem of LLMs not knowing your private data. Instead of fine-tuning, you retrieve relevant context at query time and inject it into the LLM prompt.

RAG Pipeline — Indexing Phase (one-time)
Private Docs (PDF/HTML/DB)
→
Chunk (512 tokens, 50% overlap)
→
Embed (OpenAI / local)
→
Store in Qdrant
RAG Pipeline — Query Phase (per request)
User Question
→
Embed Question
→
Vector Search top-5
→
Build Prompt
→
LLM (GPT-4)
→
Answer
// ── Complete RAG Pipeline — Java 17 ──────────────────────────────────

@Service
public class RagService {

    private final QdrantService   vectorStore;
    private final EmbeddingService embedder;
    private final OpenAiService   llm;

    // ── INDEXING PHASE ─────────────────────────────────────────────────
    public void indexDocument(String content, String source) throws Exception {
        List<String> chunks = chunkText(content, 512, 50);  // 512 tokens, 50 overlap

        List<Document> docs = IntStream.range(0, chunks.size())
            .mapToObj(i -> new Document(
                UUID.randomUUID(),
                chunks.get(i),
                source,
                "chunk-" + i
            )).toList();

        vectorStore.upsertDocuments(docs);  // embeds and stores
    }

    // ── QUERY PHASE ────────────────────────────────────────────────────
    public String answer(String question) throws Exception {

        // Step 1: Retrieve relevant context
        List<SearchResult> relevant = vectorStore.search(question, null, 5);

        // Step 2: Build augmented prompt
        String context = relevant.stream()
            .map(SearchResult::content)
            .collect(Collectors.joining("\n\n---\n\n"));

        String prompt = """
            You are a helpful assistant. Answer the question based ONLY on the
            provided context. If the answer is not in the context, say so.

            CONTEXT:
            %s

            QUESTION: %s

            ANSWER:
            """.formatted(context, question);

        // Step 3: Call LLM with context
        ChatCompletionRequest req = ChatCompletionRequest.builder()
            .model("gpt-4o")
            .messages(List.of(
                ChatMessage.builder().role("user").content(prompt).build()
            ))
            .temperature(0.1)   // low temperature for factual answers
            .maxTokens(500)
            .build();

        return llm.createChatCompletion(req)
            .getChoices().get(0)
            .getMessage().getContent();
    }

    // ── Text chunking with overlap ─────────────────────────────────────
    private List<String> chunkText(String text, int chunkSize, int overlap) {
        String[] words  = text.split("\\s+");
        List<String> chunks = new ArrayList<>();
        int step = chunkSize - overlap;

        for (int i = 0; i < words.length; i += step) {
            int end = Math.min(i + chunkSize, words.length);
            chunks.add(String.join(" ", Arrays.copyOfRange(words, i, end)));
            if (end == words.length) break;
        }
        return chunks;
    }
}

Java 17 — RAG Pipeline
RAG Best Practices
  • Chunk size: 256-512 tokens for most docs
  • Overlap: 10-15% of chunk size
  • Retrieve top 3-7 chunks (more = LLM confusion)
  • Re-rank results with cross-encoder model
  • Include source metadata in results
  • Hybrid search (vector + BM25) for better recall
Common RAG Failures
  • Chunks too large → diluted context
  • Chunks too small → missing context
  • Wrong similarity metric → poor results
  • No overlap → information lost at boundaries
  • Not filtering by tenant/user → data leakage
  • Stale embeddings after doc updates

    private final ChatClient       chatClient;
    private final EmbeddingModel   embeddingModel;

    // Index documents
    public void addDocuments(List<String> texts, String source) {
        List<Document> documents = texts.stream()
            .map(text -> new Document(text, Map.of("source", source)))
            .toList();

        TokenTextSplitter splitter = new TokenTextSplitter(512, 64, 5, 10000, true);
        List<Document> chunks = splitter.apply(documents);

        vectorStore.add(chunks); // auto-embeds and stores
    }

    // Search
    public List<Document> search(String query, String sourceFilter) {
        return vectorStore.similaritySearch(
            SearchRequest.query(query)
                .withTopK(5)
                .withSimilarityThreshold(0.75)  // min similarity score
                .withFilterExpression("source == '" + sourceFilter + "'")
        );
    }

    // Full RAG answer
    public String ragAnswer(String question) {
        return chatClient.prompt()
            .advisors(new QuestionAnswerAdvisor(vectorStore,
                SearchRequest.defaults().withTopK(5)))
            .user(question)
            .call()
            .content();
    }
}

Performance Tuning & Production Best Practices

// ── Memory planning for vector databases ─────────────────────────────
//
// Raw vector size:  1M vectors × 1536 dims × 4 bytes = 6.1 GB
// HNSW graph extra: 1M × M=16 × 8 bytes × 2 layers = 256 MB
// Payload (metadata): 1M × ~500 bytes = 500 MB
// Total: ~7 GB RAM for 1M vectors
//
// With Scalar Quantization (Int8): 6.1 GB → 1.5 GB (4x reduction)
// With Binary Quantization:        6.1 GB → 0.19 GB (32x reduction, more recall loss)
// With Product Quantization:       6.1 GB → 0.05 GB (120x reduction, biggest recall loss)

// ── Qdrant — Scalar Quantization config ──────────────────────────────
//
// quantization_config:
//   scalar:
//     type: int8         # compress float32 → int8 (4x smaller)
//     quantile: 0.99     # clip outliers
//     always_ram: true   # keep quantized vectors in RAM
//                        # full-precision on disk (rescore on top-k)
//
// Qdrant search with rescore:
// SearchPoints.params.quantization.rescore = true  # rescore top-k with full vectors

// ── Batch upsert for high ingestion ──────────────────────────────────
public void batchUpsert(List<Document> docs) throws Exception {
    int batchSize = 100;
    for (int i = 0; i < docs.size(); i += batchSize) {
        List<Document> batch = docs.subList(i, Math.min(i + batchSize, docs.size()));

        // Embed entire batch in one API call
        List<float[]> embeddings = embedder.embedBatch(
            batch.stream().map(Document::getContent).toList()
        );

        // Upsert batch to vector store
        vectorStore.upsertBatch(batch, embeddings);

        Thread.sleep(100); // rate limiting for embedding API
    }
}

// ── Caching embeddings — don't re-embed same text ─────────────────────
private final Cache<String, float[]> embeddingCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofHours(1))
    .build();

public float[] embedCached(String text) {
    return embeddingCache.get(text, t -> embedder.embed(t));
}

Golden rules:
  • Start with pgvector if you have PostgreSQL — add a vector DB only when you need filtering performance or >10M vectors
  • Always normalize vectors for cosine similarity — dot product on normalized = cosine, 40% faster
  • Use Matryoshka embeddings (OpenAI 3-small supports it) — can truncate to 256 dims at query time for 6x speedup
  • RAG quality depends more on chunking strategy and retrieval quality than on the LLM model
  • Quantize always in production — Int8 has <1% recall loss but 4x memory savings
