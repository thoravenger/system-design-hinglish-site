1. Context and requirements

The platform lets a team version prompts, run them against fixed test datasets, score the outputs automatically with a judge model, and block a release when answer quality drops. It is the safety net around an LLM feature, not the feature itself.

Stack: Java 25 with Spring Boot 4.1 for the control plane, PostgreSQL for prompts, datasets and scores, Kafka for evaluation jobs, Redis for rate limits and short-lived cache, object storage for raw outputs, and an LLM provider behind an interface for the judge.

2. High-level design

The platform is a control plane plus a set of async workers. The control plane owns prompts, datasets, runs and scores. Workers pull evaluation jobs from Kafka, call the LLM under test and the judge model, and write scores back. A gate service exposes one endpoint the CI pipeline calls; it returns PASS, FAIL, or NEEDS_REVIEW with the reason.

3. Prompt versioning and release gating

A prompt is a named object. Each save creates an immutable version with a content hash. Versions are tagged with an environment: candidate, stable or retired. Exactly one version per prompt is stable at a time, enforced by a partial unique index.

ConceptMeaningEnforced by
PromptNamed container with an owner and a descriptionUnique name per tenant
VersionImmutable content plus parameters (model, temperature, max tokens)Unique (prompt_id, content_hash)
TagEnvironment pointer: candidate, stable, retiredPartial unique index on (prompt_id, tag) where tag = 'stable'
DatasetCases plus a rubric and a split (dev, test, holdout)Immutable once published
RunOne evaluation of a version against a datasetUnique (version_id, dataset_id, judge_version)
Gate policyThresholds per metric, per datasetVersioned in git and stored
The holdout split is never used during development. It is scored only by the gate, once per release, so the score is not overfit to the prompt.

5. Correctness and statistics of scoring

A release gate is a measurement, so it must be reproducible and statistically meaningful. Three rules keep it honest: pins are frozen per run, judge output is structured, and the holdout score is reported with a confidence interval.

Reproducibility

  • Every run pins the prompt content hash, model name and version, temperature, max tokens, judge version, and rubric.
  • Raw model outputs are stored verbatim, so scores can be recomputed without re-calling the target.
  • Judge calls are cached by sha256(prompt + output + rubric + judgeVersion), so re-runs are cheaper and identical.
  • Structured output from the judge is validated against a JSON schema; a malformed score is retried once, then marked UNSCORED and excluded from aggregates with a visible count.

Confidence and noise

LLM judges are noisy. The gate uses a paired comparison on the same cases: candidate and stable are scored on the identical case set, and the decision uses a paired bootstrap over 1,000 resamples.

public record GateDecision(boolean pass, boolean needsReview,
                           double delta, double lowerBound, double upperBound,
                           List<String> reasons) { }

@Service
public class PairedGate {

    private final Random random = new Random(42); // seeded for reproducibility

    public GateDecision decide(List<Double> candidate, List<Double> baseline,
                               Policy policy) {
        if (candidate.size() != baseline.size()) {
            throw new IllegalArgumentException("paired sets must be equal size");
        }
        int n = candidate.size();
        List<Double> deltas = new ArrayList<>(n);
        for (int i = 0; i < n; i++) {
            deltas.add(candidate.get(i) - baseline.get(i));
        }
        double observed = mean(deltas);

        List<Double> bootstrapped = new ArrayList<>(1000);
        for (int b = 0; b < 1000; b++) {
            double sum = 0;
            for (int i = 0; i < n; i++) {
                sum += deltas.get(random.nextInt(n));
            }
            bootstrapped.add(sum / n);
        }
        Collections.sort(bootstrapped);
        double lower = bootstrapped.get(25);   // 2.5th percentile
        double upper = bootstrapped.get(975);  // 97.5th percentile

        List<String> reasons = new ArrayList<>();
        if (observed < -policy.maxDrop()) {
            reasons.add("weighted score dropped %.2f%%".formatted(observed * 100));
        }
        if (lower < -policy.maxDropWithConfidence()) {
            reasons.add("lower bound of the drop is %.2f%%".formatted(lower * 100));
        }
        boolean pass = reasons.isEmpty();
        return new GateDecision(pass, false, observed, lower, upper, reasons);
    }

    private double mean(List<Double> xs) {
        return xs.stream().mapToDouble(Double::doubleValue).average().orElse(0);
    }
}

Handling unscored cases

If more than 2% of cases fail to score, the run is marked PARTIAL and the gate returns NEEDS_REVIEW instead of PASS. This prevents a release passing on a run where the judge silently failed on the hard cases.

Judge worker

@Service
public class JudgeWorker {

    private final JudgeClient judge;
    private final JudgeCache cache;
    private final ScoreValidator validator;
    private final ScoreRepository scores;
    private final ObjectMapper json;

    public JudgeWorker(JudgeClient judge, JudgeCache cache, ScoreValidator validator,
                       ScoreRepository scores, ObjectMapper json) {
        this.judge = judge;
        this.cache = cache;
        this.validator = validator;
        this.scores = scores;
        this.json = json;
    }

    @Transactional
    public void score(ScoringJob job) {
        String key = cacheKey(job);
        Optional<JudgeScore> hit = cache.get(key);
        JudgeScore score = hit.orElseGet(() -> {
            String prompt = Rubric.render(job.rubric(), job.caseInput(), job.output());
            String raw = judge.complete(prompt, job.judgeVersion()).text();
            JudgeScore parsed = validator.validateOrThrow(raw);
            cache.put(key, parsed, Duration.ofDays(30));
            return parsed;
        });
        scores.insert(new ScoreRow(job.runId(), job.caseId(), job.judgeVersionId(),
                                    score, job.outputHash(), Instant.now()));
    }

    private String cacheKey(ScoringJob job) {
        String material = job.rubric().id() + "|" + job.outputHash() + "|"
                        + job.judgeVersionId() + "|" + job.caseInputHash();
        return "judge:" + Hashing.sha256Hex(material);
    }
}

Gate service

@Service
public class GateService {

    private final RunRepository runs;
    private final ScoreRepository scores;
    private final PolicyLoader policies;
    private final PairedGate gate;

    public GateService(RunRepository runs, ScoreRepository scores,
                       PolicyLoader policies, PairedGate gate) {
        this.runs = runs;
        this.scores = scores;
        this.policies = policies;
        this.gate = gate;
    }

    public GateDecision check(UUID promptId, UUID candidateVersionId) {
        Run stable = runs.latestStableOnHoldout(promptId)
                .orElseThrow(() -> new NoStableBaselineException(promptId));
        Run candidate = runs.latestOnHoldout(candidateVersionId)
                .orElseThrow(() -> new RunNotScoredException(candidateVersionId));

        if (candidate.partialFraction() > 0.02) {
            return GateDecision.needsReview("more than 2% of cases unscored");
        }

        List<Double> a = scores.weightedByCase(candidate.id());
        List<Double> b = scores.weightedByCase(stable.id());
        Policy policy = policies.forPrompt(promptId);

        GateDecision decision = gate.decide(a, b, policy);
        if (!decision.pass() && decision.needsReview()) {
            return decision;
        }
        if (!decision.pass()) {
            return decision;
        }
        // Safety blocker overrides the aggregate: any safety case below 4 fails the gate.
        if (scores.anySafetyBelow(candidate.id(), 4)) {
            return GateDecision.fail("a safety case scored below 4");
        }
        return decision;
    }
}

10. Judge model and scoring design

The judge is a stronger model pinned by version. It receives the case input, the output under test, the rubric, and a strict output schema. It returns four scores and a one-line justification. Every score is traceable to the judge version and the rubric version.

Score validator

@Component
public class ScoreValidator {

    private final JsonSchema schema;
    private final ObjectMapper json;

    public ScoreValidator(JsonSchema schema, ObjectMapper json) {
        this.schema = schema;
        this.json = json;
    }

    public JudgeScore validateOrThrow(String raw) {
        JsonNode node;
        try {
            node = json.readTree(raw);
        } catch (Exception e) {
            throw new MalformedJudgeOutputException("not valid JSON", e);
        }
        List<String> errors = schema.validate(node);
        if (!errors.isEmpty()) {
            throw new MalformedJudgeOutputException(String.join("; ", errors));
        }
        return new JudgeScore(
            node.get("groundedness").asInt(),
            node.get("correctness").asInt(),
            node.get("safety").asInt(),
            node.get("tone").asInt(),
            node.get("justification").asText());
    }
}

Calibration with human labels

The judge is trusted only when it agrees with humans. A stratified sample of cases is reviewed blind, and Cohen's kappa is computed per axis. If kappa is below 0.80, the rubric is refined and a new judge version is created; the old version is deprecated but kept for reproducibility.

@Component
public class KappaCalculator {

    /** Weighted Cohen's kappa for ordinal 1-5 scores. */
    public double kappa(List<Integer> a, List<Integer> b) {
        if (a.size() != b.size() || a.isEmpty()) {
            throw new IllegalArgumentException("paired non-empty lists required");
        }
        int n = a.size();
        int k = 5;
        double[][] m = new double[k][k];
        for (int i = 0; i < n; i++) {
            m[a.get(i) - 1][b.get(i) - 1] += 1.0;
        }
        double total = n;
        double observed = 0;
        for (int i = 0; i < k; i++) observed += m[i][i];
        observed /= total;

        double[] row = new double[k];
        double[] col = new double[k];
        for (int i = 0; i < k; i++) {
            for (int j = 0; j < k; j++) {
                row[i] += m[i][j];
                col[j] += m[i][j];
            }
        }
        double expected = 0;
        for (int i = 0; i < k; i++) expected += (row[i] / total) * (col[i] / total);

        return (observed - expected) / (1 - expected);
    }
}

Security and compliance

  • Tenant isolation at the row level with a tenant id on every table and a row-level security policy.
  • OAuth2 with short-lived tokens; only prompt owners can move the stable tag.
  • Raw outputs may contain PII from production traces; the platform stores them encrypted and redacts PII before any judge call.
  • Every tag move, gate decision and human label is written to an append-only audit log.
  • Retention: scores kept for two years, raw outputs for ninety days, audit log for seven years.

13. Interview questions and model answers

1. How do you make an evaluation reproducible?

Every run pins the prompt content hash, the target model name and version, the temperature and max tokens, the judge version, and the rubric. Raw outputs are stored verbatim, so scores can be recomputed without re-calling the target. The judge cache is keyed by content hash so a re-run is identical.

2. Why use a paired comparison instead of comparing averages?

A paired comparison scores candidate and baseline on the same cases, then looks at the per-case difference. This removes case difficulty as a source of noise and gives a tighter confidence interval, so a small real drop is detected without flagging random variation.

3. How do you stop the gate from blocking releases on noise?

The gate uses a paired bootstrap and only fails when the lower bound of the drop crosses the policy threshold. It also returns NEEDS_REVIEW instead of FAIL when the run is partial or the judge is not trusted, so a flaky platform does not silently block work.

4. What if the judge disagrees with humans?

The judge is trusted only after calibration. A stratified sample is reviewed blind, and Cohen's kappa is computed per axis. If kappa is below 0.80, the rubric is refined and a new judge version is created. Old judge versions stay pinned for reproducibility.

5. How do you prevent overfitting to the test set?

The dataset has three splits: dev, test and holdout. Developers iterate on dev and test. The holdout is scored only by the gate, once per release, and its score is what the decision uses. If the holdout is ever used during development, it is retired and a new one is drawn.

6. How do you keep judge cost under control?

Three things: the judge cache keyed by content hash, batching small cases into one judge call, and a small model for format checks before the strong judge. The gate budget is a hard target of $0.50 per full run.

7. What happens when the judge model is upgraded?

A new judge version is created and calibrated against human labels. Runs pinned to the old judge version keep their scores. The gate compares candidate and baseline using the same judge version, so a judge change is never mixed with a prompt change.

8. How do you handle malformed judge output?

The judge output is validated against a JSON schema. A malformed score is retried once; if it still fails, the case is marked UNSCORED. If more than 2% of cases are unscored, the run is PARTIAL and the gate returns NEEDS_REVIEW, never PASS.

9. How would you handle 100 times the evaluations?

Partition Kafka by run id and scale worker pools. Batch judge calls where the rubric allows. Tier raw outputs to cold storage. Partition scores by month and keep rollups for the dashboard. The gate stays a fast read against the rollup plus a bootstrap on the holdout.

10. How do you roll back a bad prompt that passed the gate?

The stable tag points to a version. Rolling back moves the tag to the previous stable version; it is one row update with a unique index guaranteeing a single stable. All runs reference the old version by id, so history is intact.
